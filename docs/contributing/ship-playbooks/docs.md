# Docs playbook

Loaded by `ship-next` for `area:docs` issues, and for any diff touching code that some doc's `covers:` maps to. The documentation-quality system ([`docs-quality-system.md`](../docs-quality-system.md)) is the standard — this playbook just points at it.

- **Front-matter.** Every doc under `docs/` (and the root gravity files) carries `owner` / `status` / `covers` / `last-verified`. `npm run docs:check` must pass; add front-matter to any new doc.
- **Acceptance gate (hard).** Any diff touching Markdown, `docs/`, `scripts/docs/`, or a gravity file must pass `npm run docs:check` and `npm run docs:test` locally before the PR opens — same standing as tests and type checks (see [Acceptance Gate](../../../.agents/skills/ship-next/SKILL.md#acceptance-gate)).
- **Coupling gate.** When a PR changes code a doc's `covers:` maps to without touching the doc, the gate flags it. Run `npm run docs:coupling` — the strict, CI-equivalent form; the bare `node scripts/docs/coupling-gate.mjs` is advisory-only and always exits 0, so it will not tell you what CI says. A doc marked `contract: true` is **blocking** and must be resolved in the same PR; the rest are advisory — confirm-or-update each and bump its `last-verified`. Only bump the date when you actually re-read the doc: a rubber-stamped `last-verified` is worse than a stale one, because the weekly staleness audit ranks on it.
- **A third class since [#2323](https://github.com/d-hinders/Haven-AI/issues/2323): *"Parent docs cleared by a shard — body not re-read"*.** A contract doc whose `satisfied-by:` glob your new CASP shard matched. It does **not** block, it needs no edit, and the shard really did satisfy the coupling requirement — it is listed because you wrote that shard, so it certifies itself, and nothing has re-read the parent's body against your diff. Re-read the sections the comment names against the files it names. Before #2323 such a doc was omitted from the comment altogether, which is how #2274 (PR #2322) shipped a false CASP sentence past a green tick: the shard was correct and `casp-risk-guardrails.md` still described an ordering that same diff had removed. "Still accurate, not edited" written into the PR is a legitimate outcome here — the point is that somebody looked.
- **Chain, never choose ([#1843](https://github.com/d-hinders/Haven-AI/issues/1843)).** Two notes on one `last-verified` line are two findings about that file, not two drafts of one. `docs:check` fails when a doc's new `last-verified` line has lost an issue reference its previous one carried — the shape a conflict resolution takes when it picks a side, which deletes the paragraph that entry pointed at and passes every other gate. A deliberate compaction writes `chain-reset(#<issue>): <why>` on the line. Rule and reasoning: [`docs-quality-system.md`](../docs-quality-system.md#last-verified-chain-integrity-1843).
- **No test assertions over freeform prose ([#2163](https://github.com/d-hinders/Haven-AI/issues/2163)).** Guard the code that *generates* agent-facing text; for hand-maintained prose, a blanket `not.toContain(<literal>)` is acceptable where the file has no legitimate use of the literal. An assertion that must *interpret a sentence* is out of scope — human review is the control there. The line is prose-interpretation, not string-matching: this is never a licence to drop cheap literal guards. Full rule, its stopping-rule sibling, and the evidence: [ship-next § Rework caps](../../../.agents/skills/ship-next/SKILL.md#rework-caps-2163).
- **haven-doc-reviewer (hard step).** When the diff touches `covers:`-mapped code, running it is a definition-of-done step, not optional: review and update the implicated docs in the same PR before opening it (see [Independent Review](../../../.agents/skills/ship-next/SKILL.md#independent-review)).
