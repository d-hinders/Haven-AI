# Frontend playbook

Loaded by `ship-next` for `area:frontend` issues. The goal: a UI issue is shipped on Haven's UX standards without the contributor having to name them. This playbook **links** the standards; it does not restate them.

## 1. Required reading (before implementing)

Read, in order — these are `AGENTS.md` → "Required Reading For UI Work":

1. [`product/README.md`](../../product/README.md) — product doctrine, IA, money-movement clarity, accessibility, and closeout checks.
2. [`product/design-system.md`](../../product/design-system.md) — tokens, typography, cards, buttons, motion, surface hierarchy.
3. [`product/copy-guidelines.md`](../../product/copy-guidelines.md) — user-facing wording and banned technical terms.
4. [`product/screen-recipes.md`](../../product/screen-recipes.md) — repeatable screen structures.
5. [`product/design-review.md`](../../product/design-review.md) — the finishing checklist (also used in §5).

If a `/design-system` route exists, inspect it before editing UX.

## 2. Reuse first

Inspect `packages/frontend/src/components/ui` (primitives) and `packages/frontend/src/components/haven` (domain components) before adding UI. Prefer composition; do **not** invent new card styles, spacing, shadows, radius, or typography unless the existing system genuinely can't express the need. Use the v2 tokens in `globals.css` and the Tailwind aliases.

**Absorb a pattern on its 2nd occurrence, not its 12th ([#901](https://github.com/d-hinders/Haven-AI/issues/901)).** If this diff writes the same markup shape a second time — a header band, badge, row, empty-state, inline `<svg>`, address slice — or re-creates something a primitive already covers, extract it into a `ui/`/`haven/` primitive **and** document it on `/design-system`, in this same PR. This is the Captain Self-Check Preflight's **Pattern Absorption** item; it's the mechanism that prevents the debt clusters epic #859 had to clean retroactively. Only skip it if the two uses will genuinely diverge — and say so.

**A new primitive must land on `/design-system` in the same PR ([#898](https://github.com/d-hinders/Haven-AI/issues/898)).** The design-system coupling gate flags any exported component added under `components/ui/**` or `components/haven/**` whose symbol never appears on `app/(authenticated)/design-system/page.tsx`. Two CI jobs, on every PR however it was opened ([#1023](https://github.com/d-hinders/Haven-AI/issues/1023)): **Design-system coupling** posts the sticky comment that explains the finding, and **Design-system coupling (strict)** blocks on it. Add a showcase entry (usage + variants) alongside the primitive, or — for a genuinely internal export, not a reusable primitive — mark the export line `// design-system-exempt: <reason>`. Check locally with `npm run design:coupling:strict -w packages/frontend`, which is the invocation CI runs — see § *Verification* for what its scope covers ([#2826](https://github.com/d-hinders/Haven-AI/issues/2826)).

## 3. Captain Self-Check Preflight

Run the matching items from the **Captain Self-Check Preflight** in [`../ai-agent-workflow.md`](../ai-agent-workflow.md) for the traps the diff touches — e.g. numeric formatters, counter/summary buckets, conditional copy predicates, async hook generations, signer-readiness gates, animation discipline, inline-gate placement, cross-surface display drift, loading-state inference. Each is one grep or one quick read. Do this **before** review so the reviewer finds fewer issues.

## 4. Verification

Verify the change in the **browser**, or — when the browser path is unavailable/flaky — add a **named headless equivalent** (vitest) that covers the skipped animation, layout, routing, loading, or interaction risk. Include empty, loading, error, and success states when the screen can enter them; check mobile and desktop.

**Which viewports actually gate ([#1768](https://github.com/d-hinders/Haven-AI/issues/1768)).** The *Frontend browser smoke* job runs **both** Playwright projects on every frontend PR, with no dispatch required:

| Project | Emulation | Runs | Gates a PR |
|---|---|---|---|
| `chromium-desktop` | Desktop Chrome — 1280×720 viewport, fine pointer, no touch, DSF 1 | every `e2e/*.spec.ts` **except** `*.mobile.spec.ts` | yes |
| `chromium-mobile` | **Pixel 5** — 393×727 viewport, coarse pointer, touch, Android UA, DSF 2.75 | `e2e/*.mobile.spec.ts` only | yes |

(Numbers read off Playwright's own `devices` table at the pinned version, not from memory. Pixel 5's `screen` is 393×851; the **viewport** — what the page actually gets — is 393×727.)

Both projects also inherit `SUITE_IGNORE` (`e2e/live/**`, and `*.visual.spec.ts` unless `VISUAL_REGRESSION=1`). That constant exists because a project-level `testIgnore` **replaces** the config-level one instead of extending it — a project that declares its own must spread `SUITE_IGNORE` back in, or the unmocked live smoke silently rejoins the fast suite.

Plus the separate *Design visual regression* job. It pixel-compares **every** `*.visual.spec.ts`, not `/design-system` alone — `/design-system` at **1280** and **390** (`scripts/evidence-viewports.mjs`), element-scoped clips on `/agents`, and whole-page captures of `/dashboard` and `/transactions` ([#2318](https://github.com/d-hinders/Haven-AI/issues/2318)) — but under `chromium-desktop` at DSF 1, by setting the viewport inside the spec. That is a pixel gate, not a device gate: it sees layout, never touch or hit-testing.

Before #1768, `chromium-mobile` existed but only a `workflow_dispatch` with `ui_suite=full` ever ran it — so **no mobile viewport gated anything**, which is a large part of why [#1749](https://github.com/d-hinders/Haven-AI/issues/1749) (primary navigation unopenable below `lg`) shipped. That input is now removed and both projects are unconditional.

**Writing a mobile test:** name the file `*.mobile.spec.ts` and it runs under real Pixel 5 emulation. Do **not** reach for `test.use({ viewport: … })` inside a desktop spec — it narrows the window but leaves `maxTouchPoints` at 0, the pointer fine and the UA desktop, so touch and hit-testing behaviour is not actually covered. Conversely, keep viewport-independent behaviour out of `*.mobile.spec.ts`: the two projects run disjoint spec sets on purpose, and duplicating a spec buys nothing but CI minutes. `e2e/navigation.mobile.spec.ts` is the reference, including the meta-guard that fails if the project ever stops being device-emulated.

**Measure overflow on the scroll box, not the document.** The authenticated shell is `overflow-hidden`, so content wider than the screen never grows `documentElement.scrollWidth` — which meant the page-level `expectNoHorizontalOverflow` helper **could not fail** on any authenticated route. Found by the #1768 mutation, not by reading, and fixed in [#1771](https://github.com/d-hinders/Haven-AI/issues/1771): the shared helper now measures `<main id="main-content">`'s own scroll box alongside the document, and `hasOverflow` is the union, so every caller gates for real. Assert `contentRegionFound: true` on authenticated routes — otherwise a `<main>` that is missing or not yet laid out measures `0` and reads as "fits".

Two failure modes, and they are not the same defect: `documentOverflows` means content escaped the page box and — under the shell's `overflow-hidden` — is genuinely **unreachable**; `contentOverflows` means `<main>` (which is `overflow-y-auto`, so `overflow-x` computes to `auto`) is wider than its box, dragging the **whole content pane into horizontal scroll** instead of the offending element scrolling inside its own `overflow-x-auto` wrapper. The second is reachable but wrong — it is the [#1772](https://github.com/d-hinders/Haven-AI/issues/1772) shape. Note the measurement compares two scroll boxes rather than walking ancestors, so an `overflow-hidden` *between* them still hides evidence; `position: fixed` overlays are invisible to both, which is why an open dialog needs its own measurement ([#1773](https://github.com/d-hinders/Haven-AI/issues/1773), below).

**A spec that opens a dialog and then asserts overflow is measuring the page BEHIND it — assert the overlay separately ([#1773](https://github.com/d-hinders/Haven-AI/issues/1773)).** A `position: fixed` element is laid out against the viewport, so it contributes to the scrollable overflow of neither the document nor `<main>`, and an ancestor's `overflow-hidden` does not clip it either. Measured: a `w-[120vw]` block inside `ReceiveFundsModal` left the assertion green. Use `measureDialogOverflow` beside `expectNoHorizontalOverflow` — a sibling, deliberately not a widened `hasOverflow`, because most callers never open a dialog and unioning would make "no dialog open" read the same as "the dialog fits". Assert `dialogFound` along with `overlayOverflows`, for the same reason authenticated routes assert `contentRegionFound`.

**And measure the whole subtree, not the dialog node.** The obvious anchor — `[role="dialog"]`'s own scroll box — fires on only ONE of the three dialogs, which was found by measuring rather than by reasoning. `ui/Modal` puts `role="dialog"` on the `fixed inset-0` container (so its `clientWidth` is the whole viewport) and `ui/SidePanel` wraps a `flex-1 overflow-y-auto` body; per CSS Overflow §3 that body's `overflow-x` computes to `auto`, so the body is itself a horizontal scroll box, absorbs the overflow and never propagates it outward. Under the same 120vw mutation the dialog node read `0` on both while the nested body read 1129 and 1010. Scanning every box in the subtree also removes the reliance on upward propagation that makes an intermediate `overflow-hidden` a blind spot in the first place. The viewport-absolute numbers are reported and not asserted, per the rule below: the three overlays have three different correct positions, and the side panel's flush right edge read 1280, 1281 and 1282 across three runs at a 1280px viewport.

**A legitimate horizontal scroller inside one of those dialogs will fail these specs, and the obvious fix for that is wrong.** The scan flags any box wider than its own content box; it does not ask whether the box meant to scroll. Excluding elements whose computed `overflow-x` is `auto`/`scroll` looks like the answer and is measurably not: `overflow-y-auto` computes `overflow-x` to `auto`, so that rule exempts `ui/Modal`'s and `ui/SidePanel`'s scrolling bodies — the exact elements that caught two of the three mutation proofs. It would gut the guard, not narrow it. A class-name rule fails the mirror image: it exempts a real defect that happens to carry the class. So exempt the known case **by name at the call site with an issue number**, the way `KNOWN_CONTENT_OVERFLOW` does — assert `offenderCount` and match `worstOffender`, which keeps the check gating on everything else instead of deleting it. A worked example is in the helper's JSDoc.

One trap if you write any subtree-scanning overflow check: **a visually-hidden element reports a large horizontal overflow and is not a defect.** Tailwind's `sr-only` is `width: 1px; height: 1px; overflow: hidden; clip: rect(0,0,0,0)`, so its `scrollWidth` is the full width of the screen-reader text against a `clientWidth` of 1 — the connect modal's `span.sr-only` reported 67px. Exclude it by geometry (skip boxes 1px or narrower), never by matching the class name, which would exempt a real defect that happened to carry the class. Found on the restore half of the mutation proof, which is the half that is easy to skip: the mutation going red says the guard can fire, and only the restore says it fires *for the right reason*.

**Relative measurement is not sufficient for shell-level geometry — anchor at least one assertion to the viewport ([#1779](https://github.com/d-hinders/Haven-AI/issues/1779)).** Any assertion of the form "A relative to B" is blind to A and B moving together, and a shell-level defect moves everything at once. Measured, not argued: mutating the mobile toggle's `fixed` to `relative` drops it into flow as a 32px flex item and displaces the entire app shell — `<header>` and `<main>` both go from x=0 to x=32 — and **three separate mobile specs stayed green**, because the toggle was checked against the header, layering as one element against another, and overflow as a content box against its own scroll box. `contentOverflowBy` still read `361 - 361 = 0`, exactly as it had read `393 - 393 = 0`. No rewording of an individual assertion fixes this; it is a property of the reference frame. So a mobile-shell suite needs at least one measurement against something the defect cannot carry with it — `getBoundingClientRect()` against `window.innerWidth`. The three suites now each carry their own: `header.left === 0` (#1766), the top bar's two viewport gaps (#1749's layering spec), and `<main>` spanning `0 → innerWidth` (#1771's overflow guard, via `contentLeft`/`contentRight`/`viewportWidth` reported — not asserted — by the shared helper, because the mobile shell, the desktop shell and `/login` have three different correct answers).

Two traps this generalises into, both paid for already. **Deliberately do not collapse the anchors into one shared helper every suite calls** — one shared reference frame that everything trusts is the defect itself, one layer up; independent anchors can disagree, a single one cannot. And **an anchor is only real once the mutation has turned that specific spec red**: the first version of the `<main>` anchor above passed the mutation on 3 of 4 routes, because `Sidebar` is `dynamic(ssr: false)` and the measurement ran before it rendered, leaving `<main>` at x=0 — the same silent-no-op shape `contentRegionFound` exists for. Wait for the shell (the `Open sidebar` toggle) before measuring it.

**A known, filed defect is exempted by name, never by deletion.** `navigation.mobile.spec.ts` keeps a `KNOWN_CONTENT_OVERFLOW` map: the route still runs and still asserts rendering and console cleanliness, only the one known-failing assertion is skipped, and only with an issue number and the measured numbers next to it. Dropping the route instead is how a gate quietly stops covering things — which is the defect #1768 exists to close. Delete the entry in the PR that fixes the issue.

**A guard proven at 1280px is not proven ([#1797](https://github.com/d-hinders/Haven-AI/issues/1797)).** `measureDialogOverflow` shipped with three call sites and three mutation proofs, all under `chromium-desktop` — the width where a dialog is *least* likely to overflow. The helper was viewport-agnostic and correct; the coverage was upside down. When you add an assertion about layout, ask which viewport its defect actually lives at, and put the spec there.

Two things that measurement showed and reasoning would not, both worth knowing before you reuse a desktop proof at mobile width:

- **The same mutation is a different size.** A `w-[120vw]` block inside `ReceiveFundsModal` reads `overlayOverflowBy: 1026` at 1280 and **137** at 393 — `120vw` is viewport-relative and the panel's own scroll box clamps it. A proof at one width is not evidence at the other, and the gap is roughly 7.5×.
- **The viewport-absolute pins catch what the overflow metric structurally cannot.** At 393 the panel is `mx-4 w-full` with `max-w-lg` no longer binding, so `dialogLeft`/`dialogRight` are a *knowable* 16 → 377 and can be asserted — unlike at desktop, where the three overlays have three different correct positions. Mutating `mx-4` → `mx-0` turns `dialogLeft` red while `overlayOverflows` stays false: a panel flush against both bezels overflows nothing. That is [#1779](https://github.com/d-hinders/Haven-AI/issues/1779)'s rule one layer down — `scrollWidth` vs `clientWidth` compares a box to itself and cannot see the box move.

Run them locally with `npm run test:e2e:mobile -w packages/frontend`, or both with `npm run test:e2e:gate -w packages/frontend` (the same projects and specs CI runs, though on a dev server rather than CI's built one — see below).

**Run the loop against a BUILT server, not `next dev`.** Both scripts above spawn `next dev`, which compiles each route on first request; CI never pays that, because `playwright.config.ts` assembles the standalone tree and boots `server.js` when `CI` is set. Three `:built` scripts take that path locally — `test:e2e:desktop:built`, `test:e2e:mobile:built` and `test:e2e:gate:built`, mirroring their non-built twins:

```bash
npm run test:e2e:mobile:built -w packages/frontend   # or test:e2e:gate:built for both projects
```

They exist as scripts rather than as a recipe here because two details are easy to get wrong by hand and silent when you do. **They rebuild every time**, deliberately: a stale build serves a frozen bundle, and the #1816 identity probe cannot see that — `scripts/e2e-identity.mjs` says so in its own docblock, because the marker proves *this worktree's files* while the bundle beside it may be an old compile. That is the [#1800](https://github.com/d-hinders/Haven-AI/issues/1800) confidently-wrong shape, one surface over. And they build with `NEXT_PUBLIC_WALLETCONNECT_PROJECT_ID=ci-placeholder`, matching `ci.yml`: `NEXT_PUBLIC_*` is inlined at build time, the placeholder is truthy, so **CI's bundle carries the `walletConnect` connector and a bare local build does not**.

Measured on one laptop at [`1baaa36d`](https://github.com/d-hinders/Haven-AI/commit/1baaa36d), `chromium-mobile`, both at `--workers=1`: the suite is **41.1s** built against **3.5 min** (~210s) on `next dev` — about 5× — and the `:built` scripts rebuild every time, so one end-to-end run is 41.1 + 56 ≈ **97s against 210s**, about 2.2×. The 5× is the figure for the suite alone, which is what you get while iterating on specs against a single build (`CI=1 npx playwright test …`, no rebuild). The whole gate — both projects, 104 tests — is **58s** built, 1:35 with the rebuild. Re-derive on your own machine before quoting; what generalises is the ratio, not the seconds. `CI=1` also pins `workers` to 2 (the local default is roughly half your cores) and turns on `forbidOnly` and one retry, so **a deliberately serial run still needs `--workers=1`** — the figures above are at equal workers for exactly that reason.

**A contended `next dev` run does not fail like a regression, and telling them apart is worth one serial re-run.** Its signature: many failures, spread across specs the diff never touched, including assertions that cannot fail for a substantive reason (`navigation.mobile.spec.ts`'s device-emulation meta-guard, which can time out but whose assertions are all about the project config), and every one a `page.goto` timeout rather than a failed assertion. That is compile starvation — several workers requesting uncompiled routes from one dev server, each waiting past the 60s test timeout. It is the same cold-compile cost [#2108](https://github.com/d-hinders/Haven-AI/issues/2108) measured for the capture harness below (315–448s under agent load), reaching a different tool; read together they corroborate rather than compete. When both projects ran, "all the failures are in one project" is the sharpest tell; when you ran only one, it tells you nothing. **Re-run serially, or against a built server, before touching any code — and if the serial re-run reproduces it, it is real.** On [#2730](https://github.com/d-hinders/Haven-AI/issues/2730) all 17 failures evaporated and the suite passed 36/36 (37 today; that branch predated `transaction-row`'s #2734 case). The same cause makes a laptop unusable while a suite runs, so kill *your own worktree's* leftover `next dev` before starting one — never another session's, which is what the per-worktree port reservation above exists to keep separate.

**Use `--retries=0` for mutation cells.** `CI=1` turns on one retry, and Playwright exits 0 when a test fails and then passes on the retry — reported "flaky", not "failed". A cell whose red is intermittent would therefore report a green exit, which is exactly the fidelity a mutation proof is buying. It also doubles the wall time of a genuinely contended run.

**Mutation proofs pay the fixed cost once per cell, and which cost depends on what you mutate.** A spec-only mutation re-runs against the same built bundle (~41s); a mutation to app source needs a rebuild, so budget the full ~97s per cell — still well under the ~210s a `next dev` cell costs, which is where [#2730](https://github.com/d-hinders/Haven-AI/issues/2730)'s eleven cells went. Do **not** try to hold one server open across cells. Under `CI` the run refuses at the `webServer` step, before `globalSetup` is reached, because `reuseExistingServer` is false; drop `CI` to get past that and you hit the identity probe instead, because the run's marker is copied into the standalone tree by the `webServer` command at boot, so a pre-booted server serves a stale one.

**Rendered-screen evidence is REQUIRED on three triggers, and only these three ([#2636](https://github.com/d-hinders/Haven-AI/issues/2636)):**

1. **A new route** — nothing has ever been captured, so there is no prior evidence and no baseline.
2. **A changed shared primitive** under `components/ui/*` or `components/haven/*` — the blast radius is every screen that consumes it, which is exactly what a diff does not show.
3. **A diff that changes what a screen shows** — different markup, different copy, different states, different data on the page.

**A logic-only change to an existing route takes the headless equivalent instead** — the named vitest coverage this section already defines. The test is what the *reader of the screen* would see: if the rendered output is byte-identical and only the path to it moved, a screenshot re-proves a screen nobody changed. Say which trigger applied, or say "logic-only, headless equivalent: `<test name>`", in the PR's Browser Verification section; an unfilled line is what this narrowing must not become.

**This is a deliberate narrowing. Here is what covers the gap, and — read this half — where nothing does.** Before #2636 the trigger was "touches a rendered route or a shared primitive", which caught every refactor under a route directory and made a full capture-and-review cycle the price of a renamed hook.

Both pixel jobs still **run** on any diff under `packages/frontend/`: `scripts/ci/change-classifier.mjs` matches `packages/frontend/*` as the whole subtree, so a purely logic-only change sets `frontend='true'` and *Design visual regression* and *Frontend browser smoke* both fire (`ci.yml`, `needs.changes.outputs.frontend == 'true'`). To that extent the narrowing is in what the **author must attach**, not in what CI does.

**But running is not comparing, and the difference decides whether this narrowing is safe on your route.** `design_visual` compares only what has a **committed baseline** under `e2e/__screenshots__/`, and coverage comes in three grades rather than two:

- **Whole-page**, at the viewports that spec committed: `/design-system`, `/dashboard` and `/transactions` (the last two desktop-only).
- **Element-scoped only.** `/agents` is the one to know: `agent-panel-states` and `focus-visible` both `goto('/agents')` and commit clips of the agent-card states, the empty states and the driven focus targets — real coverage, but of *elements*. A whole-page `/agents` regression outside those boxes is compared against nothing.
- **Nothing at all**: `/accounts`, `/custody`, agent detail, the connect flow.

On the last two grades, the job runs and compares nothing in the area you changed, and trigger 3 is the *only* check that a "logic-only" change really was.

Do not take that list as the current set: it moves (#2318 added two routes, #2635 is reshaping the `/design-system` captures). **The job prints what it actually compared** — `scripts/ci/visual-baseline-inventory.mjs`, in the run summary — and `git ls-files 'packages/frontend/e2e/**/*.png'` answers the same question locally. Read one of those, not this paragraph, when the answer decides whether you capture. This is the same point `CLAUDE.md` makes about the green tick being narrower than it looks.

So: on a baselined route, a misjudged trigger is caught by the gate. On an un-baselined one it is caught by nobody, and the honest instruction is to capture anyway when you are unsure. The narrowing buys back time on the routine case; it does not make self-assessment safe where there is no backstop.

Run `npm run screenshot -w packages/frontend -- <routes>` (see [#896](https://github.com/d-hinders/Haven-AI/issues/896)); it captures desktop (1280) + mobile (390) PNGs of `/design-system` plus the routes you pass, using a known auth/data fixture and the pre-installed browser. The fixture serves a deterministic **populated** dataset (a funded account, agents on both rails, transactions, contacts, agent activity and spend stats) so lists, tables and amounts render realistically — set `SCREENSHOT_FIXTURE=empty` when you specifically want empty states. The script also summarises any **console errors** per route; a red console means a fixture-shape gap or a real client bug — fix it before trusting the PNGs. **Attach the PNGs to the PR, or reference them in the Browser Verification section** — "browser or headless equivalent" is no longer sufficient on its own for a visual surface. A primitive change means shooting `/design-system` (where it's documented) *and* a route that consumes it. Screenshots live in the gitignored `.screenshots/`; the fixture is documented at the top of `scripts/screenshot.mjs`.

**Every value the fixture seeds must be one the product can actually produce ([#2120](https://github.com/d-hinders/Haven-AI/issues/2120)).** This is the same rule as §6's "establish that the state is REACHABLE", turned around: §6 is about a state the fixture *omits*, this is about a state the fixture *invents*. An invented seed is worse than an absent one, because these fixtures are the input to every design-review capture — a fabricated value does not weaken the evidence, it makes the reviewer sign off on a screen that cannot happen. #2111 caught two in its own rig (a chain fixture answering `isModuleEnabled → true` for a rail with no AllowanceModule; an agent holding a delegation with `allowances: []`, which `deriveDelegationAllowances` makes impossible); #2120 found four more in the standing seed, all approval-era — a `pending_approvals` count and an `actionableApprovals` count against routes that hardcode `0`, a `type: 'approval'` activity row against a feed that has emitted payments and tool calls only since #2055, and a `status: 'executed'` payment against a `payment_intents.status` that is only ever written `pending_signature | submitted | confirmed | failed | expired`. #2202 is the fifth, and it is the one that shows the rule has a *structural* form as well as a per-value one: `agent-ops` claimed `account_type: null` while sharing one `user_safes` row with two `delegator_hybrid` agents. `account_type` is not an agent column — every agent read selects it as `us.account_type` off a `LEFT JOIN user_safes` (`infra/repositories/agents.ts`) — so one safe answers one rail, and no backend could serve that response set whatever each row looked like on its own. The value was impossible twice over: migration `041_hybrid_accounts.ts` makes the column `NOT NULL DEFAULT 'safe'` under `CHECK (account_type IN ('safe','delegator_hybrid'))`, so `null` is outside its domain, and the only null-producing path (as of the #2120 fix — a snapshot claim, dated to that issue's resolution) — the join finding no row — nulls `safe_address`, `safe_name` and `safe_chain_id` in the same row. It rendered as a perfectly ordinary card because `railOf` reads anything-but-`delegator_hybrid` as the legacy rail. So: when several fixture rows are JOINED to one row in the real schema, check that they AGREE, not just that each is individually legal. **Pin a seed to the code that emits it** — name the route line or the write site beside it — and when you delete a fabricated state, replace it with a reachable one rather than leaving the branch it exercised uncovered (#2120 swapped the fake approval row for a real `status: 'failed'` payment, so the danger-tone badge kept its rendered evidence). The guard for the current set is `src/__tests__/screenshot-fixture.test.ts`. One value has a pin of its own because its failure mode is a SHAPE, not a number ([#2298](https://github.com/d-hinders/Haven-AI/issues/2298)): `allowance_amount` on `Agent.allowances[]` is the human-decimal projection `rails/delegation-budget-view.ts` builds with `formatTokenValue` (`'250.00'`), while the connect-setup `agent_budget[]` carries the atomic integer (`'25000000'`) under the same field name (#2295) — and the e2e fixture shipped the atomic one on the field `/agents` sends human, so a budget-amount baseline would have been green through the #2283 defect. `src/__tests__/fixture-shape-parity.test.ts` now pins the human shape across BOTH harnesses — the exported datasets structurally, every scenario-local `/agents` override by a literal scan of both files, and the screenshot rows by re-parsing to the `budget_atomic` of the delegation they project. That pin, not a PNG, is where the shape is asserted: #2378 rejected a `/agents` pixel baseline because `useOnChainAllowances.ts:48` fires an unmocked `readContract`, so the screen's content depends on how a network call resolves.

**Looking at a width the committed set does not render — 320 in particular ([#2006](https://github.com/d-hinders/Haven-AI/issues/2006)).** `npm run screenshot -w packages/frontend -- --viewport=320x568 /dashboard` shoots the widths you ask for **instead of** the committed pair, for that run only (repeatable, comma-separated, or `SCREENSHOT_VIEWPORTS=320x568`). Nothing a gate compares changes: the four gate consumers import `VIEWPORTS` from `scripts/evidence-viewports.mjs` and never the override, so no baseline moves and `npm run screenshot` with no flag captures exactly what it always did — same widths, same filenames, same pixels. (The run does gain one stdout line naming the widths, and the manifest gains `viewports` / `viewport_source` / `viewport_mismatches` on every run, overridden or not; nothing reads the manifest by strict shape.) An overridden viewport is **named after its dimensions**, so the PNGs come out as `dashboard-320x568.png` and the manifest records `viewports` + `viewport_source` — a 320px capture that is silently a 390px one is the [#1800](https://github.com/d-hinders/Haven-AI/issues/1800) defect in another axis.

Use this instead of the pattern it replaces. #1803's 320px evidence came from a **temporary spec kept out of the diff**, because at the time editing `evidence-viewports.mjs` was the only way to point the harness at a width and that file is read by four gates. That pattern worked and left no trace; the flag does the same job and says what it did.

**And do not read a 320px PNG as coverage.** [#1944](https://github.com/d-hinders/Haven-AI/issues/1944) declined to put 320 in the committed set and that decision stands: Haven has no breakpoint between 320 and 390 (Tailwind's `sm` is 640; the two container queries are at 718/974), so a 320 capture buys a picture of the same branches the mobile baseline already renders, at the cost of a blocking full-page `/design-system` baseline (~1.8 MB) plus a TopBar baseline plus a third PNG of every route in every evidence run, forever. What actually differs at 320 is **layout arithmetic**, and an overlap photographs perfectly happily ([#1858](https://github.com/d-hinders/Haven-AI/issues/1858)) — which is why 320 is gated by *measuring* specs (`mobile-nav-tap-target.mobile.spec.ts`, `mobile-nav-layering.mobile.spec.ts`, `transaction-row.mobile.spec.ts`, `navigation.mobile.spec.ts` all sweep it) and not by a baseline. The flag is for **seeing**; those specs are the coverage.

**One capture server per worktree, and it has to prove who it is ([#1800](https://github.com/d-hinders/Haven-AI/issues/1800)).** The harness used to bind a fixed port (3111) in every worktree. Concurrent sessions are the normal state of this repo, so the second run found the port already bound, got a **200 OK from the other worktree's app**, and captured it — PNGs that render, have plausible dimensions, show the right routes, and are of a **different branch**, with nothing about them saying so. That is worse than a guard that fails silently: it is positive evidence that is confidently wrong, and the `haven-design-reviewer` pass below reasons from exactly these artifacts. Two things now stand in the way, and the second is the one that lasts:

- the port is **derived from the worktree path** and proven bindable before the dev server starts (a busy port is skipped and the chosen one is printed — never inherited);
- before any PNG exists, the run fetches `/capture-identity.json` from whatever it is about to capture and **refuses unless the marker matches this run's own random token**. A 200 is not proof of identity. `SCREENSHOT_BASE_URL` and `SCREENSHOT_PORT` get the same treatment, so pointing either at the wrong server fails loudly instead of producing evidence (`SCREENSHOT_ALLOW_UNVERIFIED_SERVER=1` exists for a genuinely remote target and stamps `identity_verified: false`).

Every run also writes `.screenshots/capture-manifest.json` — worktree, branch, commit, dirty flag, port, and whether identity was verified — so a PNG can be traced back to what produced it. **For a dirty tree, `worktree_provenance` is the load-bearing claim:** its versioned SHA-256 snapshot covers the `HEAD` commit, the binary tracked diff, and every non-ignored untracked file's path/type/bytes. A bare dirty flag only says the commit is incomplete; it cannot identify what was rendered. **When you attach screenshots, the manifest is the claim that they are yours.** Mechanism: `scripts/capture-identity.mjs`. Same class from another angle, still open: [#1801](https://github.com/d-hinders/Haven-AI/issues/1801), where concurrent sessions share one scratchpad and overwrite each other's PR bodies.
**A cold worktree waits for a compile, and the harness now says so instead of timing out ([#2108](https://github.com/d-hinders/Haven-AI/issues/2108)).** `waitForServer` carried a single hardcoded 90s readiness budget against a cold `next dev` compile **measured at 315–448s under agent load** — a threshold set 3.5–5x below the thing it measured, so on a contended fresh worktree the harness could not capture at all. It failed with `dev server did not become ready … within 90000ms`, which names neither the cause nor the remedy and looks exactly like the failures that *are* signal: contention, a genuinely broken page, a `still-loading` floor refusal (#2036). That is the epic [#1440](https://github.com/d-hinders/Haven-AI/issues/1440) shape one level out — **a tool that fails for a reason unrelated to what it is measuring** — and its real cost is that it teaches agents to discount capture failures generally.

The fix is deliberately **not** a bigger constant. One 500s deadline would make a dev server that will never come up take eight minutes to say so, and print the same sentence a healthy-but-slow compile prints. Readiness is now two events with two budgets, because they have different orders of magnitude *and* different remedies:

| Phase | What it waits for | Default | Override |
|---|---|---|---|
| listen | `next dev` **binding** its port — process startup, seconds cold or warm | 90s | `SCREENSHOT_LISTEN_TIMEOUT_MS` |
| compile | that listening server **answering** — the webpack compile, the 315–448s event | ~986s (2.2x the measured maximum) | `SCREENSHOT_READY_TIMEOUT_MS` |

The spawned child is watched throughout, so a dev server that **dies** ends the wait in seconds whatever the budget, and one that dies *mid-compile* is reported as that rather than as slowness. Progress prints on a 15s interval, so a five-minute wait is visibly a wait — the old version was silent for its whole budget, which is indistinguishable from a hang and is part of why this kept being misdiagnosed. Each of the four causes prints a distinct message naming the cause **and** the remedy; the guard is `src/__tests__/capture-readiness.test.ts`, and the budget floor there is written so it can say no (it is fed the old 90_000 and required to object).

**The pre-warm path is supported, not folklore — and it is evidence-safe.** When you already have a dev server up, or you would rather pay the compile once across several capture runs, point the harness at it:

```
npm run dev -w packages/frontend -- --hostname 127.0.0.1 --port 3161   # once; wait for it
SCREENSHOT_BASE_URL=http://127.0.0.1:3161 npm run screenshot -w packages/frontend -- /custody
```

`SCREENSHOT_BASE_URL` sets `OWN_SERVER = false`, which skips the spawn and the readiness wait entirely. **It does not skip the [#1800](https://github.com/d-hinders/Haven-AI/issues/1800) identity check** — `verifyServerIdentity` still runs, still refuses a server that cannot prove it is this worktree's app, and the run still prints `screenshot: server identity verified`. So PNGs produced this way are provably from the right branch and are fine as committed PR evidence. (The escape hatch that *does* weaken the claim is a different variable: `SCREENSHOT_ALLOW_UNVERIFIED_SERVER=1`, which stamps `identity_verified: false` in the manifest.) Before #2108 this was undiscoverable, and every agent needing captures rediscovered it privately; it is written here so nobody re-derives it, and the harness's own compile-timeout message now prints the same two commands.

**Read the `RESULT` line, not the exit code — the exit code does not survive a pipe.** `npm run screenshot ... | tail -30` reports **`tail`'s** status, so the shell sees `0` while the run failed. That false green has misled several sessions, including the one that filed #2108. Every run now ends with a greppable terminal line on stdout — `screenshot: RESULT ok — <n> PNG(s) …` or `screenshot: RESULT FAILED — <cause>` — as the last thing printed, so a `tail` of any depth catches it. If you pipe the harness anywhere, assert on that line.

**A capture must also be FINISHED, not just non-empty ([#2204](https://github.com/d-hinders/Haven-AI/issues/2204)).** `/agents` was observed at **1856px in 1 of 4 otherwise identical runs** — same code, same pre-warmed server — against 1936px in the other three. The short run passed everything the harness asserted: `RESULT ok`, the #1800 identity check, and the #2036 content floor. Reproduced and measured on `#main-content` at 1280:

| state | `#main-content` | content floor reads | PNG |
|---|---|---|---|
| resolved | 912 CSS px | 1022 chars, 157 elements | 1936px |
| chain reads still pending | 872 CSS px | 886 chars, 150 elements | **1856px** |

The missing 40 CSS px (80 device px at `deviceScaleFactor: 2`) is the three `AllowanceBar` rows: `useOnChainAllowances` had not answered, so every `AgentCard` was showing its budget placeholder. 886/150 is 29x and 25x above the #2036 floors, so no count could see it — and #1971's chain-read guard could not either, because the reads *had* been issued.

**Why this is not an 80px story.** #2148, #2197 and #2205 each proved "this capture moved, those did not" by `ImageChops.difference(...).getbbox() → None`, and design reviewers signed off on those comparisons. A capture that can silently come back short makes every one of those unchanged-proofs an untested assumption, and the failure is biased toward false confidence: a short capture looks clean, not broken.

`resolveContentSettled` therefore asks one more question — **nothing inside the route's content region may still be `aria-busy="true"`**. That is the app's own statement that a region is mid-update, written where the loading state lives rather than as a selector list in the harness, and it is the same signal a screen reader acts on. Two shapes were deliberately rejected: a per-route expected height (a snapshot of today that fails tomorrow on a copy change) and a longer sleep (an intermittent wrong answer, slower). A refusal names its own cause, `partially-loading`, distinct from #2036's `still-loading` because the remedies differ.

**Refuse, don't retry** — decided, and the reasoning is worth keeping. The retry already exists and is the poll loop: a busy region gets `CONTENT_SETTLE_WAIT_MS` to clear, which absorbs ordinary slowness. What is *not* added is a second attempt at the whole capture, because that converts a genuine slow-paint regression into a green run whose PNG came from attempt two, with nothing in `.screenshots/` saying so. A flakier harness is the cheaper failure.

**When this fires on your route, mark the placeholder, don't touch the harness.** `AllowanceBarSkeleton` now carries `role="status" aria-busy="true"` — an accessibility fix it needed anyway (the row announced nothing when it resolved). That is the intended remedy. The escape hatch is `BUSY_TOLERANT_CAPTURES` in `scripts/full-page-capture.mjs` — beside the guard rather than in the CLI, because `captureFullPage` also has an e2e consumer (`e2e/capture-integrity.spec.ts`) and an exemption only one caller knows about is a divergence, not an exemption; tolerance is derived from the page's own URL so no caller can forget it. It exists for exactly one surface: `/design-system` renders loading states *as content*, so its skeleton showcase is permanently busy and correctly so. It is the narrow, self-expiring shape of #2197's `expectedSilentRoutes` — per route, carrying a written reason, and **fatal when stale**: a run where the declared route holds nothing busy fails with `stale_busy_declarations`, exactly as its sibling `CHAIN_SILENT_CAPTURES` fails on the mirror-image staleness. (Review of #2204 caught the first draft reporting that to stdout and the manifest only, which expires nothing in a repo whose own playbook says the exit code does not survive a pipe.)

**One residual risk, named rather than designed away.** `usePortfolio` re-flips its `loading` boolean on every 60s poll, and `/accounts` binds `aria-busy` to it — so a *previously loaded* page can legitimately re-enter a busy state under a background refetch. The poll loop absorbs it (the refetch clears in well under a second against `CONTENT_SETTLE_WAIT_MS`'s 30s), and a live 9-route × 2-viewport sweep including `/accounts` produced zero refusals, but it is the one place this guard can see a steady page go busy. If it ever bites, the fix is on the binding — distinguish initial load from background refresh — not on the guard.

**Reproducing it on demand.** `SCREENSHOT_CHAIN_STALL_MS=<ms>` stalls each JSON-RPC read *client-side*, before the request leaves the page. That detail is the whole lever and it cost a diagnosis: delaying the **answer** reproduces nothing (measured at 500 / 2000 / 6000ms — `networkidle` simply waits the in-flight request out, and all three came back at 1936px). Stalling before the fetch opens a window with no in-flight request, `networkidle` fires into it, and the shutter lands mid-load. It is also the real mechanism — the hook issues four *sequential* reads, and under load the client-side gap between two of them can exceed networkidle's own 500ms threshold, which is why the bad run is 1 in 4 on a busy machine and 0 in 10 on an idle one. Evidence from #2204: with the guard mutated off, `SCREENSHOT_CHAIN_STALL_MS=900` produced `RESULT ok` and an **1856px** PNG; with it on, the identical run produced 1936px, and 18 consecutive captures (10 plain, 8 forced-race) were byte-identical.

**Known gap, unrelated to readiness:** `npm run screenshot -w packages/frontend -- /accounts/safe-main` cannot render that route — the harness fixture uses `FIXTURE_SAFE.id = 'safe-fixture'` while the e2e fixture uses `safe-main`, so the id in the URL matches nothing the fixture serves. #2108 deliberately did not fix it; do not read a failure there as a readiness problem.



**The previous run survives this one, and it says so ([#1888](https://github.com/d-hinders/Haven-AI/issues/1888)).** Every run used to open with `rm -rf .screenshots/`, so the *normal* shape of iterating — a narrow `--scenario=X` after a wide `--scenario=all` — destroyed the wider run unconditionally. During #1879's review it did exactly that to both the candidate and the control directories (70 PNGs down to 24, 48 down to 16), leaving a summary log describing a set that no longer existed on disk; the reviewer could not visually confirm `replace-signing-key-point-of-no-return`, the largest hidden-content number in the run and the highest-stakes screen in the batch, and correctly refused to sign off by inference. Retention is not tidiness here: **a same-code control is the standard technique on this harness, and a control is only a control while you can still hold it next to the candidate.**

The current run still writes **flat** into `.screenshots/`, so every `.screenshots/<name>.png` in this playbook, in the reviewer roles and in the PR template keeps resolving to the newest run — the `.screenshots/runs/<id>/` + `latest` symlink shape was rejected for that reason, since none of those consumers is code and none of them would have failed when it went stale. Instead the run that was there before is **moved** into `.screenshots/previous/<timestamp>-<commit>[-dirty]/`, capped at three (`--keep=<n>` or `SCREENSHOT_KEEP_RUNS`; `--keep=0` restores the old destructive behaviour). Three, because diagnosing a control/candidate difference routinely means holding the control, the candidate and the re-run at once.

Two properties to rely on, both of which the archive would be dangerous without:

- **A moved-aside run is self-identifying.** Its `capture-manifest.json` is stamped `stale: true`, `archived_at`, `run_id` and `superseded_by` (the branch/commit that displaced it), its `files` list is re-pointed at the archive (it recorded repo-root-relative paths, which after the move resolve into the *current* run's directory — and a name like `design-system-mobile.png` usually exists in both, so an un-rewritten list sends a reader to a different run's PNG under the right name), and a run that crashed before writing a manifest gets an explicit `provenance: "unknown"` stub rather than inheriting silence. **Attaching last run's PNGs believing they are this run's is worse than losing them**, which is the whole reason the archive has to claim the opposite of what #1800's manifest claims.
- **Retention never restores.** Nothing ever moves archive → live. That matters because the harness deletes its own bad evidence — a failed `goto` writes no PNG, a capture blank below the fold is deleted and fails the run (#1738) — and the `SCROLL_SHELL_ROOT` blank is nondeterministic: it hit `/design-system` desktop on one run of the #1888 proof and `/design-system` mobile on the next, on identical code. A design that repopulated the live directory from an archive could put a blank the harness had already judged worthless back on the path a reviewer reads. Mechanism and mutation matrix: `scripts/capture-retention.mjs`, `src/__tests__/capture-retention.test.ts`.

**The capture harness had the dialog-subtree defect too, on the vertical axis, and its clip guard was reporting zero ([#1879](https://github.com/d-hinders/Haven-AI/issues/1879)).** `shoot()` has no selector of its own — it measures `scrollHeight - clientHeight` on **whatever locator the caller hands it**, and 19 of its 21 call sites hand it `page.getByRole('dialog')`. On `ui/Modal` that role sits on the `fixed inset-0` wrapper (`Modal.tsx:109`): viewport-sized, never scrolls, reads **0 however much** the nested `min-h-0 flex-1 overflow-y-auto` body at `:153` is hiding. So the guard could not fire, nothing was recorded in `clipped`, and no taller re-shoot happened — while the modal's rounded bottom edge and footer rendered cleanly at the clip, making the PNG **look finished**. That is worse than a missing capture, because the `haven-design-reviewer` pass below reasons from exactly these artifacts: the capture that found this was a destructive-action screen whose irreversibility banner and acknowledgement checkbox were both below the fold.

Measured on the same commit, same fixture, one full `--scenario=all` run each: the old guard reported **2** clipped captures, the corrected one reports **16**. The 14 it newly finds were always clipped — `connect-agent-manual-credential-warning` at **706px** (1280) and **1020px** (390), `replace-signing-key-point-of-no-return` at **656px** and **1060px**. Note the fix is to change *what* is measured, not which element the call sites hand in: scanning the subtree also covers `ui/SidePanel`'s body and the two `card` call sites, which a selector swap would have missed.

Three things the vertical version needs that the horizontal one above does not:

- **Skip descendants that cannot clip.** A box whose computed `overflow-y` is `visible` hides nothing — its overflow paints and propagates outward to the nearest clipping ancestor, which reports it. This is the *opposite* of the rule rejected above, which refuses to exempt `auto`/`scroll` boxes because those are the scrollers where the defect lives. It was found by measuring, not by reasoning: every genuine offender was `overflow-y: auto` (89–1060px) and **every** box in the 2–5px noise band was `visible` — `<button>` at `clientHeight: 34, scrollHeight: 39`, flex rows at 40 vs 42. Six captures were flagged on nothing but a 5px button. `hidden` and `clip` stay in; a box that truncates without even offering a scrollbar is the worst version of this, not an exempt one.
- **Measure the target itself unconditionally anyway.** An element screenshot is the target's bounding box, so content overflowing a non-clipping *target* really is cut from the PNG — and that is exactly what the old guard measured. Exempting it would have narrowed existing coverage while fixing the nested case. `ReceiveFundsModal` is the live example: its `role="dialog"` is the scrolling panel itself, which is why it was one of the only two captures the old guard ever caught.
- **Re-measure after growing the viewport, because growing does not un-clip everything.** `ui/Modal`'s `max-h-[calc(100vh-max(1rem,var(--v2-safe-top))-max(1rem,var(--v2-safe-bottom)))]` responds to a taller window; a `pre.max-h-48` code block does not, and stays 203px short at 390 forever. 8 of the 16 are in that state, so the run now says which `-full.png` is **not** actually full instead of letting the name imply it.
- **The residual's offender is a different box from the shortfall's, and the report used to conflate them ([#1887](https://github.com/d-hinders/Haven-AI/issues/1887)).** `shoot()` recorded `residual: after.hidden` but printed `before.offender`, so every "STILL clipped" line put an after-growth number under a before-growth name — and the before-offender is precisely the box the growth just *fixed*. The tell was arithmetic: four `connect-agent` mobile captures with before-values of 203 / 203 / 295 / 1020 all reported a residual of exactly **203**. Four different modal bodies do not converge on one number; one shared `pre.max-h-48` does. The run now records `residualOffender` and names it, and says when it differs from the before-offender. **Why it is not cosmetic:** the self-capped allowlist that would let this check become gating (see the recorded decision in `screenshot.mjs`) would have been keyed on those strings, and would therefore have exempted `div.min-h-0 flex-1 overflow-y-auto …` — `ui/Modal`'s body, shared by every dialog in the app, and the last box whose clipping should ever be waved through. An allowlist is only as honest as the selector it is keyed on.

**And check 390 first**, which is [#1797](https://github.com/d-hinders/Haven-AI/issues/1797)'s rule one layer down: `replace-signing-key`'s `reason` and `address` stages read **0px at 1280 and 21px / 17px at 390**. Two captures that look complete on desktop are silently truncated on mobile, and desktop is where everyone had been looking.

Prove a change here by mutation, never by a green run — this guard's whole defect was that it could not fail. The proof shape that works: inject a tall block into a dialog that currently fits, confirm the **old** guard still records nothing (it recorded 0 against a 628px injection) while the new one reports the shortfall, then revert and confirm the newly-flagged list returns to exactly its previous members. The revert half is the half that says it fires for the right reason.

**That proof now re-runs on every frontend PR, and where it lives is the whole design decision ([#1886](https://github.com/d-hinders/Haven-AI/issues/1886)).** The guard moved out of `screenshot.mjs` into `scripts/clip-guard.mjs` — verbatim, call sites unchanged — purely so a spec can import it; `e2e/clip-guard.spec.ts` then drives it over a `page.setContent()` fixture in the *Frontend browser smoke* job. Three instrument choices were live and only one of them can answer the question this gate is for:

- **jsdom cannot fail and must not be used here.** It performs no layout, so `clientHeight` and `scrollHeight` are `0` on every element and every assertion built on them passes against every input — including a guard that returns a constant. That is worse than no coverage, because it looks like coverage. It was suggested on #1879 and declined for exactly this reason; it is written down so it is not proposed a third time. The same trap applies to any layout guard in this file.
- **Asserting against the harness's own `clipped` report is the honest-looking wrong answer.** It cannot distinguish *"the guard stopped working"* from *"these captures are still clipped"*, and the second is permanently true: 8 of the 16 residuals are self-capped by design (the `pre.max-h-48` bullet above), entirely in `connect-agent` — and per [#1894](https://github.com/d-hinders/Haven-AI/pull/1894) all eight resolve to a SINGLE self-capping element, `CopyBlock`'s `pre.max-h-48`, not to eight independent cases. A gate keyed on the report would be red on unchanged `dev` forever, and any layout change to a captured screen would move its numbers for no defect at all.
- **A synthetic fixture answers only the first question, which is why it is worth its cost.** Five hand-written DOM shapes, one per rule — two of them exclusions (`overflow-y: visible` descendants, and the 1px geometric floor), three of them the coverage the guard must NOT lose (the nested scroller, `overflow-y: hidden`, and the target itself) — with no route, no API fixture, no product component and no baseline PNG — so app layout work cannot redden it — while Chromium still lays it out for real, which is the one thing jsdom cannot give. Extracting the traversal as a *pure* function over injected boxes would be faster still and would leave the `scrollHeight`/`clientHeight` read — the half #1879 actually got wrong — untested; here the real `evaluate()` runs against real boxes.

Two house rules it inherits and one it adds. **One `test()` per rule** (#1863): five assertions in one test short-circuit and turn a mutation's blast radius into a guess. **Every exclusion needs both directions** — a mutation that reddens the rule *and* a fixture proving the guard stays silent on the case #1879 deliberately excluded, because a gate that flags everything is as useless as one that flags nothing. And **pin the noise band's actual numbers, not just its verdict**: the over-fire fixture asserts the `<button>` really reads `clientHeight: 34, scrollHeight: 39` and that `39 - 34` is strictly greater than `CLIP_TOLERANCE_PX`, which is what proves the *exclusion* is doing the work rather than the tolerance quietly covering for it. That is also the assertion that keeps the tolerance at **4**: widening it to 5 silences the noise band and starts silencing real 5px shortfalls, and it turns that test red on the way past.

**The e2e suite had the same defect, and now reuses the same mechanism ([#1816](https://github.com/d-hinders/Haven-AI/issues/1816)).** `playwright.config.ts` took a fixed `PLAYWRIGHT_PORT ?? 3000` in every worktree and set `reuseExistingServer: !CI`, so a local `npm run test:e2e` adopted whatever was already on :3000 — which in a second session is **another worktree's app**. The result is not a broken run; it is a **pass or a failure attributed to a branch the run never loaded**, which is worse. So:

- the port is derived from the worktree path into a range **disjoint from the capture server's** (3300–3419 vs 3111–3230 — one worktree can be capturing and testing at the same time). Note what that does and does not do locally: the derived port is used **as is** when reuse is allowed, precisely so a warm `next dev` on it gets adopted rather than stepped over — walking forward to a free port instead would start a *second* Next in the same worktree, which cold-compiles every run and corrupts the shared `.next/`. The bind-and-walk is kept for CI, where nothing may be adopted and Next would otherwise hop ports while Playwright polled the old one;
- `globalSetup` writes a per-run marker into `public/`, fetches `/e2e-identity.json` back from whatever Playwright is about to test, and **throws unless the token is this run's own**. `reuseExistingServer` is kept but no longer trusted: it asks only whether something answered.

Two consequences worth knowing before you meet them. **A hand-started `npm run dev` is adoptable only on the derived port** — the marker is written to this worktree's `public/`, so any server serving *this* worktree's files passes, and one on some other port simply is not found. And `PLAYWRIGHT_BASE_URL` pointed at a deployed environment will be **refused**, because a deployment cannot serve your run's token; `PLAYWRIGHT_ALLOW_UNVERIFIED_SERVER=1` is the loud way past that, and it means the result may belong to another branch. CI was never exposed (`reuseExistingServer` is false there, runners are per-job isolated) but runs the probe anyway. Mechanism: `scripts/e2e-identity.mjs`.

**Surfaces no URL can reach — use a scenario ([#1409](https://github.com/d-hinders/Haven-AI/issues/1409)).** Route capture cannot see a screen that lives behind a multi-step dialog or a state machine that only advances on a timer; the connect-agent modal is both, which is why [#1399](https://github.com/d-hinders/Haven-AI/issues/1399) shipped with its rendered-evidence criterion unmet and its two review passes disagreeing about a layout question neither could see. A **scenario** drives the UI there and holds it at each state:

```
npm run screenshot -w packages/frontend -- --scenario=connect-agent   # one scenario
npm run screenshot -w packages/frontend -- --scenario=all             # every scenario
```

`connect-agent` captures step 4 at all three connection stages (`starting` → `slow` → `recovery`) at both viewports, writing `connect-agent-waiting-<stage>-<viewport>.png`. It pins the setup at `awaiting_connection` and drives Playwright's virtual clock past the staging bounds, so a three-minute state is reached in milliseconds. A scenario that cannot reach its state **fails the command** rather than writing fewer PNGs — a missing stage is the evidence gap, not a smaller run. Add new scenarios to the `SCENARIOS` registry in `scripts/screenshot.mjs`; their fixture contract is pinned by `src/__tests__/screenshot-fixture.test.ts`.

**A scenario can seed a FAILURE, not just a body ([#1725](https://github.com/d-hinders/Haven-AI/issues/1725)).** Return `httpError(status)` from a scenario's `api()` and that one route answers non-2xx; anything else is served as a 200 as before. This is what makes error states capturable at all — a card that shows its error branch when the fetch *throws* (the usual shape: `api.get` in a `try`, `lib/api.ts` throwing on `!response.ok`) cannot be reached by any 200 payload, however it is shaped. Expect the browser's own "failed to load resource" line in the run's console-error summary; for a scenario that seeds a failure that is the fixture working, not a gap. `account-backup-recovery` shoots all three of its states this way — healthy, one-way warning, load failure — re-serving `/signers` and reloading between shots. When one surface has several states, **assert the ones that must be absent as well as the one you seeded**: a positive wait passes just as happily when the card is on a neighbouring branch, and the PNG then lands under the wrong state's filename.

**A scenario can answer the app's ON-CHAIN reads ([#1935](https://github.com/d-hinders/Haven-AI/issues/1935)).** `api()` answers the Haven backend; a second class of state comes from the chain instead, and no `/api/*` body of any shape reaches it — the same "the harness cannot express this input" wall #1725 hit, one layer down. Declare `chain(method, params)` on a scenario and it answers viem's JSON-RPC calls directly: the app's transport is `fallback()` over plain `http(url)` endpoints (`lib/wagmi.ts`), so the reads leave the browser as ordinary POSTs Playwright routes like anything else — matched on pathname across every origin, so which endpoint the fallback picks is irrelevant, and the app's own encode → decode → hook → render path all runs. **Two facts that cost a run each, and will cost you one too.** First — **fixed by [#1971](https://github.com/d-hinders/Haven-AI/issues/1971), and read this before you copy an older scenario** — the shared fixture's safe is on **chain 84532**, which the wagmi config did not register: wagmi's `getClient` swallows `ChainNotConfiguredError` and returns `undefined`, so `usePublicClient` was `undefined` and *zero* RPC requests ever left the browser, in any run, since the harness existed. That was a defect in `lib/wagmi.ts`, not in the fixture — `lib/chains.ts` OFFERS 84532 in every network picker and the dev deployment DEFAULTS to it (`NEXT_PUBLIC_HAVEN_CHAIN_ID=84532`), so real users hit the same silence. `wagmi.ts` now DERIVES its chains and transports from `SUPPORTED_CHAINS`, and `src/__tests__/wagmi-transport-parity.test.ts` asserts through `getClient` itself that every offered chain yields a client. So a scenario capturing a chain-fed surface no longer has to move its account to 8453; the shared fixture's chain works, and every scenario now inherits `answerSharedChainRead` so nothing reaches a public node. Second, wagmi batches by default, and the trap is **not** the one that phrase suggests. Every contract read is wrapped in **Multicall3's `aggregate3`** — including a read that is alone in it — so a fixture that answers only the un-batched shape answers nothing. Logged live rather than reasoned about, because "the four reads arrive as one `eth_call`" is the plausible summary and it is wrong: `useOnChainAllowances` awaits each read before queueing the next, and viem's batcher only merges calls queued in the same wait window, so one fetch cycle is **four** `aggregate3` POSTs (inner counts 1, 1, 1, 2 — only the two `getTokenAllowance` calls genuinely batch) plus one un-wrapped `eth_getBlockByNumber`. A read the scenario does not answer is served a JSON-RPC error and **fails the run** (`✗ … on-chain read(s) went UNANSWERED`) — deliberately fatal, because the hook swallows the error into an empty map and the modal then renders *without* its list: a plausible, well-formed, completely wrong PNG of the very surface the capture exists to show. **And the silent half ([#1971](https://github.com/d-hinders/Haven-AI/issues/1971)):** that report can only see a read the app MADE. The failure that hid this for the whole life of the harness produces no request at all — an undefined `publicClient` makes every consumer return at its first line, silently. So a capture whose page visited a chain-fed route (`CHAIN_FED_ROUTES` — today `/agents*` and `/custody*`) and observed **zero** chain reads is now fatal too (`✗ … capture(s) of a CHAIN-FED route issued ZERO on-chain reads`), and both lists are in `capture-manifest.json`. Keyed on route rather than on scenario, because the property belongs to the screen, not to the story told about it — and the list is checked against the app's own import graph (`chain-fed-route-coverage.test.ts`), in **both** directions. (**Since [#2106](https://github.com/d-hinders/Haven-AI/issues/2106) one route is chain-fed only CONDITIONALLY, and the paragraph below is the exception to "the property belongs to the screen" — read it before assuming zero reads is always fatal.**) The second direction is the load-bearing one: `/dashboard` was in that list on a false premise (nothing chain-fed is mounted there — the entry was justified as "`useAgentPanelState` + `ApprovalQueue`" and neither was mounted on it; `ApprovalQueue` and the `/approvals` route it lived on were then deleted outright by [#1989](https://github.com/d-hinders/Haven-AI/issues/1989) / [#2055](https://github.com/d-hinders/Haven-AI/issues/2055), epic #1440, which changes nothing about the guard's shape), and five scenarios pass through `/dashboard` on their way to a modal, so one wrong entry would have made `--scenario=all` red on unchanged `dev`. The signal is a **render-time** read, never a gating `usePublicClient`. **The live worked example of that distinction is `EditAgentModal`**, and it is the useful one because it is both sides at once: it calls `usePublicClient({ chainId })` (`components/EditAgentModal.tsx:125`) purely to *gate* — the budget-save control's `disabled`, and the async submit handlers — so a resting capture of that screen issues no chain request from it, while the screen's budget list IS render-fed, via `AgentDetailClient`'s `useOnChainAllowances`. **One thing to know before you read that half as current product**: the budget editor is the legacy AllowanceModule one (`showBudgetFields = … && !isDelegationAgent`, `EditAgentModal.tsx:88`), so a delegation-rail agent never renders it — `DelegationBudgetCard` owns that now. It is still the right teaching example, because the property being taught is about the harness rather than about the rail, and `edit-agent-budget` has captured exactly this path since before the rail was retired. Do not read it as a demonstration of delegation-rail budget editing. Calling `usePublicClient` is not the signal; reaching `useOnChainAllowances` is, which is exactly the property `chain-fed-route-coverage.test.ts` walks the import graph for. That test's docstring carries the same example — keep the two in step. `edit-agent-budget` is the worked example — `EditAgentModal`'s budget list and its per-row remove control, which had no rendered evidence at any commit before this.

**A capture can declare a chain-fed route legitimately SILENT ([#2106](https://github.com/d-hinders/Haven-AI/issues/2106)).** The guard above assumes a route either reads the chain at render or does not — a property of the screen. `/custody` broke that assumption: it renders one card per account and branches on the account's rail, and only the **legacy Safe** card mounts `useOnChainAllowances`. The **delegation-rail** card proves custody from two API reads (`/accounts/hybrid/:address/signers`, `/agents/:id/delegations`) and touches the chain not at all, so on an all-delegation-rail account — which, since [#1984](https://github.com/d-hinders/Haven-AI/issues/1984), is every new account — zero chain reads is the CORRECT observation rather than the empty-surface defect. Deleting the route from `CHAIN_FED_ROUTES` would have retired the guard for the rail that still needs it, so instead: a route entry may carry a **`silentWhen`** string naming the state that makes silence correct, and a scenario may declare **`expectedSilentRoutes: [/^\/custody(\/|$)/]`** to opt that one route out for that one capture. Deliberately narrow — per capture AND per route, never "this scenario reads no chain at all" — and **bidirectional: a declared-silent route that DID read is reported too**, as a stale declaration, so the day the delegation card starts reading the chain the exemption fails instead of quietly widening. Both directions are pinned in `chain-fed-capture-guard.test.ts`. `custody-delegation-rail` is the worked example; its twin `custody-legacy-rail` declares nothing and leaves the guard armed.

**A scenario can mock a CONNECTED wallet ([#2073](https://github.com/d-hinders/Haven-AI/issues/2073)).** A third class of state comes from the wagmi connection itself — the signer gate's `wrong_wallet` answer needs a hydrated signer set AND a connected wallet whose address the gate can compare, and neither `api()` nor `chain()` can express "a wallet is connected". Declare `connectedWallet: '0x…'` on a scenario and the harness installs a minimal EIP-1193 provider on `window.ethereum` plus the two wagmi storage keys (`wagmi.injected.connected`, `wagmi.recentConnectorId`) that let the targetless `injected()` connector reconnect on mount — so wagmi's own reconnect, `useAccount`, the gate and the header render are all the product's code, nothing forced by props. The stub answers only the read methods a mounted app needs (`eth_accounts`/`eth_requestAccounts`/`eth_chainId`/`net_version`) and **throws loudly on anything else**, so a scenario that starts SIGNING fails instead of hanging on a prompt no one can answer. One knock-on cost, already paid: a connected wallet makes RainbowKit batch-read the address's native balance (`getEthBalance` on Multicall3), so `makeAllowanceChainFixture` seeds that read — zero, for any address — or the #1935 unanswered-read guard rightly fails the run. `wrong-wallet` is the worked example, and `e2e/wallet-signer-offering.spec.ts` uses the same stub shape for the owner-match/mismatch pair.

**A scenario can seed DEVICE-LOCAL state, including which account is active ([#1856](https://github.com/d-hinders/Haven-AI/issues/1856), first used by [#2202](https://github.com/d-hinders/Haven-AI/issues/2202)).** The fourth class, and the one an API body structurally cannot reach: state the product keeps in the **browser**, not on the server. Declare `seed()` on a scenario returning `{ [key]: value }` pairs and the harness writes them to `localStorage` before any app code runs — same posture as `connectedWallet` above, a browser-side store the product owns, so the app's own read path and branch are real. It was built for the passkey store (`useSafeOperationGate` resolves the signer from the credentials the app itself wrote at enrolment, and no API answer can put a credential on this device) and stood with **no callers at all** until #2202. Deliberately narrow: it seeds a store the product owns, and is **not** a hook for stubbing component state — a scenario that wants one should be re-examined instead. The keys the harness itself seeds are exported as `SEED_STORAGE_KEYS` (`haven_token`, `haven_active_safe_id`) and pinned against `src/lib/auth-storage.ts`, so a rename there fails a test rather than silently capturing logged-out screenshots. `agents-legacy-rail` is the worked example, and it shows the main reason to reach for this: **switching the ACTIVE account**. The shared fixture describes two accounts (a delegation-rail one and a legacy Safe), and a good deal of the product is gated on which is active — `useAgentPanelState` reads the chain for the active account only, and `AgentPanel` binds every agent's wallet controls to `agentUsesActiveSafe` — so the legacy rail's rendering is reachable by seeding `activeSafe` and overriding **nothing else**. Prefer that to an `api()` override: a scenario that has to restate the agent list to render a rail is evidence that the fixture disagrees with itself.

**Two PNGs when a dialog scrolls.** An element screenshot captures only the visible box, so a dialog that caps its own height drops everything below the fold — and its rounded bottom edge makes the clipped capture look complete, which would have a reviewer judge a screen they have only partly seen. When a capture overflows, the run says so (`⚠ … had content BELOW THE FOLD`, with the pixel shortfall) and writes a second `…-full.png` at a viewport tall enough to show all of it. **Judge the content from the `-full` PNG; judge what is reachable without scrolling from the other** — the fold itself is often the finding.

**A blank capture fails the run ([#1738](https://github.com/d-hinders/Haven-AI/issues/1738)).** The app shell is `h-screen` + `overflow-hidden` with `<main>` as its only scroller, so a naive `fullPage` capture paints one viewport and leaves a very long white tail — the PNG is the right size and looks fine. Route captures therefore un-clip the shell first (`scripts/full-page-capture.mjs`), then read the PNG back: a capture more than a viewport tall with nothing painted below the fold is **deleted** and fails the command, with the measured painted ratio in the message. This is not hypothetical — the committed `/design-system` baselines were 95% (desktop) and 97% (mobile) blank until that fix, so the pixel gate had been comparing white against white below the fold and the design-reviewer pass was reading empty pixels. If you see the failure, the usual cause is a layout change to the shell's overflow; do not work around it by capturing less.

**A deleted capture now says WHY it was deleted ([#1936](https://github.com/d-hinders/Haven-AI/issues/1936) / [#1939](https://github.com/d-hinders/Haven-AI/issues/1939) / [#1943](https://github.com/d-hinders/Haven-AI/issues/1943)).** That deletion used to be the entire report, and three different situations shared one sentence about the selector: a **marketing route** (`/`, `/investor-briefing`) has no `#main-content` at all and needs no un-clipping; an **authenticated route** has one that has not mounted YET, because `ProtectedRoute` renders `null` while auth resolves; and a page that **never finished rendering** (a cold `next dev` first compile — 315s measured on a contended machine) has nothing to find. So the harness now waits out the race (`shell appeared after 1550ms` is reported, not failed), captures shell-less routes directly and says it did, and separates `missing-scroll-root` / `not-rendered` / `capture-timeout` / `blank-below-fold` as named causes. **Every removed PNG is named with its cause on stderr and in `.screenshots/capture-manifest.json` (`deleted_captures`)** — so an empty `.screenshots/` is readable as *why* there is nothing, never as "there was nothing to capture". `npm run screenshot -w packages/frontend -- / /investor-briefing` is therefore now a working command; before this it returned 0 PNGs and exited 1.

**A capture that is still LOADING fails the run ([#2036](https://github.com/d-hinders/Haven-AI/issues/2036)).** `/dashboard` was captured twice, on both viewports, showing the app shell — TopBar, account chip, collapsed wallet square — around a body containing nothing but `Loading...`, and the run **exited 0**. That is worse than a failed capture: a failure announces itself, while this files a well-formed PNG under a name claiming it shows the route, and `haven-design-reviewer` reads it as evidence. Neither neighbouring guard could see it, and both were behaving correctly: `blank-below-fold` needs an image *taller than one viewport* before there is a below-the-fold to be blank, and a loading state is short; the shell guards ask whether `#main-content` **mounted**, and it did — it is the `next/dynamic` chunk inside `<main>` that never arrived. `MIN_RENDERED_CHARS` looks like it should have covered the gap and does not, because it is measured on `document.body`, which on an authenticated route is thousands of characters of *shell* before the route contributes one. So `captureFullPage` now also demands **positive evidence that the route's own content region filled** — at least `MIN_CONTENT_CHARS` / `MIN_CONTENT_ELEMENTS` inside `#main-content` — waits `CONTENT_SETTLE_WAIT_MS` for it, and on failure removes the PNG with the named cause `still-loading`, exactly as a blank one. Judged **per capture**, so a healthy `/dashboard` cannot excuse a still-loading `/agents`.

Two things about that check are deliberate. It is a **floor on content, not a list of loading states**: matching `Loading...` / `[aria-busy]` / the shared skeleton expires the moment a loading state changes its markup and only ever catches the ones somebody enumerated, whereas "the region has a real screen's worth of text and structure" is true of every rendered route *including its empty states* and false of every loading state whatever it looks like. And **waiting longer is the second half of the fix, never the whole of it** — a longer wait makes the bad capture rarer and no less silent, which is the property the issue was filed about. **The floors are set from the EMPTY-STATE population, and getting there took three measurements.** Warm live runs record, on the populated fixture, `/dashboard` 466 chars / 112 elements, `/agents` 851/138, `/design-system` 30,720/1,624 — and on `SCREENSHOT_FIXTURE=empty`, `/dashboard` 298/109, `/contacts` 116/23, `/accounts` desktop 129/15 and **`/accounts` mobile 87/15, the leanest screen the app genuinely renders**. Against a loading fallback of 10 chars / 3 elements. Two corrections are worth inheriting rather than repeating. A run at load average ~490 produced `/agents` at 105/30, which was briefly taken for "the leanest real route" and used to *lower* the floor — it was `/agents` caught mid-render, so **read a floor against a warm run**. The floor then stood at 80 chars, *reasoned* to be safely under every empty state; design review refused that as inference wearing a measured voice, and the measurement it asked for found `/accounts` empty at **87 chars — a 1.09x margin**. One word shorter and a legitimate empty state would have been silently refused, which is this guard's own defect aimed at the sparse screens that most need photographing. 30/6 now sits ~3x above the loading fallback and ~2.9x below the leanest real screen (2.0x / 2.5x on elements), and every margin is asserted **as a ratio** in `full-page-capture.test.ts` — a bare inequality is what made 87-vs-80 look fine. **The stated limit**: a partially rendered route clears these floors and is captured. The claim is "the route rendered *something*", never "the route rendered everything" — the second question needs per-route named content and is separate work. What this removes is #2036's case, where the region holds nothing at all. Marketing routes are out of scope by construction: they have no `#main-content`, and demanding one there would refuse every one of them (#1939). The margin each capture cleared is recorded per route in `.screenshots/capture-manifest.json` under `content_settle`, so a green run states what it measured rather than asking to be trusted.

The discriminator between "no shell" and "renamed shell" is **measured, and two obvious versions of it are wrong**: a clipped `/design-system` reports a 17,876px document `scrollHeight` *and* lets `window.scrollY` move, so neither "is the document tall" nor "can the document scroll" separates it from a marketing page. What does: whether any single box holds **a viewport or more** of content the document will never paint (`<main id="main-content">` holds 17,903px desktop / 29,423px mobile). Do not re-derive this from the DOM by eye.

**The whole-page `/design-system` baseline is gone — it failed on load, not on regressions ([#2635](https://github.com/d-hinders/Haven-AI/issues/2635)).** Over the last 12 *Design visual regression* CI failures before this PR, that capture accounted for **5 by the first count and 7 when an independent review re-derived it over every `ci.yml` run in the window** — both are recorded because they disagree, and the difference is per-PR vs. per-run sampling, not a correction. None was a real regression. **What they were is not what the first reading said**: the logs show Playwright computing stable diffs and failing on MAGNITUDE, from ~12k px (1%) to ~2.7M px (23% of the image), on branches with no relation to this page. A capture that renders 23% differently on unrelated work is non-deterministic, not slow — which is why raising the 15s timeout would not have fixed it and deleting was the right call. The cause of the non-determinism, most likely below-the-fold content settling, is named rather than established. `e2e/design-system.visual.spec.ts` now captures only the scoped top-bar and sidebar clips (unaffected by this change; their own budgets and rationale are unchanged, documented in the spec itself). Coverage lost, stated plainly: no baseline anywhere now diffs a primitive rendered BELOW the shell on `/design-system` itself — a component recolour or resize outside the top bar/sidebar bands has no pixel gate on that page. `/dashboard` and `/transactions` (#2318, below) remain the suite's only whole-page pixel coverage; they do not substitute for `/design-system`'s primitive gallery. `scripts/ci/visual-baseline-inventory.mjs` reads the committed baseline directory rather than a hand-written list, so its job-summary inventory reflects the removal automatically — no separate "expectations" file needed updating.

**Reading a red baseline-updater run.** `.github/workflows/update-visual-baselines.yml`'s last 30 dispatches: 28 failed at the *Report the push-attribution deadlock on the PR* step, 1 at *Audit which baselines moved* (a deliberate `proof/2218-baseline-audit-all` demonstration of that gate catching an undeclared move), 1 at *Build frontend (standalone)*. The dominant signature — the #1777 deadlock — is **by design**, not a defect this PR fixes: `BASELINE_PUSH_TOKEN` is unset on this repo (confirmed via `gh secret list`), so the push-attribution deadlock documented above fires on every dispatch against a branch with an open PR, and the workflow is written to fail loudly rather than succeed into a silent hang (#1777/#2599, both already shipped). The one fix available in code — the `BASELINE_PUSH_TOKEN` secret itself — needs repo-settings access outside a pull request's reach; `mode: changed` remains at this writing the only documented default dispatch path, unchanged by that PR. **Updating baselines for an intended change — in the SAME PR:** dispatch the **Update visual baselines** workflow on your PR branch (Actions → Update visual baselines → Run workflow → pick the branch) — it regenerates the Linux-rendered baselines and commits them to the branch, where they appear as a reviewable image diff. **Caveat — expect the regeneration run itself to go RED, and read its PR comment (#1777).** Without the `BASELINE_PUSH_TOKEN` secret (a PAT/App token with `contents: write`), the bot pushes as `github-actions[bot]`. The `pull_request` events *are* delivered and the runs *are* created; GitHub then **parks them at `conclusion: action_required`** because a bot pushed, so no job executes, no check run attaches to the new head, and every required check waits forever at "Expected — waiting for status". (Not "the event never fired" — that reading sends you looking for a missing trigger. Measured on bot commit `31003514`: `check-runs` → `total_count: 0`, `actions/runs?head_sha=…` → 5 parked `pull_request` runs.) Since #1777 the workflow **fails and posts a sticky comment on your PR** naming the condition and the recovery, instead of succeeding into the deadlock behind a `::warning::` nobody reads. **The red is about the push attribution, not your baselines** — those are committed and pushed before the failing step runs, so do not re-dispatch (a re-dispatch just regenerates them again). **Recover by approving or by re-running — not by pushing:** the comment enumerates the parked runs by URL, and clicking *Approve and run* on each resolves this PR's required checks with no push at all, because those parked runs **are** those checks. Approving needs write access **and a real user**: a human who dispatched the workflow normally has it, but **dispatching does not imply approving** — an App installation token that dispatched this very workflow was refused `403 Resource not accessible by integration` by the approve endpoint (#2599). **Where approving is not available to you, re-run each parked run instead** (`gh run rerun <run-id> -R <owner>/<repo>`, or `gh api --method POST "repos/<owner>/<repo>/actions/runs/<id>/rerun"`): a re-run is a fresh attempt attributed to whoever triggers it, so it un-parks itself with no push and no rewritten history. Observed on #2598 — all five parked runs came back `run_attempt: 2`, `triggering_actor: d-hinders`, and CI went green with no push at all. Only if neither is available, push from your own credentials (`git commit --amend --reset-author --no-edit` then `git push --force-with-lease`, or an empty commit) — the workflow cannot do that step for you, because the gate keys on *who* pushed and a second bot push parks identically; and see the force-push caveat below, which is why that route is the last one. Setting the secret retires the whole path.

**A red gate can also mean the job never compared anything at all (#1930).** The two causes above are both about *images*; this one is not, and it is the easiest of the three to misdiagnose because the surfaced signal is identical — "the blocking pixel gate is red". The `Design visual regression` job **downloads** the prebuilt frontend `.next` artifact rather than building it, so nothing in it builds the workspace's own packages, and `npm ci` alone does not create `@haven_ai/core`'s `dist/`. The prebuilt `.next` already has core bundled *into* it, so the web server starts fine and it is the **Playwright process** that is short the module. A visual spec importing `@haven_ai/core` — directly, or through a fixture like `scripts/allowance-chain-fixture.mjs` — then dies at **collection**: `Cannot find module '@haven_ai/core/dist/index.cjs'`, zero tests run, zero pixels compared, and **no `visual-regression-diffs` artifact at all**. That absence is the tell, and it inverts the first cause's diagnostic: no diff artifact means nothing was ever compared, so there is nothing in your captures or baselines to diagnose. **Do not reach for the regeneration workflow here** — regeneration would bless whatever renders and hand you a green gate carrying no information, and #2218's safer `changed` default does not help: a collection failure means nothing was compared at all, so "only rewrite what fails comparison" has nothing to protect. **Tell the two reds apart by the ARTIFACT, not by the log:** a real pixel failure uploads `visual-regression-diffs`; a collection crash uploads nothing, because nothing was ever compared. Check `gh api repos/<o>/<r>/actions/runs/<id>/artifacts` before you read a single line — it is one call, and it decides which of these two paragraphs you are in. `ci.yml`'s visual job now runs `npm run build -w packages/core` first for exactly this reason, and `browser_smoke` carries the same step; `scripts/ci/e2e-workspace-deps.test.mjs` asserts the invariant for **every** job that downloads the build, so a third such job cannot reintroduce it silently (mutation-proven: removing the step from either job reddens that job's case by name, and adding a third download-and-test job without it fails on both the named case and the membership pin). Note this was **latent rather than intermittent**: until #1930 no visual spec's transitive imports touched core, so `dev`'s green history was structurally green, not lucky — which is why nobody had been re-running it away. `Frontend browser smoke` had the same shape and the same gap, still latent (it excludes `*.visual.spec.ts`); both jobs are fixed together here ([#1998](https://github.com/d-hinders/Haven-AI/issues/1998)). Same class as #1777 above: a gate whose failure mode is indistinguishable from a defect in the diff under test.

**The force-push fallback does not re-fire the checks — only a normal push does (#1878).** The recovery above offers `git commit --amend --reset-author --no-edit` + `--force-with-lease` as the route for someone who cannot approve. It re-authors the commit correctly, and it is *not enough*: measured on this branch, a force-push carrying an identical tree (`git diff` empty, both trees `9c87a96`) produced **one** check run — *Apply surface labels*, which is `pull_request_target` and so runs in the base context and never parks. Every plain-`pull_request` workflow stayed silent: no run at any status, not `action_required`, not `queued`, not `waiting`. A subsequent NORMAL push of a real commit fired all twenty. So if you take the fallback, expect to still need a genuine follow-up commit; `ci.yml` can be `workflow_dispatch`ed to recover its own jobs, but `docs.yml`, `docs-coupling.yml`, `design-system-coupling.yml` and `frontend-copy-lint.yml` declare `pull_request` only and have no dispatch path at all.

**Never regenerate baselines from a LOCAL `test:visual` run (#1878).** `webServerCommand` only builds and serves the standalone output when `CI` is set; locally the harness runs `next dev`, and Next's dev-mode indicator is a fixed element in the **viewport's bottom-left** — exactly where the app shell's user chip sits. It lands on the avatar in `design-system-sidebar-desktop.png` (1425 px, deterministic across three runs) and bakes a red "1 Issue" badge into a locally regenerated whole-page baseline. Committing that blesses a dev-server artifact as the expected state.

**And a local run's pass count is not the parity proof it looks like.** The co-located-assertion short-circuit above cuts both ways: `pixel-stable (desktop)` asserts the whole page, the topbar and the sidebar in one `test()`, so while the whole-page assertion is red the sidebar one **never executes**. A local run reporting "12 passed, 2 failed" therefore says nothing about the sidebar — the overlay defect above hid behind exactly that arithmetic, and only surfaced once the whole-page baseline was fixed. If you are checking renderer parity, check which assertions *ran*, not how many tests passed.

**Beware the two SHA classes when you check any of this yourself.** The dispatch run's own `headSha` is the branch tip *before* the workflow pushed — a human commit, with a full set of check runs and a `success` dispatch run. The commit that shows the defect is its **child**, the bot's baseline commit. Querying the first and concluding "no problem here" is the easy mistake; name which class your SHA is in. Any PR that intentionally changes what `/design-system` renders (including its prose) without carrying new baselines leaves the job red for every PR after it. Never commit locally-rendered (macOS) baselines; fonts differ and CI will reject them. Run the spec locally only inside a Linux container with `VISUAL_REGRESSION=1`. Note: the job gates auto-merge only while it's listed in the "Haven automerge rules" ruleset's required checks — see [`autonomous-pr-loop.md`](../autonomous-pr-loop.md) §One-time setup.

**Where the job is required, and what a `dev` tick means (epic [#2632](https://github.com/d-hinders/Haven-AI/issues/2632)).** Measured against the live rulesets on 2026-09-07 (`gh api repos/<o>/<r>/rules/branches/<branch>`): *Design visual regression* is a required check on **both** `main`'s "Dev gate" ruleset and `dev`'s "Haven automerge rules" ruleset today. The epic's owner step **O2** — a GitHub-settings action, not something a pull request can do — removes it from `dev`'s required list and adds it (plus *Frontend browser smoke*, confirmed to already run as a `pull_request`-into-`main` check via `ci.yml`'s trigger, e.g. PR #2634's [run](https://github.com/d-hinders/Haven-AI/actions/runs/34113894751)) to `main`'s. O2 "can happen at any time" (epic body) and is independent of this slice; this paragraph describes the intended split rather than asserting it has landed. **Once O2 lands:** a red *Design visual regression* on a `dev` PR is advisory — informative, worth reading, but not a merge blocker — while the same red on a `main`-bound PR (a promotion, or a `hotfix/*`) still blocks. Re-check the live ruleset rather than trusting this paragraph's date if the two ever disagree. **Before reporting a frontend PR shipped, confirm this job's conclusion on the head SHA you RE-READ at that moment** — `node scripts/ci/verify-merged-head.mjs <pr>`, or `gh pr view <pr> --json headRefOid` and then `check-runs` on what it returns. Merged-state alone doesn't prove the job ran green, and a SHA captured earlier is a **third** SHA-class trap on top of the two above ([#2116](https://github.com/d-hinders/Haven-AI/issues/2116)): `gh pr update-branch`, a `dev` merge to clear `DIRTY`, and auto-merge's own branch update each move the head between opening and merging, and the superseded run's checks are then `cancelled` by `concurrency` — which is neither a failure nor a pass.

**What the gate can and cannot see, and why it is denominated in pixels rather than percent ([#1805](https://github.com/d-hinders/Haven-AI/issues/1805), [#1760](https://github.com/d-hinders/Haven-AI/issues/1760)).** Three knobs, all mis-set at once, and the reasoning is recorded next to the numbers in `e2e/design-system.visual.spec.ts` rather than restated here. The parts a contributor needs at this level:

- **The budget is an absolute pixel count, not a ratio.** A `maxDiffPixelRatio` grows with page height while the app shell does not, so 0.5% of a 29,012px-tall capture was a 56,573-pixel allowance against a 21,840-pixel TopBar — the whole chrome could change and pass, and in [#1804](https://github.com/d-hinders/Haven-AI/pull/1804) it did. Do not reintroduce a ratio "as well": Playwright takes `Math.min` of the two, so a ratio beside a small floor is inert.
- **`/design-system` is compared whole-page AND as scoped captures of the app shell's chrome** — the top bar on both viewports, and the sidebar on desktop ([#1820](https://github.com/d-hinders/Haven-AI/issues/1820)). One number cannot be both loose enough for page-wide churn and tight enough for a 56px band that is 0.2% of the image, so a shell change shows up as a small, readable image diff instead of being absorbed. That absorption is measured, not feared: recolouring the sidebar's three nav group headings one token sideways moves 366 pixels on CI, which the scoped capture fails at 3.66x its budget while the whole-page capture **passes** under its 500 (both halves were run; the scoped assertion short-circuits the full-page one, so the counterfactual needs its own run). Quote CI's number, not your laptop's — the same mutation is 282 px rendered on macOS. The sidebar is desktop-only because below `lg` it is an off-canvas drawer that is not in the pristine capture at all — measured on the element, not on pixels: at 390px the aside is `position: fixed` with `translateX(-240px)`, so its bounding rect is `x: -240, right: 0` and it contributes nothing to the capture. Do not "confirm" that by checking whether the mobile baseline's x=0..239 band is white; it is not, and that is the *consequence* of the drawer being absent — being `fixed` it reserves no space, so `<main>` paints straight through the band. An earlier draft of this bullet asserted the whiteness off a too-sparse sample and was simply wrong. Adding a scope means adding a locator: locate it **structurally** (both use an xpath anchored on `#main-content`, never a class or a bare tag) and assert `toHaveCount(1)`, because a locator that silently matches the wrong element is the failure this family of gates exists to close.
- **A scoped capture sees the resting state only — a DRIVEN spec is how a state gets covered ([#1863](https://github.com/d-hinders/Haven-AI/issues/1863)).** Nothing is focused, hovered or open in a screenshot, so no amount of extra region reaches a focus ring: `e2e/focus-visible.visual.spec.ts` drives keyboard `Tab` onto a control, asserts it is there, and captures the region around it. Four rules that cost real measurements to learn. **(1) Never hard-code a Tab count** — under `next dev` the tab order starts with three `NEXTJS-PORTAL` devtools nodes that do not exist in CI's standalone build, so press Tab until `document.activeElement` *is* the target node and throw if it never arrives. **(2) One `test()` per control**, because several `toHaveScreenshot` calls in one test short-circuit at the first failure and turn a mutation's blast radius into a guess. **(3) Assert the state before the pixels** — focus landed, `:focus-visible` matches, and the computed style actually *paints*; a driver that silently focuses nothing yields a resting-state baseline and the gate is then green forever about the thing it exists to see. **(4) "Solid 2px" is not proof of an indicator:** Tailwind's own `outline-none` compiles to `outline: 2px solid transparent`, so check the colour's alpha, not just the style and width — the first version of that assertion passed a control with no visible ring at all, and only a mutation said so. **(5) A state you cannot render is a coverage gap, not a scope decision ([#1873](https://github.com/d-hinders/Haven-AI/issues/1873)).** That spec reached 6 of 11 indicators because `AgentCard`'s footer renders at most 3 of its 8 controls at once — `isOperational`/`isRevoked`/`isArchived` are mutually exclusive and `canUseWalletActions`/`isDelegationAgent` split the operational branch — and the shared `mockHavenApi` fixture serves one active legacy agent. Reaching the rest is **fixture** work: seed the states in the spec's OWN `page.route` override with `route.fallback()` for everything else, never in `e2e/fixtures/haven-api.ts`, which twelve other specs call and four of them render. Two rules come with it. **Seeding a state is not rendering the branch** — assert the row's full control set before capturing, because a field the component ignores leaves the default branch rendered and the new baseline is a silent duplicate of an existing one. And **a control behind a disclosure is opened with Tab + Enter, never `.click()`**: `:focus-visible` keys on the last input *modality*, so one mouse gesture turns every later focus capture in that run into a resting-state capture. Do not read "there is a capture of X" as "X is covered"; ask which *state* was captured.
- **(6) Before writing the fixture, establish that the state is REACHABLE — and report the ones that are not ([#1924](https://github.com/d-hinders/Haven-AI/issues/1924)).** #1873's rule says a state you cannot render is a coverage gap rather than a scope decision; this is the other half, learned by hitting it four times in one issue. Some states are not reachable *from the fixture layer at all*, and the honest move is to say so and file it, because **a fixture that reaches a state the product cannot is worse than no capture**: it is green forever about something no user can see. Three shapes, all measured on `AgentPanel`/`AgentCard`/`ErrorBoundary`: a state behind a **route guard** (`AgentPanel`'s no-account `EmptyState` is `!safeAddress`, but `ProtectedRoute` redirects a user with no safes to `/onboarding` and renders `null` meanwhile, so the branch never mounts — seeding `safes: []` yields a blank page, which is what sends you to the guard; the guard's one apparent hole, a legacy user with `users.safe_address` and no `user_safes` row, is closed **by design** on every path that writes either side, and the single un-transacted exception is recorded in the spec rather than rounded off); a state behind a **signature** (the "Finalizing"/"taking longer" empty states need `onSetupUpdated` with a non-null `delegateAddress`, and both call sites sit behind wallet or ERC-7710 signing — the delegation one *looks* pure-API until you follow it back to `BudgetGrantAction`); and a state behind a **contract the backend cannot violate** (`ErrorBoundary` needs a child to throw; every unguarded access in the authenticated tree is on a shape the backend validates at the door — `chain_id` against `isSupportedChain`, `agent.allowances` against a wire type that makes it a required array). Ask "can the product produce this?" *before* "can I make the mock produce this?" **A fourth candidate, `UnmanagedDelegateCard`, was listed here as unreachable and is not ([#1930](https://github.com/d-hinders/Haven-AI/issues/1930)) — the correction is the more useful half of this rule.** The stated reason was that it is fed by viem/wagmi RPC reads "which `page.route` does not intercept at all". That was never true: viem's transport is `fallback()` over plain `http(url)` endpoints, so a chain read leaves the browser as an ordinary JSON-RPC POST and Playwright routes it like any other request. What was actually missing was an *answerer*, and #1935/#1971 built one — the same `makeAllowanceChainFixture` the paragraph above describes, extracted to `scripts/allowance-chain-fixture.mjs` so a spec can import it. The judgment was also made while `lib/wagmi.ts` registered a transport for only one of the two chains Haven offers, so `usePublicClient` was `undefined` and *no* read happened at all; **a reachability verdict taken under a defect is worth re-deriving once the defect is fixed**, which is the transferable lesson here. Three shapes remain, not four.
- **Do not replace `waitForLoadState('networkidle')` without replacing what it incidentally bought ([#1924](https://github.com/d-hinders/Haven-AI/issues/1924)).** `networkidle` is the wrong question for a capture (it is about unrelated wallet sockets, not about whether the subject has settled) and under `next dev` this app never reaches it — wagmi/WalletConnect hold connections open, so the wait burns the whole test timeout. But it also waits for **lazily-loaded chunks**, and `(authenticated)/layout.tsx` loads `Sidebar` with `dynamic(..., { ssr: false })`. Until that chunk mounts, `<main>` spans the full viewport; after it, the sidebar takes 240px. Measured at 1280x800: `main.clientWidth` 1280 → 1040, `AgentCard` 504 → 480, a captured banner **462 → 438**. A capture taken in that window fails as a **size mismatch**, which reads like a layout regression rather than a race and costs a diagnosis before it costs a rerun — and it reproduced on only 1 run in 4, i.e. exactly often enough to be written off as an unrelated flake later. Wait for the sidebar explicitly (`button[aria-label="User menu"]`), then let each test's own `toHaveCount(1)` wait for its subject.
- **The gates are layered, and a mutation tells you which layer you are actually in.** Measured on the Sidebar's Log out item ([#1863](https://github.com/d-hinders/Haven-AI/issues/1863)): swapping its ring tone `danger → brand` is caught by the **structural** rule (#1792's "hovers danger, focuses brand") and proves nothing about pixels — that mutation was chosen first and had to be thrown away. Dropping `ring-inset` so the ring paints outset and is clipped by the popover edge — the legibility residual #1831's design pass could not close — leaves **all 19 focus-ring assertions and design-lint green** and moves 1,576 px in the driven capture. That is what "new coverage" has to look like before you claim it: a defect every existing gate passes.
- **Run-to-run jitter in this environment is zero**, measured across four captures and four separate CI runs — antialiased pixels are excluded by pixelmatch before any budget applies, so the budget was never what absorbed AA. If you are tempted to widen a tolerance, measure first: set the budget to 0 on a branch and read the count the failure prints.
- **Regeneration has two modes, and the default is the safe one ([#2218](https://github.com/d-hinders/Haven-AI/issues/2218)).** The *Update visual baselines* dispatch takes a `mode` input. Leave it alone — `changed` is the default and the ordinary case needs no inputs at all. In the installed Playwright (1.60.0, verified in `playwright/lib/matchers/expect.js`, not read off another version's docs) the two values take different code paths: `changed` passes the baseline in as `expected`, runs the comparison **with this spec's `threshold` and `maxDiffPixels`**, and rewrites only what actually **fails**; `all` passes `expected: undefined`, so no comparison happens at all and the file is rewritten whenever the **bytes** differ. (A bare `--update-snapshots` with no value resolves to `changed` via the flag's `preset` in `program.js`; no flag at all means `missing`.)

- **Read the tick as narrowly as it is true — the job now says what it compared ([#2318](https://github.com/d-hinders/Haven-AI/issues/2318)).** A green *Design visual regression* is routinely read as "the UI is unchanged". Before #2318 that reading was licensed for `/design-system` and four element clips on `/agents`, and at that date for nothing else: **no product screen had a whole-page baseline at all.** Two things changed, and the second is the part that keeps working as the product grows. `/dashboard` and `/transactions` gained whole-page desktop baselines (`e2e/product-routes.visual.spec.ts`), and the job now runs `scripts/ci/visual-baseline-inventory.mjs`, which reads the committed PNGs and prints **exactly which baselines were compared** into the job summary — on failure as well as success. It reads the directory rather than a hand-maintained list, so it cannot drift from the thing it describes (#1874's failure mode), and it exits non-zero on an empty baseline tree, the case where the gate above passes having compared nothing. **What it deliberately does not do is enumerate what is NOT covered** — that set is the whole product minus these, so it states the negative as a sentence instead of inventing the authority to derive it. Everything absent from that summary — the connect flow, agent detail, onboarding, login/signup, every modal, and both `/accounts` and `/agents` as whole screens — has no pixel baseline, and the tick says nothing about it.

- **Adding a route to the blocking set is a decision about FLAKE first, coverage second.** `e2e/product-routes.visual.spec.ts`'s header carries the measured candidate table and the reasoning; the two rejections are worth knowing before proposing a third route. `/agents` renders a real `readContract` against a chain the harness does not have (`ContractFunctionExecutionError: … "isModuleEnabled" returned no data ("0x")`), so a whole-page baseline there would photograph a screen that depends on how an unmocked network call resolves — and a flaky blocking visual check is worse than a narrow one, because it teaches everyone to re-run red checks ([#2329](https://github.com/d-hinders/Haven-AI/issues/2329); [#2354](https://github.com/d-hinders/Haven-AI/issues/2354) records load alone causing a failure). `/accounts` is rejected on fixture fidelity: [#2225](https://github.com/d-hinders/Haven-AI/issues/2225) is filed against `scripts/screenshot.mjs`, and `e2e/fixtures/haven-api.ts` has the identical defect at `:348`/`:365` — both balance endpoints key on the path prefix and ignore the address — so a baseline there would be a blocking, re-blessed-forever PNG of a screen that is address-blind by construction. Fix #2225 in **both** fixtures first.

- **A route whose content is time-relative needs its clock frozen, and the freeze needs an assertion.** `lib/format.ts`'s `timeAgo` buckets against `Date.now()` while the fixtures carry fixed timestamps, so a `/transactions` baseline renders `3mo ago` today and `4mo ago` on a date nothing in this repo controls — a blocking gate going red on a calendar boundary, weeks after the commit it will be blamed on. `product-routes.visual.spec.ts` pins the instant with `page.clock.setFixedTime` (not `install`, which would pause React's scheduler) **before** `goto`, and then asserts the literal string the frozen clock must produce, so a clock that stops working fails by name instead of as an unattributable pixel diff. Assume any product route needs this until you have checked; `timeAgo` reaches `/dashboard`, `/agents`, `/transactions`, `/accounts` and `/accounts/[safeId]`.

- **Budgets are measured per capture family, not inherited.** `design-system.visual.spec.ts`'s 500-pixel full-page budget is argued from a 22.7M-pixel page; `product-routes.visual.spec.ts` uses **150**, because on these much shorter captures 500 swallows real regressions. Both numbers come from mutation, and the mutations are the evidence: a one-token label recolour on `/dashboard` measures 366 px and a one-sentence copy change on `/transactions` measures 479 px — **both under 500, both over 150.** Re-derive the number if you add a capture of a different size; do not copy it.

  **Why the default had to change.** It was a hardcoded `all`, so any dispatch could re-bless a baseline that was passing. Measured on PR #2217: a dispatch aimed at `agentcard-banner-stranded-desktop.png` also rewrote `unmanaged-delegate-card-desktop.png` — max channel delta **1**, a one-pixel column at x=0, **180 px of 266,448**, its test passing, and its fixture seeding `agents: []` so the changed component never rendered in it at all. Caught only because someone diffed all 22 blob hashes by hand; reverted in `02e3b719`. A re-blessed baseline looks exactly like a clean run, which is why nothing else would have found it.

  **Why `all` is still there, and when you actually want it.** #1760's point stands: because `changed` re-applies this gate's tolerance, drift that sits *under* budget is not merely un-failed but **un-refreshable** — that is the mechanical reason #1760's 2,084-pixel stale TopBar band survived every regeneration anyone dispatched, each reporting "Baselines unchanged — nothing to commit." The tolerance decides what FAILS; it must not permanently decide what can be REFRESHED. So `all` remains, as a deliberate choice rather than as what you get by saying nothing. Under `all` the `expected` input is **required** — list the baselines you expect to move, or `*` to accept a full refresh.

  **The audit runs either way.** `scripts/ci/baseline-audit.mjs` runs *before* the commit step and prints every baseline that moved with its before/after blob hash, into the job summary and the commit message — the manual audit that caught #2217, performed by the workflow instead of by whoever remembered. It only *fails* the run when you declared an `expected` set and something outside it moved, or when you chose `all` and declared nothing; the failure names the file, and nothing is pushed. Declaring `expected` under `changed` is optional and worth doing when you already know what you came for. **Do not read the safer default as making diagnosis optional** — a broken render *fails* comparison, so `changed` blesses it too. Diagnose the diff PNG first, in either mode.
- **Diagnose a diff before regenerating.** Same dimensions plus a continuous colour difference is drift; a clean horizontal cut, or a size-mismatch line in the failure, is a height change. Scan the diff PNG by row rather than dispatching the regeneration workflow first — `all` will bless whatever renders, including a broken render.

**Wire shapes come from the spec, not from you (#1447).** `npm run lint:wire-types` is a **blocking CI job** on the frontend surface. It counts hand-written types in `hooks/` and `types/` that declare a snake_case property — the API's convention — against a shrink-only baseline (`packages/frontend/wire-type-baseline.json`, frozen at 18 after #1445's migration). If the route is in the spec, import the type instead of restating it:

```
import type { ApiSchema } from '@haven_ai/core'
export type Thing = ApiSchema<'Thing'>
```

If the route is not in the spec yet, document it there first — [#1446](https://github.com/d-hinders/Haven-AI/issues/1446) tracks that backfill, and the 18 baselined shapes are waiting on it. If a type is genuinely UI-side and merely happens to carry a snake_case field, mark it `// ui-local: <reason, at least 20 chars>` on the line above; a bare marker does not exempt. After removing shapes, tighten with `npm run lint:wire-types:update` (it refuses to ratchet upward). The gate reads casing, so it does **not** see a wire shape that uses camelCase, and it cannot see an anonymous inline shape (`useState<{ tx_hash: string }>`) because there is no declaration to find. Both holes are stated in the script's header with live examples; review is the backstop.

**The vitest suite reports on the machine under contention, and now says so ([#2319](https://github.com/d-hinders/Haven-AI/issues/2319)).** Four suites — `DelegationSendModal`, `InfoModal`, `UnmanagedDelegateCard`, `Modal` — once went red on `Test timed out in 5000ms` in a full run that took 336 s instead of ~122 s. The first attribution, a new `it.each` guard, measured at 146 ms against a 214 s delta, so it was withdrawn and the question was measured instead. `vitest.config.ts` sets no `pool`, `maxWorkers`, `testTimeout` or `isolate`, so the suite runs vitest 3's defaults: the `forks` pool at `cores − 1` workers (11 on a 12-core machine), every file in its own module graph, 5000 ms per test. The per-file isolation is what makes the first test in a file the expensive one: it pays the cold React + jsdom render, and a file whose first test opens a `ui/Modal` pays the most — **250–450 ms idle for that first test, ~40 ms for each later one in the same file**. Measured across the full suite at 1, 2, 4, 8 and 11 workers on the same tree, that first test held flat at 1–2 workers (242 / 433 / 273 / 383 ms), rose at 4 (488 / 603 / 530 / 382) and reached 1.2–3.6 s at 8–11 — **proportional to load, not a fixed wall** — while the file count stayed at 136 and vitest's `tests` phase went 73 s → 400 s. At 8 workers four *different* suites timed out (`CatalogSubmitModal`, `ConnectAgentModal`, `Sidebar`, `ProfileClient`): which files tip over is luck, and the four named on the issue are only the ones whose first render is heaviest. The load in every one of those runs was external, and quantified — a sibling session's own 11-fork vitest run on the same machine held the 5-minute load average at 115 on 12 cores — which is the issue's precedent (eight orphaned vitest processes, one 9 h old) seen live. Reproduced deliberately on clean `dev`: twelve `yes` burners alone (load average 311) slowed the four first tests to 1.8–3.0 s and turned nothing red — the kernel shares CPU fairly; add a second full vitest run of the same suite (load average 200–410) and `InfoModal` times out at 6.4 s while the other three land at 4.2–4.8 s, with `ReplaceSigningKeyModal` — another Modal-rendering file — losing two tests the same way, and 1349 of 1352 tests still green. The load that bites is competing jsdom workers, not CPU alone.

Three things follow, and they are the posture rather than a fix. **`testTimeout` stays at the default.** A budget raised until a contended run passes is one at which a hung test is no longer detected, on every file at once; the backend reached the same conclusion twice (#2329, #2354) and `src/__tests__/suite-timing-posture.test.ts` pins it — the config sets no `testTimeout`, and none of the pinned suites carries a per-test override in any spelling — positional after the body (literal or `const`), `{ timeout }`, the `it.each(...)(…)` curried form, or a runtime `vi.setConfig({ testTimeout })` — each shape mutation-proved against the detector's positive control and against `Modal.test.tsx`. `UnmanagedDelegateCard.test.tsx` was the fourth suite #2319 measured; #2331 retired it with the legacy Safe surfaces, so the pinned list carries three. **Nothing in those files is made "faster".** Fake timers and `act()` remove waits; the cost here is the render itself, and the two real-clock `waitFor`s in `Modal.test.tsx` resolve on their first check because the focus effect is synchronous. **The failure names the machine.** `src/__tests__/setup.ts` runs an `afterEach` (it fires after a timed-out test too) that, for any test over 2000 ms or timed out, prints the 1-minute load average against the core count and says whether the machine was contended — `[#2319 slow-test] … CPU-contended: 1-minute load average 41.2 on 12 cores (3.4x) … Re-run the file alone before reading it as a defect.` Read that line before reading a frontend timeout as a defect, and run `ps aux | grep vitest` before a full-suite timing claim: an orphaned run from another worktree is the usual load. The signature is not in `autonomous-pr-loop.md`'s CI flake list because it has never been observed in CI, only locally.

## 5. Review (two passes: code + rendered)

An `area:frontend` diff gets **both** reviews, because a code-only reviewer is only as good as one that never sees the screen:

1. **`haven-reviewer`** (code) with UI context, checking the diff against [`product/design-review.md`](../../product/design-review.md) and [`copy-guidelines.md`](../../product/copy-guidelines.md).
2. **`haven-design-reviewer`** (rendered) — a dedicated visual/UX/design-system pass keyed off the [#896](https://github.com/d-hinders/Haven-AI/issues/896) screenshots (desktop + mobile) rather than the diff: visual weight, spacing rhythm, alignment, state coverage (empty/loading/error), touch targets, focus-visible, and design-system adherence that only shows up rendered ([#900](https://github.com/d-hinders/Haven-AI/issues/900)). Its canonical role is [`design-reviewer.md`](../../../.agents/skills/haven-agent-workflow/references/design-reviewer.md). Give it the `.screenshots/` PNGs; if a rendered surface has none, that's its first finding.

A finding from **either** pass pauses the merge **at `blocking` or `should-fix`**; a `nit` does not (§6 has the rule and the severity definitions, stated once — this line only says both passes feed it). Both roles label every finding with one of those three; an unlabelled finding is read as `should-fix`, because the safe default when severity is missing is the one that pauses. Two automated aids back this up: the Vale terminology rule (`.vale.ini`, scoped to `docs/product`) for docs copy — advisory — and **`npm run lint:copy`** (`scripts/frontend-copy-lint.mjs`), which flags banned multi-word terms in user-facing frontend copy (`app/` + `components/`, plus the individually allowlisted prose files in the script's `SCAN_FILES` — `lib/agent-skill-bundle.ts`, `lib/agent-handoff.ts`, `lib/agent-pause-copy.ts`, `lib/stranded-funds-copy.ts`, `lib/passkeyLabels.ts`, `lib/transaction-labels.ts`, `lib/transaction-presentation.tsx` and the SDK's `skill-content.ts`, #2317/#2333). **`lib/` and `hooks/` are otherwise unscanned**, so a prose file you add there is invisible to this gate until you name it in `SCAN_FILES`. **If you extract copy out of `components/` into `lib/`, add the file to `SCAN_FILES` in the same PR** — that extraction pattern (#2195, #2230) silently narrows this gate every time it is applied. Since #2333 the naming is enforced rather than remembered: a `*-copy.ts` / `*-labels.ts` / `*Labels.ts` / `.tsx` file under `src/lib` that is not allowlisted **fails the run naming the file**. It matches names, not content, so an off-convention name still evades it — see `copy-guidelines.md` § Enforcement for that ceiling. The copy lint is a **blocking CI job** ([#902](https://github.com/d-hinders/Haven-AI/issues/902)): it fails the PR on any new banned term beyond the shrink-only `packages/frontend/copy-lint-baseline.json`. For anything it can't catch (it's conservative — multi-word phrases only), check changed strings against `copy-guidelines.md` by hand. Use `// copy-lint-ignore` for a legitimate advanced/developer-facing surface; after cleaning existing debt run `npm run lint:copy:update` to tighten the ratchet.

## 6. Merge policy (UI)

A non-money frontend PR **auto-merges** on green CI + verification **unless** either §5 pass — `haven-reviewer` (code) or `haven-design-reviewer` (rendered) — raises a **`blocking`** or **`should-fix`** UX, copy, or design-system finding — then **pause**. This is the `area:frontend` case of the canonical skill's [Merge Gate](../../../.agents/skills/ship-next/SKILL.md#merge-gate). Money-path UI still follows the `money.md` bar (characterization tests, CASP guardrails); since #1024 that no longer includes a merge pause.

**The three severities, because the gate now turns on them ([#2636](https://github.com/d-hinders/Haven-AI/issues/2636)):**

| Severity | What it means | Effect |
|---|---|---|
| `blocking` | The rendered result is wrong, unusable, or off-standard in a way a user would hit — broken layout, unreadable contrast, an unreachable state, a control a viewport cannot operate. | Pause. Fix, re-capture, re-review. |
| `should-fix` | Real and worth fixing before merge, but not user-breaking — spacing rhythm off, a primitive hand-rolled where one exists, copy that fights the guidelines. | Pause. Same path. |
| `nit` | A preference or a one-line polish the reviewer would not hold a PR for, and says so. | **No pause.** See below. |

**Focus indicators are deliberately not in that list.** `npm run screenshot` captures a page as it loads and presses no keys — neither `scripts/screenshot.mjs` nor `full-page-capture.mjs` calls `.focus()` or `keyboard.press` — so a `:focus-visible` ring never appears in the PNGs this pass reads, and a reviewer working from them cannot see one missing. Focus coverage belongs to `e2e/focus-visible.visual.spec.ts`, which drives real `Tab` presses and pixel-gates the result (§4's driven-spec rules). If your diff adds a new focusable control, that spec is where it gets covered — a rendered-design finding cannot stand in for it.

**A `nit` takes one of two paths, and neither is a re-capture.** Fix it in place when it is genuinely a one-line change and the rendered output does not move — a token swap, a copy tweak, a class rename — and say so in the PR. Otherwise **drop** it under the PR body's **Not filed** list with the screenshot attached and the reason, and merge — a nit is not filed as its own issue ([#2767](https://github.com/d-hinders/Haven-AI/issues/2767)). What is **not** available is a third path where a nit is argued away silently: the severity is the reviewer's call, not the author's, and an author who thinks a `should-fix` is really a nit is in the "disputed" case below, which pauses and asks.

Before #2636 every finding paused, nit included, and clearing one cost a re-capture and a re-review — the frontend median was 18 min against 6 for everything else, p90 3.4 h. The pause was doing real work at the top two severities and almost none at the bottom, where it mostly bought a second render of an unchanged screen.

**Clearing the pause does not need a human ack ([#1968](https://github.com/d-hinders/Haven-AI/issues/1968)).** Fix the finding, re-capture the changed surface (`npm run screenshot`), re-run the pass that raised it over the *new* PNGs — and a clean re-review re-arms auto-merge on its own. The reviewer pass is the judgement layer; asking a human to re-affirm a verdict the reviewer just gave adds latency, not safety, and the ack was reliably a rubber stamp in practice.

What keeps that a gate rather than a formality is the shape of the re-run. Three cases still **pause and ask the user**, and they are the ones an "it's addressed" comment quietly collapses into the happy path:

1. **No re-review.** The author asserting the finding is fixed is not a verdict. A stale-evidence re-review — the reviewer handed the PNGs the finding was raised on — is the same failure with extra steps, which is why the re-capture is named above and not implied.
2. **A new finding on re-review.** The fix moved pixels; a clean pass on the old finding says nothing about what the fix introduced. New finding → new pause, same rules.
3. **Deferred or disputed.** "Cleared" means fixed-and-re-reviewed. Re-labelling a `blocking` or `should-fix` finding as a nit in order to ship past it is a product call, and product calls are the user's — this is the case the old blanket pause was really protecting, and it is the only one worth keeping. Note what #2636 did and did not change here: a finding the **reviewer** labelled `nit` never reached this case in the first place, and one the **author** wants to downgrade still does.

**Worked example — a nit on an existing route, which is the common case.** A PR changes the empty-state copy on `/transactions`. Trigger 3 applies (it changes what the screen shows), so `npm run screenshot` runs against the pre-warmed server from *Prepare* and both passes are dispatched together over the PNGs. `haven-design-reviewer` returns one finding: *`nit` — the empty-state icon sits 2px above optical centre against the new two-line copy; `.screenshots/transactions-1280.png`.* That is a one-line class change and the author makes it in place.

**What happens next is the whole point: nothing.** No re-capture, no re-review, no second dispatch, no human ack. The PR body records the finding, its severity, and that it was fixed in place — `haven-design-reviewer: passed @ <sha> — 1 nit (icon optical centre), fixed in place, no re-capture` — and auto-merge stays armed. Under the old rule this identical finding cost a `npm run screenshot` re-run, a second `haven-design-reviewer` dispatch over fresh PNGs, and the wall-clock of both.

Change one thing and the answer changes with it. Had the reviewer labelled it `should-fix` — say the icon were visibly misaligned rather than optically so — the pause applies, the fix moves pixels, and the re-capture is exactly what proves the fix did not introduce a second problem. Had the fix needed a layout change rather than one class, it is no longer a one-line change: drop it under **Not filed** with the PNG attached, or re-capture. The severity and the size of the fix are separate questions and both have to come out small.

**Hard definition-of-done for a diff that adds a primitive ([#898](https://github.com/d-hinders/Haven-AI/issues/898)):** run `npm run design:coupling:strict -w packages/frontend` before opening the PR. A non-zero exit (a new `ui/`/`haven/` export missing from `/design-system` and not `// design-system-exempt`-marked) means the **Design-system coupling (strict)** required check will fail — document the primitive on the reference page first. Running it locally only saves the round trip; the gate itself is in CI ([#1023](https://github.com/d-hinders/Haven-AI/issues/1023)), so it applies to every author.

**It reads the working tree, and it says what it compared ([#2826](https://github.com/d-hinders/Haven-AI/issues/2826)).** Every run opens with `design-system coupling: comparing <range>` — `origin/dev...HEAD + working tree` locally, the pull request's own range in CI. That line exists because the scope used to change silently: a local run diffed committed work alone, so a primitive that was written but not yet committed produced `no undocumented primitives added` and exit 0, and the required check then failed on the same tree. This step runs during review — before the commit — which is exactly the window that was blind. The local scope is now the union a reviewer would look at (committed branch work, staged and unstaged changes, untracked files); it can only be wider than CI's range, never narrower, so it cannot go green on something CI turns red. The docs coupling gate has read the working tree since [#1076](https://github.com/d-hinders/Haven-AI/issues/1076) for the same reason.
