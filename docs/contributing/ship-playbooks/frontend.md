# Frontend playbook

Loaded by `ship-next` for `area:frontend` issues. The goal: a UI issue is shipped on Haven's UX standards without the contributor having to name them. This playbook **links** the standards; it does not restate them.

## 1. Required reading (before implementing)

Read, in order — these are `AGENTS.md` → "Required Reading For UI Work":

1. [`product/README.md`](../../product/README.md) — product doctrine, IA, money-movement clarity, accessibility, and closeout checks.
2. [`product/design-system.md`](../../product/design-system.md) — tokens, typography, cards, buttons, motion, surface hierarchy.
3. [`product/copy-guidelines.md`](../../product/copy-guidelines.md) — user-facing wording and banned technical terms.
4. [`product/screen-recipes.md`](../../product/screen-recipes.md) — repeatable screen structures.
5. [`product/design-review.md`](../../product/design-review.md) — the finishing checklist (also used in §5).

If a `/design-system` route exists, inspect it before editing UX.

## 2. Reuse first

Inspect `packages/frontend/src/components/ui` (primitives) and `packages/frontend/src/components/haven` (domain components) before adding UI. Prefer composition; do **not** invent new card styles, spacing, shadows, radius, or typography unless the existing system genuinely can't express the need. Use the v2 tokens in `globals.css` and the Tailwind aliases.

**Absorb a pattern on its 2nd occurrence, not its 12th ([#901](https://github.com/d-hinders/Haven-AI/issues/901)).** If this diff writes the same markup shape a second time — a header band, badge, row, empty-state, inline `<svg>`, address slice — or re-creates something a primitive already covers, extract it into a `ui/`/`haven/` primitive **and** document it on `/design-system`, in this same PR. This is the Captain Self-Check Preflight's **Pattern Absorption** item; it's the mechanism that prevents the debt clusters epic #859 had to clean retroactively. Only skip it if the two uses will genuinely diverge — and say so.

**A new primitive must land on `/design-system` in the same PR ([#898](https://github.com/d-hinders/Haven-AI/issues/898)).** The design-system coupling gate flags any exported component added under `components/ui/**` or `components/haven/**` whose symbol never appears on `app/(authenticated)/design-system/page.tsx`. Two CI jobs, on every PR however it was opened ([#1023](https://github.com/d-hinders/Haven-AI/issues/1023)): **Design-system coupling** posts the sticky comment that explains the finding, and **Design-system coupling (strict)** blocks on it. Add a showcase entry (usage + variants) alongside the primitive, or — for a genuinely internal export, not a reusable primitive — mark the export line `// design-system-exempt: <reason>`. Check locally with `node packages/frontend/scripts/design-system-coupling.mjs --strict`.

## 3. Captain Self-Check Preflight

Run the matching items from the **Captain Self-Check Preflight** in [`../ai-agent-workflow.md`](../ai-agent-workflow.md) for the traps the diff touches — e.g. numeric formatters, counter/summary buckets, conditional copy predicates, async hook generations, signer-readiness gates, animation discipline, inline-gate placement, cross-surface display drift, loading-state inference. Each is one grep or one quick read. Do this **before** review so the reviewer finds fewer issues.

## 4. Verification

Verify the change in the **browser**, or — when the browser path is unavailable/flaky — add a **named headless equivalent** (vitest) that covers the skipped animation, layout, routing, loading, or interaction risk. Include empty, loading, error, and success states when the screen can enter them; check mobile and desktop.

**Which viewports actually gate ([#1768](https://github.com/d-hinders/Haven-AI/issues/1768)).** The *Frontend browser smoke* job runs **both** Playwright projects on every frontend PR, with no dispatch required:

| Project | Emulation | Runs | Gates a PR |
|---|---|---|---|
| `chromium-desktop` | Desktop Chrome — 1280×720 viewport, fine pointer, no touch, DSF 1 | every `e2e/*.spec.ts` **except** `*.mobile.spec.ts` | yes |
| `chromium-mobile` | **Pixel 5** — 393×727 viewport, coarse pointer, touch, Android UA, DSF 2.75 | `e2e/*.mobile.spec.ts` only | yes |

(Numbers read off Playwright's own `devices` table at the pinned version, not from memory. Pixel 5's `screen` is 393×851; the **viewport** — what the page actually gets — is 393×727.)

Both projects also inherit `SUITE_IGNORE` (`e2e/live/**`, and `*.visual.spec.ts` unless `VISUAL_REGRESSION=1`). That constant exists because a project-level `testIgnore` **replaces** the config-level one instead of extending it — a project that declares its own must spread `SUITE_IGNORE` back in, or the unmocked live smoke silently rejoins the fast suite.

Plus the separate *Design visual regression* job, which pixel-compares `/design-system` at **1280** and **390** (`scripts/evidence-viewports.mjs`) — but under `chromium-desktop` at DSF 1, by setting the viewport inside the spec. That is a pixel gate, not a device gate: it sees layout, never touch or hit-testing.

Before #1768, `chromium-mobile` existed but only a `workflow_dispatch` with `ui_suite=full` ever ran it — so **no mobile viewport gated anything**, which is a large part of why [#1749](https://github.com/d-hinders/Haven-AI/issues/1749) (primary navigation unopenable below `lg`) shipped. That input is now removed and both projects are unconditional.

**Writing a mobile test:** name the file `*.mobile.spec.ts` and it runs under real Pixel 5 emulation. Do **not** reach for `test.use({ viewport: … })` inside a desktop spec — it narrows the window but leaves `maxTouchPoints` at 0, the pointer fine and the UA desktop, so touch and hit-testing behaviour is not actually covered. Conversely, keep viewport-independent behaviour out of `*.mobile.spec.ts`: the two projects run disjoint spec sets on purpose, and duplicating a spec buys nothing but CI minutes. `e2e/navigation.mobile.spec.ts` is the reference, including the meta-guard that fails if the project ever stops being device-emulated.

**Measure overflow on the scroll box, not the document.** The authenticated shell is `overflow-hidden`, so content wider than the screen never grows `documentElement.scrollWidth` — which meant the page-level `expectNoHorizontalOverflow` helper **could not fail** on any authenticated route. Found by the #1768 mutation, not by reading, and fixed in [#1771](https://github.com/d-hinders/Haven-AI/issues/1771): the shared helper now measures `<main id="main-content">`'s own scroll box alongside the document, and `hasOverflow` is the union, so every caller gates for real. Assert `contentRegionFound: true` on authenticated routes — otherwise a `<main>` that is missing or not yet laid out measures `0` and reads as "fits".

Two failure modes, and they are not the same defect: `documentOverflows` means content escaped the page box and — under the shell's `overflow-hidden` — is genuinely **unreachable**; `contentOverflows` means `<main>` (which is `overflow-y-auto`, so `overflow-x` computes to `auto`) is wider than its box, dragging the **whole content pane into horizontal scroll** instead of the offending element scrolling inside its own `overflow-x-auto` wrapper. The second is reachable but wrong — it is the [#1772](https://github.com/d-hinders/Haven-AI/issues/1772) shape. Note the measurement compares two scroll boxes rather than walking ancestors, so an `overflow-hidden` *between* them still hides evidence; `position: fixed` overlays are invisible to both, which is why an open dialog needs its own measurement ([#1773](https://github.com/d-hinders/Haven-AI/issues/1773), below).

**A spec that opens a dialog and then asserts overflow is measuring the page BEHIND it — assert the overlay separately ([#1773](https://github.com/d-hinders/Haven-AI/issues/1773)).** A `position: fixed` element is laid out against the viewport, so it contributes to the scrollable overflow of neither the document nor `<main>`, and an ancestor's `overflow-hidden` does not clip it either. Measured: a `w-[120vw]` block inside `ReceiveFundsModal` left the assertion green. Use `measureDialogOverflow` beside `expectNoHorizontalOverflow` — a sibling, deliberately not a widened `hasOverflow`, because most callers never open a dialog and unioning would make "no dialog open" read the same as "the dialog fits". Assert `dialogFound` along with `overlayOverflows`, for the same reason authenticated routes assert `contentRegionFound`.

**And measure the whole subtree, not the dialog node.** The obvious anchor — `[role="dialog"]`'s own scroll box — fires on only ONE of the three dialogs, which was found by measuring rather than by reasoning. `ui/Modal` puts `role="dialog"` on the `fixed inset-0` container (so its `clientWidth` is the whole viewport) and `ui/SidePanel` wraps a `flex-1 overflow-y-auto` body; per CSS Overflow §3 that body's `overflow-x` computes to `auto`, so the body is itself a horizontal scroll box, absorbs the overflow and never propagates it outward. Under the same 120vw mutation the dialog node read `0` on both while the nested body read 1129 and 1010. Scanning every box in the subtree also removes the reliance on upward propagation that makes an intermediate `overflow-hidden` a blind spot in the first place. The viewport-absolute numbers are reported and not asserted, per the rule below: the three overlays have three different correct positions, and the side panel's flush right edge read 1280, 1281 and 1282 across three runs at a 1280px viewport.

**A legitimate horizontal scroller inside one of those dialogs will fail these specs, and the obvious fix for that is wrong.** The scan flags any box wider than its own content box; it does not ask whether the box meant to scroll. Excluding elements whose computed `overflow-x` is `auto`/`scroll` looks like the answer and is measurably not: `overflow-y-auto` computes `overflow-x` to `auto`, so that rule exempts `ui/Modal`'s and `ui/SidePanel`'s scrolling bodies — the exact elements that caught two of the three mutation proofs. It would gut the guard, not narrow it. A class-name rule fails the mirror image: it exempts a real defect that happens to carry the class. So exempt the known case **by name at the call site with an issue number**, the way `KNOWN_CONTENT_OVERFLOW` does — assert `offenderCount` and match `worstOffender`, which keeps the check gating on everything else instead of deleting it. A worked example is in the helper's JSDoc.

One trap if you write any subtree-scanning overflow check: **a visually-hidden element reports a large horizontal overflow and is not a defect.** Tailwind's `sr-only` is `width: 1px; height: 1px; overflow: hidden; clip: rect(0,0,0,0)`, so its `scrollWidth` is the full width of the screen-reader text against a `clientWidth` of 1 — the connect modal's `span.sr-only` reported 67px. Exclude it by geometry (skip boxes 1px or narrower), never by matching the class name, which would exempt a real defect that happened to carry the class. Found on the restore half of the mutation proof, which is the half that is easy to skip: the mutation going red says the guard can fire, and only the restore says it fires *for the right reason*.

**Relative measurement is not sufficient for shell-level geometry — anchor at least one assertion to the viewport ([#1779](https://github.com/d-hinders/Haven-AI/issues/1779)).** Any assertion of the form "A relative to B" is blind to A and B moving together, and a shell-level defect moves everything at once. Measured, not argued: mutating the mobile toggle's `fixed` to `relative` drops it into flow as a 32px flex item and displaces the entire app shell — `<header>` and `<main>` both go from x=0 to x=32 — and **three separate mobile specs stayed green**, because the toggle was checked against the header, layering as one element against another, and overflow as a content box against its own scroll box. `contentOverflowBy` still read `361 - 361 = 0`, exactly as it had read `393 - 393 = 0`. No rewording of an individual assertion fixes this; it is a property of the reference frame. So a mobile-shell suite needs at least one measurement against something the defect cannot carry with it — `getBoundingClientRect()` against `window.innerWidth`. The three suites now each carry their own: `header.left === 0` (#1766), the top bar's two viewport gaps (#1749's layering spec), and `<main>` spanning `0 → innerWidth` (#1771's overflow guard, via `contentLeft`/`contentRight`/`viewportWidth` reported — not asserted — by the shared helper, because the mobile shell, the desktop shell and `/login` have three different correct answers).

Two traps this generalises into, both paid for already. **Deliberately do not collapse the anchors into one shared helper every suite calls** — one shared reference frame that everything trusts is the defect itself, one layer up; independent anchors can disagree, a single one cannot. And **an anchor is only real once the mutation has turned that specific spec red**: the first version of the `<main>` anchor above passed the mutation on 3 of 4 routes, because `Sidebar` is `dynamic(ssr: false)` and the measurement ran before it rendered, leaving `<main>` at x=0 — the same silent-no-op shape `contentRegionFound` exists for. Wait for the shell (the `Open sidebar` toggle) before measuring it.

**A known, filed defect is exempted by name, never by deletion.** `navigation.mobile.spec.ts` keeps a `KNOWN_CONTENT_OVERFLOW` map: the route still runs and still asserts rendering and console cleanliness, only the one known-failing assertion is skipped, and only with an issue number and the measured numbers next to it. Dropping the route instead is how a gate quietly stops covering things — which is the defect #1768 exists to close. Delete the entry in the PR that fixes the issue.

**A guard proven at 1280px is not proven ([#1797](https://github.com/d-hinders/Haven-AI/issues/1797)).** `measureDialogOverflow` shipped with three call sites and three mutation proofs, all under `chromium-desktop` — the width where a dialog is *least* likely to overflow. The helper was viewport-agnostic and correct; the coverage was upside down. When you add an assertion about layout, ask which viewport its defect actually lives at, and put the spec there.

Two things that measurement showed and reasoning would not, both worth knowing before you reuse a desktop proof at mobile width:

- **The same mutation is a different size.** A `w-[120vw]` block inside `ReceiveFundsModal` reads `overlayOverflowBy: 1026` at 1280 and **137** at 393 — `120vw` is viewport-relative and the panel's own scroll box clamps it. A proof at one width is not evidence at the other, and the gap is roughly 7.5×.
- **The viewport-absolute pins catch what the overflow metric structurally cannot.** At 393 the panel is `mx-4 w-full` with `max-w-lg` no longer binding, so `dialogLeft`/`dialogRight` are a *knowable* 16 → 377 and can be asserted — unlike at desktop, where the three overlays have three different correct positions. Mutating `mx-4` → `mx-0` turns `dialogLeft` red while `overlayOverflows` stays false: a panel flush against both bezels overflows nothing. That is [#1779](https://github.com/d-hinders/Haven-AI/issues/1779)'s rule one layer down — `scrollWidth` vs `clientWidth` compares a box to itself and cannot see the box move.

Run them locally with `npm run test:e2e:mobile -w packages/frontend`, or both with `npm run test:e2e:gate -w packages/frontend` (exactly what CI runs).

**Rendered-screen evidence is REQUIRED** for any diff that touches a rendered route or a shared UI primitive (`components/ui/*`, `components/haven/*`). Run `npm run screenshot -w packages/frontend -- <routes>` (see [#896](https://github.com/d-hinders/Haven-AI/issues/896)); it captures desktop (1280) + mobile (390) PNGs of `/design-system` plus the routes you pass, using a known auth/data fixture and the pre-installed browser. The fixture serves a deterministic **populated** dataset (a funded account, agents on both rails, transactions, a pending approval, contacts, agent activity and spend stats) so lists, tables and amounts render realistically — set `SCREENSHOT_FIXTURE=empty` when you specifically want empty states. The script also summarises any **console errors** per route; a red console means a fixture-shape gap or a real client bug — fix it before trusting the PNGs. **Attach the PNGs to the PR, or reference them in the Browser Verification section** — "browser or headless equivalent" is no longer sufficient on its own for a visual surface. A primitive change means shooting `/design-system` (where it's documented) *and* a route that consumes it. Screenshots live in the gitignored `.screenshots/`; the fixture is documented at the top of `scripts/screenshot.mjs`.

**One capture server per worktree, and it has to prove who it is ([#1800](https://github.com/d-hinders/Haven-AI/issues/1800)).** The harness used to bind a fixed port (3111) in every worktree. Concurrent sessions are the normal state of this repo, so the second run found the port already bound, got a **200 OK from the other worktree's app**, and captured it — PNGs that render, have plausible dimensions, show the right routes, and are of a **different branch**, with nothing about them saying so. That is worse than a guard that fails silently: it is positive evidence that is confidently wrong, and the `haven-design-reviewer` pass below reasons from exactly these artifacts. Two things now stand in the way, and the second is the one that lasts:

- the port is **derived from the worktree path** and proven bindable before the dev server starts (a busy port is skipped and the chosen one is printed — never inherited);
- before any PNG exists, the run fetches `/capture-identity.json` from whatever it is about to capture and **refuses unless the marker matches this run's own random token**. A 200 is not proof of identity. `SCREENSHOT_BASE_URL` and `SCREENSHOT_PORT` get the same treatment, so pointing either at the wrong server fails loudly instead of producing evidence (`SCREENSHOT_ALLOW_UNVERIFIED_SERVER=1` exists for a genuinely remote target and stamps `identity_verified: false`).

Every run also writes `.screenshots/capture-manifest.json` — worktree, branch, commit, dirty flag, port, and whether identity was verified — so a PNG can be traced back to what produced it. **When you attach screenshots, the manifest is the claim that they are yours.** Mechanism: `scripts/capture-identity.mjs`. Same class from another angle, still open: [#1801](https://github.com/d-hinders/Haven-AI/issues/1801), where concurrent sessions share one scratchpad and overwrite each other's PR bodies.

**The capture harness had the dialog-subtree defect too, on the vertical axis, and its clip guard was reporting zero ([#1879](https://github.com/d-hinders/Haven-AI/issues/1879)).** `shoot()` has no selector of its own — it measures `scrollHeight - clientHeight` on **whatever locator the caller hands it**, and 19 of its 21 call sites hand it `page.getByRole('dialog')`. On `ui/Modal` that role sits on the `fixed inset-0` wrapper (`Modal.tsx:109`): viewport-sized, never scrolls, reads **0 however much** the nested `min-h-0 flex-1 overflow-y-auto` body at `:153` is hiding. So the guard could not fire, nothing was recorded in `clipped`, and no taller re-shoot happened — while the modal's rounded bottom edge and footer rendered cleanly at the clip, making the PNG **look finished**. That is worse than a missing capture, because the `haven-design-reviewer` pass below reasons from exactly these artifacts: the capture that found this was a destructive-action screen whose irreversibility banner and acknowledgement checkbox were both below the fold.

Measured on the same commit, same fixture, one full `--scenario=all` run each: the old guard reported **2** clipped captures, the corrected one reports **16**. The 14 it newly finds were always clipped — `connect-agent-manual-credential-warning` at **706px** (1280) and **1020px** (390), `replace-signing-key-point-of-no-return` at **656px** and **1060px**. Note the fix is to change *what* is measured, not which element the call sites hand in: scanning the subtree also covers `ui/SidePanel`'s body and the two `card` call sites, which a selector swap would have missed.

Three things the vertical version needs that the horizontal one above does not:

- **Skip descendants that cannot clip.** A box whose computed `overflow-y` is `visible` hides nothing — its overflow paints and propagates outward to the nearest clipping ancestor, which reports it. This is the *opposite* of the rule rejected above, which refuses to exempt `auto`/`scroll` boxes because those are the scrollers where the defect lives. It was found by measuring, not by reasoning: every genuine offender was `overflow-y: auto` (89–1060px) and **every** box in the 2–5px noise band was `visible` — `<button>` at `clientHeight: 34, scrollHeight: 39`, flex rows at 40 vs 42. Six captures were flagged on nothing but a 5px button. `hidden` and `clip` stay in; a box that truncates without even offering a scrollbar is the worst version of this, not an exempt one.
- **Measure the target itself unconditionally anyway.** An element screenshot is the target's bounding box, so content overflowing a non-clipping *target* really is cut from the PNG — and that is exactly what the old guard measured. Exempting it would have narrowed existing coverage while fixing the nested case. `ReceiveFundsModal` is the live example: its `role="dialog"` is the scrolling panel itself, which is why it was one of the only two captures the old guard ever caught.
- **Re-measure after growing the viewport, because growing does not un-clip everything.** `ui/Modal`'s `max-h-[calc(100vh-2rem)]` responds to a taller window; a `pre.max-h-48` code block does not, and stays 203px short at 390 forever. 8 of the 16 are in that state, so the run now says which `-full.png` is **not** actually full instead of letting the name imply it.

**And check 390 first**, which is [#1797](https://github.com/d-hinders/Haven-AI/issues/1797)'s rule one layer down: `replace-signing-key`'s `reason` and `address` stages read **0px at 1280 and 21px / 17px at 390**. Two captures that look complete on desktop are silently truncated on mobile, and desktop is where everyone had been looking.

Prove a change here by mutation, never by a green run — this guard's whole defect was that it could not fail. The proof shape that works: inject a tall block into a dialog that currently fits, confirm the **old** guard still records nothing (it recorded 0 against a 628px injection) while the new one reports the shortfall, then revert and confirm the newly-flagged list returns to exactly its previous members. The revert half is the half that says it fires for the right reason.

**That proof now re-runs on every frontend PR, and where it lives is the whole design decision ([#1886](https://github.com/d-hinders/Haven-AI/issues/1886)).** The guard moved out of `screenshot.mjs` into `scripts/clip-guard.mjs` — verbatim, call sites unchanged — purely so a spec can import it; `e2e/clip-guard.spec.ts` then drives it over a `page.setContent()` fixture in the *Frontend browser smoke* job. Three instrument choices were live and only one of them can answer the question this gate is for:

- **jsdom cannot fail and must not be used here.** It performs no layout, so `clientHeight` and `scrollHeight` are `0` on every element and every assertion built on them passes against every input — including a guard that returns a constant. That is worse than no coverage, because it looks like coverage. It was suggested on #1879 and declined for exactly this reason; it is written down so it is not proposed a third time. The same trap applies to any layout guard in this file.
- **Asserting against the harness's own `clipped` report is the honest-looking wrong answer.** It cannot distinguish *"the guard stopped working"* from *"these captures are still clipped"*, and the second is permanently true: 8 of the 16 residuals are self-capped by design (the `pre.max-h-48` bullet above), entirely in `connect-agent` — and per [#1894](https://github.com/d-hinders/Haven-AI/pull/1894) all eight resolve to a SINGLE self-capping element, `CopyBlock`'s `pre.max-h-48`, not to eight independent cases. A gate keyed on the report would be red on unchanged `dev` forever, and any layout change to a captured screen would move its numbers for no defect at all.
- **A synthetic fixture answers only the first question, which is why it is worth its cost.** Five hand-written DOM shapes, one per rule — two of them exclusions (`overflow-y: visible` descendants, and the 1px geometric floor), three of them the coverage the guard must NOT lose (the nested scroller, `overflow-y: hidden`, and the target itself) — with no route, no API fixture, no product component and no baseline PNG — so app layout work cannot redden it — while Chromium still lays it out for real, which is the one thing jsdom cannot give. Extracting the traversal as a *pure* function over injected boxes would be faster still and would leave the `scrollHeight`/`clientHeight` read — the half #1879 actually got wrong — untested; here the real `evaluate()` runs against real boxes.

Two house rules it inherits and one it adds. **One `test()` per rule** (#1863): five assertions in one test short-circuit and turn a mutation's blast radius into a guess. **Every exclusion needs both directions** — a mutation that reddens the rule *and* a fixture proving the guard stays silent on the case #1879 deliberately excluded, because a gate that flags everything is as useless as one that flags nothing. And **pin the noise band's actual numbers, not just its verdict**: the over-fire fixture asserts the `<button>` really reads `clientHeight: 34, scrollHeight: 39` and that `39 - 34` is strictly greater than `CLIP_TOLERANCE_PX`, which is what proves the *exclusion* is doing the work rather than the tolerance quietly covering for it. That is also the assertion that keeps the tolerance at **4**: widening it to 5 silences the noise band and starts silencing real 5px shortfalls, and it turns that test red on the way past.

**The e2e suite had the same defect, and now reuses the same mechanism ([#1816](https://github.com/d-hinders/Haven-AI/issues/1816)).** `playwright.config.ts` took a fixed `PLAYWRIGHT_PORT ?? 3000` in every worktree and set `reuseExistingServer: !CI`, so a local `npm run test:e2e` adopted whatever was already on :3000 — which in a second session is **another worktree's app**. The result is not a broken run; it is a **pass or a failure attributed to a branch the run never loaded**, which is worse. So:

- the port is derived from the worktree path into a range **disjoint from the capture server's** (3300–3419 vs 3111–3230 — one worktree can be capturing and testing at the same time). Note what that does and does not do locally: the derived port is used **as is** when reuse is allowed, precisely so a warm `next dev` on it gets adopted rather than stepped over — walking forward to a free port instead would start a *second* Next in the same worktree, which cold-compiles every run and corrupts the shared `.next/`. The bind-and-walk is kept for CI, where nothing may be adopted and Next would otherwise hop ports while Playwright polled the old one;
- `globalSetup` writes a per-run marker into `public/`, fetches `/e2e-identity.json` back from whatever Playwright is about to test, and **throws unless the token is this run's own**. `reuseExistingServer` is kept but no longer trusted: it asks only whether something answered.

Two consequences worth knowing before you meet them. **A hand-started `npm run dev` is adoptable only on the derived port** — the marker is written to this worktree's `public/`, so any server serving *this* worktree's files passes, and one on some other port simply is not found. And `PLAYWRIGHT_BASE_URL` pointed at a deployed environment will be **refused**, because a deployment cannot serve your run's token; `PLAYWRIGHT_ALLOW_UNVERIFIED_SERVER=1` is the loud way past that, and it means the result may belong to another branch. CI was never exposed (`reuseExistingServer` is false there, runners are per-job isolated) but runs the probe anyway. Mechanism: `scripts/e2e-identity.mjs`.

**Surfaces no URL can reach — use a scenario ([#1409](https://github.com/d-hinders/Haven-AI/issues/1409)).** Route capture cannot see a screen that lives behind a multi-step dialog or a state machine that only advances on a timer; the connect-agent modal is both, which is why [#1399](https://github.com/d-hinders/Haven-AI/issues/1399) shipped with its rendered-evidence criterion unmet and its two review passes disagreeing about a layout question neither could see. A **scenario** drives the UI there and holds it at each state:

```
npm run screenshot -w packages/frontend -- --scenario=connect-agent   # one scenario
npm run screenshot -w packages/frontend -- --scenario=all             # every scenario
```

`connect-agent` captures step 4 at all three connection stages (`starting` → `slow` → `recovery`) at both viewports, writing `connect-agent-waiting-<stage>-<viewport>.png`. It pins the setup at `awaiting_connection` and drives Playwright's virtual clock past the staging bounds, so a three-minute state is reached in milliseconds. A scenario that cannot reach its state **fails the command** rather than writing fewer PNGs — a missing stage is the evidence gap, not a smaller run. Add new scenarios to the `SCENARIOS` registry in `scripts/screenshot.mjs`; their fixture contract is pinned by `src/__tests__/screenshot-fixture.test.ts`.

**Two PNGs when a dialog scrolls.** An element screenshot captures only the visible box, so a dialog that caps its own height drops everything below the fold — and its rounded bottom edge makes the clipped capture look complete, which would have a reviewer judge a screen they have only partly seen. When a capture overflows, the run says so (`⚠ … had content BELOW THE FOLD`, with the pixel shortfall) and writes a second `…-full.png` at a viewport tall enough to show all of it. **Judge the content from the `-full` PNG; judge what is reachable without scrolling from the other** — the fold itself is often the finding.

**A blank capture fails the run ([#1738](https://github.com/d-hinders/Haven-AI/issues/1738)).** The app shell is `h-screen` + `overflow-hidden` with `<main>` as its only scroller, so a naive `fullPage` capture paints one viewport and leaves a very long white tail — the PNG is the right size and looks fine. Route captures therefore un-clip the shell first (`scripts/full-page-capture.mjs`), then read the PNG back: a capture more than a viewport tall with nothing painted below the fold is **deleted** and fails the command, with the measured painted ratio in the message. This is not hypothetical — the committed `/design-system` baselines were 95% (desktop) and 97% (mobile) blank until that fix, so the pixel gate had been comparing white against white below the fold and the design-reviewer pass was reading empty pixels. If you see the failure, the usual cause is a layout change to the shell's overflow; do not work around it by capturing less.

**If Chromium fails to launch** with an error naming a `chromium_headless_shell-<n>` path that does not exist, the cached browser build does not match the pinned Playwright version. Point `PLAYWRIGHT_CHROMIUM_PATH` at the Chromium that *is* installed rather than running `playwright install`:

```
PLAYWRIGHT_CHROMIUM_PATH=/opt/pw-browsers/chromium-1194/chrome-linux/chrome \
  npm run screenshot -w packages/frontend -- --scenario=connect-agent
```

**Visual regression (blocking CI, #897).** The visual specs are pixel-compared against committed Linux baselines on every frontend PR (the *Design visual regression* job) — `/design-system` whole-page and scoped, plus the driven focus states below. Both the job and the regeneration workflow go through the one `test:visual` script, which selects **every** `e2e/**/*.visual.spec.ts`; it named a single file until [#1863](https://github.com/d-hinders/Haven-AI/issues/1863), so a second visual spec would have been collected by neither — its baselines would have existed, and nothing would ever have compared them. `src/__tests__/visual-gate-coverage.test.ts` is what stops that narrowing back, and it reads the real script out of `package.json` rather than restating it. An unintended pixel change in a shared primitive fails the PR with a downloadable diff artifact (`visual-regression-diffs`). **Updating baselines for an intended change — in the SAME PR:** dispatch the **Update visual baselines** workflow on your PR branch (Actions → Update visual baselines → Run workflow → pick the branch) — it regenerates the Linux-rendered baselines and commits them to the branch, where they appear as a reviewable image diff. **Caveat — expect the regeneration run itself to go RED, and read its PR comment (#1777).** Without the `BASELINE_PUSH_TOKEN` secret (a PAT/App token with `contents: write`), the bot pushes as `github-actions[bot]`. The `pull_request` events *are* delivered and the runs *are* created; GitHub then **parks them at `conclusion: action_required`** because a bot pushed, so no job executes, no check run attaches to the new head, and every required check waits forever at "Expected — waiting for status". (Not "the event never fired" — that reading sends you looking for a missing trigger. Measured on bot commit `31003514`: `check-runs` → `total_count: 0`, `actions/runs?head_sha=…` → 5 parked `pull_request` runs.) Since #1777 the workflow **fails and posts a sticky comment on your PR** naming the condition and the recovery, instead of succeeding into the deadlock behind a `::warning::` nobody reads. **The red is about the push attribution, not your baselines** — those are committed and pushed before the failing step runs, so do not re-dispatch (regeneration re-runs `--update-snapshots=all`). **Recover by approving, not by pushing:** the comment enumerates the parked runs by URL, and clicking *Approve and run* on each resolves this PR's required checks with no push at all, because those parked runs **are** those checks. Approving needs the same write access dispatching the workflow already needed. Only if you cannot approve, push from your own credentials instead (`git commit --amend --reset-author --no-edit` then `git push --force-with-lease`, or an empty commit) — the workflow cannot do that step for you, because the gate keys on *who* pushed and a second bot push parks identically. Setting the secret retires the whole path.

**Beware the two SHA classes when you check any of this yourself.** The dispatch run's own `headSha` is the branch tip *before* the workflow pushed — a human commit, with a full set of check runs and a `success` dispatch run. The commit that shows the defect is its **child**, the bot's baseline commit. Querying the first and concluding "no problem here" is the easy mistake; name which class your SHA is in. Any PR that intentionally changes what `/design-system` renders (including its prose) without carrying new baselines leaves the job red for every PR after it. Never commit locally-rendered (macOS) baselines; fonts differ and CI will reject them. Run the spec locally only inside a Linux container with `VISUAL_REGRESSION=1`. Note: the job gates auto-merge only while it's listed in the "Haven automerge rules" ruleset's required checks — see [`autonomous-pr-loop.md`](../autonomous-pr-loop.md) §One-time setup. **Before reporting a frontend PR shipped, confirm this job's conclusion on the head SHA** — merged-state alone doesn't prove it ran green.

**What the gate can and cannot see, and why it is denominated in pixels rather than percent ([#1805](https://github.com/d-hinders/Haven-AI/issues/1805), [#1760](https://github.com/d-hinders/Haven-AI/issues/1760)).** Three knobs, all mis-set at once, and the reasoning is recorded next to the numbers in `e2e/design-system.visual.spec.ts` rather than restated here. The parts a contributor needs at this level:

- **The budget is an absolute pixel count, not a ratio.** A `maxDiffPixelRatio` grows with page height while the app shell does not, so 0.5% of a 29,012px-tall capture was a 56,573-pixel allowance against a 21,840-pixel TopBar — the whole chrome could change and pass, and in [#1804](https://github.com/d-hinders/Haven-AI/pull/1804) it did. Do not reintroduce a ratio "as well": Playwright takes `Math.min` of the two, so a ratio beside a small floor is inert.
- **`/design-system` is compared whole-page AND as scoped captures of the app shell's chrome** — the top bar on both viewports, and the sidebar on desktop ([#1820](https://github.com/d-hinders/Haven-AI/issues/1820)). One number cannot be both loose enough for page-wide churn and tight enough for a 56px band that is 0.2% of the image, so a shell change shows up as a small, readable image diff instead of being absorbed. That absorption is measured, not feared: recolouring the sidebar's three nav group headings one token sideways moves 366 pixels on CI, which the scoped capture fails at 3.66x its budget while the whole-page capture **passes** under its 500 (both halves were run; the scoped assertion short-circuits the full-page one, so the counterfactual needs its own run). Quote CI's number, not your laptop's — the same mutation is 282 px rendered on macOS. The sidebar is desktop-only because below `lg` it is an off-canvas drawer that is not in the pristine capture at all — measured on the element, not on pixels: at 390px the aside is `position: fixed` with `translateX(-240px)`, so its bounding rect is `x: -240, right: 0` and it contributes nothing to the capture. Do not "confirm" that by checking whether the mobile baseline's x=0..239 band is white; it is not, and that is the *consequence* of the drawer being absent — being `fixed` it reserves no space, so `<main>` paints straight through the band. An earlier draft of this bullet asserted the whiteness off a too-sparse sample and was simply wrong. Adding a scope means adding a locator: locate it **structurally** (both use an xpath anchored on `#main-content`, never a class or a bare tag) and assert `toHaveCount(1)`, because a locator that silently matches the wrong element is the failure this family of gates exists to close.
- **A scoped capture sees the resting state only — a DRIVEN spec is how a state gets covered ([#1863](https://github.com/d-hinders/Haven-AI/issues/1863)).** Nothing is focused, hovered or open in a screenshot, so no amount of extra region reaches a focus ring: `e2e/focus-visible.visual.spec.ts` drives keyboard `Tab` onto a control, asserts it is there, and captures the region around it. Four rules that cost real measurements to learn. **(1) Never hard-code a Tab count** — under `next dev` the tab order starts with three `NEXTJS-PORTAL` devtools nodes that do not exist in CI's standalone build, so press Tab until `document.activeElement` *is* the target node and throw if it never arrives. **(2) One `test()` per control**, because several `toHaveScreenshot` calls in one test short-circuit at the first failure and turn a mutation's blast radius into a guess. **(3) Assert the state before the pixels** — focus landed, `:focus-visible` matches, and the computed style actually *paints*; a driver that silently focuses nothing yields a resting-state baseline and the gate is then green forever about the thing it exists to see. **(4) "Solid 2px" is not proof of an indicator:** Tailwind's own `outline-none` compiles to `outline: 2px solid transparent`, so check the colour's alpha, not just the style and width — the first version of that assertion passed a control with no visible ring at all, and only a mutation said so. Do not read "there is a capture of X" as "X is covered"; ask which *state* was captured.
- **The gates are layered, and a mutation tells you which layer you are actually in.** Measured on the Sidebar's Log out item ([#1863](https://github.com/d-hinders/Haven-AI/issues/1863)): swapping its ring tone `danger → brand` is caught by the **structural** rule (#1792's "hovers danger, focuses brand") and proves nothing about pixels — that mutation was chosen first and had to be thrown away. Dropping `ring-inset` so the ring paints outset and is clipped by the popover edge — the legibility residual #1831's design pass could not close — leaves **all 19 focus-ring assertions and design-lint green** and moves 1,576 px in the driven capture. That is what "new coverage" has to look like before you claim it: a defect every existing gate passes.
- **Run-to-run jitter in this environment is zero**, measured across four captures and four separate CI runs — antialiased pixels are excluded by pixelmatch before any budget applies, so the budget was never what absorbed AA. If you are tempted to widen a tolerance, measure first: set the budget to 0 on a branch and read the count the failure prints.
- **Regenerating requires `--update-snapshots=all`, and the workflow now uses it.** A bare `--update-snapshots` means `changed`, which re-applies the gate's own tolerance and therefore refuses to rewrite drift that sits under budget. That is why stale baselines survived every regeneration anyone dispatched before #1760 — the refresh reported "Baselines unchanged" and committed nothing.
- **Diagnose a diff before regenerating.** Same dimensions plus a continuous colour difference is drift; a clean horizontal cut, or a size-mismatch line in the failure, is a height change. Scan the diff PNG by row rather than dispatching the regeneration workflow first — `all` will bless whatever renders, including a broken render.

**Wire shapes come from the spec, not from you (#1447).** `npm run lint:wire-types` is a **blocking CI job** on the frontend surface. It counts hand-written types in `hooks/` and `types/` that declare a snake_case property — the API's convention — against a shrink-only baseline (`packages/frontend/wire-type-baseline.json`, frozen at 18 after #1445's migration). If the route is in the spec, import the type instead of restating it:

```
import type { ApiSchema } from '@haven_ai/core'
export type Thing = ApiSchema<'Thing'>
```

If the route is not in the spec yet, document it there first — [#1446](https://github.com/d-hinders/Haven-AI/issues/1446) tracks that backfill, and the 18 baselined shapes are waiting on it. If a type is genuinely UI-side and merely happens to carry a snake_case field, mark it `// ui-local: <reason, at least 20 chars>` on the line above; a bare marker does not exempt. After removing shapes, tighten with `npm run lint:wire-types:update` (it refuses to ratchet upward). The gate reads casing, so it does **not** see a wire shape that uses camelCase, and it cannot see an anonymous inline shape (`useState<{ tx_hash: string }>`) because there is no declaration to find. Both holes are stated in the script's header with live examples; review is the backstop.

## 5. Review (two passes: code + rendered)

An `area:frontend` diff gets **both** reviews, because a code-only reviewer is only as good as one that never sees the screen:

1. **`haven-reviewer`** (code) with UI context, checking the diff against [`product/design-review.md`](../../product/design-review.md) and [`copy-guidelines.md`](../../product/copy-guidelines.md).
2. **`haven-design-reviewer`** (rendered) — a dedicated visual/UX/design-system pass keyed off the [#896](https://github.com/d-hinders/Haven-AI/issues/896) screenshots (desktop + mobile) rather than the diff: visual weight, spacing rhythm, alignment, state coverage (empty/loading/error), touch targets, focus-visible, and design-system adherence that only shows up rendered ([#900](https://github.com/d-hinders/Haven-AI/issues/900)). Its canonical role is [`design-reviewer.md`](../../../.agents/skills/haven-agent-workflow/references/design-reviewer.md). Give it the `.screenshots/` PNGs; if a rendered surface has none, that's its first finding.

A finding from **either** pass — even nit-level — trips the §6 pause-on-UI-finding gate. Two automated aids back this up: the Vale terminology rule (`.vale.ini`, scoped to `docs/product`) for docs copy — advisory — and **`npm run lint:copy`** (`scripts/frontend-copy-lint.mjs`), which flags banned multi-word terms in user-facing frontend copy (`app/` + `components/`). The copy lint is a **blocking CI job** ([#902](https://github.com/d-hinders/Haven-AI/issues/902)): it fails the PR on any new banned term beyond the shrink-only `packages/frontend/copy-lint-baseline.json`. For anything it can't catch (it's conservative — multi-word phrases only), check changed strings against `copy-guidelines.md` by hand. Use `// copy-lint-ignore` for a legitimate advanced/developer-facing surface; after cleaning existing debt run `npm run lint:copy:update` to tighten the ratchet.

## 6. Merge policy (UI)

A non-money frontend PR **auto-merges** on green CI + verification **unless** either §5 pass — `haven-reviewer` (code) or `haven-design-reviewer` (rendered) — flags a UX, copy, or design-system issue (**even a nit-level one**) — then **pause and ask the user** (UX is subjective; a flagged finding is a human call). This is the `area:frontend` case of the canonical skill's [Merge Gate](../../../.agents/skills/ship-next/SKILL.md#merge-gate). Money-path UI still follows the `money.md` bar (characterization tests, CASP guardrails); since #1024 that no longer includes a merge pause.

**Hard definition-of-done for a diff that adds a primitive ([#898](https://github.com/d-hinders/Haven-AI/issues/898)):** run `node packages/frontend/scripts/design-system-coupling.mjs --strict` before opening the PR. A non-zero exit (a new `ui/`/`haven/` export missing from `/design-system` and not `// design-system-exempt`-marked) means the **Design-system coupling (strict)** required check will fail — document the primitive on the reference page first. Running it locally only saves the round trip; the gate itself is in CI ([#1023](https://github.com/d-hinders/Haven-AI/issues/1023)), so it applies to every author.
