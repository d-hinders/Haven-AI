- **#1423** — revoke-all hardening, both #1400-review follow-ups closed. Determination first: `DelegationManager.disableDelegation` is NOT idempotent — the pinned ABI carries an `AlreadyDisabled` custom error — so a crash-window orphan (delegation disabled on-chain, DB row stale-active after a process death between UserOp landing and the UPDATE) bundled into the atomic `BatchDefault` batch would revert the entire retry and jam the one-signature stop path. The prepare step now reads the manager's own `disabledDelegations(bytes32)` view for every candidate hash, heals already-disabled rows to `revoked` (recording what the chain already enforces — authority narrows or stays, never widens), and drops them from the batch; if every candidate was already disabled the route 409s "Nothing to revoke" AFTER healing, which is exactly the step-already-done signal the #1402 retry flow consumes. Availability over blocking: a failed RPC read degrades to the pre-#1423 full batch (worst case the old loud 502, mutation-proven: severing the drop-filter fails the heal tests). Second: batches are capped at 25 `disableDelegation` calls — past it a 422 names per-hash revocation as the escape hatch, so a pathological agent can no longer construct a doomed mega-UserOp (gas/payload limits) through this route. No new authority anywhere: the reconciliation write only records on-chain state, the owner still signs every batch, Haven still cannot sign, and the per-hash route is unchanged. Perimeter unchanged.
