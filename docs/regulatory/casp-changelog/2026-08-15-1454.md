- **#1454** — `HavenClient.settleX402Erc7710()` gives the SDK an erc7710 direct-settlement path: authorize with `payTo` = the MERCHANT and `settlementScheme: 'erc7710'`, sign the returned `eip712_delegation` child (#1452), settle, and hand the backend-assembled `X-PAYMENT` header back to the caller for the merchant retry. This is the path with **no funding leg**: the merchant redeems the `[child, budget]` chain and pulls from the treasury directly, so the delegate EOA never holds the money and the stranded-delegate-funds class (#713 — hot balances, sweeps, the delegate-balance monitor) does not arise on it at all. It is also SMALLER than the 3009 path rather than larger: the backend assembles the merchant header (`assembleSettlementPayload`), so the SDK constructs no header locally and holds no funds at any point. Authority is unchanged and remains where it was: the child's bounds — exact amount, payee pin, expiry clamp, redeemer pin — are computed BY THE BACKEND and enforced ON-CHAIN as caveats during redemption; the SDK signs the backend's typed data verbatim (#1452) and cannot widen a bound it did not compute. Rail enforcement is doubled rather than moved: the backend refuses erc7710 from a non-delegation-rail account (`validateGenericSchemeRail`), and the SDK now refuses FIRST, reading the rail from `GET /machine-payments/agent` rather than letting a caller assert it — a client that cannot state its own rail cannot smuggle one. The method never silently reroutes to the other scheme: a merchant with no erc7710 entry, an account on the wrong rail, or an authorize response carrying a different `signature_scheme` each raise a typed `HavenApiError` naming which condition failed, and in the wrong-scheme case the SDK refuses to sign a payload it did not ask for. Request shapes the backend would reject are never CONSTRUCTED, each pinned by a test: `payTo` is the merchant and never the delegate EOA, `merchantPayTo` is absent, `facilitatorAddresses` is OMITTED (not `[]`) when the merchant advertises none or an empty array, and the merchant's `maxTimeoutSeconds` round-trips rather than being defaulted. **Live end-to-end settlement is NOT yet proven for this path** — the nightly `x402-erc7710-settle` QA leg exercises the raw API and deliberately excludes the SDK, so the no-funding-leg property is asserted here only at the request-shape level; the topology proof belongs to #1457 and this entry does not claim it. No new route, no new credential scope, no key material moved; existing 3009 callers untouched. Perimeter unchanged.
