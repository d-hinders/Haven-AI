- **#1455** — the local signer now RE-DERIVES what an erc7710 settlement child means, instead of trusting that Haven's declaration describes it. `assertExpectedBinding` already proved Haven *declared* the exact bytes (the expected context is signed by `HAVEN_X402_BINDING_SIGNER` and commits to their digest); that property says nothing about what those bytes DO. A backend could declare `merchantTo = the real merchant` while pinning a different payee in the child's `AllowedCalldata` caveat, and the pair would bind perfectly — the declaration covers the digest, the digest is the child's, and the child pays someone else. Since the signature on this child is exactly what lets a merchant's facilitator redeem the chain and pull from the treasury, the signer now decodes the caveats and refuses on any disagreement: a different payee, a different token, a different amount, a payee pin at the wrong calldata offset, the wrong chain, an unknown DelegationManager, an already-expired window, a window longer than `MAX_SETTLEMENT_WINDOW_SECONDS` (600s — re-checked locally so a backend that stopped clamping cannot hand out a long-lived grant unnoticed), or a child outliving the payment window Haven declared. **Absence refuses too**, which matters as much as disagreement: a child missing its payee pin, its amount caveat, its expiry, or carrying no caveats at all is refused rather than signed. Enforcer addresses are PINNED in the signer rather than read from Haven — a verifier that lets the thing it verifies choose the yardstick verifies nothing — and cross-checked against `@metamask/smart-accounts-kit` by a test on both Base and Base Sepolia, with the kit held as a devDependency so it never ships to users' machines (the same snapshot-pinning pattern `packages/core/src/chains.ts` uses, and the same cross-check `rails/delegation-policy.ts` already performs backend-side). Unrecognised EXTRA caveats are deliberately allowed: caveats are AND-ed restrictions, so one this code does not know can only narrow authority further, and forbidding them would break the next legitimate backend addition for no security gain. Authority is narrowed, never widened: this only ever REFUSES to produce a signature. No new route, no new scope, no key material moved, and the EIP-3009 path is untouched (existing signer suite green unchanged). Mutation-proven: emptying the verifier makes 13 of 18 refusal tests fail. Known gap NOT closed here and tracked as #1476 — `haven_sign` still accepts raw `payload_hash` + `typed_data` with no binding at all, so a settlement child routed to that tool rather than the `payment_id` path bypasses this check entirely; keying the refusal off the payload's `Delegation` shape rather than the caller's tool choice is that issue's deliverable. Perimeter unchanged; one local verification added.
