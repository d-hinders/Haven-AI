- **#1456** — erc7710 direct settlement becomes reachable from the hosted MCP tool surface, which is the topology a normal agent actually uses. `haven_pay_mcp_tool` now selects the scheme through #1453's single rule (prefer erc7710 when the account is on the delegation rail AND the merchant advertises `extra.assetTransferMethod: 'erc7710'`), and reports it structurally (`settlement_scheme`, `settlement.funding_leg: false`, the merchant payee and facilitator pin) so an agent can state which scheme settled a purchase instead of inferring it from prose. Both halves of that rule are enforced from data the server reads, not from anything the caller asserts: the rail comes from `GET /machine-payments/agent` (reusing the #1348 prefetch — a second fetch for one field would break that path's one-round-trip budget, which its own test caught), and the merchant half from the quote's own `accepts[]`. A prefetch failure deliberately yields the EIP-3009 path rather than guessing 'delegation', which would build a request the backend then refuses. `haven_settle_mcp_tool` gains the inverse branch, and its placement is the substance of this change: on erc7710 the agent's signature IS the settlement child, not a funding authorization, so it goes to `POST /x402/:id/settle` — an earlier attempt branched inside the delivery helper, by which point the signature had ALREADY been relayed as a funding signature. The branch therefore sits before both the funding relay and the #1398 header preflight; that preflight is skipped rather than failed because it exists to stop a malformed AGENT-SUPPLIED header from triggering funding, and on this scheme there is neither an agent-supplied header (Haven assembles it at settle) nor a funding leg to protect. Authority is unchanged throughout: the child's bounds are computed by the backend and enforced on-chain as caveats, the local signer independently verifies them before signing (#1455), hosted Haven still never holds a delegate key — the split in #1456's SDK half exists precisely so the hosted server can drive authorize and settle with the local signer in between — and no new route, scope or key handling appears here. The EIP-3009 path is byte-identical: pinned by tests asserting a legacy-rail account never takes the branch even when the merchant offers erc7710, that a 3009-only merchant stays on the bridge even on a delegation account, and that a supplied `payment_header` still preflights and still waits for funding confirmation. Mutation-proven: ignoring the rail condition fails the legacy test, removing the settle branch fails the settle test. Live proof through the deployed hosted MCP is NOT included and is not claimed — it requires this to reach the dev deployment first, and #1457's hosted variant is where it gets pinned. Perimeter unchanged; one scheme made reachable.
