- **#1469** — a null or non-object entry in an x402 `accepts[]` array now yields the same clean no-compatible-option refusal as any other unpayable entry, on every path, instead of crashing the selector. The parsed-Response path was always safe (`normalizePaymentRequired` filters falsy entries), but the hosted MCP's `haven_pay_x402_quote` cast AGENT-SUPPLIED `payment_required` straight to the SDK type — its Zod schema guarantees only a string-keyed record — so a null hole reached `selectStandardPaymentOption` unsanitized and produced a 500 where every other caller gets a structured 400-class refusal. Fixed at BOTH ends, deliberately: the selectors themselves skip non-object entries (so no future caller can reintroduce the crash by bypassing normalization), and the hosted tool now routes agent input through the SAME `normalizePaymentRequired` the parsed path uses — now exported, and extended to drop non-objects rather than only falsy values — so both later uses in the handler read the sanitized value and the raw cast is gone. Fail-closed throughout and authority unchanged: nothing was ever signed or moved on the crash path (the defect was a wrong error code and a robustness gap, not spend authority), and the fix only converts a crash into a refusal. Characterization-first per the issue's own AC: the current THROW was pinned against unchanged code in its own commit, then inverted by the fix — so the behaviour change is recorded, not implied. Mutation-proven: removing the skip guards fails three tests. Per-surface coverage per the AC: SDK selectors (null, undefined, string, number entries; both scheme branches of `selectX402SettlementScheme`) and the hosted tool (a null-holed accepts still selects the valid entry; an accepts of ONLY garbage refuses with the wrong-tool guidance naming the remedy). No new route, no scope change, no key material. Perimeter unchanged; one 500 becomes a 400.
