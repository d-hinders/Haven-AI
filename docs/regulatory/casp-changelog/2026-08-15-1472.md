- **#1472** — the merchant-visible erc7710 payer becomes mappable to a Haven agent, closing the reconciliation gap the #1454 live run surfaced: the demo merchant's receipt named the agent's DELEGATE ACCOUNT as payer, and no API surface could translate that address back to an agent — an operator holding a receipt would have had to read the delegation chain. `GET /machine-payments/agent` now returns `delegate_account_address` for delegation-rail agents. It is a PURE DERIVATION (the counterfactual Hybrid account address of the signing EOA, the same computation the authorize path already performs), so it costs a computation rather than a column, is `null` on the legacy rail where no such account exists, and degrades to `null` on a failed derivation rather than failing the identity read — the field is reconciliation metadata, never authority, and exposing an address grants nothing. The demo merchant's receipt label decision is RECORDED rather than left implicit: on erc7710 the address is printed as what it is (`delegatkonto — betalningen dras från ägarens treasury`) instead of a bare `Från`, because the funds provably leave the owner's treasury and a bare label made a custody claim the chain contradicts. Third-party merchants will print whatever they print, which is exactly why the API-side mapping exists — the non-custody story cannot depend on merchants labelling correctly. Mapping documented in `docs/architecture/04-x402-payment-sequence.md`. No new authority, no key material, no route beyond one derived read-only field. Perimeter unchanged; one unexplainable address made explainable before #1458 puts receipts on mainnet.
