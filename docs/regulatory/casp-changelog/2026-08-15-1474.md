- **#1474** — the erc7710 authorize response now carries its own Haven-signed expected context (`x402_expected_auth`), matching what the EIP-3009 branch has always emitted. This is a PARITY fix, not a restored boundary, and the distinction is worth recording because the first reading of it was wrong: the local signer's `{ payment_id }` path fetches `GET /x402/:id/sign-context`, where `rebuildDelegationSignContext` already builds a signed context for `eip712_delegation` and the signer REFUSES outright when one is absent — so the expected-binding discipline was already applied ON THAT PATH. It is NOT applied on every path: `haven_sign` accepts `payload_hash` + `typed_data` with neither `payment_id` nor `x402_expected`, and falls through to `signDelegationTypedData`, which does no binding check at all — so a settlement child routed to that tool instead of `haven_sign_x402` is signed unverified today. That is a pre-existing structural gap in `haven_sign`'s dual-purpose design, broader than erc7710, and #1474 does not touch it; tracked separately. What was genuinely missing is a declaration IN the authorize response for a client that signs straight from it. Stated precisely, because the obvious reading overstates it: this is backend-only ENABLEMENT. `HavenClient.settleX402Erc7710()` does not read `x402_expected_auth` — it signs `sign_data.typed_data` directly and verifies nothing — and `X402Erc7710Settlement` has no field to carry it. So the declaration is now available; nothing in the SDK consumes it yet. Wiring that is follow-up work, and until it lands this closes no client-side gap. The declaration is signed by `HAVEN_X402_BINDING_SIGNER` — a key this API surface does not itself control — and commits to `payloadHash` (the child hash), `typedDataHash` (the digest of the payload actually signed), plus merchantTo / amount / asset / network / expiresAt. `merchantTo` is `payTo` on this branch BECAUSE payTo being the merchant is what selected direct settlement. Authority is unchanged in every direction: this ADDS a verifiable declaration and removes no check, grants no new scope, moves no key material, creates no route, and changes neither the child's caveats nor what the DelegationManager enforces on redemption. Explicitly NOT covered, and stated so the next reader does not overestimate it: the context binds the DIGEST of the child and Haven's DECLARED fields — it does not prove the child's caveats implement those fields. A backend that declared one payee while pinning another in `AllowedCalldata` would still produce a consistently-bound pair. That local re-derivation is #1455's deliverable and remains outstanding. Proven by an assertion that the emitted declaration's digest equals the digest of the typed data in the SAME response, mutation-verified: binding it to a different payload fails three tests. The 3009 branch is untouched. Perimeter unchanged.
