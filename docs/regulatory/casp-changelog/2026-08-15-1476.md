- **#1476** — `haven_sign` now REFUSES a delegation-shaped typed-data payload that arrives without an expected context, closing the last path on which the local signer was a pass-through. #1455 made the signer verify an erc7710 settlement child's caveats against the Haven-signed context — but only on the path that HAS one. `haven_sign` also accepts raw `payload_hash` + `typed_data` with neither `payment_id` nor `x402_expected`, falling through to a bare `signTypedData`. So whether a settlement child — whose signature is exactly what lets a merchant's facilitator pull from the treasury — got verified at all depended on WHICH TOOL the caller reached for. That is a convention, not a boundary, and the local signer's entire reason to exist is that it does not sign whatever the hosted server hands it. The refusal is keyed on the PAYLOAD'S OWN SHAPE (`primaryType: 'Delegation'` with a caveats array), not on the caller's tool choice, which is what makes it a boundary: a caller cannot route around it by picking a different entry point. #1254's direct-payment case is deliberately untouched and pinned by a test — a UserOp is the account validating its OWN operation, not granting authority to a third party, and a raw hash is rejected on-chain there anyway. Authority is narrowed and never widened: this only ever refuses to produce a signature, adds no route, no scope and no key handling, and the error names the remedy (`{ payment_id }`, the path that fetches and verifies the context). Mutation-proven: disabling the shape check makes the refusal test pass a signature through. Found by the #1474 money-path review, which corrected my own earlier claim in both directions — the `{ payment_id }` path was never unverified, and this path always was. Perimeter unchanged; one convention promoted to a boundary.
