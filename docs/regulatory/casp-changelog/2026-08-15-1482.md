- **#1482** — `POST /payments/:id/sign` now shape-checks `prepared_user_op` before treating it as a UserOperation. That column is SHARED by two settlement schemes storing different things in it — a UserOp on the EIP-3009 bridge, a `{ child, budget }` delegation chain on erc7710 (#946/#1454) — and both schemes also set `delegation_hash`, so the route's existing presence checks could not tell them apart. An erc7710 intent reaching this route would have been handed to `submitDelegationPayment` as though it were a UserOp. **Unreachable today, and the guard is added anyway:** the hosted settle tool's header preflight recovers an EIP-3009 authorization signature that an erc7710 child can never produce, and the account's on-chain `validateUserOp` rejects a signature not over the correct UserOp hash — but BOTH of those live outside this route. A type guard belongs where the assumption is made, so a third writer to this column cannot quietly invalidate a safety property that currently depends on a caller-side check and a chain-side backstop. Authority is narrowed, never widened: the route can now refuse where it previously proceeded, and it refuses with a message naming the correct endpoint (`POST /x402/:id/settle`) rather than a generic type error. `isSettlementChainState` sits on the rail seam beside `deserializeUserOp` — the caller that deserializes is the caller that needs to know what it got. Characterization-first per money.md §2: the 3009 UserOp path is pinned BEFORE the guard, including bigint-marker decoding, so the invariant the change must preserve (a genuine UserOp still flows through untouched) is asserted rather than assumed. The guard requires BOTH halves of the chain, so a partial object is not mistaken for one and a payment is not refused for the wrong reason. No new route, no new scope, no key material, no on-chain behaviour change. Perimeter unchanged; one shared-column assumption made explicit.
