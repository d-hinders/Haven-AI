- **#1482** — `POST /payments/:id/sign` now refuses an erc7710 intent BEFORE claiming it, instead of shape-blind submitting it as a UserOperation. `prepared_user_op` is a SHARED column meaning different things per settlement scheme — a UserOp on the EIP-3009 bridge, a `{ child, budget }` delegation chain on erc7710 (#946/#1454) — and both schemes also set `delegation_hash`, so the route's presence checks could not distinguish them. **Correcting this entry's own first draft**, which claimed the path was "unreachable, both backstops live outside this route": that was wrong about the mechanism and undersold the fix. This route performs no rail-appropriate intent filtering and its delegation-rail signature check is a format regex, not a cryptographic check against `sign_hash` — so any agent-authenticated client could already call it with an erc7710 intent id and a well-formed hex string, bypassing the hosted settle tool's preflight entirely. Nothing moved because `submitDelegationPayment` would spread `{child, budget, …}` into `sendUserOperation` and fail ERC-4337 validation for missing UserOp fields — not because of the on-chain hash check the first draft cited, which is never reached in that scenario. So this turns a live-reachable failure into a clean, correctly-worded refusal; it does not merely guard a theoretical path. **Ordering is the substance.** The first implementation placed the guard AFTER `claimIntentForSubmission`, which stamps the signature and flips the intent to `submitted`; the throw then landed in the catch that calls `failSubmittedIntent`, so a misdirected call BURNED the intent — and since `POST /x402/:id/settle` requires `pending_signature`, it could never be retried on the endpoint that would have worked. A refusal that destroys the thing it refuses is worse than no refusal. The guard now runs before any claim and answers 409 naming the correct endpoint, matching the sibling #946 guard in `modules/x402/settle.ts` for the mirror-image case. Authority is narrowed, never widened: the route refuses where it previously proceeded to a guaranteed failure, no new route, no new scope, no key material, no on-chain behaviour change. `isSettlementChainState` sits on the rail seam beside `deserializeUserOp` — the caller that deserializes is the caller that needs to know what it got — and requires BOTH halves of the chain so a partial object cannot refuse a payment for the wrong reason. Characterization-first per money.md §2: the 3009 UserOp shape is pinned before the guard, verified against what `serializeUserOp`'s two live callers actually produce rather than an invented fixture. Mutation-proven both directions: forcing the predicate true fails the "does NOT flag a UserOp" invariant, forcing it false fails the recognition test.
