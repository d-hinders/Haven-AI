- **#1508** — Hosted erc7710 settlement stopped reporting a SUCCESSFUL settlement as a failure. `haven_settle_mcp_tool`'s erc7710 branch called `deliverMerchantPayment(..., undefined)`, whose first act is `ensureFundingConfirmed`, which reads `GET /payments/:id` **unconditionally** — the `fundingTxHash` argument gates only the on-chain WAIT, never the READ, despite a docstring that promised "No-op when the funding tx hash ... is unavailable" (corrected in this change). By that point `POST /x402/:id/settle` had already flipped the intent to `submitted`, which `agentPaymentStatusHttpCode` maps to **409**, so the SDK threw and the tool returned `API_ERROR` on a payment whose settlement had already succeeded. The fix is a `noFundingLeg` option that skips the call outright rather than tolerating its failure: on a scheme with no funding leg there is no transaction to confirm, so the wait is meaningless work whose only reachable effect was this defect. **No authority, custody, or execution boundary moves.** Nothing about what may be spent, by whom, or under which caveats changes: the settlement child's bounds are still computed by the backend and enforced on-chain during redemption, the delegate key still never leaves the local signer, and the intent lifecycle is untouched — `submitted` remains the correct end state for Haven on this scheme, because the MERCHANT redeems the [child, budget] chain afterwards and final settlement is observed via the merchant/receipt path. The change is strictly to REPORTING, and it narrows a false negative rather than widening any permission. Worth recording precisely because the direction of the error was benign-looking but operationally dangerous: an agent told a completed payment had failed is an agent liable to retry it, and the money-path guidance the tool returns is what agents act on. Also note what did NOT happen and is now pinned: the merchant leg was never reached, so no funds moved and no double-spend was possible — the failure was fail-closed, not fail-open. Mutation-proven: the new `tools.test.ts` case stubs the REAL 409-on-`submitted` response (the pre-existing test stubbed a convenient `200 / settled`, which is exactly why this shipped green) and fails against the unfixed branch. Discovered by probing live intent status across the hosted handoff — `after_quote=pending_signature after_sign=pending_signature after_settle_refused=submitted` — which also empirically confirmed the signer's `GET /x402/:id/sign-context` is genuinely read-only. Perimeter unchanged.
