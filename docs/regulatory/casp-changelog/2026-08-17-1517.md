- **#1517** — The demo merchant stopped reporting a merchant-side FAULT as if it were a payment REJECTION, and started logging it. Its verify/settle catch collapsed every non-`PaymentError` to the fixed string `Payment failed` and wrote nothing to the server log — `http.ts` contained no `console.*` at all — so an RPC failure, a viem error or a bug was indistinguishable from a policy refusal both to the payer and in the merchant's own logs. **No authority, custody, or execution boundary moves.** This is a test fixture, not Haven product code: nothing about what may be spent, by whom, or under which caveats changes; the delegate key still never leaves the local signer; Haven's payment path, policy evaluation, and intent lifecycle are untouched. A `PaymentError` — the merchant's DECISION to refuse — still reports its own reason verbatim and stays unlogged, byte-identical to before, which the pre-existing 58-test merchant suite pins. Only the previously-silent fault path changes, and only to say more: the full error (with stack, product id and settlement method) goes to the server log where it is safe to keep, while the client receives the error CLASS only — `Payment failed — merchant-side fault (HttpRequestError); see merchant logs`. That split is deliberate on a confidentiality footing: it is enough for a payer to tell a broken merchant from a strict one without putting internal messages, hostnames or addresses into a 402 body any caller can read, so the change does not widen what an unauthenticated party learns beyond the fact of a fault and its type. Recorded because the direction of the defect was operationally dangerous in a way that looked benign: a merchant that is BROKEN while claiming a payment was REFUSED invites exactly the wrong remediation — inspecting budgets, delegations and signatures that were never at fault — and it silently defeated triage for two days and four wrong diagnoses on the dev money-flow QA. Also fixes a latent defect in #1516 that this work surfaced: `buildPaymentRequired` ALWAYS sets `error: 'Payment required'`, so `merchant402Reason`'s "no error key" branch was UNREACHABLE and a lost merchant session — the #1515 case that branch exists to detect — would have been misreported as an ordinary rejection; detection now keys off that literal default. The same fact makes `error` an override rather than a first key, so `withReason()` strips the default before placing the reason first, keeping the reason readable in truncated echoes without discarding it. Mutation-proven both ways: the pre-fix catch fails the fault test, and the pre-fix absent-key check fails the bare-challenge test. An intermediate reorder attempt was caught by the existing suite (8 failures, every reason collapsing back to `Payment required`), which is how the always-present default was found. No funds moved and none could: the fault path is fail-closed — the merchant serves no goods and settles nothing. Perimeter unchanged.
