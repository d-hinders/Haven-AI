- **#1521** — SDK-only, EIP-3009 funding-leg path. **No authority boundary moves**: no route, tool schema, capability, caveat, credential scope, or signing scheme changes, and the on-chain envelope (allowance / budget delegation) is untouched — every claim in `casp-risk-guardrails.md` reads identically before and after. What changes is what the client does with an authorize response it already received, and the direction is strictly **less** spend authority created, not more: `authorizeStandardX402` used to mint the EIP-3009 authorization BEFORE posting `/x402`, so when the idempotency key resolved to an already-settled intent it created a fresh signed authorization against a delegate whose USDC was already gone, then returned it paired with the ORIGINAL payment's `tx_hash` as if it were a valid receipt. Authorization minting now happens only after the response is classified, and never at all on a settled branch — **branches, plural, and the review found the second one**: the guard was first written against the delegation rail's `success` + `tx_hash` replay shape (`modules/x402/replay.ts`), which silently missed the LEGACY (AllowanceModule, import-only) rail's approval-queue replay, where `modules/x402/legacy-authorize.ts` returns `getAgentPaymentStatus`'s body — carrying no `success` field at all — and the same unfundable header was minted through `nextAction: retry_original_x402_request`. Both shapes are now gated on what they MEAN rather than on their field layout, and the reintroduction of that gap is itself mutation-proven to fail a test. The two shapes deliberately differ in what an unverifiable balance means, because they differ in caller intent: the delegation-rail shape is an idempotency ACCIDENT (the caller did not ask for this payment) so "cannot tell" refuses, while the legacy shape is the DOCUMENTED post-approval retry loop (the caller is following published steps) so "cannot tell" proceeds and only a balance verified ABSENT refuses — refusing there would have broken every approval resume for an integrator without a `chainRpcs` entry, converting a money-safety fix into an availability regression on a live rail — the mutation-proven assertion is that `exact.evm.createPaymentHeader` is not called, so no spend authorization comes into existence rather than being created and discarded. Recorded because the defect's user-visible shape is a **payer-facing money-safety** one of the same family as #1519: the payer's funds had genuinely moved and the payer was told the payment failed, here by a merchant-side `holds 0 USDC units` error that reads identically to a broken payment rail. No funds were ever at risk of moving twice — the unfundable authorization cannot settle, which is why this is a reporting and legibility defect and not a double-spend — and the collapse itself is the idempotency guarantee working as designed: repeated calls for the same product inside a 5-minute bucket are ONE payment, which is what makes a retried HTTP request safe by default. The **discriminator is deliberately the chain, not Haven's bookkeeping**: `status: 'confirmed'` means the funding leg confirmed and is equally true of a legitimate resume, and Haven's merchant-settlement evidence record is written by the SDK *after* the merchant call, so a client that dies in between leaves the backend believing the merchant was never paid — the exact case the discriminator must get right. `balanceOf(delegate)` cannot be behind in that way. A balance that cannot be read (no `chainRpcs` entry) is reported as `basis: 'unverifiable'` rather than assumed funded, and the two paths default oppositely on purpose: the accidental-replay path refuses (the caller did not ask for this payment), the explicit `resumeAuthorizedX402` path proceeds (the caller named it) and refuses only on a balance verified ABSENT. Deliberately **not** done, on the owner's decision in-session 2026-08-17: narrowing the synthesised idempotency key. Every input a client could add — a merchant nonce, session, or request id — is re-derived from a freshly fetched 402 on each attempt, so it differs between a retry and a second purchase in the SAME direction; adding it would trade today's no-double-spend failure for a double-spend one. Callers who intend a distinct purchase pass an explicit `idempotencyKey`, which is the existing supported mechanism and is now documented as the contract. Perimeter unchanged.
