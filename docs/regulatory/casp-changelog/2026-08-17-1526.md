- **#1526** — Build/dependency configuration only. **No authority, custody, or execution boundary moves**: no route, tool schema, capability, signing path, caveat, or credential scope changes, no runtime code is touched, and every claim in `casp-risk-guardrails.md` reads identically before and after. It reaches this log solely because `scripts/release-bump.mjs` and `packages/connect/src/package-smoke.test.ts` fall inside a contract doc's `covers:` globs, not because anything about what an agent may spend changed — nothing does. Recorded rather than waved through because the *shape* of the defect is one this perimeter cares about: a rule that existed in THREE places with three hand-maintained lists, two of which had silently drifted. `packages/mcp-server` and `packages/demo-merchant-mcp` were missing `private: true`, so tooling that classifies by that flag treated them as npm-published and required exact internal `@haven_ai/*` pins — while `docs/operations/mcp-runtime-compatibility.md` had *already* listed both as unpublished workspace packages. The prose was right; the manifests disagreed with it, and the tooling believed the manifests. Both are now `private: true` with `"*"` pins (the range a workspace-only consumer must use), `mcp-server` leaves `PUBLISHED_PACKAGES` while keeping its lockstep version bump for `HOSTED_SERVER_VERSION` coherence, and the connect pin check derives its package set from each manifest's own `private` field instead of a hardcoded list. That derivation exposed a SECOND drift in the same list, in the opposite direction: `@haven_ai/cli` was absent from it and had therefore never been covered by the wildcard guard at all despite being genuinely published — verified by mutation (wildcarding its SDK dep passes on the old list, fails on the derived one) rather than inferred. Two guards now enforce both directions: `scripts/workspace-pin-lint.mjs` on every PR, and `verifyPrivateConsumersUnpinned` at release time, because a release must not depend on a lint having been run. One claim is deliberately DOWNGRADED rather than repeated: this rule is conventionally justified by "npm silently installs the stale registry tarball", citing the 2026-07-13 money-flow QA breakage — which did **not** reproduce on npm 10.9.7, where npm links the workspace even on a mismatched pin, via both `npm install` and `npm ci`, with and without a lockfile. What does reproduce is scope-sensitivity: with the dependency's workspace outside the install scope an exact pin leaves it uninstalled, while `"*"` links regardless, and an unsatisfiable range fails the install outright. The historical incident record is untouched; its stated mechanism is now labelled unconfirmed and npm-version-dependent wherever the rule is stated (`CLAUDE.md`, `scripts/README.md`, and both scripts) rather than restated as established fact. Container resolution was verified empirically, not argued: replicating the mcp-server Dockerfile's COPY set and `npm ci --workspace=... --include-workspace-root` resolves `@haven_ai/sdk` to a symlink into `packages/sdk`. Perimeter unchanged.
