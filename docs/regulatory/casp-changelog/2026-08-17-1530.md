- **#1530** — QA harness + demo-merchant test fixture. **No authority, custody, or execution boundary moves**: no route, tool schema, capability, signing path, caveat, or credential scope changes, no change to what any agent may spend, and every claim in `casp-risk-guardrails.md` reads identically before and after. It reaches this log because `packages/demo-merchant-mcp/src/x402.ts` sits inside a contract doc's `covers:` globs. The change is observational in both halves: the demo merchant now REPORTS the native balance of the wallet that submits settlements, and the money-flow QA harness reads that report — plus delegate residuals — before its first leg and refuses to run when a resource is definitively below floor. Nothing new is authorised; a run is refused EARLIER, which is a strict reduction in what executes under a known-bad precondition. Recorded because of what it says about the perimeter's observability rather than its shape. On 2026-08-17 the dev demo-merchant's settlement wallet held 255 gwei; every x402 leg requiring a merchant-side settlement failed, the merchant surfaced an error naming nothing about gas, and the cause sat undiagnosed behind four defects it was masking (#1517, #1519, #1520/#1521, #1441). Haven's own payment path was correct throughout — funding leg, delegation, allowance metering, signing and sweeps all behaved properly on-chain in every run examined — which is precisely why the failure was expensive to attribute: an exhausted third-party settlement wallet is indistinguishable from a broken Haven payment path from the outside. `docs/architecture/04-x402-payment-sequence.md` gains that as a stated guardrail, including the part that does NOT get fixed by this issue: a third-party merchant offers no readiness signal at all, so the same ambiguity remains wherever Haven is not also the fixture. Two deliberate non-disclosures, both checked rather than assumed: the settlement wallet's ADDRESS is reported and its private key is not — the address was already public, advertised as `redeemerAddress` in erc7710 challenges, and an on-chain balance is public by construction, so the readiness block discloses nothing new. And a readiness read that throws is reported as UNKNOWN rather than unhealthy, so an unreachable RPC cannot take the merchant's health endpoint down or block a QA run on the harness's own blind spot. Mutation-proven in both directions: a preflight that never blocks, a preflight that treats unknown as failure, and a headroom floor of one (which would report healthy on the very run that exhausts the wallet) each fail a distinct test. Perimeter unchanged.
