- **#1515** — The demo merchant's erc7710 rail gained the restart-survival guarantee #1519 gave the EIP-3009 rail: a merchant process restart between settlement submission and the buyer's retry can no longer turn a PAID purchase into a refusal. An exact-amount settlement child that already moved the money fails the redemption simulation (its transfer-amount caveat is exhausted) exactly like an unauthorized one, and the merchant's only memory of "already settled" lived in in-process maps that die with the container — including on every Railway redeploy, which fires on every push to `dev`. The merchant now asks the chain, under three binds that all must hold: (1) the leaf delegation decoded from the payment's `permissionContext` must carry a caveat whose enforcer is the **pinned** `ERC20TransferAmountEnforcer` for the configured chain — never an address the payload chooses, because the payload is unauthenticated on this path (it is reached precisely because simulation against the pinned DelegationManager failed), and trusting `spentMap` from an attacker-named contract would be a free-goods bypass; (2) that caveat's own committed cap must **equal** the payment amount — a settlement child is minted exact-amount per payment, and a mere `spent >= price` comparison would let a child exhausted on an expensive product satisfy a cheaper one once the restart wiped the in-memory cross-product guard; (3) the pinned enforcer's `spentMap` for this delegation's hash (obtained from `DelegationManager.getDelegationHash`, a `pure` function, so it answers while the simulation reverts) must be at least the amount. Only then is the purchase treated as already settled: the goods are served through the existing `AuthorizationAlreadyUsedError` branch and **no second `redeemDelegations` is submitted**. Every failure mode of the check — undecodable context, no pinned caveat, cap mismatch, unreachable contract, unconfigured enforcer pin — resolves to the pre-existing refusal, so the check can add served-without-payment outcomes only if all three binds are subverted at once. **No authority, custody, or execution boundary moves.** The two added calls are read-only (`pure`/`view`); the merchant gains no new ability to move funds; the delegate key still never leaves the local signer; and Haven's payment path, policy evaluation, funding leg and intent lifecycle are untouched. Scope note, corrected during review: `demo-merchant-mcp` is **not** an isolated test fixture — it is deployed as a production Railway service pinned to the mainnet DelegationManager and settles real Base USDC (the #1458 canary), so this was reviewed as a money-path change on that basis. Mutation-proven three ways: disabling the already-redeemed check fails the restart test (the paid retry is 402'd); replacing the pinned-enforcer bind with a scan of all caveats fails the forged-enforcer test; relaxing the cap equality back to `spent >= amount` fails the cross-product replay test. Perimeter unchanged.
