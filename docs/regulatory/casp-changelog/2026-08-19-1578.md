- **#1578** — The demo merchant now refuses a paid retry that carries an UNKNOWN MCP session id **before the payment gate runs**: HTTP 404 with JSON-RPC error `-32001` ("Session not found"), the MCP SDK's own contract for an invalid session. Characterization first showed today's behaviour was the opposite shape: the request silently fell through to an anonymous transport and happened to succeed — protocol-invalid, and one strict-client quirk away from money harm, because settlement ran before session validation and a client refusing the session-less response would have consumed its one-use payment authorization for a response it discards. The ordering is the fix: nothing settles on the stale path, the client re-initializes (initialize is exempt from the guard — it is the recovery door) and retries the SAME payment header, which then settles exactly once; the #1519 (EIP-3009 `authorizationState`) and #1551 (erc7710 `spentMap`) already-settled safeguards are untouched and still cover replays of a settled header. Stateless calls (no session header) are unaffected and still mint no reusable session. **No authority, custody, or execution boundary moves** — this narrows when the merchant will settle (never for a session it cannot validate), adds no new ability to move funds, and the regression test proves the stale path makes zero settlement submissions while the recovery path makes exactly one. Mutation-proven: disabling the guard fails the restart test. Perimeter unchanged.
