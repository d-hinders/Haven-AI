- **#1618** — the EIP-3009 x402 funding-leg lifecycle moved out of `HavenClient` into two internal SDK modules: `x402-protocol.ts` for what both settlement schemes share (quote, receipt and resume shapes, the merchant request snapshot, the `x402-wallet` header, the resume state checks) and `x402-funding-leg.ts` for what only the two-hop scheme has (funding confirmation, the delegate's fundability check, header minting from the local delegate key, the authorization-keyed receipt cache). **Behaviour-preserving: no authority, custody or execution boundary moves, no wire contract changes, and nothing new is grantable.** Non-custody is untouched — the delegate key never leaves the caller's process, Haven still never signs, and the module can only ask the chain and the backend the same questions the facade asked before. The `#1521` discrimination between a legitimate resume and a replayed settled payment moved verbatim, including its asymmetry (an idempotency collision refuses when the delegate's balance is unverifiable; a documented approval resume proceeds unless the balance is verified ABSENT), and its regression fixtures still pass unchanged against the extracted module — mutation-proven: neutralise the refusal in its new home and five of them fail. The separation itself is now guarded, because the leak it prevents is the one that produced #1510/#1511/#1521: a test asserts the neutral protocol layer never imports the funding leg, so the erc7710 direct-settlement path (#1619) cannot inherit a funding leg it does not have. Perimeter unchanged.
