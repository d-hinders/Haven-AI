- **#1630** — `GET /x402/receipts` now formats `amount_human` with the receipt token's own decimals instead of 6 unconditionally; an unrecognised token still falls back to 6, the same tradeoff the sibling `price_human` field has always made here. **No authority, custody or execution boundary moves, no on-chain behaviour changes, and nothing new is grantable** — `amount_human` is a DISPLAY string, and `amount_raw`, the authoritative value the receipt is reconciled against, is untouched. What changes is the accuracy of what a reader is shown: for an 18-decimal token such as Gnosis EURe the old value was wrong by twelve orders of magnitude, so a €1.50 receipt rendered as 1500000000000 — a reporting defect, not a settlement one. The OpenAPI description that documented the wart while it stood now documents the behaviour, fallback included. Mutation-proven, and because the test file stubs the chain registry, a second test pins the REAL registry's decimals so a wrong stub cannot keep a wrong test green. Perimeter unchanged.
