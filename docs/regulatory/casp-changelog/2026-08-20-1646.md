- **#1646** — login now costs materially the same whether or not the account exists. The endpoint already answered an identical 401 for an unknown email and a wrong password so it would not be an account-enumeration oracle, but `bcrypt.compare` at cost factor 10 ran ONLY when a user row existed, so an unknown address returned after a single fast SELECT and the latency difference disclosed exactly what the equal answer was hiding — measurable by anyone, unauthenticated. The comparison now runs on both paths, against a module-load hash of unguessable random bytes that is never stored, so it can only ever fail: it costs time, not security. What remains observable is the indexed lookup itself, sub-millisecond against bcrypt's tens of milliseconds — the accepted floor for this mitigation, not a claim of perfect equality. **No authority, custody or execution boundary moves and nothing new is grantable** — this closes a disclosure channel about ACCOUNT EXISTENCE, not about credentials or funds. The OpenAPI description that honestly recorded the gap while it was open is updated in the same change, since it would otherwise understate the protection. Pinned by a test that asserts the INVOCATION rather than the clock (a latency assertion tests the machine and flakes in CI); mutation-proven — against the previous shape bcrypt is called zero times for an unknown email. Perimeter unchanged.
