- **#1654** — the signup account-enumeration disclosure is now an ACCEPTED, documented tradeoff rather than an implicit one. `POST /auth/signup` answers a distinct 409 for a taken address, so one unauthenticated request reveals whether an email has a Haven account — stronger than the timing oracle #1646 closed on login, and conspicuous once login became airtight. **Nothing about the perimeter or the disclosure itself changes in this entry; what changes is that the tradeoff is written down where it is read.** The acceptance rests on two grounds the OpenAPI description now records: telling a returning user "you already have an account — sign in instead" is real product value, and the standard mitigation is structurally unavailable — signup's 201 carries the SESSION TOKEN, so an always-201 for a taken address would either mint a token for someone else's account or return a token-less 201 that is an equally strong oracle. Rate limiting was considered and deliberately not added: without trustProxy every external caller shares one per-IP bucket behind the proxy (the repo's own rate-limit doc records this), so a meaningful limit is a cheap global auth denial-of-service and a per-email key cannot throttle enumeration by construction — the trustProxy prerequisite is filed separately (#1670). Genuine hardening needs an email-verification channel this API does not have; the decision explicitly directs that if such a channel is ever added, the tradeoff is revisited in the same change, and a test pins the structural fact (token in the 201) so that change cannot land without tripping it. No authority, custody or execution boundary moves and nothing new is grantable. Perimeter unchanged.
