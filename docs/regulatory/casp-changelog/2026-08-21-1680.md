- **#1680** — the rate limiter's counters move from an in-process store to a shared Postgres table, so the documented ceiling is the real one. **No authority, custody or execution boundary moves and nothing new is grantable** — this NARROWS what an unauthenticated caller can do, and only that. What it corrects is a control that read as protection without binding: `@fastify/rate-limit`'s default store is per-process, so each replica counted only its own share and the effective ceiling was `max × replicas` — rising with load, because more traffic means more replicas. Live probing of the dev deployment surfaced it as two interleaved descending `x-ratelimit-remaining` series. Fixed on the house pattern for process-local state that breaks under replicas (`allowance_nonce_watermarks`, #692/#1196) rather than with new infrastructure: one row per bucket key, incremented by a single `ON CONFLICT DO UPDATE` so concurrent replicas serialise on the row instead of racing, proven against real Postgres including a 20-way concurrent increment that loses nothing. It carries the same two obligations, and here they are sharper: **fail-open** — a database error or a query past the 250 ms deadline degrades to per-replica counting, never to a refusal, because this guards signup and login and failing closed would lock every user out of the front door over a hiccup — and every degradation is logged, because falling back silently is the failure being ended. The database is also not consulted for a client already over its limit, so unauthenticated traffic cannot amplify a cheap request into row-lock contention. Perimeter unchanged.
