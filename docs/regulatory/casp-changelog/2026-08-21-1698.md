- **#1698** — AGENT RE-KEY: a new owner-authorised operation that retires an agent's whole credential set — delegate key and API key together — and reissues authority to a new delegate with the budget meter carried across. This one **moves an authority boundary**, so the analysis below is a real perimeter analysis rather than the "perimeter unchanged" note most shards carry. **What is new is a way to REPLACE authority; what is emphatically not new is any way to CREATE it.** Every delegation issued by a re-key is signed by the account owner exactly as an ordinary grant is (`delegationSigningPayload` → owner signs client-side → `activate`), Haven signs nothing (#824 invariants 5/12), and the total spendable inside the replaced period is capped at what the retired grant had left. A re-key that the owner never signs produces `pending` rows that redeem nothing. **Non-custody is preserved structurally, not by policy:** the endpoint takes `new_delegate_address`, a PUBLIC address of a keypair generated on the target machine, and there is deliberately no endpoint anywhere in this diff that accepts, stores, transports or "restores" private key material — #1694 records that design as out of scope and to be refused rather than built, and the absence is the enforcement. `agent_rekeys` stores two public addresses, a residual amount, and a frozen meter reading; the rotated API key is stored as a SHA-256 hash on `agents` exactly as before, so the table records THAT a rotation happened and never what it produced.

  **The authority boundary that moves, precisely.** Before this change, an agent's delegate key was immutable for the life of the agent: the only responses to a lost or exposed key were revoke-and-recreate (a new agent id, new history, a dead passport) or nothing. After it, the account owner may replace the key in place. The actor authorised to do that is the ACCOUNT OWNER and only the account owner — `agent_rekeys.initiated_by_user_id` records who, every query is scoped `WHERE user_id = $1`, and the routes sit behind `authMiddleware` (the dashboard session) with an ADDITIONAL explicit refusal, `refuseAgentCaller`, that answers 403 `agent_cannot_rekey` to any caller presenting an `sk_agent_` credential. That second guard is redundant today and deliberate: #1694's invariant is "an agent can never re-key itself — an agent rotating its own credentials would be an agent editing its own authority", and an invariant that holds only because of which hook happens to be installed is one refactor away from silently leaving. It is mutation-proven (`routes/__tests__/agent-rekey-guards.test.ts`): deleting the guard fails a test even though the route would still be behind session auth.

  **Ordering is the safety property, and it is stated twice, independently.** #1694's owner decision — "revoke must precede issue, never the reverse" — is not a preference about tidiness; the two orderings have asymmetric failure modes. Revoke-then-issue fails to *the agent has no authority*: recoverable by re-running the issue half, and the correct posture when the key is lost, because a lost key is already inert. Issue-then-revoke fails to *two simultaneously live keys on a funded account*, which is the exact failure the #1569/#1681/#1688 family is made of and which no retry repairs. Because both halves are on-chain and owner-signed, a re-key necessarily spans several requests, so the ordering has to hold BETWEEN them — which means it cannot live in the order of statements inside one handler. It lives (a) as a stage machine in `modules/agents/rekey-stages.ts`, where every route asks `assertStageAllows` before acting, and (b) as CHECK constraints in migration `065_agent_rekeys.ts` that no code path can route around: `agent_rekeys_meter_after_revoke_check` rejects any row carrying a carry snapshot without a `revoked_at`, or with a `metered_at` earlier than it, and `agent_rekeys_metered_stage_check` rejects a `metered`/`issued`/`completed` stage with no snapshot. A partial unique index allows at most one in-flight re-key per agent, so two concurrent rotations cannot race to revoke and issue against each other's measurement. Every stage advance is a conditional `UPDATE … WHERE stage = <expected> RETURNING`, so a stale caller loses rather than proceeding on a stale read.

  **The meter is read AFTER the revoke, and that this is SAFE is asserted rather than assumed.** #1694's review amended the original ordering: reading the remaining budget before the revoke leaves a window in which a payment lands and the carried remainder over-counts it by that amount, whereas after the revoke the on-chain state is frozen and the ordering costs nothing. The amendment is only sound if the caveat enforcer's spent-amount storage survives the revoke, and #1698 required that to be verified, not presumed. It is, structurally and therefore for every chain and every block rather than for one sampled read: `buildRevocation` encodes `disableDelegation` against the **DelegationManager**, while `readRemainingBudget` reads `getErc20PeriodTransferEnforcerAvailableAmount` from the **ERC20PeriodTransferEnforcer**, keyed on the delegation object alone and consulting no disabled-delegation flag. Two different contracts; the read has no input through which "this one is revoked" could reach it. Both halves are pinned by characterization tests committed BEFORE any behaviour changed (money-path rule), including the negative assertion that the revoke target is not the enforcer — the one that would fail if a future kit upgrade ever moved the disable write.

  **A budget-leak class found while writing this, and closed.** `readRemainingBudget` falls back to the FULL budget when its RPC read fails — correct for the status display it was built for (a transient RPC problem must not tell a funded agent it cannot pay), and a **budget leak** for a carry, because carrying the fallback would hand a re-keying agent a fresh full period. The carry therefore refuses a reading that did not come from the chain (`CarryRefusedError`, code `meter_not_from_chain`) rather than inheriting the fallback, and refuses a remainder larger than the granted budget rather than clamping it. Two callers of one reader, deliberately differing, with the reason recorded at both ends.

  **The carry preserves the period boundary, not only the amount** — #1694: "carrying only the amount would let repeated re-keys shorten periods and leak budget". The leak is easy to miss because the amount-only version looks right: carry 40 of a 100 daily budget with a fresh clock, re-key again an hour later carrying 40 again, and the period stops being a rate limit and becomes a tally. The period enforcer takes exactly `periodAmount`, `periodDuration`, `startDate` and refills at every boundary, so there is no "smaller first period" in that shape; expressing the decision takes two grants. A **carry** grant is capped at the frozen remainder, anchored one period before the boundary so its current period IS the old one, and given a timestamp caveat expiring AT the boundary so it can never refill; a paired **steady** grant carries the original budget and cadence with `startDate` = that same instant, dormant until the carry dies. They never overlap. Asserted against a partially-spent period rather than a fresh one, and the bypass criterion — "a re-key attempted twice in the same period cannot yield more total spend than the original period allowed" — is proven for two re-keys and again for ten, since the leak the decision names is specifically about repetition. Mutation-proven: anchoring the carry at `now` (the tempting amount-only implementation, which gets the amount right and the boundary wrong) fails `rekey-carry.test.ts`.

  **In-flight intents quoted against the retired payer are invalidated, precisely on both axes.** `payment_intents.delegate_address` is a NOT NULL first-class payer stamp, so invalidation matches `status = 'pending_signature' AND LOWER(delegate_address) = LOWER(<old>)`. Both predicates are load-bearing and both are mutation-proven: dropping the status predicate would rewrite `submitted` and `confirmed` rows — settled payments' records — and dropping the payer predicate would cancel working payments on a multi-budget agent for no reason. This is the PRIMARY defence; #1690's signer-side payer guard is a backstop, per #1694. Closing the window here also keeps #1690's refusal message truthful: a payment quoted before a re-key and signed after it would otherwise be refused with the stale-host diagnosis, which misdescribes a legitimate rotation.

  **Residual funds on the retired delegate EOA are a preflight REFUSAL, not a warning.** The EIP-3009 bridge transiently funds the delegate EOA and `haven_sweep_delegate` needs the OLD key's signature, so once a rotation completes the credential set that could authorise a sweep is gone and the balance is stranded permanently — by the user and by Haven alike. The 2026-08-21 canary's 0.002 USDC is the concrete shape. Preflight therefore reads the old EOA's balance and, when it is non-zero, refuses with 409 `residual_funds_on_old_delegate` naming the amount and the two ways forward: sweep first and retry with `residual_disposition="swept"`, or — when the key is lost and sweeping is impossible — retry with `residual_disposition="acknowledged_unrecoverable"` to proceed and write the balance off knowingly. A FAILED balance read is 503, not a shrug: proceeding would retire the only key that could sweep without knowing whether there is anything to sweep, and the mistake is unrecoverable, which is precisely the case for refusing rather than guessing. The amount and its irrecoverability are echoed again in the completion response, so nothing about a stranded residual is discovered later.

  **Rails, and what is deliberately NOT reachable.** Re-key is delegation-rail only (#1694). A legacy AllowanceModule account gets an explicit 409 `rekey_not_supported_on_legacy_rail` that names re-onboarding as the path AND says why — that rail's authority is a set of per-token on-chain allowances rather than a signed delegation, so there is no delegation to revoke and reissue and no period to carry. Refusing without naming the path reads as an oversight when it is a structural difference between the rails. Nothing is written on any refusal, which is true by construction: both guards are pure functions taking no database handle. Retired session-rail and half-provisioned accounts are refused too.

  **Custody, credential and non-custody invariants re-checked against `casp-risk-guardrails.md`:** Haven does not hold or receive any private key (the new keypair is generated on the target machine; only its public address crosses the wire); an API credential is still not sufficient to spend (the rotated key authenticates, the on-chain delegation authorises, and the re-key itself cannot be invoked with an agent credential at all); off-chain policy is not the real control (the carry's cap and boundary are compiled into caveat enforcers and enforced by the DelegationManager at redemption — the `agent_rekeys` row is a ledger, not a gate); no signed payment intent is mutated (in-flight intents are EXPIRED with a reason, never re-signed or re-pointed); no swap, ramp, fiat, card, merchant-settlement or yield surface is touched; and the user's ability to revoke Safe permissions outside Haven is unchanged — a re-key uses the same owner-signed `disableDelegation` path the dashboard already exposes. **Testnet only in this diff**; nothing here moves mainnet funds and no production database is written.

  **Honest coverage note, recorded here rather than only in the PR:** the real-DB suites that prove the CHECK constraints, the stage advances, the credential rotation and the intent invalidation could NOT be run locally — this machine has no Postgres accepting connections. The pure-arithmetic, ordering and guard suites ran green locally (mutation proofs included); CI carries the real-DB half, and the reviewer should weigh it knowingly rather than read a green local run into it.
