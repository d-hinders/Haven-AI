- **#1705** — the transaction wire contract gains one optional, nullable, read-only reporting field: `settlementScheme` (`'eip3009' | 'erc7710' | null`) on `TransactionBase`, regenerated into `@haven_ai/core`'s API types, with the matching `settlementScheme?: string | null` on the backend's `EnrichedTransaction`. **No custody or authority boundary moves, and nothing here is grantable.** This is the type/spec layer of epic #1704 and is *inert on merge*: no route is added or changed, no SQL is read, no mapper populates the field, and no UI renders it — #1706 threads the value out of the intent's `machine_metadata` JSONB and #1707 renders it, both separately reviewed. Nothing in this diff touches payment execution, credential scope, key material, a signing path, or spend authority; which scheme a payment uses is still decided where it always was (the authorize request's `payTo` shape, `modules/x402/delegation-authorize.ts`) and still enforced on-chain by the caveat enforcers during redemption — this field only *reports*, after the fact, which branch already ran. Two boundary observations stated positively. (a) The field is deliberately **describing, not deciding**: it is optional and never `required`, so a row that predates it validates unchanged, and the enum is closed to exactly the two schemes the backend actually stamps — a mapper that invents a third value or emits a snake_case key fails the contract rather than reaching a client (mutation-proven: removing the enum, snake_casing the key, making it non-nullable, marking it required, restating it on the aggregate, and dropping `execution_rail` from the description each fail exactly the assertion that guards them). (b) The **legacy-rail null asymmetry is deliberate and recorded in three places** (the spec description, the TS field's doc comment, and a test that fails if the description stops saying so): `legacy-authorize.ts` never stamps the key because that rail is structurally EIP-3009, so legacy rows carry `null` and the dashboard will show nothing rather than a value nobody wrote. Null-in-null-out — no inference, no on-chain backfill, no guess presented to a user as a fact about how their money moved. The terminology guardrail is part of the contract text for the same reason: settlement **scheme** is not `source` (the payment protocol) and not `execution_rail` (the account architecture), and collapsing the three axes in a reporting surface would misdescribe the perimeter rather than merely read badly. Perimeter unchanged.
