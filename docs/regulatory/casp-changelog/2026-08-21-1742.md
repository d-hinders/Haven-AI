- **#1742** — the passport REVOCATION anchor's confirmation wait is bounded (`tx.wait(1, PASSPORT_REVOKE_CONFIRM_TIMEOUT_MS)` instead of a bare `tx.wait()`, which waits indefinitely in ethers v6), and an expiry HANDS THE TRANSACTION OFF instead of recording a failure. **No authority, custody or execution boundary moves and nothing new is grantable** — an EAS `revoke` targets the pinned attestation contract with `value: 0`, carries no user key, delegation or allowance, and can only ever REDUCE an agent's standing; no funds move differently. This is the third instance of the defect shape fixed for the hybrid deploy (#1722) and the attest half (#1735), and it is the safety-critical one: `revocation.ts` treats Haven's DB as authoritative and this is the on-chain anchor catching up, so an unbounded wait means an agent Haven considers revoked keeps a live, merchant-readable attestation. The blast radius was larger than the anchor's, because the passport sweep is SEQUENTIAL under one leader lock (`index.ts` `runPassportSweep` → `runIfLeader`, which holds a pooled Postgres connection for the whole tick): one never-mining revoke parked every revocation queued behind it, the pooled connection, and — the sharp end — the `alarm` phase downstream of it, so `listStuckRevocations`, the one signal that reports "agents revoked in Haven still hold a live attestation on-chain", was silenced by exactly the condition it exists to report. The value is bracketed, not round — above a healthy one-confirmation EAS call on 2 s Base blocks, and below BOTH owners that can take the transaction over: the #1558 bump worker's 180 s adoption age and the 300 s revocation lease (`claimRevocation`). On expiry the durable outbound record (#1556) is deliberately left `broadcast` rather than `failed`, because a wait timeout cancels nothing and the transaction may still mine; `passport_revoke` is on the bump worker's rebroadcast-safe list (a second revoke of the same UID reverts, moving nothing) AND its stale-broadcast scan replaces at the same nonce, so the hand-off is safe on both of the worker's paths. A null receipt takes the same branch for the same reason (#690: a lagging RPC can return null for a confirmed tx) — "no receipt" is not "reverted", and the reason string no longer blames a revert that never happened. A genuine mined-and-reverted revoke still closes the record failed, unchanged, as does any non-TIMEOUT wait error. The caller `reconcileRevocation` catches the new `PassportRevokeUnconfirmedError` like any other revoke error and schedules a backoff retry, so the anchor keeps converging on the DB's authoritative `revoked` standing — which is `revocation.ts`'s stated design ("no terminal failed revocation state"); timing out is therefore the SAFE direction, re-queuing the revoke instead of hanging the queue that carries it. Mutation-proven in four directions: restore the bare `tx.wait()` and the deadline tests hang; disable the hand-off and the expiry/null-receipt tests fail; raise the constant past 180 s and the bracket test fails; widen `isWaitTimeout` to always-true and both the revert and non-timeout-error guards fail. Residual, and newly REACHABLE rather than newly created: a revoke that mines after its wait expired leaves `revocation_status` pending, because the backoff retry then hits EAS `AlreadyRevoked` and cannot tell "already revoked by MY earlier transaction" from a genuine failure — an unresolved stuck-revoke alarm plus bounded relayer gas, never a live credential, and the on-chain end state is the desired one; filed separately rather than widened into this change. Perimeter unchanged.
