- **#1745** — a passport anchor whose receipt cannot be read is no longer presumed dropped: the re-mint now requires positive evidence that the prior transaction can never mine, so one agent can no longer end up holding TWO live credentials. **No authority, custody or execution boundary moves and nothing new is grantable** — an EAS attestation is governance metadata, carries `value: 0`, targets the pinned EAS contract, and involves no user key, delegation or allowance, so nothing in this diff can move funds or change what may be spent, by whom, or from which account. What changes is when Haven is willing to sign a SECOND assertion about the same agent. **Why that is nonetheless a perimeter question and not boilerplate.** The passport is the artifact Haven signs *as issuer*, and its L0 claim set is "issued by Haven, bound to this treasury, governed by on-chain-enforced controls, and **revocable**". Duplication does not widen spend authority — the attestation confers none — but it does damage the one property the credential exists to guarantee. Revocation is derived from agent revoke and is keyed on the UID Haven has stored, and `agent_passports` stores exactly one; a duplicate mint OVERWRITES `tx_hash` and `attestation_uid` with the second attestation's, so the first becomes permanently invisible to Haven while remaining live and revocable-looking on-chain. Revoking the agent would then revoke the credential Haven can see and leave the orphan standing, and a merchant resolving that orphan's UID would read a live, unrevoked Haven-issued passport for an agent the owner believes they have shut off. That is an **authority-surface** defect in the honest sense: not authority to spend, but a durable public assertion by Haven that outlives the owner's ability to withdraw it, which is precisely what #1042/#1043 were built to prevent and what `agent-passport.md`'s "revocation is the live control" claim rests on. **The mechanism.** `recoverAnchorFromReceipt` returns `null` when `getTransactionReceipt` returns null, and ethers cannot distinguish a transaction still sitting in the mempool from one genuinely dropped; `issuePassport` read that null as "dropped" and anchored again at the next relayer nonce. The presumption fired far sooner than the 600 s anchoring-claim window the code comment implied, because `markFailed` sets `anchoring_started_at = NULL` — making that window vacuous on the failure path — and `listRetryable`'s backoff is 60 s at the first attempt, so ≈180 s after the original broadcast (120 s confirmation wait + 60 s backoff) the sweep re-mints. A merely fee-stuck attest — the exact scenario #1735 exists to make survivable — would therefore be duplicated at `N+1`, and if the original ever mined, both mined. **The fix, and the asymmetry that chose it.** A null receipt is now treated as the absence of evidence it is. `classifyAnchorTxLiveness` answers a different question from recovery — not "did it succeed" but "can it still succeed" — and only `dead` unlocks a second attest. Death is declared from ONE positive fact: the transaction's nonce slot consumed by something else, read as `getTransactionCount(relayer, 'latest')` past the nonce the durable outbound record (#1556) stamped at broadcast. A transaction can only ever mine into its own nonce and a nonce is spent once, so that is arithmetic rather than a timeout. Everything weaker withholds the re-mint: a transaction any node still knows (pending or mined-but-receipt-not-yet-visible, #690), a missing or un-stamped outbound record, a `replaced` or `mined` record, an unreadable provider, and — as the last guard against a load-balanced RPC fleet answering two reads from nodes at different heights — a receipt that appears on a confirming re-read after the burn is observed. With no probe wired at all the default is refusal, never fall-through. The trade is stated rather than buried: a wrongly withheld re-mint stalls ONE issuance, retryably, with `ISSUANCE_ATTENTION_ATTEMPTS` alarming; a wrongly permitted one mints a second real, revocable credential no later tick can take back. **The stall is recoverable, and the recovery is the operator cancel that was already the documented response — not, as a first draft of this analysis claimed, Haven's own next broadcast.** The withheld row is marked failed-retryable with the claim released, so it is due again on the ordinary backoff. It is tempting to argue further that a genuinely dropped transaction stops reserving its nonce, so the relayer's next broadcast takes the slot and issuance self-heals with no human involved; that argument is **wrong**, and the correction matters more than the claim would have. `submitRecorded` allocates from `getNonce('pending')`, but the stuck attest still holds a `broadcast` row at that nonce and migration 061's partial UNIQUE `(chain_id, nonce) WHERE status = 'broadcast'` refuses the stamp — the queue re-reads the same nonce and throws `could not win a nonce lane`. So the relayer lane that #1735 already documents as blocked stays blocked, and what burns the nonce is the same-nonce cancel in `delegation-rail-vendor-ops.md` §3 (a 0-value self-send). What this change buys is that the cancel is now **sufficient on its own**: once it mines, the burned nonce is exactly the evidence the sweep needs, so issuance completes on the next tick with no further operator action — and the runbook's duplicate-check sequencing added by #1735 is retired rather than standing in for a missing guard, because no duplicate is ever queued while the stuck transaction is live and cancelling therefore has nothing to release. The runbook now says explicitly to cancel even when the transaction has vanished from the mempool, since "it dropped, so the lane will clear itself" is exactly the intuition the UNIQUE index defeats. **What is deliberately NOT decided here, and why it is not a gap this PR should have closed:** the time question — how long an unmined attest whose nonce is STILL OPEN may sit before Haven declares it dead of its own accord. That is #1743's owner call, it has duplicate-credential consequences in exactly the direction this issue is about, and it is not derivable from the code; until it is answered, an attest holding its own nonce is live for as long as it holds it. **Accepted residuals**, named rather than implied: (1) a hand-run fee bump of a `passport_attest` outside Haven's own pipeline — the bump worker will not do it (#1735) and a `replaced` record is honoured, but a bump performed directly against the relayer key leaves no record, and re-minting after it would duplicate; the runbook's instruction to cancel rather than re-broadcast is what keeps this out of reach. (2) The by-hash read on `outbound_txs` is unindexed; it runs only on the recovery path of a stuck anchor, at most once per backoff tick, and adding an index would have gated this fix on a migration review. (3) `issuePassport` and the bump worker remain two independent reconcilers over the same chain state — this change makes the passport half consult the outbound record, which narrows the gap but does not unify them. Characterization tests pinned today's duplicate mint on the real-Postgres harness BEFORE the change and are inverted by it; every guard is mutation-proven, including a mutation that restores the vacuous 600 s window. Perimeter unchanged.
