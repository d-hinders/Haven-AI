- **#1756** — the PUBLISHED SDK's delegate sweep bounds both confirmation waits (`wait(1, DEFAULT_CONFIRMATION_TIMEOUT_MS)` instead of `wait(1)`, which passes CONFIRMATIONS and no deadline, leaving it as unbounded in ethers v6 as a bare `wait()`), and an expiry is REPORTED to the caller instead of hanging it. **No authority, custody or execution boundary moves and nothing new is grantable** — `sweepDelegate` is signed and submitted entirely by the caller's own delegate key on the caller's own machine (CASP/MiCA Red Line #2: Haven's backend never sees the key and constructs nothing here), the destination is fixed to `agent.safeAddress` as returned by the authenticated agent lookup and is not an argument, and the transfers themselves are unchanged in amount, asset, direction and gas reserve. What changes is only when the SDK stops waiting and what it tells the caller. This is the fourth and last site from the #1742 repo-wide sweep and the only one outside `packages/backend`; it is also the widest blast radius per line, because it ships on npm as `@haven_ai/sdk` and runs inside the user's agent process — a fee-stuck sweep hung the calling CLI or agent **forever**, with no timeout, no error, and no way to learn the tx hash it was waiting on, which is the one piece of information that lets a user recover funds by hand. Sweep is funds-RECOVERY: it moves stranded delegate balances back to the Safe, so a hang here is a user who cannot get their money out and cannot tell why. **The terminal state deliberately differs from the three backend fixes, and the difference is the substance.** #1722, #1735 and #1742 could each hand a stuck transaction to a durable `outbound_txs` record and the #1558 bump worker; the SDK has neither — no queue, no worker, no database — so the CALLER is the only possible owner of a stuck transfer. Throwing on expiry would therefore destroy exactly what that owner needs (the broadcast hash) and would additionally assert a negative outcome the code does not know, which is the same defect as #1754's timeout-reported-as-a-revert one layer out. Expiry instead returns a per-leg `confirmation: 'unconfirmed'` carrying the BROADCAST hash and explorer URL, alongside a top-level `unconfirmed` flag; `confirmed` continues to carry the RECEIPT hash. The two legs are reported independently because they can genuinely disagree, and a single thrown error cannot express "the USDC landed, the ETH is still in flight". A null receipt takes the `unconfirmed` branch for the same reason (#690: "no receipt" is not "confirmed"); before this it silently substituted the broadcast hash and the entry was structurally identical to a confirmed one. A genuine revert (`CALL_EXCEPTION`) and every non-`TIMEOUT` wait error still throw, unchanged. A second behaviour change follows from the bound and is a funds-recovery improvement in its own right: the native-ETH leg now runs even when the USDC leg came back unconfirmed, where previously a stuck ERC-20 transfer stranded the ETH the same sweep exists to recover. The deadline is the SDK's existing 90 s `DEFAULT_CONFIRMATION_TIMEOUT`, relocated from `client.ts` to `types.ts` AND RENAMED to `DEFAULT_CONFIRMATION_TIMEOUT_MS` (same value, same `??` fallback semantics, now a public export), shared with the payment-confirmation poller rather than forked into a fourth independently chosen literal (`x402-funding-leg.ts` is already bounded at 30 s); no new number is introduced, and nothing in the SDK derives a spend limit, expiry or authorization window from it. Characterization-first: the pre-fix hang, the arity of `wait(1)`, and the null-receipt-as-success are pinned in their own commit and inverted by the fix; the `wait` mock mirrors ethers v6 verbatim in that it settles only via the caller's `timeout` argument and never settles without one, so a regression to the unbounded call HANGS the tests rather than quietly passing them. Mutation-proven in five directions: drop the timeout argument and the deadline tests hang plus the arity assertions fail; make expiry throw and the unconfirmed-reporting tests fail; make expiry report `confirmed` and the distinguishability tests fail; widen `isWaitTimeout` to always-true and both the revert and the non-timeout-error guards fail; change the shared constant and the pin against the payment poller's default fails. **Residual, stated plainly: this does not reach npm users until the next release.** The fix lands on `dev` and ships only when `release:bump` + the `dev → main` promotion publish `@haven_ai/sdk`; until then every installed copy still hangs, and nobody should read this merging as npm having the fix. Second residual, pre-existing and deliberately not widened into here: a revert on the ETH leg still discards the USDC entry that already confirmed, because the throw unwinds the whole call — the same information-loss shape as the hang, on the path this change leaves throwing. Perimeter unchanged.
