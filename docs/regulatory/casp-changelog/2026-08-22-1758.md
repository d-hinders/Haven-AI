- **#1758** — `agent_passports.revocation_status` now CONVERGES when a passport revoke mines after its confirmation wait expired, closing the residual #1742's shard recorded at raised severity. **No authority, custody or execution boundary moves and nothing new is grantable**: the change adds one read-only EAS view call (`getAttestation`) and one read of Haven's own `outbound_txs` ledger, writes only to `agent_passports`, moves no funds, grants nothing, and STRICTLY REDUCES on-chain activity — the doomed transaction is no longer broadcast at all. The defect: #1742 bounded the revoke's wait, so the transaction can mine after the caller stopped watching (the review noted the 120 s deadline is plausibly crossed during ordinary Base congestion, not only pathological failure), and nothing then re-observed it — the #1558 bump worker's `markMined` closes only the `outbound_txs` row and holds no agent id, while the only path that could set `confirmed` was a FRESH `revokeOnChain` seeing `receipt.status === 1`, which is thereafter structurally guaranteed to revert `AlreadyRevoked`. The row therefore stayed `pending` PERMANENTLY: a false stuck-revoke alarm that never cleared, accumulating one standing false positive per affected agent, plus hourly relayer gas on a transaction that could never succeed. **The convergence is a PULL, not a push, and its evidence is positive.** `reconcileRevocation` asks the chain, before it spends anything, whether the attestation is already revoked — `revocationTime != 0` read as of a FINALIZED block (falling back to ~300 blocks of burial, with the same #1745 sanity check that a node claiming `finalized` is not merely echoing the head). That fact is independent of which transaction set it, of whether Haven ever saw a receipt, and of an operator having revoked by hand, which is why it converges cases a push from the bump worker never could; it is read at a settled block because writing `confirmed` — the one state `listStuckRevocations` never revisits — from a head read that a reorg then undid would silence the alarm for a still-live, merchant-readable credential, the exact inversion of the alarm's purpose. Deliberately NOT taken: decoding the `AlreadyRevoked` revert selector as success (#1758's suggestion 1). A revert is a claim about one transaction, reading a failure as a success is the inference #1745 established this codebase should refuse, and it would still burn the gas before reinterpreting it. **The evidence pointer** is required, not decorative: migration 049 refuses `revocation_status = 'confirmed'` without a `revocation_tx_hash`, so the transaction that carried this revoke's exact calldata is looked up in `outbound_txs` (chain + submitter + calldata, `mined` — proven status-1 — preferring `broadcast`, and NEVER `failed` or `replaced`); no migration was needed and none is proposed. Where the chain agrees but no such record exists, the row deliberately stays `pending` with a reason naming the missing pointer and STILL refuses to broadcast: a fabricated hash in an audit column is worse than an honest alarm. **Fail-safe in every other direction** — an unwired, throwing, unreadable or `unknown`-answering probe falls through to exactly the pre-#1758 behaviour, so the probe can only ever remove a stuck row, never create a wrong `confirmed` one; a `live` attestation still gets its revoke submitted, so a real revocation cannot be stalled by this path. Characterization-first on the real Postgres harness (the permanent `pending`, the never-emptying due list, the false alarm, the 3600 s cap), then inverted. Mutation-proven in ten directions, including: read the head instead of the settled block → the reorg test fails; treat a zeroed (unknown-UID) struct as `live` → fails; confirm without an evidence pointer → fails; contain nothing on a throwing probe → fails; accept a `failed` or `replaced` row as evidence, or drop the mined-first ordering → fails; drift the submitter constant between writer and reader → fails; leave the seam unwired at boot → fails. One mutation initially PASSED and the finding is kept: commenting out a `setX(...)` line in `index.ts` satisfied every assertion in `anchor-seams-wired.test.ts`, because the regex matched inside the comment — a WEAK TEST, not dead code, and it had been weak for the three pre-existing anchor seams too; comments are now stripped before matching. **Not decided here, and stated rather than assumed:** how long a revoke whose attestation is genuinely still live may go unlanded before Haven declares it dead. That is the revoke-side face of #1743's open owner call ("when is a stuck attest dead"), it is not derivable from the code, and nothing in this change takes a position on it — such a row keeps retrying and keeps alarming, which is correct, because in that case the credential really is live on-chain.
