- **#1844** — `packages/frontend/src/components/AddFundsModal.tsx` stops defaulting an unresolved chain to **Base mainnet**. The two fallbacks removed (`chainConfig?.shortName ?? 'base'`, `chainConfig?.name ?? 'Base'`) were both money-facing without moving money: the name is rendered as a deposit instruction ("Send USDC to your account address on {chainName}"), and the short name becomes Coinbase Onramp's `defaultNetwork` and `addresses` map — i.e. the delivery network of a preconfigured **fiat purchase**. With no chain resolved the modal now names no network, renders no address to copy, and does not offer the onramp at all; the copy says plainly that the network cannot be confirmed. **No authority, custody or execution boundary moves and nothing new is grantable.** Haven holds no key on this surface, signs nothing, and submits nothing: the diff changes what a dialog *tells a human* and whether it *offers an outbound link to a third-party onramp*, never what any account may spend or who may authorise it. No route, request, delegation, allowance, caveat, approval or policy evaluation is touched, and the resolved path — the only one reachable in the product today — renders byte-identically to before. The change is strictly **subtractive on the risk side**: it removes a mainnet-shaped instruction and removes an onramp offer, and it can only ever remove them, since every predicate added is a conjunction (`&& chainConfig`). Reachability is stated rather than inflated, and the audit was done before the fix: `UserSafe.chain_id` is non-nullable in the type the call chain actually consumes (`packages/frontend/src/context/AuthContext.tsx`) — cited there rather than at the generated OpenAPI surface, which carries optional `chain_id` fields for other endpoints and would be the looser claim; the sole call site (`DashboardClient.tsx:1175`) passes `selectedActionSafe?.chain_id`, `defaultSafe` falls through to `safes[0]`, and the hero renders "Add funds" only when at least one account exists — so `selectedActionSafe` is never absent while the button is clickable. **This was a latent hazard, not a live defect**, and no user was ever shown a mainnet deposit instruction for a testnet account through the shipped UI; it becomes live the moment `chain_id` turns optional on the wire, a partially loaded safe reaches the call site, or a second call site appears without a resolved chain. Mutation-proven in four directions, each verified to have actually applied before the run: restoring today's component fails the guard on `\bBase\b` appearing in the dialog; reverting **only** the onramp predicate (leaving the copy fix in place) fails it on the "Buy with card" control still being offered; forcing `chainName` to null on the resolved path fails the resolved-state test, so that half is not vacuous; and dropping the `delete safeWithoutChain.chain_id` line from the new capture scenario fails the fixture-contract test. The first run of the guard exposed a defect in the guard itself — `/Base/i` matches "Coinbase" in the onramp card's own copy — which is why the assertion is word-anchored and case-sensitive; without that, the onramp mutation would have reported green-for-the-wrong-reason. Rendered evidence exists for both states at both viewports, driven through the real dashboard with the unresolved state produced at the API boundary (a safe served without `chain_id`) rather than by editing the component. Three findings from the two review passes were applied rather than deferred, and none widens the surface. The rendered pass found that the refusal's own escape hatch was unsafe: the "Show receive address" handoff led to `ReceiveFundsModal`, which calls `getChainConfig(safe.chain_id)` unconditionally and throws on a missing chain, so the way out of "we can't confirm the network" was a crash. That CTA is now offered only when there is no address at all — its original condition — and the receive surface's own unresolved-awareness is filed as #1852. The code pass found that `chainId != null` covers only ONE of the two ways a chain fails to resolve: a present-but-unregistered id still threw. `resolveChainOrNull` now answers both shapes with the same refusal, kept local because seventeen other call sites depend on `getChainConfig` throwing. A third, from the rendered re-check, added a `Refresh page` action to the refusal state: `design-review.md` requires error copy to explain the next useful action, and the refusal offered none. It reuses `ErrorBoundary`'s existing answer for have-no-specific-fix and carries NO accompanying sentence, deliberately — a line such as "refreshing usually resolves it" would re-promise the network the copy above refuses. It authorises nothing, moves no funds, calls no route and reads no credential; `window.location.reload()` re-runs the same authenticated fetches the page already makes. All three are mutation-proven in the same discipline as the rest (restoring the dead-end CTA fails the handoff assertion; restoring the bare null check fails with `Unsupported chain: 999999`; removing the Refresh action fails on that assertion by name, and adding the over-promise sentence fails on the copy assertion), and and none adds authority: two are strictly subtractive (one removes an offer, one replaces a thrown render with a refusal) and the third adds a page reload. Perimeter unchanged.
