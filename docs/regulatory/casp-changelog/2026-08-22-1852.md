- **#1852** — `packages/frontend/src/components/ReceiveFundsModal.tsx` stops throwing on an unresolved chain and stops naming the network unhedged. The modal called `getChainConfig(safe.chain_id)` on an unconditional path (`:66`), and that function **throws** for any id outside the frontend registry — including `undefined` — so a safe arriving without a resolved `chain_id` took the whole screen down through the error boundary instead of degrading. It also stated the network as fact in four places (`:90`, `:114`, `:152`'s QR alt text, `:184`). Both are fixed the way #1844 fixed the sibling surface one screen over: `resolveChainOrNull` answers **both** shapes of unresolved — a `chain_id` that is absent, and one that is present but unregistered — with the same refusal, and with no chain resolved the modal names no network, shows no address, no copy action, no QR code, no explorer link, no supported-token list and no send checklist, saying plainly that the network cannot be confirmed. **No authority, custody or execution boundary moves and nothing new is grantable.** Haven holds no key on this surface, signs nothing and submits nothing; the diff changes what a dialog *tells a human about where to send funds*, never what any account may spend or who may authorise it. No route, request, delegation, allowance, caveat, approval or policy evaluation is touched. **Money-path by consequence rather than by file**, on the same argument as #1844 and recorded as a decision rather than an omission: nothing in the diff appears on the `ship-next` money-path file list, and nothing in it moves money — it instructs a human who will. The change is **strictly subtractive on the risk side**: every predicate added is a conjunction, so it can only ever remove a network claim, remove an address or a QR, or replace a thrown render with a refusal. The one thing it *adds* is a `Refresh page` action, which authorises nothing, moves no funds, calls no route and reads no credential — `window.location.reload()` re-runs the authenticated fetches the page already makes.

  **What still renders, and why that is the perimeter-safe choice.** The account name and its `Default` badge stay. They are true on every network, they name no network, and they offer no way to send anything; they exist so the refusal is *about* an identifiable account, which is what a person needs before they can act on it. Everything network-specific goes, and the QR is the reason the line is drawn there rather than at "hide the address". An address is chain-agnostic — the same twenty bytes on every EVM chain — and the argument for still showing it is genuine. It loses on what the screen is FOR: a receive surface is an instruction to send, and a QR is that instruction in its most one-click form. A user who scans it sends on whatever network their wallet is already on, and Haven would have named none. The two errors are not symmetric — withholding an address costs a refresh, while a transfer to the right address on the wrong network is usually unrecoverable and Haven **cannot** recover it, which is exactly the non-custody position this perimeter rests on. The explorer link would have thrown in any case: `getExplorerUrl` calls `getChainConfig` internally. **One known gap in that argument, recorded rather than fixed:** "the account name names no network" is true only because account names happen not to contain one. A user who named an account "Base Sepolia test" would see the refusal quietly reintroduce a network signal that everything else on the screen withholds. Very low likelihood and out of this issue's scope, but the argument rests on an accident and should be read that way.

  The refusal is rendered with the `ApprovalRequiredBanner` domain primitive at `tone="warning"` rather than a bespoke neutral card. That is a risk-communication decision, not a styling one: the first draft dressed "funds sent on the wrong network are usually unrecoverable" in the same neutral card as the routine "Before you send" checklist, giving a loss-of-funds warning the visual weight of a reminder. The primitive's approval-flavoured name is historical — it already ships as "Paused in Haven", "Recoverable funds in agent wallet" and "You stay in control" — so reuse follows existing practice rather than stretching it.

  **`resolveChainOrNull` moved from `AddFundsModal` into `lib/chains.ts`.** This is not the change #1844 considered and rejected. That one was making `getChainConfig` itself total, which would silently alter the ~20 call sites that treat an unknown chain as a programming error and want the loud failure; the throwing contract is untouched here. What moved is the wrapper, at the point a second surface needed the same answer — a second local copy would have drifted, and the copy in `AddFundsModal` was already the authority on a question two screens now ask. No behavioural change to `AddFundsModal`: `resolveChainOrNull` is the same function under the same name, and the modal's four gates evaluate identically.

  **Reachability — latent, not live, and stated as such.** `chain_id` is non-nullable in `UserSafe`, the type the call chain consumes (`packages/frontend/src/context/AuthContext.tsx`). `ReceiveFundsModal` has **two** call sites, and both are equally gated — stated as two rather than one because the first draft of this shard inherited #1844's "the sole call site" phrasing along with its reasoning, and that phrasing was accurate for `AddFundsModal`, which genuinely has one. A template carries its claims as well as its structure; a reachability claim has to be re-derived per component, and the review pass caught this one. The two:

  1. `DashboardClient.tsx:1169` passes `selectedActionSafe`; `defaultSafe` falls through to `safes[0]` and the hero renders its Receive action only when at least one account exists.
  2. `AccountDetailClient.tsx:664` passes `safe`, resolved at `:127` from `user?.safes?.find((s) => s.id === safeId)` and guarded by an `if (!safe) return …` not-found branch at `:248`, so the modal is unreachable without a safe.

  Both draw from the same `UserSafe[]` with its non-nullable `chain_id`, so the verdict — latent, not live — holds at each. No user has been shown a crashed receive screen, or a wrong network on one, through the shipped UI. The difference from #1844 is the failure MODE, not the likelihood: that one was confidently wrong, this one was a thrown exception. It becomes live if `chain_id` turns optional on the wire, a partially loaded safe reaches the call site, or a new call site appears without a resolved chain.

  **Mutation-proven in eight directions, each verified applied by content rather than by `git diff`** (deleting an uncommitted block returns a file to its committed state, so a `git diff --quiet` applied-check reports "not applied" for a mutation that applied — the battery therefore ran against committed code and asserted the mutated string is present). Each is recorded with the assertion that actually fired, not merely with "went red": restoring `getChainConfig` fails A1 on *both* shapes with `Unsupported chain: undefined` and `Unsupported chain: 999999`; reverting the resolver to the missing-half-only form (`chainId != null ? getChainConfig(chainId) : null`) fails A1 on the unregistered shape ONLY, which is the assertion that the second failure shape is genuinely covered; leaking the address into the refusal fails A4's `queryByText(safe_address)`; leaking a chain name into the refusal fails A3's `\bBase\b`; dropping the `Refresh page` action fails A6 by role and name; rendering the refusal instead of the resolved content fails the resolved test's address and copy-button lookups; leaking the copy-address button into the refusal fails A4's role query; and rendering the refusal *additively* alongside the resolved content fails the **paired negative** in the resolved test — the assertion that exists so the unresolved absences mean "suppressed" rather than "never built".

  **One guard defect found by the battery and fixed, in the same family as #1844's but the mirror image of it.** The network negative was first written over `dialog.textContent`, which concatenates across element boundaries with no separator: the mutation that put "Probably Base" in the refusal heading produced `…Probably BaseWe can't confirm…`, where `\bBase\b` has no boundary to match, and the mutation **survived** a green run. #1844's lesson was that a loose matcher (`/Base/i`) fires on unrelated copy ("Coinbase"); this is the same scan failing the other way, matching nothing when it should match. The assertion now joins text nodes with a space, restoring a boundary at each element edge, and additionally asserts that the fixture's account name "Based" IS present — so the string cannot be silently empty and the anchor is provably doing work. Every other assertion in the unresolved tests is role-based rather than a text scan, for the same reason.

  **A guard that could not be mutation-proven was removed rather than kept.** An early draft also gated the QR *generator* on a resolved chain. With the toggle absent from the unresolved state that branch is unreachable from the UI, so no test could turn it red — a guard no mutation can falsify reads as protection while providing none, which is the defect this repo's discipline exists to prevent. The QR's suppression rests on the assertion that its toggle is not rendered, which a mutation does falsify.

  Rendered evidence exists for both states at both viewports, captured in one run through the real dashboard with the unresolved state produced at the **API boundary** (a safe served without `chain_id`) rather than by editing the component, and the pair differs by exactly that one field — pinned by a fixture-contract test so a scenario that quietly kept `chain_id` cannot shoot the resolved screen under the unresolved filename. The resolved capture shows the address, the QR, the token list and the send checklist; the unresolved capture, same run, shows none of them. **Residual, named rather than glossed:** only the *absent*-`chain_id` shape has been captured. The present-but-unregistered shape resolves to the identical refusal by code inspection and is mutation-proven at the unit level (M2), but no one has seen it rendered — so the PNG evidence covers one of the two shapes, not both. Perimeter unchanged.
