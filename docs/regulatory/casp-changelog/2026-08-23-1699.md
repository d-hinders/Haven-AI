- **#1699** — An agent re-key rotates `agents.delegate_address` in place; an EAS attestation is immutable and `PASSPORT_SCHEMA`'s first field is `address agentEoa`, so until this change the live Agent Passport kept naming the **retired** delegate key (#1847). Re-key now revokes that attestation and issues a new one naming the new key. **No authority, custody or execution boundary moves, and nothing new is grantable.** The Agent Passport is governance metadata by construction — L0 attests issued-by-Haven, bound-to-treasury, policy-enforced-on-chain and revocable, and *nothing* in Haven consults it to decide whether a payment may proceed. Re-anchoring therefore changes what a merchant can *read about* an agent, never what the agent may spend: the spend authority is the signed delegation, which #1698 already rotated, and this diff does not touch a delegation, a caveat enforcer, a budget, a recipient pin or an expiry.

  **Money-path by the file half of the union, and stated plainly rather than argued down.** The issue is labelled *not* money-path — correctly, on the authority reading above — but the diff touches two globs in `.github/money-path-globs.json`: `packages/backend/src/infra/repositories/**` (via `agent-passports.ts`) and `packages/backend/src/routes/agent-rekey.ts`, which #1892 added to the perimeter while this change was in flight. Union, never intersection: it is classified money-path, this shard exists, and the money playbook was loaded. Worth recording that the second glob would have been *missing* a day earlier — the file-half of the union was inert for the re-key route until #1892 swept it — so this change would still have been caught by the first glob, but only by accident of which file it happened to touch. The characterization-test requirement in `money.md` §2 scopes to that section's enumerated behaviours, none of which this diff changes; the one piece of **existing** money-adjacent behaviour it does touch — `reconcileRevocation`, the agent-revocation reconciler — is covered below.

  **The riskiest thing here is a refactor, not a feature.** `retireAttestationOnChain` was extracted verbatim from `reconcileRevocation` so both retire paths share one implementation of the #1758 probe-before-spend convergence and its fail-safes. A drifted second copy of that logic fails as *a revoked agent keeps a live credential nobody revokes*, which is the exact divergence #973 exists to close — hence extraction rather than duplication. The extraction's evidence is the pre-existing revocation suite passing **unmodified**: 244 passport tests green before and after, including `revocation-convergence`, `revocation-anchor-probe` and `passport-revoke-wait-timeout`, none of which were edited by this diff.

  **The revoke-before-issue ordering is enforced in SQL, not merely intended.** `resetForReanchor` refuses unless the retired attestation is `revocation_status = 'confirmed'` **and** its `attestation_uid` matches the one the caller just retired. Clearing the uid earlier would erase the only pointer Haven holds to a credential that is still live on-chain, stranding it permanently — the passport-layer analogue of the two-live-keys failure the epic's ordering decision exists to prevent. Both refusals are asserted on the real-Postgres harness, and both were **mutation-proven**: dropping the preconditions from the UPDATE turns 9 of 26 tests red, and reducing `isStaleAnchor` to a constant `false` turns 7 red.

  **No migration, and that is a deliberate perimeter property rather than a shortcut.** The re-anchor queue is the invariant `agent_passports.agent_eoa <> agents.delegate_address` on a live agent, not a flag someone must remember to write — so a re-key that completed before this code existed, or one whose process died between the credential swap and the enqueue, is still picked up. Nothing new is written to the database schema; four new curated statements were added to `db-schema-smoke` so the queue cannot silently stop matching the schema, which is the one way an invariant queue fails invisibly.

  **`claimReanchorRevocation` is a separate gate, never a loosened one.** `claimRevocation`'s `a.status = 'revoked'` clause is a security property — it is what makes "this cannot revoke a live agent's anchor no matter who calls it" true for an unconditional fire-and-forget caller — so it was left untouched and a second gate written beside it, keyed on `a.status <> 'revoked'` plus the stale-anchor predicate. The two are mutually exclusive by construction, asserted directly: an agent revoked mid-re-anchor leaves this queue and enters the revocation queue rather than racing inside either.

  **A chain failure cannot cost an agent its standing.** `standing` derives from `agents.status` alone and is not a column of `agent_passports`; the re-anchor hook is fire-and-forget **outside** the re-key's completion transaction, so an EAS outage cannot roll back a re-key that already succeeded and leave the owner holding signatures for delegations that never activated. Asserted: with the revoker throwing, standing stays `active`, the retired uid survives, and the row is due again once the backoff expires.

  **One disclosure change, narrowed on purpose.** The merchant-facing verifier now reports `anchor: "re_anchoring"` during the window instead of `anchored`. That is strictly *less* confident, not more: saying `anchored` asserts a credential is current when the address it names can no longer spend. The receipt's internal comparison reads `agents.delegate_address`, which is **not** disclosed — the verification `SELECT` list is unchanged in what it reveals (no owner identity, no budgets, no balances, no counterparties). `standing` is unaffected and remains the answer merchants are told to use. Perimeter unchanged.
