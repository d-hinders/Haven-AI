- **#1700** — Adds `--rekey` / `--rekey-finish` to `@haven_ai/connect`, the client half of replacing an agent's signing key on the machine that runs it. **No authority, custody or execution boundary moves, and nothing new is grantable.** This connector does not call the re-key API at all and cannot: every route in `routes/agent-rekey.ts` sits behind `authMiddleware` and calls `refuseAgentCaller()`, so re-key remains authorised by the account owner through the dashboard — #1694's "an agent can never re-key itself" is enforced by the backend and *relied on* here rather than re-implemented. The change brackets that owner-authorised flow: it generates a keypair before it and writes credentials after it. Not one line of it decides whether an agent may spend, or how much, or to whom.

  **The non-custodial red line is the whole design, so it is asserted rather than asserted-about.** The new keypair is generated on the target machine (`generateDelegateKey`, ethers `Wallet.createRandom`) and the private half never leaves it: Haven receives an **address**, pasted by the owner into the dashboard. Nothing in the diff accepts, uploads or transports key material — there is no code path that could, because the connector's only outbound call on this flow is a **read** (`GET /machine-payments/agent`). Three tests pin the negative directly: the phase-one result contains the address and **not** the private key, the CLI's `--json` output carries neither, and the ordinary setup flow's overwrite guard still refuses. A design that "restores" a key to a new host is refused by construction, not merely undocumented — there is no input that accepts one.

  **Not money-path on either half of the union, and stated rather than assumed.** The issue is labelled `area:sdk` / `area:mcp` only, and the diff touches no path in `.github/money-path-globs.json`: `packages/connect/**` is not on the perimeter, and the one published-package glob that *is* — `packages/sdk/src/signer.ts` — is untouched. `scripts/ci/money-path.test.mjs` passes 8/8. This shard exists because `casp-risk-guardrails.md` declares `covers:` over the connector's credential surfaces, which is the correct reason: credential handling is a CASP question even when spend authority is not.

  **What a re-key does to the credential set, and the one guarantee that needed engineering.** The three files are rewritten **in place** at an unchanged path (owner decision, #1694 — no new directory, no tombstone, so no long-lived host is left chasing a dead path). `rewriteCredentialFiles` is the only overwrite path in the package and deliberately skips `assertDoesNotExist`; a test asserts the ordinary setup flow still refuses the same path, so the exception cannot widen into a re-run silently replacing a live agent's keys. The guarantee that mattered is **coherence under failure**: a partial rewrite must never leave the new signer key beside the old API key, or the reverse, because that pairing is worse than either generation intact — the agent would authenticate as itself and sign with a key its delegation no longer names, which is precisely the payer/signer mismatch #1690 exists to catch. All three files are written as siblings first and only then renamed, with rollback from an in-memory snapshot of the originals. **Mutation-proven**: removing the rollback turns the atomicity test red, and renaming each file as it is written (instead of all-temps-first) turns it red too — and the test injects a real `EISDIR` on the *third* rename, after the first two have already landed, so it exercises the mixed state rather than a convenient one. The residual window — a hard process kill between two renames, not an exception — is named in the code comment rather than papered over.

  **The pending key is a second copy of a private key on disk, so it is accounted for explicitly.** Between the two phases the new private half lives at `rekey-pending.json`, mode `0600`, **inside the agent's own credential directory** — the same directory, the same mode, the same machine as the live signer key it is about to replace. It crosses no boundary the live key has not already crossed, and deliberately is not in a temp directory, which is exactly the world-traversable location a private key should never occupy. It expires after 24h, a fresh `--rekey` replaces it rather than accumulating, and `--rekey-finish` deletes it **after** the rewrite lands — ordered that way on purpose, since deleting first would make a failed rewrite unrecoverable.

  **One new outbound read, and it narrows rather than widens.** `getAgentIdentity` calls the existing agent-authenticated `GET /machine-payments/agent`. Phase one uses it to refuse a legacy-rail or revoked agent the way the backend would, before the owner signs anything; phase two uses it to refuse writing unless the pasted key authenticates, belongs to this agent, **and** Haven's recorded signing address equals the address this machine generated. Every one of those is a refusal added, not a permission. No new endpoint, no schema change, no migration. Perimeter unchanged.
