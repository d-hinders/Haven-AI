- **#1712** — Domain-ownership proof for self-service catalogue ingestion (epic #1717): an HMAC-bound, expiring proof a merchant publishes at `/.well-known/haven-verify-<token>.txt` or as a `_haven-verify` DNS TXT record, plus the shared SSRF guard every outbound catalogue request now goes through. **No CASP perimeter moves.** Nothing here holds a key, signs anything, moves value, changes an allowance, grants or revokes authority, or touches a payment, a rail, a Safe, or a relayer. No money-path glob in `.github/money-path-globs.json` is matched, and the issue carries no `money-path` label — both halves of the union agree, so the classification is not a judgement call. The only capability added is a **read-only HTTPS GET** and a DNS TXT lookup.

  **The new secret is not a spend credential, and the distinction is worth stating precisely rather than waving at.** `CATALOG_OWNERSHIP_SECRET` keys the HMAC behind the proof. Whoever holds it can forge a *domain-ownership claim* — i.e. get a domain listed in the directory that nobody proved they control. They cannot thereby move a user's funds: listing is discovery metadata, and every payment out of Haven still passes the same signed delegation, caveat enforcers, budget and approval path it did before, none of which consults the catalogue for authority. The realistic harm is therefore **misdirection, not custody** — an agent could be pointed at a merchant endpoint under an attacker's control and spend *within its own budget* there. That is a real harm and the reason the secret is documented in `.env.example` with the same handling discipline as `JWT_SECRET`, but it is not a custody or authority change and does not widen the CASP perimeter. Haven remains non-custodial smart-account software throughout.

  **Fail-closed is the configured default, deliberately.** The secret is read with `?? ''` rather than `requireEnv`, so an existing deployment does not fail to boot for a feature it has not enabled — and an unset secret makes `verifyDomainOwnership` refuse **every** claim with `not_configured`, before any outbound request. There is intentionally no derived fallback: a default computed from another secret would let a deployment believe it was verifying domains while emitting proofs anyone who knew the derivation could compute. Asserted directly (`fails CLOSED when the ownership secret is unset, and makes no request`).

  **The outbound surface gets NARROWER, not wider.** Every request to a submitter-chosen host runs through `infra/http/ssrf-guard.ts`: https-only, default-port-only, no embedded credentials, no IP literals, no locally-bound names; then the hostname is resolved and **every returned address classified**, and the socket is pinned via the `lookup` hook to the address that was just cleared — closing the DNS-rebinding gap that `modules/reporting/receipt-underlag.ts` documents as a residual of its hostname-regex approach. Redirects are re-validated from the top at each hop rather than followed, so a public front door that 302s to `169.254.169.254` is refused at the hop. Total deadline, response byte cap and redirect budget are all bounded. This is what stops the ingestion queue turning Haven into a request cannon aimed at instance metadata, at the private network, or at a third party Haven would be DDoSing on a submitter's behalf.

  **Mutation-proven, because a verification that has never been shown to say no is not a verification.** Five mutations, each restored from a task-named backup and re-verified by content hash: unbinding the token from the MAC turns `refuses a proof computed from a DIFFERENT verify token` red; unbinding the hostname turns `refuses a proof computed for a DIFFERENT domain` red; forcing `isTokenExpired` to `false` turns `refuses an expired token, without making any outbound request` red; bypassing address classification turns 5 guard tests red including the metadata-redirect pivot; and skipping redirect re-validation turns 3 red. The proof-derivation test also caught a **real defect before ship**: the IPv6 dotted-tail parser mis-placed the IPv4-mapped `ffff` marker, so `::ffff:127.0.0.1` classified as *public unicast*. Fixed, and pinned by a named test.

  **What the eventual badge may claim, restated so this slice does not oversell it.** Proving domain control says *this submitter controls this domain* and nothing else. It does not attest merchant honesty, quality, solvency or settlement, and it inherits unchanged the #1669 limit the epic's trust-claim section warns against blurring: a 402 challenge shows a merchant *answers*, never that it *settles*. This slice ships no badge, no listing surface and no public copy; #1715/#1716 own that wording and remain bound by it.

  **DNS TXT trust properties, stated rather than assumed.** The TXT fallback uses the resolver the backend host is configured with, over plain DNS: no TLS, no DNSSEC validation, cacheable, and forgeable by anyone controlling resolution. The design does not require the resolver to be trustworthy. A resolver-level attacker cannot *manufacture* a passing record (it needs the HMAC key); they can *suppress* one, which fails closed; they can *replay* a genuine record, which is bound to that hostname and that submission id and so only re-proves something already true. The well-known file has strictly stronger channel authentication (TLS host authentication), which is why it is attempted first and DNS TXT is documented as the fallback.
