- **#1870** — The re-key revoke's *prepare* step now accepts an optional `signature_scheme`, resolves it through the shared `resolveSignatureScheme` core (`rails/hybrid-signer-actions.ts:75`), passes the resulting `signWith` into `createTreasuryOps`, and reports the resolved scheme back to the client. **No authority, custody or execution boundary moves, and nothing new is grantable.** What changes is *which of the account's already-enrolled signers* is told to size the UserOp — and told to the account explicitly instead of inferred. The account's on-chain validation is untouched: it accepts a signature from its own signer set and from nothing else, and `resolveSignatureScheme` validates the request against that same stored set (409 for a scheme the account cannot produce) rather than widening it. Haven still signs nothing on this path — `createTreasuryOps` builds a watch-only owner or a WebAuthn stub whose `getFn` throws (`rails/delegation-rail.ts:428-448`), so the owner's device remains the only thing that can produce the revoking signature. The delegate key, the delegations being revoked, the amounts, the recipients and the caveat stack are all untouched by this diff.

  **Money-path, and by the union rule rather than by the file list.** `routes/agent-rekey.ts` is not on the `ship-next` money-path file list, and `routes/agent-delegations.ts` — the sibling doing the identical job for ordinary budget revocation — is. That asymmetry is an artefact of the list predating #1698, not a judgement that re-key is lower stakes: this endpoint prepares the owner signature that **revokes an agent's on-chain spend authority**, which is spend authority under any reading, and the issue carries the `money-path` label besides. Classified money-path on both halves of the union. Characterization tests were written and run green **before** the behaviour was touched, per `money.md` §2: the pre-existing defaults (an EOA-owner account prepares the owner op, a pure-passkey account prepares the passkey op, an unknown owner config is a 409, a vendor error is a redacted 502) are pinned as assertions and are unchanged by the diff.

  **The refusal ordering is the regulatory-relevant property, not the new field.** #1868 records that a re-key abandoned *after* the revoke wedges the agent's in-flight slot permanently — nothing expires it, abandoning does not restore authority, and recovery is a manual owner re-grant. A change that adds new ways to fail therefore has to say *where* they fail. Every refusal this diff introduces fires in the **prepare** handler: it writes no row, advances no stage, and leaves the re-key at `preflight`, so a rejected scheme is a retryable dead end rather than a stranded agent. That is asserted directly (`agent-rekey-signing.test.ts`, "#1868 boundary — a refused scheme leaves the re-key retryable at preflight"), not merely argued. The diff adds nothing to the post-revoke path.

  **Mutation-proven, because a green test is not evidence a guard works.** Four mutations were applied to the merged behaviour and each was verified by content before and after restoration. Dropping `signWith` entirely (the pre-fix state) turns the load-bearing assertion red with `expected '120000n' not to be '120000n'` — both schemes collapse onto the owner-path gas estimate, which is precisely the defect: a several-hundred-byte WebAuthn signature validated against a `verificationGasLimit` estimated for 65 bytes. Pinning `signWith: 'owner'` additionally breaks the pure-passkey characterization (`expected '120000n' to be '480000n'`). Deleting the pre-revoke 409 turns all four refusal assertions red at 200-instead-of-409. Mislabelling the WebAuthn branch as `eip712_userop` is caught twice — by the echoed-scheme assertion and by OpenAPI conformance (`must have required property 'signing_payload'`). Recorded because of what the first mutation *also* showed: under the pre-fix code the assertion that the field merely echoes back still **passes**, as does spec conformance, so a test built around the field rather than the gas estimate could not have failed on this defect at all.

  **Backward compatibility is a perimeter question here, so it is asserted rather than asserted-about.** An existing client that sends no `signature_scheme` gets the identical resolution it got before (`resolveSignatureScheme` returns the owner scheme when an owner exists, else the passkey scheme), so no deployed caller's signing path changes and no in-flight re-key becomes unsignable on deploy. Perimeter unchanged.
