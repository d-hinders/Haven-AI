- **#1878** — The connector now reports the **MCP server name** it wired an agent as (`haven` for the unnamed pair, `haven-<slug>` for a `--name`d one); the backend stores it on `agents.mcp_server_name` (migration 067, nullable) and the agents list renders it beside the display name. **No authority, custody or execution boundary moves, and nothing new is grantable.** No spend path, allowance, delegation, caveat, signing scheme or authorization check is touched by this diff; no key, hash or token is added to any payload. What changes is that a user can tell which of several agents in one MCP harness is which.

  **The value is self-reported and is a LABEL, never identity.** It arrives from the client at registration, so it is exactly as trustworthy as the client — which is why nothing may key off it. There is deliberately no UNIQUE constraint (two machines can legitimately wire the same name, and a uniqueness error would fail a registration over a caption), no lookup by it, and no authorization decision that reads it. `agents.id` and the API key remain the only identity. This is stated in the migration comment rather than only here, because the failure mode is a later reader mistaking a stable-looking string for a handle.

  **An unrecognized value degrades to NULL rather than refusing.** `normalizeMcpServerName` accepts `haven` and `haven-<slug>` shapes under 64 chars and returns NULL for everything else — wrong type, empty, oversized, uppercase, control characters, markup, traversal. The direction is deliberate: throwing here would fail a whole registration — key already minted, config already written — over a display string, which is strictly worse than the missing caption NULL already renders honestly. The check is display safety, not the naming contract; that contract lives in `packages/connect/src/server-names.ts` and cannot be imported by the backend (connect is published to npm, the backend is not), so re-implementing it would be a second copy that drifts while buying nothing.

  **Money-path by the file half of the union, and only that half.** The issue is labeled `area:backend`/`area:mcp`/`area:frontend` and its own Money-path box is ticked **No** — correctly, on the merits: this is display and identification. It is nonetheless classified money-path because the diff adds `packages/backend/src/db/migrations/067_agents_mcp_server_name.ts`, and `db/migrations/` is on the perimeter in `.github/money-path-globs.json`. That is the union rule working as designed rather than an over-classification: the perimeter catches schema changes whatever their subject, because a migration is irreversible in a way a route handler is not. `money.md` §2's characterization-first rule is satisfied vacuously — no existing money-path behaviour changes, the column is additive and nullable — but the schema change still routes through `CODEOWNERS` for independent approval, and **auto-merge is deliberately not armed on this PR** for that reason.

  **Nullable is load-bearing, not a soft default.** Every agent that exists today has no recorded name and never will, and so does every agent registered by a connector older than this change. Backfilling a guess would be worse than the gap, and the specific guess available — "assume the bare `haven` pair" — is wrong for exactly the agents wired with `--name`, which shipped in #1696 ahead of this. That is why the column stores the resolved NAME rather than the slug: it lets `haven` (reported bare pair) and NULL (never reported) be different facts in one column, with no sentinel and no second boolean to drift. The UI renders NULL as *not recorded* and is test-pinned never to render it as `haven`, and the empty-state copy is separately pinned not to read as a fault — the overwhelming majority of agents are in this state and every one of them works.

  **Mutation-proven at the two places the design could silently collapse.** Making the UI fall back to `haven` when nothing was reported (the issue's original proposal) turns two assertions red. Making the connector omit the field for the bare pair — the change that would re-merge "reported bare" with "never reported" — turns one red. Sending the raw slug instead of the resolved name turns two red. Recorded because all three are the kind of simplification a later reader would make while believing it a tidy-up: each looks like removing a special case, and each destroys the distinction the column exists to hold. Perimeter unchanged.
