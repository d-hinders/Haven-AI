- **#1890** — The dashboard half of the re-key signing-scheme fix. `packages/frontend/src/hooks/useAgentRekey.ts` now sends `signature_scheme` on the revoke prepare (derived from `pickSigningPath`, the same device decision the budget hook makes), branches on the scheme the **server resolved** rather than on local state, imports the generated `ApiSchema<'AgentRekeyRevokePrepare'>` union in place of a hand-rolled local type, and drops the `passkey_unsupported` refusal that #1881 shipped. **No authority, custody or execution boundary moves, and nothing new is grantable.** Nothing about what the account will accept changes: the Hybrid account validates a signature from its own enrolled signer set and from nothing else, on-chain, exactly as before. What changes is *which already-enrolled signer this device offers to use* — and it is now told to the server explicitly instead of the client refusing to ask. Haven still signs nothing on this path: both ceremonies run in the owner's browser (`walletClient.signTypedData` for the EOA branch, the kit's WebAuthn `signUserOperation` / `signDelegation` for the passkey branch), and the private key never leaves the device.

  **This closes a refusal, it does not open a permission.** The population unblocked here — passkey-owned accounts, and multi-signer accounts whose reachable signer on this device is a passkey — was always entitled to re-key its own agent; the *client* refused because, before PR #1891, the backend prepared the revoke UserOperation without being told which signer would sign it, so a WebAuthn signature of several hundred bytes would have been validated against a `verificationGasLimit` estimated for 65. #1881 refused up front rather than guess, precisely because guessing would have put the failure **after** the revoke. #1891 removed that condition. The perimeter is unchanged in both directions: a scheme the account cannot produce is still refused, now by the server's `resolveSignatureScheme` with a 409 raised in the *prepare* handler.

  **Money-path, and by the label rather than the file list.** The issue carries `money-path`, and this is the client that decides how an owner signs the revocation of an agent's on-chain budget. The file half of the union is silently inert for this route in both directions: `routes/agent-rekey.ts` is absent from the `ship-next` list (filed as #1892), and the list contains no frontend paths at all, so a client that chooses a signing scheme for a spend-authority revocation can never be caught by it. Classified money-path on the label. Per `money.md` §2, the existing behaviour changed here — the EOA path #1881 shipped — is pinned by a characterization test written against it (`'leaves the EOA owner path exactly as it was'`: asserts `eip712_userop` is sent, that neither passkey ceremony is invoked, and that `signTypedData` fires exactly twice — the revoke op and one delegation).

  **The refusal ordering is again the regulatory-relevant property.** #1868 records that a re-key abandoned *after* the revoke wedges the agent's one in-flight slot permanently: nothing expires it, abandoning cannot un-revoke an on-chain transaction, and recovery is a manual owner re-grant. So the question a change like this must answer is not "does it work" but "**where can it fail**". Every new failure path introduced here lands **before** `/revoke/submit`: the scheme is sent on the prepare, a scheme the account cannot produce is the server's pre-revoke 409, and a divergence between the device's assumption and the server's resolution refuses at the signing step with nothing submitted.

  That answer required going **beyond the issue's own scope list**. `complete()` runs past the revoke, and it signed replacement delegations through an EOA-only path. Removing the passkey gate at the revoke while leaving that path untouched would have carried a passkey owner over the point of no return and then thrown "connect your account owner wallet" on the far side — a failure *introduced by this change*, sitting exactly where #1868 makes it unrecoverable. `signDelegationPayload` adds the passkey branch so that no scheme this hook will start is one it cannot finish. This is asserted, not argued: the end-to-end passkey run (`'signs the replacement delegations with the passkey too, not just the revoke'`) drives revoke → issue → complete and fails without it.

  **Mutation-proven, because a passing test is not evidence a guard works.** Six mutations, each applied, verified by content, and restored to a byte-identical file. Restoring the `passkey_unsupported` gate fails five tests on `expected <h3 …></h3> to be null` — the refusal banner reappearing. Hardcoding `signature_scheme: 'eip712_userop'` fails two on `expected { signature_scheme: 'eip712_userop' } to deeply equal { signature_scheme: 'webauthn_userop' }`. Reverting `complete` to the EOA-only signer fails two on `Unable to find an element with the text: /signing key replaced/i` — the passkey owner is stranded past the revoke, which is the defect this branch exists to prevent, demonstrated rather than asserted. Branching on local `signingPath` instead of the returned discriminant fails exactly one test, the only one where the two disagree. The remaining two are type-level and are the point of importing the schema: reaching for `prep.signing_payload` without narrowing fails `tsc` with *"Property 'signing_payload' does not exist on type '{ signature_scheme: \"webauthn_userop\"; user_op_hash: string; … }'"*, while the **same unnarrowed access under the old hand-rolled interface compiles clean** — the false compile-time confidence, in the direction of the irreversible step, that made removing the gate and replacing the type one indivisible change.
