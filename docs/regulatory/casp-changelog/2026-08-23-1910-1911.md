- **#1910 / #1911** — Two changes to `packages/connect/src/doctor.ts`, the client-side diagnostic. **No authority, custody or execution boundary moves; nothing new is grantable, revocable or spendable.** Neither issue is money-path on either half of the union: both carry `area:sdk` / `area:mcp` only, and the diff touches no path in `.github/money-path-globs.json` — `packages/connect/**` is not on the perimeter and `packages/sdk/src/signer.ts` is untouched. This shard exists because `casp-risk-guardrails.md` declares `covers:` over the connector's credential surfaces, which is the right reason: credential *handling* is a CASP question even when spend authority is not.

  **#1910 — `--repair` wrote the wrong MCP pair, and the harm was to a bystander.** `runRepair` called `writeRuntimeConfig` with no `serverName`, so `serverNamesFor(undefined)` handed it the bare `haven` / `haven-signer` names. Repairing a **named** agent (#1696) therefore did two things at once: it left that agent's real entries stale, and — the bad half — it overwrote a co-wired *bare* agent's entries with the named agent's API key and signer wrapper path. A repair tool breaking a second, working agent is the worst available outcome for the tool people reach for when something is already broken. The fix reads the slug from the directory's own `signer-runtime.json` sidecar, where #1696 already records it, and passes it to **both** writers — `writeRuntimeConfig` and `prepareSignerRuntime`, the latter because that call rewrites the sidecar and would otherwise erase the very slug that identifies the pair, re-arming the same defect for every later run. No credential file is read differently and none is written: `--repair` still writes only runtime config, wrapper and sidecar, from STORED credentials, with no setup token. **Mutation-proven, twice**: dropping `serverName` from the config write turns the byte-identical bare-pair assertion red (`expect(codexTable(after, 'haven')).toBe(bareHostedBefore)`), and dropping it from the signer-runtime call turns the sidecar assertion red (`expect(sidecar.server_name).toBe('research')` → `undefined`). The clobbering half has its own assertion rather than being implied by the first.

  **#1911 — an abandoned re-key held private-key material that no surface named.** #1700 parks a freshly generated private key at `rekey-pending.json`, mode `0600`, inside the agent's own credential directory between the two re-key phases. That placement is deliberate and unchanged here: same directory, same mode, same machine as the live signer key it is about to replace, crossing no boundary that key has not already crossed. What was missing is observability — the one surface whose job is "tell me what state this machine's Haven wiring is in" did not read the file, so a re-key started and never finished left key material on disk with nothing pointing at it, and a scrolled-away terminal left the owner with no way to re-read the address except by running `--rekey` again and discarding the parked keypair.

  **The diagnostic reports the fact, never the material, and that is enforced structurally rather than by discipline.** The new `inspectRekeyPending` accessor in `storage.ts` returns a type with **no private-key field at all** — state, path, agent id, public address, started/expires timestamps — so no output path can leak the key by forgetting to strip it. `--doctor` reports existence, age, public address and path in both the human output and `--json`'s per-agent `agents[]` shape; an expired pending re-key is its own actionable failure rather than a generic warning; an unparseable one is still reported, because the bytes were a key. Neither `--doctor` nor `--repair` deletes the file: an expired TTL is a refusal to *use* the parked key, not a licence to destroy key material an owner may still be mid-flow on, and a test asserts `--repair` leaves it intact. **Mutation-proven**: making the accessor return the private half turns the leak assertion red (`expect(serialized).not.toContain(SYNTHETIC_PENDING_KEY)`), and that test also asserts the public address IS present, so the negative cannot pass by reading nothing. The fixture key is a synthetic throwaway constant, labelled as such in the test, never used to sign anything.

  **What the diagnostic can and cannot establish about the re-key's backend stage — stated rather than blurred.** It **can** prove the backend re-key completed: `agents.delegate_address` is swapped at the `complete` stage, so a hosted identity already reporting the address this machine generated proves the whole owner-signed sequence ran, nothing is wedged, and `--rekey-finish` closes the local half. It **cannot** distinguish, within a re-key that did *not* complete, an abandonment before the on-chain revoke from one after it. `rekey-pending.json` is written before the owner opens the dashboard and never touched again; and the connector's identity probe **reads two fields** — `id` and `delegate_address` — from `GET /machine-payments/agent`, an endpoint whose response **returns eight**: `id`, `name`, `status`, `safe_address`, `delegate_address`, `delegate_account_address`, `chain_id`, `execution_rail`. Stating both separately because the distinction is auditable and the two are not interchangeable: the probe's narrowness is a client choice, whereas the claim this argument rests on is a property of the **endpoint** — **none of those eight fields is a re-key stage**. Widening the probe to read all eight would still not distinguish the two abandonments, because the field does not exist there to read. The two cases have very different costs: before the revoke, closing it is free; after it, [#1868](https://github.com/d-hinders/Haven-AI/issues/1868)'s wedge applies — old delegations revoked, no new ones issued, nothing expires the in-flight row, recovery is a manual owner re-grant. The check therefore names the wedge and points at the agent page rather than implying the reassuring half, and a test pins that the wedge language appears in the ambiguous case and is **absent** from the proven-complete one.

  **Outbound surface unchanged.** No new endpoint, no new call, no schema change, no migration. #1911 reuses the hosted-identity read `--doctor` already performs for its `identity_match` check; the pending-re-key comparison consumes that result rather than issuing a second probe, and a superseded directory is not probed at all — it reports file facts only.
