- **#1915** — One change to the client-side diagnostic in `packages/connect/src/doctor.ts` (plus its render in `cli.ts`): the directory scan that builds `--doctor`'s inventory now treats `rekey-pending.json` as a third discovery tell alongside `identity.json` and `TOMBSTONE.json`. **No authority, custody or execution boundary moves; nothing new is grantable, revocable or spendable.** Not money-path on either half of the union: the issue carries `area:sdk` / `area:mcp` only, and the diff touches no path in `.github/money-path-globs.json` — `packages/connect/**` is not on the perimeter and `packages/sdk/src/signer.ts` is untouched. No route, schema, migration, tool schema or signing scheme is involved. This shard exists because `casp-risk-guardrails.md` declares `covers:` over the connector's credential surfaces, which is the right reason: where private-key material can sit unreported is a credential-handling question even when spend authority is not in play.

  **The gap.** `discoverCredentialDirectory` enumerated a directory only when it held `identity.json` (a candidate) or `TOMBSTONE.json` (retired). A directory holding **only** `rekey-pending.json` matched neither, so it produced no `agents[]` entry, `inspectRekeyPending` was never called on it, and the live private key inside it — mode `0600`, parked by #1700 between `--rekey` and `--rekey-finish` — was invisible in the human output and in `--json` alike. #1911 shipped a diagnostic precisely so that abandoned key material gets reported, and stated the guarantee as covering the directories nothing else looks at, `superseded` and `orphaned` included. This was the one directory shape that framing did not reach. A hazard the tool exists to report, in the one place the tool could not look, is a hole in the stated guarantee rather than a missing convenience — which is why it is fixed rather than documented away.

  **Reachability is narrow, and stated rather than implied.** No shipped flow produces this shape. `writeRekeyPending` writes into an **existing** agent's credential directory, `startRekey` reads stored credentials before it parks anything, and tombstoning does not delete the pending file — so `identity.json` is present throughout. Reaching the shape requires an out-of-band deletion of `identity.json` while the pending file survives: a partially deleted directory, a hand-copied file, a restore that recovered one file, or a future flow that parks a key before writing credentials. The change is a guard against a state the code cannot currently produce, taken because of what the file contains rather than how often it occurs.

  **What did NOT change, which is the substance of the perimeter claim.** The private half still has **no slot** in `inspectRekeyPending`'s return type — a caller cannot leak it by forgetting to strip it, because it never holds it — and this change adds no field to that shape. The report carries the same facts as before: that a pending re-key exists, its state, when it started, when it expires, its **public** address and its path. `redactSecrets` still sits on top as the belt. `--doctor` remains read-only: it writes nothing, revokes nothing, deletes nothing, and this change adds no write, no network call and no deletion path. Dropping key material stays the owner's call (#1911 AC), and an expired TTL is still a refusal to *use* the parked key rather than a licence to destroy it.

  **The exit code moves no further than #1911 already moved it.** An expired or unreadable parked key outside the reported agent already failed `--doctor` through the flat `rekey_pending_elsewhere` check, on the precedent of `superseded_agents` — this repo already treats credential hazards in a directory you are not using as exit-code-worthy. Widening the enumeration lets that existing check see one more class of directory; it introduces no new check, no new severity, and no new failing state. An open pending re-key elsewhere stays informational exactly as before. Deliberately so: #1911 moved the exit-code surface once already (an expired parked key now fails where the doctor previously exited zero), and a second move for a strictly narrower case would cost automation consumers more than the case is worth.

  **Classification.** Such a directory is reported as `agents[]` `classification: "parked"`, a fifth value beside `wired` / `superseded` / `retired` / `orphaned`. It is not folded into `orphaned` because the two carry different instructions to a reader: `orphaned` means a credential set that will not authenticate ("re-run setup"), while `parked` means there is no agent in this directory at all and a private key is still in it ("take the agent id to the Haven agent page, then decide"). The entry is named by the agent id recorded **in the parked file** when no identity or tombstone supplies one, so the report can point the owner at a specific agent page rather than printing `unknown`. A `TOMBSTONE.json` still outranks the new tell: a retired directory that also holds a parked key stays `retired`.

  **Mutation-proven in both directions.** With the enumeration reverted to the two-tell form, the `#1915` block fails on the assertions that carry each half — `expect(entry?.classification).toBe('parked')` (the directory is not in `agents[]` at all), `expect(serialized).toContain(PARKED_ADDRESS)` (the parked address reaches no output), and `expect(check?.ok).toBe(false)` on `rekey_pending_elsewhere` (no check is emitted, so `ok` is `undefined`). In the other direction, a directory holding none of the three tells is still not inventoried, asserted in the same test as a positive hit so the negative is evidence rather than an empty scan; the four existing classifications are pinned unchanged; and a machine with no parked directory produces the same seven check ids in the same order. Fixture key material is a synthetic throwaway constant, labelled as such in the test, never used to sign anything, and asserted absent from the serialized report.
