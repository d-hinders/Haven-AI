- **#1984** — Slice 1 of the Safe-rail retirement (epic #1440) closes the **inflow**: no new Safe account can be created or imported. Four entry points could mint or attach one and all four now answer HTTP 410 — `POST /safe/deploy`, `POST /user/safes/deploy`, `POST /user/safes` (import) and `PUT /user/safe` (the legacy single-Safe link, which wrote `user_safes` through `linkDefaultUserSafe` and emitted the `safe_imported` funnel event). Only the first three were in the issue's scope; the fourth was found by tracing every writer of `user_safes` rather than every route named in the ticket, and no shipped client calls it, which is exactly what would have made it the hole left open. The refusal is a route `preHandler` (`middleware/safe-inflow-retired.ts`), so it precedes the handler entirely: no `pool.connect`, no query, no relayer touch, no funnel event. 410 rather than 404 follows the #834 session-rail and #1328 mpp_demo precedent — a permanently-gone flow must not read as a transient routing error that invites retries. Frontend: onboarding provisions Hybrid unconditionally (`NEXT_PUBLIC_DELEGATION_ONBOARDING` and the frontend `DELEGATION_ONBOARDING_CHAIN_IDS` set are both removed — a flag whose "off" branch now hits a 410 is not a switch), and the Accounts page's `AddSafeModal` and its trigger are gone, that modal having been the signed-in app's only Safe deploy/import surface.

  **The perimeter NARROWS; nothing is added.** This diff creates no authority, no custody relationship, no new route and no new signing scheme. It removes the ability to bring a new externally-owned contract account under Haven's operational surface, and it removes a relayer-gas surface that had no per-caller ownership check at all — `POST /user/safes/deploy` deployed a Safe for any `owner_address` the caller named, bounded only by a global rate limit. Haven's non-custody posture is unchanged in kind and strictly reduced in extent: the retiring rail is the one where Haven's relayer held an AllowanceModule grant, and the surviving rail is the delegation rail whose equivalents are already documented in `docs/security/delegation-rail-security-model.md`. **No funds move, and nothing in this diff can move funds** — the on-chain wind-down of the relayer-owned Safe and the revocation of the two live allowances is a separate, operator-run step (#1985), deliberately not automated.

  **What is deliberately still open, so this is not read as more than it is.** An existing `allowance_module` account can still pay. Stopping that is #1986's 410 on `/payments` and x402, sequenced immediately after this slice by owner decision; until it lands, this change is an inflow closure only. That is verified rather than assumed: the `/payments`, x402 and machine-payments modules are untouched by this diff, and the read/manage paths of the very same routers — `GET /user/safes`, rename, re-default, unlink, approvers, balances, history — are pinned green in `safe-inflow-retired.test.ts` under the same run that pins the refusals. Data is untouched: `user_safes` rows and the `account_type` / `execution_rail` columns stay (Hybrid lives in the same table; the rail seam stays for reversibility), and there is **no migration in this PR**.

  **Mutation-proven, eight mutations, so the refusals are measurements rather than claims.** Removing the guard from each of the four routes independently turns 3–4 named assertions red and no others (`/safe/deploy` 3, `/user/safes` import 4, `/user/safes/deploy` 4, `PUT /user/safe` 4). Changing the shared producer's status from 410 to 404 turns 8 red across all four routes. Making the `preHandler` run but not reply — the shadowing case, where a guard exists and does nothing — turns 12 red, while the four 401 cases and the three "existing account still works" cases stay green, which is the positive control: those assertions measure something other than the guard. On the frontend, restoring the old flag fork turns 3 of the 4 flag cases red (the `=1` case correctly stays green, because with the flag on the restored fork still takes Hybrid), and re-adding an "Add account" button turns both accounts-page cases red. **One mutation PASSED and was diagnosed rather than waved through:** the first version of the onboarding assertion looked for `getByRole('button', { name: /passkey/i })`, and the restored Safe fork satisfied it — the retired path's real component renders a `/passkey/i` button too. The assertion now names the branch by test id. A guard against a fork that cannot tell the branches apart is not a guard. Perimeter narrowed; no new authority, custody or execution boundary.
