- **#1986** — Slice 3 of the Safe-rail retirement (epic #1440) closes the **spend**. #1984 shut the inflow; this shuts the outflow. An account whose `execution_rail` is not `'delegation'` and not `'session_key'` — i.e. `'allowance_module'`, an unrecognised value, or the LEFT-JOIN `null` from `FIND_EXECUTION_RAIL_FOR_AGENT_SQL` — now gets **HTTP 410, fail-closed, nothing written** from every agent-payment entry point: `POST /payments`, `POST /payments/:id/sign`, `POST /x402/authorize`, `POST /x402` and `POST /machine-payments/send`. The owner-facing half closes too: `POST /approvals/:id/approve` and `POST /approvals/:id/proposed` answer 410 unconditionally, because every `approval_requests` row is a legacy-rail artifact — the delegation rail has no approval queue at all, and all three inserts (`insertPaymentApproval`, `insertSendApproval`, `insertMachineApproval`) sit on legacy paths that now refuse upstream. The refusal is produced in exactly one place, `allowanceModuleRailRetired()` in `rails/execution-rail.ts`, the #834/#993 one-gate pattern applied to the rail that actually held funds; 410 rather than 403 or 404 for the same reason as #834 and #1328, so a permanently-gone flow does not read as a policy failure a caller can retry out of.

  **The closure is defined by what can EXECUTE a spend, not by what the ticket named.** The issue named `POST /payments` and "x402 machine-payment paths". Enumerating executors found six entry points, and the two a scope read would have missed are the ones that matter most. `POST /payments/:id/sign` is the **only caller of `executeAllowanceTransfer`** in the entire backend — closing only the create path would have left every intent already sitting in `pending_signature` fully executable, which is the same class of hole #1984 found by enumerating writers of `user_safes` instead of callers of its routes. And `POST /machine-payments/send` never executes anything, but it WRITES an intent (or an over-allowance approval row) and hands back signing instructions; leaving it open would have satisfied "410 on the executor" while still manufacturing rows for a payment that can never complete. The same reasoning shaped the seam itself: `resolveExecutionRail` no longer has an `allowance_module` answer to give, and the guard is written as "not delegation and not session" rather than as a literal `=== 'allowance_module'` test, because the column's `null` case reaches the identical AllowanceModule executor and a string comparison would have left it open.

  **The perimeter NARROWS and nothing is added.** No new authority, no new custody relationship, no new route, no new signing scheme, no migration, no data dropped. What is removed is Haven's ability to construct or relay an AllowanceModule spend at all: the `Safe → delegate EOA` funding transfer of the legacy x402 two-leg no longer executes, so the transient hot-delegate balance that the security model has always flagged as this rail's residual risk cannot be created by any new payment. The relayer's `allowance_transfer` spend category becomes unreachable from the agent API. **No funds move, and nothing in this diff can move funds** — the on-chain wind-down of the relayer-owned Safe and the revocation of the two live allowances remains #1985, an operator-run step, deliberately not automated.

  **What deliberately stays OPEN, each for a stated reason, so this is not read as more than it is.** (1) Every READ: `GET /user/safes`, rename, re-default, unlink, approvers, balances, transaction history, `GET /payments`, and `GET /machine-payments/allowances`. That last one is the only judgement call in the diff and it is recorded rather than buried — it REPORTS spend authority instead of exercising any, and the epic's boundary is "accounts and history stay readable", so turning a state read into a refusal would be a read regression for exactly the population being retired. The accepted consequence is that a legacy agent can read a live remaining allowance and then be refused when it tries to spend it: misleading, not unsafe, because fail-closed happens at the spend. (2) `POST /safe/exec` — owner-signed Safe execution, relayed for gas only. It is owner authority rather than the retired rail's agent authority, and passkey-Safe approver management (#1229, the only recovery this rail has) rides on it; closing it would remove a user's ability to add a backup owner to an account they still control. (3) `POST /approvals/:id/reject` and `POST /approvals/:id/executed` — the queue must remain clearable, and `/executed` is post-hoc bookkeeping of a transaction the owner already signed and broadcast, which Haven cannot prevent and should not lose the record of. (4) `POST /machine-payments/sweep/prepare` and `/sweep/submit` — sweep moves stranded delegate balances BACK to the user's Safe. Closing funds-recovery while closing spending would strand exactly the money this retirement exists to make safe, and the machinery is shared with the live #946 EIP-3009 bridge on the delegation rail.

  **Mutation-proven, so the refusals are measurements rather than claims** — see the PR body for the per-mutation table. Each mutation broke production code, ran the named suites, and was restored from a task-named backup and re-verified by content. The positive control is mandatory and green in the same run: a delegation-rail account still creates a signable intent and still replays one by rebuilding the stored UserOperation, and a legacy account still reads its own history and allowances. Without it every assertion in `routes/__tests__/allowance-rail-retired.test.ts` would be satisfied by deleting the payment code, which is the failure mode #1984 caught in its own onboarding assertion. Both tombstones are pinned as DISTINCT: a `session_key` account still receives #834's own message, and an `mpp_demo` intent still receives #1328's, because the Safe-rail predicate also matches `execution_rail = null` and would otherwise swallow the narrower, more informative rule — the gate is ordered after it deliberately.

  **One regulatory consequence is reported rather than absorbed, and it is the most important line in this shard.** The three contract suites that turn Red Lines #3 and #4 into executable proofs (`non-custody-authz`, `non-custody-onchain-gate`, `non-custody-relay`) were written entirely against the legacy rail, and a rail that can no longer spend cannot demonstrate "only a valid delegate signature releases a transfer". Converting them to assert 410 would have turned a regulatory proof into a guard that can only say no — it would pass just as happily if the payment code were deleted. They are therefore re-based onto the delegation rail wherever the red line is still reachable there, and any proof that could NOT be honestly re-based is named explicitly in the PR body and filed as its own issue wired into the CASP rewrite (#1991), rather than being quietly replaced by a refusal assertion. Perimeter narrowed; no new authority, custody or execution boundary.
