- **#1988** — Slice 5 of the Safe-rail retirement (epic #1440) deletes the **creation** machinery. #1984 made all four Safe inflows answer 410 with a route `preHandler`, deliberately leaving the handler bodies verbatim; this slice removes them, together with `modules/accounts/safe-deployer.ts` (`relaySafeDeploy`), the Safe-proxy half of `infra/chain/safe-proxy-deployer.ts` (`encodeSafeSetupCalldata`, `predictSafeProxyAddress`, `extractSafeAddressFromReceipt`, `getProxyFactoryContract`), `modules/accounts/safe-owner-tx.ts`, the five approver routes on `routes/user-safes.ts`, and the repository readers and writers whose only callers those were. `packages/backend/src/modules/accounts/safe-deployer.ts` therefore leaves this doc's `covers:` list — a `covers:` glob that matches a file which no longer exists is a control surface over an empty set, which reads as coverage and is not.

  **The perimeter NARROWS and nothing is added.** No new authority, no new custody relationship, no new route, no new signing scheme, no migration, no table dropped, no data removed. Haven can no longer deploy a Safe proxy, relay a sponsored Safe deployment, register an imported Safe, or construct an owner-change transaction. Two of those were relayer-gas surfaces: `POST /user/safes/deploy` had **no per-caller ownership check at all** — it deployed a Safe for whatever `owner_address` a caller named, bounded only by a global rate limit — and it is now gone rather than guarded. The `safe_exec` and passkey-signer-deploy relayer spend categories remain, because `POST /safe/exec` remains (below); the Safe-deploy spend category becomes unreachable.

  **What stays OPEN, and why it is the non-custody answer rather than an exception.** `POST /safe/exec` is untouched. It is owner-signed Safe execution relayed for gas only: the Safe verifies the owner's signature on-chain, Haven contributes gas and nothing else, and it is how the holder of a passkey-owned Safe still moves funds out of an account they control. Closing it would not narrow Haven's authority — Haven has none there — it would remove a user's access to their own funds, which is the inverse of what this retirement is for. `modules/accounts/safe-details.ts` (`getSafeDetails`, a `getOwners`/`getThreshold`/`nonce` read) and `ensurePasskeySignerDeployed` stay for the same reason: both are on that path. Sweep, the delegate-balance monitor and the #946 EIP-3009 bridge share none of the deleted code and are untouched, verified by enumerating importers rather than by assertion.

  **The one consequence worth stating plainly, because it is a reduction in what a user can do.** The approver surface was Haven's only way to add a backup owner to a legacy Safe — the preventive half of the #1229 passkey-Safe recovery story, since a passkey Safe is deployed single-owner, threshold 1. Deleting it means Haven no longer offers that. It does **not** leave any account unreachable: every one of the 15 Safes in the epic's on-chain census is owned by an external EOA (13 distinct ones) or, in exactly one case, by the prod relayer that #1985 winds down — and an EOA owner adds or removes owners directly through Safe's own interfaces with their own key, which Haven's non-custody rule requires to be true regardless of what Haven's UI offers. There is no passkey-owned Safe in the census. For a hypothetical one, `POST /safe/exec` still relays any owner-signed Safe transaction, and a passkey already enrolled as an on-chain owner still authorises there against the live owner list. The claim being made is "Haven stops offering owner management", not "an owner loses control of their Safe".

  **Three closed defects are buried by this deletion and one is NOT, which is recorded rather than assumed.** #1753 (`POST /safe/deploy`'s bare `tx.wait()` inside an open Postgres transaction) is buried — the handler is gone. The `relaySafeDeploy` half of #1755 is buried. But #1754 — `POST /safe/exec`'s bare `tx.wait()`, whose timeout is reported to the user as `502 'Safe execution reverted on-chain'` — is **live**, because the route it lives on deliberately stays open; and so is the `ensurePasskeySignerDeployed` half of #1755, reached from that same route. Both were closed as not-planned against this retirement. They should not have been, and the PR says so. A money-path route that tells a user their transaction reverted when it may still confirm is a defect that outlives the rail it was found on.
