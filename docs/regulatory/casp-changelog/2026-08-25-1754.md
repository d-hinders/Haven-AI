- **#1754 (with the surviving half of #1755)** — `POST /safe/exec` awaited a bare `tx.wait()`, and so did `ensurePasskeySignerDeployed` on the same path. Verified against ethers 6.16.0 rather than assumed: `TransactionResponse.wait(_confirms, _timeout)` computes `timeout = (_timeout == null) ? 0 : _timeout` and arms the rejecting timer only `if (timeout > 0)`, so a bare wait **cannot** produce a `TIMEOUT` — it simply never returns. The timeout case did not exist to be mis-mapped; whatever error eventually surfaced fell into the handler's blanket outer catch and was answered as `502 "Safe execution reverted on-chain"`. Both waits are now bounded at 120 s (`SAFE_EXEC_CONFIRM_TIMEOUT_MS`, `PASSKEY_SIGNER_DEPLOY_CONFIRM_TIMEOUT_MS`), each bracketed under the bump worker's `STALE_BROADCAST_SECONDS` (180 s) and matched to the frontend's own 120 s direct-signing wait, with tests asserting both relations.

  **No authority, custody, route or signing-scheme change.** No new endpoint, no new caller, no migration, no schema change, no new relayer spend category, no change to who may call `/safe/exec` or to what the Safe verifies on-chain. `execTransaction` is constructed, gas-limited, signature-checked (`checkSignatures`, `staticCall`), nonce-guarded and broadcast under the relayer send lock exactly as before, and `recordRelayerSpend`/`finishRelayerSpend` still bracket the broadcast unchanged. What changes is only what the caller is TOLD after the transaction is already in the mempool.

  **The perimeter argument for the new answers.** A confirmation timeout is now `202` with `status: 'pending'` and the tx hash, carrying an explicit "this is not a failure, check the hash before retrying" — replacing a `502` that asserted a revert that had not happened. On an owner-authority path that mislabelling was the risk: it read as "it did not happen, do it again", and a Safe `execTransaction` is neither free nor idempotent, so the honest answer strictly reduces the chance of a user double-executing their own transfer. An unconfirmed passkey-signer deploy is now `504` with `status: 'signer_deploy_pending'`, stating that the prerequisite did not confirm and the Safe transaction was therefore **not** submitted — asymmetric with the 202 on purpose, because nothing of the user's is in flight in that case. A genuine mined-and-reverted transaction still answers `502 "Safe execution reverted on-chain"`, byte-identical, and the revert code is still not leaked. `TRANSACTION_REPLACED` deliberately keeps the 502 too: the timeout branch is narrow by construction.

  **Mutation-proven, both directions — the table, not the count.** A number in a compliance record that nobody can check is not evidence, so the runs are written out. Each mutation was confirmed to have LANDED by grepping the mutated file for the new text before the suite was believed (a mutation script died silently earlier in this session and a suite reported green), and each was restored and re-verified by content. Suite: `packages/backend/src/routes/__tests__/safe-exec.test.ts` (22 tests) and `packages/frontend/src/lib/__tests__/safe-tx.test.ts` (5 tests).

  M3 is the one that proves the DISTINCTION rather than merely the handling: widening the timeout predicate to always-true kills the revert test *and* the replacement test, which a suite that only exercised the timeout path could not do. M8 matters for the same reason in the other direction — without it a 202 would have been read as a confirmed success, the mirror-image lie of the one being removed.

  **One branch is deliberately unreachable and is recorded as such**, so that a later mutation of it passing is not misread as dead weight. `execReceipt == null && waitError == null` cannot occur for `confirms = 1` in ethers 6.16.0 — with a null receipt the implementation waits rather than returning — so the null-receipt half is belt-and-braces, attributed to #690's observation that a lagging RPC can report null for a transaction that confirmed. It routes to `pending`, which is the conservative direction: it can only ever turn a confirmed-but-unread transaction into "not confirmed yet", never into a false revert.

  **Known gap, named rather than half-built.** Neither broadcast on this path opens a durable outbound record, so a fee-stuck exec or signer deploy is still owned by nobody and the #1558 bump worker cannot adopt what was never recorded. Recording a user-signed, Safe-nonce-bound submission is a design decision about replacement safety (a fee-replacement mints a new hash, while the hash this route now hands back is the client's only reconciliation handle), not a line to add here; it is filed as its own issue. Today's hand-off is to the caller, which is why the hash is in the 202 body. Perimeter unchanged.
