- **#1989** — Slice 6 of the Safe-rail retirement (epic #1440) **deletes the legacy Safe frontend surfaces**. This is a UI-only slice: every spend path it fronted already answers HTTP 410 server-side (#1986) and the code behind those refusals is already deleted (#1987, #1988). **Nothing here moves funds, changes authority, adds a route, adds a signing scheme, or touches the backend** — the diff is confined to `packages/frontend/`. The perimeter can only NARROW: what disappears is Haven's ability to *ask* a user to sign a legacy Safe transaction, and the surfaces that used to do the asking.

  **Deleted, with the reason each is legacy-only:** `SendModal` (1,015 lines — the legacy owner-send; it narrows its signer to `SafeCapableSigner` and renders nothing on a delegation account) and its `useSendTransaction` hook; `DashboardSendModal` (already zero-importer dead code); `ApprovalQueue` (713 lines), the `/approvals` route, `useApprovals`, `approval-labels` and the `ApprovalNotifications` bell — the approval queue is a legacy-rail concept in its entirety, `POST /approvals/:id/approve` and `/proposed` answer 410 since #1986, and the delegation rail enforces budgets on-chain with no queue at all; `lib/safe.ts` (`deploySafe`, zero importers since #1984 closed the inflow); `lib/safePasskeySigner.ts` (zero importers, verified repo-wide including gitignored files with `/usr/bin/grep`); and the `buildSafeTx` / `SendParams` / ERC-20-transfer-ABI / Gnosis-`TOKENS` half of `lib/safe-tx.ts`.

  **The approver surface is deleted here, and that is the one thing in this slice with a regulatory reading, so it is stated rather than buried.** `ManageApprovers`, `useSafeApprovers`, `lib/approver-tx.ts`, `lib/passkey-approver.ts` and the `rail="safe"` arm of the dashboard recovery nudge are removed. Together they were Haven's **only offered way to add a backup owner to a legacy passkey-owned Safe** — the preventive half of #1229's recovery, since such a Safe is deployed single-owner, threshold 1. **The decision was not taken here.** #1988 (PR #2009, merged 2026-08-24) deleted all five `/user/safes/:safeId/approvers*` backend routes, including `POST /user/safes/:safeId/approvers/tx`, which built the owner-change transaction; its PR states explicitly that these frontend callers "are removed in #1989; until then those paths see a 404". By the time this slice branched, keeping them would have shipped a settings tab whose every action 404s — a worse outcome than removing it, and not a preserved recovery path in any sense.

  **The residual limit #1988 stated is carried forward unchanged and is NOT closed by this slice.** Its four reasons that no account is left unreachable — the epic's phase-5 data decision, the Base-mainnet census (15/15 Safes externally-EOA-owned or relayer-owned, no passkey-owned Safe among them), an EOA owner's ability to manage owners with their own key at Safe's own interfaces, and `POST /safe/exec` staying open with `resolveSigningPasskey` authorising an unbound backup passkey against the live on-chain owner list — are backend facts and are unaffected by a UI deletion. Its stated gap is likewise unaffected: the census is Base **mainnet** and current **as of that merge**, so it does not cover a non-mainnet passkey-owned Safe holding real value. That population can only shrink (`POST /safe/deploy` has answered 410 since #1984), but "can only shrink" is not "is empty". **`POST /safe/exec` is verified byte-identical to `dev` in this diff.**

  **What deliberately STAYS, each with its sharing reason.** `lib/safe-tx.ts` survives **trimmed to its shared half**, the same shape #1987 gave `rails/allowance-module.ts`: `getChainTokens` is a generic per-chain token list read by DELEGATION-rail surfaces (`DelegationSendModal`, `useAgentConnectionSetup`, `agent-panel/agent-display`), and `getSafeNonce` / `getSafeTxHash` / `signSafeTx` / `executeSafeTx` / `proposeSafeTx` / `SafeTxParams` are owner-signed Safe execution still used by the agent lifecycle (`lib/agent-setup.ts`, `lib/revoke-agent.ts`, `EditAgentModal`, `lib/allowance-module.ts`, `lib/signer.ts`), which is outside this slice's scope. `haven/ApprovalRequiredBanner` stays: it is shared — both `SendModal` and `DelegationSendModal` rendered it, and it keys on `threshold > 1`, a property of the account rather than of the rail. `connect-agent/DelegationApprovalStep` is delegation-rail and untouched. Legacy accounts keep a **fully readable** rendering — balances, tokens, agents, transaction history — with an inert `RetiredRailNotice` where the spend action used to be, which is the epic's "accounts and history stay READABLE" boundary made visible.

  **Two guards were found to have gone silent, and both are recorded rather than left green.** `src/__tests__/focus-ring.test.ts` registers (ring colour, background) contrast pairs and states its own rule that "a registered pair that no longer renders is stale data dressed as coverage". This deletion removed the *only named call-site* of two such pairs: brand-ring-on-`warning-soft` (it was `ApprovalNotifications`'s bell) and brand-ring-on-`danger-soft` (it was `ApprovalQueue`'s reject-confirmation panel). Both pairs are **retained** — they still measure a real contrast ratio and still fail on a palette change, so neither is a guard over the empty set — but both are now labelled in place as having **no verified live call-site**, after sweeping all 21 surviving `warning-soft` and all 32 surviving `danger-soft` placements and finding no brand-ring control inside any of them. Registered-but-uncalled beats deleted here specifically because the background arrives from a *parent*, which is the one shape a grep over a control's own class string structurally cannot see.
