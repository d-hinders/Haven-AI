- **#1990** — Slice 7 of the Safe-rail retirement (epic #1440) drops **one** table, `safe_approver_metadata`, and nothing else. **No control is removed, because this table was never one.** 024's own header states its status: rows are "best-effort decoration" — a display label and an `eoa`/`passkey` type — and "membership decisions (add/remove, last-owner guard) are always made against the live on-chain owner set, never this table." No authorization answer, no spend decision and no custody determination has ever depended on a row here, so its absence cannot weaken a guardrail. Its only callers were the approver routes, deleted by #1988. The perimeter narrows and nothing is added: no new authority, no new custody relationship, no new route, no new signing scheme, no funds moved, and the on-chain wind-down of the relayer-owned Safe remains #1985.

  **What this slice did NOT drop, and why that is the regulatorily interesting half.** #1990 was scoped to three tables. Enumerating every reader and writer — the step the ticket demanded and the step #1987 proved you cannot skip — found that only one of the three was actually dead:

  - **`agent_allowances` stays** (split out to **#2020**). It is not a legacy-rail table. `routes/agents.ts:95` reads it for *all* of a user's agent ids **before** the `account_type` branch, so it is on the hot path for pure delegation-rail accounts with no Safe at all. Four live writers and five live readers remain, one of which — `GET /machine-payments/allowances` — **#1986 deliberately left open** as the epic's "accounts and history stay READABLE" boundary. Closing it would reverse a recorded decision and is therefore an owner call, not an implementation detail.
  - **`approval_requests` stays** (split out to **#2021**, as a DECISION rather than a work item). Dropping it contradicts this epic's own phase-3 commitment that accounts and history stay readable — `routes/approvals.ts` records verbatim that `GET /`, `POST /:id/reject` and `POST /:id/executed` are "Deliberately NOT closed" for that reason — and `transaction-history.ts` joins it unconditionally, so the drop would break `GET /transactions` for every user on every rail, not merely for legacy-rail holdouts. The three uncalled `approval_requests` INSERT helpers #1987 handed to this slice travel with #2021 instead.

  **A money-path data-integrity hazard found while scoping the drop, recorded here because it had never been written down anywhere and the next migration is the one that would hit it.** `machine_payment_evidence.approval_request_id` carries `ON DELETE CASCADE` (migration 018), and `018`'s exactly-one-anchor `CHECK` means an evidence row anchored on an approval can never be re-pointed at a `payment_intent_id`. `DROP TABLE ... CASCADE` drops the dependent *constraint*, not the child *rows* — which is precisely what makes the natural "empty it, then drop it" instinct dangerous rather than merely redundant: a `DELETE FROM approval_requests` issued first silently destroys x402 payment proofs, protocol receipts and merchant settlement statuses, with no error and no recovery. **This is demonstrated, not asserted:** the migration test seeds a real approval and a real evidence row on the real-Postgres harness, confirms the evidence row exists (a positive control, so its later absence cannot be an insert that never landed), deletes the parent, and observes the evidence row gone. The warning is carried in 068's own header for whoever writes #2021's migration.

  **Reversibility, stated precisely rather than claimed.** `down()` restores 024's shape verbatim — every column, and the lower-cased unique index, both asserted against `pg_indexes` rather than by eyeball. The DATA is not restored; this is a retirement, not a migration. The degradation on rollback is exactly the one 024 designed for: an owner shows up unlabelled.

  **#1994's torn-row census is not foreclosed by this drop**, and that is verified by execution rather than by inspection. The predicate touches only `users.safe_address` and `user_safes`, both of which #1440 phase 5 explicitly keeps. The migration test runs the census for real after the drop, with a deliberately torn row as a positive control so the query is proven able to say *yes* before any empty result is allowed to mean anything, and with a case-mismatched healthy pair proving #1994's first recorded trap — `LOWER()` on both sides, because `user_safes.safe_address` is unnormalised `VARCHAR(42)` — still holds. No census has been run against any production database.
