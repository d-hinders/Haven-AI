- **#2041** — the hosted MCP generic plain-HTTP x402 tool (`haven_pay_x402_quote`)
  now applies the shared #1450/#1453 settlement-scheme preference rule instead of
  hard-routing every payment to the EIP-3009 funding-leg bridge, and `haven_submit`
  gained an explicit, optional `settlement_scheme` so the erc7710 half of that flow
  has a settle leg. **No new authority, no new custody, no new route.** The
  perimeter argument is that this change only ever *removes* a custody-adjacent
  step: on the selected erc7710 path there is no funding leg at all, so the
  delegate EOA never holds a transient hot balance, no sweep can strand it, and
  the #713 reconciliation class does not arise — the same structural absence the
  #1450 owner decision was recorded for. Nothing was added to the SDK's
  `settlementScheme` vocabulary or to any wire enum; both values (`erc7710`,
  `eip3009`) already existed on `POST /x402` and the backend's own
  `validateGenericSchemeRail` / `deriveFundingShape` guards are untouched and
  remain the authority on which shape an account may use. #1360's explicitness
  property is preserved on **both** branches and on the new submit argument: the
  scheme is always stated on the wire and never inferred from `payTo` alone, so a
  stale or rotated delegate address still fails as a loud shape-mismatch 400
  rather than silently rerouting. Recipient-**pinned** budgets keep the existing
  403 refusal at a merchant that offers only EIP-3009, and — the severity
  correction this change carries — can now reach a merchant at all through this
  tool, where previously every generic-path payment they attempted was refused
  because 3009-mode structurally cannot fund a pinned delegation (owner decision
  2026-07-15). Mutation-proven: eight mutations of the new selection and settle
  code (never-select-erc7710, always-select-erc7710, always-claim-delegation-rail,
  `funding_leg` misreported, facilitator pin dropped, submit never branching,
  submit inventing a `tx_hash`, and submit re-introducing a funding relay) were
  each confirmed to have landed by content and each turned a specific named
  assertion red, alongside positive controls proving a 3009-only merchant and a
  legacy-rail account still take the bridge byte-identically. It **widens the
  population that meets [#2023](https://github.com/d-hinders/Haven-AI/issues/2023)**
  (on erc7710 an over-budget authorize returns `201 pending_signature`, because the
  budget is enforced on-chain at merchant redemption rather than at authorize) —
  it does not change that behaviour in kind, and no money is at risk from it: the
  caveat enforcer still reverts the redemption. Perimeter unchanged.
