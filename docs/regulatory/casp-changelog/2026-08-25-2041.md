- **#2041** — the hosted MCP generic plain-HTTP x402 tool (`haven_pay_x402_quote`)
  now applies the shared #1450/#1453 settlement-scheme preference rule instead of
  hard-routing every payment to the EIP-3009 funding-leg bridge, and `haven_submit`
  gained an explicit, optional `settlement_scheme` so the erc7710 half of that flow
  has a settle leg. **No new authority, no new custody, no new route.** The
  perimeter argument is that this change only ever *removes* a custody-adjacent
  step: on the selected erc7710 path there is no funding leg at all, so the
  delegate EOA never holds a transient hot balance, no sweep can strand it, and
  the #713 reconciliation class does not arise — the same structural absence the
  #1450 owner decision was recorded for. Nothing was added to the SDK's
  `settlementScheme` vocabulary or to any wire enum; both values (`erc7710`,
  `eip3009`) already existed on `POST /x402`, `check:api-types` confirms the
  generated contract is unmoved, and the backend's own `validateGenericSchemeRail`
  / `deriveFundingShape` guards are untouched and remain the authority on which
  shape an account may use. #1360's explicitness property is preserved on **both**
  branches and on the new submit argument: the scheme is always stated on the wire
  and never inferred from `payTo` alone.
- **#2041, spending-control correctness (the part a reader must not assume).**
  Independent review found that the pre-network price cap did **not** bind the
  option this new branch authorizes. #1453 made `selectStandardPaymentOption` and
  `selectErc7710PaymentOption` mutually exclusive, so the cap was compared against
  a different `accepts[]` entry than the one sent — and because `payment_required`
  is merchant-controlled input, that is an **attacker-steerable bypass of a
  user-stated spending limit**, not merely a guard that fails to bind. It is fixed
  here for this branch by re-asserting the cap against
  `x402AuthorizationAmount(selection.option)` using that option's own asset and
  decimals, before any authorize; and a merchant advertising *only* erc7710 is no
  longer refused as unsettleable merely because a cap was stated. Separately, the
  erc7710 authorize now carries the caller's `idempotencyKey`, which it never did:
  the backend's replay dedup existed on this branch all along and was simply never
  invoked, so a retried call minted a second **independently signable settlement
  child** for one purchase — a double-authorize hazard on the one scheme whose
  signed artifact is spend authority rather than a funding step.
- **#2041, what this shard does NOT cover.** The same two defects exist in the
  already-shipped `haven_pay_mcp_tool` and `haven_prepare_catalog_purchase`
  (#1456/#1547) and are **deliberately not fixed here**. The cap bypass was
  measured live on `haven_pay_mcp_tool` — 900 USDC authorized against a stated
  1 USDC cap, with the response reporting 1 USDC — and is filed as **#2051**. This
  shard's perimeter verdict covers the generic path only; #2051 carries its own.
  Also recorded rather than implied: `runDelegationAuthorize` accepts `amountRaw`
  as given and re-validates no client-stated cap, so the client is the **only**
  place a `max_amount` cap exists. What binds on-chain is the *budget*, enforced by
  the caveat enforcer at merchant redemption — a different mechanism protecting a
  different thing, and on erc7710 its enforcement timing is the open question in
  **#2023**, whose population this change widens without changing in kind.
- **#2041, spending-control correctness, part two (found by re-review).** The
  first fix bound the cap correctly on the erc7710 branch but left the ORIGINAL
  pre-selection check in place, so the same root cause survived in the opposite
  direction: an expensive standard entry beside a cheap erc7710 entry made the
  cap **over-bind** and refuse a purchase citing an amount that was never going
  to be authorized (proven live at a 3.00 USDC standard entry beside a 0.50 USDC
  erc7710 entry under a 1 USDC cap). That direction fails safe — it loses the
  purchase, not the money — but it is the same defect class, and it lands
  squarely on the recipient-pinned population this change exists to unblock,
  since they are the ones taking the erc7710 branch. Fixed structurally rather
  than with a second special case: the scheme is now selected **first** and the
  cap is asserted exactly **once**, against `selection.option`. Two cap checks
  guarding two mutually exclusive selectors is how the defect occurred twice.
  The reordering moves one read-only agent GET ahead of a refusal that used to be
  pure; no authorize is created on either path, which is the property that
  protects money, and that is pinned by an updated characterization test rather
  than quietly dropped.
- **#2041, mutation evidence.** Fifteen mutations of the new selection, cap,
  idempotency, settle and resume code were each confirmed to have landed **by
  content** before any result was read, and each turned a **named** assertion
  red: never-select and always-select erc7710, always-claim-delegation-rail,
  `funding_leg` misreported, facilitator pin dropped, the cap assertion deleted,
  the cap bound to the UNSELECTED option (which reproduces the pre-fix bug in
  BOTH directions and kills the under-bind and over-bind tests together), the cap
  decimals taken from the wrong option, the erc7710-only precondition guard
  reverted, the idempotency key dropped at the tool and again at the SDK, submit
  never branching, submit inventing a `tx_hash`, submit re-introducing a funding
  relay, and the resume gate removed. Positive controls prove a 3009-only
  merchant and a legacy-rail account still take the bridge byte-identically, that
  the same cap which refuses an over-cap erc7710 entry still ALLOWS the bridge,
  that the same fixture on a legacy rail IS still refused (so "do not over-bind"
  did not decay into "do not bind"), and that an in-cap erc7710 payment still
  succeeds.
- **#2041, a near-miss worth inheriting.** The first full mutation run reported
  **12 of 13 killed and was entirely false**. The repo's `assert-fresh-dist`
  guard aborts vitest at *global setup* when a package's `dist/` is older than its
  `src/` — and editing SDK sources after the last build tripped it, so every
  mcp-server run exited non-zero having executed **zero tests**. A rig that reads
  "non-zero exit" as "mutation killed" cannot tell that apart from a real kill.
  The fix that made the sweep trustworthy was to require **positive proof the
  suite ran** (vitest's `Tests …` summary line) plus at least one **named** `×`
  test, and to report `DID-NOT-RUN` rather than `KILLED` otherwise; the guard's
  own signature is now detected explicitly. Recorded because the failure mode is
  indistinguishable from success at the exit code, which is where mutation rigs
  are read. Perimeter unchanged.
