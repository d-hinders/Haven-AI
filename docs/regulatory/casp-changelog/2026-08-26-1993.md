- **#1993** — **The Safe rail's closing structural guard, and the second occurrence of the unfalsifiable-spy defect inside the proof that was fixed for it.** Test-only and documentation-only; no runtime code, no route, no schema, no authority surface and no custody surface is touched, and nothing here moves a wei. It is recorded as a money-path change for the same reason #2044 and #2049 were: one of the files it edits, `packages/backend/src/routes/__tests__/non-custody-onchain-gate.contract.test.ts`, is a *regulatory proof* of the non-custody perimeter, and the change concerns whether that proof can fail.

  **The defect.** #2044 removed three spies that could never fail and kept three on an explicit argument: `computeEffectiveAllowance`, `getTokenAllowance` and `getLatestBlockTimeSec` were still live exports of `rails/allowance-module.js`, so a re-added call on the payment path would trip them through the route's transitive import graph — mutation-proven, per name. A later retirement slice then shrank that module to shared chain infrastructure plus the legacy wallet-approval read (`getProvider`, `getRelayerWallet`, `getTokenAllowance`, `getTokenBalance`, `getTokensForDelegate`), and **two of the three stopped being exports**. Nothing failed, and nothing could: `vi.mock(..., () => allowanceMocks)` replaces the module wholesale, so a factory entry for a missing export is not an error — it is a new function nobody calls. The suite went on asserting that two functions production does not have were never called. Unfalsifiable again, by the identical mechanism, seventeen days after it was fixed.

  **What is removed, and what carries the capability instead.** Both dead entries are gone from the mock factory and from `expectNoOffChainCoverageArithmetic()`. **No coverage is lost.** `getTokenAllowance` — the one survivor — keeps its mutation-proven claim, and it is the load-bearing one of the three: a call added *before* the retirement gate reddens the two `#1986 RETIREMENT` cases, which is what makes their "refused before ANY on-chain allowance read" a genuine ordering assertion rather than a restatement of the 410. Both removed names stay in `BANNED_ARITHMETIC`, where the structural import assertion still names them and CAN fail on them. The generalizable finding, recorded because the specific one will recur otherwise: **a spy set pinned to another module's export surface decays silently whenever that module shrinks**, and no gate watches the pinning.

  **The new guard.** `packages/backend/src/routes/__tests__/retired-rail-routing.guard.test.ts` is epic #1440's closing structural assertion — that nothing routes to the retired Safe/AllowanceModule rail. Five rules over the TypeScript AST: (1) no backend source file references a DELETED retired-rail module in any literal, static or runtime; (2) none binds or re-exports a retired-rail execution symbol; (3) no payment ENTRY POINT names a retired-rail module — including the reads-only survivor `rails/allowance-module.ts` — or uses a computed `import()`; (4) the route registry mounts no deregistered prefix (`/approvals`); (5) the rail-decision union offers no live allowance answer. It **extends** #2049's extractor rather than copying it: `parseImportFacts()` moved into a shared `routes/__tests__/helpers/import-facts.ts` that both suites consume, gaining two fact buckets (mounted route prefixes, rail-union literals). Two AST readers that drift is the failure both files exist to prevent.

  **Every rule is proven able to fail, separately.** Each carries a fixture-based positive control showing the detector reports that rule's violation on synthetic input — the discipline #2049's reviewer imposed after finding two of its five rules passing vacuously on buckets the real file never fills. Each was additionally mutation-proven against the real tree, one mutation per rule, each confirmed landed by diff before its colour was read and each restored from a task-named backup: a side-effect import of a deleted module (rule 1), a bound `executeAllowanceTransfer` (rule 2), a query-suffixed dynamic `import()` of the survivor from `routes/payments.ts` (rule 3), a re-registered `/approvals` prefix in `index.ts` (rule 4), and a `{ rail: 'allowance_module' }` member added to `ExecutionRailDecision` (rule 5). Each produced exactly **one** named `×`. A negative control proves an ordinary delegation-rail file trips no rule, and a reach control proves the scan read a real tree rather than reporting an empty, meaningless pass.

  **One rule was widened by review, on a measurement.** `haven-reviewer` demonstrated — not argued — that a dynamic `import()` of a deleted module from a backend file outside the five pinned entry points passed all twelve tests. Rule 1 was widened from static specifiers to every code string literal, and the reviewer's exact edit now produces one named `×`. The remaining blind spots are enumerated in the assertion's own file, not only here: transitive reach through a permitted module, behaviour (nothing here executes a request), arithmetic re-implemented inline, `eval` indirection, non-backend packages, routes mounted outside `index.ts`, a non-literal route prefix, and the database — a row still marked `execution_rail='allowance_module'` is *expected*, since the epic keeps `user_safes` readable.

  **Perimeter unchanged.** No control is added, removed or weakened; what changes is that the retired rail now has a structural reason it cannot grow back, and that every assertion in the Red Line #4 proof can again fail for the reason it states.
