# 2026-08-26 — #2054: erc7710-only merchants reachable through the MCP purchase tools

- **#2054** — a **reachability fix, not a security fix**: `haven_pay_mcp_tool`
  and `haven_prepare_catalog_purchase` could not pay a merchant advertising
  ONLY an erc7710-tagged `accepts[]` entry, because their shared quote helper
  (`buildX402Quote`, `packages/sdk/src/x402-protocol.ts`) was standard-anchored
  and threw "no compatible payment option" before the #1450/#1453 scheme
  selector could ever see the entry Haven actually PREFERS on the delegation
  rail. Pre-existing, fails closed, filed from the #2051 hotfix work and
  recorded there as a known limitation; fixed here.
- **The fix, and why it cannot reintroduce #2051.** `buildX402Quote` now falls
  back to DESCRIBING the erc7710 entry when no standard entry exists, and says
  which selector produced it (`acceptedScheme`). At the two purchase tools the
  scheme selection is then **guaranteed non-null before pricing**
  (`requireSettleableSelection` in `packages/mcp-server/src/tools.ts`), which
  allowed the `?? quote.accepted` display fallbacks to be REMOVED — the quote
  shown, the cap checked (`priceSelectedOption`, asserted exactly once), and
  the amount authorized all read the SAME selected option. A fallback that can
  name a different entry than the one authorized is precisely the #2051 defect
  class; there is now no such fallback on either tool.
- **The refusal perimeter is unchanged in authority and improved in honesty.**
  Three refusals, all pre-intent, none creating anything: (1) an erc7710-only
  merchant reached by an account whose rail cannot settle it — legacy, or the
  pay tool's failed agent read — gets `ERC7710_RAIL_REQUIRED`, naming the
  ACCOUNT as the reason instead of blaming the merchant, and a failed rail
  read refuses rather than guesses (guessing `delegation` would build a
  request the backend then 403s; guessing `eip3009` on this merchant has no
  path at all); (2) a merchant with nothing payable of either kind keeps the
  byte-identical pre-existing "no compatible payment option" refusal, where it
  is accurate; (3) every cap refusal (`PRICE_EXCEEDS_MAX`,
  `DELEGATION_BUDGET_EXCEEDED`) still fires before any intent — funding or
  settlement child — exists.
- **No new authority, no new custody, no wire change.** No endpoint, scheme,
  enum, or signing payload is added or altered; `selectStandardPaymentOption`'s
  #1453 erc7710-skip is untouched and every EIP-3009 settlement path still
  re-selects through it, so an erc7710-described quote structurally cannot leak
  into a 3009 authorization (the stranded-delegate-balance hazard the skip
  exists for). The newly reachable path is the PREFERRED erc7710 shape: no
  funding leg, no transient delegate hot balance, nothing to sweep. Additive
  response fields only (`accepted_scheme` / `erc7710_only` on the read-only
  quote tools); `ERC7710_RAIL_REQUIRED` is a `code` on the existing failure
  envelope.
- **The cap still binds the newly reachable path, and this is mutation-proven,
  not asserted.** Five mutations, each rebuilt into `dist/`, each killed with a
  vitest summary line plus named `×` failures, each restore SHA-256-verified:
  the quote fallback reverted (10 named tests red), the rail refusal disabled
  (3 red), the fallback widened to ANY entry (killed by the quote tool's
  no-settleable negative control), the catalog null-guard removed (1 red), and
  the `acceptedScheme` label hardcoded (1 red). Fixtures give the erc7710-only
  entry an amount (2 500 000) nothing else in the suite's default fixtures
  carries, so no assertion can be satisfied by an inherited number — the #2051
  fixture lesson applied.
- **Backend guards untouched and still the authority.**
  `validateGenericSchemeRail` / `deriveFundingShape` and the on-chain budget
  caveat enforcer are unchanged; everything in this change is a client-side
  refusal becoming reachable-and-honest or a quote describing the entry that
  will actually be authorized.
- **Review findings, applied rather than deferred.** The independent pass
  found the quote helper's blast radius outside the two named tools: the local
  stdio `haven_quote_x402` (a bare SDK passthrough) now also quotes an
  erc7710-only merchant, while the SDK's key-holding pay paths
  (`authorizeX402` / `payX402Quote` / `HavenClient.fetch`) remain standard-only
  by design — so a quote could succeed and the matching pay then refuse with
  the old message blaming Base USDC. Behavior is unchanged (those paths still
  fail closed, nothing signed or moved — an EIP-3009 path structurally cannot
  settle an erc7710-only merchant); the refusal TEXT is fixed instead: all
  four SDK sites now raise the shared `noCompatiblePaymentOptionError`, which
  appends the real reason (the erc7710 tag / settlement scheme) when that is
  the reason. (The helper stays internal to the SDK — the #1618 module
  boundary pins that `x402-protocol` is not published from the entrypoint, and
  its boundary tests enforced exactly that when an export was attempted; the
  hosted server's unreachable defensive branch keeps the base message.) The
  doc-reviewer's blocking finding — the runtime-
  compatibility doc's "local stdio MCP is unaffected" overclaim — is corrected
  in the same pass, with the local/hosted quote skew recorded explicitly.
- **Docs carried with the change:** the #1456→#2041 roll-call passage in
  `docs/architecture/04-x402-payment-sequence.md` gains the #2054 selection-
  aware-quote paragraph (its `last-verified` is date-only per #1496 — this
  shard is the verification record); `docs/operations/mcp-runtime-compatibility.md`
  is re-verified and edited (one additive tool-inventory paragraph, note in
  `last-verified`).
