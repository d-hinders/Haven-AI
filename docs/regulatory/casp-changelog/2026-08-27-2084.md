- **#2084** — the Safe-rail retirement (epic #1440) drops one more table,
  `allowance_nonce_watermarks`, and nothing else. **No control is removed,
  because this table was never one.** 055's own header states its status: a
  WATERMARK, "not a lock — nothing here serialises anything". It was the shared
  half of a **liveness** fix (#692/#718/#1196), never a safety one — signing
  against an already-consumed AllowanceModule nonce was made safe by the #693
  preflight, and what a stale read cost was a failed-and-retried payment, not a
  double spend. No authorization answer, no spend decision and no custody
  determination has ever depended on a row here. The perimeter narrows and
  nothing is added: no new authority, no new custody relationship, no new
  route, no new signing scheme, no funds moved.

  **The table has been inert since #1987**, which deleted the coordinator, the
  repository, `readSharedWatermark`, `waitForFreshAllowanceNonce`, the
  structural test policing the builders, all four call sites and
  `generateTransferHash` itself. That was re-verified for this drop rather than
  inherited: zero SQL statements anywhere in the repository name the table in
  any clause. Every surviving mention is prose — 055 itself, two comments
  citing it as a precedent, the operations doc that keeps the multi-replica
  lesson deliberately past-tense, and the dated shards below.

  **The one real hazard is a name collision, and it is pinned by execution.**
  `payment_intents.allowance_nonce` is a LIVE column on the money path,
  written and read on every intent; it shares a prefix with the dropped table
  and nothing else. A name-based sweep that took the column with the table
  would break payment creation on every rail, and would do it silently until
  the next intent. The migration test therefore does not merely assert the
  column exists in `information_schema` — it inserts a real intent through it
  and reads the value back. The issue's own acceptance grep was written against
  the bare string `allowance_nonce`, which cannot ever come back clean for
  exactly this reason; it is recorded on the pull request as scoped to
  `allowance_nonce_watermarks`.

  **The 069/070 cascade hazard does not arise here, and that is asserted
  rather than assumed.** Those migrations carry a loud warning about
  `DELETE FROM` before `DROP TABLE`, because
  `machine_payment_evidence.approval_request_id` is `ON DELETE CASCADE` and
  emptying the parent first would have destroyed money-path payment evidence.
  055 states this table is "Deliberately NOT foreign-keyed" — specifically so
  it could never fail a money-path write over referential drift — so nothing
  references it and it references nothing. The migration test queries
  `pg_constraint` for foreign keys in **both** directions, expects none, and
  then drops the table with a plain `DROP TABLE` rather than `DROP … CASCADE`,
  because a CASCADE would mask a dependency instead of proving its absence.
  The migration itself still avoids `DELETE FROM`, so this file cannot become
  the counter-precedent if it is the one copied next.

  **Reversibility, stated precisely rather than claimed.** `down()` restores
  055's shape verbatim, including the four-column primary key — asserted
  against `pg_indexes` and then exercised, by inserting a row and observing the
  duplicate-key refusal on the same key. The DATA is not restored, and here
  that is a non-event even by 055's own terms: the rows were disposable scratch
  state whose loss "degrades the system to the pre-#718 in-process behaviour,
  never to incorrectness", and since #1987 there is not even that to degrade.

  **Scope of this shard.** It records only what the drop makes false, which is
  little: an operations doc that said this table had "no tracked removal
  issue", and two prose comments citing it as a precedent. The CASP guardrails
  rewrite against the delegation rail is **#1991**, shipped 2026-08-26 (and
  #1985's on-chain wind-down with it) — this drop neither depends on it nor
  changes it. Perimeter unchanged.

  The TABLE name survives, correctly, in exactly two dated shards — #1680,
  which cites it as the precedent for the rate limiter's shared counters, and
  this one — plus the past-tense operations record. Other shards (#1555,
  #1987, #2044) mention a watermark, but the hyphenated
  `allowance-nonce-watermarks.js` REPOSITORY MODULE that #1987 deleted, or the
  concept, never the table; the distinction is worth keeping straight, because
  the module went in 2026-08 and the table only goes now. All of it is frozen
  history: nothing there claims the table is live, and the multi-replica
  lesson it set the precedent for deliberately outlives it.
