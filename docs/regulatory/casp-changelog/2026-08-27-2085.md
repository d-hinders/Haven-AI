- **#2085** — the backend's unreachable `approval_request` branches are removed
  from six money-path files. **This deletes code that could not run; it removes
  no control, no refusal, and no record.** Every branch removed was gated on a
  `kind` discriminator that two SQL reads produce as a **literal** —
  `'payment_intent'::TEXT AS kind`, `FROM payment_intents` — with no sibling
  read able to supply the other value since #2055 dropped `approval_requests`
  (migration 070). That claim is not an inference from reading the code: a
  characterization test written BEFORE the deletions, on the real-Postgres
  harness per `money.md` §2 and epic #1219, asserts both reads return
  `payment_intent` for real rows, asserts the literal is in the SQL rather than
  a column (so the value is unconstructible rather than merely unobserved), and
  asserts `approval_requests` is absent from `information_schema` so no new
  query could produce the other kind without a migration first. Mutation-proven:
  changing either SQL literal fails two of its four assertions.
  **The read side is deliberately KEPT, and that is the load-bearing decision
  here.** Migration 070 dropped `approval_requests` with `DROP TABLE ... CASCADE`
  **specifically so historical evidence and reconciliation rows would survive**
  holding their `approval_request_id` values — its own header names the
  alternative an FK hazard that would cascade away proof-of-payment records, and
  #2021's owner decision waived queue-history readability while explicitly
  keeping the accounts and their evidence readable. `mapEvidence` still reads
  `approval_request_id` and still uses it as the `payment_id` fallback, because
  for a pre-#2055 approval-era receipt it is the only anchor that row has;
  removing it would have returned `payment_id: null` for every one of them. The
  distinction is now written at the call site so a future dead-code sweep
  cannot mistake the read for residue, and the one evidence test that asserted
  the opposite was INVERTED rather than deleted — it now pins that nothing NEW
  is anchored that way, which is the property that actually holds.
  **What changed, precisely:** write-side branch collapses in
  `modules/mpp/{evidence,reconciliation}.ts` (new rows always anchor to a
  payment intent), the unreachable `approval_request` HTTP-code block in
  `modules/payments/agent-payment-status.ts` (202/200/409/410 — none reachable;
  the module's own comment four lines above already said so), the zero-caller
  `pendingApprovalResponse` + `X402ApprovalRow` in `modules/x402/`, two
  zero-reference row types in `infra/repositories/transaction-history.ts`, and
  the `'approval'` variant of `allowanceModuleRailRetired` in
  `rails/execution-rail.ts` — which had zero production callers AND a message
  that had gone false (it promised the queued approval "stays readable, and it
  can still be rejected" while `/approvals` is deregistered and the table is
  dropped). A test asserted that false promise verbatim; it is replaced by one
  pinning the variant's absence. **The rail seam itself is untouched** and stays
  for reversibility per CLAUDE.md — this removed one dead branch inside it. Two
  user-visible strings changed, both away from naming a thing that cannot
  exist: a 404 body (`'Payment or approval request not found'` →
  `'Payment not found'`) and no other. No route, schema, authority, credential,
  signing surface or custody boundary moved; no refusal was removed or relaxed;
  the full backend suite is green at 2599/2599. Perimeter unchanged.
