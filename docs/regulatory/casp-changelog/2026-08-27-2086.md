- **#2086** — the local MCP server's **first-launch consent gate**
  (`packages/mcp/src/consent.ts`) is re-based off the retired Safe
  AllowanceModule and its approval queue onto the delegation rail. **Copy only:
  no route, tool schema, capability, request/response shape, authority, custody
  or execution boundary moves**, and the gate remains informational rather than
  enforcement exactly as before — the agent's signed budget delegation and its
  caveat enforcers were the policy primitive prior to this change and are the
  policy primitive after it. What changes is that the text now says so.
  **Why it is a guardrail matter and not tidying.** This block is the last thing
  an operator reads before handing payment tools to a model, and it told them
  *"Anything above the on-chain allowance pauses for owner approval in the Haven
  dashboard"* and, with no budget configured, *"Any payment will queue for
  manual approval. The on-chain Safe AllowanceModule is the real spend gate."*
  Every one of those sentences is false on the only rail that can pay: the
  AllowanceModule rail answers HTTP 410 on the payment paths (#1986), an
  over-budget payment is declined on-chain rather than held, and since #2055
  there is no `approval_requests` table for a queue to live in. An operator who
  believed it would size a budget expecting a human backstop that does not
  exist — a disclosure defect in the CASP sense (the user is told a control
  exists that does not), which is why it is corrected rather than left to a
  wording pass. The new text states the decline, states that nothing is queued
  and no one is asked to review it, and names the remedy (the wallet owner
  grants or raises the budget), following `docs/product/copy-guidelines.md`'s
  rule that an out-of-rules payment is never described as pending, queued or
  waiting (#2063). It is ONE description rather than rail-aware prose, matching
  the shape every other surface in epic #1440 was re-based to, because a reader
  cannot be in the legacy state.
  **No re-consent is triggered, and this was verified rather than assumed.**
  `computeConsentHash` covers credential identity + registered tool NAMES +
  the allowance summary — never the rendered prose — so existing `HAVEN_MCP_ACK`
  values and `<credentials>.ack.json` sidecars stay valid, and the frontend's
  pre-computed hash (`packages/frontend/src/lib/mcp-consent-hash.ts`, same three
  inputs) needs no matching change. A test now pins that property, so a future
  refactor that folds prose into the hash has to argue with a test rather than
  silently re-prompt every operator.
  **Scope held deliberately.** The consent block interpolates tool descriptions
  from `@haven_ai/sdk`, seven of which still name the AllowanceModule and two of
  which still offer a `pending-approval` outcome. Those are agent-visible prose
  on a different package with its own shrink-only size ratchet (#1591) and are
  filed as #2100 rather than absorbed here; the tests added by this change scope
  their negative assertions to the gate's own prose and say so, so the remaining
  residue is recorded rather than hidden. Guards are mutation-proven — restoring
  the approval-queue sentence fails 3 tests, restoring the AllowanceModule gate
  label fails 1, restoring the no-budget manual-approval claim fails 2.
  Perimeter unchanged (`packages/mcp/**` is not on it).
