- **#2094** — the erc7710 settlement child became **intent-unique**, so a
  settlement can be attributed to exactly one payment instead of to a shape.
  Until now `buildSettlementDelegation` left `salt` at the framework default
  (`0x00`, verified by probe) and the child's only clock-derived field was the
  `timestamp` caveat's `beforeThreshold`, so two authorizations sharing
  merchant `payTo`, token, amount and expiry SECOND produced a BYTE-IDENTICAL
  child with the same `childHash` — the residual #2092 recorded and #2096
  answered by refusing to guess. The child is now salted with
  `keccak256("haven-x402-settlement:" || <payment intent id>)`, and the intent
  id is generated before the child is built and written as the row's explicit
  primary key, so the mapping intent → child is a pure, reproducible function
  of stored data rather than an opaque stored value. **No authority moved, no
  spend limit changed, and no fund movement was added or changed:** the salt is
  a uniqueness field inside the delegation struct — the caveats that bound what
  can move (exact amount, payee pin, ≤600s expiry, redeemer pin when
  advertised) and the parent budget delegation that meters it are untouched,
  Haven still signs nothing, and the agent still signs the child client-side.
  **Nothing sensitive reaches the chain.** The salt is public — it travels in
  the child and is emitted in the DelegationManager's `RedeemedDelegation` log
  — and its preimage is a domain tag plus a v4 UUID: 122 bits of CSPRNG entropy
  encoding no user, agent, merchant, amount or timing information. That UUID is
  not a Haven secret either; it is the `payment_id` already returned to the
  agent, quoted in the settle URL and shown in the dashboard, and knowing it
  authorizes nothing. Because it is hashed it is not even legible on-chain, and
  the payer smart account was already visible in the `Transfer` log's `from`,
  so no new correlation is possible. The domain tag makes a settlement salt
  structurally incapable of colliding with a budget-delegation salt.
  **Verification got STRONGER, not looser.** `verifySettlementTransferTx` gained
  check 8: when the transaction carries `RedeemedDelegation` logs from the
  **pinned, audited** DelegationManager, the emitted `Delegation` struct is
  re-hashed with the framework's own `hashDelegation` and this intent's stored
  `delegation_hash` must be among them — otherwise the settlement is refused as
  a `mismatch`. This reads the manager's EVENT, never facilitator-shaped
  calldata, so it adds no coupling to any merchant-side implementation; a
  transaction carrying no such log, or an intent with no stored child, falls
  back to checks 1–7 exactly as before, because an absent log is "we learned
  nothing", not evidence of a forgery. **#2096's ambiguity guard is KEPT, and
  narrowed rather than deleted.** It is now looked past only when all of: the
  settlement was bound to this intent's own child by check 8; this intent has a
  recorded child; and the twin has a recorded child that is a DIFFERENT one. A
  twin whose child was never recorded is unknown, and unknown is treated as
  ambiguous, not as different. Two pre-#2094 authorizations therefore share one
  child hash, fail the last conjunct, and are still both refused — the
  fail-closed behaviour is preserved exactly where it is still the only safe
  answer. **In-flight compatibility is proven, not assumed:** an authorization
  created before this change and settled after it carries the old constant
  salt, and the verifier reads what the chain emits rather than what today's
  builder would build, so its stored hash still binds; a lone such payment
  still confirms, and a look-alike pair of them is still refused. Every guard
  is mutation-proven — 10 mutations, 10 kills, each landing confirmed by file
  hash before the run was read and each producing a named failing test, plus a
  positive control proving the collision case would still collide under a
  constant salt. The net effect on the money path is that two of a user's own
  look-alike payments now each reach the books on their own evidence instead of
  both being stranded, and that a settlement can no longer be attached to a
  look-alike sibling even when its transfer shape matches perfectly. Perimeter
  unchanged.
