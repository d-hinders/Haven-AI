- **#2100 / #2101** — the **agent-facing tool descriptions and MCP server
  instructions** (`packages/sdk/src/tool-descriptions.ts`,
  `packages/sdk/src/tools.ts`, `packages/mcp-server/src/{tools,server}.ts`,
  `packages/mcp/src/server.ts`, plus the three published READMEs and the shipped
  SDK examples) are re-based off the retired Safe AllowanceModule and its
  approval queue onto the delegation rail. This is the follow-up #2086 recorded
  as deliberately out of its scope. **Prose only: no route, tool schema,
  capability handshake, request/response shape, authority, custody or execution
  boundary moves**, and descriptions were never an enforcement surface (the
  #1591 precedent) — every refusal is enforced in code and on-chain, before and
  after.

  **Why it is a guardrail matter and not tidying.** These strings are not
  documentation a human skims past: they are what an LLM agent reads at
  `tools/list` and `initialize` to decide what to do. Seven descriptions named
  the Safe AllowanceModule as the spend path — an endpoint that answers HTTP 410
  on every agent-payment entry point since #1986 — and both servers'
  `instructions` presented `pending_approval` as a reachable outcome, the hosted
  one as the *default* over-budget result. The hosted `HOSTED_INSTRUCTIONS` go to
  every model on every session on the default topology
  (`docs/architecture/08-local-vs-hosted-mcp.md`). An agent following them would
  poll for an approval that cannot arrive: `pending_approval` is emitted by no
  backend path, appears in no migration, and #2055 dropped the
  `approval_requests` table it was ever read back from. In CASP terms this is
  the same disclosure defect #2086 corrected one layer up — a control is
  described that does not exist — except the reader here is an autonomous agent
  that acts on it rather than a human who might notice.

  **What the replacement says, and what makes it true.** An out-of-policy
  payment is *declined before any money moves*: `POST /payments` answers 403
  when no active delegation authorizes the token/recipient and 502 on a caveat
  rejection, both with nothing written (`packages/backend/src/routes/payments.ts`);
  `POST /x402/authorize` answers 403 `delegation_budget_exceeded` before an
  intent row exists (`modules/x402/delegation-authorize.ts`, #2082); and both
  retired rails answer 410 (`rails/execution-rail.ts`). The wording follows
  PR #2066/#2075's established framing and
  `docs/product/copy-guidelines.md`'s rule that an out-of-rules payment is never
  described as pending, queued or waiting. It is ONE description rather than
  rail-aware prose, matching every other surface in epic #1440, because a reader
  cannot be in the legacy state.

  **Retained deliberately, and argued rather than defaulted.** The
  `isPendingApproval` branches in both MCP runtimes and the SDK's
  `pending`/`pending_approval` state mapping are kept: they are fail-CLOSED (they
  stop the agent and return the payment_id instead of delivering a merchant
  header), and deleting them would trade a defined stop for an undefined
  fall-through on a money surface. What is removed is the agent-visible PROMISE —
  no description or instruction now tells a model to expect the status or wait
  for an approval, and the servers' general "a status you do not recognise →
  stop and tell the user" rule covers the residue. The wire-schema question is
  #2105's.

  **No re-consent is triggered.** `computeConsentHash` (local MCP) and
  `computeSignerConsentHash` (signer) hash credential identity + registered tool
  NAMES + the allowance summary, never the rendered prose (#2086), and no tool
  was added or removed — so existing `HAVEN_MCP_ACK` values and
  `<credentials>.ack.json` sidecars stay valid.

  **Guard.** The queue-framing census (#2063) is extended to these surfaces and
  moved to `scripts/ci/queue-framing-census.test.mjs`, which runs on EVERY pull
  request; in `packages/frontend` it sat behind a surface filter and could not
  fire on an SDK- or MCP-only change. Mutation-proven in both directions, with
  positive controls that the scanner detects every phrase it bans and does not
  flag the corrected prose. The #1591 shrink-only description-size ratchet stays
  green and the served payload is byte-for-byte flat (17,423 bytes, cap 18,365).
  **Applied from independent review, and worth recording because both were
  disclosure defects the first pass missed.** (1) Three live hosted guidance
  payloads (`haven_pay_mcp_tool`, `haven_prepare_catalog_purchase`,
  `haven_quote_catalog_purchase` catch branches) still told the agent the payment
  was *"queued for the wallet owner… then poll next_tool"* — the same false
  backstop, in the machine-readable response rather than the description. (2) The
  retained fail-closed branches emitted `next_action: wait_for_user_approval`
  beside prose saying not to wait; the agent contract says to follow the
  structured field FIRST, so the field won and the payload contradicted itself.
  Both are corrected to `stop_and_tell_user` with matching prose (in
  `packages/mcp-server/src/tools.ts`, `packages/mcp/src/tools.ts` and the SDK's
  own `payment-state.ts` status mapping), and the SDK's exported enum description
  maps (`packages/sdk/src/types.ts`) now mark the retired values as producible by
  no live rail. The census scanner was hardened in the same pass: it now joins
  adjacent string literals — the three payloads above were split across a `' +`
  line break, which a contiguous-substring scanner walks straight past — and no
  longer strips Markdown headings and star-bullets when scanning a README.
  Perimeter unchanged (none of these packages is on it).
