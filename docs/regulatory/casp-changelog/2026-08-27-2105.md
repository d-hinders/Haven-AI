- **#2105** — **Documentation only. No route, handler, authority, custody,
  credential or key-material change, and no behavioural change of any kind.**
  The published OpenAPI contract (`packages/backend/src/openapi/spec.ts`, served
  live by `routes/openapi.ts` and regenerated verbatim into
  `packages/core/src/api-types.ts`) still described the **retired Safe /
  AllowanceModule rail as the live spend path**. Epic #1440 closed that rail —
  #1984 shut the Safe inflows, #1986 made every agent-payment entry point answer
  HTTP 410, #2020 retired the `agent_allowances` surface, #2055 dropped
  `approval_requests` outright, and #1993 shipped the AST-based structural guard
  that nothing routes to it — but the machine-readable contract an integrator
  reads first had not been re-based. **This commit changes what Haven SAYS, so
  that it matches what Haven already DOES.** Nothing becomes payable, refusable,
  or authorised that was not already.
- **The perimeter is unchanged and nothing on the money-path file list is
  touched behaviourally.** `openapi/spec.ts` is not on the money-path glob list.
  The one file on that list in this diff is `routes/payments.ts`, and the edit
  is **a comment only** — a stale docstring line claiming "a pending approval
  replays as 202", four lines above the #2055 note that deleted that very
  branch. Independent review (`haven-reviewer`) confirmed zero behavioural
  change; `git diff` on that file is comment lines exclusively.
- **What was corrected, and why each one matters for a regulated reading.** The
  spec documented a `201 pending_signature` / `202 pending_approval` happy path
  for `POST /machine-payments/send`, whose handler (`modules/mpp/send.ts`) is
  three refusals and nothing else — two 410s and a 422 — and did **not** document
  the 422 that actually happens. It documented `202` approval branches on `POST
  /payments`, `POST /x402/authorize` and `POST /x402` that no code path emits.
  Most consequentially for the custody argument: `bearerIdentityDescription`,
  attached to **every operation in the document**, stated the non-custodial
  boundary as `API key = identity / delegate signature = authority / on-chain
  Safe module state = enforcement` — naming the retired AllowanceModule as the
  live enforcement primitive. It now names the on-chain **budget delegation**
  and its audited caveat enforcers, checked by the DelegationManager at
  redemption. **The three-way split itself is unchanged** — identity, authority
  and enforcement remain separate, and an API key alone still cannot move funds.
  Only the primitive holding the third term was corrected to the one that is
  actually enforcing.
- **A second finding, raised by independent review, on the LIVE rail's primary
  success response.** `paymentSignData` — the `sign_data` of the `201` of `POST
  /payments`, and of the x402 authorize `200`/`201` through
  `X402SignablePayment` — still described the retired
  `executeAllowanceTransfer` signing scheme: it *required*
  `components.{safe, payment_token, payment, nonce}`, was
  `additionalProperties: false`, and therefore **forbade** the
  `signature_scheme: 'eip712_userop'` and `typed_data` that the live handlers
  emit. An integrator following it would have signed a bare hash with raw ECDSA.
  Corrected to the shape both live emitters actually produce, and pinned by
  assertions that run the spec's own validator over real emitted bodies. Note
  what this does **not** relax: the #829 invariant that the agent signs the
  account's exact EIP-712 typed data **verbatim, never a bare hash**, is now
  stated by the schema rather than merely by prose, and `hash` carries an
  explicit "do NOT sign this directly" note.
- **The retain-vs-delete rule applied, stated because the deleting direction has
  its own regulatory cost.** A retired endpoint that still answers 410 is part
  of the live contract, and an integrator needs to know it returns 410 and why —
  deleting it would leave a 404-shaped surprise. So: a response or schema the
  route can **never** emit is DELETED (an unreachable 2xx instructs a caller to
  build a dead branch); a path the router still registers and answers 410 on is
  RETAINED and re-described as retired (the pattern already set by the
  `POST/DELETE /agents/{id}/allowances` tombstones); a value still serialized
  but unreachable is RETAINED with an explicit wire-compatibility note in the
  #2055 style (`AgentPaymentStatus.kind` keeps `approval_request`); and a
  mention that is **accurate about live behaviour is left alone**. The last
  category was checked case by case rather than swept: the merchant-side
  `POST /x402/resources/{id}/verify` genuinely still requires an AllowanceModule
  transfer (`infra/chain/allowance-transfer-verifier.ts` decodes
  `executeAllowanceTransfer` and pins `tx.to` to the AllowanceModule contract),
  the `/agent-connection-setups/{setupId}/wallet-approval` `202` is a real,
  live legacy-Safe connect approval, and the `uint96` cap on atomic amounts is
  still enforced — only its stated *reason* had drifted to the retired rail,
  and now names the delegation rail's `ERC20PeriodTransferEnforcer` word size.
  **Over-deleting here would have removed true statements about live behaviour**,
  which is why each was verified against the route rather than against the
  issue.
- **`PendingApproval` and `X402PendingApproval` are DELETED, not tombstoned, and
  the distinction is deliberate.** A tombstone earns its place when something is
  still on the wire — a path answering 410, or a field still serialized at a
  fixed value (`pending_approvals` / `actionableApprovals`, both "always 0 since
  #2055"). Neither applies: with the three `202`s gone and
  `X402PendingApproval` dropped from the `x402AuthorizeResponse` `oneOf`, no
  response in the document can carry either shape. The removed comment on
  `PendingApproval` actively invited future work — it said direct approvals,
  x402 approvals "and **future rail-specific approvals** share this base shape",
  instructing a builder to extend an approval taxonomy this epic retired. The
  delegation rail has **no approval queue at all**: budget is enforced on-chain
  by the caveat enforcers, and an over-budget payment reverts during gas
  estimation rather than queuing for a human.
- **Verification.** Generators re-run (`npm run generate:api-types`), the
  generated `packages/core/src/api-types.ts` committed, and `npm run
  check:api-types` green — a hand-edited spec that drifts from its generated
  types is worse than a stale spec, because the gate then passes on an
  inconsistency. The new guard suite does **not** restate a description: it
  CALLS `handleSend` across all four rail populations (`session_key`,
  `allowance_module`, `null`, `delegation` — `null` included because
  `resolveExecutionRail`'s fall-through means a missing Safe row lands on
  `retired_allowance`) and asserts the status it really returns is one the spec
  really documents, and it runs the spec's own validator over real `sign_data`
  bodies. Fourteen mutations were applied and killed, each confirmed by a
  `Tests …` summary line plus a named `×`, including two positive controls (a
  disabled `$ref` walker, and a schema widened to accept anything) and one
  mutation that **survived** — re-opening `components` — which exposed a real
  looseness in the new schema and was fixed by closing the object and adding the
  assertion that now pins it. Perimeter unchanged.
