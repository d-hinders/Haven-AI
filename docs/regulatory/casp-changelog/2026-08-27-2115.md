- **#2115** — `GET /payments/:id` stops telling an agent to wait for an approval
  that cannot arrive. **No control, refusal, record or authority moves; the
  change is response prose plus one removed type and one fail-closed default.**
  `messageForRail` in `modules/payments/agent-payment-status.ts` overrode the
  payment intent's own message on the x402 and MPP rails for four statuses —
  `pending`, `approved`, `proposed`, `executed` — with instructions to hold the
  merchant session open and poll for a wallet-owner approval. **It is deleted,
  not reworded**, because all four are unconstructible: this module reads
  `payment_intents` and nothing else since #2055 removed the `approval_requests`
  fallback, and every write to `payment_intents.status` in the repository layer
  sets one of five literals (`pending_signature` from all four INSERTs;
  `submitted` / `confirmed` / `expired` / `failed` from the UPDATEs in
  `payment-intents.ts`, `x402-authorizations.ts` and `agent-rekeys.ts`). The
  four overridden values were `approval_requests` statuses, fed here by
  `approvalState`, which #2055 deleted with the table. That claim is not an
  inference from reading the code: a real-Postgres characterization test
  (`modules/payments/__tests__/status-domain.test.ts`, epic #1219) pins the
  five-literal write domain structurally, asserts the emitted `message` /
  `next_action` / `phase` by VALUE for each reachable status on both rails, and
  asserts `approval_requests` is absent from `information_schema`. The column is
  a bare `VARCHAR(20)` with no CHECK, so the domain is a property of the writes
  and had to be proven rather than read off the schema.
  **Why this string mattered more than the average retired-rail sentence:** the
  SDK passes the backend's `message` and `next_action` straight through
  (`mapPaymentStatusResult`), minting its own text only when the backend sent
  none. So on this one path the backend's string overrode every client-side
  correction PR #2113 made, on the endpoint an agent calls specifically to
  decide what to do next about a payment. No live rail can produce the outcome
  it promised: the legacy AllowanceModule rail answers 410 at every
  agent-payment entry point (#1986), and the delegation rail declines an
  out-of-policy payment at prepare with nothing written (403/502 from
  `routes/payments.ts`; 403 `delegation_budget_exceeded` from
  `modules/x402/delegation-authorize.ts`, #2082).
  **One behavioural change, deliberate and fail-closed.** The catch-all in
  `paymentIntentState` answered `check_status_later` — a poll instruction — for
  any status the module does not recognise. It now answers `stop_and_tell_user`
  with prose saying the state is unrecognised and must not be polled or retried.
  This is unreachable today (the five recognised branches are the whole domain)
  and so changes no live response, but it makes the backend agree with the SDK's
  `nextActionForStatus`, which #2101/PR #2113 moved to `stop_and_tell_user` for
  exactly these statuses — and since the backend's value overrides the SDK's on
  this path, the SDK's correction was inert without it. `phase` is left at
  `payment_submitted`: a closed wire enum has no "unknown" member, and
  `next_action` is the field the agent contract says to follow first.
  **SDK:** the hand-written `interface PendingApproval` is **removed** (with the
  reasoning written at the removal site), not retained with a note. It is the
  one case on this epic where retention is not fail-closed: it was a type, not
  runtime code, and after #2113 nothing in the SDK maps any status to
  `wait_for_user_approval`, so no value the SDK produces can inhabit it. Its
  wire twin was already deleted by #2105/PR #2112. The retained fail-closed
  `isPendingApproval` branches in both MCP runtimes are untouched, as are the
  `PaymentStateKind` and `AgentPaymentNextAction` wire values and their
  "Retired wire value" descriptions. Nine JSDoc comments on those retired enum
  members were corrected to match the `x-enumDescriptions` beside them, which
  #2113 had already fixed — the comment and the description sat in the same
  file contradicting each other.
  **Guard:** the repo-wide queue-framing census
  (`scripts/ci/queue-framing-census.test.mjs`, moved there by #2113 so it runs
  on every PR) gains both files in `GUARDED_FILES` and two phrases —
  `the user approved this`, `the remaining account approvals` — that the
  `approved` and `proposed` strings walked straight past. Extended, not
  duplicated. No route, schema, migration, authority, credential, signing
  surface or custody boundary moved. Perimeter unchanged.
