- **#2117** — the Fortnox reporting-feed fail-forever gap for erc7710 direct-settlement payments is closed on two sides. **The integrity posture is unchanged: Haven still never submits, holds, or moves funds on this path — the observer only CONFIRMS a settlement the merchant already redeemed on-chain, through the same fail-closed seam the agent-report path uses.**

  **The change, precisely.** (1) SDK: `reportEvidence` now retries — bounded, ~1.5s worst case, only on the post-delivery path — when the `/machine-payments/evidence` route answers **503 `settlement_unobservable`** (the backend's documented retryable "not known yet" refusal: tx not yet mined / RPC unreachable). Terminal refusals (409 `settlement_unverified`, 400, 404) remain swallowed per the best-effort evidence contract, keyed on `HavenApiError.statusCode`, never on message text. (2) Backend: a leader-locked observer (`infra/erc7710-settlement-observer.ts`, new `LEADER_LOCK_KEYS.delegationSettlementObserver=811009`, per-intent `KEYED_LOCK_NAMESPACES.settlementObservation=811102`) ticks every 90s. It scans `submitted` delegation-rail x402 intents (`execution_rail='delegation'`, `machine_metadata->>'settlement_scheme'='erc7710'`, `tx_hash` NULL, settled-window still open, ≤ ~13 min after authorize), finds the settlement on-chain (`eth_getLogs` for the token contract's `Transfer` from the Safe to the merchant), and — under no trust of its own — runs the candidate through the EXISTING `verifySettlementTransferTx` + `observeErc7710Settlement` seam, then `recordMachinePaymentEvidenceBase`, so the evidence row, fee ledger and Fortnox auto-feed fire exactly as for a reported hash. Discovery is candidate-finding only; anything short of the verifier's `verified` verdict is skipped and retried next tick, and an RPC outage is never a verdict. The per-intent advisory lock serialises the observer against the agent-report HTTP path; the CAS/replay/ambiguity guards in `confirmObservedSettlement` decide the winner, fail-closed to `submitted` on any refusal. A settlement whose window has fully expired is left alone (never hammered, never wrongly completed); the single remaining no-path case is an RPC outage spanning the whole scan window.

  **What moved.** `packages/sdk/src/merchant-completion.ts` (retry predicate + bounded backoff), `packages/backend/src/infra/erc7710-settlement-observer.ts` (new), `modules/x402/settlement-observed.ts` (window derivation factored into a shared `expectedSettlementTransferFor`, used by BOTH the HTTP seam and the observer so there is one source of truth), `infra/repositories/x402-authorizations.ts` (eligibility SQL + `findPendingErc7710Settlements`), `infra/chain/settlement-transfer-verifier.ts` (exported `ERC20_TRANSFER_TOPIC`), `platform/leader-lock.ts`, `infra/index.ts` wiring, plus a db-schema-smoke entry.

No migration; no new fund movement; no custody, delegation, caveat, signing, or credential boundary touched.
