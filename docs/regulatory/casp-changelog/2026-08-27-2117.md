- **#2117** — an erc7710 settlement that no agent ever reported is now completed
  by **passive on-chain observation**, closing the #2092/#2096 residual in which
  settled money stayed permanently absent from the user's accounting feed. On
  erc7710 direct settlement the merchant redeems the delegation chain and Haven
  submits nothing, so the intent sat at `submitted` until an agent posted the
  merchant's settlement hash; when the merchant returned no `PAYMENT-RESPONSE`
  transaction, or the generic plain-HTTP flow (#2041) meant Haven never saw the
  header, no `machine_payment_evidence` row was ever written and the payment
  reached neither the Fortnox auto-feed nor "Sync now". A leader-gated tick now
  scans the **pinned, audited** DelegationManager's `RedeemedDelegation` logs
  over a bounded block range, matches each open intent's stored
  `delegation_hash` (intent-unique since #2094), and hands the transaction it
  finds to the SAME `observeErc7710Settlement` seam the agent-reported path
  uses. **No authority moved, no spend limit changed, and no fund movement was
  added, changed or initiated:** the sweep is read-only against the chain — it
  broadcasts nothing, signs nothing, holds no key, and its only write is the
  existing `submitted → confirmed` transition plus the evidence/fee/feed rows
  that transition already produced. It cannot cause a payment to happen; it can
  only record one that already did. **Verification is unchanged and, for this
  caller, STRICTER.** Every candidate runs through `verifySettlementTransferTx`
  checks 1–8 and through the guarded `UPDATE` with its replay guard and #2096's
  ambiguity guard, exactly as an agent-reported hash does — and additionally the
  sweep passes `requireDelegationBound`, so a transaction that matches this
  payment's token, payer, merchant, exact amount and settlement window is still
  REFUSED unless the pinned manager's own log named this payment's settlement
  child. **The refusal to guess is the design, not a limitation.** The sweep has
  exactly one attribution path — the manager's event, re-hashed with the
  framework's own `hashDelegation` — and deliberately no transfer-shape
  fallback, because the pre-existing behaviour was *fail-closed: never wrong,
  sometimes missing*, and on an accounting feed a confidently misattributed row
  is strictly worse than a missing one (a missing row surfaces at
  reconciliation; a wrong one does not). Three residuals are therefore left open
  on purpose and stay `submitted`: a facilitator route emitting no decodable
  manager log, a pre-#2094 look-alike pair sharing one child hash, and a
  settlement older than the 24-hour recovery horizon. Each is logged as an
  operational warning once its settlement window has closed, so the residue is
  visible rather than silent. **The settlement window bounds the transaction,
  not the search.** A settlement of this child cannot be mined outside
  `authorize .. authorize + 600s` — enforced on-chain by the `timestamp` caveat
  and still checked — but the sweep keeps looking for 24 hours, so an RPC outage
  spanning a payment's window is recovered rather than converted into permanent
  invisibility. **RPC discipline:** each candidate is scanned over its own
  settlement window (a few hundred blocks), overlapping windows share calls, one
  `eth_getLogs` per 500-block batch, address- and topic-filtered, at most 20
  batches per chain per tick, an exponential backoff on a fruitless scan, and a
  90-second grace so the ordinary agent report happens first. Independent review
  of the first draft found a starvation defect — one range per chain anchored on
  the oldest candidate could be frozen short of the chain head by a permanently
  unattributable row and blind the sweep to every newer payment on that chain;
  per-candidate windows remove the coupling, and the regression is pinned by a
  test that reproduces it. Any RPC failure abandons the scan for that chain and
  confirms nothing, with no in-tick retry; a partial log index is never used,
  because "absent from a truncated range" is indistinguishable from "not
  settled"; and a candidate the batch budget did not reach is left untouched
  rather than judged, because "not scanned" and "not found" are different
  facts. **SDK:**
  `reportEvidence` no longer discards the backend's deliberate retryable/terminal
  distinction in a bare `catch {}` — a `503 settlement_unobservable` is retried
  with bounded backoff (three retries, 1s/2s/4s), a `409` is not, and neither
  can change the caller-visible outcome of an already-paid resource. Every guard
  is mutation-proven — 11 mutations, 11 kills, each landing confirmed by file hash
  before its run was read and each producing a named failing test — with
  positive controls on both halves so a rig that confirms nothing, ever, cannot
  pass. Perimeter unchanged: Haven still custodies nothing and still signs no
  settlement.
