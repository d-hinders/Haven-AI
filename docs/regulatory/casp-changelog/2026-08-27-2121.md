- **#2121** — `docs/architecture/04-x402-payment-sequence.md` stops presenting
  the deleted approval queue as reachable on the live rail. **Documentation
  only: no route, schema, migration, authority, credential, signing surface or
  custody boundary moves, and no source file is touched.** The doc is
  `contract: true` and covers `modules/x402/**` plus most of the SDK/MCP payment
  surface, so the failure mode was concrete rather than cosmetic — an integrator
  reading it would have written a polling loop for a state no code produces.
  **Four sites, two treatments, and the choice is stated per site.**
  (1) The `## Hosted Generic Split Flow` sequence diagram's `else pending
  approval` branch is **rewritten, not banner-wrapped**: it is the live
  EIP-3009 shape of the hosted path, and the text below it says the flow applies
  to the delegation rail too, so a branch that cannot occur was replaced with
  the refusal that actually occurs. The refusal is stated per rail and scheme
  rather than flattened — `502` with no intent row on the EIP-3009 shape the
  diagram draws (the redemption is estimated, so the caveat enforcer's refusal
  surfaces there), `403 delegation_budget_exceeded` on erc7710 where authorize
  pre-checks the live remaining budget (#2082), `410` on the legacy rail
  (#1986). None writes anything and none mints a `payment_id` to poll.
  (2) The `## Approval Resume` section is **deleted as instruction and retitled
  `## Resuming An Authorized Payment`**, keeping a retirement banner in the
  voice this file already uses for its legacy two-leg diagram. Deleted rather
  than kept as history because it was step-by-step integrator instruction, not
  a record of a flow. What survives is the half that was never
  approval-specific: `getResumeState` rehydrates a payment's stored x402 context
  after a restart, with no status precondition, rail-neutrally, and it is live.
  The resume CALL is stated separately and honestly as **retained but currently
  unreachable**: `resumeX402Payment` / `resumeAuthorizedX402` are gated by
  `assertCanResumeX402`, which hard-requires `nextAction ===
  retry_original_x402_request`, and nothing emits that value. The route the
  guard actually reads is `GET /machine-payments/:id/status`, mapped by
  `mapPaymentStatusResult` as a plain pass-through with no client-side
  fallback, so it takes the backend's value verbatim — and no backend path
  mints that literal (the member exists only in
  `domain/agent-payment-taxonomy.ts` and an OpenAPI description). The SDK's own
  `executed` → `retry_original_x402_request` mapping lives in
  `nextActionForStatus`, reached only via `paymentStateFromRaw`, which is typed
  to authorize/sign responses rather than this status route. An earlier draft
  of the doc attributed the same conclusion to `GET /payments/:id` and to an
  override mechanism that does not apply to this route — correct verdict,
  fabricated mechanism, caught by `haven-reviewer` and corrected before merge.
  Writing that
  down rather than implying a live loop is the point: the first draft of this
  section called the resume path live and then said two paragraphs later that
  its trigger was unreachable — the same internal contradiction the issue was
  filed about, caught in self-review. The polled lifecycle it narrated
  — `pending` → `approved` → `proposed` → `executed` — is unconstructible:
  `payment_intents.status` has a five-literal write domain and those four were
  `approval_requests` statuses, pinned structurally by the real-Postgres
  `modules/payments/__tests__/status-domain.test.ts` (#2115), which this entry
  cites rather than re-deriving.
  (3) The `next_action: retry_original_x402_request` row in the already-executed
  table named `modules/x402/legacy-authorize.ts` as a live producer; #1987
  deleted that module. The row is **kept and relabelled retired**, because the
  SDK-side guard on the shape (`packages/sdk/src/x402-funding-leg.ts`) is
  deliberately retained fail-closed — the same wire-compatibility call
  #2100/#2101 made for the `pending_approval` branches.
  (4) The `safe_to_continue` field description said `false on pending approval —
  over-budget is a user decision … the settle tool's queued-funding branch`,
  with no rail qualifier. Answered from the code as the issue asked: the value
  **is** still one the contract carries — three `isPendingApproval` branches in
  `packages/mcp-server/src/tools.ts` and the settle tool's `!fundingPending` are
  live, retained fail-closed code (#2101/#2113). What was wrong is the framing,
  not the field, so the sentence is rail-scoped and reframed rather than
  removed: `safe_to_continue: false` is a **decline**, its `next_action` is
  `stop_and_tell_user` and never `wait_for_user_approval`, and an over-budget
  delegation-rail amount never reaches the field because authorize refuses first
  (#2082).
  Also corrected in the same pass, as internal contradictions the above would
  have left standing: the `## Differences From Direct Payments` "Approval
  resume" row (now "Restart recovery"), a sentence naming an
  `approval_requests` INSERT writer that `#2055` deleted with the table — which
  this file's own Guardrails section already records as deleted — and
  `docs/architecture/README.md`'s doc-4 summary row, which advertised "approval
  resume" as a reason to read the doc. Perimeter unchanged.
