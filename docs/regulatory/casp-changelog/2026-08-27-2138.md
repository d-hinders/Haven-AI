- **#2138** — Agent Passport issuance is refused on the retired rails. **This
  NARROWS what Haven attests; it grants nothing, moves no authority, and touches
  no payment path.** Owner decision, 2026-08-27, verbatim: *"we should not
  support issuance on legacy rails."*
  **Why this NARROWS what Haven attests, in the sense that matters here.** A
  passport's L0 claim is that the agent's spending limits are *enforced by the
  chain during the payment*. On the retired AllowanceModule and Smart Sessions
  rails that claim cannot be honoured — every agent payment entry point answers
  410 (#1986, #834), so no spending occurs for a contract to govern — yet
  issuance was never gated by rail, so an agent there could hold a signed,
  anchored, publicly readable credential asserting exactly that. Verified
  reachable rather than assumed: `issuance.ts` branched on rail only to decide
  address derivation, and `passport-issuance.test.ts` explicitly issued a
  passport for `execution_rail: 'allowance_module'`. The receipt's own
  `policyEnforcedOnchain` already reported `false` for those accounts (#2110), so
  the wire was honest while the product prose was not; this closes the gap at
  the issuing end instead of relying on a reader to reconcile the two.
  **Allowlist, not denylist.** An account qualifies on
  `execution_rail = 'delegation'` OR `account_type = 'delegator_hybrid'` — the
  same pair `issuance.ts` already treats as one question when deriving the
  smart-account address, so a hybrid account is not refused on a rail-string
  mismatch. Everything else is refused, including a future rail nobody
  remembers to classify. Fail-closed is the correct direction for a credential
  that attests governance.
  **Existing passports are NOT revoked**, by the same owner decision. The gate
  is on new issuance; `issuePassport`'s idempotent early return sends an
  already-anchored row home before the gate runs. No on-chain action, no
  relayer spend, no attestation retired. The product doc now states this
  explicitly rather than implying a clean sweep, and points a merchant at the
  receipt's `policyEnforcedOnchain: false` — which was always the honest answer
  for those accounts.
  **Money-path surface and why.** `infra/repositories/**` is on the perimeter,
  and two functions there changed: `findAgentChain` returns the rail so the
  route can refuse with a reason, and `listRetryable` excludes ineligible
  accounts. The second is not cosmetic — the retry sweep calls `issuePassport`
  for every non-anchored row each tick, so gating without it would make a
  legacy row fail forever, climbing `attempts` until it tripped
  `ISSUANCE_ATTENTION_ATTEMPTS` and alarmed an operator about a refusal working
  as designed. The revoked-agent exclusion already solves that exact problem
  (#1043 finding 3); this follows that precedent rather than inventing a second
  mechanism.
  **Proven, not reasoned.** Per `money.md` §2 the current behaviour of
  `listRetryable` is characterized BEFORE the change, and per epic #1219 on the
  real-Postgres harness, because the claim is about what a query returns
  (`infra/repositories/__tests__/passport-rail-eligibility.test.ts`). The rule
  exists in two languages — a TypeScript predicate and a SQL fragment, both in
  `domain/passport-issuance-rail.ts` — and nothing in the type system makes them
  agree, so a drift guard asserts they agree across the column's whole CHECK
  domain, read from migration 041 rather than restated, with a non-vacuity
  assertion that the domain contains both an eligible and an ineligible member.
  **Mutation-proven in three directions**, each landed as valid type-checking
  code before its colour was read: drifting the TS predicate, drifting the SQL
  fragment the other way, and removing the gate entirely. Each turns tests red.
  **Two facts verified rather than assumed, both of which changed the design.**
  `user_safes.execution_rail` is NOT NULL with DEFAULT `'allowance_module'` and a
  CHECK of `allowance_module | session_key | delegation`, so null never appears
  in the column — it appears from the LEFT JOIN when an agent has no bound
  account. #2138 called null "the legacy population"; the truer statement is
  that the DEFAULT is the legacy rail. And that default is inert for live
  accounts: the only account-creation path, `POST /accounts/hybrid`, sets both
  markers explicitly (`routes/hybrid-accounts.ts:149-150`), so no live account
  can land on it — only test fixtures had, and they now name the live rail.
  **One existing test was CONVERTED, not deleted.** *"An EOA-only agent still
  binds the absent sentinel"* asserted that a legacy agent still receives a
  passport. That scenario is now unreachable, so the test keeps its setup and
  asserts the refusal — including that **nothing is anchored**, since refusing
  after the chain write would spend relayer gas minting a credential Haven then
  rejects. This leaves the zero-address-sentinel branch in `issuance.ts`
  unreachable through issuance; it is retained as defence, and removing it is a
  separate judgement rather than a consequence smuggled into this change.
  **Not a CASP perimeter change, and this shard should not be read as claiming
  one.** The passport surface is explicitly outside the merchant-acquiring
  scope this changelog tracks (`docs/product/agent-passport.md` § Perimeter):
  it verifies no payment, settles nothing, holds nothing and takes no fee. What
  narrows is the set of accounts Haven will make a governance ASSERTION about —
  an accuracy fix on an attestation, not a change in custody, spend authority or
  regulated activity. Recorded here because the shard convention covers
  money-path diffs and `infra/repositories/**` is on the perimeter, not because
  the change carries regulatory weight of its own.
  No route beyond one added refusal, no schema, no migration, no credential, no
  signing surface and no custody boundary moved. Perimeter unchanged.
