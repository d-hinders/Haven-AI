- **#2095** — two **indexes** were added to `payment_intents` for the erc7710
  settlement path (migration `072_payment_intents_settlement_indexes`): a partial
  expression index `(LOWER(tx_hash)) WHERE tx_hash IS NOT NULL`, serving #2092's
  replay guard, and a partial index `(created_at) WHERE status = 'submitted' AND
  tx_hash IS NULL`, serving #2117's passive settlement sweeper's candidate query.
  **Nothing about the perimeter can move here, and the reason is structural
  rather than argued: an index is not a predicate.** It changes how Postgres
  finds rows, never which rows a `WHERE` clause matches, so every guard on this
  path admits and refuses exactly what it did before — the CAS
  (`status = 'submitted' AND tx_hash IS NULL`), the replay guard (one settlement
  transaction confirms at most one intent), #2096's ambiguity guard and #2094's
  narrowing of it, and the `pg_advisory_xact_lock` on the hash that closes the
  `NOT EXISTS` race. No authority moved, no spend limit changed, no key exists,
  and no fund movement was added, changed or initiated: the diff contains no
  runtime code at all — one migration file, its registration, its test, and this
  shard. **A unique index was deliberately NOT used**, keeping #2095's original
  reasoning: uniqueness on `tx_hash` would retroactively constrain historical
  rows and could turn a legacy duplicate into a hard write failure on a money
  path, so the replay guard stays a query-level `NOT EXISTS` under the advisory
  lock. **Asserted by execution, not by assertion:** the replay guard is driven
  to its refusal twice in the migration's own real-Postgres test — once with the
  indexes present and once with them dropped via `down()` — and the outcome
  (`replayed: false, fresh: true`) must be identical; the #2092/#2094/#2117
  suites (`x402-settlement-observed`, `payment-intents`, `x402-authorizations`,
  `settlement-sweeper`, `erc7710-settlement-evidence`,
  `settlement-child-uniqueness`) were re-run unchanged and stay green. The index
  definitions themselves are mutation-proven: replacing the partial `LOWER()`
  expression with a plain `(tx_hash)` column index produces a named failing test.
  **One operational note, not a perimeter one:** `migrate.ts` wraps every
  migration in a transaction and Postgres refuses `CREATE INDEX CONCURRENTLY`
  inside one (SQLSTATE `25001`), so the build takes a `SHARE` lock on
  `payment_intents` and briefly blocks writes to it — measured at ~6 s on a
  200 000-row harness table. The documented escape needs no code change: build
  both indexes by hand with `CONCURRENTLY` under these exact names, after which
  the migration's `IF NOT EXISTS` is a no-op. Perimeter unchanged: Haven still
  custodies nothing, still signs no settlement, and this change moves no money.
