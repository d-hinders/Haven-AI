- **#2131** — Haven stops instructing agents to gate on an x402 resume trigger
  that nothing emits. **Agent-facing guidance and comments only: no route,
  schema, migration, authority, credential, signing surface or custody boundary
  moves.** No runtime behaviour changes — `assertCanResumeX402`
  (`packages/sdk/src/x402-protocol.ts`), the hosted-MCP gate
  (`packages/mcp-server/src/tools.ts`) and the `AgentPaymentNextAction` enum are
  all retained **unchanged and fail-closed**; the enum member stays because it
  is in two published unions (`@haven_ai/sdk`, `@haven_ai/core`) and removing it
  would be a breaking change for typed consumers.

  **Why a guidance change is worth a shard at all.** `nextAction` is the field
  Haven's own agent contract tells an agent to follow *first*. Ten live
  agent-facing strings told a compliant agent to wait on, or gate on,
  `retry_original_x402_request` — and nothing on any rail emits it. The
  reachability was verified on **both** paths rather than assumed: the backend's
  `paymentIntentState` has five reachable branches plus a fail-closed catch-all
  and never returns it, and the SDK's `executed` → retry mapping
  (`payment-state.ts`) reads a status the backend **cannot construct** —
  `'executed'` appears nowhere in backend production code, having been an
  `approval_requests` status until #2055 dropped that table.

  **Thirteen instruction sites in three categories** — stated as categories with
  their own counts, because a single number has now been wrong three times on this
  issue and the corrections are worth leaving visible rather than overwriting. The
  issue said "five"; a first draft of this shard said "nine" while the PR said
  "ten", and neither folded in the READMEs; then "twelve" under-counted, because
  `sdk/src/tools.ts` holds TWO description strings and was being counted as one
  site. Counted here as STRINGS EDITED, which is what a reader can verify from the
  diff: 10 + 1 + 2. (Guard coverage is per-FILE — three files — which is the "four
  of six sites" language in the commit that added the first guard. Conflating the
  two units is how the arithmetic drifted.) **(A) Ten agent-facing runtime
  strings**, the ones an agent actually reads at run time. **(B) One
  API-contract description** — `openapi/spec.ts`'s x402 authorize operation told
  integrators to "resume once next_action is retry_original_x402_request", and
  that text flows into the generated `@haven_ai/core` types. **(C) Two published
  READMEs** (`packages/sdk`, `packages/mcp`). Within (A) the split matters for
  who was affected. **Seven are tool-description strings across three files**
  (`packages/sdk/src/tool-descriptions.ts` ×4, `packages/sdk/src/tools.ts` ×2,
  `packages/mcp-server/src/tools.ts` ×1 — the original issue counted five and
  missed `sdk/src/tools.ts` entirely). The other three
  are **artifacts handed to an agent at connect time** rather than read by a
  developer: `HAVEN_SKILL_MD` (`packages/sdk/src/skill-content.ts`), the
  dashboard's generic skill bundle
  (`packages/frontend/src/lib/agent-skill-bundle.ts`) and the agent handoff
  (`packages/frontend/src/lib/agent-handoff.ts`). Those three phrase it as a
  **restriction** — "retry the original request *only when* the result says
  `retry_original_x402_request`" — which, with an unsatisfiable condition,
  instructs an agent never to take that branch at all.

  **Four tests required the stale guidance, so it was enforced rather than
  merely un-noticed.** `sdk/src/tool-descriptions.test.ts` asserted the x402 pay
  descriptions *must* contain the literal (on the sound reasoning that an agent
  should branch on a structured field rather than prose — right intent, dead
  anchor); `sdk/src/skill-content.test.ts`,
  `frontend/src/lib/__tests__/agent-skill-bundle.test.ts` and
  `frontend/src/lib/__tests__/agent-handoff.test.ts` each pinned it in a
  token-presence list. The first is rewritten to anchor on the *shape* — a
  structured `nextAction=<value>` is referenced, and every referenced value must
  be a declared taxonomy member — so no single literal's fate is hard-coded
  again. The other three invert to negative assertions, matching the
  `not.toContain('pending_approval')` precedent already in the bundle test.

  **Six new guards, and each later one exists because an earlier one was not
  enough.** A guard over the shared `toolDescriptions` object covers four of the
  six description sites. `haven-reviewer` found the other two by mutation:
  `sdk/src/tools.ts` and `mcp-server/src/tools.ts` build their descriptions as
  hand-written string literals outside that object, and reintroducing the dead
  value into either left both packages fully green. Shipping a fix that defends
  four of six sites — in a change whose entire subject is an advertisement
  nobody caught — would have been the same defect one level up, so each package
  now scans its own ASSEMBLED tool definitions (so a newly registered tool is
  covered without anyone extending a list). All three guards were mutation-proven
  against the exact regression, with the mutation confirmed present on disk
  before its result was read and the restore verified against git.

  Three more followed on re-review: the local `packages/mcp` package has its own
  `toolDescriptions` record — a third description surface, clean today and now
  kept that way — and both published READMEs are guarded, following the
  precedent of `packages/mcp/src/consent.test.ts`, which pins README prose
  because #2086 found that file still showing retired AllowanceModule copy long
  after the renderer had moved on ("Nothing checked it, so nothing said so").
  The SDK README's guard took **three attempts**, and the sequence is the point.
  (i) It pinned two exact sentences; a re-added instruction inside a blockquote
  slipped past, because `\s+` cannot span a `> ` marker. (ii) Rewritten to
  "no line naming the value also says *call*"; `haven-reviewer` defeated that
  twice with prose in the file's own house style — a same-line synonym
  ("invoke"), and the word "call" itself split across an ordinary ~80-column
  wrap. (iii) Inverted: assert a POSITIVE property instead. A count pin over the
  whole file catches any new mention however worded or wrapped, and a framing
  check over whitespace-collapsed prose requires every remaining mention to sit
  in retirement framing.

  Attempts (i) and (ii) both failed *because they claimed to be complete*, so
  (iii) records its own limit rather than repeating that: an instruction
  referring to the value by pronoun adds no occurrence and names nothing, and
  passes — verified, not assumed. That residue is accepted. What bounds it is
  that a reader can only ACT on the value by naming it verbatim, and every
  verbatim mention is now pinned and framed. Each guard names in its own body
  the condition for deleting it (#2145 giving the value a producer).

  **What the replacement text says, and what it deliberately does not.** It does
  not say resume was never intended, and it does not describe the capability as
  removed. The ordinary path never needed resume — the `payX402*` helpers
  perform the merchant retry themselves — so the descriptions now say that, and
  the resume tool's own description states plainly that it is not currently
  reachable and tells an agent to read `get_payment_status` and report rather
  than pay again. The anti-double-pay instruction ("do not start a new merchant
  session") is preserved at every site that carried it.

  **Perimeter: unchanged.** No file in this diff is on the money-path perimeter
  (`.github/money-path-globs.json`), no value moves, and no authority is granted
  or withdrawn. This shard is recorded because the diff edits **agent-facing
  spend guidance on the x402 path** — the surface a CASP reviewer would read to
  understand what an agent is told to do with money — not because the change
  carries regulatory weight of its own. It is an accuracy fix on instructions,
  and stating that plainly is more useful than inflating it.

  **Two stale producer citations corrected in the same pass**, both relabelled
  rather than deleted, because each documents a guard that is retained:
  `packages/sdk/src/x402-funding-leg.ts` named `modules/x402/legacy-authorize.ts`
  as a live producer (deleted by #1987), and `packages/mcp-server/src/tools.ts`
  carried a `#2041` comment stating the backend emits the value for status
  `executed` — true when written, false since #2055. The `#2041` reasoning is
  kept beneath the amendment because it remains true and is the narrower case.

  **The capability gap is tracked, not closed here**
  ([#2145](https://github.com/d-hinders/Haven-AI/issues/2145)). An agent that
  dies between the EIP-3009 funding leg confirming and the merchant retry leaves
  a payment reporting `next_action: none` / *"The payment is confirmed"* while
  value sits on the delegate EOA and the merchant was never paid. The
  `sweep_stranded_funds` override exists but is gated on a reconciliation event
  whose only producer is client-side (`packages/sdk/src/merchant-completion.ts`,
  written when the agent retries and is rejected), so it cannot fire for an
  agent that never came back. That is a correctness defect in the status
  projection and is **not** a Safe-retirement regression: the trigger was only
  ever emitted for the legacy approval queue's `executed`, so crash recovery was
  never covered on the live rail.
