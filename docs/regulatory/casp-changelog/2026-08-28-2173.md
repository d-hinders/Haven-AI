- **#2173** — `packages/connect` gains two additive `ConnectOutcome` fields
  (`hosted_mcp_url`, `superseded_agent_ids`) and persists its terminal outcome
  to `last-connect-outcome.json` in the agent's credential directory. **No
  custody boundary, signing surface, credential, backend route, schema or
  migration moves.** This is setup observability only: the connector emits what
  it already knew and parks a copy of the object it already printed.

  **Authority.** Nothing here creates, widens or relays spend authority. The
  budget delegation, its caveat enforcers and the DelegationManager redemption
  path are untouched; the delegate key is still generated locally and still
  never leaves the machine; Haven still signs nothing on the agent's behalf. A
  caller reading the new record gains no capability it did not have from the
  same object on stdout — it gains only the ability to read it after the stream
  was lost.

  **Custody and secret exposure — the one surface worth arguing.** The new file
  is written inside the existing 0o700 credential directory at 0o600, and its
  content is *exactly* the `ConnectOutcome` already emitted on stdout: the
  writer serializes what it is handed and never reads or embeds
  `identity.json`, `signer.json` or `agent.json`. That object is secret-free by
  construction — no API key, no private key, no full credential path, no full
  delegate address — and the recovery file inherits that property rather than
  asserting it, with tests pinning the API key and the private key absent from
  the written bytes and the credential directory absent from the emitted
  outcome. `hosted_mcp_url` is a non-secret endpoint the connector already
  wrote verbatim into the user's own MCP config file; the API key travels
  beside it in a header, never in the URL, and the value is passed through the
  secret filter regardless. `superseded_agent_ids` are agent identifiers, which
  the connector already printed on stderr under #1688 and which confer nothing
  — revoking a superseded agent remains an owner action in the dashboard.

  **Fail-open direction, deliberately.** The record write is best-effort at the
  call site: a failed write never fails a setup that otherwise completed and
  never changes the verdict the run reached. That is the safe direction here,
  because the artifact is a convenience for a caller that lost its stream, not
  a control — nothing gates on its presence. A refusal that happens before
  credentials exist (`runtime_undetermined`, an expired setup challenge, the
  Node floor) writes nothing at all, so no failure record can appear for a run
  that created nothing.

  **Evidence.** Vitest in `packages/connect/src/{runtime,storage,cli}.test.ts`
  pins the two fields on a completed run, the superseded ids on a re-run
  fixture (excluded by directory rather than agent id, per #1696), byte-equal
  record content with the API key and private key absent, 0o600 permissions,
  the failure record after a post-credential refusal, no record for a
  pre-credential refusal, and a completed setup surviving an injected failing
  writer. `schema_version` stays 1 and every pre-existing outcome contract test
  is untouched and green. Perimeter unchanged.
