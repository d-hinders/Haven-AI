- **#2174** — the `runtime_undetermined` `--json` refusal now carries what the
  #1719 installed-client scan found on the machine (`error.installed_clients`,
  and `error.suggested_runtime` when one candidate is unambiguously top), plus
  the same names in the prose message. **No custody or authority boundary
  moves, and no spend-capable surface is added, widened or reached.**

  **Where this sits in the run.** Before everything. The refusal fires at
  runtime selection — ahead of the setup-token resolve, the storage preflight,
  key generation, the agent registration and every credential write (the #1161
  ordering). At the moment this code runs there is no agent, no API key, no
  delegate key and no unspent setup token to burn, so there is no authority for
  a change here to affect. The `--json` record it decorates is a REFUSAL: the
  outcome stays `failed` with `rerun_connect_with_explicit_runtime`.

  **The one property worth arguing, because it is where a mistake would
  matter.** The scan populates choices and never selects (#1719's property 2).
  A `suggested_runtime` is a hint the agent may echo back as `--runtime`; it
  never causes the connector to proceed. That matters in custody terms rather
  than ergonomic ones: proceeding on a guess would write an API key and a
  delegate key into an agent client the user does not actually run — key
  material placed by inference instead of by instruction. The invariant is
  pinned by test at the point it would be cheapest to break (exactly one
  installed client, where auto-selecting is most tempting): the run still
  refuses, and `resolveSetup`, key generation and the credential write are all
  asserted un-called. A suggestion is additionally withheld whenever "top"
  would be an artefact of the scan's fixed ordering rather than evidence.

  **Disclosure.** The new fields name runtime ids (`codex-cli`, `cursor`, …) —
  not paths, not credentials, not user data. They describe which agent clients
  are installed, which the same machine's own filesystem already states and
  which the interactive prompt has printed to the terminal since #1719; this
  change moves that finding into the machine channel that was discarding it.
  Scan-derived config paths stay in the prompt's `detail` field and never enter
  the JSON record. The read is existence checks only — no file contents are
  opened, nothing is written, and nothing leaves the machine.

  **Failure direction.** Best-effort and fail-quiet: a scan that throws
  degrades to the un-hinted refusal, so a permission error on a home directory
  cannot replace a precise, actionable refusal with a filesystem error, and the
  thrown detail cannot leak into the record (pinned by test). Absence rather
  than an empty array represents both "found none" and "could not run", so the
  record never asserts a finding it did not make.

  **Evidence.** Vitest in `packages/connect/src/{installed-clients,runtime,cli}.test.ts`
  covers the hint's tie/clear-winner rules, the still-a-refusal invariant, the
  prose mirror, both degrade paths, the unchanged
  `runtime_force_unrecognized` shape, and the serialized `--json` record.
  `schema_version` stays 1 and every pre-existing contract test is untouched
  and green. Perimeter unchanged.
