- **#2175** — an investigation issue, resolved as two compounding defects in the
  agent-retirement *bookkeeping* path: the `haven-reset` skill told an agent to
  build the tombstone path from an AGENT ID (wrong for slug-named directories,
  #1696), and `--tombstone --json` wrote its refusal to stderr only, leaving
  stdout empty so the caller could not tell a refused retirement from an
  unread stream. **No custody or authority boundary moves, in either
  direction, and none could: a tombstone touches no key material, revokes
  nothing, signs nothing and moves no funds.**

  **Why this is bookkeeping and not authority.** `writeAgentTombstone` replaces
  a directory's `bin/haven-signer.mjs` with a self-contained diagnostic script
  and writes `TOMBSTONE.json` plus its mirror. `identity.json` and `signer.json`
  are left byte-for-byte as found — the #1688 rule that connect reports and the
  user revokes is unchanged and is re-asserted by the existing test that reads
  the API key back out of `identity.json` after a retirement. Revocation
  remains an owner action on the Haven agent page; a tombstone is a marker that
  a stale host is spawning a retired path, never a capability change.

  **What the fix changes, precisely.** (1) The refusal for a non-existent
  directory becomes a typed `ConnectError` (`tombstone_directory_not_found`)
  whose message names the slug-vs-id trap. (2) Under `--json` that refusal is
  additionally emitted on stdout as
  `{"tombstoned": false, "error": {code, next_action, message}}`, redacted by
  the same `redactSecrets` filter as the success record and the stderr prose,
  and the exit code stays 1. Nothing is written to disk on this path — the
  guard that produces it runs *before* any write, which is the property that
  made a mistyped path safe to begin with (#1681 review).

  **Disclosure.** The failure record carries the refused path, which is the
  path the caller itself supplied and which already appeared on stderr. No
  credential contents, no key material, and no agent API key enter it; the
  existing CLI tombstone tests assert the API key is absent from output, and
  the new failure-path test asserts the record's shape rather than echoing
  secrets. The skill change adds no command that touches key material — it
  adds a verification gate *before* the existing deletion step, which is
  strictly safer than the order it replaces.

  **The narrowing stated rather than glossed.** The same stderr-only failure
  shape remains in `--rekey`, `--doctor` and `--unwire`; measured (3 of 6 CLI
  catch blocks remain so after this fix) and deliberately left, because this issue's evidence covers
  the tombstone path only and widening the change would alter three more
  contracts without field evidence. Tracked as [#2184](https://github.com/d-hinders/Haven-AI/issues/2184).

  **Evidence.** Reproduced end to end against a two-agent fixture (one
  uuid-named, one slug-named): the skill's command exits 1 with 0 bytes on
  stdout before the fix and a parseable failure record after it. Vitest in
  `packages/connect/src/{tombstone,cli}.test.ts` pins the typed code, the
  slug-vs-id message and the stdout record; reverting either fix turns tests
  red. Perimeter unchanged.
