- **#2179** — test-only change: connect's Hermes-path suites now isolate the
  real `HERMES_HOME` before running. `packages/connect/src/test-helpers.ts`
  adds `isolateHermesHome()` / `restoreHermesHome()` (save/clear/restore
  `process.env.HERMES_HOME`), wired via vitest hooks into the three Hermes-path
  suites (`config-writers.test.ts`, `runtime-install.test.ts`, `unwire.test.ts`)
  so a developer running the connect suite from inside a Hermes gateway shell no
  longer writes test config into the live `~/.hermes` — a bogus `haven` /
  `haven-signer` MCP pair and a `MCP_HAVEN_API_KEY` line used to land in the
  real `config.yaml` + `.env`. **No custody or authority boundary moves, and no
  spend-capable surface is added, widened or reached.** The diff touches zero
  production source: no key material is created, read, printed or transferred;
  the writers under test still write only to the state the fixture home points
  at; nothing revokes or signs on the backend. The runtime-selection ladder,
  the Supported Runtime Manifest, the Node floor, the failure vocabulary and
  every credential-safety boundary this document governs are untouched — the
  change is confined to which home directory a few tests look at. The dangerous
  condition this fixes is itself an environment leak, not a code path: with
  `HERMES_HOME` unset (CI parity) the suites behave exactly as before, and the
  fix is pinned by the two-direction validation in the PR body (byte-identical
  `~/.hermes` hashes with the env set, 417-passed suite with it unset).
  Perimeter unchanged.
