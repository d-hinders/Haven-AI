- **#2184** — the `--json` failure record #2175 gave `--tombstone` is extended
  to the three remaining subcommands (`--unwire`, `--rekey`,
  `--doctor`/`--repair`) through one shared `failSubcommand` helper in
  `packages/connect/src/cli.ts`. **No custody or authority boundary moves, and
  no behaviour changes on any success path.** This is failure *reporting*: what
  a caller can observe about a command that already failed, on the channel
  automation reads.

  **Why it is not authority.** Nothing here signs, spends, revokes or moves
  funds, and nothing changes what any subcommand *does* — only what it says
  when it has already thrown. Exit codes are unchanged, stderr prose is
  unchanged, and every success payload is byte-identical (pinned: the whole
  pre-existing connect suite is untouched and green). `--rekey`'s underlying
  rotation, the one flow here with real spend-authority consequences, is not
  touched at all; the change is that a caller can now *see* that a rotation
  phase failed rather than reading an empty stdout and inferring success.

  **Disclosure, the one surface worth arguing.** Each record carries a stable
  `code` and `next_action`, and `message` **only** for a connector-authored
  `ConnectError` — the same gate `failedConnectOutcome` applies and the one
  #2175 introduced for `--tombstone`, now inherited rather than re-decided per
  branch. That gate is load-bearing here in a way it was not for tombstone:
  `rekey.ts` throws several bare `Error`s whose messages embed **agent ids and
  credential directory paths** (e.g. "the pending re-key at &lt;dir&gt; belongs to
  agent &lt;id&gt;"). Those stay on stderr, where they always were, and never enter
  the machine channel. Pinned by a test that drives `--rekey` into a bare-Error
  failure and asserts `message` is absent while stderr is non-empty.

  **A misread this record exists to prevent.** Each envelope inverts its own
  branch's success discriminant (`{unwired: false}`, `{rekey: 'failed'}`,
  `{doctor: 'failed'}`) rather than sharing one generic shape, because two
  branches would otherwise be ambiguous: `--doctor`'s SUCCESS output is a JSON
  report, and `--unwire` emits `{unwired: true}` with a **non-zero exit** when
  some runtime entries were refused — a partial result, not a failure. A
  generic `{ok: false}` envelope would have made a refused-entry run and a
  thrown run indistinguishable. Mutation-proven: flipping either envelope to
  its success value turns exactly one test red.

  **Scope, stated rather than assumed.** The issue's file list allowed typing
  bare `Error`s in `{rekey,unwire,doctor}.ts` "where warranted". On inspection
  none was: the single best candidate (`rekey.ts`'s missing-`--api-key` guard)
  is **unreachable from the CLI** — `args.ts` refuses the same condition at
  parse time, and `finishRekey` is not exported — so typing it would have been
  a change with no reachable caller. Reverted after verifying, and the
  parse-path behaviour is pinned instead so the ordering is not misread later.

  **Evidence.** Re-measured before and after: 6 catch blocks, 3 stdout-silent
  before, **0 after**. Vitest in `packages/connect/src/cli.test.ts` pins each
  branch's record, the bare-Error message withholding, and the doctor
  report-vs-failure distinction. Perimeter unchanged.
