- **#2150** — the migration runner gains a per-migration opt-out from its
  `BEGIN`/`COMMIT` wrapper, so a migration can run `CREATE INDEX CONCURRENTLY`
  and the other statements Postgres forbids inside a transaction block
  (SQLSTATE `25001`). **No custody or authority boundary moves, no money-path
  behaviour changes, and no migration in `db/migrations/` uses the opt-out
  yet** — this change adds a capability and its safety rails, nothing else.
  The default lane is byte-for-byte the old one.

  **Why a schema-tooling change is logged here at all.** `db/migrations/**` is
  inside the money-path perimeter (`.github/money-path-globs.json`) and behind
  the `CODEOWNERS` hard gate, because an irreversible schema change against
  `payment_intents` is one of the few things in this system that cannot be
  undone by redeploying. This change alters what a *failed* migration can
  leave behind, which is exactly the property that gate exists to protect. It
  therefore deserves the record even though nothing it touches moves funds.

  **What is given up, stated as a loss rather than a feature.** In the default
  lane the `schema_migrations` row is written inside the same transaction as
  the work, so a failure rolls back both and the next boot retries against an
  untouched schema — a failed migration is a non-event. A migration that
  declares `transactional = false` gives that up permanently: its statements
  commit as they go, and a failure halfway leaves the schema partially changed
  with no way for the runner to undo it. That is not mitigated away here. It
  is accepted, narrowly, because the alternative it replaces is worse: PR
  #2149 had to take a measured ~6.0 s write-blocking `SHARE` lock on the live
  `payment_intents` table because a lock-free index build was impossible at
  any price.

  **What compensates is detection, not prevention.** The runner writes the
  bookkeeping row `status = 'running'` *before* `up()` and promotes it to
  `'applied'` only after it returns. A crash therefore leaves a row that says,
  precisely, "this migration was interrupted" — and the next boot **refuses to
  start**, printing the version, the declared reason, and the two recovery
  statements (mark applied, or delete and re-run). The two naive designs were
  both rejected for being silent: recording after `up()` lets the next boot
  re-run a half-applied migration blind, and recording before it lets a
  half-applied migration be skipped forever. A backend that will not boot is a
  worse morning and a better outcome than a production schema nobody can
  describe.

  **The index case is handled specifically, because its silent failure is the
  dangerous one.** A failed `CREATE INDEX CONCURRENTLY` leaves the index in
  place marked `indisvalid = false`; a plain `IF NOT EXISTS` retry then sees
  the name taken, reports success, and the database carries an index the
  planner will never use — indefinitely, looking exactly like a green deploy.
  `createIndexConcurrently()` drops an INVALID index before rebuilding and
  re-checks validity afterwards, failing the migration rather than recording a
  dud as applied.

  **Perimeter unchanged.** No route, rail, signer, allowance or delegation
  surface is touched; no migration is added, removed or renumbered; the
  `db/migrations/` CODEOWNERS gate and the `qa-freshness` promotion gate are
  untouched. The opt-out is opt-in by construction — absence means
  transactional, and a migration declaring `transactional = false` without a
  written reason does not compile.

  **Evidence.** `packages/backend/src/db/__tests__/migrate-non-transactional.test.ts`,
  11 tests on the real-Postgres harness (no mocks — a fake `pg` client cannot
  raise `25001`, cannot leave an INVALID index, and cannot fail to roll back).
  The load-bearing pair drives the *same* `CREATE INDEX CONCURRENTLY` through
  the real runner twice: it succeeds with the opt-out and still fails with
  SQLSTATE `25001` without it. The default lane's rollback is proven by
  execution (work and bookkeeping both absent after a mid-`up()` throw) with a
  positive control. Five mutations, each producing a named red: reverting the
  opt-out, running *everything* non-transactionally, recording `'applied'`
  before `up()`, treating a crashed partial as applied, and dropping the
  helper's drop-if-invalid step.
