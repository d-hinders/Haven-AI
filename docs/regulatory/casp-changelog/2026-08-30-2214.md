  **The observation, and its correction.** @PhilipEriksson raised on PR #2134 —
  confirmed by execution under #2136 — that
  `FIND_SWEEPABLE_ERC7710_INTENTS_SQL`'s `delegation_hash IS NOT NULL` sits in
  SQL, upstream of `sweepOne`. A row it drops is therefore neither completed NOR
  counted in `unresolved` NOR logged, missing both halves of the module's stated
  design ("complete what can be attributed, and log the rest loudly as it ages
  out"). That reading of the code is exactly right. The population it names,
  however, cannot be constructed: the sole production writer of
  `machine_metadata->>'settlement_scheme' = 'erc7710'` is
  `modules/x402/delegation-authorize.ts`, and it passes
  `delegationHash: built.childHash` two lines below `settlement_scheme:
  'erc7710'` in the SAME `insertMachineIntent` call — one INSERT, both columns —
  and has done so since #830 introduced the erc7710 path (852a9034, 2026-07-10),
  not since #2094 (f7d26642, 2026-08-27). No UPDATE writes `machine_metadata`
  and none nulls `delegation_hash`. So the conjunct is defence in depth over an
  empty set. What #2094 changed is the child's SALT: a pre-#2094 intent carries
  the old constant-salt hash, IS a candidate, IS scanned, and IS counted and
  logged — appearing as documented residual gap 2 when a look-alike twin makes
  it unattributable. The `delegation_hash IS NULL` rows that do exist —
  pre-#2094 payments confirmed by agent report whose evidence write then failed
  — are already covered by #2213's recovery query, which deliberately omits the
  conjunct and asserts that omission.
  **Why no counter, census or residue bucket was built.** The issue's own option
  1 was "document and count it" and its option 2 was "bound the population
  first". Bounding it returns *unconstructible*, not merely empty, so a counter
  would report zero on every environment forever — an elaborate mechanism for
  zero rows, and one more number an operator must learn to ignore. Option 3, a
  shape-verified fallback gated behind `delegation_hash IS NULL`, was NOT taken
  and is explicitly rejected: it would reintroduce exactly the ambiguity #2094
  and #2135 exist to refuse, and on an accounting feed a confidently
  misattributed row is worse than a missing one. `requireDelegationBound` stays
  and there is still no transfer-shape fallback behind it.
  **What was built instead: the invariant, checked from both directions.** A
  real-DB positive control drives the PRODUCTION writer (`insertMachineIntent`
  with delegation-authorize's own argument object) and asserts its row IS
  returned by the candidate query; and a source scan asserts that every
  non-comment writer of `settlement_scheme: 'erc7710'` sits inside an intent
  insert that also sets `delegationHash`. The second is the one that catches the
  real regression: `delegationHash` is OPTIONAL on `NewMachineIntent`, so a
  second writer omitting it would break no type, fail no query, and silently
  drop settled payments out of both halves of the sweep. The scan carries its
  own positive control (`writers.length > 0`), so a walk that matches nothing
  cannot pass vacuously.
  **An overstatement corrected, in the same direction PR #2220 corrected one.**
  The residue warning read "it will not reach the accounting feed", full stop.
  It is the SWEEP that is stuck, not the payment: the agent-reported path
  (`POST /machine-payments/evidence`) runs the same on-chain verifier with
  `requireDelegationBound` OFF, so it needs no DelegationManager log (residual
  gap 1) and is not bounded by the 24-hour recovery horizon (gap 3). The warn
  now carries a `remedy` field naming that route. This is a reporting change
  only — the verifier, the CAS, the replay guard and the ambiguity guard are
  untouched, and residual gap 2 (two indistinguishable payments) still requires
  a human decision before anything can be attributed, which the doc says.
  **Five mutations, five kills**, each confirmed landed against `git diff`
  before its colour was read and each restored with `git checkout HEAD --` and
  verified by `git diff --exit-code`: dropping `delegation_hash` from the
  repository INSERT; deleting `delegationHash` from the authorize call; renaming
  the `'erc7710'` literal so the scan finds zero writers (the always-reports-zero
  control, which failed on its own named message rather than passing vacuously);
  removing the `remedy` field from the log; and removing the
  `delegation_hash IS NOT NULL` conjunct itself.
