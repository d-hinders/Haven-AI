The perimeter classification comes from both halves — the issue carries `money-path`, and `packages/signer/` is a money-path glob (`.github/money-path-globs.json`, #1896) — but the diff is a comment-only change in a listed file with review-confirmed zero behavioural delta. What the change corrects is the code's **account** of a guard, not the guard: the comment claimed funds may leave "only to its own Safe", which is unconditionally false for the destination half. `expectedSafe` is threaded from `options.audit?.safeAddress` and therefore from the local credential's `safe_address`, absent in three reachable, supported configurations — `HAVEN_DELEGATE_KEY` set without `HAVEN_SAFE_ADDRESS` (the README quickstart, where `loadSignerCredentials` DOES run and simply returns no account address), a credential recording no account address (`safe_address: string | null`, `packages/connect/src/api.ts:151`), and an embedder calling `resolveEdgeSigner({ delegateKey })`, whose fast path returns before credentials are read at all. Note for anyone reading #2247's body as the record: the issue attributes the CLI case to that fast path, and that attribution is wrong. `cli.ts` never sets `options.delegateKey`, so the documented env-var invocation does not take the fast path at all — the gap there is an unset `HAVEN_SAFE_ADDRESS`, not an unread credential.
