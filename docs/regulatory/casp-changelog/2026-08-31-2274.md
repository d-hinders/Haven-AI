- **#2274** — Moves the retired-rail **HTTP 410 gate ABOVE token and amount resolution** on both agent payment entry points, `POST /payments` (`routes/payments.ts`) and `POST /x402/authorize` (`modules/x402/authorize.ts`). **Perimeter unchanged** — no new authority, no new custody relationship, no route added or removed, no signing scheme, no migration, no funds moved. Both the old outcome and the new one are **refusals** of the same request; what changes is which refusal a doomed request receives, and therefore what a retired-rail account is told before it is told the rail is gone. Recorded here rather than absorbed because it is an ordering change on two money-path files inside epic #1440's retirement, and the coupling gate correctly implicates the two contract docs.

  **What the routes actually did, measured on `origin/dev@4a1f1314` rather than inferred.** On both routes token resolution ran above the rail seam. A retired-rail account (`execution_rail='allowance_module'`, the LEFT-JOIN `null` most of that population carries, or an unrecognised value) naming an asset the chain registry does not know received, verbatim: `400 {"error":"Unsupported token: NOTATOKEN","supported":["ETH","USDC"]}` from `POST /payments`, and `400 {"error":"Unsupported token asset: 0x…deadbeef","supported":[{"symbol":"ETH",…},{"symbol":"USDC",…}]}` from `POST /x402/authorize` — a list of the assets it can pay with, ahead of the 410 saying it can pay with none of them. `POST /payments` disclosed the same thing one step later through `parseTokenAmount`: an unparseable amount for a real token returned `400 {"error":"Invalid amount for USDC"}`, a refusal phrased in terms of a token the account cannot spend. Money-safe throughout, and this record does not claim otherwise: nothing was read on-chain and nothing written on either path, before or after.

  **Why it is a disclosure defect and not a rail defect.** The residue is rail-INDEPENDENT — it asserts nothing false about any rail, which is precisely why #2245 removed the rail-DEPENDENT guard above the same seam and filed this separately instead of folding it in. It is the same class as the 401 auth hook that legitimately precedes the 410. Fixed on **both routes together**: a one-route fix would have recreated the asymmetry #2245 removed, and is the failure mode #1892 documented, where a perimeter list read as though it knew about a route it did not cover.

  **The bound, stated because "410 for every input shape" is the wrong reading of the fix.** Structural, rail-independent request validation still precedes the gate on both routes — required fields, address and network shape, the `settlementScheme` enum, the numeric form of `amount`. A malformed request is not a request about a rail, and answering 410 to one would make the tombstone the route's error handler. That bound is asserted, not assumed.

  **Mutation-proven in both directions, per the acceptance criteria.** Seven new assertions in `routes/__tests__/allowance-rail-retired.test.ts` § *the 410 precedes TOKEN RESOLUTION too (#2274)*, run against the real handler through `app.inject`. (A) **Reproduction first**: on unmodified `dev` ordering the suite is **7 failed / 4 passed**, each failure naming the exact 400 body the route returned — the four that already passed are the bound and the positive controls, which is what makes the seven meaningful. (B) Restoring the pre-#2274 ordering on **both** routes from a `cp` backup turns those **7** red again. (C) Restoring it on **`POST /payments` only** — the half-fix this issue exists to prevent — turns **4** red, so the symmetry is enforced rather than merely intended. (D) The **over-410 direction**: `resolveExecutionRail` mutated to refuse every rail turns the two new POSITIVE CONTROLS red by name, so the fix cannot be satisfied by 410-ing everything. (E) The **structural bound**: the gate mutated to sit above step-1 validation turns the structural-precedence assertion red by name. Every production file was restored from a `cp` backup and verified byte-identical with `diff -q`, never by inverting the edit; `git status` confirms `rails/execution-rail.ts` carries no diff at all. Pass/fail was taken from the runner's **process exit code**, not from grepping its output.

  **Positive controls, because a guard that can only say no proves nothing.** A DELEGATION-rail account naming an unsupported token still receives its `400` **with** the `supported` list on both routes, green in the same run — the list is correct information for an account that can actually spend; the defect was disclosing it to one that cannot. The pre-existing delegation-rail positive control (`POST /payments` still returns signable `sign_data`) is green throughout, as are the 401-precedes-410 and both-tombstones-coexist assertions: the session rail keeps its own distinct #834 message.

  **Cost of the reordering, stated.** `POST /payments` now issues its one indexed `FIND_EXECUTION_RAIL_FOR_AGENT_SQL` lookup before token resolution, so a request naming an unsupported token costs one extra read that it previously avoided. No chain call moves, no write moves, and the fail-closed contract is unchanged: nothing is written on the way to either refusal, asserted against the real query log.

  Perimeter unchanged; the retirement's fail-closed contract is strengthened from "410 for a well-formed request" to "410 for every request the route can parse", symmetrically on both agent payment entry points.
