- **#2282** — An ordering correction on the hosted x402 settle path: a control
  that ran, answered correctly, and ran **after** the money movement it would
  have refused. `haven_settle_mcp_tool` resolved the merchant-call context
  inside the merchant-delivery helper, i.e. after `POST /payments/:id/sign` had
  relayed the funding userop. Intents created by `haven_pay_x402_quote` carry no
  stored context — that entry point receives only the raw HTTP 402, and an x402
  `PaymentRequired` carries a resource URL but no MCP tool name and no
  arguments — so a quote-first settle funded on-chain and only then answered
  `MERCHANT_CALL_CONTEXT_UNAVAILABLE`, stranding the caller in
  `funded_but_unsettled`. Reported from a real dev run on Base Sepolia (agent
  `577dcd3f`), recovered by the reporter through `haven_complete_mcp_tool` with
  explicit context; test USDC only, nothing lost.
  **What changed:** the context is resolved before either submit — the funding
  relay on the EIP-3009 bridge and `POST /x402/:id/settle` on erc7710 — and the
  single resolved value is threaded into delivery, so the resolve is not
  duplicated. The identical refusal now lands while the intent is still
  `pending_signature` with nothing spent, and the caller retries the same tool
  with explicit context and settles. Storing a context at
  `haven_pay_x402_quote` time was considered and rejected: that tool has no tool
  name or arguments to store, so an optional accept-and-store would leave every
  caller who omitted them in the state being removed.
  **Second half:** a wrong-shaped `mcp_transport` is refused rather than
  dropped. The tool schema is `.strict()` — matching the
  `additionalProperties: false` it already advertised, which a bare `z.object`
  silently contradicted by stripping — and its required-key message names the
  snake_case (hosted tool) vs camelCase (SDK / `POST /x402/authorize`)
  mismatch. Behind it, the internal transport parser throws on a
  present-but-unrecognised transport instead of returning `undefined`, which is
  the same value "no transport supplied" produces; absent and
  `handshake_required: false` keep their existing meaning.
  **Custody, authority and perimeter unchanged.** No signing scheme, delegation,
  caveat, budget, route, rail or refusal code moves; no key material and no
  header content is added to any error. The change is strictly
  refusal-ordering and input validation in `packages/mcp-server/src/tools.ts`,
  which is not on the money-path glob list — the `money-path` label comes from
  the issue.
  **Mutation-proven:** reverting the ordering produces four named reds
  (`does NOT relay funding when a quote-first intent has no stored merchant
  context`, the explicit-context-retry control, the erc7710 twin, and the
  stored-transport guard); restoring the permissive schema and the silent drop
  produces five, including the protocol-boundary refusal in `server.test.ts`;
  restoring the silent drop on an unrecognised transport `source` — the one
  branch independent review found unproven — produces a sixth. Each restore
  verified with `git diff --exit-code` against the committed fix.
