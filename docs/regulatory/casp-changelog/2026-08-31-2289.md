- **#2289** — the SDK's merchant retry now sets both x402 payment header names,
  `PAYMENT-SIGNATURE` (v2) and `X-PAYMENT` (v1), to the same value; previously it
  sent only the v1 name, so a strict v2 merchant never received the header. The
  change is to the **name of an HTTP header**, not to its contents: the EIP-3009
  authorization it carries — payer, payee, amount, nonce, and validity window —
  is byte-identical, is still produced by the delegate key inside the local
  signer, and is still bound by the Haven-signed expected context that
  `assertExpectedBinding` verifies before anything is signed. No new route, no
  new authority, no change to what an API credential can do, and no custody
  change: Haven still never holds the delegate key and still cannot construct or
  alter the authorization. The single outbound site is
  `McpMerchantTransport.deliverPayment`; the backend only assembles header values
  and never transmits them, so the perimeter of code that can reach a merchant is
  unchanged in extent. Both names are set with `set`, not `append`, so a stale
  header on a caller's request is replaced rather than presented alongside the
  live one — a merchant reading the first of two values cannot be shown a
  superseded authorization. Risk moves downward, not up: on the EIP-3009 bridge
  the funding leg had already moved user funds to the delegate EOA before the
  merchant leg failed, so the defect's live consequence was user funds debited
  against undelivered goods, with the residue stranded below the sweep floor.
  Mutation-proven in `packages/sdk/src/x402-payment-header-name.test.ts`: a
  fixture merchant reading only `PAYMENT-SIGNATURE` returns 402 against the
  pre-change code and 200 after, while a four-assertion characterization block
  pins the legacy name, the stale-header overwrite, and body/header pass-through
  so v1 and lenient merchants are provably unaffected. Perimeter unchanged.
