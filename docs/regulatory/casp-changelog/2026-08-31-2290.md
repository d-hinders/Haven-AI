- **#2290** — **a deliberate widening on the read side of the x402 signing
  handoff, argued below rather than glossed.** `GET /x402/:id/sign-context`
  previously refused every `confirmed` intent with `409 already_executed`. It
  now serves a rebuilt signing context for exactly one confirmed state: an
  eip3009 x402 intent whose FUNDING leg confirmed, whose merchant leg was never
  reported, whose client-reported rejection event is absent, and whose
  merchant-report grace window has elapsed. Every other confirmed intent —
  erc7710 (where `confirmed` IS settlement), a reported merchant leg, a
  rejected retry, an intent inside the grace window, an intent with no
  `settlement_scheme` metadata, and an unreadable derived row — still receives
  the same 409, and a PENDING intent past its quote window still receives 410.
  **What this widens is who may FETCH a context; it does not change what the
  signer will sign without one.** `assertExpectedBinding` and the signer's
  typed-data digest re-derivation are byte-for-byte untouched, the binding is
  still minted only by Haven and verified against Haven's key, and no binding
  can be constructed client-side.
  **Why this cannot move money that was not already moving.** #2145 taught the
  status endpoint to answer `retry_original_x402_request` for this state and
  left every route that could rebuild the merchant header shut, so the remedy
  Haven published was unreachable and 0.01 USDC of a live Base-mainnet purchase
  sat undeliverable on a delegate EOA. The funding UserOperation for such an
  intent is already submitted and confirmed on-chain; Haven refuses a second
  submit, and this path writes nothing — no intent row, no status transition,
  no reconciliation or evidence row. So re-serving the context cannot re-fund
  and cannot initiate a transfer from the user's account. The value it exposes
  is the delegate EOA's EXISTING balance, whose only intended destination is
  the merchant that was already paid for. The alternative to delivering it is
  not safety; it is the funds staying stranded, recoverable only by sweep.
  **The one field that is not merely re-served, stated plainly.** For this
  state and only this state, `expires_at` in the freshly Haven-signed expected
  context is minted fresh (a 10-minute window, matching the intent insert's own
  `interval '10 minutes'`) instead of being re-served from the stored row. The
  stored value is the QUOTE window: it bounded signing the FUNDING leg, which
  has happened. Re-serving it would hand the signer a context its own
  `assertX402PaymentWindowOpen` (`packages/signer/src/core.ts`) refuses, so the
  rebuild would be inert for precisely the payments this path exists to rescue.
  The merchant-side EIP-3009 validity window is a separate clock the signer
  derives at signing time and is unaffected. Reachability of the fresh window
  is bounded by construction: `rebuildDelegationSignContext` has three callers,
  the option defaults off, and only the new gate passes it — the #961
  idempotent replay and the ordinary pending-signature fetch are unchanged. The
  binding still pins `payment_id`, atomic amount, payee, asset, network and the
  typed-data digest, so a longer window widens WHEN that one header may be
  signed and nothing about WHAT it authorises.
  **The remedy and the permission to act on it are now one predicate.**
  `isFundedX402AwaitingMerchantLeg` is exported from
  `modules/payments/agent-payment-status.ts` and called by both the status
  answer and the route gate, over the same derived row
  (`FIND_INTENT_STATUS_ROW_SQL`, whose `funded_but_unsettled` and
  `merchant_leg_reported` are joins over reconciliation events and evidence,
  not columns). A biconditional test on real Postgres asserts the predicate is
  true exactly when the status endpoint answers `retry_original_x402_request`,
  across nine seeded evidence states, so the two cannot drift into a published
  remedy nothing can serve. `!funded_but_unsettled` is load-bearing: a merchant
  that was asked and refused keeps the `sweep_stranded_funds` remedy and is
  never handed a fresh header to ask again with.
  **Mutation-proved, four mutations and four kills, each restore verified
  against the working tree.** Forcing the gate false fails the four positive
  tests while all seven refusal tests still pass; reverting the fresh window to
  the stored value fails the window test alone; dropping `!funded_but_unsettled`
  from the predicate fails the two rejection-agreement cases, the explicit
  sweep-direction case, and the route's rejected-retry refusal; and removing the
  `!fundedMerchantRetry` conjunct from the already-executed refusal fails the
  no-stored-payload case that guard protects.
  **The signer half is proved on its own side, with the stale window as its
  control.** The backend's assertion that a future `expires_at` reaches the wire
  cannot show that minting it fresh was necessary, because nothing in the
  backend consumes the value. `packages/signer/src/x402-funded-retry-window.test.ts`
  drives a funded-retry-shaped v2 context through `haven_sign_x402` to a real
  merchant header, asserts the merchant's own `extra` domain is what the signer
  selects, and then submits the byte-identical context carrying the window the
  stored row would have supplied — refused for the window, not the binding. No
  funding submit occurs anywhere in that flow. Backend suite 2812 passed / 8
  skipped, signer 177, mcp-server 305, sdk 369; full `npm run quality`
  (typecheck + unit + build, all packages) exit 0.
  Haven still custodies nothing, still holds no user key, still signs no
  settlement, and no spend limit, delegation, caveat enforcer or signing scheme
  is touched by this change. Perimeter unchanged; an unreachable published
  remedy became reachable.
