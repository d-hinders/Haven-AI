- **#2291** — **agent-facing guidance and one refusal message; no authority,
  no signing scheme, and no custody boundary moves.** Haven's own structured
  guidance named a sequence its tools cannot execute:
  `haven_pay_x402_quote` emitted `next_tool: haven_sign_x402` while the same
  response's `reason` said to finish with `haven_x402_sign_header`.
  `haven_sign_x402` is a one-shot that calls `buildX402PaymentHeader`
  internally, and that function consumes the `x402_binding` on every exit path
  — so the binding it hands back is already spent and the named successor could
  only refuse. This change picks the contract the tool already implements (the
  one-shot's inline `payment_header` is the header to retry with) and makes the
  structured `reason`, `PAY_X402_QUOTE_DESCRIPTION`, `RESUME_X402_DESCRIPTION`,
  both signer tool descriptions and the skill content say that one thing.
  **What is deliberately NOT changed.** The single-use property of a binding is
  untouched — bindings are still consumed on every exit path, and the
  decomposed `haven_sign` → `haven_submit` → `haven_x402_sign_header` flow
  still works because `haven_sign` never consumed one; both are pinned by their
  own tests. `assertExpectedBinding`, `assertX402MatchesExpected`, the
  typed-data digest re-derivation and `assertX402PaymentWindowOpen` are
  byte-for-byte unmodified. No binding can be minted client-side, no route
  gains or loses authority, no delegation, caveat enforcer, budget or spend
  limit is touched, and no code path here moves, holds or initiates the movement
  of funds. The signer still holds the only key and Haven still never sees it.
  **The one behavioural change, and why it retains nothing new.**
  `buildX402PaymentHeader` now distinguishes THREE outcomes where it had one
  message: a binding spent building a header, a binding retired because its
  payment window closed first, and an id the signer never held. Each names its
  own remedy — use the header you already have; re-quote for a fresh window
  (no header was ever built); sign first, or the signer restarted. The single
  message is what sent the reporter hunting a lookup bug that did not exist.
  Implemented as a bounded `Map` from retired binding **id** to a two-value
  reason: the `X402ExpectedPayment` is still deleted from the live map exactly
  as before, so the payment context Haven's data-retention comment protects is
  not kept a moment longer. A retired id is an opaque UUID carrying no payer,
  merchant, amount or asset, and the reason is an enum, not payment data. The
  map is capped at 64 and drops oldest-first, which degrades a stale re-use to
  the unknown-binding message rather than to a wrong one — the fail-safe
  direction, since the unknown-binding remedy (re-sign) is valid in every
  situation while the other two are not.
  **The window-expired case exists because review found the first version
  lying.** A single spent/unknown split marked the window-check path as spent
  too, so a client retrying after PAYMENT_WINDOW_EXPIRED was told to "retry the
  merchant with THAT header" when the window had closed before any header was
  built and none existed. A confident wrong remedy is worse than the vague one
  it replaced; the third outcome is that finding, fixed and pinned by its own
  test.
  **A correction to #2290, recorded rather than reflowed.** #2290's
  `RESUME_X402_DESCRIPTION` replaced one impossible order with the other,
  instructing agents to pass the one-shot's binding to
  `haven_x402_sign_header`. That is the same contradiction this issue is about,
  written into the same file a second time within a day. It is corrected here
  and both passes are named in the code comment, because a defect that recurs
  in one file is evidence about the file, not about either author.
  **Mutation-proved, five mutations and five kills, three of which changed the
  change.** Collapsing the spent/unknown distinction fails three tests;
  removing the `!fundedMerchantRetry`-style spent bookkeeping on the v2 path
  fails the v2 single-use pin. The other two are the ones worth recording,
  because each exposed a guard that did not guard: restoring the contradictory
  `reason` verbatim passed the entire suite, since the new chain-walk test
  proves the emitted chain EXECUTES and never reads the prose beside it — a
  literal `reason` guard now covers it; and deleting the v2 binding-consume
  passed the whole signer package, whose x402 fixtures are `x402Version: 1`, so
  single-use had only ever been asserted on the v1 branch while production
  takes the v2 one. Coverage of that property no longer depends on a
  cross-package integration test. The fifth came from review: reverting
  `RESUME_X402_DESCRIPTION` to its #2290 wording had been caught by nothing,
  because the test #2290 wrote asserted only that three tool names appear
  somewhere in the string — which the corrected text, saying "do NOT chain
  them", also satisfies. That test passed straight across a contract reversal;
  rewritten to pin the contract, it and one other now fail on that revert.
