- **#2292** — **a new inbound evidence channel on the plain-HTTP x402 path,
  carrying no authority.** On that path Haven tells the agent to retry the
  merchant itself and never contacts that merchant — the keyless property this
  rail exists for. The consequence was that the outcome of the retry had
  nowhere to go: `intentStateFor`'s merchant-rejected branch needs an open
  `merchant_retry_rejected_after_payment` reconciliation event whose only
  producer was the SDK's own retry path, and the alternative branch waits out
  `MERCHANT_REPORT_GRACE_MIN` (15 minutes). A demonstrably failed purchase
  therefore read `confirmed` / `payment_confirmed` / `next_action: none` for
  that window. Not a wrong status; one nothing could yet inform.
  **What changed:** one new hosted MCP tool, `haven_report_x402_outcome`, and
  its SDK twin `HavenClient.reportX402MerchantOutcome`. `rejected` posts the
  existing `POST /machine-payments/reconciliation-events`; `accepted` posts the
  existing `POST /machine-payments/evidence`. **No new route, no new table, no
  migration, no change to any signing scheme, delegation, caveat, budget, rail
  or refusal code.** Haven still never contacts the merchant — a "verify it for
  you" convenience was explicitly rejected, because it would undo the
  architecture the epic exists to protect, and a test asserts every outbound
  request in the flow is to Haven's own origin.
  **Why the perimeter is unchanged despite the report being caller-asserted.**
  The boundary is drawn as #2092/#2096 drew it for a caller-asserted settlement
  hash. Verified: the payment resolves scoped to the calling agent (both routes
  are `WHERE agent_id = $`, so another agent's payment is a 404 with nothing
  written); it is an x402 intent, `confirmed`, with a Haven funding
  transaction; the anchor transaction hash and resource URL are read from that
  payment's own record and are **not arguments** — the tool schema is
  `.strict()` and refuses `tx_hash` / `resource_url` loudly rather than
  stripping them (#2282's lesson); `merchant_status` must be a 100–599 integer
  that agrees with the asserted outcome. Deliberately NOT verified: that the
  merchant returned that status, or that the resource was delivered — checking
  means calling the merchant. What a hostile or buggy caller can therefore
  achieve is bounded to its own payment: hide its own stranded-funds prompt, or
  raise a spurious one. It cannot move funds, cannot alter the intent's status,
  amount, recipient or transaction, cannot confirm a `submitted` erc7710 intent
  (no Haven funding hash exists there and the report is refused — the
  on-chain-verified seam in `attachMachinePaymentEvidence` remains the only
  door), and cannot block or unblock a sweep, which is driven by the delegate's
  on-chain balance and not by this claim. A false `accepted` additionally fires
  the server's own post-settlement residue read, which re-flags stranded funds
  independently of what was reported.
  **One behaviour change on an existing money-path route, stated rather than
  buried.** `POST /machine-payments/reconciliation-events` now answers 409 for
  a `merchant_retry_rejected_after_payment` on a payment that already carries a
  client-upgraded evidence row. This decides a precedence that previously fell
  out of the upsert's guard and was incoherent — `reject → accept` resolved,
  `accept → reject` opened a stranding on a delivered payment, and
  `reject → accept → reject` stayed resolved. An acceptance is now terminal in
  every order. It narrows what can be written, never widens it, and the SDK's
  own `recordRetryRejected` swallows failures, so nothing on that path changes
  behaviour.
  **Mutation-tested:** removing the precedence guard, writing the rejection
  event as `resolved`, downgrading the acceptance's `proof_status`, dropping
  the agent scoping from the reconciliation/evidence lookups, dropping
  `.strict()`, disabling the outcome/status agreement check, removing the
  funding-transaction anchor gate, reporting every outcome as a rejection, and
  making the tool contact the merchant — each produced a named red, each
  restore verified with `git diff --exit-code`. Perimeter unchanged.
