- **#2330** — **agent-facing guidance only; no route, authority, signing scheme
  or custody boundary moves, and no byte of wire format changes.** #2289 fixed
  the x402 merchant header name where Haven MAKES the request: `deliverPayment`
  (`packages/sdk/src/mcp-merchant-transport.ts`) sets both `PAYMENT-SIGNATURE`
  (x402 v2) and `X-PAYMENT` (v1) to the same value, and every SDK-driven retry
  routes through it. It did not fix the name where Haven TELLS THE AGENT to make
  the request — and `haven_pay_x402_quote`'s stated premise is *"retry the
  merchant YOURSELF — Haven never talks to this merchant and never holds the
  key."* Three agent-facing strings still said `X-PAYMENT` alone, two more named
  no header at all, and nothing on any surface named `PAYMENT-SIGNATURE` to an
  agent. Following that guidance against a strict v2 merchant reproduces the
  originating failure of epic #2288 exactly: the merchant never sees a header,
  re-issues its 402, and on the EIP-3009 bridge the funding leg has already
  moved user funds to the delegate EOA. This change makes every such instruction
  name both wire names, v2 first, and adds a guard so no surface can regress to
  naming v1 alone.
  **What is deliberately NOT touched.** `deliverPayment`, the payload wrap, and
  the header-name constants (`X402_PAYMENT_HEADER_NAME`,
  `X402_LEGACY_PAYMENT_HEADER_NAME`, `X402_PAYMENT_HEADER_NAMES_SENT`) are
  byte-for-byte unmodified, and #2289's eight `x402-payment-header-name.test.ts`
  tests pass unchanged — an explicit acceptance criterion, because the wire is
  already correct and only the instruction was wrong. No signing scheme, binding
  verification, delegation, caveat enforcer, budget or spend limit is involved.
  No code path here moves, holds or initiates the movement of funds; the diff is
  description strings, one runtime error string, documentation, and one test.
  **Why a wrong instruction is a money-path concern at all.** It is the sentence
  that decides whether an already-funded payment is delivered. Getting it wrong
  does not move money incorrectly — it strands money already moved, on the
  delegate EOA, with the user debited and nothing received. That is what
  happened to the payment that opened #2288, and this issue exists because the
  epic's own remedy still routed agents into it on the one path the originating
  purchase used.
  **The guard, and the two ways its first versions were wrong — recorded
  because the shape is the point.** `packages/mcp-server/src/x402-header-name-guidance.test.ts`
  asserts, per description, that naming `X-PAYMENT` implies naming
  `PAYMENT-SIGNATURE`, across the exported description records of all three
  tool surfaces plus the SDK's `havenTools` definitions. Version one read
  `@haven_ai/sdk`'s `toolDescriptions` and was GREEN while the primary defect
  sat uncovered: `AUTHORIZE_X402_DESCRIPTION` — the only string in the issue
  that says *"when doing a manual HTTP retry"* in as many words — is not in that
  record, it is a `description` field on `havenTools`. Reverting it to its
  v1-only wording passed every test in the repository. Version two then assumed
  `havenTools.claude` was an array when it is a factory, and silently collected
  zero entries; the non-vacuity assertion caught that rather than letting it
  pass. Both are written into the test's header. A guard that measures the wrong
  surface is the same failure as the one being fixed, one level up.
  **Mutation-proved, four mutations and four kills.** Reverting the SDK's
  manual-retry instruction fails three tests (it failed none before the guard
  was widened); reverting `PAY_X402_QUOTE_DESCRIPTION` fails two; reverting the
  signer's `X402_SIGN_HEADER_DESCRIPTION` fails one; reverting the
  `/protocols/x402` code sample fails the tree scan.
  **Two blocking review findings, both of the same family as the issue itself.**
  First, the guard's own header claimed the two `buildAgentGuidance` `reason`
  strings were "pinned separately in `tools.test.ts`". They were not — no test
  in the repository asserted a header name on either, so two of the five fixed
  sites had no regression protection while the test file said they did. A false
  claim of coverage is worse than a named gap, because the next person to revert
  either site sees green. Both are pinned now and the paragraph is corrected in
  place rather than deleted. Second, a SIXTH surface: the public
  `/protocols/x402` page shipped a copy-pasteable client sample setting
  `'X-PAYMENT'` alone — no description record contains it, so the record-walking
  guard structurally could not see it. That produced the tree-wide scan below,
  and three `qa-agent` erc7710 scenarios doing the same thing (harmless only
  because the demo merchant accepts the v1 alias) were fixed with it.
  **The scan was then widened, and then tightened, both on review evidence.**
  Review demonstrated a live miss by rewriting the `/protocols` sample to use
  `Headers.append` — a normal way to do this, and a worse one for this bug since
  `append` does not overwrite a stale value — and named computed keys, bracket
  assignment, header tuples and inline `curl -H` as the other blind spots. All
  are now matched, each verified by mutating the sample into that shape. The
  first widening over-matched in the other direction, flagging three evidence
  fixtures and a doc comment that RECORD which header name was sent rather than
  setting one; the pattern now matches the header in KEY position only. Both
  directions mattered: a guard that cries wolf earns an allowlist entry per false
  positive until the allowlist is the real configuration.
  A third pass then constructed one more: a BACKTICK computed key,
  ``[`X-PAYMENT`]: token``, which the tightened bracket alternative rejected
  because it accepted only `'` and `"`. Inside brackets a template literal is
  valid key syntax, so that is a real setting site and not prose — the reason
  for excluding backticks only ever applied to the plain-key form. Now covered
  and mutation-verified. Worth recording that the guard needed three rounds and
  an independent reviewer to reach this state: each round it was green, and each
  round it was still missing a shape its own commit message claimed it covered.
  Review also proved that `packages/sdk/src/x402-payment-header-name.test.ts`
  was passing by COINCIDENCE — unrelated tests later in the same file happen to
  name the v2 name, and redacting them made the guard fail. It is allowlisted
  explicitly now, with that reason, because an accidental pass is not coverage.
  **The scan, and why it matches the ACT rather than the mention.**
  `#2330 — nothing SETS the v1 header alone` walks `packages/` and `docs/` for
  an object-literal key, a `headers.set(...)`, or a Markdown header line naming
  `X-PAYMENT`, and requires the file to name `PAYMENT-SIGNATURE` too. Matching
  the act leaves every legitimate discussion of the v1 name alone — historical
  changelog entries, retired-rail sections, spec references — without listing
  them. One allowlist entry, with its reason: an SDK test that plants a stale
  v1 header precisely to prove `deliverPayment` overwrites it. Non-vacuity is
  asserted in both directions (files walked, and files that actually set the
  header), because a broken glob reporting a clean sweep of nothing is how this
  guard would fail the same way its predecessors did.
  **A ratchet changed the shape of the fix, correctly.** The first wording
  repeated the rationale — why a strict v2 merchant ignores the legacy name — in
  five descriptions, pushing the per-tool description mean to 887 bytes against
  the 874 cap that #1591 set and #2311 re-based. Rather than raise the cap, the
  rationale moved into `HOSTED_INSTRUCTIONS` once, which is exactly where #1591
  says shared flow guidance belongs. The guard produced a better result than the
  author would have chosen unaided; noted because a ratchet that only ever
  obstructs gets relaxed, and this one did not merely obstruct.
  Suites: backend 2865 passed / 8 skipped, frontend 1340, mcp-server 327,
  sdk 369, signer 182; `npm run quality` (typecheck + unit + build, all
  workspaces) exit 0 with `HAVEN_SKIP_ENFORCER_PROBE=1` — the
  deployed-caveat-enforcer probe needs outbound network to `sepolia.base.org`,
  which the authoring sandbox blocks. Named with that qualifier rather than as a
  bare exit 0 because it is a Red Line #4 check and did not run here; it is
  unaffected by this change and runs in CI.
