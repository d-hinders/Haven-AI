It carries **16 non-merge commits** touching the five published packages across `273cf376..dad1a2d7` (18 counting the merge commits; `git log --no-merges 273cf376..dad1a2d7 -- packages/{sdk,signer,mcp,connect,cli}` is the derivation, stated because review could not reproduce the bare figure and a number nobody can re-derive is not evidence), and **none of them moves an authority, custody or discretionary-execution boundary** — each was independently perimeter-reviewed in its own shard (#2289, #2290, #2291, #2292, #2293, #2330, #2341, #2343, #2245, #2262, #2280, #2301), and this cut re-publishes them under a new version.

  **What the published surface does, measured rather than asserted.** Comparing the declaration set of each built `index.d.ts` against the published 0.1.32-alpha.0 tarball: **zero declarations are removed or renamed in any of the five packages.** `@haven_ai/sdk` goes 152 → 159, gaining exactly seven — the five x402 header-name constants `X402_PAYMENT_HEADER_NAME`, `X402_LEGACY_PAYMENT_HEADER_NAME`, `X402_PAYMENT_HEADER_NAMES_SENT`, `X402_PAYMENT_REQUIRED_HEADER_NAME`, `X402_PAYMENT_RESPONSE_HEADER_NAME` (#2289) and the two merchant-outcome types `X402MerchantOutcome`, `X402MerchantOutcomeReport` (#2292). `@haven_ai/signer` (53), `@haven_ai/mcp` (29) and `@haven_ai/connect` (77) have declaration sets identical to the published ones, and their entire `.d.ts` diff is the version literal — one line each for signer and mcp, four for connect, whose `runtime-manifest` mirrors the other three. `@haven_ai/cli`'s **`index.d.ts`** is byte-identical — `CLI_VERSION` is not part of its public export surface, so the bump never reaches the declarations. Its compiled bundle and `package.json` carry the ordinary version bump like the other four; the qualifier is kept because an unscoped "byte-identical" would say the artifact did not change this release, which is false (review finding). There is no consumer-visible compile-time break in this release. The set comparison is the assertion that matters: the raw line diff for the SDK is 105 lines, almost all of them inside `HAVEN_SKILL_MD`, a single large string constant whose *content* #2330 rewrote — a line-count reading would have called that a removal, and it is not one.

  **The consent hash is checked span-wide, not inherited.** `packages/mcp/src/tools.ts` and `packages/mcp/src/consent.ts` are byte-unchanged across `273cf376..dad1a2d7`, so `registeredToolNames()` returns the same sorted names and `computeConsentHash` produces the same hash: **no operator is re-prompted on upgrade.** This is verified for the release span rather than composed from the per-slice notes, because a per-PR "adds no tool" does not add up to a per-release one. #2292 does add a tool — `haven_report_x402_outcome` — but it is **hosted-only** and never enters the local schema map that the hash is computed over. `SUPPORTED_X402_EXPECTED_VERSIONS`, the expected-context shape and the `>= 22.0.0` Node floor are untouched in the same span.

  **Why epic #2288's six slices do not reach the perimeter.** The epic exists because Haven sent the x402 **v1** header name to **v2** merchants, which read `PAYMENT-SIGNATURE`; the merchant never saw the header, and on the EIP-3009 bridge the funding leg had already moved user funds to the delegate EOA. #2289 changes the *name of an HTTP header*, not its contents — the EIP-3009 authorization it carries is byte-identical, still produced by the delegate key inside the local signer, still bound by the Haven-signed expected context. #2330 changes agent-facing description *text* only, so that the instruction telling an agent what to put on the wire matches what the wire already does; its one behavioural addition is a guard test, which can only ever fail a build. #2291 narrows rather than widens: where the signer previously answered "spent" for a binding whose window had merely expired — telling a client to reuse a header that was never built — it now returns three distinct refusals, and refusing more precisely is not a widening. #2290 widens *who may fetch a signing context*, in exactly one state (a funded, undelivered, unrejected eip3009 intent past its grace window), and leaves `assertExpectedBinding` and the typed-data digest re-derivation byte-for-byte untouched; a binding still cannot be minted client-side. #2292 adds a hosted tool that writes reconciliation and evidence rows and moves no money. Together they make a failed v2 purchase both less likely and, for the first time, recoverable.

  **One consequence of this release takes effect at the promotion, not at the merge, and is named here rather than left to be discovered.** #2293 lowers the delegate sweep recovery floor from `1` USDC to `0.01` (`config.sweepMinUsdc`). Production sets **no** `SWEEP_MIN_USDC` override — reported by the operator from the live Railway dashboard, not verified from this repository, which cannot see prod env; if an override does exist it wins and the floor does NOT move, so confirm the effective value after deploy rather than inferring it from this change. On the reported configuration prod inherits the code default and its effective floor changes from 1 to 0.01 the moment `dev → main` deploys — no operator variable change is involved, which is precisely why it is worth writing down. This *is* a change to when Haven will move user funds off a delegate wallet, so it is stated as one. It moves in the safe direction on every axis: the sweep destination is unchanged and unchangeable (the user's own Haven wallet, pinned in the binding), the transfer is a relayer-paid gasless EIP-3009 for which the user pays no gas, and its only effect is that ordinary 0.01 USDC x402 micropayments stranded by a failed merchant leg become recoverable instead of stranded permanently below a floor calibrated for a gas regime Haven does not operate in. The floor never gated *spending*; it gated *recovery*. Lowering it returns user money that was previously unreachable — including the 0.01 USDC stranded on delegate `0xc83239ef…ff07` by the purchase that opened #2288.

  **Custody is unchanged in the way that matters most: Haven still custodies nothing.** User funds remain in the user-controlled Hybrid DeleGator; authority remains the signed budget delegation enforced on-chain by the audited caveat enforcers during redemption; the delegate key is still generated on the user's machine, still loaded only in the signer's `core.ts`, still never transmitted and never written to an audit row. Haven still holds no user key and still signs no settlement. The retired Safe/AllowanceModule rail is untouched by this cut and still fails closed. `publish.yml` is byte-unchanged since the previous bump and still derives the dist-tag from the version, so this prerelease goes to `alpha` and `latest` is untouched on all five packages. Perimeter unchanged.
