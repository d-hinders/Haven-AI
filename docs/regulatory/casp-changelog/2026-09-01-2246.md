- **#2246** — Removes the last two live violations of this document's own § *Product Copy Rules* avoid list from `packages/frontend/src/components/UsingYourAgentInfo.tsx`, a file this document `covers:` by exact path, and **deletes the § Product Copy Rules "Known compliance gap" paragraph** that disclosed them. **Perimeter unchanged** — no route, no signing scheme, no authority, no migration, no on-chain behaviour and no money movement is touched; the entire code diff is rendered English in one modal, plus two literals added to a lint list. Recorded here because the defect was a **false custody and false key-holder claim made to the user**, which is what § Product Copy Rules exists to prevent, and because a disclosure paragraph leaving this document is a change to the document's own compliance record.

  **What was live, and what each phrase falsely claimed.** The component is the dashboard's onboarding step 3 ("Make your first agent payment" → *Show me how*, `DashboardOnboardingGuide.tsx:119` → `DashboardClient.tsx:1116`), so it is read by a user who has funded an account and connected an agent and is about to make their first payment.

  - **Line 33** — "*Haven signs and settles the payment automatically — within the agent's remaining allowance.*" This is the avoid-list entry "Haven signs and settles the payment." verbatim, and **both halves are false on the live rail**, not only the listed phrase. Haven signs nothing: the payment is signed by the delegate key, which is held by the local signer (`packages/signer/`, #1138), and Haven's backend never receives it. On erc7710 direct settlement — the owner-preferred scheme (#1450) — the **merchant** redeems the `[child, budget]` delegation chain and Haven submits no settlement transaction at all. Saying Haven signs and settles asserts exactly the two roles the *Preferred Architecture Summary* below lists under "Haven must not be": **key holder** and **payment processor**. "remaining allowance" is retired-rail vocabulary (#1440): the live primitive is the owner-signed budget delegation, and `/custody` (#2106) reserves "allowance" for the legacy Safe branch precisely so the two are not conflated.
  - **Lines 11–14** — "*When you created your agent, Haven gave you a **credential** — a private key plus a small JSON file…*" The avoid-list entry is "Haven gave you the private key.", and an earlier telling of the deleted paragraph recorded that phrase as gone. The literal string was; **the claim was not**, and it was the first sentence of the modal. It is also false as a matter of fact, checked rather than inferred: the delegate keypair is generated **client-side** in both creation paths — `useAgentConnectionSetup.ts:772` calls `generatePrivateKey()` in the browser and POSTs only `delegate_address`, and the connector generates locally in `packages/connect/src/key.ts`. The credential artifact the modal describes already says so in its own `notes.custody` field ("Haven is non-custodial. The delegate_key in this file lives only on this machine. Haven's backend never receives it.", `lib/agent-credential.ts`), so the modal contradicted the file it was describing.

  **The corrected copy, derived from this section's *Use wording like* list rather than paraphrased.** Step 2 now reads "*the payment is signed by your agent's own key and constrained by the budget you signed — automatically, with no extra step from you*", which is the approved line "Payments are signed by your agent's key and constrained by the budget you signed" with the original's "automatically" preserved, since this is onboarding copy about an unattended payment. It names **no** Haven actor at all, which is stronger than substituting an approved Haven verb. The opening paragraph now attributes generation to the user's device and splits the two credentials per `copy-guidelines.md` § *Separate authentication from payment signing* — the API key identifies the agent and cannot spend by itself; the private signing key signs and never reaches Haven's backend. "allowance" is replaced by **"budget"** throughout, matching what `/custody` landed on in #2106 rather than inventing a term, and the delegate address is called the **"signing address"**, the label `PaymentCredentialsModal.tsx:204` already ships for it.

  **Why the gate did not catch it — measured, because the obvious diagnosis is wrong.** The natural assumption is that the file is unscanned or baselined. It is neither: it lives under `src/components`, inside the copy lint's `SCAN_DIRS`; it has **no** entry in `packages/frontend/copy-lint-baseline.json` (which holds 2 files / 3 occurrences, none of them this file); and `findCopyIssues` over the live file returned `[]`. **The gate was green because nothing in `BANNED` described either phrase.** #2334's five attribution literals are `haven authorizes|authorises|approves|grants|permits`, and neither of these is one. Control run before believing that zero: injecting `Haven authorizes the payment.` returns a hit, so the instrument can say yes. **No baseline entry was removed and the baselined count did not drop** — there was nothing there to shrink. That is the finding rather than a missing step, and it is why the same copy had to be found by hand twice (#2063's tracker closed without fixing it; #2347's repo-wide sweep re-found it independently a week later).

  **Mutation-proven, by process exit code, never by inverting an edit.** (A) Baseline on the fixed tree: **exit 0** — read first, because a mutation proof whose baseline is also red proves nothing (#2347's stale-`dist` instrument failure). (B) The pre-fix component restored verbatim from a `cp` backup: **exit 1**, naming `UsingYourAgentInfo.tsx:12:40` (`haven gave you`) and `:33:15` (`haven signs and settles`). (C) The counterfactual that makes the diagnosis a measurement rather than a story — pre-#2246 lint script *and* pre-fix component together, i.e. the state that actually shipped: **exit 0**. (D) Both files restored from `cp` backups and verified byte-identical with `diff -q`; restored baseline back to **exit 0**. `scripts/frontend-copy-lint.test.mjs` gains four tests, 28/28 green.

  **The two literals added, and the two rejected — the rejections are the load-bearing half.** Added: `haven signs and settles` and `haven gave you`, both **zero occurrences** across the full scanned set (149 files under `SCAN_DIRS` plus the 8-entry `SCAN_FILES` allowlist), so the false-positive cost is nil on the #2334 bar. They are deliberately **shorter than this document's sentences**, and that is measured: `haven gave you the private key` matches the live defect at no point, because the defect was split across a JSX interpolation and a line break. Rejected on the same measurement, not on taste: `signs and settles` fires on `app/protocols/x402/page.tsx:12` ("Client signs and settles on‑chain" — the client is the actor and the sentence is correct), and `haven signs` fires on `components/AccountSignersCard.tsx:10` ("Haven signs nothing.") — **the non-custody claim itself**, which a compliance gate must never make harder to write.

  **The ceiling, stated so a green run is not miscited.** This is a single-line literal match. The avoid list bans a **claim**; the lint can only hold a **phrase**. Reword the same claim ("the key we issued you when you created the agent") and it goes green; that evasion is asserted on purpose in the test file, on the #2334 precedent. Human and design review remain the control for attribution, and this addition is the cheap floor under it — never evidence that the modal's custody claims were checked.

  Perimeter unchanged. What changes is that the covered UI now states the delegation rail's real actors — the agent's key signs, the owner-signed budget constrains, the credential is generated on the user's device — so § Product Copy Rules no longer carries a live counterexample inside its own `covers:` set, and its disclosure paragraph is deleted with the gap it disclosed.
