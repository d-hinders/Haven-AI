- **#2312** — A first batch of hosted MCP tools now **REFUSES** an argument they do not declare, where they previously stripped it silently. Four tools: `haven_report_x402_outcome`, `haven_submit`, `haven_complete_mcp_tool`, `haven_settle_mcp_tool`. **Perimeter unchanged, and narrowed in one direction only** — no new authority, no new custody relationship, no route, no signing scheme, no migration, no funds moved, and nothing a caller could previously do that had an effect is removed. The only behaviour that changes is that an input which used to be *discarded without a word* now produces a 400 before anything is read or written.

  **Why a refusal-adding change is recorded here at all.** This doc's implementation rule is that *Haven must not silently create or expand an agent's authority*, and its `agent-connection-setups.ts` precedent states the mechanism version of it: a caller cannot name the Safe, the delegate or the module its approval is checked against, because every identifying field is equality-checked against the stored row rather than accepted as input. The four tools above are the tool-boundary analogue. Each takes a `payment_id` and reads the rest — amount, recipient, merchant address, resource URL, the anchor funding transaction — from the payment's own stored row. The permissive parse meant a caller could supply `tx_hash`, `amount` or `resource_url`, have it dropped, and receive **`success: true`**. Nothing was mis-authorised: those values were always read from the record, so no payment ever moved under a caller-supplied field. What was defective is the *evidence a caller receives about what it authorised* — an operation returning cleanly while being about a different question than the caller thinks. That is a record-integrity property on the money path, so it is recorded rather than absorbed.

  **The guard #2292 shipped could not fire, and that is the substantive finding.** #2292 added `parseStrict` and pointed it at `haven_report_x402_outcome`, reasoning correctly about why that tool needed it. It was placed in the tool **handler**. Measured on 2026-09-01 by driving a real `InMemoryTransport` client against `buildHostedMcpServer`: `@modelcontextprotocol/sdk`'s `McpServer.validateToolInput` parses the call against the registered input schema and passes the handler `parseResult.data` — the already-stripped object — so the handler-level `.strict()` never saw the key. The exact call the guard exists to refuse (`haven_report_x402_outcome` with an undeclared `tx_hash`) returned `success: true` and **wrote its reconciliation event**, with three Haven requests made. #2292's own test passed because it calls the handler directly, which is the one shape in which the property held. A guard that can only pass in its own test's shape is the unfalsifiable class #2307 removed 56 of. This entry corrects the record for #2292's shard rather than editing it, per *Once merged, a shard is immutable* — #2292's analysis was **true of the code it described** and wrong about which layer enforces it, which is a mechanism gap rather than the log's *wrong when written* case. Strictness is therefore now declared at **registration** (`toolInputSchema`, consumed by `server.ts` through `McpServer.registerTool`, because the deprecated `.tool()` overload refuses a `ZodObject` outright), with `parseStrict` retained as the second line for callers that import the exported `createToolHandlers` directly.

  **No consent surface moves, and this was measured rather than argued.** Two independent reasons, either sufficient. (1) The advertised JSON Schema does not change: `zod-to-json-schema` already emits `additionalProperties: false` for a strip-mode `z.object`, so the loose and strict advertisements are byte-identical for **all 22** hosted schemas — surface hash `cf41c32a83b10c54` under both, against a control mutation of one schema at `3c8ea4a1f4bc564b` proving the comparison discriminates. The advertisement was already strict; only the behaviour was permissive, which is the mismatch being closed. (2) `computeConsentHash` (`packages/mcp/src/consent.ts`) hashes credential identity + tool **NAMES** + the allowance summary. It takes no schema argument, measured by holding the name list constant (hash unchanged at `1a2f8df4b7191587`) against a control that drops one name (hash moves to `ec985f30f80a4a04`) — and the hosted server has no consent gate in the first place; the gate lives in `packages/mcp` and `packages/signer`, neither touched. So this is **not** an operator re-prompt and not a rollout decision. Recorded because the opposite conclusion would have made it one.

  **Two live callers were already passing a key the schema does not declare, both found by the change itself.** `tools.test.ts` sent `max_amount: '2000000'` to `haven_settle_mcp_tool` — a tool that has never declared a cap, because the cap belongs on the prepare/pay leg where it is checked against the live quote **before** any funding — and asserted a successful settle, so the test spent its life certifying a cap that was being discarded. The same file's shared `mcp_transport` fixture sent `signature` to `haven_complete_mcp_tool`, which does not relay a signature. Both were test-side, so no production caller was mis-served; both are exactly the defect the change exists to make impossible, and neither was visible to any check before it. The SDK, the connect flow, the `qa-agent` legs and the e2e fixtures were enumerated against the declared schemas and pass only declared properties.

  **Deliberately not switched, so the batch is a decision rather than a sweep.** `haven_send`, `haven_pay_mcp_tool`, `haven_quote_x402` and `haven_pay_x402_quote` stay permissive in this change: the local MCP spells the same arguments differently (`idempotencyKey`, `quote`, a local-only `body`), so an agent carrying the local shape is silently stripped **today** — losing idempotency protection on a payment, which is a duplicate-spend hazard and the stronger money-path case of the two. Converting that live silent path into a hard refusal is the right answer and wants its own change with the agent-facing guidance corrected alongside it, not a line in a batch that is about record-reading tools. `haven_get_agent` and `haven_get_allowances` declare `{}`, where strict refuses every key including a client's decoration, for no money-path gain. Both exclusions are stated in the code, not only here.

  **Mutation-proven, four ways, each restored from a `cp` backup and verified byte-identical with `diff -q` rather than by inverting the edit.** Dropping `.strict()` from the registration schema turns 5 of 15 tests red (the wire guard); dropping it from `parseStrict` turns 4 red (the direct-embedder guard); restoring the pre-change `.tool()` registration in `server.ts` turns 4 red (proving the registration-API change is load-bearing and not cosmetic); and removing the top-level-path filter in `parseStrict` turns the two #2282 `mcp_transport` tests red (proving the nested snake_case hint is not swallowed by the new generic message). Every assertion in the new suite runs client → transport → server → handler, with a negative control on a deliberately permissive tool proving the harness can observe a strip as well as a refusal, and a `fetches === []` assertion proving the refusal precedes every read and write. Full `mcp-server` suite 342/342 and `qa-agent` green; `tsc --noEmit` clean.

  Perimeter unchanged; a money-path tool boundary that accepted-and-discarded now refuses, and the evidence behind #2292's own record-integrity claim moves from a guard that could not fail to one proven to fail under four separate mutations.
