- **#2341** — **a money-path REGRESSION introduced by this epic's own fix, and
  the narrowing that closes it.** #2289 set both x402 wire names on every
  merchant retry — `PAYMENT-SIGNATURE` (v2) and `X-PAYMENT` (v1), same value,
  unconditionally. On the EIP-3009 bridge that is correct and is unchanged
  here: the header is a signature plus a six-field authorization, duplicating
  it costs nothing, lenient v1-only merchants are real, and it is the path the
  purchase that opened #2288 used. On **erc7710** it broke every settlement.
  That header carries the whole `[child, budget]` delegation chain plus the
  UserOperation, so duplicating it pushed the request past the server
  header-size limit and merchants answered **HTTP 431 Request Header Fields
  Too Large**. The header was never read, and on the hosted path the funding
  leg had already moved user funds when the 431 landed
  (`MERCHANT_REJECTED_AFTER_FUNDING`) — user debited, nothing delivered. That
  is the #2288 defect class exactly, reintroduced by #2288's own remedy on the
  other scheme, and it is recorded here in those terms rather than as a tidy
  follow-up.
  **What changes, and what deliberately does not.** `deliverPayment` now asks
  `x402PaymentHeaderNamesFor(paymentHeader)` which names to send: both for
  EIP-3009, `PAYMENT-SIGNATURE` alone for erc7710. No signing scheme, binding
  verification, delegation, caveat enforcer, budget, spend limit, route or
  authority moves. The header VALUE is byte-identical — still produced by the
  delegate key inside the local signer, still bound by the Haven-signed
  expected context that `assertExpectedBinding` verifies, still unconstructable
  by Haven. This changes which HTTP header name carries an unchanged
  authorization, in one direction: strictly fewer copies on the wire.
  **The rule is by SCHEME, not by byte count, and that distinction is
  load-bearing.** An erc7710 payload is always `x402Version: 2` — the backend's
  `encodeXPaymentHeader` hardcodes it — and a merchant able to redeem a
  delegation chain is by construction running x402 v2 plus the MetaMask
  erc7710 extension, so it reads the v2 name. The legacy alias cannot help such
  a merchant and can only cost the request; removing it there forfeits no
  compatibility that ever existed. A size threshold would have been an
  arbitrary number that changes behaviour silently near its own edge, and would
  have left the alias being sent pointlessly whenever it happened to fit.
  **A name not sent is DELETED, not left behind.** #2289 used `set` rather than
  `append` precisely so a stale header on the caller's init could not present a
  superseded authorization alongside the live one. Sending one name reopens
  that hole from the other side, so `deliverPayment` iterates every name Haven
  may send and explicitly deletes the ones it is not using. A stale `X-PAYMENT`
  left in place would be a superseded authorization deliberately not
  overwritten — worse than the duplicate being removed, and pinned by its own
  test.
  **The audit trail is derived from the same decision, not restated.** The
  evidence record's `paymentProofHeaderName` was the constant
  `X402_PAYMENT_HEADER_NAMES_SENT`, whose own comment says it exists so the
  record "cannot drift from the request". That constant was true while the
  answer was always both. Both call sites now use
  `x402PaymentHeaderNamesSent(paymentHeader)`, so an erc7710 payment can no
  longer be recorded as having carried a legacy header it never sent — the
  exact drift that comment was written to prevent, one scheme later.
  **Review found the fix was scoped to ONE code path, and the instruction half
  was still wrong — the same defect one level up, again.** `deliverPayment` is
  only reached when HAVEN makes the merchant call (the hosted
  `haven_settle_mcp_tool` / `haven_complete_mcp_tool` path). On the plain-HTTP
  path the AGENT retries the merchant itself — by design, and stated as such in
  the tool surface — so Haven's only lever there is the guidance text it hands
  back. That text still said "set BOTH", including in the two erc7710-specific
  `reason` branches, so an agent following Haven's own instruction against a
  real erc7710 merchant still reproduced the 431 with the code fix in place.
  Four surfaces carried it: the two erc7710 `reason` strings, the plain-HTTP
  quote description, the hosted server instructions, and the SDK's own
  function-calling description. This is exactly #2330's lesson — the wire and
  the instruction are two different fixes — arriving from the opposite
  direction, and it was found by review constructing the path, not by any test.
  Of the three qa-agent scenarios edited alongside, only `x402-erc7710-hosted`
  (untouched here) actually exercises `deliverPayment`; the other three drive
  raw `fetch`, so editing them proved the scheme rule but not the code.
  **A guard that pinned the fix now pinned the DEFECT, and is reversed in
  place.** #2330 added assertions that the erc7710 `reason` names both wire
  names. It was right that the reason must name the wire correctly and wrong
  about what correct is on that scheme, so `tools.test.ts` now asserts
  `not.toContain('X-PAYMENT')` on both erc7710 branches, with the reversal
  written where the old assertion stood rather than deleted. The reason text
  deliberately does not name the legacy header even to FORBID it: a first pass
  wrote "do not add X-PAYMENT", which failed that very assertion, because
  `not.toContain` cannot tell an instruction from a prohibition — and a negated
  header name is a poor thing to hand an agent regardless.
  **A second review pass found the same drift on one more tool, and paying for
  it restored the ratchet's headroom.** `SETTLE_MCP_TOOL_DESCRIPTION` still
  summarised itself as delivering the header under "both x402 wire names",
  and that tool has a live erc7710 branch. Its RUNTIME was already correct —
  the branch routes through the fixed `deliverPayment` — so no money-path
  defect, and no test could have caught it: the only wrong thing was a summary
  promising behaviour its own branch no longer had. That is the exact drift
  class this issue is about, found on the one tool whose code was already
  right. Removing the 24-byte overclaim more than paid for the guidance added
  elsewhere.
  **The npm landing page carried six of them, including two copy-pasteable
  samples — and only an ADVISORY gate pointed at it.** `packages/sdk/README.md`
  is the published `@haven_ai/sdk` page. #2330 made every merchant-retry
  instruction in it say "both names", which was right then and wrong on erc7710
  the moment this issue scoped the send by scheme. Two of the six are `fetch`
  snippets a developer would paste verbatim; applied to an erc7710 payment they
  produce the 431 directly. The bridged EIP-3009 samples keep both names —
  correct for them — and now say they are bridge-only rather than reading as
  the general rule. Worth recording HOW this was found: the docs-coupling gate
  listed the README as advisory, not blocking, because its blocking half covers
  only contract docs. Nothing mechanical would have stopped it shipping; it
  took re-reading a doc the tooling had explicitly said was optional.
  **Then a full sweep, because finding these one at a time was not working.**
  After the README, every remaining "both names" instruction in `packages/` and
  `docs/` was enumerated and classified individually rather than pattern-matched:
  fourteen sites, of which **four** were erc7710 and wrong and ten were EIP-3009
  and right. Two of the four were flow DIAGRAMS with the instruction sitting
  directly under an `haven_submit { settlement_scheme: "erc7710" }` line
  (`packages/signer/README.md`, `docs/architecture/07-edge-signer.md`); each
  file also carries the EIP-3009 diagram saying the same thing, which is
  correct there and is deliberately left saying it, now annotated so the pair
  reads as a contrast rather than a repetition. The other two were a stale
  `client.ts` comment and the runtime-compatibility doc's body, which still
  stated #2330's rule as current. Checking each rather than assuming mattered:
  two of the four this pass expected to fix turned out to be the EIP-3009 half
  of their file and were left alone.
  **Nothing mechanical pointed at any of this, and that is the honest state of
  the guard.** `packages/signer/README.md` was not even on the coupling gate's
  advisory list, because the commit that made it wrong did not touch
  `packages/signer/src`. The #2330 guard asserts "naming X-PAYMENT implies
  naming PAYMENT-SIGNATURE" and stays green on every one of these, because they
  all name both — that is the defect. Its counterpart, "does not instruct BOTH
  where only one is correct", requires knowing which scheme a sentence is about,
  which is prose interpretation the #2330 guard explicitly refuses to do. No
  guard was added for it, and this is recorded as an accepted gap rather than
  papered over with something unfalsifiable: the coverage here is an
  enumeration done once, and it will decay.
  **On the #1591 description ratchet, stated rather than absorbed.** The scheme caveat is
  three more words on a served description; the full rationale went into
  `HOSTED_INSTRUCTIONS` once, which is where #1591 says shared flow guidance
  belongs. The first pass landed at exactly **874.000/874** — legal, since the
  cap is shrink-only and was never raised, but a landmine: the next PR to touch
  any description would have failed a guard whose message would look unrelated
  to whatever it was doing. Removing the `SETTLE_MCP_TOOL_DESCRIPTION`
  overclaim brought it to **872.955**, 23 bytes of headroom. The cap is still
  not raised, and a note now sits beside the constant saying headroom is thin
  and that the answer to tripping it is to find a real overclaim or re-argue
  the number on its own evidence — never to bump it quietly. Deleting the
  header sentence from `haven_pay_x402_quote` would have bought 63 bytes and
  was rejected: #2330 explicitly pins that description as naming both wire
  names, and that pin is the epic's flagship deliverable on the surface the
  originating purchase used.
  **Mutation-proved, and the first version of the size test was green for the
  wrong reason.** Restoring #2289's unconditional dual-send fails four of the
  six new tests. It initially failed only three: the byte-size test passed
  under the mutation, because this fixture's doubled header block is still
  under 16 KB and size alone cannot distinguish the two. Counting how many
  header names carry the payment value is what makes it fail for the right
  reason. Recorded because a guard that measures the consequence without tying
  it to the cause is the failure mode this whole epic keeps producing.
  **What the tests do NOT prove, stated rather than implied.** The erc7710
  fixture is a deliberate LOWER BOUND on a real payload and does not by itself
  exceed the header limit when duplicated; the assertion says only that
  removing the duplicate saves kilobytes, which is what the fixture supports.
  The live evidence for the threshold crossing is the money-flow QA run
  (33473212469) on `b4de1023`, where four erc7710 scenarios failed and one
  returned the 431 explicitly while all four EIP-3009 scenarios passed. The
  acceptance evidence is a green `qa-dev`, not this unit file — a fixture
  merchant answering on names alone is precisely what let the defect ship, and
  every #2289 test used a short placeholder header, so no test in the
  repository had ever measured a request.
  #2289's eight `x402-payment-header-name.test.ts` tests pass unchanged, under
  the mutation as well as after the fix, confirming they pin the EIP-3009
  dual-send this change does not touch. Suites: backend 2865 passed / 8
  skipped, frontend 1340, mcp-server 327, sdk 375, signer 182; `npm run
  quality` exit 0 with `HAVEN_SKIP_ENFORCER_PROBE=1` — the
  deployed-caveat-enforcer probe needs outbound network to `sepolia.base.org`,
  which the authoring sandbox blocks. Named with that qualifier rather than as
  a bare exit 0 because it is a Red Line #4 check and did not run here; it is
  unaffected by this change and runs in CI.
  **One version-skew consequence, named because it is real.** `deliverPayment`
  ships in `@haven_ai/sdk`, so a client pinned at or below 0.1.32-alpha.0 keeps
  sending both names on erc7710 and keeps hitting the 431 until it upgrades.
  Nothing negotiates this and nothing fails closed on it — a merchant's header
  limit is not a Haven contract — but the failure is LOUD
  (`MERCHANT_REJECTED_AFTER_FUNDING`, HTTP 431) rather than silent, and it is
  the same failure those versions already have: this release fixes it rather
  than introducing a new incompatibility. Hosted server guidance is served by
  the deployment, not the client, so an old client against a new server already
  gets the corrected instruction for its own manual retries.
  Haven still custodies nothing, still holds no user key, still signs no
  settlement. Perimeter unchanged; a fix that stranded funds on the preferred
  settlement scheme no longer does.
