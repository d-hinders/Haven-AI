- **#2343** — **a serialization bug on the x402 settle-leg handoff, fixed; no
  authority, custody or execution boundary moves.**
  `GET /x402/:id/merchant-call-context` re-serves the merchant call context
  (#1307) so a hosted settle does not need the agent to re-thread
  `merchant_url` / `tool_name` / `arguments` / `mcp_transport`. It converted
  every TOP-LEVEL field from the stored camelCase blob to the endpoint's
  snake_case contract, and passed the NESTED `mcpTransport` object through
  verbatim under a snake_case key. The wire therefore carried
  `"mcp_transport": { "handshakeRequired": true, ... }` — snake_case key,
  camelCase innards. The SDK read `.handshake_required` as `undefined`, and the
  hosted `parseMcpTransport` refused Haven's own rehydrated value with
  `INVALID_INPUT`, advising the caller to rename a key the caller never sent:
  the guided catalog path settles with `{ payment_id, signature }` and nothing
  else, which is the entire point of #1307. One line of shape conversion.
  **Direction of risk: this only ever refused.** The path failed CLOSED —
  nothing relayed, no funds moved, the error body says so. No signing scheme,
  binding verification, delegation, caveat enforcer, budget or spend limit is
  involved, and this endpoint constructs and authorizes nothing: its own header
  says a wrong value here "fails the outbound merchant HTTP call; it cannot
  redirect funds or alter the signed payment context". The fix makes a refusal
  stop happening; it grants nothing that was previously withheld.
  **A first draft of this paragraph claimed the cost was "a funded payment
  needing the #2290 resume path or a sweep". That was WRONG, and it is
  corrected here rather than quietly reworded, because this is a regulatory
  record and because the error is instructive.** The failing scenario uses
  `haven_settle_mcp_tool` on both its legs, and #2282 moved the merchant-call
  context resolution to run BEFORE anything is submitted, on both schemes, for
  exactly this reason — its own comment says the refusal "lands while the
  intent is still `pending_signature` and nothing has been spent". So on the
  path that actually failed, no funding was ever relayed and there was nothing
  to strand or sweep. The stranding framing belongs to a different tool
  (`haven_complete_mcp_tool`'s decomposed flow, where funding happens in a
  prior, separate call), and the cited run did not exercise it. The draft
  reached for the stranding story because that is this epic's theme; #2282 had
  already removed it from this path, and a changelog that asserts the theme
  over the evidence is worth less than one that says what happened.
  **How it shipped, recorded because it is the same shape as everything else in
  this epic.** `x402-delegation.test.ts` asserted
  `expect(body.mcp_transport).toEqual({ handshakeRequired: true, source: 'path' })`
  — the one test that looked at this value **agreed with the defect**. It is
  reversed in place rather than deleted, and now asserts both halves: the
  snake_case key is present with a boolean, AND the camelCase key is absent,
  because `toEqual` alone would pass on a merged object carrying both. Mutation
  confirms: restoring the pass-through fails it.
  **What is NOT fixed here, and why.** `parseMcpTransport` selects its friendly
  "supplied in the SDK camelCase shape" hint by testing
  `'handshakeRequired' in input` — which cannot fire on this round trip,
  because `serializeMcpTransport` has already renamed the key to
  `handshake_required` (value `undefined`) before the check runs. So the one
  diagnostic written for exactly this confusion was bypassed by the round trip
  that caused it. Teaching it to recognise that shape is a real improvement and
  is deliberately left out: it is a diagnostics change with its own tradeoffs,
  it does not fix the bug, and folding it in would mix a behaviour fix with a
  message change in one money-path commit.
  **Review found the guard that would have caught this for free, and it is now
  wired up.** The OpenAPI schema for this endpoint has ALWAYS declared the
  correct snake_case nested shape with `additionalProperties: false`, and the
  generated `@haven_ai/core` type has always matched it — the spec was right
  the whole time and nothing checked the route against it. `expectMatchesSpec`
  is the established pattern in 20+ other route test files and was wired to
  neither x402 test file. It is added to this endpoint's 200 paths now, and its
  claim is PROVED rather than asserted: called in isolation on the buggy
  `{ handshakeRequired: true }` body it rejects it, so it would have failed CI
  the moment the defect shipped instead of surviving to a live qa-dev failure.
  Stated plainly because it matters: the value assertions above kill the
  mutation first, so the contract line never gets a chance to — which is why it
  was verified separately rather than inferred from a green run.
  **The acceptance evidence is a green `qa-dev`, not this unit test.** The unit
  layer had a test on this exact value and it passed throughout, because it
  pinned the wrong shape. `x402-catalog-guided-purchase` failing deterministically
  on both attempts of run 33481274140 is what found it, and that scenario
  passing is what closes it.
  Suites: backend 2866 passed / 8 skipped, and the changed route file's own 83.
  Haven still custodies nothing, still holds no user key, still signs no
  settlement. Perimeter unchanged; an endpoint that refused its own output no
  longer does.
