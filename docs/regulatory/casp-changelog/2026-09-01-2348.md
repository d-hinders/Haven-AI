- **#2348** — Four more hosted MCP tools now **REFUSE** an argument they do not declare, where they previously stripped it silently: `haven_send`, `haven_pay_mcp_tool`, `haven_quote_x402`, `haven_pay_x402_quote`. Batch 2 of #2312, and the batch with a real money-path consequence behind it rather than a record-integrity one. **Perimeter unchanged** — no new authority, no new custody relationship, no route, no signing scheme, no migration, no funds moved, and no on-chain envelope altered. What changes is that an input which used to be discarded without a word now produces a 400 before anything is read or written.

  **Why this batch is money-path in a way batch 1 was not.** #2312's three tools read amount, recipient and merchant address from the payment's own stored row, so a stripped key never mis-authorised anything — the defect was the *evidence a caller receives about what it authorised*. These four are **argument-driven**, and the stripped key is the idempotency key. The four are reachable through both the hosted boundary (snake_case) and the local MCP transport (`@haven_ai/mcp`, camelCase), so an agent or operator carrying the other surface's spelling lost duplicate-spend protection with no refusal. Measured over a real `Client` → `InMemoryTransport` → `buildHostedMcpServer` round trip against `origin/dev` `c259d9ca` on 2026-09-01, not inferred from the schemas — and the four were **not equally silent**, which the divergence table in #2348 implies and the measurement contradicts:

  - **`haven_send` / `idempotencyKey` — total loss.** The outbound request was observed on the wire as `POST /payments {"token":"USDC","amount":"1","to":"0xabc"}`, with **no `idempotency_key` field at all**; the control passing the correct spelling produced `…,"idempotency_key":"K-CALLER"`. `client.ts` spreads the field conditionally, so an absent key is an absent field, and the backend's replay contract never engages. A caller that believed it had pinned a retry key had not, and a retry is a second spend. This is the strongest instance of the class.
  - **`haven_pay_mcp_tool` / `idempotencyKey` — replay scope REPLACED, not lost.** The key is stripped and the SDK falls back to `buildX402IdempotencyKey(paymentRequired, option)`: a SHA-256 over the resource URL, description, payee, asset, amount, network and a `Math.floor(now / 300_000)` bucket. That is the harder shape to reason about, not the softer one — it de-dupes two genuinely distinct purchases of the same item inside one 5-minute bucket, and fails to de-dupe a legitimate retry that crosses a bucket boundary. A caller's stated replay scope is silently swapped for a different one.
  - **`haven_quote_x402` / `body` — the wrong quote, not a lost key.** The local surface declares a request `body`; the hosted one has no field to route it to, and built its `RequestInit` from `method` and `headers` only. Measured: a call with `method: 'POST'` and `body: '{"q":1}'` probed the merchant as `POST /paid :: ` — **empty**. The quote therefore described a request the caller never made. The `idempotencyKey` half of this tool's crossover costs nothing directly, because a quote creates no payment.
  - **`haven_pay_x402_quote` — its headline crossover already failed loudly, and always had.** Passing `quote` in place of `payment_required` was refused over the transport with `-32602 … {"path":["payment_required"],"message":"Required"}` and **zero** Haven calls, because `payment_required` is a required field rather than an optional one. Only `idempotencyKey` was silent here. Stated explicitly because the issue's table reads as though both keys were equally exposed, and shipping a refusal on the strength of a hazard that did not exist would be the wrong reason for a right change.

  **No live caller passes the crossover spelling — enumerated before the change, not asserted after it.** This was the gating question, because the same rollout hazard pulled `haven_complete_mcp_tool` out of batch 1: Haven's own auto-installed `SKILL.md` told agents to pass it an undeclared key, so refusing would have 400'd Haven's documented flow. Scope enumerated: `packages/sdk/`, `packages/mcp/`, `packages/connect/`, `packages/frontend/`, `packages/qa-agent/` (the hosted-MCP QA legs), `packages/backend/`, the agent-facing skill text in `packages/sdk/src/skill-content.ts` and its byte-pinned twin `packages/frontend/src/lib/agent-skill-bundle.ts`, `packages/sdk/src/tool-descriptions.ts`, `.agents/`, `docs/` and the e2e fixtures. Result, with its denominator stated: measured with `git ls-files` over **tracked** files matching `*.{ts,tsx,md,mjs,json,js}` on the committed branch tree (this shard included, since it names both terms), **128 contain "idempotency"** — the control proving the search can return >0 — and **60 contain the camelCase `idempotencyKey`**, of which **none is a hosted-MCP tool argument**. (Quote that pair with its scope or not at all: an unscoped sweep also walks `node_modules/` and `dist/` and gives a different, meaningless number.) Every one of the 60 is either the SDK's own programmatic camelCase API (`haven.quoteX402(url, init, { idempotencyKey })` — a JavaScript option bag, not an MCP call), the local `packages/mcp` server's own schema where the spelling is correct, or documentation describing the divergence. The shipped agent skill teaches `idempotency_key`, the correct hosted spelling, in all three places it names the field — the opposite of the #2353 situation. The two live hosted-MCP QA legs (`x402-hosted-mcp-signer.ts`, `x402-erc7710-hosted.ts`) pass `idempotency_key` and `max_amount_human`, both declared. So this refusal converts a silent path with **no** live caller, and is not a rollout decision.

  **`haven_complete_mcp_tool` stays permissive, and that is unchanged by this batch.** #2353 fixed the shipped guidance, but the skill is auto-installed and agents carry the old copy on disk, so the switch remains a rollout decision that belongs to the owner (#2353 is still open; see also #2365). This shard makes no claim about it and the test file's `not.toContain` pin on it is untouched.

  **No consent surface moves, re-measured on this branch with its own controls rather than inherited from #2312.** Two independent reasons, either sufficient. (1) The advertised JSON Schema is unchanged: `zod-to-json-schema` already emits `additionalProperties: false` for a strip-mode `z.object`, so across all **22** hosted schemas the loose advertisement, the all-strict advertisement and what `server.ts` actually registers today (7 strict, 15 raw) all hash to `b7f3d2e52716796c`, against a control that adds one property to one schema at `01288ba6b247e6d6` — proving the comparison discriminates. The advertisement was already strict; only the behaviour was permissive, and that mismatch is what is being closed. (2) `computeConsentHash` (`packages/mcp/src/consent.ts`) takes credential identity, the sorted tool **NAME** list and the allowance summary — no schema argument anywhere. Holding the names constant: `1ba50b3d1d97dd6c`, unchanged. Controls, both of which move it: adding a tool name → `a661e628eadf0bcd`; changing one allowance amount → `7b5fb7ae0f1001a9`. And the hosted server has no consent gate at all — the gate lives in `packages/mcp` and `packages/signer`, neither touched. **No operator is re-prompted.** Recorded because the opposite conclusion would have made this a rollout decision.

  **Refusing loudly is the on-ramp, not the destination, and the code says so.** Two surfaces diverging forever behind a good error message is a worse end state than converging. Convergence is deliberately not taken here for a reason about release mechanics rather than taste: `@haven_ai/mcp` is a **published** package, so renaming `idempotencyKey` is a breaking change to an installed contract needing a deprecation window — a release-train decision, not a parse decision. Filed as **#2366**, which also carries the one place this refusal *removes* a capability the silent strip was faking: the hosted `haven_quote_x402` has no `body` field, so a body-bearing paywall is now honestly unquotable there rather than dishonestly quotable. That is the right way round — a wrong quote is worse than no quote — but it is a gap, and it is written down rather than absorbed.

  **Two defects found by the change itself, both fixed here.** (1) `haven_quote_x402` and `haven_pay_x402_quote` parse **before** their `runTool`, unlike batch 1's three, so a validation error escaped the direct-embedder path (`createToolHandlers`, exported from `index.ts`) as a raw throw instead of a `ToolFailure`. That was already true of the permissive `parse` — a missing `url` threw a bare `ZodError` at an embedder — but strictness makes the path reachable often enough that leaving it would be a real defect; both now normalise through the same envelope every other tool uses. (2) The inherited test harness was **vacuous under deletion**: every block iterates `Object.keys(STRICT_INPUT_TOOLS)`, so removing the four entries removed their own tests and the file went from 30 tests to **18 passing**. Batch 1 pinned the two deliberate *exclusions* with `not.toContain` and never pinned the *inclusions*, so the suite could be silently emptied of exactly the guard it exists for. Found by mutation, not by reading; an explicit membership assertion over all seven now makes that mutation red.

  **Mutation-proven, each restored from a `cp` backup and verified byte-identical with `diff -q` rather than by inverting the edit, and judged on process exit code rather than on runner output.** Baseline 30/30 green (exit 0). Mutation A — drop `.strict()` from `toolInputSchema`, the registration layer — turns **8 tests red (exit 1)**, including all four of this batch's transport refusals, while the direct-embedder tests stay green: that asymmetry re-proves #2312's founding finding, that the MCP SDK strips before the handler runs and a handler-level guard cannot see an undeclared key. Mutation B — delete the four `STRICT_INPUT_TOOLS` entries — first came back **green at 18 tests**, which is the vacuity above; after the membership pin it turns red (exit 1) as it should. Restores verified byte-identical against `/tmp/tools.candidate.ts` with `diff -q` in both cycles. Every refusal assertion runs client → transport → server → handler with a `fetches === []` assertion proving the refusal precedes every read and write, and the deliberately permissive `haven_get_payment_status` control proves the harness can still observe a strip. The crossover keys themselves are pinned against `@haven_ai/mcp`'s exported `toolSchemas` (added as a devDependency, `"*"` per the private-consumer rule) rather than restated as literals, so a rename on the local side cannot leave this test asserting an invented typo. Full `mcp-server` suite green; `tsc --noEmit` clean.
