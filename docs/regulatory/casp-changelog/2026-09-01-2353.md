The guidance is corrected; no tool, route, schema, authority, custody relationship or settlement path changes.** The diff is two byte-pinned copies of one paragraph of `SKILL.md`, two tests, and three docs. **No code that constructs, authorises, signs, relays or settles a payment is touched** — `packages/mcp-server/src/tools.ts` is byte-identical to `origin/dev` on this branch, checked with `git diff --quiet` rather than by eye. Editing it pulls `docs/operations/mcp-runtime-compatibility.md` into the blocking coupling gate, and both that doc and that comment are claimed by a concurrently live session (#2347) — so the finding was handed to it on the coordination issue rather than raced. Recorded because a reader of this shard would otherwise find the stale comment and assume nobody looked.

  **What was wrong.** `packages/sdk/src/skill-content.ts` — imported directly by `packages/connect` and **auto-installed** into runtime skills folders, and mirrored byte-for-byte in `packages/frontend/src/lib/agent-skill-bundle.ts`, which the connect success screen serves as a download — instructed an agent, for the decomposed x402 MCP purchase: *"Pass `payment_required`, `arguments`, and `mcp_transport` verbatim from the quote/prepare result."* `haven_complete_mcp_tool` has never declared `payment_required`. Its declared shape is `payment_id` (required) plus optional `merchant_url`, `tool_name`, `arguments`, `mcp_transport`, `payment_header`; since #1307 the merchant call context **and the 402** are rehydrated server-side from `payment_id`. The tool's own served description has said so correctly the whole time. Only the agent-facing skill was wrong.

  **Why it is recorded here rather than absorbed as a typo.** This is #2312's record-integrity property reached from the guidance side. No payment ever moved under a caller-supplied 402 — the field was discarded before the handler ran, and the recorded 402 was always used. What was defective is **the evidence the caller receives about what it authorised**: an agent following Haven's own auto-installed instructions believed it had pinned the payment requirement it quoted, received `success: true`, and had in fact authorised against a value it never saw. On the happy path the two are the same value, which is exactly why it survived. Haven publishing instructions that misdescribe what its own money-path tool acts on is a record-integrity fact about the money path, so it is stated rather than fixed quietly.

  **Measured over the real transport, not asserted.** Driving a `Client` → `InMemoryTransport` → `buildHostedMcpServer` against the exact call the shipped skill instructed: the undeclared `payment_required` produces **no refusal**, the call reaches the handler, Haven requests are made, and the first of them is `GET /x402/pay_1/merchant-call-context` — the rehydration read, i.e. the recorded 402 in use while the caller's is gone. Pinned in `packages/mcp-server/src/strict-tool-input.test.ts` § `#2353`, with a falsifiability control alongside it: supplying the **declared** `merchant_url` + `tool_name` takes the explicit-context branch and that GET disappears, so the harness is demonstrably able to observe an argument surviving the transport. Without that control the first assertion could not distinguish a strip from a blind harness.

  **The tool stays permissive, and that is the decision this entry exists to record.** `haven_complete_mcp_tool` belongs in `STRICT_INPUT_TOOLS` on the merits — it is the clearest rehydration case in the hosted surface, and #2312 pulled it from batch 1 only because of this guidance. Fixing the guidance does not by itself make the switch safe: the skill is **auto-installed**, so an unknown number of agents carry the previous copy on disk today and would meet a hard 400 on Haven's own documented flow the moment the tool refuses. The switch is a live behaviour change with a rollout question attached and it is not in this PR. Two tests hold the halves apart — #2312's control asserts the tool's absence from `STRICT_INPUT_TOOLS`, and this issue's block asserts the strip that absence produces — so both go red together on the day someone flips it.

  **Scope of the check behind "nowhere else".** The wrong instruction was searched for repo-wide with `/usr/bin/grep` (not the shell's gitignore-skipping `ugrep`), quoted globs, and a control search returning >0 before any zero was believed. Two shipped copies carried it (SDK + frontend twin, both fixed here). Separately, every hosted tool named in the skill text was cross-checked **field by field against `toolSchemas`** rather than read: no other sentence names an argument its tool does not declare. `packages/mcp-server/README.md` mentions `payment_required` only as an **output** of `haven_pay_mcp_tool` (lines 86-87, 100), which is correct and unchanged. `packages/sdk/README.md` does not contain the string at all — `/usr/bin/grep -c` returns 0 there against a control of 1 for `haven_complete_mcp_tool` in the same file, so the file is reachable and the zero is real.
