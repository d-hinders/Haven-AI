- **#2361** — **the v2 payment envelope gains the spec-mandated
  `resource`/`extensions` echoes; nothing about who may spend, sign, or
  execute changes.**
  Haven's EIP-3009 signer and SDK funding leg emitted
  `{x402Version, accepted, payload}`; the erc7710 settle handoff emitted the
  same plus top-level `scheme`/`network`. The x402 v2 spec's `PaymentPayload`
  (§5.2.2) additionally carries optional `resource` and `extensions` echoes of
  the merchant's 402 challenge, and makes the extensions echo a client MUST
  ("must include at least the info received; it may append additional info but
  cannot delete or overwrite existing info"). Haven omitted both. Now all three
  emitters echo both objects VERBATIM when the challenge carries them, and omit
  them when it does not — the omission case is byte-identical to the pre-#2361
  envelope. One shared builder (`x402V2PaymentEnvelope`, exported from the SDK
  and used by the edge signer) replaces the two copies that could drift; the
  erc7710 path sources its echo from the #1355 verbatim
  `machine_metadata.payment_required` at settle.
  **Why this is on the record: it was a live spending failure, not a style
  fix.** Two funded Base-mainnet purchases at CoinGecko (payments `37ac8288…`
  and `d6fe585a…`, 2026-09-01) were rejected by their facilitator with a bare
  400; both were fully recovered by sweep. The cause was pinned by live
  bisection (#2360): the *same* funded payment — identical EIP-3009 signature,
  identical `accepted`/`payload` bytes — was refused in the echo-less shape and
  **settled on-chain with HTTP 200** once the two echoes were added, five
  minutes apart. Ampersend and Soundside settled the echo-less shape the same
  day, which is why omission (not an empty echo) is the compat-critical default
  and is pinned by test in every emitter.
  **Direction of risk: none toward authority; the echoes are merchant data,
  not spend authority.** The signed EIP-3009 authorization tuple, the EIP-712
  domain, the `accepted` echo, the amount, recipient, window and nonce are all
  byte-unchanged — the envelope is not signed, which is what made the live
  bisection possible and equally what makes this change unable to alter what
  the delegate authorized. The signer's binding verification
  (`assertExpectedBinding`) and the Haven-signed expected context are
  untouched. The hosted relay preflight (`validateStandardX402PaymentHeader`)
  was WIDENED by exactly two optional keys, structurally checked
  (object-or-absent, never arrays or strings) and never validated against the
  intent, with the stray-key rejection pinned by test in both directions —
  a v0.1.33-and-earlier signer's three-key envelope remains accepted, so no
  deployed client is refused. No route's authorization, no budget, no caveat
  enforcer, no key handling and no refusal semantics change; the perimeter is
  unchanged, and nothing is grantable that was not grantable before.
  **The QA-blindness half, because this is the second envelope defect that
  reached mainnet through the same gap.** The demo merchant validated only the
  envelope Haven happens to send (#2288's header name was the first instance).
  It now ADVERTISES an `extensions` block in every 402 and ENFORCES the echo
  rule (drop → refused; overwrite → refused; append → accepted, all pinned by
  test), so a Haven client that stops echoing fails in the Sepolia QA harness
  instead of at the first strict mainnet facilitator. Its pre-existing
  `resource`-echo check goes from vacuous to live for the same reason.
  **Bounded residual risk, stated rather than glossed:** a merchant whose
  challenge carries a very large `extensions` block enlarges the payment
  header, and the EIP-3009 path sends it under two header names (#2289), so a
  sufficiently large echo could approach Node's default 16 KB per-request
  header ceiling at the merchant — the #2341 failure class from a new
  direction. CoinGecko's real-world block is well under it, the erc7710 path
  sends one name only (#2341), and the hosted preflight's 64 KB header cap is
  unchanged; no size-based dropping of a spec-mandated echo was added, on the
  judgement that silently violating the MUST to pre-empt a hypothetical
  merchant limit reintroduces exactly the class this fixes.
  Perimeter unchanged — the echoes are merchant data riding an unsigned
  envelope, never spend authority, and nothing is grantable that was not
  grantable before.
