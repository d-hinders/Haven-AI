- **#2373** — **the erc7710 authorize request now carries the full 402
  challenge, completing #2361's echo chain; no authority, custody or
  execution boundary moves.**
  #2361 wired the erc7710 settle handoff to echo `resource`/`extensions` from
  the stored `machine_metadata.payment_required` — the read half. The write
  half was never exercised: the SDK's erc7710 `prepare()` posted `/x402` with
  decomposed authority fields only and no `paymentRequired`, so the stored
  challenge was null on that scheme and every erc7710 payment failed a
  merchant enforcing the spec's extensions-echo MUST. Caught in one run by
  the first money-flow QA pass against the echo-enforcing demo merchant
  (#2364's own enforcement working as designed — all five erc7710 scenarios
  refused, run 33541290285, auto-filed as #2372); the EIP-3009 scenarios
  passed, since that path already sent the challenge.
  **The change:** one hunk in `packages/sdk/src/x402-erc7710.ts` — the
  authorize POST includes `paymentRequired` under the same ≤64KB guard and
  omission behaviour as the 3009 path (an oversized challenge omits the
  field, degrading to an echo-less envelope, rather than turning a large
  bazaar block into an unpayable merchant — the backend 400s an oversized
  copy by design). The hosted MCP and catalog-guided flows funnel through
  this same `prepare`; the QA harness's own raw-API driver was a SECOND
  echo-less client (found by the independent review of this fix, not by
  its author), so `packages/qa-agent`'s `authorizeX402` and its two
  raw-API erc7710 scenarios now pass the decoded challenge through too —
  two clients changed, not one, and any future raw-API caller must send
  `paymentRequired` to survive an echo-enforcing merchant.
  **Direction of risk: none toward authority.** The backend already accepted
  and persisted the field on both branches (#1355) and treats it as
  persisted-not-trusted — verified against the Haven-signed expected context
  at the signer, never authority at the route. Amount, recipient, asset,
  network, window and scheme selection are untouched; the field added to the
  wire is the merchant's own challenge riding back to the merchant.
  **Why review missed it on #2361, recorded so the next echo-shaped change
  checks both halves:** the settle-route test seeded `machine_metadata` with
  `payment_required` already present — it proved the read side and never
  asked who writes the value on this scheme. The QA harness's enforcement
  closed that gap live on Sepolia, which is precisely the
  Haven-against-Haven blindness #2364 was built to end.
  Perimeter unchanged — the added request field is merchant data, never
  spend authority, and nothing is grantable that was not grantable before.
