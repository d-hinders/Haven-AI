- **#2242** — **six copies of a retired security claim corrected across `packages/signer/` and the architecture docs describing it. Prose and comments only: no code path, no authority boundary, no custody boundary moves.**
  `packages/signer/README.md` — a **published npm landing page**, the first thing
  a developer reads before installing the package that will hold their delegate
  key — asserted under § *Custody*: *"The signer makes no network calls — it
  can't leak the key to Haven or anyone else."* That has been false since #1263
  (`9a6198db`), which gave the MCP server layer an authenticated read of a
  signing context from Haven by `payment_id`. PR #2249 replaced the sentence on
  `dev`; #2242 stayed open because further copies of the same retired premise
  were left standing, and because the published `latest` dist-tag still serves
  the old text (operator work, tracked separately as #2310).
  **The custody invariant itself was, and remains, intact — what was false was
  the stated basis for it.** The delegate key is never transmitted:
  `sign-context.ts` sends only an `Authorization: Bearer <api_key>` header and
  the key is never in a request or a response; `core.ts` is network-free and
  never returns the key; the local audit log records neither key nor signature.
  The risk this defect carries is therefore not key leakage but a **false
  egress expectation**: a reader auditing by the README's own reasoning ("no
  network calls, therefore nothing can leak") would run the signer in a
  namespace they believe needs no outbound access, or read the one legitimate
  call as compromise.
  **What the code actually does, established by reading it rather than by
  restating the issue.** The signer's entire network surface is one call —
  `GET ${identity.apiUrl}/x402/${payment_id}/sign-context`, read-only,
  Bearer-authenticated (`packages/signer/src/sign-context.ts`). It is reached
  only through `resolveSignContext` in `tools.ts`, and only under three
  conditions together: (1) the caller uses the `{ payment_id }` form, which
  `haven_sign` and `haven_sign_x402` document as preferred — `resolveSignContext`
  returns `null` immediately without one, so a `typed_data_b64` call is offline;
  (2) the delegate key was loaded from a **file**, since
  `buildSignerMcpServer` passes `options.credentials?.sourcePath` and
  `credentials.ts` sets `sourcePath` only in `loadFromFile`; and (3) an
  `identity.json` carrying both `api_url` and `api_key` sits in that file's
  directory. Fail (2) or (3) — a `HAVEN_DELEGATE_KEY`-only run has no file and
  so no directory — and the path **refuses** with a message naming the
  `typed_data_b64` fallback rather than reaching out. The other two MCP tools
  (`haven_x402_sign_header`, `haven_sign_sweep_delegate`) and the whole library
  surface over `core.ts` never fetch. Nothing in the package relays, submits or
  broadcasts. Each of those claims was independently re-derived by a second
  reviewer against the same files, not taken from this analysis.
  So the honest statement is narrower than the old claim *and* narrower than the
  correction already on `dev`, which reads "makes exactly one kind of network
  call" and so implies an unconditional one. **At most one kind of call, on one
  path, and it is a read** — the corrected surfaces now say that, including the
  start-mode consequence, because an operator sizing egress rules needs the
  condition and not just the endpoint.
  **The six corrected copies.** `README.md` § *Custody*: the network paragraph
  rewritten to the conditional form above, with key-confinement stated
  explicitly ("only the Bearer API key goes out; the delegate key is never part
  of that request or its response") rather than left as a corollary of a
  premise that no longer holds. `src/credentials.ts` file JSDoc: *"it signs, it
  does not call the Haven API"* replaced — the surviving true half (this loader
  requires only `delegate_key`, no `api_key` belongs in this file) is kept and
  scoped as a claim about the credential rather than about the process, and the
  note now explains why `sourcePath` is load-bearing. `src/cli.ts` `--help`:
  *"It has no API access, so it cannot show a live allowance summary"* — the
  conclusion is still true (the one endpoint carries no allowances) but its
  premise was not, so the premise is corrected and the conclusion kept.
  `src/capabilities.ts` module JSDoc: *"the signer never calls the Haven API"*,
  offered as a premise for why skew detection must be agent-mediated. The
  conclusion survives and the premise is replaced with the real reason — the
  one Haven call fetches a payment's signing bytes, not the hosted server's
  handshake, and it happens at signing time, after the quote that module exists
  to get ahead of. `docs/architecture/06-hosted-mcp-connect-flow.md`: "four
  local, no-network tools" above the signer tool table. And
  `docs/architecture/08-local-vs-hosted-mcp.md` § *Key custody*: hosted mode
  narrowing the key surface to a "dedicated, no-network signer" — corrected to
  name the single read and to keep the claim that actually carries the custody
  argument, that the fetch never carries the key.
  **How the last three were found, recorded because the omission is the
  instructive part.** This change first shipped as three corrections, on the
  author's belief — written into an earlier draft of this shard as an
  affirmative statement that `capabilities.ts` had been "re-read and is correct
  as it stands" — that no further copies existed. Two independent reviewers,
  reading separately, each found `capabilities.ts:17` and the doc-reviewer
  found both architecture copies. `capabilities.ts` contradicted **itself**: its
  `signerInstructions()` string, 67 lines below the false JSDoc line, has said
  *"Its one network capability is an authenticated READ of a signing context
  from Haven"* since #1263. A false claim of verification in a compliance record
  is worse than the omission it covers, because it tells a later reader the file
  was checked; that sentence is gone and this paragraph replaces it. The
  author's grep had also returned zero matches for `fetch(` across
  `packages/signer/src/*.ts` — a false zero, since the call site is `fetchImpl(`
  behind a default parameter — which is the same instrument failure in a
  different direction.
  **One further correction, same file, different defect.** `README.md` stated in
  two places that `createEdgeSigner` returns "five" signing methods; the
  `EdgeSigner` interface in `core.ts` declares **six** (`signPaymentHash`,
  `signDelegationTypedData`, `signX402FundingHash`, `signX402FundingTypedData`,
  `buildX402PaymentHeader`, `signSweepAuthorization`; `delegateAddress` is a
  readonly property, not a method). One of the two was pre-existing and one was
  introduced by this change's own new sentence, which repeated it. Both are
  corrected, counted against the interface rather than against the prose. Not a
  custody or authority claim, but wrong published copy in the file whose wrong
  published copy is this issue's subject.
