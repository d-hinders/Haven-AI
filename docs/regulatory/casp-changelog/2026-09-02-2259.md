- **#2259** — The legacy connect-approval half is **deleted**, and this is a deliberate capability removal rather than dead-code cleanup: `POST /agent-connection-setups` carries no rail gate, so a surviving legacy Safe account could still create a setup and reach `active` by two paths, and both are now gone. The first was `POST /agent-connection-setups/:setupId/wallet-approval` itself. The second was quieter and is the reason this is recorded rather than filed as cleanup — the dashboard status read `GET /agent-connection-setups/:setupId` reconciled a `proposed` / `approval_in_progress` setup from live AllowanceModule state and wrote through `persistWalletApprovalState(..., activateAgent: true)`, so a plain authenticated GET was an agent-activation path. That GET is now purely a read, pinned by a falsifiable test asserting the handler issues no `UPDATE`. Deleted with them: `validateWalletApprovalBody` (and its `allowance_module_address` equality check), `tryVerifySetupAuthority`, `maybeActivateFromLiveAuthority`, `isTransientSetupAuthorityVerification`, `normalizeHash`, the `WalletApprovalBody` type, and the OpenAPI path with its generated `api-types`. `rails/allowance-module.ts` loses its last two contract readers (`getTokenAllowance`, `getTokensForDelegate`), the `getContract` binding, the `AllowanceInfo` type and the AllowanceModule ABI fragment, leaving exactly the three shared, rail-agnostic exports `CLAUDE.md` has claimed all along — `getProvider`, `getRelayerWallet`, `getTokenBalance` — and no backend reader of `chain.contracts.allowanceModule` at all (its removal from the shared registry is #2260). **Narrowing only**: nothing gains authority, no signing path, key material, relayer behaviour or on-chain state changes, and no historical AllowanceModule permission is revoked — a permission still live on-chain remains the Safe owner's to revoke externally, exactly as before. The delegation rail's `budget-approval` counterpart is untouched and keeps its 11 tests. **Explicitly NOT done, and recorded because a sweep would get it wrong in the other direction**: the eight `pending_approval` branches and `isPendingApproval` in `packages/mcp-server/src/tools.ts` are **retained**. #2101 kept them deliberately because they are fail-CLOSED — they stop the agent and return the `payment_id` rather than delivering a merchant header for funding that never confirmed — and the row they guard is a stored pre-retirement `payment_intents` row, which epic #1440 deliberately does not delete. The impossible fixture asserting *"legacy rail: insufficient allowance still proceeds … queues for approval"* is **re-based, not deleted**: the legacy rail answers 410 at every payment entry point since #1986, so no fresh intent can produce that status, but a stored row echoed back can — so the test keeps the guided-catalog pass-through coverage it uniquely provides and drops the false claim about how the status arises. Whether the status union itself should shrink stays with #2105, where #2101 put it. Perimeter narrowed.
