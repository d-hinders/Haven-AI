- **#2273** — **a change to the release/QA control surface only: `.github/workflows/qa-dev.yml` (a `controlGlob`) and the freshness guard that watches it. No payment, signing, custody or authorization code moved; the perimeter is unchanged.**
  What changed in the control surface. The money-flow harness's post-deploy
  trigger — `repository_dispatch: [dev-deployed]`, which #2268 measured had
  fired 0 times in the repository's history and the owner established could
  not be sent from Railway at all — is REPLACED by GitHub's `deployment_status`
  event, which Railway's integration emits for every dev backend deploy
  (`railway-app[bot]` → environment `Haven AI / dev`; 28 of the newest 100
  Deployments on 2026-09-02, plus 2 → `Haven AI / production`). A new `gate`
  job, outside the money concurrency group, admits a run only when the status
  is `success`, the environment is the dev backend, the deployment's creator is
  the Railway GitHub App, and the deployment is still the NEWEST for the
  environment — every dev deployment emits `success` twice, so without that
  last check the testnet-money-moving harness would queue twice per deploy.
  Unreadable API → the gate errors and nothing runs. The concurrency group
  moved from the workflow to the money-flow job so a skipped run never holds
  it; `cancel-in-progress: false` is preserved. Workflow permissions gain
  `deployments: read` only. The harness steps (validation of the URL override,
  checkout, build, the bounded-retry run, the completeness gate) are spliced
  byte-for-byte from the previous file; the failure-issue step now records the
  Railway deployment id/sha/creator or the dispatching actor on its `Trigger:`
  line.
  **What the freshness guard now refuses (#2271).** `scripts/ci/guard-freshness.mjs`'s
  registry entry is repointed (not deleted) at `deployment_status` and gains a
  provenance rule: a run counts only if the Deployments API holds a deployment
  of that run's exact `headSha` to `Haven AI / dev` created by
  `railway-app[bot]`. A manual `workflow_dispatch`, a `repository_dispatch`, a
  Deployment created by hand, a skipped run, and a missing index all fail it —
  ten mutations red (skipped counted; provenance dropped; environment and
  creator literals drifted in the workflow; `repository_dispatch` re-added;
  `deployments: read` removed from either workflow; dedupe removed; missing
  index treated as pass; manual runs counted), each restored via `cp` and
  `diff -q`, 41/41 green on the restored tree.
  **Direction of risk.** No authority is grantable that was not before and no
  refusal is loosened: the harness runs the same scenarios with the same
  testnet-only QA identity, only the *when* changed, and the new trigger runs
  strictly less often than a naive one would. The QA credentials still reach
  only the `QA_HAVEN_API_URL` secret or a `workflow_dispatch` override validated
  to a Railway origin (#1047, unchanged). What is honestly NOT proven: the
  trigger has not been observed firing — `deployment_status` runs only the
  default branch's workflow file — so #2268/#2273 stay open in operator-verify
  mode. The `dev → main` promotion gate (`scripts/ci/qa-freshness.mjs`) is
  untouched here — PR #2398 owned it while this was built, and #2404
  (PR #2409, landed in parallel) already made it select by SHA ancestry and the
  `money-flow` job's conclusion, so it admits these runs once they exist. Until
  the first one is observed, promotion coverage rests on the nightly and manual
  runs exactly as it did before this change — no worse, and the guard says so
  loudly.
  Perimeter unchanged.
