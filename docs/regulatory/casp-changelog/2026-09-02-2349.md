- **#2349** — The remaining twelve hosted MCP tools now **REFUSE** an argument they do not declare, where they previously stripped it silently, and the list is **closed**: 19 of the 22 hosted tools are on `STRICT_INPUT_TOOLS`, the three that are not are on an equally explicit `PERMISSIVE_INPUT_TOOLS` with their reasons, and a tool on neither list fails to compile and fails `strict-tool-input.test.ts`. Batch 3 of #2312. **Perimeter unchanged** — no new authority, no new custody relationship, no route, no signing scheme, no migration, no funds moved, and no on-chain envelope altered. What changes is that an input which used to be discarded without a word now produces a 400 before anything is read or written, on twelve more tools.

  **Which twelve, and on what grounds.** `haven_sweep_delegate`, `haven_pay`, `haven_quote_mcp_tool`, `haven_prepare_catalog_purchase`, `haven_quote_catalog_purchase`, `haven_resume_x402_payment`, `haven_get_payment_status`, `haven_get_resume_state`, `haven_list_receipts`, `haven_verify_receipt`, `haven_discover_tools`, `haven_submit_catalog_entry`. Each carries its reason in the code, and the reason is what the refusal message says. The principle that closes the list is the one #2312 opened it with: every hosted schema already advertised `additionalProperties: false`, so permissive behaviour was a contract mismatch on each of them, and the only reason to leave a tool permissive is a live caller that would break. Three shapes recur. **Record-reading** (#2312's category): the catalog prepare and quote take the merchant URL, tool name and arguments from the catalog row `catalog_id` names; a resume rebuilds the retry from the stored payment; a sweep's destination and amount are re-derived by Haven from the prepared authorization — on all of these a stripped `arguments`, `payment_header` or `expected_auth` let a caller believe it had pinned a value that the call then ignored. **Filters and lists**: `haven_discover_tools` and `haven_list_receipts` returned the *unfiltered* catalog or the *first* page looking filtered when a `query`, `offset` or similar was dropped. **Argument-driven**: `haven_pay`'s dropped key is the replay key, and `haven_quote_mcp_tool`'s is a cap that nothing then enforced.

  **`haven_pay` was measured, not inferred, and it is the #2348 `haven_send` total loss again.** Over a real `Client` → `InMemoryTransport` → `buildHostedMcpServer` round trip on 2026-09-02 against `origin/dev` `d09a6cf5`, with `haven_pay` re-registered in its pre-#2349 permissive shape: a call carrying `idempotencyKey: "K-CALLER"` reached the wire as `POST /payments {"token":"USDC","amount":"1","to":"0xabc"}` — **no `idempotency_key` field at all** — while the control carrying `idempotency_key` produced `…,"idempotency_key":"K-CALLER"`. The backend's replay contract never engaged, so a retry was a second spend. On the candidate the same call is refused with `-32602 … unrecognized_keys` and **zero** `POST /payments`; the control still carries the key.

  **No live caller passes an undeclared key to any of the twelve — enumerated before the change.** This was the gating question, because the same rollout hazard pulled `haven_complete_mcp_tool` out of batch 1. Scope: `packages/sdk/` (client and `tool-descriptions.ts`), `packages/mcp/` (the local surface, schema-by-schema for the ten same-named tools — no spelling divergence on any of them; `haven_pay`, the two quote tools and the two catalog tools have no local twin), `packages/connect/` (constructs no tool arguments; its verification instruction names `haven_get_agent` / `haven_get_allowances` with no arguments), `packages/signer/` (`haven_sign_sweep_delegate` returns `{ signature }` only, and the hosted phase-1 response tells the agent to call back with `{ authorization, signature }`), the shipped skill text `packages/sdk/src/skill-content.ts` and its byte-pinned twin `packages/frontend/src/lib/agent-skill-bundle.ts` (names three of the fourteen; none with an argument), `packages/qa-agent/` (the guided-purchase leg passes `catalog_id` + `max_amount` + `idempotency_key`, all declared; the erc7710 leg's settle call is batch 1's), the e2e fixtures (no hosted-tool argument construction), `docs/**` and `.agents/**` (no documented invocation carries an undeclared property). **One undeclared caller was found, test-side, and is fixed here**: `packages/mcp-server/src/tools.test.ts` sent `max_amount: '2000000'` to `haven_quote_mcp_tool`, which has never declared a cap — the #2312 `tools.test.ts:2399` shape again, a cap certified by a test while being discarded. The assertions around it never depended on it.

  **The two `{}` tools are permissive on purpose, and what strictness would mean there was measured rather than argued.** Over the same transport (SDK 1.29.0, `validateToolInput`): absent `arguments` is refused **today** under both the raw shape and `.strict()` (`invalid_type, expected object`); `arguments: {}` passes under both; only a *decorated* call — `{ random_string: "dummy" }` — differs, raw stripping and strict refusing. So `.strict()` on `{}` changes exactly one observable case, and it is a case where nothing can be mis-pinned: `haven_get_agent` and `haven_get_allowances` are `async () =>` handlers that read no input at all. Meanwhile Cursor — a runtime `packages/connect` supports by name (`RuntimeId`), and the one whose connect verification step sends a new user to exactly these two tools — is documented decorating parameterless tools with a `random_string` "Dummy parameter for no-parameter tools" (forum.cursor.com/t/…/109840, Cursor 1.1.6, June 2025, no fix recorded; the report shows the schema rewrite, and does not itself confirm the model echoes the key on every call — the evidence limit is stated rather than rounded up). A refusal would land on the read that could not have been wrong, on the first call a new user is told to make. All three facts are pinned in `strict-tool-input.test.ts` with a discriminating control: a scratch server registering `z.object({}).strict()` over the identical transport *does* refuse the decoration, so "the decorated call passed" is a measurement of the permissive decision and not of a harness that cannot see refusals on an empty schema.
