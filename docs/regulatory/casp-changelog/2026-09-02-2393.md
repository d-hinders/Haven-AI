- **#2393** — **Haven's own shipped agent instructions named the wrong field for `haven_pay`. The guidance is corrected; no tool, route, schema, authority, custody relationship or settlement path changes.** The diff is two byte-pinned copies of one sentence of `SKILL.md` and one test. **No code that constructs, authorises, signs, relays or settles a payment is touched** — `packages/mcp-server/src/tools.ts` is byte-identical to `origin/dev` on this branch, checked with `git diff --quiet` rather than by eye.

  **What was wrong.** `packages/sdk/src/skill-content.ts` — imported directly by `packages/connect` and **auto-installed** into runtime skills folders, and mirrored byte-for-byte in `packages/frontend/src/lib/agent-skill-bundle.ts`, which the connect success screen serves as a download — instructed an agent, for a direct transfer / non-MCP paywall: *"`mcp__haven__haven_pay` with recipient, amount, and token for a plain transfer."* The hosted `haven_pay` schema (`packages/mcp-server/src/tools.ts`) declares `token`, `amount`, `to` and `idempotency_key`. `recipient` is `haven_send`'s spelling, not `haven_pay`'s. So an agent that followed the sentence literally and sent `{ token, amount, recipient }` was refused before any Haven call — `to` is required — and the call made zero Haven requests. This is #2353's defect class (shipped guidance mis-naming a field on a money-path tool) reached from the same side, on a different tool.

  **Why it is recorded here rather than absorbed as a typo.** The correction is to what Haven tells an agent to send, so that what the agent believes it sent matches what the tool actually accepts. The old sentence was not a silent-strip hazard and not a rollout blocker: the permissive shape already answered `-32602 … "to" Required` and made zero Haven calls, so no working flow becomes a 400 and no payment ever moved under a mis-named field. What was defective is shipped guidance on a money-path tool, sitting next to the exact defect class #2312/#2348/#2349 closed. It is stated rather than fixed quietly for the same reason #2353 was.

  **The fix, and why it is safe.** The sentence now names the declared field: *"`mcp__haven__haven_pay` with `to`, `amount`, and `token` for a plain transfer."* The corrected copy only makes a call that already failed start working — it cannot change the outcome of any call that previously succeeded, because the previous spelling was refused before reaching a handler. Both byte-pinned copies change in one PR; the parity test (`packages/frontend/src/lib/__tests__/agent-skill-bundle.test.ts`) holds them byte-identical.

  **Pinned the way #2353 pinned its correction.** `packages/sdk/src/skill-content.test.ts` gains a literal assertion on the corrected sentence, no sentence interpretation (ship-next § Rework caps rule 1): it asserts the `haven_pay` sentence names `` `to` `` and that the old `haven_pay … recipient` shape is gone. It guards the specific shape that was wrong, not the field's mere presence — the word `recipient` is still correct elsewhere in the skill (the decline paragraph), so a blanket `not.toContain('recipient')` would be false. **Mutation-proven, restored from a `cp` backup and verified byte-identical with `diff -q` rather than by inverting the edit:** restoring the old `recipient` sentence in the SDK copy turns the new guard red (1 failed / 13 passed), and the restored tree returns to 14/14. The byte-parity test passes on the corrected twins (9/9).

  **Scope of the check behind "nowhere else."** The wrong instruction was searched for repo-wide with `/usr/bin/grep` (not the shell's gitignore-skipping `ugrep`), quoted globs, and a control search returning >0 before any zero was believed. Two shipped copies carried it (SDK + frontend twin, both fixed here). The hosted `haven_pay` schema, its served description, and the `haven_send` spelling are all correct and unchanged. Every other field name in the direct-transfer sentence (`amount`, `token`) was cross-checked against `toolSchemas` and is already correct.
