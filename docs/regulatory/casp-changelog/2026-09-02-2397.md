- **#2397** — **a test-only change: one added unit test pins existing
  demo-merchant refusal behaviour. No production code, no authority, no
  perimeter movement.**
  `assertExtensionsEchoed` in `packages/demo-merchant-mcp/src/x402.ts` checks
  `payload.x402Version` against the challenge's FIRST and unconditionally,
  before it looks at `extensions`. The `describe('extensions echo rule
  (#2361)')` block pinned drop, overwrite, append and the version-mismatch
  *dodge* (v1 AND a dropped echo). It did not pin a version mismatch with an
  intact echo. That case was established by code inspection and a live capture
  against a running merchant (HTTP 402, `Payment x402Version 1 does not match
  the challenge's 2`) rather than by a test. A companion docs change, #2383,
  writes it into the demo merchant's README; that PR is unmerged at the time
  of writing, so this shard does not rely on it and no claim here depends on
  README prose that is not yet on `dev`. This adds the test and nothing else; `src/x402.ts` is byte-unchanged, verified by
  `git diff --stat` showing one changed file.
  **Why a test-only diff is on the CASP record at all.** It is not a
  money-path change — `packages/demo-merchant-mcp` appears on no glob in
  `.github/money-path-globs.json`, the issue carries no `money-path` label,
  and the demo merchant is a counterparty in the QA harness, never a custodian
  of user funds. The shard exists because `casp-risk-guardrails.md` declares
  `covers: packages/demo-merchant-mcp/src/**`, which is broader than the
  money-path perimeter and fires the blocking contract-doc gate on any change
  under that path, tests included. Recording that distinction is the point:
  the gate firing is not evidence of perimeter movement, and a shard that
  implied otherwise would misstate the record.
  **Direction of risk: none, in either direction.** Nothing is grantable that
  was not grantable before, and nothing that was refused before is now
  accepted. The change adds an assertion over behaviour that already shipped
  under #2361/#2364; it cannot alter what the delegate authorized, what the
  merchant settles, or what any refusal says, because no non-test byte moved.
  The demo merchant's strictness — deliberate, so a Haven client that stops
  echoing fails in the Sepolia QA harness rather than at the first strict
  mainnet facilitator — is unchanged in substance and is now one case better
  covered.
  **Mutation-tested, and the result corrected the issue's own claim.** The
  issue predicted that "reordering the version check after the subset check
  (or deleting it) makes exactly this test fail". Measured on this branch:
  deleting the check fails TWO tests (this one and the dodge), and reordering
  fails only the DODGE test while this one still passes — reordering leaves
  the check reachable, so a perfect-echo payload is still refused, just later.
  The mutation this test uniquely catches is a version check made
  *conditional* on a missing echo (the plausible "only cross-check when the
  echo looks suspect" edit): that fails this test alone, 1 failed / 25 passed.
  Each mutation was restored via `cp` from a pre-mutation copy and verified
  with `diff -q`; the suite is 26/26 green on the restored tree.
  Perimeter unchanged — a test was added, no production code was touched, and
  nothing about who may spend, sign, or execute is different.
