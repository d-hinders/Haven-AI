- **#2404 (promotion gate: which QA runs count)** — **no route, authority,
  custody or execution boundary moves; this is a CI gate script that can only
  ever refuse a `dev → main` promotion.** `scripts/ci/qa-freshness.mjs` is a
  `controlGlob`: the last automatic check between unverified money-path code
  and production, so it is labelled money-path and gets this record without a
  QA re-run (the harness cannot test the gate). What changed: the query that
  picks the green money-flow run no longer filters `--branch dev`. #2273 fires
  the post-deploy run from GitHub's `deployment_status` event for a Railway
  Deployment created against a bare SHA, and GitHub documents `GITHUB_REF` as
  "empty if commit" for that case — so the run that tests exactly the deployed
  commit carries no branch label and the old filter dropped it. The gate was
  answering a different question than it claimed. Selection is now a pure,
  tested function over a window of green runs: event in `{deployment_status,
  schedule, workflow_dispatch}`; commit an ancestor of the promotion head
  (`git merge-base --is-ancestor`, checked for every event — strictly stronger
  than the label, and the label is still required on the two events that carry
  one); and the `money-flow` **job** concluded `success` — because a run whose
  `gate` job skipped the harness has run-level conclusion `success` (measured on
  three `ci.yml` runs whose jobs were `skipped=7,success=7`), so `--status
  success` alone would have anchored a promotion to a "green" run at the
  deployed SHA in which nothing ran. That third rule closes a hole the widening
  would otherwise have opened, and it applies to every event. Newest admitted
  run wins; provenance is a tie-break at the same commit only, so the documented
  re-dispatch-after-fix route still clears a red gate rather than routing
  through `qa-override`. `repository_dispatch` is refused outright (#2271).
  **Unverified leg, named:** no `deployment_status` run exists in the repository
  as of 2026-09-02 (#2273 unmerged; the event runs only the default branch's
  workflow file), so "no `headBranch`" is what the GitHub docs and Railway's
  bare-SHA Deployments predict, not what a run has shown; the rules give the
  same answer either way. **Six mutations, six kills**, each restored and
  `diff -q`-verified: restoring `--branch dev` (2 tests red, naming the
  deployment run), dropping the ancestry check (2), dropping the job check (6),
  dropping the branch-label check for `schedule`/`workflow_dispatch` (1 — added
  by review, which re-ran every mutation itself), making `evaluate()` excuse an
  uncovered money-path change for a `deployment_status` run (1), and dropping
  `event` from the `--json` projection (2 — the selector fails closed on a row
  with no event). The "before"
  leg is carried in the suite: the pre-#2404 query, replayed through a model of
  gh's `branch` filter written from the REST docs, returns the older manual run
  and not the deployment run. `evaluate()` and the money-path glob matching are
  untouched; the gap-1 coverage rule and every fail-closed branch are pinned as
  before, 79 tests pass (was 55). Review of the first version found the
  commit ordering could be skewed by a row that was later refused (a
  fail-safe direction — a spurious block — but it contradicted the header's
  own invariant); the selector now lets only ADMITTED rows decide which commit
  anchors the diff, with a regression test for that shape. Haven still custodies nothing, still holds no
  user key, still signs no settlement. Perimeter unchanged; the promotion gate
  now sees the run that tests the deployed commit, and refuses the one that
  merely looks green.
