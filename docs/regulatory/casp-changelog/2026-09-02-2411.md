- **#2411** — **budget activation retired the grant it had just activated; fixed, and the invariant no longer depends on statement order. No authority, custody or execution boundary moves.**
  `POST /agents/:id/delegations/:hash/activate` runs one transaction: lock the
  agent row, retire every `active` grant in the (agent, token, recipient) slot
  as `replaced`, flip the pending row `active`, activate the agent (#1053/#1061).
  #2331 (`b21727b7`) moved the activation into the repository
  (`activatePendingDelegation`) and, in doing so, ran it BEFORE the sweep — and
  the sweep, still inlined in the route, had no `id <>` exclusion. So the sweep
  retired the row the previous statement had just activated: every activation
  since the 2026-09-02 07:46Z dev deploy committed with ZERO active rows in the
  slot, and the first payment 403ed on `SELECT_DELEGATION_FOR_PAYMENT_SQL`
  (`status = 'active'`) from both `modules/x402/delegation-authorize.ts` and
  `routes/payments.ts`. Diagnosed and reproduced on real Postgres 16 on the
  issue before this PR; the two failing `qa-dev` legs are the two fresh-agent
  activate-then-pay scenarios, and the twelve warm legs pass because the shared
  QA agent's grant predates #2331.
  **The fix is both halves, and each is proven load-bearing on its own.** The
  sweep moves into the repository as `replaceOtherActiveDelegationsInSlot`
  with `AND id <> $4` (the pending row's id, threaded as a parameter — no SQL
  built by concatenation), and the ordered pair becomes ONE repository call,
  `activatePendingDelegationInSlot`: sweep first, then activate. The route
  makes that single call, so no future route edit can reorder the statements;
  and the exclusion makes the sweep correct in either order anyway. A real-DB
  `describeDb` test seeds a pending row over an older active one in the same
  slot, runs the call inside a transaction, and asserts exactly one active row
  remains, that it is the new one, that the payment selector returns the new
  hash with the signed JSON, and that a recipient-pinned grant, another token's
  grant and another agent's grant are untouched. Mutation matrix over that test,
  each cell restored by `cp` and checked `diff -q` byte-identical: fixed order
  with the clause, exit 0; #2331's order without the clause, **exit 1** (the
  slot's active set is `[]`, the row is `replaced`); fixed order WITHOUT the
  clause, exit 0 (order protects it); activate-then-sweep WITH the clause,
  exit 0 (the clause protects it). The clause has its own pin — a sweep run
  with the excluded row already active retires only its sibling — red in the
  no-clause cells; and the mocked route test pins the statement order and the
  pending id in the sweep's parameters, red in both reordered cells. A third
  real-DB test pins the documented contract that a `false` return (row no
  longer pending) leaves the sweep for the caller's ROLLBACK, which is the
  route's existing 409 path. The new statement is PREPARE-checked by
  `db-schema-smoke` by import.
  **CASP argument.** Spend authority on this rail originates in the
  owner-signed delegation and is enforced by the on-chain caveat enforcers;
  `agent_delegations.status` decides only which owner-signed grant Haven
  *selects* when constructing a redemption. A sweep that retires one row too
  many (the defect) makes Haven refuse to construct a payment the chain would
  honour — fail-closed, the wrong way round; a sweep that retired one too few
  would leave a superseded, still-owner-signed, still-revocable grant
  selectable, which the recipient/budget/expiry caveats bound exactly as
  before. Neither direction can create, widen, redeem or move authority; no
  signature is produced, verified or stored differently; the owner's revoke
  path is untouched. Red Lines 1-5, *Make All Agent Authority User-Approved*
  and the Payment-Related Merge Checklist re-read for this change: the
  activate route still stores the OWNER'S signature over a delegation the
  owner built, still cannot activate without it, and still cannot widen a
  budget. This fixes Haven *losing track of* an active grant, not granting one.
