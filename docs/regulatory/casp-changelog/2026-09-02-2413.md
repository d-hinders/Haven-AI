- **#2413** — The dashboard stops rendering retired-rail accounts, and every `account_type` branch behind that rendering is deleted. Epic #1440's owner decision of 2026-09-02 is that retirement is deletion rather than accommodation, so rather than maintain ~25 files of branching to present a legacy Safe account nicely, the account and agent list queries stop returning those rows: `LIST_SAFES_FOR_USER_SQL`, `LIST_SAFES_WITH_ACCOUNT_TYPE_FOR_USER_SQL` and `LIST_SESSION_SAFES_FOR_USER_SQL` (the `/auth/me` projection that feeds the dashboard's active account) gain `AND account_type = 'delegator_hybrid'`, and `LIST_AGENTS_FOR_USER_ALL_STATUSES_SQL` gains the same predicate on its joined account. `= 'delegator_hybrid'` is an equality test rather than `<> 'safe'`, so it also excludes any future value. It does not exclude NULL: `041_hybrid_accounts` added the column `NOT NULL DEFAULT 'safe'` under a two-value CHECK, so legacy rows were backfilled to `'safe'` and NULL is not in the column's domain. **This is a filter, not a migration**: no row is deleted, the rows remain readable to any direct query, and reversing it is one clause — the same reversibility argument that kept `rails/execution-rail.ts`. Dropping the rows outright is a separate, still-open decision on the epic, blocked on `payment_intents`' RESTRICT foreign key. **Two consequences are deliberate and recorded rather than discovered.** First, a user whose only account is legacy now sees no accounts and is routed to onboarding, which provisions a Hybrid DeleGator; there is nothing for them to lose, since the retired rail has answered HTTP 410 at every payment entry point since #1986. Second, an agent ORPHANED by an account unlink (`safe_id` NULL) is excluded too, because the LEFT JOIN gives it a NULL `account_type`: an owner decision on the same date, on the evidence that since #2331 such an agent receives 403 from `agentAuth` on every route and the single exemption — sweep recovery — refuses it as well, because `has_bound_safe` is false. It is a dead record, not a usable one. Deleted with the branches: `RetiredRailNotice`, `useRetiredRailOwnerAccess`, `retired-rail-owner-access.ts` and `useSafeDetails` (whose last consumer was that classifier); the custody page's `SafeControlCard`; `ReplaceSigningKeyModal`'s rail refusal; the connect flow's `isDelegationRailAccount` gate, its `retired_rail` step view and the `approval_in_progress` / `proposed` mappings that only the legacy wallet-approval could produce; `custody-rail.ts`'s `railOf` and rail-keyed claim table; and `AccountDetailClient`'s "Required approvals" and "Approvers" blocks, which were fed by the Safe-details read and were already inert for a delegation account because that read was gated to the retired rail. **Narrowing only**: no authority is granted, no signing path, key material, relayer behaviour or on-chain state changes, and no historical AllowanceModule permission is revoked — one still live on-chain remains the Safe owner's to revoke externally, exactly as before. Tenant scoping is untouched: every filtered query keeps `user_id = $1` and the new clause only narrows further, pinned by a real-DB case that seeds both rails for the same user. Perimeter narrowed.
