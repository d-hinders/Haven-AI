- **#2415** — **budget activation no longer holds the agent row lock across an RPC call. No authority, custody or execution boundary moves; the refusal it protects is byte-identical.**
  `POST /agents/:id/delegations/:hash/activate` runs one transaction: lock the
  agent row, retire the slot's other active grants, flip the pending row
  `active`, activate the agent (#1053/#1061/#2411). #2331 added a correct guard
  inside that transaction — refuse a pending delegation built for a delegate key
  the agent has since rotated away from — by recomputing the delegate's hybrid
  account address under the lock. `computeHybridAccountAddress` →
  `buildWatchOnlyAccount` → `toMetaMaskSmartAccount` costs **one RPC**, per its
  own docstring at `rails/hybrid-provisioning.ts:84`, so a slow or hanging RPC
  held both a pooled connection and the `FOR UPDATE` agent row lock. Everything
  that lock serializes blocked behind it: Safe unlink, re-key open, re-key
  completion, and sibling grant activations for the same agent. An availability
  defect, not an authority one — which is why the fix must not buy latency with
  a weaker refusal.
  **The fix keeps the guarantee and drops the network call, by splitting the
  comparison in two.** The derivation moves ABOVE `pool.connect()` and runs on
  `agent.delegate_address` — the pre-lock `loadOwnedDelegationAgent` read — and
  under the lock the route asserts `lockedAgent.delegate_address` still equals
  that exact key, in addition to the existing comparison of the stored
  delegation's own `delegate` field against the derived address. Those two
  together say the derived address IS the current delegate's account at commit
  time, which is precisely what #2331's single comparison said. A re-key that
  commits between the pre-lock read and the lock changes the key and is refused
  with the same 409 and the same message, `Delegation was built for a previous
  delegate key`. Between `BEGIN` and `COMMIT` there is now no network call at
  all.
  **No column and no migration, deliberately, and the issue's proposed shape is
  the reason.** #2415 suggested persisting the delegate address on the pending
  row at `build` time and comparing the stored value under the lock. That value
  is by construction identical to the `delegate` field already inside
  `delegation_json` — both are written from the same `delegateAccountAddress`
  local in the same handler — so the comparison would be a value against itself
  and would prove nothing about rotation. The check needs the agent's CURRENT
  key, which is what the RPC was deriving and what the locked row already
  carries. So the perimeter gains no schema change, `CODEOWNERS` is not
  implicated, and `infra/repositories/{agents,delegation-budgets}.ts` are
  untouched.

  **CASP argument.** Spend authority on this rail originates in the owner-signed
  delegation and is enforced by the on-chain caveat enforcers; this change moves
  a read-only, deterministic address derivation from inside a transaction to
  just before it, and adds an equality check on a column the same transaction
  already locks. Nothing signs, verifies or stores a signature differently; no
  amount, token, recipient, route or expiry is touched; no delegation is
  created, widened or redeemed; the owner's revoke path is untouched. The set of

  rule out are (a) refusing an activation that should succeed, which would be
  fail-closed and is pinned by the unchanged happy-path suite, and (b) admitting
