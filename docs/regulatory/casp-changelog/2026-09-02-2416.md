- **#2416** — **a budget grant refused for an in-flight re-key said "revoked"; the reason reporting is now discriminated. No authority, custody or execution boundary moves, and the set of refused requests is unchanged.**
  `POST /agents/:id/delegations/build` (grant step 1) refused with the fixed
  string `Revoked agents cannot receive new budget delegations` whenever
  `insertPendingDelegationForOwnedNonRevokedAgent` returned `false`. That was
  accurate when the helper's only refusal was a revoked agent. #2331 widened
  `lockOwnedNonRevokedDelegationAgent` to FOUR refusals — revoked agent, an
  account that is not `delegator_hybrid`, a missing `delegate_address`, and an
  in-flight re-key (`agent_rekeys.stage IN ('preflight','revoked','metered','issued')`)
  — and all four kept the one sentence. The re-key case is the one that reaches
  a real owner: start a re-key, park it, then try to set a budget on a
  perfectly healthy `active` agent and be told the agent is revoked. The
  sibling `activate` handler in the same PR got correct wording
  (`Agent cannot receive a budget while its account or re-key is unavailable`);
  `build` did not follow.
  **What changed is the sentence, never the decision.** The refusal is already
  final when the new code runs: `inserted` is `false` and the response is a 409
  either way. Precisely, because a regulatory record should not assert a
  mechanism it does not have: the helper returns `false` from inside
  `withTransaction`'s callback, which is a normal return, so the grant
  transaction COMMITs empty rather than rolling back — the lock matched no row
  and nothing was written. The refusal is carried by the boolean, not by an
  aborted transaction; what matters here is that no delegation row exists
  either way. A route-local
  `describeBuildRefusal` re-reads the agent (and, only then, the `agent_rekeys`
  EXISTS probe) to decide which 409 body the owner sees. Its branch order
  mirrors `lockOwnedNonRevokedDelegationAgent`'s own SQL — status, then
  `account_type`, then `delegate_address`, then the re-key probe — so when more
  than one reason holds, the message names the one the lock actually stopped
  on. The four refusal strings became exported constants and the three
  pre-checks above the insert now use them, so the pre-check and the
  post-refusal paths cannot drift into two different sentences for one reason.
  Deliberately NOT done: no change to `infra/repositories/agents.ts` (the
  natural home for a typed reason, and the file `ship-next` would otherwise
  have reached for) — it is claimed by #2413 in a parallel session, and a
  second writer on a money-path repository file is the collision this
  repository's claim protocol exists to prevent. The already-exported
  `HAS_IN_FLIGHT_REKEY_FOR_AGENT_SQL` is imported read-only instead.
  **CASP argument.** Spend authority on this rail originates in the
  owner-signed budget delegation and is enforced on-chain by the caveat
  enforcers; `build` only returns EIP-712 typed data for the OWNER to sign and
  stores a `pending` row. This change touches neither. It creates no
  delegation, widens no budget, produces, verifies or stores no signature, and
  reads nothing on-chain; it runs strictly AFTER a refusal and cannot turn one
  into a grant. Haven still holds no key, signs nothing here, and the owner's
  revoke path is untouched. The re-key wedge itself — a parked re-key holds its
  slot against a new grant, fail-closed, on the owner's explicit abandon signal
  and never on a clock (#1868) — is unchanged in kind and in code; what changes
  is that a correct fail-closed refusal stops being reported as a broken
  account. Red Lines 1-5, *Make All Agent Authority User-Approved* and the
  Payment-Related Merge Checklist re-read against the diff: no line moves.
  Telling an owner the wrong reason for a correct refusal is a disclosure
  defect, not an authority one, and fixing it does not become an authority
  change.
