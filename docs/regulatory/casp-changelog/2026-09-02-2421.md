- **#2421** — **a second npm publish channel (`dev`) is added to the existing publish workflow. No authority, custody, execution or disclosure boundary moves; what changes is which artifacts reach which dist-tag, and a new refusal that keeps them apart.**
  Slice 1 of epic #2420. `.github/workflows/publish.yml` now fires on a push to
  `dev` as well as `main`. On `dev` it computes
  `0.0.0-dev.<YYYYMMDDHHMM>.<shortsha>`, runs `scripts/release-bump.mjs` over
  the CI checkout with a new `--snapshot` flag, builds, and publishes all five
  published packages under the **`dev`** dist-tag. Nothing is committed: the
  checkout is discarded with the runner. The `main` path is unchanged —
  version-gated, tag derived from the version (`alpha`/`latest`), per-package
  failure isolation (#1159) and step-summary table all reused rather than
  reimplemented.
  **Why this is money-path at all.** No payment is constructed, signed,
  authorised or executed by this change, and no schema, route, rail, budget,
  delegation or key handling is touched — the diff contains no
  `packages/**` source file. It is money-path by the FILE half:
  `.github/workflows/publish.yml` and `scripts/release-bump.mjs` are both
  `controlGlobs` in `.github/money-path-globs.json`, i.e. the money-path
  safeguard's own control surface. That classification is exactly right here.
  This workflow is the mechanism by which the signer that holds a delegate key
  and the SDK that constructs payments reach a user's machine, so a defect in
  it is a supply-chain defect on the spend path even though the diff never
  mentions spending. `controlGlobs` and not `globs` for the standard reason:
  re-running the money-flow QA harness proves nothing about a CI config
  change, so the change is labelled and read by a human without forcing a
  `qa-freshness` re-run.
  **The invariant, and what enforces it.** *A snapshot must never be able to
  land on `alpha` or `latest`, and the `main` path must never publish a
  `0.0.0-dev.*` version.* Three independent enforcement points, because they
  fail differently:
  (1) a **ref/channel refusal** in `publish.yml`'s "Resolve the publish
  channel" step. This is the only route by which `dev`-branch code could reach
  `alpha`: a `workflow_dispatch` of `channel: prod` on the `dev` ref would skip
  the snapshot bump and publish the committed release version under its own
  prerelease tag, and nothing downstream could tell, because by then the
  version and the tag both look ordinary.
  (2) `assert_publish_allowed()` in `publish.yml`, called immediately before
  **every** `npm publish` and deliberately outside the per-package failure
  isolation — a package failing to publish is an incident, a channel/version/tag
  combination that should be impossible is a defect in the file, and continuing
  the loop would publish four more of them. It is called BEFORE the
  already-on-npm skip, so a version that should never have been built fails the
  job loudly instead of being reported as "someone got there first".
  (3) `scripts/release-bump.mjs --snapshot`, whose check is **bidirectional**:
  `--snapshot` requires a `0.0.0-dev.*` version, and a run WITHOUT it refuses
  one. That second half is what keeps a snapshot version from being committed
  to a release branch, riding the `dev → main` promotion and reaching the
  production channel — the only path to `alpha` that no CI condition on a ref
  can see. It runs before the first write, so a refusal leaves the tree
  untouched.
  **`0.0.0-` is load-bearing, not cosmetic.** It sorts below every real
  version, so no `^0.1.x` range can resolve to a snapshot by accident and no
  reader has to reason about whether `dev` or `alpha` wins as a prerelease
  identifier. Verified against the workspace semver rather than assumed:
  `semver.lt('0.0.0-dev.202609021905.abc1234', '0.1.28-alpha.0')` is `true`.
  The same check found the one shape that is NOT valid semver — an all-digit
  short sha with a leading zero (`0.0.0-dev.<ts>.0123456` returns `null` from
  `semver.valid`, roughly 1 commit in 4300) — which is now refused at
  computation time with an actionable message rather than dying inside the
  bump.
  **Why the bump script is reused rather than five versions being set by
  hand.** The version lattice is not five numbers: `@haven_ai/connect` pins
  exact sibling versions in `runtime-manifest.ts`, the signer is installed into
  a version-named directory, and five source constants are baked into the
  bundles. Hand-setting the versions would ship a snapshot whose connector
  resolves a different signer than the one it was built against — a
  supply-chain hazard on precisely the package that holds the delegate key.
  The bump script rewrites all of it atomically and runs
  `verify-connect-bundle.mjs`, unchanged, in both modes.
  **Mutation-proved in both directions, every cell restored by `cp` and
  verified byte-identical by `shasum -a 256`.** The two `publish.yml` guards
  were driven by extracting their real shell out of the YAML (via the parser,
  so there is no hand-copied second copy to drift) and running it: with the
  guards intact, 6 resolve cases and 11 publish cases classify correctly,
  including three CONTROL cases that must be ALLOWED. Deleting the prod-channel
  `0.0.0-dev.*` refusal → the snapshot version is **allowed** under `--tag
  alpha` and `--tag latest` (exit 0), i.e. the guard is what stops it.
  Disabling the ref/channel mismatch refusal → `channel=prod` on the `dev` ref
  is **allowed** (exit 0). Disabling the "no snapshot without `--snapshot`"
  half of the bump check → 1 red in `release-bump.test.mjs`, by name.
  **Regulatory reading.** Haven custodies nothing here, holds no user key,
  signs nothing and moves no funds. Red Lines 1-5 and the Hard Architecture
  Invariants re-read against the diff: none moves — this change cannot create,
  widen, verify or redeem a delegation, and no code path in it reaches a chain,
  a database or a payment. The *Payment-Related Merge Checklist* is not

  **A false verification claim in an earlier draft of this shard, corrected and
  recorded rather than quietly fixed.** This paragraph read "Suites:
  `npm run release:bump:test` 39 passed." It was **38 passed, 1 failed**. The
  cause was ordering, not judgement: the suite was run green, and only
  afterwards did the `cli` build line get added to the snapshot step — which
  broke a pre-existing guard, `'the manual fallback builds in the order
  publish.yml builds in (#1791)'`. That guard scanned the WHOLE workflow for
  `npm run build -w packages/X` and compared the flat list against the manual
  fallback documented in `scripts/README.md`; a second build step in the file
  made it read `['cli', 'sdk', 'signer', 'mcp', 'connect', 'cli']` against a
  documented five. `haven-doc-reviewer` re-ran the one claim here that was
  concretely re-runnable and it did not hold. The lesson is the one this
  repository already writes down: a regulatory record must not assert a check
  that was not run against the artifact being recorded, and "I ran it earlier"
  is not that.
  **What that finding changed in the code.** `scripts/README.md` was NOT wrong
  — the emergency manual path is the break-glass substitute for the PROD
  publish path and is still those five in that order — so the guard was
  rescoped to the prod build step rather than the documentation being edited to
  match a widened scan. Narrowing a guard is how guards die, so the narrowing
  is itself pinned: the helper asserts the step it selected carries
  `if: steps.channel.outputs.channel == 'prod'`, and the test asserts the
  selected step still builds every published package, so a scope that silently
  collapses to the wrong step or to nothing fails rather than passing
  vacuously. A NEW guard was added for the defect class the `cli` line existed
  to fix — `'the dev-channel snapshot BUILDS every package it publishes'` —
  because nothing in the repository could see it: `release-bump.mjs` wipes all
  five dists and `publish.yml` builds them, and both files are individually
  correct.
