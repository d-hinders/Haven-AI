  **What changed, exactly.** The module constant `CONNECTOR_PACKAGE`, previously
  the literal `'@haven_ai/connect@alpha'`, is now
  `` `@haven_ai/connect@${config.connectorChannel}` ``. `config.connectorChannel`
  is `alpha` unless `HAVEN_CONNECTOR_CHANNEL` is set. It feeds exactly two
  agent-facing strings — the `npx -y …` setup command and the consent copy's
  "download and execute the published npm package …" line — plus a new
  `connector_package` field on the create and status responses, so the frontend
  reads the spec instead of restating `@alpha` as a client-side literal.
  **What did NOT change.** No signature is produced, verified or stored
  differently. No delegation is created, widened, activated or revoked. No
  amount, token, recipient, chain, expiry, route or authentication check is
  touched. `POST /:setupId/budget-approval` — the handler that verifies the
  signed delegation against the setup and flips setup and agent to `active`,
  i.e. the reason this file is on the perimeter at all — is not in the diff.
  Neither is `verifyDelegationSetupAuthority`, the `allowance_granted` funnel
  event, or the one-budget-per-agent rule. The setup token, its hashing and its
  single-use consumption are untouched. No migration, no schema change, so
  `CODEOWNERS` is not implicated.
  **CASP argument.** This changes which npm dist-tag a human or agent is told to
  install, not what Haven does with what they install. Haven still custodies
  nothing, still holds no user key, and the connector still generates the
  signing key locally and sends Haven only the public address plus proof — that
  sentence is in the consent copy and is unedited. Red Lines 1-5,
  *Make All Agent Authority User-Approved* and *Use On-Chain Enforcement
  Wherever Account Authority Is Exercised* were re-read against the diff:
  authority still originates in an owner-signed delegation enforced on chain,
  and nothing in this diff sits between the owner's signature and that

  **The one real risk, named rather than waved away: this field decides which
  npm package a user is told to execute.** A channel is therefore an
  execution-surface value, and it is treated as one in two ways. First, the
  package spec is interpolated into `npx -y <spec> …` **unquoted** — `shellQuote`
  in the same file covers the setup token and the API URL, not the spec — and
  that command is pasted into a real terminal, so the validator is a shell
  boundary, not a label check. `/^[a-z][a-z0-9-]{0,31}$/` excludes whitespace,
  quotes, `;`, `&`, `|`, `$`, backticks, parentheses, redirection, `\`, `/` and
  `@`; a test enumerates every one of those and is mutation-proved. Second, the
  scope of the value is bounded by construction: the pattern cannot express a
  different package, only a tag on `@haven_ai/connect`, so a compromised
  environment variable can select a different Haven-published channel and
  nothing else. Setting the variable is a deployment action available only to
  whoever already controls the deployment.
  **An invalid value REFUSES THE BOOT rather than falling back to `alpha`, and
  that direction was chosen, not defaulted into.** A silent fallback is the
  worse failure here: a typo (`HAVEN_CONNECTOR_CHANNEL=dve`) would land on the
  production channel, the dev dashboard would keep handing out the production
  connector, and the environment would look FIXED while reproducing the exact
  defect this slice removes. A refusal is loud, is attributable to one named
  variable, and cannot half-serve traffic — the process never accepts a
  request. The refusal message says in words that it is not falling back,
  because "invalid value" alone invites the assumption that the service came up
  on the default. The residual, recorded rather than hidden: a *well-formed but
  wrong* tag (`dve`) is accepted by this validator and fails later at `npx`,
  where the error names the package. A test asserts that limit explicitly
  instead of leaving it implied.
  **Mutation proofs, each restored by `cp` from a pristine copy and checked
  `diff -q` byte-identical before proceeding.** (1) Default `alpha` → `dev`:

  runnable-instruction cases plus #1719's never-back-through-setup guarantee.
  Three further mutations on the skew-fallback sentence, added after the
  rendered design re-review reshaped it, each **2 red / 11 green**: bare flags
  with no invocation; a second backtick pair (the sentence lands in a `<dd>`
  that does no markdown parsing, so pairs render literally); and dropping the

  one that matters most and it is the one written against a **literal**: every
  pre-existing assertion in the route suite reads
  `` toContain(`npx -y ${CONNECTOR_PACKAGE}`) `` and would follow a drifted
  default silently, which is precisely the test-that-cannot-fail shape.
  **The mutation harness itself was proven before its output was believed.**
  A first run reported all three fallback mutations "red"; they were not. The
  replacement strings carried unescaped backticks, which terminated the
  template literal early, so vitest collected **no tests at all** and the
  summary line read `Tests no tests` — a shape that greps as "not passing".
  The harness now asserts the unmutated tree is green before it starts and
  refuses to score a run that collected nothing, so a syntax error cannot
  masquerade as a caught defect. Recorded because a mutation proof whose
  instrument cannot say YES proves nothing, and this one briefly could not.
