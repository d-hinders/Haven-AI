- **#2522** — **hand-off links so an agent can point a human at the exact step it cannot perform itself. No authority, custody, execution or disclosure boundary moves; no payment is constructed, signed, authorised or executed.**
  Three deep links (`/signup?next=`, `/onboarding?next=`, `/agents?setup=<id>`),
  an `approval_url` on the connection-setup create and status responses, and an
  attribution marker (`via=agent`) stored on two new nullable columns.
  **Why this is money-path at all.** By the MIGRATION rule only. Migration 076
  adds `users.via` and `agent_connection_setups.via` — both nullable TEXT, no
  default, no backfill, no existing row read or rewritten. Nothing about a
  rail, budget, delegation, allowance, key, or settlement path is touched. The
  approval step these links route a human TO is unchanged: the WebAuthn
  signature and `POST /agents/:id/delegations/:hash/activate` are not in this
  diff.
  **What the links can and cannot do.** They can put a human in front of a
  budget-approval screen. They cannot approve anything: `/agents?setup=<id>`
  carries no setup token — that is a create-time secret and deliberately absent
  from this path — and the modal renders from `GET /agent-connection-setups/:id`,
  which is owner-scoped and answers 404 for a setup belonging to anyone else. A
  pasted link handed to the wrong person therefore reaches a not-found state,
  not somebody else's agent.
  **The disclosure-adjacent risk this closes.** `next` is handed to
  `router.replace`, so an unsanitised value is an open redirect — a Haven URL
  that lands the user on someone else's page, which is the shape a credential
  phish takes. `sanitizeNextPath` accepts same-origin paths only, and an origin
  check alone was measured to be insufficient: `/..//evil.com` resolves to the
  same origin while its pathname is `//evil.com` (protocol-relative, so the
  browser leaves the site), and a tab inside a path is silently stripped during
  parsing, so the string checked is not the string resolved. The sanitiser
  therefore tests the leading slashes of the RESULT and refuses control
  characters rather than stripping them. Both cases are pinned verbatim in
  `packages/frontend/src/lib/__tests__/handoff-links.test.ts` and were
  mutation-proved — removing either guard fails exactly the case that names it.
  **Attribution collects nothing new about a person.** `via` is an ENUM whose
  only legal value is the literal `agent`; every other input is dropped to
  NULL. It records what an agent PASTED, not who anyone is, and deliberately
  not a user agent — which says what a client claimed to be and is wrong by
  construction here, since the human arrives in an ordinary browser. No IP, no
  device signal, no free text: a free-text column was rejected precisely
  because it would let whoever writes a link put arbitrary content into stored
  data and into the funnel metric.
  **Enforcement.** Real-DB tests (`handoff-attribution.test.ts`) pin both
  columns, the funnel metadata, and the segment query; three mutations (drop
  `via` from the SELECT projection, bind null into the setup insert, bind null
  into the user insert) each failed exactly one test with every file restored
  byte-identically. The full backend suite (230 files, 2996 tests) is green
  with the new column and the changed `insertUser` signature.
  **One key was NOT reused, and that decision is the shard's main record.** The
  funnel metadata already carries `via`, meaning which CODE PATH created a
  record (`'connection_setup'`; absent from `POST /agents`). Writing the
  hand-off marker there would have given one key two meanings and silently
  redefined every historical row — an audit trail quietly changing meaning
  under rows already written. The marker rides as `handoff_via`, and a test
  pins both keys surviving one emission.
