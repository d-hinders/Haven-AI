# 2026-09-04 — #2523: the connector's rule sentences move to one home in the SDK, and are published to agents as `/for-agents.md`

Prose only. A new `packages/sdk/src/agent-guidance.ts` holds seven sentences
that already existed verbatim inside `buildSetupPrompt`
(`packages/backend/src/routes/agent-connection-setups.ts`) plus a new agent

No route, schema, rail, budget, delegation, key-handling or execution change.

`packages/backend/src/routes/agent-connection-setups.ts`, and that file is a

**What changed, as authority.** Nothing. The setup prompt the backend returns is
byte-for-byte the string it returned before — proved by execution, not by
reading: `agent-connection-setups.test.ts` pins each sentence as a literal and
separately asserts the prompt contains the SDK exports, and the suite's
`matches the e2e fixture setup_prompt mirror line for line` test compares the
whole prompt against `packages/frontend/e2e/fixtures/haven-api.ts`. Mutating one
imported sentence by a single word (`should` → `SHOULD`) turns both red; the
file was restored from a content-verified backup (`cmp`). The extraction removes
the *possibility* of divergence between the prompt an agent is pasted and the
runbook it fetches, which is a narrowing of an instruction surface, not a change
to any authority.

**What the new page says about authority.** `/for-agents.md` is written to an
agent whose user has no account. Its attribution follows § Product Copy Rules:
the budget is "a delegation they sign, enforced on-chain", the opening sentence attributes the grant to the user ("Your user gives you a budget on their own account", corrected on review from a first draft that made Haven the giver — the § Product Copy Rules inversion), the vocabulary
table says "It authorises the payment; Haven constructs and relays it", and the
page never claims Haven grants, approves or holds anything. It states four
human-only steps (account + passkey, funding, budget, approval) and instructs
the agent to hand over a link for the first three and, for the approval, to send the user back to the Haven tab that completes it (see the correction below) — the owner constraint recorded on #2519 that
the human keeps every signature. A test asserts the page carries
"I will never ask for your password" and matches no instruction to enter the
user's credentials, with a positive control on the same matcher family.

**Custody.** Unchanged. Nothing in this diff reads, writes, transmits or

**A false claim caught in review, and what replaced it.** The first draft's
budget-approval hand-off told the agent to relay `<approval_url>` and said the
`--json` outcome carried the approval link and the setup id. Neither is true:
`ConnectOutcome` carries `approval: { required, expires_at }` and nothing more,
`--json` prints that object alone, and the connector's own status poll answers
`{ status, approved_budget }` — #2560's `approval_url` reaches the dashboard's
routes, never the agent. Found by `haven-reviewer` (blocking @ `1ba1b920`) and
verified in the connector source before changing anything. The page now says to
go back to the Haven tab, which is what actually completes an approval today,
and says plainly that no link exists so an agent does not invent one. Nothing
about authority moved: the human still signs the delegation, in the same place.

**Dependency, stated because the page is published to agents.** The hand-off
scripts use the link shapes from #2522 (`?next=`, `&via=agent`, `?setup=`),
which are not read by any route on `dev` yet — PR #2560 implements them and is
open. The links resolve today (the parameters are ignored), so no script sends a
user anywhere that does not exist; what does not happen yet is the return to the
exact step. Raised as a blocking finding by `haven-reviewer` and settled by the
owner in-session: keep the shapes, merge after #2560. Nothing about the money
path turns on it — no payment, authority or key behaviour reads these links.

Perimeter unchanged.
