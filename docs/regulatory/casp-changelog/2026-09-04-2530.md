- **#2530** — **an agent handed only a backend URL can now find out what the service is and which credential each door wants. One surface changes from authenticated to public: the merchant catalogue, in a reduced shape. No authority, custody or execution boundary moves; no payment is constructed, signed, authorised or executed.**
  A root document at `GET /`, a `hint` field on 401 refusals, a
  request-derived `servers[0]` in the OpenAPI document, and a public read of
  `GET /catalog`.
  **Why this is money-path at all.** By the FILE half only:
  `packages/backend/src/routes/**` and `middleware/**` are perimeter globs
  (#2300). Nothing about a rail, budget, delegation, allowance, key, schema or
  settlement path is touched, and no request that was accepted before is
  refused now, or the reverse — except the one deliberate change below.
  **The one disclosure change, stated as a list rather than as prose.**
  `GET /catalog` answered 401 and now answers unauthenticated callers with an
  ALLOW-LISTED subset: `id`, `name`, `description`, `category`, `rail`,
  `protocol`, `endpoint_host`, `status`, `verified_at`, `source`,
  `domain_verified`, `verified_payable`. A test fails on any key outside that
  list, so widening it is a visible decision rather than a side effect of
  adding a column.
  **What is withheld, and why those.** The full `resource_url` (the public
  shape gives the HOST — enough to know who the merchant is, not a copy-paste
  call target), and the price and tool-invocation fields. An agent that intends
  to PAY holds a credential by then and gets the full shape. Conservative is
  the right default for a surface that has never been public, and widening
  later is a smaller decision than narrowing after the fact.
  **Whose data is it.** Nobody's, in the CASP sense: every column of
  `merchant_catalog` is merchant metadata about a third-party payable endpoint.
  There is no per-agent, per-user or per-account field in the table to leak.
  This was checked against the row type rather than assumed, because "never
  per-agent data" is a guarantee only if somebody looked.
  **What did NOT become public.** Every other catalogue route still requires a
  credential (asserted). A caller presenting a BAD credential still gets its
  401 rather than a silent downgrade to the public shape — serving a reduced
  answer to a revoked agent would hide the revocation from the only party who
  would notice, which is the opposite of an audit trail.
  **The 401 hints do not weaken two existing information boundaries, and both
  are pinned.** #1640: a purpose-scoped token gets a body IDENTICAL to a failed
  verification, so which kind of token was presented is not something an
  unauthenticated caller is told — the two refusal sites now share one
  constant, making that identity structural instead of remembered, and a test
  signs a real purpose-scoped token and compares the raw bodies. And
  `Invalid or revoked API key` stays uniform across an archived agent, a
  revoked agent, a key matching nothing and an unrecognised status: the hint is
  shared by reference and a test asserts it contains none of the words that
  would distinguish those cases.
  **The root document is deliberately thin.** Names, paths and credential
  guidance only — no version, build identifier or environment name. A banner
  that fingerprints the deployment is a gift to a scanner and buys an agent
  nothing; a test asserts the schema carries no such property.
  **Origin derivation and spoofing.** `servers[0]` and the root document's URLs
  come from the request. `x-forwarded-host` is honoured only where
  `TRUST_PROXY_HOPS > 0`, AND the value is read that many hops from the RIGHT,
  because the host decides where a client is told to send its next request.
  Gating alone is not the job: a forwarded header can be APPENDED to, so the
  leftmost entry is the one an original client could have written. An earlier
  draft of this shard claimed parity with `authRateLimit` (#1670); that path
  gates on the same variable but hands selection to `proxy-addr`, which counts
  from the right — the gating matched and the selection did not, which is the
  half that mattered. Corrected on review, and the correction is
  mutation-proved: reading index 0 fails three tests. The scheme is deliberately NOT gated — gating it would
  make every TLS-terminating deployment without that variable advertise
  `http://` for its own API, a downgrade hint introduced in the name of
  security. The SCHEME additionally takes the leftmost entry, unlike the host,
  because `x-forwarded-proto: https,http` means the client reached the edge
  over https — right-indexing it would make a correct two-hop deployment
  advertise its own internal `http`. The residue is stated rather than implied:
  the scheme stays injectable, bounded by the host being both gated and
  right-indexed, so a downgraded scheme on a correct host yields a URL that
  fails against a TLS-only origin. Confirming the edge overwrites that header
  is an infrastructure question this repository cannot answer. The spec
  response carries `must-revalidate` and a `Vary`, so a shared cache cannot
  serve one caller an origin derived from another's headers.
  **Enforcement.** Full backend suite green (230 files, 3015 tests) including
  the real-DB harness. Six mutations, six caught: removing the owner hint,
  breaking the #1640 body identity, putting "revoked" into the invalid-key
  hint, adding `resource_url` to the public allow-list, reverting the root-path
  normalisation, and dropping the origin derivation — plus a seventh added on
  review: reading the forwarded host from the client end instead of the trusted
  one.
