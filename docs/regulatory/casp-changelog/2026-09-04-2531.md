- **#2531** — **a public, unauthenticated capability manifest and the backend read it draws from. Both re-serve values that are already public; no authority, custody, execution or disclosure boundary moves, and no payment is constructed, signed, authorised or executed.**
  `/.well-known/haven.json` on the frontend, generated per request, and
  `GET /discovery` on the backend, which supplies its environment-dependent
  half.
  **Why this is money-path at all.** By the FILE half only:
  `packages/backend/src/routes/**` is a perimeter glob (#2300). Nothing about a
  rail, budget, delegation, allowance, key, schema or settlement path is
  touched, and no request that was accepted or refused before changes.
  **What `GET /discovery` returns, as a list.** `hosted_mcp_url` (with a
  `hosted_mcp_note` when null), `connector_package`, `openapi_url`, `chains`.
  A test enumerates the keys and fails on any other, so adding one is a
  decision rather than a side effect of editing the handler.
  **Nothing here is newly public.** The connector package is printed in every
  setup handout, the chain list is `GET /chains`, the hosted MCP URL is given
  to every connecting agent, and the spec URL is the spec URL. This route
  re-serves them together so the frontend manifest does not restate the
  backend's environment logic — a restated fact goes stale on one surface and
  not the other. A second test asserts the serialized document contains no
  `user`, `agent_id`, `relayer`, `key_hash`, `balance` or database string, and
  a mutation that inserts a relayer address fails it.
  **Nothing from `/health`.** That surface is being restricted separately
  (#2542) and none of its values appear here.
  **One refusal is deliberately downgraded, and only here.** `hostedMcpUrl`
  THROWS for a non-production backend with no `HAVEN_HOSTED_MCP_URL` — correct
  for a connect handout, which must never invent another environment's URL, and
  that behaviour is untouched on that path. On the discovery document the same
  condition is REPORTED (`hosted_mcp_url: null` plus a note saying to connect
  with `--local`) rather than propagated as a 500, because a discovery document
  that refuses tells an agent nothing. The distinction is that this route hands
  out no credential and constructs no payment; it describes.
  **The manifest names no surface that 404s.** Two keys the issue specified are
  absent until their surfaces exist (`docs.for_agents` → #2523,
  `dashboard.device_approval` → the device-code flow), recorded as data so a
  test asserts their absence, and every same-origin path the manifest does name
  is checked against `PUBLIC_SURFACES` with a positive control. An agent that
  cannot tell "not offered" from "offered and broken" is the disclosure defect
  #2520 removed from the artifacts.
  **A server-side request forgery was introduced and removed before merge, and
  it is recorded here rather than quietly fixed.** The manifest's first version
  fetched the backend at `${origin}/api/discovery`, where `origin` came from
  `x-forwarded-host`. That is a server-side fetch to a caller-chosen host, with
  the reply embedded in the response the caller reads. Measured, not theorised:
  `curl /.well-known/haven.json -H 'x-forwarded-host: localhost:3154'` made the
  Next server issue `GET /api/discovery` to that host and the listener logged
  it. A caller could have aimed it at a cloud metadata endpoint or any service
  reachable from the frontend's network and read the answer back out.
  The fetch target now comes from `NEXT_PUBLIC_API_URL` — deployment
  configuration, the same variable the `/api` rewrite reads, so the manifest and
  the proxy cannot disagree — with a 2s timeout and `redirect: 'error'`. Re-run
  after the fix: zero requests reached the injected host and the real backend's
  facts still resolved. The rule the code now states: a URL this server FETCHES
  is never request-derived.
  **The reflection was then closed too, not merely argued to be acceptable.**
  A second review round observed that this manifest differs from `robots.txt`
  in a way that matters: it is built for an agent's code to ACT on, and
  `dashboard.signup` is the field it would send a human to. Echoing a
  caller-supplied host there is a thin phishing primitive even with
  `must-revalidate` and a `Vary`. Own-origin fields are therefore relative
  paths — an agent resolves `/signup` against the URL it actually fetched,
  which is unspoofable by construction, and it is the same-origin rule the
  artifacts already follow (#2520, #2521). Only the API base and the hosted MCP
  stay absolute; both name a different origin and both come from configuration.
  Verified by re-running the attack: the injected host appears NOWHERE in the
  served document.
  **Caching, stated precisely.** The two responses derive their origin from
  DIFFERENT headers, and an earlier draft of this shard flattened that into
  "both from `x-forwarded-host`", which is false for the backend. `GET
  /discovery` reads `Host` and `x-forwarded-proto` only. The manifest reads
  `x-forwarded-host`. Both carry `must-revalidate` and a `Vary`, so no shared
  cache serves one caller a document built from another caller's headers.
  `/discovery`'s `Vary` deliberately lists `x-forwarded-host` even though it is
  not consulted today: #2530 changes that helper to read it, and an
  over-inclusive `Vary` costs an extra cache variant while an under-inclusive
  one is a correctness bug — so it is written for whichever of the two lands
  first. Corrected on review.
  **Enforcement.** Backend 230 files / 3000 tests, frontend 138 / 1332, both
  green. Four mutations, four caught: advertising the not-yet-existing
  `/for-agents.md`, hard-coding an `@alpha` channel fallback, adding a relayer
  address to the discovery document, and propagating the hosted-MCP refusal
  instead of reporting it — plus two regression tests pinning that the fetch
  target is read from configuration, and one that fails if a caller-supplied
  host reaches any own-origin field. Verified end to end against both services running:
  the manifest's `api.base`, `api.openapi`, `hosted_mcp.url`,
  `packages.connect.channel` and `chains` matched `GET /discovery` exactly, with
  zero mismatches.
