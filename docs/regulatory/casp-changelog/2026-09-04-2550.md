- **#2550** — **an additive field is added to the hosted MCP's agent-guidance responses so a non-default client can find its own signer. No authority, custody, execution or disclosure boundary moves; no existing field changes value.**
  Guidance responses gain `next_tool_server_role` (`hosted` | `signer`), derived
  at the single emission point (`buildAgentGuidance`,
  `packages/mcp-server/src/tools.ts`) from the server name already parsed out of
  `next_tool`. `next_tool`, `next_tool_server` and `next_tool_name` are
  unchanged, byte for byte.
  **The defect it addresses.** `next_tool` is a hardcoded literal at six call
  sites naming the DEFAULT local servers (`mcp__haven-signer__haven_sign`), and
  `next_tool_server` is parsed back out of that same literal — so both name the
  default pair on every install. A connector run with `--name <slug>` (#1694)
  wires `haven-<slug>` / `haven-signer-<slug>`, and that slug is client config
  that never reaches Haven. Observed on dev 2026-09-04 with `--name devtest`:
  `haven_prepare_catalog_purchase` returned `next_tool_server: haven-signer`
  while the wired servers were `haven-devtest` / `haven-signer-devtest`. The
  hosted instructions tell an agent to follow those fields *first*, so the
  guided catalog path (epic #1305/#1312) dead-ended on the field it was told to
  trust most.
  **Why this is money-path at all.** No payment is constructed, signed,
  authorised or executed by this change, and no schema, route, rail, budget,
  delegation or key handling is touched. It is money-path by the FILE half:
  `packages/mcp-server/src/**` is a `globs` entry in
  `.github/money-path-globs.json` (#2300), and `tools.ts` is the file that
  decides whether a funding userop is relayed and in what order. The
  classification is right for the reason #2300 gives — four money defects have
  lived in this file — even though this diff only adds a routing hint.
  **What the defect could and could not do.** It misroutes an instruction; it
  cannot misdirect money. A signer holding a different agent's key cannot sign
  another agent's payment: the signer fetches the settlement child itself and
  verifies its caveats against Haven's signed context before signing (#1455),
  and the delegate key is bound to one agent. So the wrong call fails closed,
  loudly, rather than spending. That is the only reason this was filed as a
  defect rather than an incident, and it is stated here so a later reader does
  not have to re-derive it.
  **Why additive rather than corrective.** The alternative — dropping the
  `mcp__…` namespace, or having the connector register its slug with Haven so
  `next_tool` could be made truly correct — was considered and deferred by an
  explicit owner decision this session. Removing or changing `next_tool` would
  break every client that follows it correctly today, which is every default
  install, in order to serve the named minority; registering the slug would
  push a client-side wiring detail across the boundary into Haven. The residue
  is recorded rather than hidden: **an agent that ignores the new field is
  exactly as wrong on a named install as it was before.** This adds a correct
  path; it does not remove the incorrect one.
  **Enforcement.** A characterization test pins `next_tool`,
  `next_tool_server` and `next_tool_name` to their pre-change values on the
  signer path — written and run green *before* the field was added, so it
  demonstrably pins current behaviour rather than the new one. Two further
  tests cover the role on both the `signer` and `hosted` paths, because both
  are emitted (six and five call sites) and a role field that only ever said
  one would leave a client unable to distinguish the other role from a missing
  field. Literal guards in `server.test.ts` pin that the instructions actually
  tell an agent to use the role — the field alone is inert, and until this
  landed the instructions directed agents to `next_tool_server`, the field that
  is wrong on a named install.
  **Disclosure surface.** The hosted instruction text changes to name the role
  and the two non-default runtimes (Codex config keys; `--name <slug>`). No
  claim about custody, authority, enforcement or spend limits is added, removed
  or altered.
