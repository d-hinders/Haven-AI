- **#2557** — **a published SDK type is corrected to describe the response it already documents, and the hosted MCP's emission point is bound to it. Type and documentation only; zero runtime behaviour changes and no field's value moves.**
  `AgentNextStep` in `packages/sdk/src/types.ts` declared three of the six
  next-step fields the hosted MCP emits. It now declares `next_tool_server`,
  `next_tool_name` and `next_tool_server_role` as well, and
  `buildAgentGuidance` in `packages/mcp-server/src/tools.ts` carries an explicit
  return type built from it. The wire shape is unchanged — this makes the
  published type match what was already being sent.
  **Why this is money-path at all.** No payment is constructed, signed,
  authorised or executed, no schema, route, rail, budget, delegation or key
  handling is touched, and **no runtime code path changes**: the diff in
  `tools.ts` is a type alias, a return-type annotation and comments. It is
  money-path by the FILE half only — `packages/mcp-server/src/**` is a `globs`
  entry in `.github/money-path-globs.json` (#2300). The Merge Gate's
  behaviour-free allowance is claimed explicitly rather than silently: review
  confirmed zero behavioural change, and the full hosted suite (420 tests) is
  unchanged and green.
  **Disclosure surface — the substantive half.** `next_tool`'s docstring said
  *"Fully-qualified tool name for the next call."* Since #2550 that is known to
  be misleading in the way that matters: it is fully-qualified with the
  **default** server names, which is precisely the assumption that fails on a
  `--name <slug>` connector install. The docstring now states the default-name
  caveat, names both non-default runtimes (Codex config keys; `--name <slug>`),
  and points at `next_tool_server_role`. This is the same correction
  `docs/operations/mcp-runtime-compatibility.md` received in PR #2555, applied
  to the type a consumer actually reads in their editor. No claim about custody,
  authority, enforcement or spend limits is added, removed or altered.
  **What the binding does and does not catch — measured, not asserted.** The
  return-type annotation was mutation-tested in three directions, reading exit
  codes rather than output:
  a field written DIRECTLY into the returned literal fails the typecheck
  (exit 2); a field introduced through a conditional spread does **not**
  (exit 0), because TypeScript does not excess-property-check spread results
  and every optional field here arrives that way; the unmutated control passes
  (exit 0). Removing `next_tool_server` or `next_tool_server_role` from
  `AgentNextStep` now fails the build (exit 2 each), because the emission point
  and the tests both depend on it.
  So the type is load-bearing where it was decorative — a field REMOVED or
  RETYPED breaks the build — but the exact hole the two earlier drifts came
  through (a new field added by spread) is **not** closed. That residue is
  recorded here and in the code comment rather than left for a reader to
  discover, because the tempting summary — "the type is now enforced" — would
  be false in the one direction that has actually failed twice.
  **Test coupling.** The hosted suite's next-step assertions no longer reach
  these fields through inline casts; they type their responses against the
  published `AgentNextStep` instead. The casts were the observable symptom of
  the gap, and typing against the contract is what makes a future omission fail
  a test rather than quietly need another cast.
