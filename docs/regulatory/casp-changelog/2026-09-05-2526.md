- **#2526** — **an owner session that a human approves in a browser instead of an agent holding a password. It adds a token type whose default answer on every authenticated route is REFUSAL, with one opt-in allow-list; no authority, custody or execution boundary moves, and no payment is constructed, signed, authorised or executed.**
  Three routes (`/auth/device/start|approve|token`), grant rows in migration
  078, an `/device` approval screen, and `haven login` defaulting to the flow.
  **Why this exists.** Every owner action needed the owner JWT, and the only way
  to get one was email + password. An agent must never hold that; the
  2026-09-04 cold-test agent correctly refused to type the test password. This
  gives the agent something better to do — ask its human.
  **Why this is money-path.** By the FILE half (`routes/**`, `middleware/**`,
  `db/migrations/**`) and by the migration rule. It is also money-adjacent in
  substance, which is why the shard is longer than the diff warrants: it mints
  credentials.
  **The token's polarity is the security story, and it is unchanged.** #1640
  refuses every `purpose`-carrying token on every authenticated route, stated
  the safe way round — "a future single-purpose token inherits this refusal by
  default". That refusal stands. `owner_cli` is a single exception and it is an
  OPT-IN: a route accepts the token only by being on the allow-list.
  **An allow-list, not a deny-list, and the difference is enforcement rather
  than taste.** A deny-list grants every future route by default and relies on
  somebody remembering. `owner-cli-route-census.test.ts` DISCOVERS every
  registered route from the route modules — no hard-coded count, which would go
  stale on the next PR — and measures what `routeAllowsOwnerCli` answers for
  each at the door. Its negative control pins that an undecided new route is
  refused; a further test refuses any listed route not actually behind
  `authMiddleware`, and another holds the list against an independent opinion
  about which path shapes are authority. Its reverse direction
  caught three entries in the issue's own list naming routes that do not exist
  (`POST /agents/{id}/rename`, `GET /user/safes/{id}/balances`,
  `GET /agent-activity`); an entry for a missing route grants nothing while
  reading like coverage.
  **The list IS the enforcement.** The issue sketched a per-route marker. These
  modules attach auth with one module-level hook, so that would have meant ~22
  markers across nine files and two sources of truth that must agree: a listed
  route whose marker was forgotten grants nothing, a marked route nobody listed
  grants something nobody decided. The middleware reads the list, so the census
  guards real behaviour rather than a parallel document. The marker survives as
  an additive escape hatch and both paths are tested.
  **What an owner-CLI session cannot do**, by construction: signer changes,
  re-keying, passkey management, credential/password/email changes, account
  provisioning, transfers, and delegation build/activate/revoke. It can create
  an agent and ask for a budget; it cannot approve one. The human keeps every
  signature. `POST /auth/device/approve` is itself absent from the list — a CLI
  session approving further CLI sessions would turn one human approval into an
  unbounded grant.
  **Two purposes must not be confused.** An opted-in route accepts `owner_cli`
  SPECIFICALLY, not "any purpose": the Fortnox OAuth state token verifies with
  the same secret and stays refused everywhere. A mutation accepting any
  purpose fails a test written for exactly that.
  **The grant rows.** Both codes hashed at rest; user codes 8 characters from
  an alphabet without `0`/`O`/`1`/`I`/`L`/`U`, drawn with `randomInt` rather
  than `Math.random` because a human types them; single use enforced INSIDE the
  UPDATE, so two concurrent redemptions mint one session rather than racing a
  read-then-write; ten-minute expiry with an opportunistic purge, because these
  are spent credentials and not history. A wrong, expired or already-decided
  code all answer alike, so codes are not enumerable by a signed-in caller. A
  CHECK constraint refuses an approved row with no user — the invariant stated
  in SQL rather than trusted to the route.
  **Disclosure.** The approval screen names what the session can and cannot do,
  in both directions. Its failure copy does not distinguish the 404 cases, so
  the UI cannot leak what the API refuses to. The `client_label` is free text
  from an unauthenticated caller: bounded, stripped of control characters, and
  rendered as text rather than markup.
  **The requester is named BEFORE the decision**, which is the point of the
  label and was missing from the first cut of this work: the backend built and
  sanitized `client_label` and the screen never rendered it. The attack this
  flow must survive is not code theft — it is a stranger starting their own
  device login and getting a signed-in victim to open `/device?code=<theirs>`.
  Every code looks alike, so with no label on the page there was nothing for
  the victim to recognise as wrong. `POST /auth/device/lookup` (owner session,
  rate-limited, absent from the allow-list, and 404-uniform exactly like
  `approve`) is the read that fixes it; the screen offers no Approve button
  until it has answered, so there is no path to a grant that skips seeing who
  is asking. The label is captioned as the requester's own claim, never as
  something Haven vouches for.
  **A correction this record has to carry.** The census suite's headline
  assertion, cited here and in the security model as the proof that the opt-in
  had not become an opt-out, was a tautology: written in terms of
  `isOwnerCliAllowed`, it reduced to `!X && X` and passed for any allow-list,
  including an empty one. Two independent reviewers caught it before merge and
  nothing in the suite did. It is replaced by checks phrased against what the
  list does not define — the enforcement function's real answer, the modules'
  auth wiring, and an independent opinion about authority-shaped paths — each
  with a recorded mutation that makes it fail. The general rule, worth more
  than the fix: a test written in terms of the thing it checks cannot check it.
  **A second correction, from the re-review of those fixes.** The approval
  screen's own invariant had a race: the auto-lookup runs on mount, and while
  it is in flight the outcome is `idle`, so the input's reset guard does
  nothing. Someone who distrusted a pasted link and retyped their own code
  ended up with the LINK's label on screen and their code in the box — and
  Approve submitted the box. A human would have reviewed one grant and
  authorised another, which is exactly what the review step exists to prevent.
  Fixed with a generation counter that drops a stale response, and by binding
  the decision to the reviewed grant's own code rather than the input's current
  value. The same round found the new auth-gate check crediting `catalog.ts`'s
  conditional public-read carve-out as full gating; the detector now answers
  `conditional` as a third state and refuses it unless the entry is
  acknowledged by name, with a check that a stale acknowledgement also fails.
  **Enforcement.** 17 real-DB repository tests including two concurrency cases;
  8 census tests; 7 authorization tests; 16 approval-screen tests; 8 CLI poll
  tests with an injected clock. Every mutation below was run against the
  suite and made it go red; the list IS the figure, so a reader can re-run any
  line rather than trust a total. **The build:** storing codes in the clear,
  dropping the single-use predicate, dropping the expiry guard, turning the
  opt-in into a blanket grant, accepting any purpose on an opted-in route, a
  manifest key naming a 404, ignoring `slow_down`, ignoring `--no-wait`, and
  reporting a denial as not-authenticated instead of refused. **Review round
  one** (the census rewrite and the label): re-adding the dead
  `connector-status` entry, adding `PUT /user`, adding a `rekey` route,
  emptying the allow-list, making `routeAllowsOwnerCli` return true
  unconditionally, dropping its `:id`→`{id}` normalisation, an auth-gate
  detector that always says yes (a vacuity control on the new check itself),
  not rendering the client label, approving without the lookup step, keeping a
  stale label after the code is edited, dropping the lookup's `pending`
  predicate, and dropping its code normalisation. **Review round two:** removing
  the generation guard so a stale lookup lands its label beside a newer code,
  submitting the input box instead of the reviewed grant, dropping the
  generation bump on edit, adding `/delegations/build` to the list, dropping the
  `GET /catalog` conditional-gate acknowledgement, treating a conditional gate
  as a full one, and re-adding `connector-status` against the tri-state
  detector.
