## What was built

`haven agents connect` creates a connect setup from a terminal and prints the
connector command, the approval link and the expiry; `--run` executes that
command as a child process; `--status <id>` reads a setup and `--wait` polls it.

## The three properties that matter here, and how each is held

**The connector command is printed, never composed.** Byte-identity with the
dashboard is structural rather than maintained by comparison: both surfaces
render the `connector_command` field `buildConnectorCommand` produced, so there
is one string rather than two kept in agreement. `connector-command-parity.test.ts`
asserts this from both ends — the builder's exact shape for known inputs, and
that no CLI source file contains `@haven_ai/connect`, `--ack-local-tools` or
`npx -y`. The second assertion is the load-bearing one: if the CLI ever built a
command itself, identity would become a coincidence, and the first divergence
would be a command a user pastes that does not match what their dashboard shows.

That test asserts through TEXT rather than by importing the CLI's own splitter.
The obvious version compiles under vitest and fails under `tsc` — the backend's
`rootDir` is its own `src` — so it would have gone green here and red in CI. The
repo's existing idiom for cross-package agreement is a pinned value checked from
both sides, and that is what this uses.

**`--run` applies exactly one of the two permitted changes.** The setup prompt
allows an agent `--json`, and after a runtime refusal `--runtime`. The CLI
appends `--json` and nothing else: it never rewrites `--api`, never composes a
command, and deliberately has no `--replace` or `--name` of its own to pass
down. It does not apply `--runtime` either — it relays the refusal and exits 4,
because choosing a runtime, like choosing between replacing an existing wiring
and installing alongside it, is the human's decision. This is
@d-hinders' boundary note from #2551 held as a structural property rather than
a list: **a refusal is recognised by the presence of `error`, never by matching
a code**, so a refusal the connector adds next year reaches the human through
the same path with no CLI change. A mutation that enumerated the two known codes
passed every other test in the file, which is why the unknown-refusal test now
exists.

The connector **exits 1 on a refusal** while still writing a complete outcome
object to stdout. Treating the exit code as the verdict would discard exactly
the structured refusal the human needs, so the outcome is parsed whatever the
code was, and the code only decides what to do when there is no outcome at all.

**Human → atomic conversion is written out, and refuses rather than rounds.**
`@haven_ai/cli` ships with zero runtime dependencies — asserted by a test,
because `npx @haven_ai/cli` is the path an agent uses — so `parseUnits` is not
available and `parseTokenAmount` does the arithmetic in strings over BigInt.
`allowance_amount` is ATOMIC on the way in and human-decimal on the way back
(#2295); nothing sniffs which shape it holds, and the conversion runs in one
direction only. Excess precision is **refused**, not truncated the way
`parseUnits` truncates it: for a number a person is about to authorise, quietly
changing it is worse than declining it, and the dashboard's own
`validateMoneyInput` refuses first for the same reason — a budget the dashboard
would not accept must not become acceptable by being typed into a terminal.

The vectors were **measured, not reasoned about**: the 17 in the conversion
table plus the further value asserted elsewhere in that file — 18 distinct
(value, decimals) pairs — were run through the real `parseUnits` in the frontend
workspace, where viem is installed, and all agreed. A hand-written table of
expected values is a claim about another library until somebody executes it,
and this one decides a budget.

Token decimals are read from `GET /balances/:safeAddress` — the same registry
the modal reads — rather than from a table in the CLI. A local table would be a
second source of truth for a number that sets a budget's magnitude, and it would
drift silently the first time a chain gained a token.

## The perimeter, stated exactly

- **No allow-list change was needed.** All four routes these commands call
  (`GET /user/safes`, `GET /balances/{safeAddress}`, `POST /agent-connection-setups`,
  `GET /agent-connection-setups/{setupId}`) were already on
  `OWNER_CLI_ALLOWED_ROUTES` from #2526, and the census test still passes
  unchanged. The issue's instruction — if a route is missing, add it here with
  the census updated, never loosen the default — did not have to be exercised.
- **No backend change was needed for `source: 'cli'`.** `normalizeDiscoverySource`
  already accepts any lowercase slug; the route did not assume a frontend
  origin. Verified by test rather than by reading.
- **`via` is never inferred.** The agent hand-off marker is sent only when
  `HAVEN_AGENT_DRIVEN=1` says an agent is driving. A guess would mislabel a
  human's own run in the funnel.
- **Nothing here signs, and nothing here approves.** Budget approval remains
  human plus WebAuthn in the browser. The CLI creates the request and relays
  the link; it cannot advance a setup past the approval gate.

## Two things the issue asked for that are deliberately absent

Owner decision, 2026-09-05, on evidence from the API rather than preference:

- **`--recipient`** — neither `POST /agents` nor `POST /agent-connection-setups`
  has a field for one. A recipient pin lives in the delegation's caveat
  enforcers and is set when the human approves the budget. A flag that is
  silently dropped, or one that invents a wire field, is worse than a flag you
  cannot ask for.
- **`haven agents create`** — `POST /agents` requires a valid `delegate_address`
  (400 without one) and refuses `allowances` outright (the retired-rail 400
  from #2020). The command as specified therefore cannot exist without the CLI
  generating a signing key, which is precisely what an agent-driven CLI must
  never hold. `connect` is the path that generates one locally, on the user's
  machine, which is the non-custody premise this epic exists to protect.

Both are named in `packages/cli/README.md` so nobody goes looking for them, and
the acceptance criterion covering `create` is recorded as not delivered rather
than quietly reinterpreted.

## Enforcement

147 CLI tests and 4 backend parity tests; the #2526 census suite is unchanged.

**Six mutations, one of which survived and was the useful one.** Caught
immediately: sending the human amount instead of the atomic one; always claiming
an agent is driving; treating the connector's exit code as the verdict; placing
`--json` first instead of appending it; allowing shell metacharacters through
the command splitter. The sixth — recognising a refusal by enumerating the two
known codes instead of by structure — **passed every test in the suite**, which
is precisely the guard @d-hinders' boundary note asks for. The existing test
exercised `relayLine` rather than the exit path, so the unknown-refusal case was
added and the mutation now fails.

There is no mutation-testing tool in this repository; these were run by hand,
each restored from a `cp` backup and compared with `cmp`. The list is the
figure — a reader can re-apply any line — because a bare tally of an
instrument nobody can re-run is the kind of number this record should not
assert. An earlier draft of this shard said "eight, eight caught after the
ninth", which was both wrong and not checkable; haven-doc-reviewer counted the
named items and found the framing did not add up.

The parity test also caught two real defects while being written: the CLI's
splitter refused the backend's own `'\''` quote escaping — a command the builder
can emit and `--run` could not execute, which is a broken contract rather than a
safe refusal — and the CLI's test fixture had invented quotes around values
`shellQuote` leaves bare.
