# 2026-09-05 — #2528: the approval link reaches the agent, and a setup records how it was run

Two additions on the connect path: the register response returns the setup's
`approval_url`, and the connector reports `run_mode` (`json` | `prose`) so the
onboarding funnel can tell an automated setup from a narrated one. One
migration (077) adding one nullable column. No rail, budget, delegation,
signing or route-authorisation change.

**Money-path by the LABEL, and by the file half too — both, not either.** The
issue carries `money-path`, and `routes/agent-connection-setups.ts` plus
`db/migrations/**` are on the perimeter. Re-take it rather than trust this
shard:

```
node scripts/ci/money-path-classify.mjs $(git merge-base origin/dev HEAD)
```

The migration is why this needs an independent code-owner approval
(`.github/CODEOWNERS`); the route is on the list because its budget-approval
path is where an owner's signature becomes an agent's on-chain spend authority
(#2264).

**What changed, as authority. Nothing.** Neither addition can move money or
widen what anything may spend.

- `approval_url` is a **link to a page**, not a grant. It is the same string
  `POST /agent-connection-setups` (201) and the owner-authenticated status read
  have returned since #2522 — built by `buildApprovalUrl` from
  `config.frontendUrl` and the setup id, with no token in it. Opening it shows
  the owner the approval screen; approving still requires their passkey and
  still produces the signed delegation the DelegationManager enforces. An agent
  that relays the link has handed its user a destination, and nothing else: it
  cannot follow the link to any effect, because the approval is a WebAuthn
  signature it cannot produce. The epic invariant — no slice may let an agent
  create a passkey, sign a delegation, change a signer, or re-key — is
  untouched, and this slice moves in the safe direction: it replaces a sentence
  telling the user to go find a page with the page's address.
- `run_mode` is **telemetry about the caller, written by the caller**. It
  segments a funnel; nothing reads it to decide anything. It is refused with
  400 unless it is exactly `json` or `prose`, so the dimension cannot absorb a
  value nothing recognises — an untrusted string is rejected rather than stored
  or silently nulled. It is not a capability claim: a connector asserting
  `run_mode: 'json'` gains no permission, and a lying one gains a wrong metric.

**Custody.** Unchanged. No key material, no credential, and no token enters or
leaves by either field. The register response already carried `api_key_prefix`
and the delegate address; `approval_url` adds a same-origin dashboard path. The
setup token — the one secret in this exchange — appears in no response, which a
route test asserts directly rather than by inspection.

**What an agent is told to do with it, which is the part that could go wrong.**
The shared guidance sentences (`packages/sdk/src/agent-guidance.ts`, consumed
by the backend's setup prompt and the `/for-agents.md` runbook) now say: relay
`approval.url` when the outcome carries one, otherwise send the user back to
their Haven tab — **and never build the link yourself**. That last clause is
load-bearing and is asserted in the runbook guard. The connector's outcome
carries no setup id, so an agent has the whole link or none; a page that taught
it to assemble `?setup=…` would be teaching it to guess at a URL it then asks a
human to trust. `approval.url` is likewise never synthesised inside the
connector: it is echoed from the backend or omitted.

**Attribution (§ Product Copy Rules).** The new copy keeps the actor correct:
the user approves the budget, and approval is what authorises spending. No
sentence added here says Haven grants, authorises, approves or holds anything.
`npm run lint:copy` is green with no new baseline entry.

**Backward compatibility, stated because absence is the normal case.**
`approval.url` is optional in the connector outcome and `run_mode` is optional
on the wire. A connector older than #2528 sends no `run_mode` and registers
unchanged (asserted on the real-DB harness: the column stays NULL and `runtime`
beside it is undisturbed); a backend older than #2528 returns no
`approval_url`, and the connector falls back to its previous prose rather than
printing `undefined` (asserted in `packages/connect/src/runtime.test.ts`). A
NULL `run_mode` therefore means *unreported*, not *prose* — the measurement
query COALESCEs it to `unreported` for exactly that reason, since collapsing
the two would inflate `prose` by the entire pre-#2528 population.

**Evidence.** Characterization tests were written against unchanged code and
green there before either behaviour moved — one pinning that the register
response carried no `approval_url`, one pinning that `runtime` was already
accepted and already persisted (which is why migration 077 adds ONE column, not
the two the issue named: a second `runtime` column would have shadowed a
populated one). The database claim is proven on the real-Postgres harness per
`testing-strategy.md`, not against a mock, and mutation-proven two ways:
dropping the `run_mode` assignment from the UPDATE turns 3 tests red, and
swapping the `runtime`/`run_mode` bind positions turns 2 red — the second only
because the test asserts both columns in one case, which is the renumbering
slip a positional mock cannot see. A positional fake in the route suite did
mis-decode that renumbering and had to be corrected in this PR, which is that
argument arriving as a fact rather than a prediction.
