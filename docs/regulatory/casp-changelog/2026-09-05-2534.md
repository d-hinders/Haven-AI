# 2026-09-05 — #2534: funding became a machine-readable step — an owner-scoped funding read, its CLI command, and a dashboard card that stopped keeping its own copy of the minimum

Read-only surface work on epic #2519 slice B4. Three pieces, all of them ways
of *showing the human the same numbers*:

1. `packages/backend/src/routes/user-safes.ts` gained
   `GET /user/safes/:safeId/funding` — an owner-scoped read returning the
   account address, chain and explorer, per-token balances beside each token's
   documented `minimum_useful_human` constant, `native.needed: false` (gas is
   relay-sponsored), `funded` (any token balance ≥ its minimum), and a
   `faucet_url` on testnets. The allow-list in
   `packages/backend/src/middleware/owner-cli.ts` gained the one entry, and the
   route census pins it.
2. `haven wallets funding` (`packages/cli/src/commands.ts`) renders that
   response — the paste-ready sentence, or the object under `--json` — and
   `--wait` polls until `funded` flips, read-only in every mode.
3. The dashboard's onboarding card (`DashboardOnboardingGuide.tsx`) stopped
   hard-coding "Even $5" — a second copy of the minimum-useful constant — and
   now renders step 1 from the same endpoint, so the card, the CLI and the
   backend cannot disagree about the amount.

**Why it touches the CASP perimeter at all.** `casp-risk-guardrails.md` covers
`packages/backend/src/routes/user-safes.ts`, the route file, by exact path, and
the money-path labeler may classify the diff via its globs — a route file is
asked whether the change moved a safeguard. This one did not, and the negative
is specific: the endpoint performs no transfer, no approval, no allowance
change, no delegation build, activate or revoke; it composes no transaction of
any kind. It reads balances through the same `getChainClient('ethers')` seam
`GET /balances/:safeAddress` already uses, projects them through the constants
in `@haven_ai/core` (`minimumUsefulTokens` — the same constants the funding
copy has always quoted), and answers with facts. Ownership is enforced by the
same tenant-scoped lookup the balances read uses; another user's Safe is a 404
that reveals nothing. The CLI command is a renderer of that response with GETs
only — its test suite fails on any non-GET call and asserts it never names a
faucet — and `--wait` polls the same read; it cannot move money because it
never builds anything that could. The dashboard change deletes a duplicated
constant, which removes drift risk rather than adding any. No key, credential,
custody, signing or spend-authority surface moved; the human keeps the transfer,
as the product rule requires — funding is a human step and this change only
makes its instructions machine-*readable*, not machine-*executable*.

**Guardrail framing, stated rather than implied.** Haven does not hold user or
agent keys and this change gives it no new way to: the endpoint and the command
are read-only facts for a human to act on, in the same category as the balances
read that has existed all along. The `purpose: owner_cli` token can now reach
one more read; the security model's § 9 records the entry and its scope, and
the allow-list census (positive and negative directions) pins it in both
suites.

**Mutation-checked by unit test.**
`packages/backend/src/routes/__tests__/user-safes-funding.test.ts`
(characterization: auth refusal for agent API keys, tenant-scoped 404s, the
payload shape, `funded` at the atomic threshold, faucet presence/absence),
`packages/backend/src/__tests__/owner-cli-route-census.test.ts` (the
allow-list entry), and `packages/cli/src/commands.test.ts` (rendering from the
response, the `--wait` poll and its timeout exit, the read-only GETs-only
invariant). No handler was mutated outside tests; nothing to restore.

Perimeter unchanged: this is the read half of the funding hand-off — no
movement, no authority, no custody.
