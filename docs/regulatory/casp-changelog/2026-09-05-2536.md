# 2026-09-05 — #2536: `latest` follows the newest published release

A **release-control** change, classified **money-path by the file half on a
CONTROL glob only** — `.github/workflows/publish.yml`. That distinction is the
first thing a reader needs, because it decides what evidence is owed:

```
  0 runtime-glob + 1 control-glob = 1 of 7 on the perimeter
  => MONEY-PATH (control surface only). Labelled and read by a human; no QA
     re-run is implied, because the harness cannot exercise a CI control change.
```

**Zero change to any money path at runtime.** No route, policy, signing,
custody, authority or spend surface is touched. Nothing in `packages/**/src`
changes. The diff is one workflow, one test file, and four documents.

## What changed, in one sentence

After a successful **prod-channel** publish, the workflow additionally runs
`npm dist-tag add <name>@<version> latest`, keeping the version's own
prerelease tag.

## Why this is a control-surface change and not a cosmetic one

`publish.yml` is on the perimeter because it decides **what reaches users**. It
now writes one more registry pointer than before, so the reasoning below is
about what that pointer can and cannot be made to point at.

- **`npm publish --tag` is unchanged.** The version→channel rule
  (`alpha` for a prerelease, `latest` for a stable, `dev` for a snapshot) is
  untouched, so `HAVEN_CONNECTOR_CHANNEL` — derived from that same rule and
  baked into every published package — still resolves to `alpha`, and the
  epic-#2519 invariant that `npx -y @haven_ai/connect@alpha` stays verbatim in
  every artifact is unaffected. Verified against
  `packages/sdk/src/connector-channel.ts` rather than assumed: a change there
  would have failed `scripts/ci/connector-channel-agreement.test.mjs`.
- **The snapshot wall still holds, and gains a fourth enforcement point.**
  `promote_latest()` never calls `npm dist-tag add … latest` with a
  `0.0.0-dev.*` version. It examines the version shape before deciding
  anything, so the rule turns on the ARTIFACT; the channel then decides only
  whether an unexpected snapshot is a silent no-op (dev, where snapshots are
  ordinary) or a failure (anywhere else).
- **A re-run cannot drag `latest` backwards; a new publish of an older line
  still can.** The move is tied to a publish this run actually performed, so
  re-running an old workflow run moves nothing — every version is already on
  npm and skips. It does **not** compare the candidate against the currently
  live `latest`, so publishing a genuinely new version of an older release line
  (a 2.x hotfix while `latest` is 3.0.0) would move `latest` down to it. Raised
  by `haven-reviewer` on this change; the first draft of this bullet said
  "cannot", which was true only of the re-run case.

  **Two cheap guards were measured and rejected rather than assumed
  unavailable**, which is why none is in this change:
  `sort -V` is not semver — it orders `1.0.0` *before* `1.0.0-alpha.1`, so a
  guard built on it would refuse the 1.0 release this repo is heading toward;
  and `semver` is only a hoisted transitive dependency here, not a direct one,
  so a release-control guard resting on it could vanish on an unrelated
  dependency change. Adding `semver` as a direct dependency of the publish path
  is a real option and a separate decision — filed as #2580 rather than widened
  into this one, with both measurements recorded there so they are not
  re-derived. The run log now prints the tag's before-value on every
  move, so a backwards move is visible in the record even without a guard.
- **A failed tag move fails the run**, and reports the true state: the package
  is live under its own tag and only `latest` is stale, with the one-line
  remedy printed. It is deliberately not reported as a publish failure, which
  would send the next reader hunting for a publish that did happen.

## The release-plumbing enumeration § *Product Copy Rules*' sibling requires

`casp-risk-guardrails.md` states it directly: "When release plumbing changes, the
shard states which of these moved, and that the rest did not." Answered item by
item, because a shard that skips the list its parent asks for is the
self-certification the coupling gate's #2323 notice exists to catch — and this
enumeration was added only after re-reading the parent, not when the shard was
first written.

| Item | Moved? |
|---|---|
| version fields | **no** — no `package.json` version changes |
| cross-package dep pins | **no** |
| connect's pinned `sdkVersion` / `signerVersion` | **no** |
| **dist-tag selection** | **the only change.** `npm publish --tag` selection is byte-unchanged; a SECOND tag move is added afterwards |
| the publish trigger | **no** — same `on:` block, same paths |
| the ref it builds from | **no** |
| build order | **no** — both build steps untouched |
| the credential path | **no change made**, but see below |
| wildcard-pin re-check | **intact** — `release-bump.mjs` untouched |

**The credential path is unchanged and its SUFFICIENCY is unverified, which is a
different statement.** The workflow authenticates by npm Trusted Publishing
(OIDC, `id-token: write`, no `NPM_TOKEN`). Nothing in this repository records
whether the short-lived credential that OIDC mints for `npm publish` also
authorises `npm dist-tag add`, which is a different registry endpoint
(`PUT /-/package/<pkg>/dist-tags/<tag>`). It could not be tested here: the tests
run against a stubbed `npm`, and a real attempt would be a live registry write.

That is disclosed rather than assumed away, and the failure mode is deliberately
loud rather than silent. If the credential does not cover it, the first release
after this merges publishes all five packages normally, the tag move fails, and
the job exits non-zero naming the packages and printing the one-line remedy
(`npm dist-tag add <name>@<version> latest`). Nothing is left in a state a
reader cannot see: the packages are live under their own tag and only `latest`
is stale, which is exactly the state the run summary reports. The #2536 operator
checklist carries a step to confirm this on the first release.

## Evidence — behavioural, not textual

Six tests in `scripts/release-bump.test.mjs`, all asserting on what the step
**actually called**, recorded by a stub `npm` on `PATH`. Suite: 56 pass, 0 fail
(`node --test scripts/release-bump.test.mjs` at this head).

| # | Mutation | Result |
|---|---|---|
| 1 | delete the `promote_latest` call (guard present, unreachable) | **2 red** |
| 2 | drop the dev-channel no-op | **1 red** (see below) |
| 3 | drop the `tag = latest` short-circuit | **1 red** |
| 4 | swallow a `dist-tag` failure with `|| true` | **1 red** |
| 5 | drop `\|\| echo unknown` from the informational registry read | **1 red** |

Each mutation was restored and the suite re-run to 56 pass.

**Mutation 5 is the one that needed a different kind of test, and the reason is
worth recording.** Dropping that fallback survives every loop-level test:
`promote_latest` is invoked as `if promote_latest …; then`, and bash suppresses
`errexit` for a command that is part of an `if` condition — including inside a
called function — so a failing registry read cannot affect the job's exit code
there, whatever the code says. Invoked directly, where `errexit` applies, the
same omission does fail. The sixth test invokes the lifted function that way
with a failing `npm view` stub, and the mutation goes red. It also pins the read
as informational: exactly one `dist-tag` call regardless of what the read
returned, and nothing branches on its value.

**Mutation 2 initially SURVIVED, and the reason is recorded rather than
smoothed over.** Through the publish loop that line is unreachable: on the dev
channel every version is a snapshot, so the snapshot branch returns first, and
a non-snapshot on a non-prod channel is refused by `assert_publish_allowed`
before any publish. Rather than delete a defensive check in a tag-moving
function, the test now calls the lifted function directly with that pair, where
the line is load-bearing — and mutation 2 then goes red.

**Two defects in this change were found by executing it, not by reading it**,
and both are worth the record:

1. The first draft refused a snapshot version on **every** channel, which failed
   every dev-channel publish outright — it conflated "this is dangerous" with
   "this is the ordinary dev path".
2. The first version of the guard's unit test ran the **real** `npm` and issued
   a live `PUT https://registry.npmjs.org/…/dist-tags/latest` against a real
   package, stopped only by a 401. A unit test for a release guard must not be
   one credential away from mutating the registry it describes; it now runs
   against a stubbed `npm`.

## The operator half is NOT done by this merge

The workflow acts only on a future publish, so all five packages keep their
current stale `latest` until an owner moves them once by hand, and
`@haven_ai/mcp` keeps its stray `alpha~` tag. That is a numbered checklist on
#2536, which carries the `operator-verify` label and stays open. This shard
therefore records a mechanism that is merged and an outcome that is not yet
true — stated in that order so nothing here reads as a claim about the live
registry.
