# 2026-09-05 — #2536: `latest` follows the newest published release

A **release-control** change, classified **money-path by the file half on a
CONTROL glob only** — `.github/workflows/publish.yml`. That distinction is the
first thing a reader needs, because it decides what evidence is owed:

```
  0 runtime-glob + 1 control-glob = 1 of 7 on the perimeter
  => MONEY-PATH (control surface only). Labelled and read by a human; no QA
     re-run is implied, because the harness cannot exercise a CI control change.
```

**Zero change to any money path at runtime.** No route, policy, signing,
custody, authority or spend surface is touched. Nothing in `packages/**/src`
changes. The diff is one workflow, one test file, and four documents.

## What changed, in one sentence

After a successful **prod-channel** publish, the workflow additionally runs
`npm dist-tag add <name>@<version> latest`, keeping the version's own
prerelease tag.

## Why this is a control-surface change and not a cosmetic one

`publish.yml` is on the perimeter because it decides **what reaches users**. It
now writes one more registry pointer than before, so the reasoning below is
about what that pointer can and cannot be made to point at.

- **`npm publish --tag` is unchanged.** The version→channel rule
  (`alpha` for a prerelease, `latest` for a stable, `dev` for a snapshot) is
  untouched, so `HAVEN_CONNECTOR_CHANNEL` — derived from that same rule and
  baked into every published package — still resolves to `alpha`, and the
  epic-#2519 invariant that `npx -y @haven_ai/connect@alpha` stays verbatim in
  every artifact is unaffected. Verified against
  `packages/sdk/src/connector-channel.ts` rather than assumed: a change there
  would have failed `scripts/ci/connector-channel-agreement.test.mjs`.
- **The snapshot wall still holds, and gains a fourth enforcement point.**
  `promote_latest()` never calls `npm dist-tag add … latest` with a
  `0.0.0-dev.*` version. It examines the version shape before deciding
  anything, so the rule turns on the ARTIFACT; the channel then decides only
  whether an unexpected snapshot is a silent no-op (dev, where snapshots are
  ordinary) or a failure (anywhere else).
- **It cannot drag `latest` backwards.** The move is tied to a publish this run
  actually performed. Re-running an old workflow run publishes nothing — every
  version is already on npm and skips — so no tag moves.
- **A failed tag move fails the run**, and reports the true state: the package
  is live under its own tag and only `latest` is stale, with the one-line
  remedy printed. It is deliberately not reported as a publish failure, which
  would send the next reader hunting for a publish that did happen.

## Evidence — behavioural, not textual

Six tests in `scripts/release-bump.test.mjs`, all asserting on what the step
**actually called**, recorded by a stub `npm` on `PATH`. Suite: 55 pass, 0 fail.

| # | Mutation | Result |
|---|---|---|
| 1 | delete the `promote_latest` call (guard present, unreachable) | **2 red** |
| 2 | drop the dev-channel no-op | **1 red** (see below) |
| 3 | drop the `tag = latest` short-circuit | **1 red** |
| 4 | swallow a `dist-tag` failure with `|| true` | **1 red** |

Each mutation was restored and the suite re-run to 55 pass.

**Mutation 2 initially SURVIVED, and the reason is recorded rather than
smoothed over.** Through the publish loop that line is unreachable: on the dev
channel every version is a snapshot, so the snapshot branch returns first, and
a non-snapshot on a non-prod channel is refused by `assert_publish_allowed`
before any publish. Rather than delete a defensive check in a tag-moving
function, the test now calls the lifted function directly with that pair, where
the line is load-bearing — and mutation 2 then goes red.

**Two defects in this change were found by executing it, not by reading it**,
and both are worth the record:

1. The first draft refused a snapshot version on **every** channel, which failed
   every dev-channel publish outright — it conflated "this is dangerous" with
   "this is the ordinary dev path".
2. The first version of the guard's unit test ran the **real** `npm` and issued
   a live `PUT https://registry.npmjs.org/…/dist-tags/latest` against a real
   package, stopped only by a 401. A unit test for a release guard must not be
   one credential away from mutating the registry it describes; it now runs
   against a stubbed `npm`.

## The operator half is NOT done by this merge

The workflow acts only on a future publish, so all five packages keep their
current stale `latest` until an owner moves them once by hand, and
`@haven_ai/mcp` keeps its stray `alpha~` tag. That is a numbered checklist on
#2536, which carries the `operator-verify` label and stays open. This shard
therefore records a mechanism that is merged and an outcome that is not yet
true — stated in that order so nothing here reads as a claim about the live
registry.
