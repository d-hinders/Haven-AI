# 2026-09-05 — #2561: the dashboard offers to revoke the agents a setup superseded

A **connector + backend + dashboard** change, classified **money-path by the
file half** on **one** glob of fifteen changed files:
`packages/backend/src/routes/agent-connection-setups.ts`
(`node scripts/ci/money-path-classify.mjs origin/dev`, self-test passed
6 positive / 6 negative). The issue itself checks the money-path box for this
reason and says so.

**No authority changes.** Revoke stays on the existing owner-authenticated
route (`POST /agents/:id/revoke`), no migration, no new column, no new
credential, and no new permission. What moves is *information*: which agents a
connector run displaced now reaches the owner's screen. The one thing a
reviewer should check hardest is the sentence that follows.

## Nothing is revoked without a click

The connector cannot revoke, and must not. `POST /agents/:id/revoke` is
owner-authenticated; the connector holds only agent API keys; and an agent
credential retiring a sibling agent is precisely the "agent editing its own
authority" the re-key routes (#1694) already refuse. So the connector reports
and the dashboard offers.

The offer is one agent at a time, behind the same danger-toned `ConfirmDialog`
the agent page uses for removal, with the irreversibility stated before the
button. Nothing fires on mount, nothing batches, and cancelling is not
dismissing — the offer stays. Five of the sixteen component tests exist only
to hold that line, including one that asserts the first click does **not**
revoke.

## The scan's own ambiguity, fixed at the source

`listOtherAgentIds` returned `[]` for two different facts: the credential root
holds no other agent, and the credential root could not be read. The connector
knew the difference in the moment and threw it away, and the outcome field's
doc comment had to warn readers that emptiness was not a guarantee.

A warning in prose cannot reach a dashboard. So the scan now returns `null` for
the second case and the install-status report carries a **tri-state** end to
end — a list, `[]` (scanned, none), `null` (could not run) — described that way
in the OpenAPI schema, which is `additionalProperties: false` and would
otherwise forbid what the API sends.

The reason this matters is a claim, not a shape: **a dashboard that renders
"nothing to revoke" for an unscanned machine is Haven asserting something it
does not know about somebody's computer.**

Two deliberate consequences:

- The `--json` outcome is **unchanged** and still flattens to `[]`, per the
  issue's own criterion. The tri-state exists on the report only.
- The wire sends `?? null` rather than the `input.x` shorthand its neighbours
  use. `undefined` disappears from `JSON.stringify`, and an absent key means
  "unchanged" to the backend's jsonb merge — right for a probe result, wrong
  here. "The scan could not run" is a fact this report is *making*.

## Characterization first, on the money-path file

Seven assertions pinned `sanitizeInstallStatus` before it was touched, per the
rule. One of them named the single line the change would move; it fired when
array support landed, which is what a characterization test is for — the change
became visible rather than assumed. The other six still assert the untouched
behaviour, which is what makes the widening provably narrow:

- unknown keys are still dropped silently;
- `retired_agent_ids` — a real connector field — is still **not** carried,
  because nothing in the offer needs it and widening by association is how an
  allowlist stops being one;
- an array in a string slot is still refused rather than coerced;
- `error_code` remains the precedent the new meaningful null follows.

The ids themselves are shaped, never believed: trimmed, credential-shape
filtered by the same `looksLikeRawPathOrSecret` guard the string fields use,
capped at 120 characters each and 50 entries, non-strings dropped rather than
coerced, and a bare string refused rather than wrapped into a one-element list.

## Ownership is resolved where it is known

The connector falls back to a **directory name** when an `identity.json` exists
but will not parse, so the reported list can legitimately hold strings that are
not agent ids — or that name somebody else's agent. The card intersects the
report with the agents this session actually owns, which is data the dashboard
already has, and drops anything already revoked. The revoke route's 404 on a
foreign id is the backstop, not the plan: an offer the user cannot act on is
still a claim about their machine.

## Enforcement

Backend: `install-status-characterization.test.ts` (7) and
`superseded-agent-ids.test.ts` (6). Frontend:
`SupersededAgentsCard.test.tsx` (19), and the connect client's four-state wire
contract in `api.test.ts`. Backend 3108 non-skipped, frontend 1472, connect 527. Read the backend figure
narrowly: a full run intermittently fails one unrelated migration test
(`070_drop_approval_requests`) that passes in isolation — cross-worktree
contamination of the shared test schemas, which CI does not have. Both a
reviewer and this author hit it, so "green" is stated as what it is rather than
as a clean sweep.

**Eighteen mutations, run by hand with `cp` backups and `cmp` restores** (there is
no mutation tool in this repository), and the list is the figure so any line can
be re-applied: collapsing the tri-state's null in the sanitiser; dropping the
secret-shape filter on the ids; accepting a bare string by wrapping it; removing
the count cap; trusting the report instead of intersecting with owned agents;
revoking straight from the list button with no confirm; offering already-revoked
agents; removing the card's null short-circuit; going silent again when the
agent list fails to load; offering a revoke the read cannot support; re-focusing
the destructive button; and moving the count cap back after the per-element
work (which survived — see below).

**Review round two changed two things a reader should know about.** The shared
`ConfirmDialog` focused its CONFIRM button on open, and the modal focuses
synchronously — so a keyboard user's second Enter, an ordinary reflex right
after the Enter that opened the dialog, confirmed the revoke. "Nothing happens
without a deliberate click" was not true for them. Danger-toned dialogs now
focus Cancel, which also reaches the three existing destructive dialogs that
had the same shape.

And the card read the owner's agent list itself without applying its own rule
to that read: a failed fetch left the list empty for good, and rendering
nothing then looked exactly like "this setup replaced nothing" — about a list
we know is not empty. It now says the list could not be loaded, offers a retry,
and offers no revoke it cannot support. Two lower findings closed with it: the
count cap now runs before the per-element work (identical output, bounded work
— and no test can pin an ordering that changes nothing observable, which is
said in the code rather than implied), and the scan's doc comment no longer
implies a non-null return saw every entry, since an unreadable directory is
skipped and the list can under-report in the safe direction.

**Review round three caught a regression I introduced while fixing round two.**
Round two asked for the count cap to run before the per-element work, to bound
the work; I moved it and wrote in the code that the change was
behaviour-preserving. It is not. Capping the raw array first looks at the first
50 entries only, so 60 junk entries followed by 40 real ids keep **zero**
instead of 40 — measured, and exactly this feature's own failure mode, on the
input a hostile client would send deliberately. The cap is last again, the
comment says what actually happened, and a test pins the case the original
fixture could not distinguish.

Two more from the same round. The connect client collapsed `undefined` into
`null`, so the early config-written ping — which fires before the scan starts —
asserted "the scan could not run" on every run; absent is a fourth state and
the backend's merge honours it, so the client now sends the key only when it
has something to say. And the card vanished mid-retry, because `refetch` clears
the error synchronously before the request settles; it now stays visible with
the button disabled.

**And a rendered capture found what neither review did.** Round two moved the
offer below `SetupDoneState` to stop it pre-empting the grant line. The
screenshot showed the consequence: it landed below the **Done** button, where
the one action a finished screen invites closes the modal past it. It now
renders inside that component, above the button — the only position that is
both. Three screenshot scenarios are committed so the next reviewer does not
rebuild them a third time.

**Round four, and the worst one was mine twice over.** Round three's retry fix
branched on `useAgents`' `loading` — which is `true` on first mount, before
anything has failed — so a freshly completed setup announced that the agent
list could not be read. A false claim, on the one screen this flow exists to
make trustworthy. And the test written alongside it ASSERTED that as correct:
it set exactly the first-mount state and expected the error card. A test can
enshrine a defect as thoroughly as it can catch one.

The branch now keys on a retry THIS card started, never on any load in flight.
Fixing the test surfaced a second gap in it: the mock did not clear the error
the way the real hook does synchronously, so a mutation removing the retry flag
survived. The mock models the hook now, and both directions fail.

**The last of the original eight survived, and was the useful one.** It exposed that the
short-circuit was doing no work — the intersection already produces the same
silence — so a comment claiming the component enforced the tri-state was
overstating. The comment is corrected and the test now pins the property the
component really has: it never says "nothing to revoke", for any of the three
empty cases. The tri-state's value is on the wire, asserted there, and available
to a later surface that wants to say "we could not check this machine".
