# 2026-09-05 — #2580: a release bump may only move the version forward

A **release-control** change, classified **money-path by the file half on
CONTROL globs only**. No runtime money path is touched; nothing under
`packages/*/src` changes. Measured at the head being shipped, not reasoned about:

```
=== SELF-TEST PASSED (6 positive, 6 negative) ===
  MONEY-PATH (controlGlobs) .github/money-path-globs.json
  MONEY-PATH (controlGlobs) .github/workflows/publish.yml
  MONEY-PATH (controlGlobs) scripts/release-bump.mjs
  MONEY-PATH (controlGlobs) scripts/release-version-order.mjs
  0 runtime-glob + 4 control-glob = 4 of 13 on the perimeter
  => MONEY-PATH (control surface only). Labelled and read by a human; no QA
     re-run is implied, because the harness cannot exercise a CI control change.
```

The fourth entry is the module this change adds — it is on the perimeter
*because* this change put it there (see § Perimeter change), so the count is
self-referential in the same way #2536's file total was.

**What it does.** `scripts/release-bump.mjs` now refuses a bump that does not
move the version forward. The rule lives in a new module,
`scripts/release-version-order.mjs`, and runs before anything is written to the
tree.

## Why this exists, and why it is HERE

#2536 made `publish.yml`'s prod channel move the `latest` dist-tag onto whatever
it publishes. It does not compare against the live `latest`, so publishing a
genuinely new version of an OLDER release line would drag `latest` down onto it —
`latest` is 3.0.0, someone cuts a 2.x fix as 2.5.1-alpha.0, and a bare
`npm install` starts serving the older build. Raised by `haven-reviewer` on the
#2536 pull request and filed as #2580 rather than widened into it.

The owner chose **option C**: put the check at the bump, not at the publish. It
fails at the release PR, where a human is already looking and the remedy is to
type a different number — rather than after publication, where the remedy is a
manual dist-tag repair against the live registry.

The two publish-time guards #2580 recorded stay rejected, on measurement rather
than preference: `sort -V` is not semver (`printf '1.0.0\n1.0.0-alpha.1\n' |
sort -V | head -1` prints `1.0.0`, the release ordered *before* its own
prerelease, so a guard on it would refuse the 1.0 release this repo is heading
toward), and `semver` is not a direct dependency. Option C sidesteps both: the
bump script already resolves `semver`, and a failure there is a loud local error
rather than a silent registry state.

## Two deliberate narrowings, stated because each is a limit

**The baseline is the repo's current version, not the published `latest`.**
#2580 worded option C against the registry. This script is offline, and a
registry read would make a deterministic release tool fail on a flaky network or
an air-gapped run. Haven has one release line and `hotfix/*` branches from
`main`, so the repo version IS the newest version and the scenario above is
caught with no network call. **Not caught:** a long-lived release branch whose
`package.json` genuinely sits below the published `latest`. No such branch and
no LTS scheme exists; introducing one means revisiting this baseline.

**Dev-channel snapshots are exempt.** `0.0.0-dev.*` sorts below every real
version by construction — that is what keeps a `^0.1.x` range from ever
resolving to one. A forward-only rule applied to it would close the dev channel.
The identical conflation of "dangerous" with "the ordinary dev path" was shipped
once in #2536's own workflow guard and caught by execution; the exemption here
has its own test with a positive control (the same version *without*
`--snapshot` is still refused, so the flag is doing the work).

## Perimeter change

`scripts/release-version-order.mjs` is **added to the money-path control globs**,
in all three places the drift test pins together (`.github/money-path-globs.json`,
`.github/labeler.yml`, and the Merge Gate list in `ship-next`'s SKILL.md). A rule
that decides which version may reach npm belongs on the same footing as the
script that applies it; lifting it into a new file and leaving it off the list
would be the #1892 failure exactly — the perimeter reading as though it knew
about a control surface it did not cover.

## Evidence

Five mutations, five caught, each restored and the suite re-run (61 pass, 0 fail
— `node --test scripts/release-bump.test.mjs`):

| # | Mutation | Result |
|---|---|---|
| 1 | drop the `semver.lt` refusal | **2 red** |
| 2 | drop the snapshot exemption | **1 red** |
| 3 | drop the `semver.eq` no-op refusal | **1 red** |
| 4 | remove the CALL from `release-bump.mjs` | **1 red** |
| 5 | invert the comparison (`lt` → `gt`) | **3 red** |

**Reachability is proven by executing the real script, not by reading it:**

```
$ node scripts/release-bump.mjs 0.0.1 --yes
  Current SDK version: 0.1.34-alpha.0
  New version:         0.0.1  (0.0.1)
✗ Refusing to bump BACKWARDS: 0.1.34-alpha.0 -> 0.0.1.
$ echo $?   → 1
```

`git status --porcelain` afterwards shows **no unexpected file modified** — the
refusal precedes every write. The *allow* path is proven by unit test over five
pairs (including `0.1.34-alpha.0 → 1.0.0`, the exact pair #2580's acceptance
criteria name) and by mutation 5, which turns those assertions red; it is not
proven by execution, because doing so would perform a real release.

## A miscount corrected, and it was mine

`publish.yml`'s header said the snapshot invariant "is enforced in **three**
independent places" while listing **four** — #2536 added the fourth
(`promote_latest()`) and did not update the sentence directly above it.
`docs/operations/package-dev-channel.md` then repeated the three. Neither
reviewer caught it and no gate could: the count and the list are in the same
file, and the doc was citing it faithfully. Both corrected here, and named as
#2536's defect rather than left to read as a pre-existing one.
