**One line of it is unfixable, and saying so is the point.** The `head` field
names `7d91242c`, the commit BEFORE the one that pastes this block. That is not
an oversight to be corrected on the next commit: a transcript stored inside the

that SHA does not exist until the paste is committed. Chasing it is a fixpoint
that never closes — each correction is itself a commit that invalidates the line
it just fixed. So the field is left naming a real, checkable ancestor rather than
a fabricated current SHA, and what it dates is the RUN, not the shipping head.

**What that gap can and cannot hide.** An earlier version of this paragraph went
further and claimed the numbers were stable across it, "because every commit

**What it does.** `scripts/release-bump.mjs` now refuses a bump that does not
move the version forward. The rule lives in a new module,
`scripts/release-version-order.mjs`, and runs before anything is written to the
tree.

## Why this exists, and why it is HERE

#2536 made `publish.yml`'s prod channel move the `latest` dist-tag onto whatever
it publishes. It does not compare against the live `latest`, so publishing a
genuinely new version of an OLDER release line would drag `latest` down onto it —
`latest` is 3.0.0, someone cuts a 2.x fix as 2.5.1-alpha.0, and a bare
`npm install` starts serving the older build. Raised by `haven-reviewer` on the
#2536 pull request and filed as #2580 rather than widened into it.

The owner chose **option C**: put the check at the bump, not at the publish. It
fails at the release PR, where a human is already looking and the remedy is to
type a different number — rather than after publication, where the remedy is a
manual dist-tag repair against the live registry.

The two publish-time guards #2580 recorded stay rejected, on measurement rather
than preference: `sort -V` is not semver (`printf '1.0.0\n1.0.0-alpha.1\n' |
sort -V | head -1` prints `1.0.0`, the release ordered *before* its own
prerelease, so a guard on it would refuse the 1.0 release this repo is heading
toward), and `semver` is not a direct dependency. Option C sidesteps both: the
bump script already resolves `semver`, and a failure there is a loud local error
rather than a silent registry state.

## Two deliberate narrowings, stated because each is a limit

**The baseline is the repo's current version, not the published `latest`.**
#2580 worded option C against the registry. This script is offline, and a
registry read would make a deterministic release tool fail on a flaky network or
an air-gapped run. Haven has one release line and `hotfix/*` branches from
`main`, so the repo version IS the newest version and the scenario above is
caught with no network call.

**Not caught, and the first draft of this shard understated the trigger.**
Any state where `package.json` sits below the live `latest` defeats the
comparison, and it does not take a parallel release line to get there.
`haven-reviewer` supplied the path on this pull request: release 4.0.0 and
publish it, find a bug, `git revert` the merge — one ordinary emergency move —
and `package.json` reads 3.0.9 while `latest` is 4.0.0. The next patch bump to
3.0.10 is forward *locally*, passes this guard, and drags `latest` down when
published. That is the #2536 defect surviving the rule meant to close it.

Recorded as accepted risk with a **process** control rather than a second
mechanism: `docs/contributing/branch-and-release-flow.md` now states that a
published release bump is not reverted — the fix is a forward version carrying
the revert. Detecting it in code would need the published `latest`, i.e. the
network read rejected above; comparing against git tags instead was considered
and deliberately not taken here, because tags are absent in a shallow CI clone
and that is its own decision rather than a line in this change.

**Dev-channel snapshots are exempt.** `0.0.0-dev.*` sorts below every real
version by construction — that is what keeps a `^0.1.x` range from ever
resolving to one. A forward-only rule applied to it would close the dev channel.
The identical conflation of "dangerous" with "the ordinary dev path" was shipped
once in #2536's own workflow guard and caught by execution; the exemption here
has its own test with a positive control (the same version *without*
`--snapshot` is still refused, so the flag is doing the work).

## Perimeter change

`scripts/release-version-order.mjs` is **added to the money-path control globs**,
in all three places the drift test pins together (`.github/money-path-globs.json`,
`.github/labeler.yml`, and the Merge Gate list in `ship-next`'s SKILL.md). A rule
that decides which version may reach npm belongs on the same footing as the
script that applies it; lifting it into a new file and leaving it off the list
would be the #1892 failure exactly — the perimeter reading as though it knew
about a control surface it did not cover.

## Evidence

Seven mutations, seven caught, each restored and the suite re-run (63 pass, 0
fail — `node --test scripts/release-bump.test.mjs`):

| # | Mutation | Result | Caught how |
|---|---|---|---|
| 1 | drop the `semver.lt` refusal | **5 red** | behaviour |
| 2 | drop the snapshot exemption | **1 red** | behaviour |
| 3 | drop the `semver.eq` no-op refusal | **3 red** | behaviour |
| 4 | remove the CALL from `release-bump.mjs` | **2 red** | behaviour |
| 5 | invert the comparison (`lt` → `gt`) | **5 red** | **`TypeError`, not behaviour** |
| 6 | swap the `lt` arguments (`lt(current, next)`) | **2 red** | behaviour |
| 7 | `getSemver` returns a permissive stub | **1 red** | structure |

**Row 5 is weaker than its red count suggests, and the table says so rather
than banking it.** The suite hands the rule a recording double, and that double
defines only `lt` and `eq` — so renaming the call to `gt` fails as
`semver.gt is not a function`, which catches the typo but proves nothing about
ordering. Rows 6 and 7 carry the weight instead: swapping the ARGUMENTS keeps a
real method name and a plausible-looking call, and is the likeliest actual bug
in this file; row 7 is the attack that broke the first version of this suite.

**Row 7 is here because a reviewer performed it, not because it was imagined.**
`haven-reviewer` replaced `getSemver`'s body with
`{ lt: () => false, eq: () => false, … }` — a comparator that refuses nothing —
left the `node_modules/semver/index.js` path alive in an unused variable, and
watched **all 62 tests pass**. The commit that introduced the double had claimed
in as many words that its guard stopped exactly that. It did not: the guard was a
substring scan over the whole file, so keeping the string anywhere satisfied it.
It is now scoped to `getSemver`'s BODY and asserts the function's shape — that it
returns the imported module, and that it does not fabricate an `lt`/`eq` object.
The same stub now fails.

## What the double genuinely COST, named rather than glossed

Switching from the real semver to a double lost something real, and the first
telling of this change framed it as pure gain. `haven-reviewer` named the loss:
nothing was left proving that the ACTUAL pinned semver orders Haven's own version
pairs the way this rule assumes — above all `0.1.34-alpha.0 -> 1.0.0`, the pair
#2580's acceptance criteria name and the one `sort -V` gets wrong. The double
answers with configured constants whatever strings it is handed, so it cannot
speak to that, and no other automated test exercised it.

Restored where it can be: a test resolves the real semver and asserts the rule's
verdict on those exact pairs, in both directions. It **cannot run in CI** —
`Repo CI config checks` has no `node_modules` by design and is the only job that
runs this file — so it is availability-gated. The gate is deliberately LOUD: when
semver is absent the test still runs and asserts the import failed for the
expected reason, rather than vanishing from the count. `# skipped 0` in both
conditions; 63 pass with dependencies and 63 pass without.

**So the honest summary is a trade, not an upgrade.** Given up: an in-CI check of
real semver's ordering on these pairs. Gained: a suite that runs at all in the
job it belongs to, plus argument-order and structural coverage the real-semver
version never had (rows 6 and 7, neither of which the old suite caught). The
residual risk is that semver's precedence behaviour changes under a version bump
and only a local or reviewer run would notice — low, since prerelease precedence
is fixed by the semver spec, but it is a real gap and it is stated here rather
than left for the next person to discover.

**Reachability is proven by executing the real script, not by reading it:**

```
$ node scripts/release-bump.mjs 0.0.1 --yes
  Current SDK version: 0.1.34-alpha.0
  New version:         0.0.1  (0.0.1)
✗ Refusing to bump BACKWARDS: 0.1.34-alpha.0 -> 0.0.1.
$ echo $?   → 1
```

`git status --porcelain` afterwards shows **no unexpected file modified** — the
refusal precedes every write. The *allow* path is proven by unit test over five
pairs (including `0.1.34-alpha.0 → 1.0.0`, the exact pair #2580's acceptance
criteria name) and by mutation 5, which turns those assertions red; it is not
proven by execution, because doing so would perform a real release.

## The CI failure this shard did not predict

The first push of this change was **red in `Repo CI config checks`** — four of
the new tests died with `ERR_MODULE_NOT_FOUND` on `node_modules/semver/index.js`.
That job is deliberately dependency-free (checkout, setup-node, **no `npm ci`**,
by design so it can run on every PR in seconds), and `release-bump.test.mjs` runs
*only* there. The tests imported the workspace semver, which exists on a
developer machine and does not exist in that job. Reproduced before fixing, in a
clone with no `node_modules`: **4 fail** on the original file, **0 fail** on the
replacement, and the job's other steps (`scripts/ci/*.test.mjs`, 489 pass; the
workspace-pin lint) unaffected either way.

The fix removes the dependency rather than adding an install step, because the
import was testing the wrong thing. `backwardsVersionViolation` does not order
versions — it delegates ordering and decides what to do with the answer. Ordering
is semver's own tested behaviour. What is this module's to get wrong is which
comparator it calls, in which argument order, and whether the snapshot flag
short-circuits above both; a recording double pins all three exactly, and row 6
above is the proof that it is stricter here than the real library was.

One assertion guards the obvious risk a double introduces: production must be
handed the real comparator, not a stand-in. `release-bump.mjs`'s call site is
asserted to pass `await getSemver()`, and `getSemver` to resolve the real
package path.

**Recorded because the near-miss is instructive.** `haven-reviewer` listed "the
`node_modules` symlink caveat" among the things it could not verify from an
isolated worktree. That caveat was the defect, one step removed — a review
correctly naming the boundary of what it checked, and a builder (me) reading the
green local run as though the boundary were not there. The lesson is not "run
more tests"; it is that a suite pinned to a dependency-free CI job has to be
executed under that job's actual conditions, which cost one `git clone` with no
install.

## The perimeter gap this change opened, and how it was caught

Lifting the rule out of `release-bump.mjs` into its own module did something the
refactor did not advertise: it moved release machinery **outside the CASP
perimeter**. Measured, before the fix:

```
$ node scripts/docs/coupling-gate.mjs --strict --changed=scripts/release-bump.mjs
  - [contract] docs/regulatory/casp-risk-guardrails.md      ← implicated

$ node scripts/docs/coupling-gate.mjs --strict --changed=scripts/release-version-order.mjs
  (casp-risk-guardrails.md absent — not implicated at all)
```

§ *Release plumbing is in scope* exists because #1739 found `release-bump.mjs`
gated by nothing — "nine commits in ninety days on a file gated by nothing". Its
argument is that `covers:` gates *edits to a file, never runs of it*, so what it
protects is a change to the release machinery. That argument applies to the new
file identically: it decides which version may reach npm. One refactor of mine
had put it back outside. `scripts/release-version-order.mjs` is now in that
document's `covers:`, and the same command implicates it.

**How it was caught is the part worth recording.** Not by a blocking check —
nothing was red. The docs-coupling gate cleared `casp-risk-guardrails.md` via
this shard's `satisfied-by` glob and printed the #2323 advisory: *the shard is
written by the author of the change, so it certifies itself; nothing has re-read
the parent's body against this diff.* Re-reading it, as that advisory asks, is
what surfaced the gap. A shard asserting "documented" is not evidence that the
parent still describes the world, and here the parent's own reasoning had been
quietly outgrown by the diff that cited it.
