**One line of it is unfixable, and saying so is the point.** The `head` field
names `7865486c`, the commit BEFORE the one that pasted this block. That is not
an oversight to be corrected on the next commit: a transcript stored inside the
file it describes cannot contain the SHA of the commit that stores it, because
that SHA does not exist until the paste is committed. Chasing it is a fixpoint
that never closes — each correction is itself a commit that invalidates the line
it just fixed. So the field is left naming a real, checkable ancestor rather than
a fabricated current SHA, and what it dates is the RUN, not the shipping head.
Everything the shard actually relies on is stable across that gap: the four
control-glob files, the `0 runtime-glob` numerator, and the `4 of 12` denominator
are unchanged from `7865486c` to the shipping head, because every commit since
touches only this file, which is already counted in the 12. Re-run the command
above at any head on this branch and only the `head` line moves.

The fourth entry is the module this change adds — it is on the perimeter
*because* this change put it there (see § Perimeter change), so the count is
self-referential in the same way #2536's file total was.

**The denominator is the fragile half of that block, and it moved once during
this change.** It read `4 of 13` until a review finding sent the branch back to
revert an in-place edit to the already-merged #2536 shard (§ *A miscount
corrected* below); dropping that file from the diff dropped the file total to

re-running the instrument at the shipped head rather than by arithmetic. The
NUMERATOR and the classification did not move and could not have, for a
stronger reason than this paragraph first gave: it said only that no revert of a
docs file can add a *runtime* glob, but `docs/regulatory/**` matches neither
`globs` nor `controlGlobs` in `.github/money-path-globs.json`, so the reverted
file was never eligible for the numerator on either list. The four control-glob
files are named above and are unchanged.

Recorded because the failure mode is the interesting part — a hand-frozen count
in a compliance record decays against its own diff, and only the count that is
cheap to re-run gets caught.

**What it does.** `scripts/release-bump.mjs` now refuses a bump that does not
move the version forward. The rule lives in a new module,
`scripts/release-version-order.mjs`, and runs before anything is written to the
tree.

## Why this exists, and why it is HERE

#2536 made `publish.yml`'s prod channel move the `latest` dist-tag onto whatever
it publishes. It does not compare against the live `latest`, so publishing a
genuinely new version of an OLDER release line would drag `latest` down onto it —
`latest` is 3.0.0, someone cuts a 2.x fix as 2.5.1-alpha.0, and a bare
`npm install` starts serving the older build. Raised by `haven-reviewer` on the
#2536 pull request and filed as #2580 rather than widened into it.

The owner chose **option C**: put the check at the bump, not at the publish. It
fails at the release PR, where a human is already looking and the remedy is to
type a different number — rather than after publication, where the remedy is a
manual dist-tag repair against the live registry.

The two publish-time guards #2580 recorded stay rejected, on measurement rather
than preference: `sort -V` is not semver (`printf '1.0.0\n1.0.0-alpha.1\n' |
sort -V | head -1` prints `1.0.0`, the release ordered *before* its own
prerelease, so a guard on it would refuse the 1.0 release this repo is heading
toward), and `semver` is not a direct dependency. Option C sidesteps both: the
bump script already resolves `semver`, and a failure there is a loud local error
rather than a silent registry state.

## Two deliberate narrowings, stated because each is a limit

**The baseline is the repo's current version, not the published `latest`.**
#2580 worded option C against the registry. This script is offline, and a
registry read would make a deterministic release tool fail on a flaky network or
an air-gapped run. Haven has one release line and `hotfix/*` branches from
`main`, so the repo version IS the newest version and the scenario above is
caught with no network call.

**Not caught, and the first draft of this shard understated the trigger.**
Any state where `package.json` sits below the live `latest` defeats the
comparison, and it does not take a parallel release line to get there.
`haven-reviewer` supplied the path on this pull request: release 4.0.0 and
publish it, find a bug, `git revert` the merge — one ordinary emergency move —
and `package.json` reads 3.0.9 while `latest` is 4.0.0. The next patch bump to
3.0.10 is forward *locally*, passes this guard, and drags `latest` down when
published. That is the #2536 defect surviving the rule meant to close it.

Recorded as accepted risk with a **process** control rather than a second
mechanism: `docs/contributing/branch-and-release-flow.md` now states that a
published release bump is not reverted — the fix is a forward version carrying
the revert. Detecting it in code would need the published `latest`, i.e. the
network read rejected above; comparing against git tags instead was considered
and deliberately not taken here, because tags are absent in a shallow CI clone
and that is its own decision rather than a line in this change.

**Dev-channel snapshots are exempt.** `0.0.0-dev.*` sorts below every real
version by construction — that is what keeps a `^0.1.x` range from ever
resolving to one. A forward-only rule applied to it would close the dev channel.
The identical conflation of "dangerous" with "the ordinary dev path" was shipped
once in #2536's own workflow guard and caught by execution; the exemption here
has its own test with a positive control (the same version *without*
`--snapshot` is still refused, so the flag is doing the work).

## Perimeter change

`scripts/release-version-order.mjs` is **added to the money-path control globs**,
in all three places the drift test pins together (`.github/money-path-globs.json`,
`.github/labeler.yml`, and the Merge Gate list in `ship-next`'s SKILL.md). A rule
that decides which version may reach npm belongs on the same footing as the
script that applies it; lifting it into a new file and leaving it off the list
would be the #1892 failure exactly — the perimeter reading as though it knew
about a control surface it did not cover.

independent places" while listing **four** — #2536 added the fourth

`docs/operations/package-dev-channel.md` then repeated the three. Neither

**A second miscount, in this shard, and also mine.** The perimeter block at the
top of this file froze `4 of 13` at a head that no longer exists. `haven-doc-reviewer`
caught it by re-running the classifier rather than reading the number, which is
the only way it could have been caught — the figure was *true when written* and
was invalidated by a later fix on the same branch, so nothing in the diff of that
fix looks wrong. Two corrections in one shard, both mine, both found by execution
rather than by reading: the pattern is that a count copied into prose has no
owner, while a count with a named command beside it has one. Every figure in this
shard now carries the command that produces it — the perimeter block at the top
included, which had none until this finding. That is a claim about THIS shard
only: `2026-09-03-2423.md` and `2026-09-05-2576.md` already name the classifier
beside their own perimeter figures, and a first draft of this sentence said
otherwise.

**The immutability line these two corrections sit on either side of.** The #2536
shard is MERGED, so it is a compliance record and gets no in-place edit; the
correction to what it claims lives here, in the new shard, per
`docs/regulatory/casp-changelog/README.md`. THIS shard is not merged yet, so
correcting its own stale denominator in place is not the same act — it is a

moved the denominator.
