**#2366 part 1 — the `idempotencyKey` deprecation window on `@haven_ai/mcp`.** The local
MCP surface now accepts `idempotency_key` alongside `idempotencyKey`, warns on the legacy
name, and refuses the pair when they disagree. Schema plus argument routing in
`packages/mcp/src/tools.ts`; no route, no credential path, no signing surface, and no
change to what any tool may spend.

The perimeter argument turns on what the argument controls. An idempotency key is the
replay contract: with it, a retry of a payment is the same payment; without it, a retry is
a **second spend**. #2312 found the hosted surface silently stripping the local spelling,
so a caller believed it had set a replay scope it had not — measured on `haven_send` as a
`POST /payments` carrying no `idempotency_key` field at all. #2348 replaced that strip
with a refusal, which is strictly safer and left two surfaces permanently
non-interchangeable. This is the window to one spelling (owner decision 2026-09-06).

Three properties carry the safety of the window itself. **Both spellings with different
values is REFUSED, never resolved** (`AMBIGUOUS_IDEMPOTENCY_KEY`), because choosing either
would be Haven deciding which replay scope the caller meant, and a wrong choice on this
argument is the exact second-spend failure the key exists to prevent; the refusal happens
in a preflight, before anything is contacted, so nothing is spent. **Equal values are not
ambiguous** and are accepted. **The legacy name still works**, because a published package
cannot break installed callers on the release that renames an argument — the warning is
what makes this a window rather than a fork, and it rides in an additive optional
`warnings` field, so a caller that ignores it sees exactly the response shape it saw
before.

Pinned over the real `client → InMemoryTransport → server` path rather than by calling
handlers, because the MCP SDK strips undeclared keys before a handler runs and a
handler-level test cannot tell a declared argument from an undeclared one (#2312's
lesson). All five tools that take the key are proven wired individually, by the ambiguity
refusal, after a mutation showed a single unwired tool is otherwise invisible: the legacy
name keeps working there and the new one is silently dropped, which is the pre-#2366
behaviour. Mutation-proven both ways — unwiring one tool, and removing one schema alias.

One behaviour change this PR first described as preservation, corrected on review: moving
`objectInput` inside `preflight`'s try/catch made a schema rejection **structured on all
five tools**, where three of them previously threw a raw `ZodError` out of the handler.
Only the direct-embedder path can observe it — through the MCP client the SDK validates
against the registered schema first and answers `-32602` identically before and after —
and no money moves on either path, since both refuse before any network call. It is an
improvement rather than an accident, and it is now asserted for the three tools that
changed, which were untested precisely because the two that already behaved this way were
the two with tests.

**Deliberately NOT included, and it is the finding worth carrying:** the issue lists
`quote` (local) versus `payment_required` (hosted) alongside this as a second spelling to
converge. **It is not a spelling.** Hosted `payment_required` is the parsed HTTP 402
PaymentRequired object; local `quote` is the whole `X402Quote` and is passed to
`payX402Quote` as such. Renaming one to the other would change what a caller must send,
not what it is called — silently, in the direction that looks correct. That divergence
needs its own decision and is recorded rather than bundled. Perimeter unchanged.
