**#2366 (part 2) — the hosted `haven_quote_x402` can quote a body-bearing paywall.** One
optional `body: z.string()` on the hosted schema (`packages/mcp-server/src/tools.ts`),
threaded into the probe's `RequestInit`, plus tests over the real MCP transport. No route,
no credential path, no signing surface, and no change to what any tool may spend.

The perimeter argument is that this **removes** a way for Haven to describe a payment
inaccurately. Before #2348 the hosted surface silently STRIPPED a `body` the caller sent,
so a body-bearing POST paywall was probed with an empty body and the returned quote
described a request the caller never made — measured over the real transport on
2026-09-01 as `POST /paid :: ` (empty). #2348 replaced that lie with a refusal, which is
strictly better and also left the merchant honestly unquotable. This closes the gap in
the direction the issue named: the field exists, so the probe is the request.

Two details carry the safety argument rather than the convenience one. First, the value
is threaded **verbatim** and no `Content-Type` is inferred — the caller sends `headers`
for that, exactly as the local surface does, so Haven never invents a request shape the
caller did not ask for. Second, the guard is `!== undefined` rather than truthiness: an
empty-string body IS a body, and a paywall that varies on a payloadless `POST` is a
different request from one with no body at all. Conflating them would be the same class
of error the refusal existed to avoid committing, one layer down.

A quote creates no payment, reserves no price and moves no funds — it is a read that
returns what a merchant would charge — so the blast radius of getting this wrong is a
misinformed caller rather than a misdirected payment. That is precisely why it is worth
fixing rather than tolerating: the quote is what a caller sets a spending cap from, and a
cap chosen against a quote for a different request is a cap that does not bind what the
caller thought it bound.

Pinned over the real `client → InMemoryTransport → server` path, never by calling the
handler directly, because the SDK strips undeclared keys before a handler runs and a
handler-level test would prove nothing (#2312's lesson). Mutation-proven three ways:
dropping the threading, swapping `!== undefined` for truthiness, and removing the schema
field each turn the suite red.

**Part 1 of #2366 is deliberately NOT in this change and the issue stays open for it.**
Converging `idempotencyKey`/`idempotency_key` renames an argument on the published
`@haven_ai/mcp` package and needs a deprecation window — an owner call about a release
train, not a parse decision. Two crossover guards in `strict-tool-input.test.ts` that
named `body` as this tool's local-only key were re-based to `idempotencyKey` rather than
deleted, so they keep guarding the divergence that actually remains. Perimeter unchanged.
