**#2537 — an onboarding section in the shipped `haven-pay` skill.** The skill
string in `packages/sdk/src/skill-content.ts` (auto-installed by the connector,
byte-pinned twin in `packages/frontend/src/lib/agent-skill-bundle.ts`) gains an
**Onboarding and setup** section for the agent asked to connect a second agent
or set a colleague up. Text only: no route, tool, schema or credential path
changes, and the diff adds no code that runs. The perimeter argument is that
this section makes Haven's existing custody boundary *harder* to cross by
accident rather than moving it. Its load-bearing sentence says that none of the
skill's payment tools creates authority — no tool opens an account, mints a
credential or approves a budget — which is the fact an agent asked to "set
Haven up" would otherwise have to infer from the absence of such a tool, and
the inference it actually makes instead is to reach for a payment tool. The
four human-only steps are named whole (account and passkey, funding, every
budget approval, credential rotation), because an agent that relays three of
them leaves its user stuck at the fourth believing setup is done. Funding is
described as the human step it is — the user copies the wallet address from
their dashboard and sends USDC on Base — and deliberately does NOT name
`haven wallets funding`, which is B4/#2534: still open, no PR, absent from
`dev` at this commit. Naming a command that does not exist would put a
fabricated instruction in the one document an agent is told to trust; the
omission is pinned by an assertion (`expect(section).not.toContain('wallets
funding')`) so it cannot be reintroduced silently before B4 lands. The
device-code login is described as the allow-list it is
(`packages/backend/src/middleware/owner-cli.ts`) rather than as the user's full
authority, and the section states in as many words that the session cannot
approve a budget, rotate a key, change a signer or move money — `rotate-key`
included, on the owner's decision of 2026-09-05. The three connector rules
(approval relay, permitted command modifications, wiring collision) are
interpolated from `packages/sdk/src/agent-guidance.ts`, the same source the
backend's `buildSetupPrompt` and the `/for-agents.md` runbook read, so a rule
an agent meets on two surfaces cannot drift into two versions; the parity test
is mutation-proven (a one-word edit to the frontend twin turns it red, restored
by `cmp`). The standing owner constraint that the human keeps every signature
and the agent never asks for a password is asserted with a positive control, so
the negative is a fact about the text rather than about the regex. No money
moves, no authority is created, and nothing in the custody model changed.
Perimeter unchanged.
