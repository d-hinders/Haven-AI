**What changed.** C3 of epic #2519: `haven budget grant` and `haven budget
revoke` construct signature requests and hand them to a human. The CLI (and the
newly allow-listed `POST /agents/{id}/delegations/build` and per-hash
`.../revoke` PREPARE routes for `owner_cli` tokens) can now reach the two
CONSTRUCT routes. The build response gained `build_id` / `typed_data_hash`
(both the delegation hash — one identifier, no new column) and `signing_url`
(the dashboard grant form with `?grant=` prefill, host from `FRONTEND_URL`); the
revoke prepare gained `revocation_url`, built by the same helper.

**Authority and custody: what moved, what did not.** Before this change, an
`owner_cli` token could read delegations and nothing else about them; the
dashboard built, activated and revoked. After it, the token can additionally
CONSTRUCT — build an unsigned delegation row, or prepare an unsigned sponsored
`disableDelegation` UserOp. The perimeter question is whether either route can
now change authority with an API credential alone, and the answer is no, three
ways, each already enforced by existing machinery this PR did not touch:

1. **The signature steps stayed refused.** `activate` and both `submit`
   routes are not on the allow-list; `routeAllowsOwnerCli` answers no, the
   census discovers and refuses them by name (`mustRefuse` gained
   `.../activate`, `.../revoke/submit`, `revoke-all/submit`), and the
   authority-shape regex class narrowed from `delegations/(build|revoke)` to
   the signature steps (`delegations/.*/submit` plus `/revoke-all`), because
   build and revoke-prepare moved from the forbidden class to the allow-list
   in the same commit. `activate` also still demands the owner
   WebAuthn/ECDSA signature at the route itself (pinned by the
   characterization test added this PR), independent of which token arrives.
2. **Nothing in the two construct routes writes a signature.** Build inserts a
   `pending` row (or reuses one — see below) and returns typed data plus a
   link; revoke-prepare returns an unsigned UserOp plus a link. Neither can
   flip a row: activate/submit remain the only writers of the signed state,
   and they require the owner signature in the request body. This is the same
   construct/commit split §3 already draws for the grant itself — the slice
   moved the construct half behind a second door, not the commit half.
3. **The CLI never signs.** `packages/cli/src/commands.ts` gains no key
   material, no signer import, no call to activate or submit; `--wait` polls
   `GET /agents/:id/delegations`, a read. The human's signature in the
   dashboard remains the only way either flow completes — the boundary §9
   draws ("the human keeps every signature") is unchanged; what changed is
   that the agent can now also print the paper to sign.

**The one semantic change to the build route: idempotent reuse (#2539's
load-bearing piece).** `POST /agents/:id/delegations/build` previously minted a
fresh version and a fresh pending row on every call. Now, an identical
`(agent, token, recipient|open, budget, period)` slot with a still-pending,
UNEXPIRED row returns THAT row — same `delegation_hash`, same `version`,
201 shape unchanged, nothing inserted. The money-path property this protects:
a CLI `--wait` polls for a specific hash to go active; without reuse, the
dashboard form's own rebuild of the same grant would mint version N+1 and
strand the CLI's hash pending forever (an agent budget silently stuck behind a
row nobody will ever sign). Reuse cannot RAISE authority: it matches the exact
budget string cast to numeric (a raise is a new version), the exact recipient
slot, and requires the row still pending and unexpired — an expired offer is
dead and is rebuilt fresh rather than re-handed, because its timestamp caveat
would refuse the signature on-chain. The refused-request SET is unchanged:
every pre-existing 400/404/409 path runs before the reuse lookup, which only
ever turns "insert a duplicate pending row" into "return the existing one".

**Perimeter unchanged** in the sense this log means: no new chain interaction,
no new signature verifier, no change to what a signature authorizes, no
non-custody surface moved. The two routes an API credential may now reach
construct exactly what the dashboard could always construct, and the
signature-gated steps they hand off to are precisely as refused as before —
now pinned by three more census refusals and a characterization suite. The
spend authority a delegation grants is bounded on-chain by the same caveat
enforcers; nothing here widened a budget, only who may TYPE the request for
one.
