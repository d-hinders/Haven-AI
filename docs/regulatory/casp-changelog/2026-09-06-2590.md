**#2590 — the CLI's `--help` told an agent the truth about neither of its two
authority-relevant commands.** Text-only: `helpText()` in `packages/cli/src/args.ts`,
plus a guard in `commands.test.ts`. No route, no schema, no credential path, and no code
that runs differently. The perimeter argument is that this narrows a gap between what
Haven's surfaces claim and what the software does, on the two commands closest to
authority.

The first claim was an omission. `agents connect` — which creates a connection setup and
prints the connector command a human will run — is in `COMMANDS`, is dispatched, and
works, and appeared nowhere in `--help`. The cold-agent run of 2026-09-06 (#2538) hit
exactly that: it followed `/for-agents.md` to the step that names the command, ran
`haven --help` to check it, did not find it, and concluded the command does not exist.
Three agent-facing surfaces — the runbook, the backend's setup prompt, and (since #2537)
the shipped `haven-pay` skill — instruct an agent to run a command the CLI's own help
omitted. The guard added here pins `helpText()` against `COMMANDS`, which is itself
already pinned against `dispatch`'s switch, closing the third edge of that triangle; it
immediately found a second omission (`agents resume`, present only inside
`agents pause|resume`, which an agent searching for the command name does not match).

The second claim was false rather than absent, and it is the one that touches custody
copy. `--help` described `login` as *"Sign in (password via prompt or HAVEN_PASSWORD)"*.
Since #2526 the **browser device-code flow is the default** and `--email` selects the
password path — `commands.ts:310` says so in as many words. So the CLI's own help told a
reader that signing in means handling a password, while `/for-agents.md`, the setup
prompt and the skill all promise an agent it will never need its user's password. An
agent that trusted the help over the runbook would have had no correct action available:
it must not hold that password, and the help offered no other route. The corrected text
leads with the device flow and states that it never asks for a password, keeping the
`--email` path findable for a human who wants it.

Nothing here changes what the CLI can do, and in particular nothing changes what an
`owner_cli` session may reach — that allow-list is unchanged, `rotate-key` remains off
it, and the human keeps every signature. The change is that the CLI now describes its
own authority boundary the same way every other Haven surface does. Both corrections are
mutation-proven (removing every mention of `agents connect`, reverting the `login` line,
and adding a command to `COMMANDS` with no help line each turn the guard red), and every
mutated file was restored from a task-named backup and verified byte-identical.
Perimeter unchanged.
