- **0.1.35-alpha.0 release** — **34 commits across the five published packages
  since the `0.1.34-alpha.0` tarballs; no custody or execution boundary moves,
  and the two authority-adjacent changes are analysed in their own shards.**
  The largest published-set release so far and the first in six days
  (`0.1.34-alpha.0` was cut on 2026-09-01 at `dce50f6e`), so it is summarised by
  theme rather than commit-by-commit; every substantive issue below carries its
  own shard in this changelog and those are not restated here.

  **The CLI becomes a usable agent surface** — `--json` on every command with
  documented exit codes and a `haven guide` (#2525), browser-approved
  device-code login bounded by an `owner_cli` route allow-list (#2526),
  `haven agents connect` (#2527), `haven budget grant|revoke` (#2539), and help
  and README corrections (#2593, #2607).

  **Connect flow** — existing-agent wiring collisions resolved at setup before
  registration (#2551), the approval link reaching the agent with the setup
  recording how it was run (#2528), a channel-aware re-run command and a local
  runtime-spec override (#2423, #2424), the non-TTY prose path no longer
  waiting on an approval it cannot observe (#2484), an offer to revoke agents a
  setup supersedes (#2561), funding as a machine-readable step (#2534), and a
  copyable onboarding prompt (#2535).

  **MCP and SDK** — the idempotency-key spelling window on `@haven_ai/mcp`
  (#2366, shards `2026-09-06-2366.md` and `-2366-spelling.md`), `AgentNextStep`
  bound to what the hosted server actually emits (#2565), and the agent
  onboarding runbook published at `/for-agents.md` (#2571).

  **Two authority-adjacent items, both with a perimeter verdict of their own.**
  **#2526** adds a *session-acquisition* route for the CLI, not a new authority:
  what an owner session may reach through it is bounded by an explicit route
  allow-list, whose shard records the mutation set that pins it (including the
  owner's own removal of `rotate-key` from that list, which two tests refuse).
  **#2539** is construct-and-hand-off — the two routes an API credential may now
  reach construct exactly what the dashboard could always construct, and the
  signature-gated steps they hand off to are precisely as refused as before; in
  its shard's words, nothing widened a budget, "only who may TYPE the request
  for one".

  **Verified for this release rather than assumed.** The local runtime's
  registered tool-name set is **identical** to the `0.1.34-alpha.0` tarballs
  (`packages/mcp/src/tools.ts`, name sets diffed at `dce50f6e` vs this commit)
  and `packages/mcp/src/consent.ts` is byte-unchanged; since the consent hash
  binds the api-key prefix to the registered tool set, **no operator is
  re-prompted on upgrade**. `packages/mcp/src/tools.ts` did change (+124/-14) —
  an additive argument alias and a preflight helper, no tool added or removed.
  The signer's signing path is unchanged: `core.ts` moves only an import,
  comment text, and one guidance string now derived from `connectorRerunCommand()`
  rather than a hardcoded `@alpha` literal, so the #1143 signing-time guard is
  untouched. On the hosted server, `parse` → `parseStrict` is a rename within
  the existing strict-input mechanism; `STRICT_INPUT_TOOLS` membership is
  unchanged. The `haven_x402_authorize` / `haven_list_transactions` exports were
  deleted, and that is not a surface removal: they were defined in #314 and
  never registered, so a caller using either name has received "tool not found"
  since then.

  **Release mechanics:** versions, cross-package pins, source version constants
  and the runtime-manifest table were rewritten atomically by
  `release-bump.mjs` (nothing hand-edited); the resulting diff is 33 insertions
  and 33 deletions across 14 files, version lines only. Publishing remains gated
  on the `dev → main` promotion, which also carries four schema migrations
  (075–078) that are backend-side and outside the published packages.

  Perimeter unchanged — this release changes who may *ask* for an action and how
  an agent is onboarded, and nothing about who may spend, sign, or execute. The
  spend authority a delegation grants remains bounded on-chain by the same
  caveat enforcers.
