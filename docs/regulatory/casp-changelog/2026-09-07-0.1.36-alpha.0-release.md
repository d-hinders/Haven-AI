- **0.1.36-alpha.0 release** — **one issue reaches npm (#2618, the CLI's
  non-blocking login); no custody, signing or execution boundary moves.** A
  small release cut one day after `0.1.35-alpha.0`, because that release's CLI
  login work was superseded on `dev` before anyone could use it.

  **The baseline for "what this carries" is `main`, not the previous bump
  commit — and getting that wrong is how a release shard overstates itself.**
  `publish.yml` builds tarballs from **`main`'s tree at promotion time**, not
  from the tree at the bump. The 0.1.35-alpha.0 promotion (`783300eb`) carried
  the bump *plus* #2619 and #2627 to `main` in the same merge, so both were
  already baked into the published 0.1.35-alpha.0 artifacts. The first draft of
  this shard measured from `bee38440` and claimed three issues; two of them were
  already on npm. Corrected here, and the correction is recorded rather than
  quietly applied because the error class — measuring a release against the bump
  instead of against what the registry holds — would recur.

  **Verified against the published tarballs, with positive controls** (an
  earlier attempt grepped a path that does not exist in the bundle and returned
  a meaningless zero, so each probe below is preceded by a control string that
  must fire):

  | probe | published `@haven_ai/sdk@0.1.35-alpha.0` | published `@haven_ai/cli@0.1.35-alpha.0` |
  |---|---|---|
  | control (`USDC only, no ETH` / `budget show`) | 2 ✓ | 5 ✓ |
  | #2619 `funding card on` | 1 — already shipped | — |
  | #2627 `--hashes` | — | 4 — already shipped |
  | #2618 `--poll` | 0 | **0 — genuinely new** |

  Ancestry agrees: `466a6a32` (#2619) and `e8aec20b` (#2627) are ancestors of
  `origin/main`; `b2167b08` (#2618) is not.

  **So the new-to-npm content delta is 7 files, +339/-14**
  (`git diff origin/main <head> -- packages/cli/src packages/sdk/src`): six
  files under `packages/cli/src` and one line of
  `packages/sdk/src/agent-guidance.ts`.

  **#2618 — non-blocking CLI login.** `--no-wait` documented in help,
  `haven login --poll <device_code>` as a one-round poll (exit 3 while pending,
  0 once approved), a 30-second `--json` wait, and a password hint. The SDK line
  is the consequence: step 1 of the agent onboarding runbook now tells an agent
  not to hold its process open waiting on a human's browser approval.

  **Perimeter reasoning.** `login --poll` exchanges a device code a human has
  already approved in a browser; it acquires a **session**, and the session it
  acquires is the `owner_cli` scoped token whose route allow-list was analysed
  under #2526 — this change alters *when the CLI stops blocking*, not what the
  resulting credential may reach. Nothing under `modules/x402/`, `rails/`, or
  the payment routes is carried by a published package here.

  **What did NOT change, by construction rather than by inspection.**
  `git diff origin/main <head> -- packages/mcp/src packages/signer/src
  packages/connect/src packages/mcp-server/src` returns **empty**, and
  `@haven_ai/core` is unchanged, so there is no shared-kernel path either. All
  four subjects that matter live inside those trees: the registered tool-name
  set and `consent.ts` (`packages/mcp/src`), `STRICT_INPUT_TOOLS`
  (`packages/mcp-server/src/tools.ts`), and the #1143 signing-time guard
  (`packages/signer/src`). The one live exposure — all four depend on
  `@haven_ai/sdk`, which did change — was traced rather than waved away: the
  changed export is `HAVEN_AGENT_RUNBOOK_MD`, which no file in those four trees
  imports; the SDK guidance symbol they do import, `HAVEN_SKILL_MD`, is defined
  in the unchanged `packages/sdk/src/skill-content.ts`.

  **Therefore no operator is re-prompted on upgrade.** `consent.ts` is
  byte-identical to `main`, and its hash covers three components — the identity
  (api-key prefix, api URL, agent id, safe address, delegate address, chain id),
  the canonical tool set, and the canonical allowance set. No version constant
  feeds it, so a bump cannot move it.

  **Release mechanics:** versions, cross-package pins, source version constants
  and the runtime-manifest table were rewritten atomically by
  `release-bump.mjs` (nothing hand-edited). Reading the script-owned files
  alone, the diff is 33 insertions and 33 deletions across 14 files, version
  lines only — the raw commit shows 16 files / +105/-35, the difference being
  this shard and two hand-written `last-verified` notes, which the bump does not
  own. `HAVEN_CONNECTOR_CHANNEL` is untouched because the channel does not move:
  `alpha` → `alpha`.

  **Tested, and the gap named:** all five published packages pass their suites
  (sdk 422, signer 183, mcp 126, connect 527 + 5 skipped, cli 195), plus
  typecheck, `check:dist`, workspace-pin lint and `docs:check`. The **backend
  and frontend suites were not run** — no Postgres in the authoring
  environment — and that is an environment limit, not a result. CI covers both
  on the PR, which matters for one specific coupling: `packages/cli/src/agent-guidance-text.ts`
  is a byte-exact vendored copy of the SDK runbook string, pinned by a hard
  length assertion, and the frontend suite separately asserts the served
  `/for-agents.md` equals the same source.

  **This promotion is the first to run the `promote-tags` job (#2647).** That
  job moves the `latest` dist-tag with a credential path never yet exercised —
  a `main`-only environment secret — so a **half-green** outcome is a live
  possibility here rather than a hypothetical: packages published, `latest`
  unmoved. `latest` currently reads `0.1.35-alpha.0` on all five (the E401 tag
  moves from that release were repaired by hand afterwards), so a half-green
  promotion would strand it there. Verify with
  `npm view @haven_ai/<pkg> dist-tags`, never with a green workflow.

  Perimeter unchanged — this release changes how an agent *acquires a session*
  and nothing about who may spend, sign, or execute. The spend authority a
  delegation grants remains bounded on-chain by the same caveat enforcers.
