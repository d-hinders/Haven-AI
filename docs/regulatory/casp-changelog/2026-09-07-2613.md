- **#2613** — `POST /agents/{id}/delegations/build` now runs its reuse read,
  its `MAX(version) + 1` read and its insert inside ONE transaction holding
  `pg_advisory_xact_lock` on the `(agent, token, recipient|open)` slot. No new
  route, no new authority, no new custody surface, and no change to what
  Haven can sign — the build path still returns an UNSIGNED delegation and the
  owner's browser still produces every signature (invariant 3 unchanged). The
  defect was a duplicate-offer one, not an authority one: unsynchronized, two
  concurrent identical builds each missed the reuse read before either
  committed, each computed version 1, and each inserted, because `startDate` is
  `nowSec - 60` and a request pair straddling a second boundary hashes
  differently, so the `ON CONFLICT (delegation_hash)` guard never fired. One
  slot then held two pending version-1 rows and the owner was asked to choose
  between two unsigned grants for the same authority, with no rule saying which.
  The lock makes the second caller's reuse read run after the first commits, so
  it returns the existing row — the #2539 behaviour, now reached under
  concurrency and not only sequentially. Two properties are proven against real
  Postgres rather than asserted: a POSITIVE CONTROL runs the same sequence
  WITHOUT the lock and observes the two rows appear, so the harness is shown
  able to see the defect before the fixed case is trusted; and removing the
  `pg_advisory_xact_lock` statement reddens the locked test by name (restored
  byte-identical, verified with `cmp`). The chain round trip that derives the
  delegate account address was moved ABOVE the lock so no slot is held across
  an RPC. Perimeter unchanged.
