- **#2618** — CLI auth UX and docs only, on the existing device flow: `haven
  login --json` now waits at most 30 seconds by default and then emits
  `{ status: 'pending', device_code, retry_after }` with exit 3 instead of
  polling to the code's expiry; a new `haven login --poll <device_code>`
  performs ONE round against the SAME endpoint the blocking loop already
  polls (`POST /auth/device/token`, unauthenticated by design — the device
  code is the credential) and exits 0 approved / 3 pending / 4 denied, so an
  agent can finish an approval without holding a process open or killing it
  and losing the code. The link object now also carries `device_code`, the
  handle that poll command consumes. No new route, no new authority, no
  custody surface, no signing path: the session either path saves is the
  same `purpose: owner_cli` device-flow token the backend scopes by its
  allow-list, unchanged since #2526, and the CLI still never signs. The
  `not_authenticated` hint was rewritten to name the device flow FIRST and
  describe `HAVEN_EMAIL`/`HAVEN_PASSWORD` as the human path — the runbook's
  standing rule that an agent never holds the password, previously
  undermined by a hint that offered the credentials as a co-equal route.
  The new vitest cases pin the exit-code mapping (0/3/4, `slow_down`
  widening, expired treated as the blocking flow's exit 3), the pending
  object shape, the 30-second `--json` cap with the prose-mode full wait
  pinned unchanged, and the hint text with the old wording asserted absent.
  Perimeter unchanged.
