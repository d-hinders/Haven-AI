- **#2647 (release-record amendment) — one space in the agent onboarding
  runbook, and the record corrections that found it.** No route, no credential,
  no signing path, no key handling. The code change is a single character.

  **What the character is.** #2617 and #2618 each appended a sentence to step 1
  of `HAVEN_AGENT_RUNBOOK_MD`, and the seam between them lost its space:
  `never a tag you pick.Do not hold the process open`. Neither PR could see it —
  each read only its own sentence, and each was correct in isolation. It
  surfaced when the 0.1.36-alpha.0 release shard's SDK-delta claim was reviewed
  against the *merged* string, which is the only place the defect exists.

  **Fixed in all three copies, because there are three and only one instrument
  compares them.** The canonical source (`packages/sdk/src/agent-guidance.ts`),
  the CLI's generated vendored copy (`packages/cli/src/agent-guidance-text.ts`,
  regenerated with `packages/cli/scripts/sync-agent-guidance.mjs` rather than
  hand-edited), and the served artifact
  (`packages/frontend/public/for-agents.md`, which nothing regenerates — its
  parity test is the mechanism, #2523). The byte-length assertion in
  `agent-guidance-text.test.ts` moves 10224 → 10225 with its reason recorded
  inline, and the frontend parity test confirms the served file matches source.

  **Perimeter: none.** The runbook is prose an agent reads before it has an
  account. It confers nothing, and a missing space confers nothing either — the
  defect is legibility, caught before publication (`0.1.35-alpha.0` predates
  #2617, so the run-on never reached npm). `@haven_ai/sdk` 422 and
  `@haven_ai/cli` 195 re-run green after the change, plus the `/for-agents.md`
  parity test at 10/10.

  **The rest of this change is a regulatory record correcting itself**, and is
  worth recording as a pattern rather than an incident. The 0.1.36-alpha.0
  release shard was amended twice before promotion: first because it measured
  scope from the previous *bump commit* rather than from `main` (two of its
  three claimed issues were already on npm), then because #2617 merged 76
  minutes after the bump and joined the same promotion. Both were found by
  `haven-doc-reviewer`, neither by the author. The second pass also caught four
  derived claims that had gone stale with the baseline — `@haven_ai/core`
  described as unchanged when #2617 moved one line of it, a diff described as
  "empty" that is six version literals against `main`, a bump stat that did not
  reconcile with its own decomposition, and a delta labelled "new-to-npm" that
  counted 219 lines of test files which never ship while omitting the README
  that does.

  The structural cause is stated in the release shard and repeated here because
  it will recur: `publish.yml` builds tarballs from **`main`'s tree at promotion
  time**, so any release record written when the bump is cut is wrong by
  construction the moment anything lands behind it. A release record is not a
  document you write once; it is a measurement you re-take at the door.

  **Recorded, deliberately not fixed here:** `packages.cli.channel` holds a full
  package spec (`@haven_ai/cli@alpha`), not a bare tag, while #2617's runbook
  copy tells an agent to substitute it as `<channel>` — composing
  `npx @haven_ai/cli@@haven_ai/cli@alpha`, which does not resolve.
  `packages.cli.one_liner` is the field that works. Left to #2617's author
  because the fix is a product-copy decision, not a mechanical correction; it
  ships in 0.1.36-alpha.0 and is named in that release's shard so the promotion
  is not made in ignorance of it.
