- **#2647** — **authenticates the `latest` npm dist-tag promotion so it cannot silently regress to E401; no authority, custody, signing or execution boundary moves.**
  **Incident.** Production publish run 34114664962 published five `alpha`
  prereleases cleanly via npm Trusted Publishing (OIDC), then failed every
  `npm dist-tag add … latest` with `npm error code E401` for all five packages
  in a row. OIDC Trusted Publishing authorizes `npm publish` and nothing
  else — `promote_latest()` (#2536) had no usable credential for the dist-tag
  mutation, and the failure is deterministic, not transient: it would repeat
  on every future prerelease publish until authenticated.
  **Money-path classification: YES, control surface only, by the file half.**
  `.github/workflows/publish.yml` is a `controlGlob` in
  `.github/money-path-globs.json` (added #1045: "the harness cannot exercise
  it"). Re-derived with `scripts/ci/money-path-classify.mjs origin/dev` at
  commit `edabb848`: 2 files changed (`.github/workflows/publish.yml`,
  `scripts/release-bump.test.mjs`), 0 runtime-glob + 1 control-glob = 1 of 2
  on the perimeter — labelled and read by a human, no QA re-run implied,
  because the money-flow harness does not exercise a CI publishing
  workflow's own auth wiring.
  **What changed, exactly.** `promote_latest()` now refuses to call
  `npm dist-tag add` at all without its own credential
  (`secrets.NPM_LATEST_TAG_TOKEN`), applied ONLY to that one command via a
  throwaway `--userconfig` file created and deleted around the single call —
  never written to the job's ambient `~/.npmrc`, so it cannot substitute for
  OIDC on the `npm publish` calls, which keep authenticating exactly as
  before. Without the token it fails closed with a named `GUARD:` line
  instead of a bare `E401`. Separately, the publish loop's "already on npm"
  branch now calls `promote_latest()` instead of skipping outright, so a
  re-run (or a `workflow_dispatch` of `channel=prod` on `main`) heals a stale
  `latest` left by a partial failure — idempotently: `npm publish` rejects a
  duplicate version, so nothing already registered can be re-published, and a
  healthy re-run's only new work is one `npm view` and, where needed, one
  `npm dist-tag add` per package.
  **What did NOT change.** No signature is produced, verified, stored or
  transported differently. No payment, delegation, allowance or budget check
  moves — this workflow does not touch any of them. The four-guard channel
  wall from #2421/#2536/#2580 (ref/channel refusal, `assert_publish_allowed()`
  before every publish, `release-bump.mjs`'s `--snapshot` requirement, and
  `promote_latest()`'s own version-shape check) is untouched in shape: a
  `0.0.0-dev.*` snapshot is still refused inside `promote_latest()` **before**
  the new token check is ever reached — the case statement handling the
  snapshot shape runs first and `return`s (or fails) without falling through
  to the credential check, so the new guard cannot loosen the old one, only
  add a further requirement on the path the old guards already allow. No
  migration, no schema change, so `CODEOWNERS` is not implicated.
  **CASP argument.** This changes which registry API call is authenticated by
  which credential during a package release, not any user-facing money
  movement. Haven still custodies nothing, holds no user key, and signs
  nothing here; Red Lines 1-5 are not implicated because this workflow sits
  entirely outside the payment/delegation surface — it decides which npm
  dist-tag a `package.json` version publishes under, nothing about how an
  agent spends. The one real risk is supply-chain-adjacent, and the first
  version of this shard understated it — corrected here after independent
  review rather than left standing. It said the token is "restricted to
  dist-tag operations — it cannot publish a new version". **No such npm scope
  exists.** Granular tokens are read-only or read-and-write over a package
  set, with no verb-level split, so the token an operator provisions from that
  instruction is read-and-write on the five `@haven_ai` packages and CAN
  publish them. The confinement this change actually delivers is a property of
  the WIRING, not of the credential: the token is applied only inside
  `promote_latest()`, to one `npm dist-tag add`, through a throwaway
  `--userconfig` that is deleted immediately, never exported job-wide and
  never able to substitute for OIDC on a publish call in this workflow. A LEAK
  of it, however, reaches further than that, so it is to be stored, rotated
  and audited as a publish credential. Stating this plainly matters more than
  the reassurance it replaces: an operator who believes a token cannot publish
  will guard it accordingly. Provisioning
  that token is an **operator step this PR does not perform** — the secret is
  referenced only by name (`secrets.NPM_LATEST_TAG_TOKEN`) throughout, and
  nothing in this diff states or implies it has been set. The issue stays
  open (`Refs #2647`, not `Closes`) for exactly that reason.
  **What this document does NOT assert.** That `secrets.NPM_LATEST_TAG_TOKEN`
  exists on the repository. That the incident's stranded `alpha` publishes
  (`0.1.35-alpha.0` on `sdk`/`signer`/`connect`) have had their `latest` tag
  healed — that requires the operator step above, then a re-run of this
  workflow, neither of which this PR performs.
  **Mutation-proven, not merely asserted.** Three independent mutations
  against the real `.github/workflows/publish.yml`, each restored via `cp`
  and verified byte-identical with `cmp` before the next: (1) removing the
  `NPM_LATEST_TAG_TOKEN` presence check — 2 new tests red (the missing-token
  refusal and the already-published-with-no-token case); (2) removing the

  makes for that env var); (3) reverting the "already on npm" branch to its

  recovery-failure reporting, and the no-token-plus-already-published
  composition). All three restored and the full suite re-run green (69
  passed) before this shard was written.
