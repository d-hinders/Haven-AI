- **#2647** — Release plumbing only, no product surface and no perimeter move:
  the `latest` npm dist-tag move is split out of the publish job into a
  separate, `main`-only `promote-tags` job. The defect being repaired is a
  credential mismatch, not a policy one. npm Trusted Publishing (OIDC)
  authorises `npm publish` and nothing else; #2536 put `npm dist-tag add`
  inline in the same job on the untested assumption that it would inherit that
  authority. The 0.1.35-alpha.0 release was its first real execution — all
  five packages published under `alpha`, all five tag moves failed E401, and
  `latest` was left pointing at `0.1.34-alpha.0`. That is precisely the state
  #2536 exists to prevent, reintroduced by the mechanism meant to prevent it.
  Nothing was mis-published: the versions on npm are the versions the release
  cut, and no consumer received a build it was not entitled to.

  **Why a job and not four lines.** A tag mutation needs a long-lived
  registry token, and the only scoping GitHub offers that can withhold a
  secret from a `dev` run is a **GitHub Environment**, which is job-level. It
  cannot be applied to the publish job: that job's Trusted Publisher entries
  are registered with an *empty* environment field, so adding one would break
  publishing outright. Hence the split. `promote-tags` carries
  `environment: npm-production-tags` (deployment branches restricted to
  `main`), `permissions: contents: read` with **no** `id-token: write`, and an
  `if:` on the publish job's output, so it cannot publish, and cannot obtain
  the token on any ref but `main`.

  **The snapshot wall is strengthened, not weakened.** The dev channel's
  guard count goes from four to five: the publish job now only *nominates*
  what it published (`record_latest_promotion()`, which still refuses a
  `0.0.0-dev.*` version), and the job that performs the move is `main`-only
  twice over. The re-run property #2536 established is preserved by
  construction — nomination happens inside the successful-publish branch, so
  re-running an old workflow, where every version already exists and skips,
  nominates nothing and `promote-tags` does not run at all; a stale re-run
  still cannot drag `latest` backwards. #1159's partial-publish rule is
  preserved for the same reason it existed: the nomination list, not the
  publish job's exit code, decides what to promote, so four packages live and
  one failed still moves `latest` onto the four — the list is written before
  every exit in the publish step, and the job carries `!cancelled()` so a
  failed publish does not suppress it. Both halves of that were regressions in
  a first draft of this change, caught by reading the diff rather than by CI,
  and each now has a test.

  **The pre-existing suite was updated rather than narrowed.**
  `scripts/release-bump.test.mjs` proves the #2536 behaviour by executing the
  publish step's own shell against a recording `npm` stub, and the job split
  broke seven of its tests — caught by `haven-reviewer`, not by the author, who
  had run the new suite and the `scripts/ci` glob but not this one. The
  behavioural question it asks ("which `dist-tag add` calls actually happen,
  for which versions") did not disappear when the mutation changed jobs, so the
  harness now runs BOTH steps in sequence, passing the real `GITHUB_OUTPUT`
  nomination list from the first into the second exactly as the runner does,
  rather than being reduced to whichever half still fit. Two tests were added
  in the same place: a missing token must fail by name before touching npm, and
  the five real scoped specs must survive the `name@version` split. That last
  one initially passed on a deliberately broken split — the mutation passes the
  spec verbatim, so a bad split damages the before-value read and the run
  summary rather than the tag move — and was tightened until it failed.

  A regression suite
  (`scripts/ci/publish-tag-promotion.test.mjs`, on the every-PR
  `scripts/ci/*.test.mjs` glob) pins the credential boundary rather than the
  job's existence: the publish job must contain no tag mutation and no
  reference to the token, `promote-tags` must keep its `environment:` and must
  not request `id-token: write`, the snapshot refusal must remain, and the
  scoped `name@version` split is verified by running the real shell rather
  than by reasoning about parameter expansion. Each assertion was
  mutation-checked against a deliberately broken copy of the workflow.

  **One claim in the gravity files was falsified and is corrected here.**
  `README.md` § *Releasing npm packages* and `scripts/README.md` both said the
  release path has "no `NPM_TOKEN` secret" with "nothing to leak or rotate".
  True until this change; false after it. Both now scope that statement to
  PUBLISHING and name the second credential, the job that holds it, why it
  could not be an `environment:` on the publish job, and its expiry. Flagged by
  the ADVISORY half of the coupling gate — the blocking contract-doc check was
  already green — and fixed rather than deferred, because the claim was
  falsified by this diff rather than merely aged. It is a security-posture
  claim: a reader who takes "nothing to rotate" at face value would not know a
  credential now exists to be rotated.

  **A dated obligation this shard records rather than resolves.** The token
  is a granular npm token and npm caps write-enabled granular tokens at 90
  days: it expires **2026-12-06**, and separately, around 2027-01 npm
  restricts bypass-2FA granular tokens from package-management actions, which
  plausibly includes this one. When it lapses, releases publish and `latest`
  silently stops moving — this same defect. The workflow therefore fails with
  the cause named (which token, its 90-day cap, where to update it) instead of
  a bare E401, and the durable answer — stop needing two dist-tags — is filed
  as its own decision rather than assumed here. Perimeter unchanged: nothing
  about who may spend, sign, or execute is touched, and the authority a
  delegation grants remains bounded on-chain by the same caveat enforcers.
