- **#2702** — Four migrations guarded constraint creation with a **schema-blind**
  idempotency check, so two `user_safes` constraints were silently skipped in
  every schema created after another schema claimed their names. The checks are
  now schema-qualified and a forward migration (079) re-adds what was skipped.
  **No perimeter move, no route, no authority change, and nothing production
  executes differently.**

  **The defect.** `IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname =
  '…')` carries no `connamespace` predicate, and `conname` is not unique across
  schemas. Once `public` held a name, every schema migrated afterwards saw it
  and skipped its own copy. Measured before the fix on one developer machine:
  **185 worker schemas held `user_safes`; zero held
  `user_safes_user_id_safe_address_chain_id_key` or
  `user_safes_account_type_check`.** A third constraint on the same table,
  `user_safes_execution_rail_check`, was present in all 185 and byte-identical
  to production's — 041 drops and re-adds it unconditionally, so it was never
  exposed. That asymmetry is the reason the defect survived: it looked like
  ordinary schema variation rather than a systematic skip.

  **Why this is not a production perimeter move.** Production already holds both
  constraints — that is precisely why the blind check kept matching — so both
  branches of 079 are no-ops there, and its `NOT EXISTS` guards are themselves
  schema-qualified so they cannot be satisfied by another schema's copy. Nothing
  in this change touches a route, a policy evaluation, a signing path, a
  credential, or the on-chain envelope. No refusal is removed and none is added
  on the money path.

  **What it does change is the honesty of the test bed**, and that is the
  regulatory-relevant half. Every real-DB test on this machine has been
  certifying behaviour against a `user_safes` that accepts a duplicate
  `(user_id, safe_address, chain_id)` and an out-of-range `account_type` which
  production rejects. The tests were weaker than the schema they claimed to
  exercise, silently, for as long as `public` has held those names. #2702 is
  therefore a **strengthening** of the evidence base for every claim this
  document makes that rests on a repository test.

  **Parent hand-read, not shard-cleared (#2323).** The gate reports a
  shard-satisfied parent as "body NOT re-read", so the sections a migration
  change could plausibly move were opened rather than assumed: the § *What
  `covers:` must span* migration clause at :163 ("since #1139 every migration in
  the mainnet-money table set carries a…"), and the Safe-retirement paragraph as
  corrected by #2669/#2691, since `user_safes` is the account table both
  discuss. Neither needed an edit — 079 adds no column, drops nothing, and
  changes no account's rail, type or ownership. **That is the finding, not an
  omission.**

  **Discovered by the #2622 reservoir guard**, on PR #2694: comparing each
  worker schema against a freshly migrated reference is the first mechanism in
  this repository that has ever asked whether a worker schema actually matches
  migration head, and the first thing it reported was this. The CI job it
  reddened (`Advisory-lock deadlock proof (40P01)`) was correct to fail.

  **Verification.** Four schema-blind checks qualified, zero remaining
  (`grep -c "FROM pg_constraint WHERE conname"` → 0). Full backend suite green:
  244 files, 3160 passed, 2 skipped. A new test asserts the constraints EXIST in
  a freshly migrated worker schema and that the UNIQUE one actually **rejects** a
  duplicate insert (23505) — existence in the catalog and enforcement being
  different claims, and this defect having looked right enough to pass for
  months. Mutation-proven: with 079's `up()` made a no-op against a schema in
  the pre-fix state, three of the four assertions redden while the positive
  control stays green. After one suite run, 64 of the machine's worker schemas
  were repaired — one per real-DB file that ran; the rest heal as they are used.
