**What the tests prove, and what they cannot.** `viewport-fit=cover` is a
compositing instruction to the OS and `env(safe-area-inset-*)` is inert in every
engine without a notch, so the rules read `--v2-safe-*` and the Playwright specs
override those properties to reproduce a notch's arithmetic against the real
stylesheet: `e2e/safe-area-insets.mobile.spec.ts` (390x844, chromium-mobile)
sets all four, and the inset case added to
`e2e/modal-action-row-reachability.spec.ts` sets the vertical pair. Each test
reads the computed padding back before judging any geometry, so a renamed
variable fails the control rather than passing an empty band. Mutation-tested on the
VERTICAL insets: every rule group named in the pull request's results table was
removed one at a time and the spec claiming to cover it went red, each file
restored byte-identically afterwards, with the count and the per-cell results in
that table rather than stated here. The landscape (left/right) components are
deliberately NOT mutation-covered: the vertical spec pins `--v2-safe-left` and
`--v2-safe-right` to 0 and the modal case never sets them, so both are 0 in
every engine that runs them — removing a horizontal rule computes the same 24px
it did before and no assertion could go red. That half rests on the device
checklist with the rest of what no local engine can see — that iOS reports the
insets we assume, and that the status bar tints to `theme-color #4f46e5` — as it
did for #2729. Perimeter unchanged.
