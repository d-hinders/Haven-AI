- **#2842** — a test-only change in the hosted MCP server with no source edit and no perimeter effect: `packages/mcp-server/src/tools-registry-boot.test.ts` moves its two module imports out of the test body and makes them static, so the cost of loading the SDK + server module graph is paid in vitest's collect phase rather than against a per-test timer. **Authority/custody argument: nothing under test changed and nothing in the product changed.** The file asserts one thing — that `buildHostedMcpServer` calls `assertHostedToolRegistry` before registering any tool, so a registry with a handler-less tool cannot boot — and that assertion is byte-identical before and after; the #2807 guard it protects is untouched, as is every handler, schema, refusal, cap check and signing boundary. The change is worth recording here only because of what the defect looked like: the test failed intermittently under a loaded full-suite run (4 red of 11 runs on clean `dev`) and the failure surfaced as the registry guard "not throwing", which reads like the completeness check regressing on a money-path package rather than like a timer expiring. A guard that reports a false regression is a guard that gets muted. **What is mutation-tested:** leaving the mocked handler map COMPLETE (not deleting `haven_pay`) turns it red, so the assertion is still live after the restructure; commenting out `assertHostedToolRegistry(handlers)` at its call site in `server.ts` turns it red, so the wiring this file exists to prove is still proven; and pointing the import at a missing module fails the FILE and exits 1 — verified on the exit code rather than on the reporter, which does not name the test at all in that case but drops it from the count (`471 passed`, no failure line for it). That reporting shape is the one thing this change makes worse and it is recorded in the file: CI is still red, but the trail is shorter than a named assertion. **What was measured rather than argued:** importing `server.js` costs ~1.0–1.1s on an idle machine and 5–10s inside a loaded full suite, and is 99.4% of the original test's duration, while the `vi.mock` factory adds no material share (paired idle runs: 1057/1048/1131ms unmocked against 1066/1066/1295ms mocked) — so the first explanation shipped for this, blaming the mock factory, was wrong and is corrected in the file. An intermediate fix that hoisted the imports into `beforeAll` was rejected on measurement rather than taste, and on DURATIONS rather than a pass/fail count, because at this load the count is a draw: in paired full-suite runs under 28 spinning background processes the hook form took 8722ms and 9796ms — 87% and 98% of the 10000ms hook budget — against 22ms and 96ms for the static form, with the original form at 7521ms and 5195ms against its 5000ms test budget. An independent second measurement on another machine got 7584/8991/8009ms hook against 16/149/207ms static and saw no red in three runs, where a run here did go red with `Hook timed out in 10000ms`; that disagreement is the argument, not against it, since at 98% of budget whether it fails is a coin flip. The hook form trades the 5s test budget for the 10s hook budget instead of removing the exposure. Perimeter unchanged.
