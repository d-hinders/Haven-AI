- **#2860** — the accounting feed's provider secrets move to a provider-generic table and are encrypted at rest; the epic's one migration (#2858, slice 2). `fortnox_connections` (one Fortnox-shaped row per user, OAuth tokens in plaintext columns) is replaced by `accounting_connections` (one row per user and provider, secrets as an AES-256-GCM blob with a per-row key version, exactly one row per user flagged as the active feed destination by a partial unique index). **Authority/custody argument: nothing about payment authority changes.** The feed reads settled payments and delivers them to the user's own accounting platform under the user's own OAuth grant; the secrets in question are the USER's credential to THEIR accounting software, never a Haven signing key, never a delegate key, and never anything that can move funds — the keyless custody boundary is untouched. What this slice changes is the exposure of that credential at rest: today it is plaintext in a database column, after this it is a ciphertext that only `infra/secrets.ts` can open, with the key held in the environment and never in the database. **The migration is schema-only and reads no environment**, on the review finding that `runMigrations()` runs at boot on every replica including production and that CI applies every migration with only `DATABASE_URL` set: rows are copied AS-IS at key version 0, the old table is renamed to `fortnox_connections_retired` rather than dropped (a rolling deploy's overlapping old replica cannot lose a committed write, and a deploy-level rollback fails loudly on a missing table name rather than silently reading an empty one), and encryption happens at the application layer on the first boot that has `HAVEN_SECRETS_KEY` — inert without it, idempotent with it, per-row on failure, never blocking `listen()`. New connection writes fail closed without a key so a fresh grant cannot land in plaintext; reads of a version-0 row need no key so "no key yet" cannot become "the feed is down". Production and CI hold zero rows, so nothing there fails and nothing is left unprotected; dev's rows stay exactly as exposed as they are today until the operator sets the key, then encrypt at the next boot — with one operator ordering that the first draft of this record did not state: without a key a token REFRESH is refused before the provider is called, so the stored single-use refresh token is never consumed and the connection survives, but the feed stops for that user until the key lands; Fortnox access tokens live one hour, so the dev key should be set before or promptly after this deploys. The same migration lands the two names slice 1 deferred — `reporting_feed_syncs` → `accounting_feed_syncs`, `reporting_feed` → `accounting_feed` in `account_entitlements` — with the repository SQL and the entitlement constant flipped in the same deploy so dev availability has no gap. Disconnect now keeps the row and clears the secrets (owner decision: history stays), and a reconnect preserves `settings` and `feed_from` and reclaims the active flag if no other provider holds it — a first draft preserved the flag unconditionally, which after a disconnect left a connected row that fed nowhere; reproduced in review and now pinned by a real-DB test. **Three review findings, each with a test that fails on the code it replaced:** the key check ran AFTER the Fortnox refresh call, so a replica without a key would have burned the single-use refresh token and then thrown — bricking the connection; the boot re-encrypt job's write had no version guard and could overwrite a token a serving replica rotated between the job's read and its write (reproduced with an interposing executor); and the reconnect-after-disconnect flag defect above. **What is mutation-tested:** on the crypto helper — removing the fail-closed check (encrypt with a zero key when none is set), deriving the IV from a constant instead of drawing it, and dropping the GCM auth-tag check on decrypt each redden their own assertion; on the migration, on the real database with no environment set — dropping the entitlement rewrite and writing an empty secrets blob each redden the copy test, while removing the one-active-destination index or replacing the rename with a DROP is refused by the db-harness's own head-shape check before any test runs (exit 1; the assertions for those two properties are structurally falsifiable but were reached by the harness, not by the mutation). A first draft's single-statement active-destination switch tripped the partial unique index on the real database — Postgres checks a unique INDEX per row and a partial index cannot be deferrable — and was replaced by clear-then-set inside a transaction, where the intermediate zero-active state is one the index permits. The Fortnox lifecycle's refresh-and-persist and fail-closed paths moved off positional `db.js` mocks onto the real harness, where an encrypted UPDATE and an untouched-row refusal can actually be shown. Full backend suite green (3224); every ratchet and doc gate green. Perimeter unchanged — narrowed, if anything: a credential that was readable from a database dump no longer is.
