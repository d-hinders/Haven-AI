- **#2863** — Fortnox token lifecycle hardened for production shape (epic #2858, slice 5): the refresh runs under a per-connection lock, the rotated refresh token is persisted before the new access token is used, a refused refresh flips the connection to `needs_reauthorisation` and is never retried, and disconnect revokes the grant at Fortnox before the stored secrets are cleared. All of it lands in the generic OAuth2 flow (`modules/accounting/oauth-flow.ts`), so every `oauth2` provider inherits it; Fortnox is the concrete case (`fortnox.ts` gains the RFC 7009 `revokeUrl`, `registry.ts` flips `capabilities.revoke` to `true`, `fortnox-connector.ts` implements `revoke` as `POST /oauth-v1/revoke` with `token_type_hint=refresh_token` under Basic client auth). **Authority/custody argument: nothing moves.** The secrets involved are the user's OAuth grant to their own accounting ledger — never a Haven key, never a delegate key, never anything that can move funds — and this slice only changes HOW that grant is refreshed, refused and revoked. No migration: `needs_reauthorisation` is already among migration 080's `accounting_connections_status_check` values (`connected`, `needs_reauthorisation`, `revoked_at_provider`, `scope_missing`, `disconnected`). The perimeter files in the diff — `fortnox.ts`, `fortnox-connection.ts` (unchanged), `infra/repositories/accounting-connections.ts` — construct no transaction, sign nothing, touch no delegation, allowance, relayer or signer, and add no write path to any money table; the one repository addition is `LOCK_ACCOUNTING_CONNECTION_SQL` (`SELECT … FOR UPDATE` on the connection row) behind `withLockedConnection`, registered in the schema smoke; #2860's CAS re-encrypt, clear-then-set and disconnect-keeps-the-row are byte-identical. **Three narrowings, one closed race.** (1) The row lock: two workers refreshing the same single-use token — the settlement hook racing a "Sync now" click — used to burn each other's rotation and lock the connection out; now the second waits, re-reads the row the first already rotated, and uses that token with no provider call, and the rotated pair is committed with the lock BEFORE the access token is returned to either caller (the `secretsKeyConfigured()` check still runs before the single-use token is consumed, as #2887 established). (2) A token-endpoint refusal that is a verdict on the grant — `invalid_grant`, or a 400/403 with no readable code; never `invalid_client`/`invalid_request`/`unauthorized_client`/`unsupported_grant_type`/`invalid_scope` (Haven's client credentials, RFC 6749 §5.2 — a rotated client secret must not flip every user; tightened after the independent review of PR #2895), never 401/408/429 (429 is Fortnox's rate limit, 25 calls / 5 s with no `Retry-After`) or 5xx, all of which leave the row and the refresh token untouched — flips the row to `needs_reauthorisation` with `status_reason = refresh refused: … invalid_grant` (the RFC 6749 `error` code only, validated against `^[a-z_]{1,64}$`; never a token, never the description), the flow throws `ConnectionNeedsReauthorisationError` on every later call without touching the provider, and the orchestrator records each sync as `skipped` with `connection needs_reauthorisation: …` — re-claimable (#1365) once the user re-consents. `scope_missing` keeps #2862's shape (no destination, no rows). (3) Disconnect posts the refresh token to Fortnox's revoke endpoint with the secrets still in hand and clears them whether or not the call succeeded — a Fortnox outage cannot keep a grant the user asked to drop stored here; the failure is reported by error name only. **What is mutation-tested**, each restored from a `cp` backup and verified by `cmp`, every count from one named scope at the delivered tree — `npx vitest run --root packages/backend src/modules/accounting src/routes/__tests__/accounting-connections.test.ts`, 20 files / 174 tests green (the new real-database suite is `__tests__/fortnox-token-lifecycle.db.test.ts`, 5 tests; the `fetch` seam counts provider calls): dropping `FOR UPDATE` from the lock statement — **1 failed / 173 passed** (the two-concurrent-callers test: "expected 2 to be 1" refresh calls); dropping the grant-verdict → `needs_reauthorisation` flip — **1 failed / 174 passed** (the `invalid_grant` test: the second call refreshed again); widening the verdict back to every 4xx — **1 failed / 174 passed** (the `invalid_client` test: the row flipped); skipping the `revoke` call in `disconnectProvider` — **6 failed / 168 passed** (both conformance runners' case 5, both route disconnect tests, both real-database disconnect tests); disabling the degraded-destination branch in the orchestrator — **1 failed / 4 passed** of the new suite (no `skipped` row was written). Perimeter unchanged — narrowed, if anything: a grant Haven drops is now also revoked at the provider, and a dead grant is refused before any provider call instead of retried on every sync.
