- **#2866** — Background retry sweep for the accounting feed, with backoff and rate-limit awareness (epic #2858, slice 8): a new in-process interval (`modules/accounting/retry-sweep.ts`, `startRetrySweep` registered in `src/index.ts` after the sibling monitors, `unref()`ed, leader-locked on the new key `LEADER_LOCK_KEYS.accountingRetrySweep = 811010`, cadence `HAVEN_ACCOUNTING_RETRY_SWEEP_INTERVAL_MS` default 5 min) selects the `failed` / `skipped` / stale-`pending` sync rows whose connection is `connected` and the active destination and whose backoff has elapsed, and re-feeds each through the SAME `feedSettledPayment` the settlement hook uses. **Authority/custody argument: nothing moves.** The sweep re-runs an idempotent, best-effort feed over payments that are ALREADY settled on-chain; it constructs no transaction, signs nothing, touches no delegation, allowance, relayer or signer, and reaches the provider only through the existing connector with the user's own OAuth grant to their own ledger. No migration: backoff is DERIVED from the columns `attempts` and `updated_at` that the ledger already has (`backoff(n) = min(1 min · 2^(n−1), 1 h)`, computed inside `LIST_DUE_RETRY_SYNCS_SQL`), the attempt cap (8) is a parameter of the same statement, and a row that reaches it stays `failed` with its reason prefixed `exhausted:` — the string the dashboard keys on; a manual "Sync now" still re-claims it, the cap bounds the sweep and not the human. The repository additions in the perimeter file `infra/repositories/accounting-feed-syncs.ts` — `LIST_DUE_RETRY_SYNCS_SQL`, `RELEASE_STALE_PENDING_SQL` (flips a `pending` row older than 15 min to `failed` WITHOUT touching `attempts`, guarded on it still being pending and still stale, so the live claim guard #497 relies on is intact), `COUNT_SYNCS_FOR_USER_SQL` (the `counts` on `GET /accounting/feed/status`) — are all registered in the schema smoke; `claimSync`, `markPushed` and the pushed-is-final rule are byte-identical, and `feedSettledPayment` gains only a return value (`FeedOutcome`, so the sweep can tell a provider 429 from any other failure) with its control flow unchanged. **Three narrowings.** (1) Rows `skipped` for a state reason are retried only once the cause is gone: the selection JOINs `accounting_connections` and requires `status = 'connected' AND is_active_destination`, so a `needs_reauthorisation` (#2863) or `scope_missing` connection holds its rows until the user re-consents — nothing is ever pushed against a dead grant by the sweep; FX-not-ready rows are selected but the orchestrator's FX gate no-ops before any claim, consuming no attempt. (2) The provider is paced under Fortnox's documented 25 requests / 5 s per client-id + tenant as a FIXED floor (`RequestPacer`, 8 requests budgeted per push, one connection at a time, groups walked serially), and a 429 — which Fortnox sends without `Retry-After` — defers the whole connection to the next tick with every remaining row left untouched (no claim, no `attempts + 1`); a `Retry-After` is honoured as an in-process courtesy when present, never depended on. (3) The sweep is inert with `HAVEN_ACCOUNTING_ENABLED` off — `startRetrySweep` registers nothing and `runRetrySweep` returns before its first query — and an overlapping tick on one replica is skipped in-process. **What is mutation-tested**, each planted alone, restored from a `cp` backup and verified by `cmp`, counts from the named scope at the delivered tree (`npx vitest run --root packages/backend src/modules/accounting/__tests__/retry-sweep.test.ts src/modules/accounting/__tests__/retry-sweep.db.test.ts src/infra/repositories/__tests__/accounting-feed-syncs.test.ts`, 38 tests green): zeroing the backoff in `LIST_DUE_RETRY_SYNCS_SQL` (`$3 * 0`, so every failed/skipped row is due at once; the parameters stay typed — a first attempt that deleted the clause made Postgres refuse `$3`'s type and failed 13 tests for the wrong reason, discarded) — **3 failed / 35 passed** (the repository "not before" and "curve" tests, the real-database sweep "not before" test); lifting the attempt cap (`s.attempts < $2 + 1000000`) — **2 failed / 36 passed** (the repository cap test and the real-database "at the cap is not retried" test); feeding the remaining rows after a 429 instead of breaking (their attempts then increment) — **3 failed / 35 passed** (the 429 test in both sweep suites and the Retry-After courtesy test); dropping `c.status = 'connected'` from the query — **2 failed / 36 passed** (the `needs_reauthorisation` test in both the repository and the real-database sweep suite); 38/38 after each restore. Perimeter unchanged — narrowed, if anything: the one new automated path to the provider runs only against a `connected` active destination, under a fixed request floor, over rows whose payment has already settled.
