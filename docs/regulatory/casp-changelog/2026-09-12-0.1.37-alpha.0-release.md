- **0.1.37-alpha.0 release** — **three issues reach npm (#2850, #2710, #2809);
  no custody, signing or execution boundary moves, and the one behavioural
  change in a published package REMOVES a signing path rather than adding
  one.** Cut against `origin/main` (`86de3224`) at this branch's head; the
  promotion range is 101 commits, of which the overwhelming majority are
  backend, frontend, docs and CI and reach no tarball.

  **The shipped delta is measured, not counted: 8 files, +31/-15.** Read out of
  `dist/` by `npm run release:scope` after a full build, which resolves each
  source file through the bundle sourcemaps and the `files` field rather than
  trusting a `--stat`. **The head is the script's default, `origin/dev`
  (`5a6f40dd`)**, which is the right one to record because it isolates the
  shipped delta from the 33/33 the bump itself wrote; the same script at this
  branch's head reads 17 files / +47/-31, the difference being exactly the nine
  bump-written version-literal files. It excluded 730 files — 718 outside a published package,
  11 test files unreachable from any bundle entry, 1 inside a package but
  outside the tarball. **This figure must be re-measured at the promotion door**
  if anything lands on `dev` behind this branch; the tarballs are built from
  `main`'s tree at promotion time, so a record written now is wrong by
  construction the moment `dev` moves. That is the standing lesson of the
  0.1.36-alpha.0 shard, which was amended three times.

  Four of the five packages carry a source change: `@haven_ai/sdk`,
  `@haven_ai/cli`, `@haven_ai/mcp`, `@haven_ai/signer`. **`@haven_ai/connect`
  carries version literals only** — `git diff origin/main..origin/dev --
  packages/connect/src` is empty.

  **#2850 — the SDK refuses an absent `signature_scheme` instead of signing a
  bare hash.** This is the one executable change in the published surface and
  the only one worth a perimeter argument. `packages/sdk/src/client.ts`
  previously fell through to `signHash(this.delegateKey, signData.hash)` when
  `signature_scheme` was absent — the legacy AllowanceModule rail's shape. That
  rail is retired (closed to new accounts #1984, unable to spend #1986, whole-rail
  retirement 2026-08-14 / #1440) and the backend spec makes the field required,
  so the branch now throws `HavenSigningError` naming the reason. `types.ts`
  carries the matching doc correction: the "absent = raw ECDSA over `hash`"
  reading is retired.

  **One schemeless emitter still exists in the backend, and saying so is more
  useful than the absolute an earlier draft wrote here.** That draft read "every
  live `sign_data` emitter sets it"; independent review found it false.
  `packages/backend/src/routes/payments.ts:257-273` — the else-branch of
  `replayIntentBody` — emits the legacy shape with **no `signature_scheme`**,
  and its own `instructions` string still names the raw-ECDSA behaviour #2850
  removed. It is a **replay** path: it returns a previously prepared intent, it
  never prepares a new one.

  Reachability, traced rather than waved off. The `retired_allowance` /
  `retired_session` 410 gates (`payments.ts:338-345`) fire **before**
  `findPaymentReplay`, which is the strongest fence — but they key off the
  *account's current* rail via `loadExecutionRailState(agent)`, while the replay
  row carries its *own historical* `execution_rail`, and
  `FIND_SEND_INTENT_BY_KEY_SQL`
  (`packages/backend/src/infra/repositories/payment-intents.ts:364-371`) does
  not filter on it. What closes the gap in practice is lazy expiry
  (`payments.ts:204-209`) combined with the legacy rail having closed a month
  ago: intents expire in minutes, so no such row survives to be replayed.

  **The worst case is therefore an SDK client throwing on a dead replay, not a
  signature on a guessed scheme** — which is the outcome #2850 wants. This
  reachability argument is a **static trace, not an executed test**: the backend
  real-DB suite could not run in the authoring environment (no Postgres), and
  CI's `allowance-rail-retired.test.ts` covers the gate but not the
  historical-rail replay row. Named here rather than left implied.

  **The direction of this change is the security argument.** It removes the
  ability of a malformed or truncated payload to obtain a raw ECDSA signature
  over an attacker-influenced 32 bytes from the delegate key, on a guessed
  scheme. Nothing gains a signing path; one is deleted. `signHash` itself stays
  live and exported — the EIP-3009 bridge leg still uses it — so this is a
  narrowing of *when the client will sign unprompted*, not a removal of a
  primitive.

  **Compatibility, tested rather than asserted.** `npm pack
  @haven_ai/<pkg>@0.1.36-alpha.0` for all five, extracted, and each
  `dist/index.d.ts` diffed against this branch's build: **zero declarations
  added or removed in any of the five** (sdk 111 → 111, mcp 17 → 17, signer
  31 → 31, connect 38 + cli.d.ts 3 → same, cli 8 → 8). The only non-comment
  type-surface differences are the version literals the bump wrote
  (`MCP_VERSION`, `SIGNER_VERSION`, `CONNECTOR_VERSION`, and connect's
  `sdkVersion`/`mcpVersion`/`signerVersion`) plus the runbook string constant
  below. **A consumer pinned to the published `.d.ts` compiles unchanged**; the
  #2850 break is a runtime refusal on a payload shape the backend no longer
  emits, not a type break.

  **#2710 — the funding step routes chain identity through the discovery
  manifest.** One line of `HAVEN_AGENT_RUNBOOK_MD`, net, in both copies
  (`packages/sdk/src/agent-guidance.ts` and the CLI's vendored
  `packages/cli/src/agent-guidance-text.ts`, kept in parity by
  `agent-guidance-text.test.ts`). Step 2 now tells an agent to read
  `/.well-known/haven.json` — `chains.default` for the expected chain,
  `environment` for whether the deployment is `production`, and each
  `chains.supported` entry's `testnet` flag — and to tell its user which case
  theirs is before they send funds, rather than confirming the chain from
  `haven wallets funding` alone. **Read-only metadata on a public manifest; it
  changes what an agent is told to check, never what it may do.** Its own
  perimeter analysis is `2026-09-08-2710.md` and is not restated here (#1503
  precedent: a release shard may decline to re-verify the shards of the work it
  carries).

  The same issue carries the CLI's `login --json` payload gaining `interval`,
  documented in `packages/cli/README.md` (+3/-3) with the instruction to wait
  that many seconds before the first `--poll` round. A poll-rate hint on a
  device-code flow whose approval is a human browser action; it acquires the
  `owner_cli` scoped session analysed under #2526 and changes nothing about its
  route allow-list.

  **#2809 — comment and path corrections only.** The hosted MCP server's
  handlers were extracted out of `packages/mcp-server/src/tools.ts` into
  `tools/support/quote-response.ts`, `tools/support/mcp-context.ts` and
  `tools/state-direct-recovery.ts`. Three published files carried cross-file
  references naming the old path — `packages/mcp/src/tools.ts`,
  `packages/sdk/src/client.ts`, `packages/signer/src/core.ts` — and now name the
  new one. **Not one executable line among them**, verified against the net
  diff. `mcp-server` is `private: true` and reaches no tarball; only the
  pointers to it shipped.

  `packages/cli/src/commands.ts` carries the release's other two shipped
  changes, net +2/-1, and **one of them is executable, not copy**: `interval:
  start.interval` (`:277`) adds the new field to the `login --json` payload
  (#2710), and the `delegate_sweep` activity label reads `sweep` rather than
  `allowance funding` (#2850). The label change is **not** the last
  AllowanceModule vocabulary in the CLI's output, as an earlier draft claimed —
  `commands.ts:960` still prints "To also remove its on-chain allowance, use the
  dashboard" on every agent revoke. Left as found; this release does not touch
  it. (`budget show --json`'s `allowances` / `allowance_amount` keys are the
  derived-VIEW name the architecture sanctions, and are not counted here.)

  **The registered tool surface did not move: 15 names on `origin/main`, the
  same 15 on `origin/dev`.** The instrument matters here, because an earlier
  draft recorded a "sorted `name:` extraction over `packages/mcp/src/tools.ts`"
  and review showed that probe returns **zero names on both refs** — the schemas
  are keys of the `toolSchemas` object, not `name:` fields, so its "empty diff"
  was vacuously true. Re-measured over `Object.keys(toolSchemas)`
  (`registeredToolNames()`, `packages/mcp/src/consent.ts:331-333`) the sets are
  identical: `haven_discover_tools`, `haven_get_agent`, `haven_get_allowances`,
  `haven_get_payment_status`, `haven_get_resume_state`, `haven_list_receipts`,
  `haven_pay_mcp_tool`, `haven_pay_x402`, `haven_pay_x402_quote`,
  `haven_quote_x402`, `haven_resume_x402_payment`, `haven_send`,
  `haven_submit_catalog_entry`, `haven_sweep_delegate`, `haven_verify_receipt`.
  The conclusion held either way; the evidence for it did not, and the
  "no operator is re-prompted" argument below depends on this one. `packages/connect/src` is
  unchanged apart from bump-written version literals, so the capability
  manifest, `installed-clients` and the connector's runtime detection are
  untouched.

  **Therefore no operator is re-prompted on upgrade.** `packages/connect/src/consent.ts`
  is **byte-identical** to `origin/main` — asserted with `git diff --quiet`, not
  by reading it. Its hash covers identity (api-key prefix, api URL, agent id,
  safe address, delegate address, chain id), the canonical tool set and the
  canonical allowance set; no version constant feeds it, and none of the three
  components moved.

  **`@haven_ai/core` is irrelevant here by construction, not by luck.** No
  published package depends on it: `sdk` and `cli` declare no `@haven_ai/*`
  dependency at all; `mcp` and `signer` depend only on `@haven_ai/sdk`;
  `connect` on the sdk plus `mcp` and `signer`. There is no shared-kernel path
  into a tarball.

  **The SDK exposure, traced.** All four runtime packages take `@haven_ai/sdk`
  as a runtime dependency and it did change, so the exposure is traced rather
  than waved off. The two changed exported constants are `HAVEN_AGENT_RUNBOOK_MD`
  (#2710, one line) and the `signData` refusal inside the client's signing path
  (#2850). The refusal is reachable by a consumer that drives the SDK client;
  the runbook constant has no importer in `packages/{mcp,signer,connect,mcp-server}/src`.
  `STRICT_INPUT_TOOLS` and the signer's #1143 signing-time guard are
  **unchanged in content**; `STRICT_INPUT_TOOLS` did *move file* in the same
  #2809 refactor described above (`mcp-server/src/tools.ts` →
  `mcp-server/src/tools/contracts.ts:574`), which reaches no tarball because
  `mcp-server` is `private: true`. In `packages/signer/src`, `core.ts` changed
  by three inserted and one deleted line, all comment; `server.ts` changed by
  the `SIGNER_VERSION` literal, accounted for above as bump-written.

  **Release mechanics:** versions, cross-package pins, source version constants
  and the Supported Runtime Manifest table were rewritten atomically by
  `release-bump.mjs`. Its script-owned diff is **33 insertions / 33 deletions
  across 14 files**, version lines only (11 lockfile + 11 `package.json` +
  7 source constants + 4 manifest-table rows). `HAVEN_CONNECTOR_CHANNEL` is
  untouched: `alpha` → `alpha`. The manifest table's `last-verified` moved
  2026-09-11 → 2026-09-12 by hand; its four version rows were not hand-edited.

  **Tested, and the gaps named.** Recorded in the release PR against this
  branch's head. Any suite that could not reach a real Postgres in the authoring
  environment is named there as an environment limit, not reported as a pass;
  CI covers those.

  **Promotion caution carried forward from #2660 and #2647.** The `latest` move
  is its own `main`-only `promote-tags` job, so a half-green promotion is live:
  every package published under `alpha`, `latest` unmoved. `latest` currently
  reads `0.1.36-alpha.0` on all five. Verify with the registry
  (`curl https://registry.npmjs.org/-/package/@haven_ai/<pkg>/dist-tags`, or
  `npm view … --prefer-online`), never with a green workflow, and poll for
  several minutes before concluding a tag is stranded — the registry lagged a
  successful publish by ~4.5 minutes on 0.1.36-alpha.0.

  Perimeter unchanged — this release deletes one permissive signing fallback,
  tells an agent to read a public manifest before naming a chain to its user,
  adds a poll-interval hint to a human-approved device-code flow, and corrects
  three file-path comments. Nothing about who may spend, sign, or execute. The
  spend authority a delegation grants remains bounded on-chain by the same
  audited caveat enforcers, and the refusal added here can only reduce what the
  delegate key will sign.
