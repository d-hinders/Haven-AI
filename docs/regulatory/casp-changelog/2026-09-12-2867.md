- **#2867** — Backfill choice and per-connection settings for the accounting feed (epic #2858, slice 9, backend only): two new session-authenticated routes appended to `routes/accounting-connections.ts` — `POST /accounting/connections/:provider/backfill { since }` and `PATCH /accounting/connections/:provider/settings { suggested_account?, auto_feed? }` — plus two additive statements in the perimeter file `infra/repositories/accounting-connections.ts` (`RECORD_BACKFILL_SQL`, `MERGE_CONNECTION_SETTINGS_SQL`, both registered in the schema smoke) and one predicate added to `LIST_DUE_RETRY_SYNCS_SQL` in `accounting-feed-syncs.ts`. No migration: `feed_from` and `settings JSONB` exist since 080 (#2860). **Authority/custody argument: nothing moves.** Both routes act on metadata of the user's OWN accounting connection — a timestamp floor and two JSON keys — and reach the provider only through the existing `syncUser` over payments that are ALREADY settled on-chain; no transaction is constructed, nothing is signed, no delegation, allowance, relayer or signer is touched, and the secrets column is not read or written by either statement. **The feed-from rule is preserved and made one-directional.** Every connection still gets `feed_from = now` at connect/activate (#2862) and at a company switch (#2864); the backfill is the ONE path that moves it EARLIER, and the "earlier only" check is the WHERE clause of the UPDATE itself (`feed_from IS NOT NULL AND feed_from > $3`), so a later date, an equal date or a NULL floor updates zero rows and the route answers 400 `SINCE_NOT_EARLIER` with the floor untouched and no sync run; `since` is additionally bounded to the past and to 2020-01-01 or later, and only the active `connected` destination can be backfilled. The sync it triggers is the existing bounded, resumable one (200 payments, claim ledger). **The non-asserting principle is untouched.** `suggested_account` is stored as a hint and reaches the Fortnox payload only through the SAME `FeedTransaction.suggestedAccount` field the legacy per-merchant override has used since #496, surfaced as `YourReference: "suggested account NNNN"`; `assertNonAsserting()` still bans `Account`, `VAT`, `VATType`, `SupplierInvoiceRows` and `VoucherRows`, and the connector test now asserts the `Account` case by name. Validation is by provider: Fortnox takes a four-digit BAS account (`^[1-8]\d{3}$`), other providers 1–32 characters. **One narrowing.** `auto_feed = false` makes the settlement hook a no-op for that user (an early return in `feedSettledPayment` BEFORE the entry is built and before any claim row) and removes the connection from the retry sweep's selection (the new predicate `COALESCE((c.settings ->> 'auto_feed')::boolean, true)`), so the two automatic paths to the provider are closed for that user while the two manual ones — `POST /accounting/feed/sync` and the backfill, which call `syncUser` with `manual: true` — still push; the settings write is a SQL-side JSONB merge, never read-modify-write, so the #2864 `companySwitches` log is preserved by construction. Supplier strategy stays fixed at one supplier per merchant (owner decision; no setting). Connect-time `since` (carrying the choice through the OAuth `state`) is deferred: the connect-url and callback handlers are #2865's concurrent surface, and connect-then-backfill is the same two writes in the same order. **What is mutation-tested**, each planted alone, restored from a `cp` backup and verified by `cmp`, counts from the named scope at the delivered tree (`npx vitest run --root packages/backend src/modules/accounting/__tests__/backfill-and-settings.db.test.ts src/routes/__tests__/accounting-connections.test.ts src/modules/accounting/__tests__/fortnox-connector.test.ts`, 80 tests green): (a) allowing a `since` later than `feed_from` (`feed_from > $3` → `TRUE` in `RECORD_BACKFILL_SQL`) — **2 failed / 78 passed** (the real-database "a LATER since is refused" and "NO floor" tests); (b) dropping the `auto_feed` early return in `feedSettledPayment` — **1 failed / 79 passed** (the real-database "the settlement hook is a no-op" test); (c) accepting a three-digit account (`^[1-8]\d{2,3}$`) — **1 failed / 79 passed** (the route test "a non-BAS account is refused"); (d) carrying the hint as `Account` in the Fortnox payload — **1 failed / 79 passed** (the connector test "surfaces the suggested account as a HINT, never as an account field"); and, beyond the four the issue asked for, (e) dropping the `auto_feed` predicate from `LIST_DUE_RETRY_SYNCS_SQL` (`→ TRUE`) — **1 failed / 79 passed** (the real-database "the retry sweep does not enumerate" test); 80/80 after each restore. Perimeter unchanged — narrowed, if anything: the one new write to the floor can only widen the window the user explicitly asked for, and the one new setting can only close automatic paths.
