- **#2877** — Multi-currency ledgers for the accounting feed (epic #2858): the reporting feed pushes the currency the connected company books in, converted with the rate frozen at settlement, instead of pushing SEK to every destination. **No production connection is non-SEK today** — the only `live` provider is Fortnox and its `getCompanyInfo` reports `SEK` by construction — so this ships the capability ahead of its first user (the `coming_soon` providers), and the non-SEK path is exercised by the conformance suite and the real-database tests rather than by traffic. One additive migration (`082_evidence_ledger_fx_rates.ts`: `machine_payment_evidence.fx_rates JSONB`, nullable, no backfill and no row rewritten), one new pure domain file (`domain/ledger-currency.ts` — `SUPPORTED_LEDGER_CURRENCIES = SEK, EUR, USD, DKK, NOK, GBP`, read by both `infra/prices.ts` and `modules/accounting/provider.ts` so "accepted at connect" and "a rate the feed can be quoted" are one list), a capture widened in place (`infra/fiat-values.ts` `getBookTimeCapture` — ONE `getTokenPrice` read yielding the SEK value and every ledger rate, so the timestamp and the map cannot come from different fetches across the 60 s price cache), and the currency carried through `entry.ts` → `feed-transaction.ts` → `feed-orchestrator.ts` to the connector as `ledgerCurrency` / `amountLedger`. **Authority/custody argument: nothing moves.** Every file in the diff is downstream of settlement — the payment is already confirmed on-chain before any of this code runs. No transaction is constructed, nothing is signed, and no delegation, allowance, enforcer, relayer, signer or secrets column is read or written; `amount_raw`, `amount_human` and every spend-authority path are never WRITTEN by this change (`amount_human` is newly *read*, as the multiplicand for a non-SEK ledger amount), and the one schema change adds a nullable column to an evidence table that no payment path reads to decide whether a payment may proceed. The perimeter files present (`modules/accounting/**`, `infra/repositories/machine-payments.ts`, `db/migrations/`, `infra/chain`-adjacent none) carry reporting data only. **Red Line #9 (reporting/accounting/tax assertions) is unchanged, and no new assertion is introduced.** The record pushed is still an *unattested* supplier invoice: `assertNonAsserting()` still bans `Account`, `VAT`, `VATType`, `SupplierInvoiceRows` and `VoucherRows`, and this change adds only `Currency` and a `Total` in that currency — the two fields that say what the figure on the source document *is*, which is factual provenance and not an accounting judgment. Nothing is booked until a human attests it. An FX rate is recorded, never asserted: it carries `fx_source` and `fx_at` exactly as the SEK capture has since migration 026, and **a USD-denominated ledger records the rate the source quoted for a USDC payment (≈ 1.0) rather than an assumed 1:1 parity** — Haven states no equivalence between a stablecoin and the currency it is named after, and the accountant confirms that figure like any other on the document. **Three narrowings, no widenings of what Haven may do:** (1) the SEK path is answered from the `amount_sek` COLUMN, never re-derived from the new map, so no existing Swedish ledger can be re-priced by this change; (2) **the whole book-time capture now freezes as one record** — `amount_sek`, `fx_rate_sek`, `fx_source`, `fx_rates` and `fx_at` are written only by the write that finds the row holding no capture at all (rather than keying on `fx_at` alone, which would rest on a caller invariant the repository's own freeze test does not honour), replacing the per-column `COALESCE` these columns have used since migration 026. Two review rounds drove this. Per-column `COALESCE` was equivalent while the capture was all-or-nothing (`getBookTimeSekValue` returned a value or null, so `fx_at` was non-NULL exactly when `amount_sek` was); `getBookTimeCapture` can succeed for the rate map and fail for SEK, because the price source quotes per currency, and `recordMachinePaymentEvidenceBase` re-runs from the proof-attach path weeks later and re-reads prices. Under `COALESCE` that write would have filled the missing half — a NULL map on a pre-082 row, or a NULL `amount_sek` on a partial capture — with a rate taken on the day of the attach while `fx_at` still said settlement: a feed-time rate wearing a book-time label, and in the SEK case on the very path this change claims is untouched. Both holes were found by the independent review pass before merge, the second one in the fix for the first. The accepted consequence, stated rather than hidden: a row that captured anything keeps exactly what it captured and never gains the missing half, so a ledger in the missing currency reads it as not-ready **permanently** — its book-time rate is not knowable after the fact. A capture that failed outright (`fx_at` NULL) is unaffected and still genuinely backfillable; SEK ledgers are unaffected, reading the `amount_sek` column as always. Found by the independent review pass on this change, before merge, and pinned by a real-database test; (3) a missing rate for the destination's currency is *not ready* — the payment is left unfed and unclaimed for the retry sweep and the backfill — never a SEK substitute pushed into a non-SEK ledger, which would be a wrong number wearing the right label. A computed amount is emitted at `amount_sek`'s own scale (four decimals, migration 026), so no raw-float tail or exponent notation can reach a supplier invoice, and the underlag PDF attached to a record states that record's own figure and currency with the SEK capture kept below it as a labelled reference. The connect-time refusal (#2864) is widened from SEK-only to the six supported currencies but is otherwise identical in mechanism and still refuses before any secret is stored (409 `UNSUPPORTED_BASE_CURRENCY` / `reason=unsupported_currency`, existing row untouched, the already-exchanged grant revoked best-effort where the descriptor declares `revoke`). **What is mutation-tested**, each planted alone, restored from a `cp` backup and verified by `cmp`, every count re-derived at the delivered tree `202639a313d88a83d0ab8a6522d3dfecec4259c5` from one named scope — `npx vitest run --root packages/backend src/modules/accounting src/modules/mpp/__tests__/evidence.test.ts src/infra/__tests__/fiat-values.test.ts src/infra/__tests__/prices.test.ts src/infra/repositories/__tests__/machine-payments.test.ts src/routes/__tests__/accounting-connections.test.ts` — **30 files / 319 tests green** at baseline and **319 green again after the last restore**, with the whole table re-run on an otherwise idle database after a first attempt was contaminated by a concurrent run against the same Postgres (the tests shard by vitest worker id, so two simultaneous runs share schema names; the contaminated baseline showed two unrelated failures and was discarded rather than reported).
