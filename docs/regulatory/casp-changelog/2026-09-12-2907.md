- **#2907** — Naming epic #2906, phase 0: renamed the wire contract
  ADDITIVELY in `packages/backend/src/openapi/spec.ts`. Nine Safe-named paths
  (`/user/safes*`, `/transactions|balances|portfolio/{safeAddress}`) gained
  `/user/accounts*` / `{accountAddress}` twins sharing the exact same handler
  (registered a second time under the new prefix where the path has more than
  one segment; a single dynamic segment needs no second registration — the
  URL is already served under both names). The 11 operationIds gained
  `*Account*` twins; old operationIds and paths carry `deprecated: true` and a
  removal-release sentence built from one shared `deprecatedSafeAlias()`
  template (DRY rather than 31 copies of the same string) — the literal
  source-text `grep -c "removed in" openapi/spec.ts` is 3 (the template
  definition plus one unrelated pre-existing usage plus a doc-comment
  naming the convention); `grep -c "deprecatedSafeAlias(" openapi/spec.ts`
  is 31 and is the number that reflects how many old names actually carry
  the sentence at runtime.
  Schemas `userSafe`/`sessionSafe` are unchanged in name (owner review on
  #2906 corrected the epic's original "rename `components.safe`" plan); new
  flat-duplicate schemas `account`/`sessionAccount` share one properties
  object with the old schemas (`accountAliasProperties` /
  `sessionAccountAliasProperties`) rather than an `allOf` $ref — #2888's
  established lesson: `closeObjects` registers every component CLOSED, so a
  `$ref` inside `allOf` is left open and false-fails `additionalProperties:
  false`. Safe-named properties in `Agent`, `Transaction`,
  `DashboardAgentPreview`, `TransactionsResponse` and the session-user shapes
  gained account-vocabulary twins in `properties` (declared, always emitted,
  dual-emit equality-tested — `openapi/wire-aliases.ts` /
  `wire-aliases.test.ts`), deliberately kept OUT of each schema's `required`
  array: widening `required` flips the generated `packages/core/src/
  api-types.ts` field from optional to non-optional for every downstream
  consumer repo-wide (frontend fixtures/hooks/components), a blast radius
  this additive backend slice does not own — the emission guarantee is
  enforced by the mapper's equality test instead, which is what the PR's
  mutation proof exercises. `AgentPaymentNextAction`'s served enum gained
  `fund_account_or_raise_allowance` additively (schema + `x-enumDescriptions`)
  without touching the backend taxonomy mirror, which stays parity-pinned to
  the SDK (`agent-payment-taxonomy.parity.test.ts`, a P1/#2908 surface); the
  server still only emits the old `fund_safe_or_raise_allowance` value,
  pinned by `agent-next-action-account-alias.test.ts` with a comment naming
  #2914 as the flip. `?accountId=` is accepted alongside `?safeId=` on both
  transactions list endpoints (both filter identically — an unrecognized-id
  400 and a real filtered-vs-unfiltered count difference are both asserted,
  since an unknown query key is otherwise silently ignored). `sign_data.
  components.payer_account` is a same-value twin of `components.safe` on the
  two routes that emit it (`delegation-authorize.ts`, `replay.ts`) —
  deliberately NOT a rename into `components.account`, which already means
  the delegate account address on those two shapes (a different address; an
  installed SDK reads `components.safe` as the x402 receipt's `payer` field,
  `x402-funding-leg.ts:312`, so collapsing the two would silently corrupt that
  field for every client that predates this release). `components.account`
  is untouched, and no `x402_expected_context_version` change was made
  anywhere (`sign_data` is response metadata, never part of the signed
  expected-context payload — confirmed on #2906; a version bump would have
  made every installed signer refuse to sign, `SUPPORTED_X402_EXPECTED_
  VERSIONS = [1, 2, 3]` unchanged). The dashboard CSV export gained an
  appended `account_address` column (same value as `safe_address`), per the
  export's own "append at the end, never reorder" contract. `api-types.ts`
  regenerated and the blocking drift check (`check:api-types`) is green.

  **Authority/custody argument.** Nothing here changes who can spend, from
  what account, or under what caveat: every new field, path and enum value is
  a same-value, additive alias over an existing read or an existing
  server-emitted value — no new query, no new authority check, no altered
  signed payload. The one new user-visible value
  (`fund_account_or_raise_allowance`) is accepted on input only and changes
  no server behavior; the server's own emission is unchanged and pinned.
  Mutation-proven: (a) dropping a twin field from a `wire-aliases.ts` mapper
  fails its equality test; (b) simulating an early flip to the new enum value
  fails the emission pin; (c) removing the `?accountId=` fallback makes the
  filtered-count-differs-from-unfiltered assertion fail; (d) aliasing
  `payer_account` to `components.account` instead of `components.safe` fails
  the payer-account equality test. Perimeter unchanged.
