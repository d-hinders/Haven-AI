- **#2908** — Naming epic #2906, phase 1: the five published packages
  (`@haven_ai/sdk`, `signer`, `mcp`, `connect`, `cli`) and the hosted MCP
  server READ both the Safe-vocabulary and the account-vocabulary names and
  prefer the new, EMIT both with one value for the one-release window, and
  WRITE only the new. This is the packages PR; the `0.2.0` release bump is a
  second PR. **No expected-context version change and no migration.**
  **What changed, per reader.** *Signer credential file*
  (`signer/src/credentials.ts`): `account_address ?? safe_address ??
  safeAddress` — the two old keys are read PERMANENTLY (#2906 decision 2a: a
  credential file on disk never rewrites itself; a signer that stopped reading
  `safe_address` would silently lose the account address, change the consent
  hash and drop the local sweep-destination check for every agent connected
  before this release). *Signer / mcp environment*: `HAVEN_ACCOUNT_ADDRESS ??
  HAVEN_WALLET_ADDRESS ?? HAVEN_SAFE_ADDRESS` (survivor decided on #2906; the
  two old names go at #2914). *mcp credential file, single and split*
  (`mcp/src/credentials.ts`): the same file chain per file, with an explicit
  `accountAddress` key added to `HavenCredentialFile` (this shape is separate
  from the signer's, as the epic review noted) and the split-file agreement
  check relabelled `account_address`. *connect* writes `account_address` only
  (`storage.ts` — all three payloads), reads stored sets new-name-first with a
  permanent `safe_address` fallback, chains the re-key rewrite
  `stored.accountAddress ?? identity.account_address ?? identity.safe_address`,
  and `--doctor`'s `credentials` check now reports which name the set carries.
  *SDK receipt builder* (`x402-funding-leg.ts`, via `account-naming.ts`):
  `raw.payer ?? raw.account_address ?? raw.sign_data?.components.payer_account
  ?? raw.safe_address ?? raw.sign_data?.components.safe` — deliberately NEVER
  `components.account`, which on the funding shapes is the DELEGATE account
  (a different address; reading it would put the delegate on the receipt as
  the payer). *SDK mappers* (`account-reads.ts`): one `accountAddressTwins(
  readAccountAddress(raw))` per shape (`HavenAgent`, `HavenAllowanceSummary`)
  — which is also the hosted `haven_get_agent` / `haven_get_allowances`
  dual-emit point, since those spread the SDK objects; equality-tested for
  old-only, new-only and both server shapes. *Enum*:
  `fund_account_or_raise_allowance` is accepted through
  `AgentPaymentNextActionAccountAlias` and collapsed onto the canonical
  `fund_safe_or_raise_allowance` at the SDK's two read boundaries
  (`payment-mappers.ts`, `payment-state.ts`), so a `switch` on the taxonomy
  const does not fall through when the server flips its emit at #2914; the
  alias lives BESIDE `AgentPaymentNextAction`, not inside it, because the
  backend keeps a parity-pinned hand-mirror of that const and this slice does
  not touch `packages/backend`. *CLI*: new paths (`/user/accounts*` — no 404 fallback to the old paths, so the backend carrying #2907 must be live before the CLI release is promoted to `latest`; recorded in `packages/cli/CHANGELOG.md`),
  `?accountId=` AND `?safeId=` (same value — an unknown query key is silently
  ignored, so the old key is what keeps a pre-#2907 server filtering),
  `account_id` AND `safe_id` on the setup request, `--json` and the CSV
  header dual-emit (`account_address` APPENDED after `chain_id`, append-only
  contract). *Agent-facing prose* (`sdk/src/tool-descriptions.ts`, the #1598
  treatment, extended not replaced): both enum spellings documented with the
  emitted one still old; `accountAddress` listed first with `safeAddress` as a
  deprecated same-value alias; "originating Safe" → "originating account".
  **Where `tool-descriptions.ts` lives.** The issue asked for it to move to
  `mcp-server`; it stays in the SDK because `sdk/src/tools.ts` (the
  function-calling definitions), the published `@haven_ai/mcp` (re-exports it
  from `@haven_ai/sdk`) and the SDK's public index all import it, and
  `mcp-server` is a PRIVATE package downstream of the SDK — a shim in the
  reverse direction is not expressible. The strings are edited in place.
  **Authority/custody argument.** Nothing here changes who can spend, from
  what account, or under what caveat. Every reader resolves the SAME value it
  resolved before from one more (earlier) key; every emitter adds a second
  key with the same value; the one writer (connect) writes one key instead of
  another with the same value. No signed payload changes:
  `SUPPORTED_X402_EXPECTED_VERSIONS` is `[1, 2, 3]` before and after
  (`version-skew.test.ts` untouched and green; a new
  `naming-window-no-version-change.test.ts` pins the list and the advertised
  capability from this slice's side), `signer/src/capabilities.ts` is
  unchanged and `core.ts` changed only in a comment. The consent-hash INPUT is
  the resolved address, not the key it came from, so an old-file machine's
  ack stays valid. The signer's sweep-destination check (`expectedSafe`) is
  fed the same resolved address. No new query, endpoint, or authority check.
  **Mutation-proven** (each restored from a `cp` backup, the named test file
  re-run): (a) dropping `account_address` from the signer's file chain → 3 of
  17 fail in `signer/src/credentials.test.ts` (the NEW-shape, BOTH and
  exact-chain tests); (b) dropping the `safe_address` fallback → 3 of 17 fail
  (the OLD-shape test, the exact-chain test and the pre-existing
  snake_case-file test); (c) the receipt builder reading `components.account`
  instead of `payer_account` → 3 of 18 fail in `sdk/src/account-naming.test.ts`
  (the new-only-inside-`sign_data` fixture, the precedence fixture and the
  delegate-trap fixture); (d) the CLI emitting only the new key (`account_id`
  without `safe_id`; `account_address` replacing `safe_address` in the CSV
  header) → 2 of 77 fail in `cli/src/json-contract.test.ts`; the same
  drop-new / drop-old pair on the mcp file chain → 5 of 25 / 7 of 25 fail in
  `mcp/src/credentials.test.ts`; on the SDK's `readAccountAddress` → 3 of 18 /
  2 of 18 fail (which includes the hosted-shape mapper rows); on connect's
  `readStoredAccountAddress` → 4 of 16 / 3 of 16 fail in
  `connect/src/storage.test.ts`; and emitting only one camelCase twin from the
  SDK's `accountAddressTwins` mapper → 4 of 18 fail (the three server-shape
  equality rows plus the helper's own pin). **Server twins P0 (#2907) does not emit yet**, read first and
  never required by this slice: `account_address` on `GET
  /machine-payments/agent`, `GET /machine-payments/allowances` and the top
  level of the x402 authorize response (`sign_data.components.payer_account`
  IS emitted there); `account_id` on `CreateAgentRequest` is in P0's second
  round, so the CLI sends both. The dev-channel O3 proof (`npx
  @haven_ai/connect@dev` on a machine with an OLD credential file and OLD env;
  the receipt's `payer` populated) is a post-merge operator step recorded on
  #2906, before promotion. **Perimeter unchanged.**
