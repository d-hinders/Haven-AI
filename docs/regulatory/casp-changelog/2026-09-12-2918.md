- **#2918** — gate `/accounting/connections/*` on `config.hosted && config.accountingEnabled`, closing a hole #2917 review surfaced: the connection routes carried `authMiddleware` only, so a signed-in user on a deployment that is not hosted, or is hosted with the flag off, could still start an OAuth consent, store a grant and set a destination — the flag hid the feature in the UI, not on the server. **What changed.** A new `requireAccountingFeature` middleware (`middleware/accountingFeed.ts`, alongside the existing `requireAccountingFeed`) checks `config.hosted && config.accountingEnabled` only — deliberately NOT the account entitlement, which stays the feed's own gate (#2861 decision, explicitly preserved): an unentitled account on a hosted, enabled deployment can still connect, activate and backfill, so upgrading later needs no reconnect. Applied to `GET /accounting/connections`, `POST …/:provider/connect-url`, `POST …/:provider/api-key`, `DELETE …/:provider`, `POST …/:provider/activate`, `POST …/:provider/backfill`, and `PATCH …/:provider/settings` — same 404 body shape as `requireAccountingFeed` (`{ error: 'Not found' }`), so a deployment with the feature off does not advertise it by answering differently. `GET /accounting/providers` is deliberately exempt: it stays session-only so the Coming soon page (#2869) can still list platforms with the flag off. The OAuth callback (`GET …/:provider/callback`) is handled differently on purpose: it is reached by a browser redirect, not a fetch the SPA controls, so a consent already in flight when an operator flips the flag is not the user's fault — the off-path redirects to `/accounting?provider=<id>&connect=error&reason=feature_off` instead of a bare 404, and the `state`'s single-use `jti` is consumed EITHER WAY (before the feature check, same as the existing before-code-exchange consumption), so a state issued while the feature was on cannot be replayed after it is re-enabled. **Authority/custody argument: this closes reach, it does not add any.** No new route, no new write path, no change to what a route DOES once it runs — only when it is reachable. The gate runs before every handler's first read or write (repository calls, the OAuth/API-key flows, the sync orchestrator) — proven by asserting none of them are invoked when the gate answers 404. `.github/money-path-globs.json` is untouched; nothing here touches a transaction, delegation, allowance, relayer, signer or key. **What is mutation-tested** (each restored from a `cp` backup and the suite re-run green): (a) removing `requireAccountingFeature` from the route registrations turns every 404 assertion (14 across the two off configurations: `hosted=false` and `hosted=true,accountingEnabled=false`, seven routes each) into a 200/201/204 — caught; (b) moving the feature check in the callback ahead of `consumeOAuthState` (so the off-path no longer consumes the jti) turns the replay-after-re-enabling assertion green when it should be red — caught, the state was wrongly accepted a second time and `connect=connected` came back. The #2861 preservation is asserted directly: the entitlement repository (`hasEntitlementRow`) is mocked to throw if called, and a connect-url issue on a hosted, enabled deployment with no entitlement row still succeeds. Full count: 60/60 tests green in `routes/__tests__/accounting-connections.test.ts`, including the 16 new/changed gate assertions. **Perimeter unchanged.**
