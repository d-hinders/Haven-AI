  **Authority argument: rename only, zero rows touched, no view created, SQL
  semantics unchanged.** `up()` is twenty-one unconditional `ALTER TABLE …
  RENAME TO` / `RENAME COLUMN` / `RENAME CONSTRAINT` and `ALTER INDEX …
  RENAME TO` statements in one transaction — no `CREATE`, no `DROP`, no
  `UPDATE`, no `DELETE`. Every predicate any live query evaluates is
  byte-identical before and after; only the identifier naming the column or
  table changed. `agents.account_id` (renamed from `safe_id`) stays a bare
  `UUID` with no foreign key — it never had one, and adding one is a
  separate, later decision explicitly out of this migration's scope. The
  `account_type` value `'safe'` and its CHECK's IN-list are untouched byte-
  for-byte (only the CHECK **constraint's name** changes,
  `user_safes_account_type_check` → `smart_accounts_account_type_check`) —
  that value is #2912's scope. `083`'s `account_type` default
  (`'delegator_hybrid'`, migration 083 on the stacked #2851 branch, PR #2940) carries forward automatically
  under the new table name: a table rename touches no column attribute, so
  nothing in `084` re-derives or re-asserts it — proven by a dedicated test
  that a legacy `account_type='safe'` row survives the rename with its value
  unchanged.

  **Decision 3, re-decided after review (epic Notes): no compatibility
  view.** A view could shadow the table name `user_safes`, but not the six
  other relations whose COLUMNS this migration renames
  (`agents.safe_id`/`account_id`, `agent_connection_setups.safe_id`/
  `.safe_tx_hash`, `users.safe_address`, `payment_intents.safe_address`,
  `user_passkeys.safe_address`, `hybrid_account_passkeys.user_safe_id`) — a
  view protects one relation of seven and makes the deploy only look
  protected. The operator procedure is a **quiesced deploy** instead (epic
  step O2): scale the backend to 0, confirm no old container still serves,
  deploy the image carrying this migration, confirm it in the boot log, scale
  back up. Migrations run on boot on every replica in the same image as the
  code (`db/migrations/index.ts:333`), so a new replica never meets the
  pre-rename schema; the hazard this closes is an OLD replica still serving
  after the rename commits, which the view could not have prevented for six
  of the seven relations regardless.
