  **Authority argument: one value rename on inert-history rows, CHECK
  tightened, no row deleted.** `up()` runs, in one transaction: (1)
  `ALTER COLUMN account_type SET DEFAULT 'delegator_hybrid'` — an idempotent
  no-op, since `083_drop_dead_safe_rail_tables.ts` already set this default
  and `084` carried it forward under the renamed table; kept per the issue so
  this migration does not need to know which branch shipped first; (2)
  `DROP CONSTRAINT smart_accounts_account_type_check`; (3)
  `UPDATE smart_accounts SET account_type = 'legacy_safe' WHERE account_type =
  'safe'` — the ONLY row mutation in this migration, and the only row UPDATE
  in the whole PR; (4)
  `ADD CONSTRAINT smart_accounts_account_type_check CHECK (account_type IN
  ('legacy_safe', 'delegator_hybrid'))`, explicit name (the `079`/`084`
  lesson — name every constraint explicitly, never rely on Postgres's default
  naming or a schema-blind idempotency check). The DROP-before-UPDATE order is
  load-bearing, not stylistic: the OLD CHECK does not admit `'legacy_safe'`
  and the tightened CHECK, if added first, would `ADD CONSTRAINT`-validate
  every existing row and reject the very `'safe'` rows the UPDATE is about to
  fix — measured, not assumed, on a fresh schema via `db:schema-smoke` before
  the order was corrected (see the migration's own header). `down()` is the
  exact mirror. No `DELETE FROM` anywhere in this file, matching epic #1440's
  standing decision that retired rows stay as inert history — renamed, never
  dropped.

  **What is explicitly NOT touched, and why:** `onboarding_events.event`'s
  `'safe_deployed'/'safe_imported'/'safe_funded'` values and
  `relayer_gas_events.operation = 'safe_deploy'` are event HISTORY describing
  what happened in the past, not the account's current rail (epic #2906
  Notes, "Not renamed, on purpose") — neither table nor any row in it is
  touched. `DELEGATION_RAIL_ONLY`-style filters
  (`infra/repositories/smart-accounts.ts`'s `AND account_type =
  'delegator_hybrid'`, and the equivalent literal in `infra/repositories/
  agents.ts`) compare against the LIVE value only and were never keyed on the
  retired value's spelling — unaffected by construction, and the migration's
  own test proves it by running the real repository query
  (`listAccountsWithTypeForUser`) after the rename and asserting it returns
  exactly the `delegator_hybrid` rows, none of the renamed `legacy_safe` ones.
  Column/table/constraint NAMES are untouched — already `smart_accounts` /
  `smart_accounts_account_type_check` as of `084` (#2911); only the
  constraint's CONTENT and the one row value change here.

  **Wire-contract assessment: not a breaking change for any client.** The
  OpenAPI `account_type` field (`openapi/spec.ts:749,7429`) is typed as a bare
  `['string','null']` with no enum — it never advertised `'safe'` as a valid
  value. The one place the spec DOES narrow it to an enum
  (`openapi/spec.ts:3986`, the hybrid-account provisioning response) already
  reads `enum: ['delegator_hybrid']` only, unrelated to this rename. Every
  production TypeScript reader of `account_type` (backend routes/modules,
  `packages/cli/src/commands.ts`, frontend `Agent`/`SmartAccount` types) types
  the field as `string | null` and compares only against the literal
  `'delegator_hybrid'` — there is no `AccountType` union with `'safe'` as a
  literal member anywhere in production code to rename. `check:api-types`
  confirms `api-types.ts` is already in sync with the spec both before and
  after this change — no regeneration was needed. No route echoes a legacy
  account's raw `account_type` value back to a caller: every account
  list/detail read that could is already filtered to `delegator_hybrid` only
  (#2413), and the internal reads that carry the unfiltered value
  (`AGENT_BY_API_KEY_SQL`, `rekey-guards.ts`, `agent-passports.ts`,
  `agent-delegations.ts`) only ever compare it, never serialize it into a
  response body. Net: no SDK, CLI, or connect reader observes this rename on
  the wire, because the wire never carried the retired value in the first
  place.

  **What is mutation-tested** (`__tests__/085_account_type_legacy_safe.test.ts`,
  10 assertions), each planted alone via a `cp` backup and restored: (a)
  commenting out the `UPDATE` statement in `up()` — "up() renames exactly the
  seeded 'safe' rows" fails (the ADD CONSTRAINT that follows it, still

  target one); (b) keeping the widened CHECK ADD/DROP pair OUT of `up()`
  entirely (UPDATE still runs, CHECK left untouched at the old

  fails exactly as expected (6 of 10 tests go red). Both restored via `cp`

  proves: exact post-count (N seeded `'safe'` rows → 0 `'safe'` / N
  `'legacy_safe'` after `up()`; M `'delegator_hybrid'` rows untouched by id);

  `information_schema.columns.column_default` reads `'delegator_hybrid'`
