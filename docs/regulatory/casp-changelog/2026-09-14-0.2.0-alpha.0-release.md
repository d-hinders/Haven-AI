  ## The rename, and why it is safe this release

  `account_type` value `'safe'` becomes `'legacy_safe'` (migration 085), the
  table `user_safes` becomes `smart_accounts` (084), and the dead Safe-rail
  tables are dropped (083). Across the wire the vocabulary moves `safe_*` →
  `account_*`. The published packages implement **one stated rule** —
  `packages/sdk/src/account-naming.ts`, new in this release:

  > READ both names and prefer the new; EMIT both names with the same value;
  > WRITE only the new.

  **The old names are removed by #2914, one release AFTER this one, and #2914
  is verifiably absent from this range.** The instrument is named precisely,
  because this claim is what the release's safety rests on and a loose one
  falsifies itself: a plain `git log origin/main..origin/dev | grep 2914`
  returns **seven** hits — every one a commit *body* referring to the future
  contraction, none implementing it. What establishes the claim is the closing
  keyword and the subjects:
  `git log origin/main..origin/dev --format='%s%n%b' | grep -iE '(close[sd]?|fix(e[sd])?|resolve[sd]?) +#2914'`
  → **no match**, and no commit subject mentions #2914.

  This release is the window itself: a consumer on
  0.1.37-alpha.0 keeps working against a server that now emits both names, and
  a consumer on 0.2.0-alpha.0 keeps working against a server that still emits
  only the old ones. Shipping the removal alongside the rename would have
  collapsed that window to zero.

  One fallback is **permanent rather than windowed**, and the distinction
  matters: the credential-FILE reads (`safe_address` / `safeAddress` in a file
  on disk) never expire, because a file written before this release does not
  rewrite itself until the next re-key.

  ## Compatibility, tested against the published tarballs

  `npm pack @haven_ai/<pkg>@0.1.37-alpha.0` for all five, extracted, each
  `dist/*.d.ts` compared against this branch's build — by **declaration name**,
  not merely by count, because a net increase can hide a removal:

  | package | declarations | removed | added |
  |---|---|---|---|
  | `sdk` | 178 → 186 | **none** | **8** |
  | `signer` | 53 → 56 | **none** | 3 (2 exported) |
  | `mcp` | 29 → 29 | none | none |
  | `connect` | 84 → 84 (+ `cli.d.ts` 3 → 3) | none | none |
  | `cli` | 14 → 14 | none | none |

  **The instrument matters, and the first version of this table used a broken
  one.** An earlier draft counted `declare` statements, which covers
  `const`/`function`/`class`/`enum` and **excludes every `type` alias and
  `interface`** — the shapes most likely to break a consumer. It reported
  sdk 111 → 118 and signer 31 → 33, and it lost exactly the name that carries
  this release's one break. The figures above come from matching
  `(export )?(declare )?(const|function|class|enum|type|interface) <name>`,
  which admits both. Review caught this; the "zero removed" conclusion survives
  under the wider instrument, but under the narrow one it was luck rather than
  measurement.

  **Zero declarations removed anywhere; ten exported names added** — eight in
  the sdk (`readAccountAddress`, `readAccountId`, `readX402ReceiptPayer`,
  `accountAddressTwins`, `canonicalAgentPaymentNextAction`,
  `isFundAccountOrRaiseAllowance`, `AgentPaymentNextActionAccountAlias` and
  **`AgentPaymentNextActionWire`**) and two in the signer
  (`readAccountAddressEnv`, `readAccountAddressField`; a third addition,
  `RawCredentialFile`, is not exported). The sdk's `export { … }` barrel gained
  those eight and dropped none; the signer's gained two.

  **It is NOT purely additive, and calling it that would be the easy error
  here.** One existing field changed type. `next_action` on the agent-payment
  summary moves from `AgentPaymentNextAction` to
  `AgentPaymentNextActionWire = AgentPaymentNextAction | AgentPaymentNextActionAccountAlias`
  — a **widening** union carrying `fund_account_or_raise_allowance` beside the
  canonical `fund_safe_or_raise_allowance` for the window's duration. No
  declaration is removed, so a declaration-name diff reports "nothing lost" and
  a count reports "+8"; both miss it. The consequence is precise and worth
  stating exactly:

  - Reading `next_action`, or passing it on: **unaffected.**
  - Assigning it to a variable or parameter typed `AgentPaymentNextAction`:
    **now a type error**, because the wider union is not assignable to the
    narrower.
  - An exhaustive `switch` over it with a `never` default: **now non-exhaustive**.

  So this is a **source-level breaking change for a TypeScript consumer that
  narrows the field**, exactly as epic #2906's item 7 anticipated ("the SDK
  public types change shape: this is a breaking release"). The migration path
  ships with it: `canonicalAgentPaymentNextAction()` collapses the alias onto
  the canonical value and passes everything else through, so a consumer that
  wants the old narrow type calls it at the boundary. The runtime value a
  server actually emits is unchanged this release — the epic's decision 2(c)
  keeps the server **emitting the old** value through the window and flips it
  at #2914 — so nothing breaks at runtime; the break is at compile time only,
  and only on narrowing.

  ## Consent re-prompt: safe forwards, NOT safe backwards

  This claim needed more work than last release, because the consent input
  genuinely changed: `packages/connect/src/local-mcp-consent.ts` and
  `signer-consent.ts` now read `credentials.accountAddress ?? credentials.safeAddress`
  where they read `credentials.safeAddress`. The hash covers identity
  (api-key prefix, api URL, agent id, **account address**, delegate address,
  chain id), the canonical tool set and the canonical allowance set. Two of
  those three inputs were checked directly:

  - **The address VALUE is identical across both file shapes.** The stored
    reader's own tests pin it: an OLD-shape set (`safe_address` only) and a
    NEW-shape set (`account_address` only) both resolve to the same address,
    and a set carrying both prefers the new. So an existing credential file on
    disk — which carries only `safe_address` — feeds the hash exactly the byte
    string it fed before. The key the value was read from is not a hash input;
    only the value is.
  - **The registered tool set did not move: 15 names on `origin/main`, the same
    15 on `origin/dev`** — measured over `Object.keys(toolSchemas)`, the set
    `registeredToolNames()` actually returns, not a regex over the file (the
    0.1.37 shard recorded an instrument that matched zero names on both refs
    and was therefore vacuously "identical"; that error is not repeated here).

  The allowance set is untouched by this change, and no third hash input moved:
  the split-file loader still resolves per file before comparing, so a mixed-era
  identity/signer pair agrees on the value rather than throwing a mismatch.

  **An earlier draft stopped here, concluded "therefore no operator is
  re-prompted on upgrade", and named its own gap as "no cross-version hash
  comparison exists". Review built that comparison. It passes — and it exposed
  a second direction the draft never asked about, which fails.**

  | reader | credential file shape | account address resolved | consent hash |
  |---|---|---|---|
  | mcp 0.1.37 | old (`safe_address`) | resolved | `f7979aa598477318` |
  | mcp 0.2.0 | old (`safe_address`) | resolved | `f7979aa598477318` |
  | mcp 0.2.0 | new (`account_address`) | resolved | `f7979aa598477318` |
  | **mcp 0.1.37** | **new (`account_address`)** | **absent** | **`5af1154583687a0b`** |

  Rows 1-3 close the gap the draft named, and close it better than the draft
  claimed for itself: **upgrading a runtime against an existing credential file
  does not re-prompt.** That is the common path and it is safe.

  **Row 4 is the finding.** A credential file written by
  `@haven_ai/connect@0.2.0` — which writes `account_address` and deliberately
  **no** `safe_address` — is unreadable by a **0.1.37** runtime. Measured against
  the published tarballs: `@haven_ai/mcp@0.1.37-alpha.0` and
  `@haven_ai/signer@0.1.37-alpha.0` contain **zero** occurrences of
  `account_address` / `accountAddress` / `HAVEN_ACCOUNT_ADDRESS`; the dual-read
  landed in #2933, which is *in this release*, not before it. The old loader
  does not throw — it yields `undefined` — so the failure is **silent**: the
  address drops out of the consent input, the hash changes, the operator is
  re-prompted, and the consent block loses its account line entirely.

  **The reachable path, named rather than left as theory.**
  `connect`'s `--rekey-finish` rewrites the credential files to the new name
  *before* it re-installs the runtime, and the re-install is conditional on
  `--runtime` being passed. So `--rekey-finish` **without** `--runtime` leaves
  new-name files beside a runtime still pinned at 0.1.37 — row 4 exactly. A
  failure between the rewrite and the re-install leaves the same state, and the
  warning printed on that path speaks only about a stale API key.

  **Bounded, and why this is recorded rather than blocking.** No funds are at
  risk and nothing is unrecoverable: the backend resolves the account from the
  API key, not from the file, so the affected installation re-prompts for
  consent rather than losing spend authority, and re-running with `--runtime`
  restores it. But an operator reading "no operator is re-prompted" would be
  told the opposite of what this path does, which is why that sentence is gone
  from this record.

  ## Perimeter reasoning

  The rename is **vocabulary, not authority**. No route, credential, signing
  path or caveat enforcer is added, removed or widened. `account_type` is a
  descriptive column: the value `'safe'` → `'legacy_safe'` renames what the
  retired AllowanceModule rail's accounts are *called*, and those accounts
  remain closed to new signups and unable to spend (#1984, #1986, whole-rail
  retirement #1440). **085's CHECK is renamed one-for-one, not narrowed:**
  `IN ('safe','delegator_hybrid')` → `IN ('legacy_safe','delegator_hybrid')`,
  two admissible values before and two after. An earlier draft called this a
  tightening and inferred a fail-closed property from it; the migration's own
  prose says "tighten", and converting that loose word into an explicit safety
  guarantee manufactures one. There is no safety property here — it is a
  rename.

  ## This promotion requires a QUIESCED DEPLOY, not a rolling one

  Migrations 083, 084 and 085 are backend-only — `packages/backend` is
  `private: true` and reaches no tarball — but **"backend-only" is the wrong
  thing for an operator to take from this record**, and an earlier draft said
  only that, reducing the obligation to "verify the migrations applied". That
  is a post-hoc check. The precondition is downtime.

  Migration 084 renames `user_safes` → `smart_accounts` and renames columns
  across **seven relations** (`agents`, `users`, `payment_intents`,
  `user_passkeys`, `agent_connection_setups`, `hybrid_account_passkeys` and the
  table itself). Migrations run on boot in the same image as the code, so new
  code never meets the old schema — the hazard is the reverse: **old replicas
  still serving after the rename commits**, which take
  `relation "user_safes" does not exist` on every request. Epic #2906 decision 3
  considered an updatable view and rejected it, because a view protects one
  relation of seven and makes the deploy only *look* protected.

  The operator procedure is epic #2906 step **O2**, and it is not optional:
  **scale the backend to 0 → confirm no old container is still serving
  (Railway's rolling deploy does not by itself stop the old container) → deploy
  the image carrying 084 → confirm the migration in the boot log → scale back
  up**, with timestamps recorded on #2906. Step **O4** follows the promotion:
  grep backend logs for `relation "user_safes"` and `column "safe_` errors,
  expecting zero.

  083 drops `self_sign_agents`, `self_sign_payment_intents` and `owner_aliases`
  (epic #1440's final slice) and also changes `user_safes.account_type`'s
  DEFAULT — stated because "the dead Safe-rail tables are dropped" understates
  it.

  ### O3 was waived by the owner for this release

  Epic #2906's promotion checklist gates the promotion on **O3**: re-run
  `npx @haven_ai/connect@dev` on a founder machine carrying an OLD credential
  file and OLD env, confirm the agent pays **and the x402 receipt's `payer`
  field is populated** — the dual-read proof on the wire. **The owner decided on
  2026-09-14 to proceed without it.** Recorded here rather than ticked on the
  epic, because the checkbox means the proof was taken and it was not.

  What that leaves unverified is specific: the *wire* half of the dual read —
  a real server response reaching a real installed runtime with an old-shape
  credential file and `HAVEN_SAFE_ADDRESS` still set, and the receipt `payer`
  resolving through `readX402ReceiptPayer`'s fallback chain. The type-level and
  hash-level checks in this record do not substitute for it; they cover shapes,
  not a live payment. Row 4 above is the concrete reason the direction matters.

  `@haven_ai/core` remains irrelevant by construction: **no published package
  depends on it** — verified by reading each `package.json`'s `@haven_ai/*`
  dependencies this release, not carried over from the last one (`sdk` and
  `cli` declare none; `mcp` and `signer` only `@haven_ai/sdk`; `connect` the
  sdk plus `mcp` and `signer`).

  **One deliberate off-contract passthrough, recorded because it is a cast.**
  `accountAddressTwins` declares `{ accountAddress: string; safeAddress: string }`
  but casts, so a server that sends NEITHER name yields `undefined` under both
  keys rather than a fabricated `''`. That is the pre-#2908 behaviour preserved
  exactly — a blank-but-present address would read downstream as a real
  destination in the hosted MCP outputs and the sweep, which is the worse
  failure. The cast is commented at the site as the one place the off-contract
  case passes through unchanged.

  ## Version: 0.2.0-alpha.0, a minor bump, decided against the script convention

  `scripts/README.md` § *Which version string* states the alpha convention as
  `0.1.<N+1>-alpha.0`, and ~38 consecutive releases have followed it. **This
  release departs from it deliberately**, and the departure is recorded here
  rather than left to be inferred from the version number.

  Two in-repo instructions call for a minor bump, and one of them was written by
  the very slice that created the break:

  - `packages/sdk/CHANGELOG.md`, under the entry for this change: "Under the 0.x
    convention this is a **minor** bump (`0.1.x → 0.2.0`)."
  - Epic #2906 item 7: "this is a **breaking release** of the SDK — under the
    0.x convention a **minor** bump with a changelog entry naming every renamed
    field."

  `scripts/README`'s own framing is the tiebreaker: it introduces that section
  with "The bump-type table above is a description of the script's arithmetic,
  **not a recommendation**", and says nothing about a breaking release. A
  convention describing default arithmetic does not override a per-release
  decision recorded by the change's author.

  A first cut of this release went out as `0.1.38-alpha.0` — a patch bump —
  and the first draft of this shard cited epic item 7 for the proposition that
  the release is breaking while stopping the quotation immediately before the
  clause naming the lever. Independent review caught both. Nothing was published
  at `0.1.38-alpha.0`; it was never pushed to npm, so the correction costs one
  bump cycle and nothing else. Correcting it after publication would have been
  impossible: npm versions cannot be unpublished after 72 hours and `latest`
  cannot move backwards.

  ## Release mechanics

  Versions, cross-package pins, the seven source version constants and the
  Supported Runtime Manifest table were rewritten atomically by
  `release-bump.mjs`: **33 insertions / 33 deletions across 14 files**, version
  lines only (11 lockfile + 11 `package.json` + 7 source constants + 4
  manifest-table rows). `HAVEN_CONNECTOR_CHANNEL` untouched: `alpha` → `alpha`.
  The manifest table's `last-verified` moved 2026-09-13 → 2026-09-14 by hand;
  its four version rows were not hand-edited.

  **Tested, and the gaps named.** All five published suites at this tree:
  sdk 41 files / 443, cli 8 / 202, mcp 6 / 137, signer 17 / 194, connect
  24 / 535 (+5 skipped) — 1,511 passed. `lint:workspace-pins`, `typecheck` and
  `check:dist` exit 0. **Not a result:** the backend real-DB suite, which
  cannot reach Postgres in the authoring environment (no Docker daemon) — and
  it matters more this release than last, because migrations 083/084/085 are
  exactly what it would exercise. CI covers it, and the promotion's own
  operator step verifies the migrations applied.

  **Promotion caution (#2647, #2660).** The `latest` move is its own
  `main`-only `promote-tags` job, so a half-green promotion is live: published
  under `alpha`, `latest` unmoved. `latest` currently reads `0.1.37-alpha.0` on
  all five. Verify against the registry over HTTP, polling for several minutes,
  never off a green workflow — on the 0.1.37 promotion two of the five packages
  still read the previous version on the first read and were current 27 seconds
  later.

  Perimeter unchanged — this release renames what Haven calls an account, in a
  window that keeps both names working, and adds nine read helpers. Nothing
  about who may spend, sign, or execute. The spend authority a delegation
  grants remains bounded on-chain by the same audited caveat enforcers.
