- **#2960** — Quality scan 2026-09-13 finding F1: one shared party vocabulary
  (`treasury_account` / `delegate` / `delegate_account` / `merchant`) is now
  emitted ADDITIVELY on every response that already names a lone
  `payer*`/`payerAddress` address — a bookkeeping/audit-transparency claim
  about which of Haven's own addresses moved the funds, never an authority or
  custody change. No route gains a new signed input, no delegation is read
  differently, and every existing `payer*` field keeps its exact prior value
  (characterization-tested — see below).

  **Where.** `openapi/spec.ts` gains one flat, closed `Parties` component
  (`#2888` — no `$ref` inside `allOf`) and a single mapper,
  `withParties(row, parties)` in a new `openapi/party-model.ts` (a sibling to
  `wire-aliases.ts`, not an addition to it: the existing file's own header
  scopes it to same-value `safe`→`account` twins, and these four are
  DISTINCT addresses with no single old-name sibling to equal-test against).
  Wired into `GET /machine-payments/receipts` and the `POST
  /machine-payments/evidence` echo (`modules/mpp/evidence.ts`'s
  `mapEvidence`), `GET /machine-payments/{id}/status`
  (`modules/payments/agent-payment-status.ts`), and
  `PaymentReceipt.payment` (`modules/payments/receipt.ts` — the `safe`/
  `account` twins from #2907 are untouched, `parties` sits alongside them).
  The published `@haven_ai/sdk` `PaymentReceipt`, `HavenPaymentReceipt` and
  `PaymentStatusResult` types gain an optional `parties` field
  (`packages/sdk/src/types.ts`, one shared `mapParties` helper in
  `payment-mappers.ts`); `verifyPaymentReceipt` is unaffected — it recovers
  the signer from `authorization` only and never reads `payment`
  (direct test: `receipt.test.ts` asserts identical verification with and

  Hosted MCP (`haven_list_receipts`, `haven_get_payment_status`) spreads the
  SDK shape unchanged (`state-direct-recovery.ts`'s passthrough was already a
  bare `return`; no hand-built object to update).

  **The scheme split, named explicitly.** EIP-3009 and erc7710 disagree
  about which of these four addresses a merchant calls "the payer" —
  confirmed by reading both settlement paths, not assumed:
  `modules/x402/x402-delegation.ts:211` (`delegator: delegateAccountAddress`)
  for erc7710; for EIP-3009 there is no backend header builder — the
  `transferWithAuthorization` header is signed CLIENT-SIDE by the agent's
  delegate key (`packages/sdk/src/x402.ts:~834,853`), and its `from` is the
  delegate EOA, not the treasury. On the 3009 bridge the treasury is one
  transfer EARLIER: the budget delegation funds the delegate EOA (treasury →
  delegate, the funding leg), and the delegate then signs the
  merchant-visible `transferWithAuthorization` (delegate → merchant). So
  `treasury_account` means the same thing on both schemes — the account the
  funds LEFT Haven's custody model from (`machine_payment_evidence.payer_address`,
  written from `intent.account_address` at settlement,
  `modules/mpp/evidence.ts`) — but the merchant-visible `from` differs: it
  equals `parties.delegate` on EIP-3009 and `parties.delegate_account` on
  erc7710. Tests on both surfaces name both values for both schemes
  (`openapi/party-characterization.test.ts`; `routes/__tests__/machine-payments.test.ts`
  covers the erc7710 receipts case explicitly, alongside the eip3009 and
  status cases it already had).

  **`delegate_account`: persisted at authorize time, not derived live.** It
  is written into `payment_intents.machine_metadata.delegate_account_address`
  on BOTH delegation-rail authorize legs (`modules/x402/delegation-authorize.ts`
  — the erc7710 leg already computes `delegateAccountAddress` for the
  settlement child, and the eip3009 leg already computes it for the funding
  UserOp), the same JSONB column `settlement_scheme` already lives on. The
  receipts list, status read, and payment-receipt bundle all read it back off
  `machine_metadata` (no RPC, no extra query beyond the column already
  selected). It is null only for rows authorized BEFORE #2960 shipped, and on
  the legacy rail, where no such account exists — not a permanent decision,
  a migration boundary. `GET /machine-payments/agent` remains available as a
  live derivation (`computeHybridAccountAddress`) for the agent's CURRENT
  identity, independent of any specific historical intent.

  **`parties.delegate` on receipts is the delegate that PAID, not the
  agent's current one.** `mapEvidence` originally threaded
  `AgentContext.delegate_address` in from the route — the CALLING agent's
  current delegate, which rotates on rekey. A rekeyed agent would then show
  its NEW delegate on an OLD receipt it never paid with. Fixed to join
  `payment_intents.delegate_address` in `LIST_EVIDENCE_RECEIPTS_SQL` /
  `GET_INTENT_SETTLEMENT_FIELDS_SQL` (`infra/repositories/machine-payments.ts`)
  as `intent_delegate_address` and read that in `mapEvidence` instead — the
  same intent-captured value the status surface already used
  (`payment.delegate_address` off `payment_intents`, never re-derived from
  the agent row). `routes/machine-payments.ts` no longer threads
  `agent.delegate_address` into `listReceipts`/`attachEvidenceHandler` at
  all. Null only for pre-#2055 approval-era rows that never joined to a
  payment intent.

  **Characterization first.** `packages/backend/src/openapi/__fixtures__/
  party-characterization/*.json` were recorded from a scratch worktree at
  this PR's base commit (`24a08ec3`), one erc7710 and one eip3009 fixture
  each for the receipts list and the status read (4 fixtures total), using
  the same mocked-`pool.query` harness style the sibling `p0-characterization`
  fixtures use. `party-characterization.test.ts` replays the identical
  inputs against HEAD and asserts (1) every old field is byte-for-byte
  unchanged with `parties` stripped, and (2) `parties` is present and
  correct per scheme. `p0-characterization.test.ts`'s own `payment-receipt`
  fixture (`buildPaymentReceipt`) now also carries `parties` at HEAD; its
  strip logic (`stripTwins`) is extended with one additive-only key set
  (`P2960_ADDITIVE_KEYS = new Set(['parties'])`, commented as #2960) rather
  than folded into `TWIN_KEY_PAIRS`, since `parties` has no single old-name
  sibling for `collectTwinMismatches` to compare against. The four base
  fixtures are recorded with `machine_metadata: null` (the base commit
  predates the `delegate_account_address` write), so they stay byte-identical
  and keep proving additivity — they do NOT exercise `parties.delegate_account`
  being populated. A separate HEAD-only test per scheme
  (`party-characterization.test.ts`) supplies a real `machine_metadata` with
  `settlement_scheme` + `delegate_account_address` and asserts
  `parties.delegate_account` reads it back.

  **Accounting feed.** `modules/accounting/entry.ts`'s `counterparty` was
  already, correctly, the MERCHANT (`merchant_address`) — but the feed had
  no notion of "our own side" anywhere in code before this pass: neither
  `AccountingEntry`, `AccountingEntrySourceRow` nor `ENTRY_SOURCE_SQL`
  selected `payer_address`. Added additively as `AccountingEntry
  .treasuryAccount` (same source column, `machine_payment_evidence
  .payer_address`, as every other surface's `parties.treasury_account`);
  documented and tested (`modules/accounting/__tests__/entry.test.ts`);
  `docs/operations/accounting-feed.md` states the asymmetry. No exporter
  (SIE, Fortnox) reads the new field — the merchant is what a supplier
  invoice needs — so nothing downstream changes.

  **Demo merchant.** The invoice document (`packages/demo-merchant-mcp/src/
  invoice.ts`) was the one surface quality-scan finding F1 traced to a REAL
  merchant-visible artifact: its `kopare` ("buyer") block named the payer
  address with no qualification, while the confirmation TEXT
  (`server.ts`'s pre-existing `fromDelegate` label, #1472) already
  disambiguated it. `InvoiceParams` gains `payerRole:
  'agent_delegate' | 'agent_delegate_account'`, derived from
  `payment.settlementMethod` at the one call site
  (`invoiceForPayment`); `InvoiceJson.kopare` gains an additive `roll` field
  carrying it. The SWEDISH bookkeeping render (`buildInvoiceText`, #1550's
  byte-for-byte artifact) is UNCHANGED — `roll` is never read by it. The
  ENGLISH render's header changes from an unqualified `BUYER` to `PAYER`
  plus a `Role:` line naming which party it is, and — since the treasury is
  not knowable merchant-side on either scheme (it never appears in the x402
  payload) — never calls a delegate address "the buyer." Mutation-proven:
  reverting the English render to a bare `BUYER` header fails
  `invoice.test.ts`'s dedicated guard test.

  **Authority/custody argument.** Nothing here changes who can spend, from
  what account, or under what caveat: every new field is an additive
  derivation from already-fetched rows or already-computed in-memory values
  — no new query beyond columns already read into memory
  (`payment_intents.account_address`/`delegate_address` on the status read,
  the two `machine_metadata->>` extractions and the `delegate_address` join
  on the receipts list, `machine_payment_evidence.payer_address` on the
  accounting feed — all read-only, no migration, no row write), no new chain
  read, no altered signed payload, no changed value on any existing field.
  `delegate_account_address` is written at authorize time on an intent row
  that money-path caveats never read — it rides in the same `machine_metadata`
  JSONB write the `settlement_scheme` key already made, not a new write path.
  Mutation-proven (cp-backup, diff-verified restore): (a) swapping
  `treasury_account` and `delegate` in `withParties` fails 6 tests across
  `party-characterization.test.ts`, `routes/__tests__/machine-payments.test.ts`
  and `modules/accounting/__tests__/entry.test.ts`; (b) dropping the
  `withParties(...)` call from `mapEvidence` breaks its return shape and
  fails the receipts/evidence route tests; (c) reverting the demo-merchant
  invoice's English render to a bare `BUYER` header fails `invoice.test.ts`;
  (d) reverting `mapEvidence`'s delegate source back to the threaded
  `agent.delegate_address` fails the rekey test (a rotated agent's receipt
  must still show the delegate that paid); (e) dropping the
  `delegate_account_address` write on the erc7710 authorize leg fails the
  receipts/status parties test for that leg.
  `check:api-types` is green (spec and generated `api-types.ts` back in
  sync); `lint:wire-types` is green (no new hand-built wire shape — the one
  mapper is reused everywhere).

  **Not done in this pass, and why.** The x402 authorize response's
  `sign_data.components` object is read-only reference material for this
  slice (per the issue's own file-ownership list) and is unchanged — it
  already carries `payer_account`/`safe`/`account` from #2907/#2908, and
