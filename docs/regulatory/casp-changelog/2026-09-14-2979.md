- **#2979** — Demo merchant `/mcp` now gates on its own settlement-wallet
  readiness before it will take a paid tool call, instead of only reporting
  the wallet's gas band on `GET /healthz` (#2490): the merchant issued 402
  challenges and let an agent sign a payment authorization even with the
  settlement wallet in the `fail` band, and the agent only learned settlement
  was impossible after signing — the 2026-08-17 class this closes. Every PAID
  `tools/call` now reads `SettlementClient.readiness()` (cached per server
  process for `readinessCacheMs`, default 15s) on every paid `tools/call` —
  the unpaid call that would receive the 402 challenge and the agent's signed
  retry alike, so a wallet that drains between the two is caught before
  settlement — and refuses
  with `HTTP 503 { error: 'merchant_not_ready', reason_code:
  'settlement_wallet_out_of_gas', settlements_remaining, fail_floor,
  retry_after_s }` plus a matching `Retry-After` header when the band is
  `fail`; no 402 is ever issued and nothing is ever settled on that path. The
  `warn` band and a throwing (unknown) readiness read both proceed exactly as
  before, matching `/healthz`'s existing "unknown never blocks" rule; free
  tools and the testnet-only `MERCHANT_SKIP_SETTLE_PRODUCT` QA fixture are
  exempt because neither settles anything on-chain, so a drained wallet cannot
  block a settlement that never runs. The existing merchant-fault 402 body
  (the #1517 fault-class message) additionally carries a machine-readable
  `reason_code` (`settlement_wallet_out_of_gas` / `settlement_rpc_unreachable`
  / `merchant_fault`), additive only — the existing fault-class message text
  is unchanged. On the hosted side, the SDK's `X402UnexpectedStatusError` now
  carries the merchant's response body when it parses as JSON, and
  `packages/mcp-server`'s shared MCP-probe helper (`quoteMcpToolCall`) checks
  for this specific `merchant_not_ready` shape BEFORE running its #1271
  same-origin discovery fallback — previously a 503 (or any non-402 status)
  was treated identically to a genuinely wrong endpoint, so the agent was told
  a same-origin discovery probe had failed to find a document, discarding the
  merchant's own honest, machine-readable reason entirely. Both
  `haven_quote_mcp_tool` and `haven_prepare_catalog_purchase` now report a new
  additive `AgentPaymentFailureCode.MerchantNotReady` with a
  `StopAndTellUser` `next_action` and the merchant's `reason_code` folded into
  the message, rather than a bare `API_ERROR` with no `next_action`. The x402
  wire contract on the happy path — 402 challenge shape, `PAYMENT-REQUIRED`/
  `PAYMENT-RESPONSE` headers, settlement submission — is unchanged; this is a
  new refusal path plus additive fields on two existing refusal shapes.
  Mutation-proven: removing the readiness gate re-fails the fail-band 503
  test (a 402 passes through and the payment settles); removing the
  `MERCHANT_SKIP_SETTLE_PRODUCT` exemption check re-fails the skip-settle
  HTTP-level test (it now gets refused with 503 instead of served); removing
  the fault-path `reason_code` assignment re-fails all three reason-code
  pins; and reverting the hosted-side ordering to run the #1271 discovery
  fallback first re-fails both the `haven_quote_mcp_tool` and
  `haven_prepare_catalog_purchase` `MERCHANT_NOT_READY` pins, which regress to
  the old `API_ERROR`/discovery-guidance shape. Perimeter unchanged.
