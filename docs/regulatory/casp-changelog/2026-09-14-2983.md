- **#2983** — Follow-up from the #2979 review closing the two remaining
  merchant-refusal gaps between the local and hosted MCP runtimes. First, the
  local runtime (`packages/mcp/src/tools.ts`, `haven_pay_mcp_tool`) now
  recognises the demo merchant's own `503 { error: 'merchant_not_ready',
  reason_code, settlements_remaining, retry_after_s }` capacity refusal on
  the quote path the same way the hosted server already did (#2979): it is
  reported as `AgentPaymentFailureCode.MerchantNotReady` (`next_action:
  stop_and_tell_user`, `retry_with_new_quote: true`) BEFORE the #1301
  same-origin discovery fallback runs, on both the original probe and a
  retry against a discovered endpoint. A bare 503 with no matching JSON body
  is unaffected and still falls through to the existing discovery-miss path.
  No new failure code was defined — the value is imported from `@haven_ai/sdk`.
  Second, the hosted paid-retry refusal (`MERCHANT_REJECTED_AFTER_FUNDING`,
  `deliverMerchantPayment` in `packages/mcp-server/src/tools/paid-mcp-completion.ts`)
  is now scheme-aware: on erc7710, where the signature IS the settlement
  child and there is no funding leg, a merchant refusal at this point means
  nothing moved — no delegate balance was ever created, so there is nothing
  to strand and nothing to sweep. The refusal no longer carries
  `sweep_stranded_funds` guidance or a claim of stranded delegate funds; it
  states what is true — delivery was refused, no settlement occurred, the
  agent's budget is intact, and re-quoting later is the correct recovery —
  and surfaces the merchant's `reason_code` / `retry_after_s` when its body
  is `merchant_not_ready`. The eip3009 branch is unchanged: funding is
  confirmed on-chain before this refusal on that scheme, so the delegate
  wallet genuinely may hold stranded funds, and the sweep guidance stays. No
  funds-path change: no settlement, funding, or signing logic moved — both
  fixes are refusal-reporting corrections on paths that already refused,
  bringing the wire guidance in line with what actually happened. Two
  affected tool descriptions (`haven_complete_mcp_tool`,
  `haven_settle_mcp_tool`) were updated to say the sweep guidance is
  eip3009-only; the `description-size` mean ratchet moved from 861.13 to
  867.22 bytes across 23 tools, still under the 874-byte cap.
  Mutation-proven: dropping the `merchant_not_ready` body check on the local
  runtime's quote path re-fails the negative pin (a bare 503 would then
  wrongly report `MERCHANT_NOT_READY` instead of the discovery path); removing
  the `options?.noFundingLeg` branch in `deliverMerchantPayment` re-fails the
  erc7710 paid-retry test (it regresses to sweep guidance and a stranded-funds
  claim); and reverting the discovery-miss short-circuit ordering to run
  discovery before the `merchant_not_ready` check re-fails the local runtime's
  positive pin (the merchant's own reason is discarded for a discovery-miss
  message again). Perimeter unchanged.
