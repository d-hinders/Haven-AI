- **#2998** — Machine-payment receipts (`GET /machine-payments/receipts`,
  `HavenPaymentReceipt` in the SDK) now name which of the two transactions
  `tx_hash` used to leave unlabelled. On the eip3009 bridge, `tx_hash` is
  the FUNDING transaction (the user's account → delegate, relayed by Haven) while the merchant's
  SETTLEMENT transaction, when reported, lives in
  `protocol_receipt_payload.transaction` — the 2026-08-13 receipt `dcc28fad`
  showed two different hashes with nothing on the receipt saying which was
  which. On erc7710 there is one transaction and `tx_hash` IS the settlement.
  Two additive fields resolve the ambiguity: `funding_tx_hash` (`tx_hash` on
  eip3009 and on scheme-less retired-x402-rail rows; `null` on erc7710, which
  has no funding leg, and on scheme-less retired mpp-rail rows, whose one
  transaction moved account → merchant directly) and `settlement_tx_hash`
  (`tx_hash` itself on erc7710 and on those retired mpp-rail rows; on
  eip3009, `protocol_receipt_payload.transaction` when it is a non-zero
  0x-prefixed 32-byte hash, using the same zero-hash recognizer
  (`isZeroSettlementTxHash`) the #2970 hosted gate already uses, else
  `null`). Trust level, stated on the field: on erc7710 the settlement hash
  was verified on-chain by Haven before the receipt existed; on eip3009 it
  is the merchant's claim as relayed in PAYMENT-RESPONSE, not verified
  on-chain by Haven. The existing `tx_hash` / `txHash` fields are unchanged and kept
  for wire compatibility, marked deprecated in their description only. The
  hosted `haven_list_receipts` tool passes the new fields through unchanged
  (no schema or description edit); `haven_verify_receipt` is unaffected —
  it verifies the receipt object it is given and does not branch on these
  fields. Money-path classification: this is the payments READ path only —
  `infra/repositories/machine-payments.ts` matches the runtime money-path
  glob, but the change adds derived, read-only fields to an existing receipt
  projection; no funds movement, no migration, no change to which
  transaction Haven signs, submits, or verifies on-chain. Mutation-proven:
  swapping the `funding_tx_hash` / `settlement_tx_hash` assignments in
  `deriveReceiptTxHashes` (`packages/backend/src/modules/mpp/evidence.ts`)
  re-fails the real-DB receipts-list test across all three row shapes
  (eip3009 with a merchant settlement, eip3009 without one, erc7710).
  Perimeter unchanged.
