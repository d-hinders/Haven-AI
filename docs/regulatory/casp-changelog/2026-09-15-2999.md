- **#2999** — the hosted plain-HTTP `haven_quote_x402` (the third and last
  hosted quote surface, after #2991 covered `haven_quote_mcp_tool` and
  `haven_quote_catalog_purchase`) gains the same two additive fields,
  `expected_settlement_scheme: 'erc7710' | 'eip3009' | null` and
  `expected_funding_leg: boolean | null` — plus `expected_settleable: boolean`
  when the rail is known, `false` where `haven_pay_x402_quote` will refuse to
  settle (an erc7710-only merchant next to a non-delegation account, or ANY
  merchant for a non-delegation account, since Haven's x402 entry points 410
  every retired rail before anything is written) so a predicted scheme never
  reads as "Haven will settle it". Computed by the SAME
  `selectX402SettlementScheme` selection `haven_pay_x402_quote` runs at pay
  time, reached through a new shared support helper,
  `settlementPredictionFields` (`tools/support/quote-response.ts`), so this
  quote can never predict a different settlement shape than the one its own
  pay sibling goes on to select — `buildMcpToolQuoteResponse` (the two MCP
  quote tools) is refactored onto the same helper rather than keeping a
  parallel copy of the field-and-warning shape. Before this, the plain-HTTP
  quote reported only the merchant's own `accepted_scheme`, which — exactly as
  #2991 found for the other two quote tools — can legitimately disagree with
  what pay actually selects: a merchant advertising both a standard and an
  erc7710-tagged entry quotes a delegation-rail agent `accepted_scheme:
  'standard'`, then asks it, at pay time, to sign an erc7710 settlement child
  instead. When the agent's execution rail cannot be read,
  `expected_settlement_scheme` is `null` with the same `X402_SCHEME_UNKNOWN`
  warning the other two tools already carry, rather than a guess.
  `accepted_scheme` / `erc7710_only` are unchanged — they still describe only
  the merchant's offer.

  **New network call, unlike #2991.** `haven_quote_x402` previously made no
  Haven call at all (only the merchant probe); the prediction requires reading
  the agent's execution rail, so this adds one `getAgent` read per quote,
  started BEFORE the merchant probe resolves and using the SDK's existing
  non-throwing `.then(a => a, () => undefined)` prefetch convention
  `haven_pay_x402_quote` already used. The SDK's in-flight `getAgent` dedupe
  means a `haven_pay_x402_quote` call issued while this prefetch is still
  outstanding reuses the same request rather than firing a second one, but two
  separate, sequentially-awaited tool calls (quote, then a later pay) each
  make their own read — this is a read-only account lookup, not a spend
  authority check, so the added round trip carries no money-movement risk.

  No authority change — the quote still reserves no price, creates no intent,
  and moves no funds; the fields are read-only narration of a decision pay
  makes independently and re-derives fresh regardless of what the quote
  predicted. Mutation-proven: severing the prefetched `agent` at the
  `settlementPredictionFields` call site (forcing `undefined`) fails the
  both-entries/delegation-rail, the both-entries/legacy-rail, and the
  quote-then-pay agreement tests; a second mutation flipping
  `expected_settleable` to unconditionally `true` fails the legacy-rail test
  here and the equivalent #2991 test on `haven_quote_catalog_purchase` (the
  shared helper's two callers). Both were restored after confirming red.
  Perimeter unchanged.
