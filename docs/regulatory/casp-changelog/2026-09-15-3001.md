- **#3001** — signer refusal shape, not signing logic: every throw site in
  `fetchX402SignContext` (`packages/signer/src/sign-context.ts`) — timeout,
  unreachable host, a non-ok backend response (404/410/…), a malformed body —
  now throws `HavenSignContextError`, a `HavenSigningError` subclass, instead
  of the generic prose-only refusal #2985 introduced. `normalizeError`
  (`packages/signer/src/tools.ts`) serialises it with `code`
  (`SIGN_CONTEXT_TIMEOUT` / `SIGN_CONTEXT_UNREACHABLE` / `SIGN_CONTEXT_REFUSED`
  / `SIGN_CONTEXT_MALFORMED`) and `next_action`, routed per refusal class
  (#3010 review): a transport failure or an unreadable body carries
  `fallback: 'typed_data_b64'` + `stop_and_tell_user` (the version-mismatch
  refusal's value); a backend REFUSAL carries no fallback (re-signing an
  expired, executed or unsignable intent's bytes is no remedy) plus
  `http_status` and the backend's own `backend_error_code`, with the 410
  `expired` class routed exactly as the signer already routes
  `PAYMENT_WINDOW_EXPIRED` (`next_action: payment_window_expired`,
  `retry_with_new_quote: true`) and every other class `stop_and_tell_user`
  — mirroring the version-mismatch refusal's shape. These codes
  are signer-local: distinct from, and never touching, `@haven_ai/sdk`'s
  `AgentPaymentFailureCode`, and they never reach the backend's REST/OpenAPI
  surface — only this package's MCP tool responses. `message` text is
  unchanged, `instanceof HavenSigningError` still holds for the new class, and
  the digest re-derivation / Haven-binding verification the fetched bytes go
  through afterward is untouched. No custody, key-handling, or authority
  change; the delegate key and the agent's API key are never part of a
  serialised failure (asserted directly in
  `packages/signer/src/sign-context-wire.test.ts` against the identity
  fixture's key). Mutation-tested: reverting the four throw sites to the
  original `HavenSigningError` (collapsing every code back to the generic
  `SIGNING_ERROR`) turns the new wire and unit tests red; dropping the
  `http_status` field from `normalizeError`'s serialisation does the same.
  Perimeter unchanged.
