- **#3015** — boolean environment flags refuse the boot on an unrecognised
  value instead of reading as off. `packages/backend/src/config.ts` gains
  `parseBooleanFlag(name, raw)` — unset / `null` / empty-after-trim → `false`,
  `'true'` / `'false'` accepted (trimmed), **anything else throws** naming the
  variable and quoting the offending value — and it replaces the
  `process.env.X === 'true'` comparison at all six call sites:
  `CATALOG_DISCOVERY_ENABLED`, `HAVEN_FEE_ENABLED`,
  `HAVEN_LEGACY_BOOKKEEPING_ENABLED`, `HAVEN_HOSTED`, and both names inside
  `readAccountingEnabled` (`HAVEN_ACCOUNTING_ENABLED` and the deprecated
  `HAVEN_REPORTING_FEED_ENABLED`, whose #2859 warning is unchanged). Same shape
  as `parseConnectorChannel` (#2423) and `parseAccountingEntitlementMode`
  (#2861) in the same file. **Authority/custody argument: nothing moves.**
  `config.ts` is not in `.github/money-path-globs.json`; no payment,
  delegation, allowance, relayer, signer or key path is touched, and no route,
  schema or migration changes. **One behaviour change is NOT a pure
  tightening, and is stated rather than glossed:** the parser trims, so a
  PADDED value that previously read as off now reads as on — `" true "` was
  `false` under `=== 'true'` and is `true` now. That can turn a flag ON,
  including `HAVEN_FEE_ENABLED` (`config.ts:438`), the platform-fee switch
  whose comment reads "when false the fee is always zero and no funds move".
  An earlier draft of this shard claimed the change "can never turn one on";
  that was wrong and is retracted here. Trimming is kept because it is the
  house convention the two sibling parsers in this file already use
  (`parseConnectorChannel` #2423, `parseAccountingEntitlementMode` #2861, the
  latter's suite asserting `' all '` accepted and `'ALL'` refused), and because
  a padded value is a dashboard paste artefact whose intent is not in doubt —
  unlike a different spelling. The exposure is bounded by the audit below:
  neither Railway project defines `HAVEN_FEE_ENABLED` at all, so no fee flag
  changes state on this deploy.
  **Why it exists, stated because the failure was live:** `HAVEN_HOSTED` was
  set to `TRUE` on the production backend, `'TRUE' === 'true'` is `false`, so
  `config.hosted` was false in production and `/accounting` told users of the
  hosted service that the feed "is not available on a self-hosted deployment".
  The variable was present in the dashboard, looked set, and did nothing — a
  silently-off flag is indistinguishable from a deliberately-off one, which is
  why it survived and why the same reading error produced a wrong finding on
  epic #2858 before the bytes were read. Corrected in production 2026-09-15 by
  setting the value lower-case; this change makes the next one impossible to
  miss. Case normalisation was the alternative and was **rejected by the owner
  on 2026-09-15** ("flags should fail loudly"): lower-casing fixes `TRUE` and
  still reads `1`, `yes` and `on` as off — the same defect, smaller blast
  radius. **What is mutation-tested**, each planted alone, restored from a `cp`
  backup and verified by `cmp`, counts from the scope
  `npx vitest run src/__tests__/config-boolean-flags.test.ts` in
  `packages/backend` (8 tests green at the delivered tree): replacing the
  `throw` with a silent `return false` — **6 failed / 2 passed**; replacing the
  two literal comparisons with `value.toLowerCase() === …`, i.e. shipping the
  rejected normalising alternative — **4 failed / 4 passed**, so the tests
  distinguish the two designs rather than merely asserting "some error";
  8/8 restored after each. A THIRD cell, planted after the independent review
  found the gap: reverting `config.ts`'s `hosted:` line to the pre-change
  `process.env.HAVEN_HOSTED === 'true'` — the production defect itself,
  verbatim — left `config-boolean-flags.test.ts` **8/8 green**, because that
  suite tests the pure function and nothing pinned the six call sites. A
  wiring suite on the `config-trust-proxy-wiring.test.ts` pattern (#2630) now
  exercises each variable through a real module load and asserts the import
  REJECTS, with a positive control at `'true'` so a field that stopped being
  read cannot pass; under the same revert it is **1 failed / 14 passed**. **Operator precondition, and the one risk this
  carries:** the change converts a silent-off into a boot refusal, so any of
  the six variables carrying an unrecognised value in a deployed environment
  stops the backend from starting. **For the dev backend this is a PRE-MERGE
  step, not a promotion step** — the Railway dev service deploys from the
  `dev` branch (`docs/operations/dev-environment.md`), so merging this PR *is*
  the deploy, and a bad value there reddens qa-dev with a cause that looks
  nothing like this change. The audit must also look for PADDED values, which
  flip ON rather than refusing (above). One guarantee is deliberately narrowed:
  `config.ts:450-454` promises the pre-#2859 `HAVEN_REPORTING_FEED_ENABLED`
  "is still honoured so a deployed backend keeps working across the deploy that
  carries this rename" — a deployment mid-rename carrying an unparseable value
  on that name now refuses to boot rather than degrading to off. That is the
  intended trade and the only way this change can break a working deployment.
  The repository is clean (`.env.example` and `.env.dev.example` set all four
  to lower-case `false`, and both now document the contract including the
  trim/case asymmetry). **Audit completed 2026-09-15, both Railway projects:**
  production defines only `HAVEN_HOSTED` (lower-case `true`, corrected earlier
  that day) and none of the other five; dev defines `HAVEN_HOSTED` and
  `HAVEN_ACCOUNTING_ENABLED`, both provably lower-case `true` since the
  accounting feed is available there and pushed to Fortnox that day, which
  requires both to evaluate true. Absent is accepted as `false`. Nothing in
  either environment refuses the boot. **Perimeter unchanged — no file entered or left
  `.github/money-path-globs.json`.**
