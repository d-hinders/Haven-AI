  ## Why the perimeter is unaffected

  The release changes what Haven and its agents *say about* a settlement, and
  when they refuse — never who may spend. Taking the authority-bearing changes
  one at a time:

  **`haven_report_settlement_evidence` (#2973) grants no authority.** An
  erc7710 agent hands Haven the merchant's settlement hash. That is an *input to
  verification*, not an instruction: Haven verifies it against the chain and the
  intent before a payment counts as settled, so a false or hostile report fails
  verification rather than causing a transfer. Nothing about the tool can move
  funds, mint a delegation, or alter a caveat.

  **What it does reach, which a regulatory record should say rather than stop at
  "cannot move funds":** confirming an intent triggers
  `recordMachinePaymentEvidenceBase` — book-time FX, a fee-ledger row, and the
  best-effort Fortnox accounting feed. So an agent can now push a verified
  on-chain fact into the operator's accounting surface. The chain verification is
  exactly what makes that safe: `modules/x402/settlement-observed.ts` treats the
  reported hash as CLIENT INPUT and fails closed — anything short of `verified`
  leaves the intent `submitted`, and an unreachable RPC is reported as retryable
  rather than accepted. Unverified evidence reaches no ledger.

  **"Settled means verified" (#2971) NARROWS the path.** Hosted settle/complete
  now gate on backend settlement evidence, and a payment past the window reports
  `awaiting_settlement_evidence` instead of claiming success. Combined with
  #2968 — the zero transaction hash never rides out, and an unconfirmed
  settlement never rides silently — the release removes two ways a payment could
  *appear* settled without being so. Both are fail-closed directions.

  **New refusals add refusals.** `merchant_not_ready` reaches the local runtime
  at parity with hosted (#2983, #2979), and `MERCHANT_UNRESPONSIVE_AFTER_FUNDING`
  (#3000) and `PRICE_EXCEEDS_MAX` / `INVALID_MAX_AMOUNT` (#2975) carry
  `next_action`. A refusal that did not exist before cannot widen a perimeter,
  and guidance attached to one grants nothing.

  **The party model (#2965) and the two named hashes (#2998) are vocabulary.**
  `parties { treasury_account, delegate, delegate_account, merchant }` on
  receipts and payment status, and `funding_tx_hash` / `settlement_tx_hash`
  beside the existing unlabeled `tx_hash`, name distinctions the system already
  made — the funding leg and the settlement leg of the EIP-3009 bridge were
  always different transactions, and the hot-delegate discipline in `CLAUDE.md`
  § *Security Model* already required recording the merchant address separately
  from the funding address. Naming them makes the existing separation legible;
  it does not create or merge an authority.

  **`expected_settlement_scheme` (#2991) is a prediction, not a selection.**
  Quotes now say which scheme `prepare` will pick. The backend still picks it
  from the payTo shape at prepare time; a quote that predicted wrong changes
  nothing about what executes.

  **The signer's 15-second abort (#2985) bounds a wait.** `fetchX402SignContext`
  previously hung the agent. Timing out is a refusal to proceed, never a
  decision to sign.

  ## What did NOT move

  No route gains spend authority. No caveat enforcer, delegation shape, budget
  or recipient pin changes. Haven acquires no signing capability: every
  signature in the money path is still produced by an agent-held delegate key,
  and the account's typed data is still signed verbatim. The retired Safe and
  session rails remain fail-closed at HTTP 410. No key material changes hands,
  and the `safe` → `account` compatibility window opened by 0.2.0-alpha.0 is
  **unchanged** — `safe` is still emitted, so #2914's removal has not happened
  and this release is not that cutover.

  **Published-surface compatibility, tested rather than assumed.** Against the
  published `@haven_ai/sdk@0.2.0-alpha.0` tarball, the built declarations remove
  **zero** names and add five (`EvidenceReportOutcome`,
  `HavenZeroSettlementHashError`, `PaymentParties`, `RawPaymentParties`,
  `isZeroSettlementTxHash`); the export barrel, diffed separately because the
  name extractor cannot parse it, likewise removes zero and adds three.

  **Independent review corrected this paragraph, and the correction is worth more
  than the conclusion.** A first draft said "the one changed interface body is
  `PaymentReceipt.payment`". That is false: several bodies changed, and the one
  that matters most was not named. Measured:

  - `HavenPaymentReceipt` gains **two NON-optional fields**, `fundingTxHash:
    string | null` and `settlementTxHash: string | null`, plus optional
    `parties?`, and `txHash` gains a `@deprecated` tag.
  - `AgentPaymentSummary` gains optional `parties?`.
  - `MerchantCompletion` gains `evidenceOutcome?` and the method
    `reportSettlementEvidence`.
  - `X402UnexpectedStatusError`'s constructor gains an optional third parameter.
  - `PaymentReceipt.payment` gains optional `parties?`, keeping `safe` and
    `account?` unchanged.

  **Why the conclusion survives anyway:** `HavenPaymentReceipt` occurs only in
  return position (`Promise<HavenPaymentReceipt[]>`), so adding a required field
  cannot break a caller — a reader receives the field, never constructs one.

  **Two exported unions DID widen, and a blanket "nothing narrowed" would be
  wrong.** `AGENT_PAYMENT_NEXT_ACTION_VALUES` gains
  `"awaiting_settlement_evidence"` and `AGENT_PAYMENT_FAILURE_CODE_VALUES` gains
  `"MERCHANT_NOT_READY"`. Since `AgentPaymentFailureCodeDescriptions` is typed
  `Record<AgentPaymentFailureCode, string>`, a consumer building their own such
  record, or writing an exhaustive `switch` with a `never` check, stops
  compiling. That is a **compile-time-only source break**, no runtime behaviour
  change for existing values, no value removed — but it is a break, it is named
  in the five package CHANGELOGs shipped with this release, and the accurate
  claim is "no EXISTING field became required", not "no field became required".

  **One published-surface gap, recorded rather than fixed here.**
  `PaymentParties` is declared but **not re-exported from the SDK barrel**, so
  the type named by the two new `parties` fields cannot be imported by name. The
  fields are structurally usable. This is #2965's defect and this release is what
  publishes it; a release commit is the wrong place to change a published source
  surface, so it is stated in the SDK CHANGELOG as a known gap and left to its
  own change.

  **The 0.2.0 compatibility window is EXTENDED, not closed, and the prior shard
  said otherwise.** `casp-changelog/2026-09-14-0.2.0-alpha.0-release.md` states
  the old names are "removed by #2914, one release AFTER this one". This is that
  release and the removal did not land — verified with the closing-keyword
  instrument over `origin/main..origin/dev` (no match) rather than a bare grep.
  So the window now extends past 0.2.1-alpha.0, and the published `@deprecated`
  JSDoc — "removed in #2914 (the release after the naming window)" — is now
  pointing at a release that has shipped without the removal. A consumer reading
  that tag on 0.2.1-alpha.0 could conclude `safe` is gone; it is not. The JSDoc
  wording is a published source surface and is therefore NOT edited in this
  release commit; it needs its own change before it misleads further.
