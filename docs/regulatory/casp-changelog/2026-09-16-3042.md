- **#3042** — the hosted MCP's two erc7710 branches
  (`haven_pay_mcp_tool` and `haven_prepare_catalog_purchase` in
  `packages/mcp-server/src/tools/catalog-purchase.ts`) never forwarded the
  caller's `idempotency_key` to the authorize, while their EIP-3009 siblings
  always did and the backend has deduplicated on the key since the delegation
  rail shipped (`findX402IntentByIdempotencyKey` before the shape branch,
  insert with `conflictTarget: 'x402_idempotency_key'`). Measured live on dev
  2026-09-16 (scan B2): four prepares of one catalog entry, two with the same
  explicit key, minted four independently signable settlement children. On
  this scheme the signed child IS the spend authority — a retried prepare +
  sign would be a second payment inside the budget the owner delegated, which
  is the #2041 defect class that reached `plain-http-x402.ts` only. Both
  branches now forward the caller's key exactly as #2041 did there —
  explicitly given keys only, NOT the EIP-3009 branches' `?? quote` fallback:
  on the MCP quote path that fallback is a 5-minute-bucket key the SDK
  derives without the tool arguments, and forwarding it would have switched
  deduplication on for every unkeyed call (a `submitted` child answering 409
  for the rest of the bucket; two different arguments at one price
  colliding). So a keyed retry replays the first child while it is still
  pending; without a key the behaviour is unchanged (one child per call —
  the auto-generated-key design is scan F3, not this). No change to what is
  signed, to the caveats the signer verifies, or to the budget enforcement.
  Mutation-tested per branch: dropping the key, or substituting the 3009
  fallback, reddens that tool's own test alone. Perimeter unchanged.
