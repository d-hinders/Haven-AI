  ## Why the perimeter is unaffected — and narrower

  A contraction removes ways to be understood; it grants nothing. Every change
  moves the same direction:

  **Retired paths answer 410 with a typed body, not 404.** A deleted Fastify
  route is a bare 404, which is indistinguishable from a typo; the tombstone
  names its replacement. Refusing is not a new authority.

  **Retired request names are refused with 400, not ignored.** An ignored field
  is indistinguishable from one never sent — the reason #2914 required refusal
  rather than deletion. A client that sends `safeId` is now told to send
  `accountId`; it is not silently interpreted. **This narrows what the server
  accepts**, which cannot widen a spend perimeter.

  **The next-action enum flips and stops accepting the old value on input.**
  Emission moves to `fund_account_or_raise_allowance`; the old value is rejected
  rather than mapped. Again: fewer admissible inputs, not more.

  **No authority, custody or execution change whatsoever.** No caveat enforcer,
  delegation shape, budget, recipient pin or expiry is touched. Haven gains no
  signing capability: every money-path signature is still produced by an
  agent-held delegate key over the account's typed data, verbatim. The retired
  Safe and session rails remain fail-closed at 410. No migration is in this
  slice, and no key material changes hands.

  ## The two response twins that deliberately SURVIVE this release

  Recorded here because a regulatory reader should not have to infer it from
  the absence of a claim. `GET /user/accounts` still emits the `safes` envelope
  key beside `accounts`, and the `GET /transactions` feed still emits
  `safeName` beside `accountName`. Both are declared `deprecated` in the spec.

  The reason is a consumer-safety one, owner-approved as a scope narrowing on
  #2914: `@haven_ai/cli@0.2.1-alpha.0` — what `latest` resolved to before this
  release — destructures `{ safes }` at five call sites and renders its ACCOUNT
  column from `t.safeName`. A published client cannot dual-READ. Contracting
  those two now would break a `latest` install **with no bounded end**, because
  the backend deploys from a branch while the packages publish on the later
  promotion, and per `CLAUDE.md` that promotion can go **half green** —
  published, with `latest` unmoved.

  The removal condition is written at the call site
  (`packages/backend/src/middleware/retired-safe-names.ts`): delete both helpers
  and their two call sites **in the release after this one**, once
  `npm view @haven_ai/cli dist-tags` shows `latest` at or past 0.3.0-alpha.0.
  This release is what makes that condition true — the fixed CLI, which reads
  `accounts`/`accountName` and fails loudly against an old server, publishes
  here. Keeping two deprecated aliases for one release is a compatibility
  decision, not a perimeter one: both are read-only projections of a value the
  response already carries under its new name, and neither is an input.

  Perimeter unchanged, and the accepted surface is strictly smaller.
