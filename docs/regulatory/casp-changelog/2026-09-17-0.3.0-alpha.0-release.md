- **0.3.0-alpha.0 release** — **the naming-P5 contraction reaches npm: the
  compatibility window 0.2.0-alpha.0 opened is closed, an old client now fails
  loudly and typed, and seven published declarations are removed. No custody,
  signing or execution boundary moves, and every change is in the
  fail-CLOSED direction.** Cut against `origin/main` (`92beaadd`); the
  promotion range is 13 commits (`origin/main..origin/dev`, `9d200212`), one of
  which touches a published package.

  **Shipped delta, measured: 27 files, +272/-377** — a net DELETION, which is
  what a contraction should look like — read out of `dist/` by
  `npm run release:scope` after a full build, which resolves each source file
  through the bundle sourcemaps and the `files` field rather than trusting a
  `--stat`. It excluded 335 files: 303 outside a published package, 27 test
  files unreachable from any bundle entry, 5 inside a package but outside the
  tarball. Measured at `origin/dev` before this release commit;
  **re-measure at the promotion door.**

  **A MINOR bump, and the version carries the argument.** Against the published
  `@haven_ai/sdk@0.2.1-alpha.0` tarball, the built declarations remove **seven**
  names and add **none** — `AgentPaymentNextActionAccountAlias`,
  `AgentPaymentNextActionWire`, `accountAddressTwins`,
  `canonicalAgentPaymentNextAction`, `isFundAccountOrRaiseAllowance`,
  `readAccountAddress`, `readAccountId` — and **all seven** are also gone from
  the export barrel, diffed separately because the name extractor cannot parse
  it. (A first draft of this shard said six: seven names span six diff hunks,
  and the count was taken from the hunks.) 0.2.0-alpha.0 was MINOR for carrying
  a break; this carries a larger one.

  **State the instrument's reach, because it is narrower than the break.** That
  diff compares exported declaration NAMES, so it cannot see a field removed
  from a type that still exists — and three other published packages have
  exactly that, which no name-level count would show:

  | package | member removed |
  |---|---|
  | `signer` | `SignerCredentials.safeAddress?` |
  | `mcp` | `HavenCredentialFile.safeAddress?`, plus two `safeAddress?` fields renamed to `accountAddress?` |
  | `connect` | `AgentIdentity.safe_address: string \| null`, and `account_address` narrowed from optional to required |

  At the NAME level those three packages and `cli` are unchanged (0 removed,
  0 added), so the MINOR call rests on the SDK alone — but the break a consumer
  meets is wider than "seven declarations in one package".

  ## Why the perimeter is unaffected — and narrower

  A contraction removes ways to be understood; it grants nothing. Every change
  moves the same direction:

  **Retired paths answer 410 with a typed body, not 404.** A deleted Fastify
  route is a bare 404, which is indistinguishable from a typo; the tombstone
  names its replacement. Refusing is not a new authority.

  **Retired request names are refused with 400, not ignored.** An ignored field
  is indistinguishable from one never sent — the reason #2914 required refusal
  rather than deletion. A client that sends `safeId` is now told to send
  `accountId`; it is not silently interpreted. **This narrows what the server
  accepts**, which cannot widen a spend perimeter.

  **The next-action enum flips — and the first draft of this shard got the
  mechanism wrong, which matters in a regulatory record even though the verdict
  survives.** It said the old value "is rejected rather than mapped" on input.
  There is no input to reject on: `openapi/spec.ts` says at the enum itself,
  *"No route takes this as request input — it is a response-only enum."* What
  actually went is the SDK's CLIENT-SIDE normaliser
  (`canonicalAgentPaymentNextAction`), which mapped the new value back to the
  old one while READING a response, together with `isFundAccountOrRaiseAllowance`.

  So the honest statement is: emission moves to
  `fund_account_or_raise_allowance`, and the SDK stops translating for you. A
  response-only enum cannot widen a spend perimeter — that conclusion holds, and
  is why this is not a perimeter event. But the consumer consequence is real and
  is NOT a narrowing: a 0.3.0 SDK against a pre-0.3.0 server now passes
  `fund_safe_or_raise_allowance` through as an unrecognised `nextAction`, and a
  consumer that branched on `isFundAccountOrRaiseAllowance` loses that branch
  silently. Recorded because "fewer admissible inputs" would have been a
  comforting sentence that no code backs.

  **No authority, custody or execution change whatsoever.** No caveat enforcer,
  delegation shape, budget, recipient pin or expiry is touched. Haven gains no
  signing capability: every money-path signature is still produced by an
  agent-held delegate key over the account's typed data, verbatim. The retired
  Safe and session rails remain fail-closed at 410. No migration is in this
  slice, and no key material changes hands.

  ## The two response twins that deliberately SURVIVE this release

  Recorded here because a regulatory reader should not have to infer it from
  the absence of a claim. `GET /user/accounts` still emits the `safes` envelope
  key beside `accounts`, and the `GET /transactions` feed still emits
  `safeName` beside `accountName`. Both are declared `deprecated` in the spec.

  The reason is a consumer-safety one, owner-approved as a scope narrowing on
  #2914: `@haven_ai/cli@0.2.1-alpha.0` — what `latest` resolved to before this
  release — destructures `{ safes }` at five call sites and renders its ACCOUNT
  column from `t.safeName`. A published client cannot dual-READ. Contracting
  those two now would break a `latest` install **with no bounded end**, because
  the backend deploys from a branch while the packages publish on the later
  promotion, and per `CLAUDE.md` that promotion can go **half green** —
  published, with `latest` unmoved.

  The removal condition is written at the call site
  (`packages/backend/src/middleware/retired-safe-names.ts`): delete both helpers
  and their two call sites **in the release after this one**, once
  `npm view @haven_ai/cli dist-tags` shows `latest` at or past 0.3.0-alpha.0.
  This release is what makes that condition true — the fixed CLI, which reads
  `accounts`/`accountName` and fails loudly against an old server, publishes
  here. Keeping two deprecated aliases for one release is a compatibility
  decision, not a perimeter one: both are read-only projections of a value the
  response already carries under its new name, and neither is an input.

  **A THIRD retired response name survives, and it is not one of the two.**
  `GET /transactions/filters` still returns a `safes` envelope key
  (`routes/transactions.ts`), and unlike the two twins it is **not** marked
  `deprecated` in the spec and is in that response's `required` list. It is not
  a *twin* — there is no `accounts` beside it — so "nothing else is twinned"
  stands, but `retired-safe-names.ts`'s sentence that the contraction "removes
  the retired names from every RESPONSE, and for every name but two that is
  safe" is contradicted by its own tree, and so was this shard's first draft.

  **Why it is not a perimeter concern, and not fixed here.** Its only consumer
  is the dashboard frontend, which deploys from the same branch as the backend —
  no published package reads it, so the bounded-end argument that kept the two
  twins does not apply to it. `packages/frontend/src/types/transactions.ts` says
  the key "stays `safes` until #2914 retires it"; #2914 is this release and it
  did not. That is a gap in #3075, not in this bump, and a release commit is the
  wrong place to widen. Its natural home is the follow-up release that removes
  the two twins.

  Perimeter unchanged, and the accepted surface is strictly smaller — with the
  three survivals above named rather than implied.
