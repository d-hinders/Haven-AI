- **#2914 follow-up** — the last four retired RESPONSE names leave the wire.
  **Perimeter unchanged** — no new authority, no new signing path, no change
  to who may move funds, no migration, and nothing added to any response.
  This is a deletion. **No file in this diff is on
  `.github/money-path-globs.json`** — measured with the repo's own matcher,
  0 of 25 changed files match `globs` ∪ `controlGlobs`, and the only
  middleware entry on that list is `agentAuth.ts`. So this shard is written
  VOLUNTARILY, and that strengthens the perimeter argument rather than
  weakening it: the removal does not reach money-path code at all. It is
  recorded because #2914 has a shard and this release is the second half of
  the removal that shard SCHEDULED — a record that describes a pending
  deletion and then goes silent when it happens is worse than no record. An
  earlier draft of this shard claimed the diff matched the money-path globs;
  independent doc review measured it and it does not.

  **What is removed, and the asymmetry that governs it.** #2914 contracted
  the Safe vocabulary out of the wire but left three retired response names
  standing:

  | name | why it survived #2914 | removed because |
  |---|---|---|
  | `safes` envelope on `GET /user/accounts` | `@haven_ai/cli@0.2.1-alpha.0` destructured it at five call sites | `latest` is 0.3.0-alpha.0, whose `accountsEnvelope()` reads `accounts` |
  | `safeName` on the `GET /transactions` feed | the same CLI rendered its ACCOUNT column from it | same |
  | `safes` on `GET /transactions/filters` | never twinned — missed, found in independent review | never read by any published package; the dashboard is its only consumer |
  | `safe_tx_hash` on `GET /agent-connection-setups/{id}`'s `approval` | never noticed at all — found by the new spec sweep, in this change | migration 084 renamed the column to `account_tx_hash`; the emit kept the old spelling, so the name outlived the epic by reading the new column through the old key |

  The first two were deliberate one-release twins. The reason they needed a
  window at all is the asymmetry this epic keeps running into: #2908 told
  published clients to dual-SEND, and a request can be sent twice — but a
  response cannot be READ twice, so a published client cannot protect itself
  against a removed response key. That is why the retired REQUEST names are
  still refused with a 400 naming the replacement, and the `/user/safes*`
  TOMBSTONE PATHS are still 410: a path is what an old client types. Only the
  response BODIES contracted.

  **The removal condition was written, not remembered.** It lived at the call
  site in `packages/backend/src/middleware/retired-safe-names.ts` as an
  executable sentence: remove in the release after #2914's, once
  `npm view @haven_ai/cli dist-tags` shows `latest` at or past that release.
  It named `latest` rather than `alpha` deliberately, because a bare
  `npx @haven_ai/cli` resolves `latest`. On 2026-09-17 the 0.3.0-alpha.0
  promotion published and moved `latest` for all five packages, verified
  against the registry directly rather than from a green workflow — CLAUDE.md
  records that a promotion can be half green (published, `latest` unmoved),
  and this condition is exactly the kind that a half-green promotion would
  have falsified while CI looked fine.

  **One skew window, stated plainly rather than claimed away.** The third
  name is not a twin removal but a rename (`safes` → `accounts`), and the
  dashboard reads it. Backend and dashboard deploy from the same promotion but
  not in the same instant, so there IS a window, and it is worse than a blank
  control: a dashboard bundle built before this change sets `safes` from an
  absent key and then calls `.map` / `.find` on it unconditionally during
  render (`useTransactionFilters.ts`, `TransactionsClient.tsx`,
  `FilterBar.tsx` at base `c587ca88`), so the whole transactions screen
  THROWS, and the same value feeds `accountNamesById` behind the rows and the
  export — not one dropdown. A first draft of this shard called it cosmetic
  and confined to a dropdown; independent doc review read the pre-change
  bundle and it is neither.

  What still distinguishes it from the published-CLI break is not severity but
  BOUNDEDNESS. This window closes when the dashboard finishes deploying from
  the same promotion, and the next load recovers. The CLI break had no bounded
  end at all: the backend deploys from a branch while packages publish on the
  later promotion, that promotion can be half green, and a bare
  `npx @haven_ai/cli` resolves `latest`. That is what earned the twins a
  release and this rename none — an unbounded break, not a louder one. A
  retroactive `?? []` in the old bundle is not available, so saying this
  plainly is the only fix available.

  **Custody and authority, re-checked.** No signed payload moves: none of the
  three names appears in any signed x402 expected-context, in a consent hash
  input, or in a delegation caveat. `SUPPORTED_X402_EXPECTED_VERSIONS` is
  untouched, so no installed signer fails closed across this change. The
  ownership scope is untouched — every query behind these three responses is
  still scoped to the caller's `user_id` (the two list queries bind it as
  `$1`; the x402 legs behind `GET /transactions` bind it as `$2` alongside an
  account-id `ANY(...)`, which is the same property written differently).
  The fourth name is the same: `account_tx_hash` carries the identical value
  the old key did, off the same column. Removing a response key cannot widen
  a query;
  the case where a retired name COULD widen one is a request filter, and
  those are refused rather than ignored precisely for that reason.

  **What now prevents a fourth.** The two twins were each pinned by a test
  that knew about that one shape. The filters key was pinned by NONE — no
  test named `TransactionFilterOptionsResponse.safes` and the route had no
  request-level test at all — which is how it survived a slice that believed
  it had removed everything.

  The sweep is a PATTERN, not a list of the names being retired here, and
  that distinction was earned rather than assumed: independent review
  mutation-tested a first draft that used a five-name denylist, injected a
  plausible new name (`safeChainId`) and watched it pass silently. The
  widened pattern then immediately found the fourth name above — a real
  defect, in code neither review was looking at, on its first run. One
  deliberate exception remains and is asserted exactly rather than merely
  allowed: the two `safe_id` REQUEST properties stay declared so the handlers
  can refuse them, and a separate test fails if either is ever actually
  deleted, so the allowance cannot silently outlive its subject. This change adds a
  property-level sweep over the whole served spec
  (`packages/backend/src/openapi/retired-response-names.test.ts`) and the
  first request-level test `GET /transactions/filters` has ever had
  (`routes/__tests__/transactions-filters.test.ts`). The sweep is a
  property-NAME walk, not a string search over the JSON, because the
  tombstone paths and their 410 prose must keep the old vocabulary forever.

  **Evidence.** Backend 2970 tests green and frontend 2116 green at the
  reviewed head, plus the naming census (750 surviving hits, all allow-listed,
  with two ceilings tightened as the twins left). The spec sweep is
  mutation-tested in both directions: re-adding each of the four removed names
  reddens it, and so does deleting either refusal-declared request field. The
  one backend failure is the on-chain enforcer probe, which cannot reach
  `sepolia.base.org` through this sandbox's egress and says of itself that it
  is a transport failure, not a policy failure; no enforcer code is in this
  diff. `Perimeter unchanged.`
