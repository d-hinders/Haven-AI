- **#2914 follow-up** — the three retired RESPONSE names leave the wire.
  **Perimeter unchanged** — no new authority, no new signing path, no change
  to who may move funds, no migration, and nothing added to any response.
  This is a deletion. Recorded here because the convention is one shard per
  money-path change and the diff matches `.github/money-path-globs.json` on
  `middleware/**` and `routes/payments.ts`'s sibling feed routes; #2914 itself
  has a shard, and this release is the second half of the change that shard
  describes, so the record would break if the removal it scheduled were
  silent.

  **What is removed, and the asymmetry that governs it.** #2914 contracted
  the Safe vocabulary out of the wire but left three retired response names
  standing:

  | name | why it survived #2914 | removed because |
  |---|---|---|
  | `safes` envelope on `GET /user/accounts` | `@haven_ai/cli@0.2.1-alpha.0` destructured it at five call sites | `latest` is 0.3.0-alpha.0, whose `accountsEnvelope()` reads `accounts` |
  | `safeName` on the `GET /transactions` feed | the same CLI rendered its ACCOUNT column from it | same |
  | `safes` on `GET /transactions/filters` | never twinned — missed, found in independent review | never read by any published package; the dashboard is its only consumer |

  The first two were deliberate one-release twins. The reason they needed a
  window at all is the asymmetry this epic keeps running into: #2908 told
  published clients to dual-SEND, and a request can be sent twice — but a
  response cannot be READ twice, so a published client cannot protect itself
  against a removed response key. That is why the retired REQUEST names are
  still refused with a 400 naming the replacement, and the `/user/safes*`
  TOMBSTONE PATHS are still 410: a path is what an old client types. Only the
  response BODIES contracted.

  **The removal condition was written, not remembered.** It lived at the call
  site in `packages/backend/src/middleware/retired-safe-names.ts` as an
  executable sentence: remove in the release after #2914's, once
  `npm view @haven_ai/cli dist-tags` shows `latest` at or past that release.
  It named `latest` rather than `alpha` deliberately, because a bare
  `npx @haven_ai/cli` resolves `latest`. On 2026-09-17 the 0.3.0-alpha.0
  promotion published and moved `latest` for all five packages, verified
  against the registry directly rather than from a green workflow — CLAUDE.md
  records that a promotion can be half green (published, `latest` unmoved),
  and this condition is exactly the kind that a half-green promotion would
  have falsified while CI looked fine.

  **One skew window, stated plainly rather than claimed away.** The third
  name is not a twin removal but a rename (`safes` → `accounts`), and the
  dashboard reads it. Backend and dashboard deploy from the same promotion
  but not in the same instant, so during that window a dashboard bundle built
  before this change sees no account list in the transactions filter bar. It
  is cosmetic, self-healing on the next load, and confined to one dropdown —
  a different class from the published-CLI break the twins were protecting
  against, which would have thrown on every `wallets list` with no bounded
  end. That difference is the whole reason the twins got a release and this
  rename did not.

  **Custody and authority, re-checked.** No signed payload moves: none of the
  three names appears in any signed x402 expected-context, in a consent hash
  input, or in a delegation caveat. `SUPPORTED_X402_EXPECTED_VERSIONS` is
  untouched, so no installed signer fails closed across this change. The
  ownership scope is untouched — every query behind these three responses is
  still `WHERE user_id = $1`. Removing a response key cannot widen a query;
  the case where a retired name COULD widen one is a request filter, and
  those are refused rather than ignored precisely for that reason.

  **What now prevents a fourth.** The three names were each pinned by a test
  that knew about that one shape, which is how the filters key survived a
  slice that believed it had removed everything. This change adds a
  property-level sweep over the whole served spec
  (`packages/backend/src/openapi/retired-response-names.test.ts`) and the
  first request-level test `GET /transactions/filters` has ever had
  (`routes/__tests__/transactions-filters.test.ts`). The sweep is a
  property-NAME walk, not a string search over the JSON, because the
  tombstone paths and their 410 prose must keep the old vocabulary forever.
