- **#2914** — Naming epic #2906, phase 5: the CONTRACTION. The Safe
  vocabulary leaves the wire. **Perimeter unchanged** — no new authority, no
  new signing path, no change to who may move funds, and no migration. What
  moves is naming, plus two new refusal classes and eight 410 addresses (seven under
  the `/user/safes*` prefix plus `PUT /user/safe`), all
  of which narrow rather than widen. Recorded here because the convention is
  one shard per money-path change and this diff matches
  `.github/money-path-globs.json` on `infra/repositories/**`,
  `middleware/agentAuth.ts`, `modules/mpp/**`, `modules/x402/**`,
  `routes/payments.ts`, `routes/machine-payments.ts`,
  `routes/agent-connection-setups.ts`, `packages/mcp-server/src/**` and
  `packages/signer/**`; phases 1–4 each have a shard, including #2913 which
  was frontend-only, so phase 5 is the point at which the record would have
  broken had it been skipped. An earlier draft of this PR argued no shard was
  needed because nothing moved; independent doc review was right that "no
  perimeter move" is a shard's CONTENT, not its exemption.

  **Custody and authority, unchanged and re-checked.** No signed payload
  moves: `sign_data.components.safe` is removed, but `components` is response
  METADATA and never part of the signed x402 expected-context, and
  `SUPPORTED_X402_EXPECTED_VERSIONS` stays `[1, 2, 3]`
  (`naming-window-no-version-change.test.ts` beside the untouched
  `version-skew.test.ts`, green in the signer's 210/210) — so no installed
  signer fails closed across this change. The consent hash does not move
  either: it takes the resolved ADDRESS, not the key it arrived under.
  Verified by running the pre- and post-rename sources against identical
  input: the digest is byte-identical across the rename on both sides, mcp
  `c9bf60085df62823` against the fixture at the top of
  `packages/mcp/src/consent.test.ts`. The signer side is pinned by
  `packages/signer/src/consent.test.ts` rather than by a digit quoted here —
  an earlier draft quoted one that reproduced from no fixture, and a hash a
  reader cannot re-derive is worse than none. The structural argument is what
  carries the claim and it is checkable in four lines: only the property NAME
  changed in `signer/src/consent.ts` and `mcp/src/consent.ts`, the hashed
  material is the resolved address VALUE, so equality across the rename is
  forced. An acknowledgement given before this release stays valid.
  `components.account` still means the DELEGATE account address and is
  deliberately NOT merged with `payer_account`, which carries the account the
  payment is drawn from; merging them would make the SDK's receipt-payer read
  resolve to the wrong address.

  **The two refusal classes, and why they refuse on RELIANCE rather than
  presence.** `?safeId=` and the `safe_id` body field stay DECLARED so they
  can be refused with a typed 400 naming the replacement. Deleting them would
  not make them errors — Fastify drops an undeclared key in silence, and the
  failure is money-shaped in both directions: an ignored filter returns EVERY
  row the user owns instead of one account's, and an ignored account id
  creates an UNLINKED agent that looks successfully created until a payment
  has nothing to spend from. The first cut refused on presence, which would
  have 400'd `activity list`, `activity export` and `agents connect` for
  every client that followed #2908's own instruction to dual-send both names
  — `@haven_ai/cli` on `latest` is exactly such a client. The verdict now
  keys on what the caller relies on: retired name alone refuses, both with
  the same value is accepted, both disagreeing refuses. An unmigrated client
  still fails loudly and typed; a migrated one is not punished for migrating,
  and the release-ordering constraint the presence check would have imposed
  does not arise.

  **Retired addresses.** The `/user/safes*` prefix and `PUT /user/safe`
  answer 410 with `replacement` as a field, behind `authMiddleware` so an
  anonymous caller gets 401 and never learns which paths this deployment used
  to serve (asserted, not assumed). Three of those replacements are
  themselves 410 from the Safe-rail inflow closure (#1984), so those bodies
  say the operation is closed and name `POST /accounts/hybrid` rather than
  sending a caller in a circle. `{safeAddress}` path segments got no
  tombstone deliberately: a single dynamic segment has no wire-visible name,
  so the old and new spellings were always the same route.

  **Correction to #2913's shard, which cannot be edited.** That entry records
  the one-time `haven_active_safe_id` → `haven_active_account_id` migration
  as "selection preserved". This slice deletes that migration, per its own
  planned removal at #2914, so the claim no longer holds: a returning user
  whose browser still carries the pre-#2913 key loses their remembered
  account SELECTION — not their account, not their funds — and falls back to
  the default on next load. Nothing about custody, authority or balances is
  affected; the exposure is that a transfer or receive flow opens pointed at
  the default account rather than the last-chosen one, which the UI displays
  before any action. Recorded here because the rule is that a claim made
  stale by a later change is corrected in the NEW shard and the old one stays
  untouched.

  **Operator consequences.** `HAVEN_WALLET_ADDRESS` and `HAVEN_SAFE_ADDRESS`
  are no longer read; `HAVEN_ACCOUNT_ADDRESS` is the only env name, and a
  machine configured through either old variable resolves no account address
  — which is the condition under which the signer's sweep-destination check
  degrades to "no local value to compare against". The credential-FILE
  fallbacks in `signer`, `mcp` and `connect` are PERMANENT and unchanged, as
  is the signer audit JSONL's persisted `safe_address` key: a file on disk
  never rewrites itself. The transactions CSV drops its deprecated
  `safe_address` column, shifting column indexes for an importer keyed on
  position.
