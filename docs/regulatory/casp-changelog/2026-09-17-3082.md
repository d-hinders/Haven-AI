- **#3082** — The request-validation layer was **mutating the requests it was
  only supposed to observe**, and that broke the budget-grant path on dev.
  **Perimeter unchanged** — no new authority, no new signing path, no change to
  who may move funds, no migration. What moves is that a measurement layer
  stops editing payments traffic. Recorded here because the convention is one
  shard per money-path change and this diff touches
  `packages/backend/src/openapi/request-validation.ts`, on
  `.github/money-path-globs.json` since #3029 precisely because it sits IN
  FRONT OF every payment route.

  **The defect.** `installRequestValidation` attaches the spec schema to the
  route in **shadow** mode as well as enforce, and `REQUEST_AJV_OPTIONS` sets
  `coerceTypes: 'array'`. ajv coerces **in place**, so validating a request for
  measurement rewrote the payload the handler then read. A JSON `null` became
  `""`. The plugin's own header promises shadow means "no behaviour change on
  any currently-accepted request"; that promise was false from the day it
  landed.

  Live consequence: `POST /agents/{id}/delegations/build` — the grant of an
  agent's on-chain spend authority — answered
  `400 recipient_address must be a valid address when set` for **every open
  (unpinned) budget**, because the handler's `recipient_address != null` guard
  was handed `''`. three client surfaces sent `null` and all three
  were refused: `connect-agent/DelegationApprovalStep.tsx:77` (unconditionally
  — the connect-modal approval could not complete at all),
  `hooks/useDelegationBudget.ts:242` (the hook that actually POSTs the build,
  reached from the agent-detail budget card) and `packages/cli/src/commands.ts:846`
  (`@haven_ai/cli` whenever `--recipient` is omitted). This was not a
  connect-modal-only outage.
  An unpinned budget is also the only shape the EIP-3009 bridge can use, so the
  failure fell on the standard x402 onboarding path.

  **Authority, unchanged.** This layer reads shape; it does not authorize,
  alter or construct spend intent, and that is unchanged here. No caveat
  enforcer, delegation payload, signed x402 expected-context or consent hash is
  touched. The change **narrows** what the layer does: it now observes the body
  without writing it. Nothing that was refused becomes permitted — a budget grant
  that was refused for a real reason is still refused, and the enforcers remain
  the only spend control.

  **Scope of the fix, and what deliberately stays.** The body is snapshotted
  before validation and restored after it, for shadow routes only. Querystring,
  params and headers are deliberately **not** restored: they arrive as strings
  on the wire, coercion is what makes a typed spec parameter usable, and the
  handler is meant to see the coerced value (pinned by the `limit=10` case in
  `openapi/__tests__/request-validation.test.ts`). **Enforce mode still coerces
  the body** — deliberate and visible, because an enforced route answers on the
  validation result, so the coerced value is part of a contract a client can
  see and test rather than a silent edit made while claiming to measure. Epic
  #3028 slices 2–4 flip modules to enforce one at a time and should read that
  note before each flip.

  **New operator-visible surface.** The same snapshot now also measures
  divergence: a body that coercion alone made valid raises no would-refusal
  yet would reach the handler differently once enforced, so it is logged as
  `request_validation.would_coerce` and counted under `wouldCoerce` /
  `coerceByRouteField` on `GET /health/ops`. Only spec-declared property names
  are emitted, never values. The two counters are NOT mutually exclusive and
  must not be summed — one request can coerce an earlier field and be refused
  on a later one.

  Separately, `recipient_address` on the build request is now declared
  `['string', 'null']`. Its description had always said null means an open
  budget; the declaration said otherwise, and the validation layer reads the
  declaration.

  **Evidence.** The failure and the fix are both mutation-proven rather than
  asserted. With both fixes reverted, the new
  `routes/__tests__/agent-delegations.test.ts` block reproduces the production
  signature exactly: the two shadow-branch setups (`shadow`, and `enforce`
  with no matching prefix) fail on an open budget, while `off` attaches no
  schema at all and so never coerced, and a pinned budget passes in every
  setup — the defect is null-specific, and dev runs `shadow` by default.
  Removing only the restore hook turns THREE `request-validation.test.ts`
  cases red (the `would_coerce` case rides the same snapshot); removing only
  the nullable declaration turns two others red, and reverting only the
  declaration fails the genuinely-enforced setup while shadow passes — which
  is what proves the two halves are independent.

  A correction to this shard's own first draft, recorded rather than quietly
  fixed: it claimed a `mode: 'enforce'` case proved enforcement. It did not.
  `enforced` is derived only from `prefixIsEnforced(prefix,
  enforcedPrefixes)`; `mode` gates the `off` early-return and the counters and
  nothing else, so a bare `mode: 'enforce'` takes the shadow branch for any
  unlisted prefix. Independent review caught it; the test now enforces via
  `enforcedPrefixes: ['/agents']`.

  Backend suite at the shipped commit: **2967 passed / 860 skipped** with
  `HAVEN_SKIP_DB_TESTS=1` — the 87 real-DB files did NOT run, so this figure
  is no evidence about the data layer, and one test *file*
  (`non-custody-onchain-enforcer.contract.test.ts`) fails in both the author's
  and the reviewer's sandbox on an unreachable RPC probe, which the harness
  itself labels a transport failure. CI runs the real-DB suites against a
  `postgres:16-alpine` service container.

  **Why the suite was green while dev was broken.** Every other app in the
  delegation route tests registers the routes alone; production registers
  `installRequestValidation` first. The gap was not a missing assertion — it
  was a test app assembled differently from the one that serves traffic. The
  new cases assemble it the production way, in all three modes.

  **Correcting #3029's shard.** `docs/regulatory/casp-changelog/2026-09-16-3029.md`
  states of this same plugin: "the plugin is a validator only — it reads the
  shape of a request the spec already governs, refuses or logs, and never
  authorizes, **alters**, or constructs spend intent". The "alters" clause was
  wrong when written, not made wrong by a later change: shadow mode was
  already rewriting request bodies in place at that commit, via the
  `coerceTypes: 'array'` option that same shard documents. Per
  `casp-changelog/README.md` § *Once merged, a shard is immutable*, the
  correction belongs in a new dated shard rather than an edit, so it is
  recorded here. What remains true of #3029's claim: no coercion ever altered
  spend INTENT — amount, token, recipient and route were never rewritten, and
  the semantic money-path refusals kept their exact position. What was false
  is the unqualified "alters": the layer did alter the payload, and the
  consequence was a refusal of legitimate traffic rather than a widened
  authority.
