- **#3117** — Haven was **rewriting the merchant's advertised x402 requirements
  before echoing them back**, so the `accepted` envelope a facilitator verifies
  against no longer described the offer the merchant made. **Perimeter
  unchanged** — no new authority, no new signing path, no change to who may
  move funds, no migration. What moves is that protocol echo data stops being
  reconstructed from Haven's own state. Recorded here because the convention is
  one shard per money-path change and this diff touches
  `packages/backend/src/modules/x402/settle.ts` and
  `packages/backend/src/modules/x402/x402-delegation.ts`, both on
  `.github/money-path-globs.json`.

  **The defect, in two places.** The SDK's `normalizePaymentOption` clamped
  `maxTimeoutSeconds` at parse time, so the advertised value was lost before it
  could be echoed. The backend's `encodeXPaymentHeader` rebuilt `accepted` from
  six scalar fields plus a re-synthesised `extra` carrying only
  `assetTransferMethod` and the trusted facilitator pins, discarding every
  other merchant `extra` key. A merchant that advertised a 1200 s
  timeout, or any `extra.name` / `extra.version` metadata, received an echo that
  did not match its own offer.

  **The fix.** The SDK parse path now retains the advertised timeout, floored
  to an integer; the signing conversion `toStandardPaymentRequirements` keeps
  its existing `clampAuthorizationWindow` cap and the #1256 forward margin, so
  the SIGNED lifetime is unchanged. Backend settlement selects the stored
  challenge option that matches the authorized intent and settlement state —
  scheme, network, the authorized amount (`maxAmountRequired ?? amount`, the
  field the SDK itself authorizes against), `payTo`, `asset`,
  `maxTimeoutSeconds`, `assetTransferMethod`, and containment of the
  facilitator pins the child is redeemable by — and echoes THAT object without
  rebuilding it.

  **Authority, unchanged.** Merchant metadata is protocol echo data, never
  authority. Selection is keyed on trusted intent and settlement state, so
  nothing a merchant writes into its 402 can change the amount, recipient, asset
  or facilitator the delegation authorizes; a merchant can only cause its own
  offer to be echoed or refused. No owner or delegate key handling, budget
  caveat, signed child delegation, relay authority or account revocation changes.
  API credentials remain identity-only. No schema migration or operator flag.

  **The change is fail-closed, and deliberately narrow about WHEN it closes.**
  `selectStoredAccepted` refuses — before submission, rather than guessing —
  only when the stored challenge carries erc7710 candidates for this network
  and none, or more than one after de-duplicating deep-equal entries (key order
  included) and preferring an exact facilitator-pin set over a merely
  containing one, matches the authorization. A challenge carrying no erc7710 candidate at all,
  like one stored empty or describing only the 3009 scheme, keeps the previous
  reconstructed echo, as do legacy intents with no stored challenge: those are
  a different trust statement, and refusing them would dead-end an intent the
  agent has ALREADY signed. The refusal answers 409 with a re-authorize
  instruction, not a retryable 502, because the same stored challenge refuses
  forever — and `POST /x402` now runs the same match at AUTHORIZE time, where a
  caller whose `maxTimeoutSeconds` or `facilitatorAddresses` disagree with the
  challenge it sent is refused with a 400 before any child is signed. The
  settle-time refusal is the backstop, not the first line. One residual is deliberate and worth stating: an advertised timeout
  can now match its echo while still exceeding the retained signing lifetime,
  which is a facilitator verification outcome and not a widened signing
  authority.

  **Evidence, mutation-proven rather than asserted.** Restoring the parse-time
  clamp turns the new `packages/sdk/src/x402-signing.test.ts` regressions red
  while the signed-lifetime assertions stay green; removing the signing cap
  instead inverts that — which is what proves the two lifetimes are now
  independent. Restoring the rebuilt `accepted` literal turns the metadata-loss
  cases in `packages/backend/src/modules/x402/__tests__/accepted-echo.test.ts`
  and `packages/backend/src/routes/__tests__/x402-delegation.test.ts` red;
  removing the mismatch refusal turns the mismatch and ambiguity cases red.
  The SDK and signer wire-format tests compare the echo against the official
  `@x402/core` matcher rather than against Haven's own expectation. The
  availability direction is pinned too, because that is where a settlement
  guard does its damage: a `maxAmountRequired`-spelled offer, a facilitator
  list the SDK filtered or re-ordered, an authorize body that pinned no
  facilitator, checksum-cased addresses, deep-equal duplicate offers and
  an empty `accepts[]` each assert a SETTLEMENT, not a refusal — every one of
  them settled before this guard existed.

  Focused suites at this head, on the real-DB harness with nothing skipped:
  SDK **86 passed** (`x402-signing.test.ts`, `x402.test.ts`), signer
  **11 passed** (`x402-wire-format.test.ts`), demo conformance **37 passed**
  (`demo-merchant-mcp/src/x402.test.ts`), backend settlement **146 passed**
  across the three x402 delegation files. No live payment was performed; the
  nightly `x402-erc7710-settle` QA leg was not run, and it posts its challenge
  fields consistently, so it could not have exercised any of the skew cases
  above. Perimeter unchanged.
