- **#3125** — receipt provenance made legible at every point of use: a
  `haven_list_receipts` receipt carries two values that read as "who paid" and
  are not the same kind of thing — `payerAddress` (Haven's own, from
  `machine_payment_evidence.payer_address`, written from the intent's treasury
  account) and `protocolReceiptPayload.payer` (the merchant's
  `PAYMENT-RESPONSE` relayed verbatim since #2092, opaque and
  merchant-controlled). In the 2026-09-18 field run the two held different
  addresses on every row read, so an agent or bookkeeping client reading
  "payer" unqualified attributes settled payments to the wrong party. The
  SDK type's doc comment (`HavenPaymentReceipt.protocolReceiptPayload`,
  modelled on the `settlementTxHash` trust-level comment) and the shared
  `listReceipts` tool description (consumed by the local MCP and composed into
  the hosted `haven_list_receipts`) now name the payload as the merchant's
  unverified claim, state that `parties.treasuryAccount` is Haven's
  authoritative payer record, and pin that anything inside the payload is not
  Haven's record; the relay site in `modules/mpp/evidence.ts` `mapEvidence`
  carries the same statement where the object is wired through. The field is
  NOT renamed, namespaced, or key-prefixed on the wire — decided, not
  defaulted: the relay must stay the merchant's object verbatim (its
  `transaction` key feeds `settlementTxHash` derivation), a prefix on the
  envelope cannot prefix the merchant-controlled keys inside it, and a wire
  rename would buy nothing but a #2907/#2914-shaped compatibility window. No
  money moves differently and no spend control changes: this is attribution
  clarity on records of already-settled payments, the reporting side of the
  non-assertion posture — Haven's facts and a third party's claims are now
  named as such where an agent reads them. Tool-description mean gate
  (#1591/#2292/#2341) re-verified at the exact delivered head: the shared
  fragment was sized to keep the hosted mean under the 874-byte cap (other
  22 descriptions untouched; the fragment trades the old "for bookkeeping"
  phrasing, subsumed by "transaction history", for the provenance
  guidance). `tool-descriptions.test.ts` pins the guidance in both the
  composed description and the type doc, so the boundary cannot be dropped
  silently.
