- **#3126** — the agent-answerable sufficiency signal: an agent could read
  only its spend AUTHORITY (`haven_get_agent`, `haven_get_allowances`,
  `POST /machine-payments/budget-precheck`) and none of those said whether
  the account HOLDS funds behind it, so a funded budget against an empty
  account was discovered only at transaction failure (field observation
  2026-09-18). **New backend read** `GET /machine-payments/balance-coverage`
  (`routes/machine-payments.ts`, orchestration in
  `modules/mpp/balance-coverage.ts`): agent auth from the route file's
  plugin-wide hook, plain GET with `token` + `amount_atomic` query params.
  The compare is `chainBalanceOf(agent.account_address) >= amount_atomic`,
  asked of the CHAIN through the #994 ChainClient port (`ethers`
  implementation — the same one the user-facing balance route keeps), and
  the amount arrives in the #1351 cap spelling on the hosted tool
  (`max_amount_human` preferred, exactly one spelling required, converted
  through the token registry's decimals — an unresolvable token or
  over-precise human amount refuses before any read). **The judgement call
  the issue required, decided deliberately: this is NOT a balance tool.**
  A constrained actor has no business reading the treasury total; a
  boolean answers the only decision an agent has (attempt the payment, or
  tell the user funds are missing). The response returns `covered:
  true/false/null` and NO balance field anywhere — pinned over the wire in
  `routes/__tests__/balance-coverage.test.ts` (the body must not even
  contain the chain's answer as a figure). `covered: null` means the chain
  read FAILED (`coverage_error` carries why) — the same honesty rule
  `x402-funding-leg.ts`'s `delegateCanFund` established (#1521): treat it
  as unverifiable, never as absence or as funded. **Naming keeps the two
  concepts apart** (#3126's binding constraint): nothing is named like the
  authority figures — no bare `remaining`, no `available`, no balance
  field; `budget_remaining_atomic` is the PERMITTED figure, from the SAME
  #1090/#1145 derivation `GET /machine-payments/allowances` reports as
  `onchain.remaining`, chain-scoped like that read, carried as context so
  an agent can compare authority against holdings without either figure
  wearing the other's name. **Rail posture** is verbatim the rail-aware
  reads: `resolveExecutionRail` first, both retired rails answer 410
  fail-closed before anything is derived, only the delegation rail
  answers. **Hosted surface**: new tool `haven_check_funds`
  (`HostedToolName`, `toolSchemas`, `toolDescriptions`,
  `STRICT_INPUT_TOOLS` — all four compile-enforced seams updated, counts
  24 tools / 22 strict pinned in `tools-contracts.test.ts`,
  `tools-registry.test.ts`, `server.test.ts`,
  `strict-tool-input.test.ts`), handler in
  `tools/state-direct-recovery.ts` delegating to the new SDK method
  `HavenClient.checkFunds` (`account-reads.ts`, camelCase shape
  `HavenBalanceCoverage`); the hosted handler never reads a chain itself —
  it asks the backend's rail-aware read, and its amount arguments reuse
  the cap contract's `readMaxAmountCap`/`humanToAtomic` verbatim so the
  two surfaces cannot drift. **Authority/custody argument**: the read
  grants no authority and moves no funds — it adds no API credential
  capability beyond reading a boolean about the caller's own account,
  holds no key, constructs no signed payload, and enforcement stays
  exactly where it was (the on-chain ERC20PeriodTransferEnforcer still
  reverts an over-budget redemption; a covered answer says nothing about
  whether a payment is within budget). The balance itself remains
  user-surface-only (`GET /balances`, owner JWT + account-ownership
  check, untouched here). The agent-facing prose states the distinction
  in the tool description (SDK `tool-descriptions.ts` fragment
  `checkFunds`, the hosted `CHECK_FUNDS_DESCRIPTION` leading with the
  same summary), the routing lines on `haven_get_allowances` /
  `haven_send` / `haven_sweep_delegate` name where funds-held questions
  go, and the shipped agent skill text (`skill-content.ts` +
  its byte-pinned frontend twin `agent-skill-bundle.ts`) documents the
  tool with its tri-state semantics so the absence of a balance tool is a
  documented decision rather than a gap. Shards: no migration; no change
  to who may spend; per-issue file touches were
  `packages/backend/src/modules/mpp/**` and `packages/mcp-server/src/**`
  (both on `.github/money-path-globs.json` `globs` since #2850/#2300), so
  this shard records the perimeter argument in place of any
  characterization-suite delta; the response-shape is pinned by
  `expectMatchesSpec` against the new `BalanceCoverageResponse` schema
  and the real-DB route suite.
