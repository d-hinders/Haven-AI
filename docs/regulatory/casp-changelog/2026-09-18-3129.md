- **#3129** — reporting only: address FORM on the transaction feed and the
  bookkeeping underlag, no change to what any record says happened. Values
  lifted out of a block-explorer response or a `payment_intents` row were
  copied through as their source gave them, and the sources disagree —
  Blockscout (Base, the default chain) returns EIP-55 checksummed addresses,
  Etherscan (Gnosis) returns them lowercase, and the columns hold a mix — so a
  single payment record carried both forms at once and the same field's form
  varied by chain. Every address on a transaction row, on the
  `/agents/{id}/activity` feed and on the accounting entry
  (`counterparty.address`, `treasuryAccount`, read by the underlag) is now
  emitted checksummed, settled at the boundary where the value enters rather
  than at each read site. `blockNumber` becomes `integer | null` on the wire:
  the x402-synthesized row is built from a payment intent, no migration
  defines a `block_number` column, and the hard-coded `0` read as block zero
  beside a hash that is a real settlement transaction. The block-number and
  timestamp parses are strict, so a partly-parseable string is `null`/`0`
  rather than its prefix. Not money-path by either half: **zero** changed
  files match a runtime or control glob in `.github/money-path-globs.json`
  (`node scripts/ci/money-path-classify.mjs`, whose self-test passes 6
  positive and 6 negative cases), and the issue carries no `money-path`
  label — only `area:backend` and `area:sdk`. The count of changed files is
  deliberately not quoted here: it moves with every rebase, while the figure
  that matters, the numerator, is zero and cannot move without a new file on
  the perimeter. No amount, counterparty, chain, timestamp,
  token, FX rate or SEK figure changes value; the underlag's fields, the CSV
  column set and the entry's shape are untouched. Every address comparison on a rendered or matched
  path already lowercased both sides, so no name resolution, dedup key, token
  filter or ledger match changes outcome — pinned by tests rather than
  asserted. One derived STRING did change and was corrected rather than
  accepted: `supplierNameFor` builds an unnamed merchant's Fortnox supplier
  name out of the address, and `findOrCreateSupplier` resolves it through a
  REMOTE `GET /suppliers?name=` filter whose case sensitivity is Fortnox's and
  cannot be pinned from this repository. Had the derived name followed the new
  casing, the first feed push after this change could have failed to match a
  merchant already booked and created a duplicate supplier in a customer's
  live accounting system; the name is now lowercased at the point it is built,
  so it is byte-identical to every supplier name already written and no longer
  moves with the address form at all. Perimeter unchanged.
