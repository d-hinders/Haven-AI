- **#3135** — The request-validation layer's per-module enforcement switch is
  re-keyed from the mount **prefix** to the route **file**, and the parameter
  resolver stops silently dropping `$ref`'d path parameters.
  **Perimeter unchanged** — no new authority, no new signing path, no change to
  who may move funds, no migration, no route's answer changed on any module
  that refuses today. Recorded here because the convention is one shard per
  money-path change and this diff touches
  `packages/backend/src/openapi/request-validation.ts`, on
  `.github/money-path-globs.json` since #3029 precisely because it sits IN
  FRONT OF every payment route.

  **Why the key had to move.** Slice 1 (#3029) flipped a module to enforcement
  through `enforcedPrefixes`, matched with `prefix === p || prefix.startsWith(p + '/')`.
  Epic #3028 then partitions the remaining modules across slices 2–4 — and the
  partition is not expressible in prefixes. `/agents` is the mount for
  `agents.ts`, `agent-delegations.ts` (slice 3), `agent-rekey.ts` and
  `agent-passports.ts` (slice 4), so listing `/agents` enforced all four at
  once; and the root prefix `''` matched every module beneath it under the
  `startsWith` arm, so listing it would have enforced the entire server. The
  option is now `enforcedModules: ['routes/contacts.ts', 'routes/merchants.ts']`,
  matched on exact equality, resolved per operation through a generated
  `(method, OpenAPI path) → route file` table
  (`packages/backend/src/openapi/route-modules.generated.ts`, 148 operations at
  `b16be14`, derived by `route-inventory.ts` from the same `index.ts`
  registration table the server reads). The table is generated and committed
  rather than derived at boot because the derivation reads TypeScript source
  and the deployed image ships only `dist/*.js`; a boot-time derivation would
  resolve nothing in production and silently un-enforce every flipped module.
  `npm run check:route-modules` (in CI beside `lint:request-schemas`) and a
  backend test both fail on a stale table — which is the control that matters,
  because a stale table misfires in BOTH directions: an added route it does not
  know is never enforced, and a MOVED route keeps its old attribution and stays
  enforced under a file nobody listed.

  **Authority, unchanged.** This layer reads shape; it does not authorize,
  alter or construct spend intent, and that is unchanged here. No caveat
  enforcer, delegation, signing surface, credential or custody boundary is
  touched. The two enforced modules are the same two before and after
  (`contacts.ts`, `merchants.ts`), reached by a different key, and no payment
  route changes mode: every module epic #3028 has not yet flipped stays in
  shadow, logging and counting only.

  **The `$ref` defect, found while re-keying and fixed here.**
  `requestSchemaForOperation` filtered parameters on `parameter.in`, which is
  `undefined` on a `$ref` node — so every `$ref`'d parameter was dropped before
  compilation. That was **40 of the spec's 134 request parameters** at
  `b16be14`, and not an arbitrary 40: every `AgentId`, `PaymentId` and
  `SetupId` path parameter, i.e. the uuid path parameters on the agent,
  payment and setup routes. Those are the money-adjacent surfaces slices 3 and
  4 flip, and a malformed uuid reaching the query instead of being refused is
  the #1464 class epic #3028 cites as demonstrated cost.

  It is fixed in this diff rather than filed because the deliverable of the
  next slice (#3030) is a shadow **reading** taken on dev, and a reading from
  an instrument that skips 30% of the request parameters would record "no
  refusals" for constraints it never checked — the readings would then decide
  which money-path modules get enforced. A blind instrument is worse than a
  missing one.

  **Blast radius of that fix is shadow-only, and that is measured rather than
  argued.** Neither enforced module uses a `$ref`'d parameter
  (`PUT`/`DELETE /contacts/{id}` and `GET /merchants/{slug}` all declare their
  path parameter inline), so no route that refuses today changes its answer;
  `routes/__tests__/contacts.test.ts` and `routes/__tests__/merchants.test.ts`
  run under enforcement and are unchanged apart from the option's name. What
  changes is what shadow MEASURES: `lint:request-schemas` moved
  `routes/agent-passports.ts` from `shadow: 0` to `shadow: 1`, because its only
  request constraint was a `$ref`'d `AgentId` and both the gate and the plugin
  had been blind to it. That entry's `0` was a false zero, never an
  achievement — the module has never been in `enforcedModules`.

  **Shadow's remaining promise is now asserted.** #3082 closed the body half by
  snapshot/restore; the querystring/params half rested on a comment saying the
  spec's `default:`s happen to agree with the handlers' fallbacks.
  `__tests__/request-validation-shadow-invariants.test.ts` pins both sets: the
  11 request-side defaults and the 13 coerced query/path parameters, each
  against a reviewed row. Stated precisely, because review round 1 caught an
  earlier draft of this sentence overclaiming: the test asserts the spec's
  default against the row, and asserts the fallback EXPRESSION the row cites is
  still present verbatim in the route file it names. Judging that the
  expression means that fallback is the review step, not the test — what the
  test removes is the possibility of the row silently ceasing to describe the
  code. A new `default:` or a new typed parameter reddens it until somebody
  writes the row.
  No request **body** declares a default, which is now asserted rather than
  observed — a `useDefaults` injection into a body is the same class of rewrite
  #3082 was filed for.

  **Two further honesty fixes to the gate, neither behavioural.**
  `lint:request-schemas` gains `ownSchema` (routes declaring their own Fastify
  `schema:`, which the plugin refuses to clobber and which therefore escape
  validation; baseline 0) and `unspecced` (registered routes with no spec
  operation at all; baseline 1, `POST /safe/deploy`, the retired-rail tombstone
  that carries a coverage-gate exemption). Both were invisible to the gate
  before, so epic #3028 slice 4's "every entry zero" could have been reached
  with unvalidated routes still registered. Epic #3028 open question 1 is
  answered here in the direction the epic assumed: keep the exemption, count
  it.

  **`ajv` and `ajv-formats` move from `devDependencies` to `dependencies`.** The
  plugin makes them runtime code and the backend Docker build runs
  `npm ci … --omit=dev` (`packages/backend/Dockerfile:38`); the image booted
  only because `@fastify/ajv-compiler` hoisted them. Measured both ways:
  `npm ls ajv --omit=dev -w packages/backend` showed `ajv` reachable only
  beneath `fastify → @fastify/ajv-compiler` before, and as a direct dependency
  of `@haven/backend` after.

  **Mutation-tested** (each restored and the control re-run green):
  dropping the `$ref` resolution reddens the `$ref` parameter test (1 of 50);
  making `routeModuleFor` answer a constant reddens the independent-flip proof
  (6 of 50); reinstating the `operation.__pathItemParameters` write reddens the
  frozen-spec tests (2 of 50); a stale generated table reddens the drift tests
  (5 of 50); withholding the schema from a `'/'`-declared route reddens the
  trailing-slash pin (6 of 50); a spec default disagreeing with its handler
  fallback, and a new default with no reviewed row, each redden one invariant
  (1 of 50 apiece). On the gate: removing `routes/contacts.ts` from
  `enforcedModules` re-enters the proof module in shadow and reddens
  `lint:request-schemas`; adding a route with its own `schema:` reddens
  `ownSchema`; adding a second route with no spec operation reddens
  `unspecced`.

  **Review round 1 changed two things here, both worth recording.** The
  independent `haven-reviewer` pass found that this same invariants guard
  filtered parameters on `parameter.in` — the exact predicate this change
  removes from `requestSchemaForOperation` — so its two walks were blind to all
  40 `$ref`'d parameters, and it proved it: mutating `AgentId` to carry
  `type: 'integer'` and `default: 'MUTANT'` left the file green. A guard blind
  in precisely the way the change under test is about is worse than no guard,
  and it would have failed silently in slices 3 and 4, not here. Both walks now
  go through the plugin's own exported `resolveParameter`, with a control
  asserting the walk sees `$ref`'d parameters at all; the reviewer's mutation
  now reddens 2 of 8. The `haven-doc-reviewer` pass separately found two live
  sites the retired-vocabulary sweep missed — `.env.example:251` and
  `.github/workflows/ci.yml:405`, both naming `enforcedPrefixes` — because the
  sweep's perimeter covered `docs/**`, `packages/**`, tests and skill text but
  not repo-root dotfiles or `.github/**`. Both are corrected.

  **A claim epic #3028 and #3030 both carried, corrected here.** Both recorded
  a "permanent hole" in shadow coverage: a route declared at `'/'` under a
  prefix registers twice, and fastify skips the `onRoute` hooks for the
  `prefixing: true` trailing-slash variant. The hook count is right and the
  conclusion is wrong — `addNewRoute` mutates and reuses one `opts` object, and
  the second variant's Context is built from that same mutated object, so the
  schema, `attachValidation` and `errorHandler` the first variant's hook
  installed are exactly what the trailing-slash variant gets. Measured on
  fastify 5.8.5: `POST /contacts` and `POST /contacts/` both refuse the same
  off-spec body with the same envelope and both accept the same conformant one.
  No code was needed; the behaviour is now pinned by test so a fastify upgrade
  that clones `opts` cannot land silently.

  Perimeter unchanged.
