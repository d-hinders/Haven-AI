  ## Why MINOR — and why the instruments said otherwise

  **The break is a tool result shape.** `haven_list_receipts` on the local MCP
  runtime now returns `{ receipts, total, hasMore, nextCursor }` **instead of a
  bare array**, and accepts an optional `cursor` (#3128, via the SDK's new
  `listReceiptsPage`). For an MCP server package the tool result shape **is**
  the published contract, so an agent or script that indexed the old array meets
  an object. Under the 0.x convention that made `0.2.0-alpha.0` and
  `0.3.0-alpha.0` MINOR, a break takes the minor step.

  **This is recorded because it was nearly missed, and the near-miss is the
  regulatory point.** No commit subject in the range carries a `!:` marker —
  #3128's does not — so a convention-based scan reported no break. Worse, BOTH
  declaration-level instruments agreed with it: a name-level `.d.ts` diff
  against the published tarballs, and an independent TypeScript-compiler-API
  pass that enumerates `getExportsOfModule` and recurses three levels into every
  exported type's members (marking optionality, so a required↔optional flip
  would show). Both reported **zero removals across all five packages** and
  **24 additions** (23 `sdk`, 1 `signer`). Both are correct, and both are
  structurally blind here: a tool's runtime result shape appears in no `.d.ts`.
  The release's own CHANGELOG — "instead of a bare array" — is what names it.

  The standing lesson, and it generalises past this release: **"the declaration
  surface lost nothing" is evidence about declarations, never evidence that a
  release carries no break.** The 0.3.0 shard hit the same class one layer in,
  where a name-level diff could not see a field removed from a surviving type;
  this is that failure one layer further out.

  The SDK itself is not part of the break:
  `listReceipts(): Promise<HavenPaymentReceipt[]>` is byte-identical to the
  published `0.3.0-alpha.0` declaration, and `listReceiptsPage` is additive.
  The 24 additions are the typed-next-step surface (`NextStep`,
  `createNextStepBuilder`, `NEXT_TOOL_SERVER_ROLES`,
  `SIGNER_HOSTED_HANDOFF_SHAPES` and siblings), the x402 retry-target guards
  (`X402RetryTarget`, `assertSecureX402RetryTarget`, `isSecureX402RetryTarget`,
  `HavenInsecureRetryTargetError`, `INSECURE_RETRY_TARGET_CODE`) and three read
  types (`HavenBalanceCoverage`, `HavenPaymentReceiptsPage`,
  `HavenCatalogMerchant`).

  ## Why the perimeter is unaffected — and, on two paths, narrower

  This is a heavier money-path range than a routine promotion: **78 of the 399
  changed files match `.github/money-path-globs.json`**, and it carries three
  new migrations (087 hosted-refusal source, 088 merchants, 089 marketplace
  prospects) plus a modification to 086. Each is addressed rather than covered
  by a blanket sentence. **The `haven_list_receipts` break is not a perimeter
  event**: receipts are a read of settled history, and the change is to how that
  read is paginated.

  **x402 unsupported transfer methods are now refused before funding or
  signing (#3116).** `selectStandardPaymentOption` treated every non-`erc7710`
  entry as EIP-3009-compatible, so an entry advertising
  `extra.assetTransferMethod: 'permit2'`, or an unrecognised `extra.paymentFlow`,
  could be selected and signed into an EIP-3009 authorization payload the
  exact-EVM spec does not define for it — which v2 §6.1 forbids. An entry is now
  EIP-3009-constructible only when the transfer method is absent or exactly
  `eip3009` AND the flow is absent or exactly `authorization`; a malformed value
  reads as unsupported rather than falling back to the default. Unsupported
  entries are skipped when a supported alternative exists and refused —
  **before intent creation, funding or signing** — when they are the only
  option, with `toStandardPaymentRequirements` throwing as a last stop before
  `createPaymentHeader`. Strictly fewer payloads Haven will sign.

  **The paid retry can no longer be redirected to a merchant-declared insecure
  resource (#3097).** The retry after payment goes to the URL the caller quoted;
  the merchant's declaration remains the fallback **only when the caller passed
  no URL, and must itself be secure** — `isSecureX402RetryTarget` allows https
  anywhere and http only to loopback-by-octet or RFC 2606/6761 reserved hosts.
  A merchant could previously name the destination of the authenticated retry
  outright. Narrowing who chooses where a paid request lands.

  **Advertised accepted requirements are preserved across SDK and backend
  encoding (#3117).** A correctness fix on what is echoed back, not a change to
  what may be spent.

  **Hosted prepare refusals reach the ledger (#3054, migration 087).** Refusals
  that happened in the hosted MCP before any backend call were not recorded, so
  the Analytics "Refused" tile under-counted on exactly the paths an agent hits
  first. This release adds `POST /machine-payments/budget-precheck` and the SDK
  `precheckBudget`. It **moves no funds, mints no delegation and constructs no
  intent; its only write is a refusal-ledger row** (`source 'hosted_prepare'`).
  Recording more refusals is a transparency gain, not an authority change.

  **The hosted sufficiency check (#3126) is a read** —
  `GET /machine-payments/balance-coverage` answers whether a budget is backed by
  funds, from `chainBalanceOf`, returning `covered=null` when the chain read
  fails. Its route test asserts the body never carries a balance figure.

  **The three migrations add tables and columns; none touches custody.** 087
  widens the existing refusal ledger's source check with `hosted_prepare`. 088
  creates the marketplace `merchants` table and its foreign keys; 089 seeds two
  `coming_soon` prospects that carry zero offers by construction. Catalogue
  metadata, with chain scoping applied to non-agent reads. No migration alters a
  delegation, budget, signer set or execution path, and all three are code-owner
  gated on merge as direct migration files.

  **No authority, custody or execution change whatsoever.** No caveat enforcer,
  delegation shape, budget, recipient pin or expiry is touched. Haven gains no
  signing capability: every money-path signature is still produced by an
  agent-held delegate key over the account's typed data, verbatim. The retired
  Safe and session rails remain fail-closed at 410. No key material changes
  hands, and the connector work in this range (#3120–#3123) moves the same way —
  `--unwire` now refuses to destroy the recovery credential, and `--doctor`
  stops reporting a green verdict it cannot substantiate.

  ## What this release does NOT prove

  Stated so a reader does not infer coverage from silence. The money-flow QA
  harness admitted for this promotion is a `workflow_dispatch` run at
  `6937e314`, dev's tip, whose `money-flow` **job** concluded success —
  dispatched because every recent `deployment_status` run had that job
  **skipped** by the duplicate-deployment gate, a run-level green whose harness
  never executed. The backend real-DB suites did not run in the cutting
  environment (no Docker daemon); that is an environment limit, not a green
  result. Two unrelated gates are red there and red at base: two `chmod 000`
  tests that cannot fail-as-designed under uid 0, and an on-chain enforcer probe
  with no outbound reach to `sepolia.base.org`.

  Perimeter unchanged; on the two x402 paths above, strictly narrower. The one
  break this release carries is a read's pagination shape, and the version says
  so.
