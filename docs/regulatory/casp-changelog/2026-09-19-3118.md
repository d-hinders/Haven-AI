- **#3118** — **The SDK speaks the official x402 MCP transport profile beside
  Haven's HTTP-402-over-MCP layering: a payment-required TOOL RESULT is quoted
  like a 402, the paid retry carries the payment in `params._meta["x402/payment"]`
  as well as the header, and settlement is read from
  `result._meta["x402/payment-response"]` when no `PAYMENT-RESPONSE` header
  arrives. No backend file, no route, no migration. `money-path` by LABEL
  (the issue's own classification) AND, since review round 1, by FILE:
  `scripts/ci/money-path-classify.mjs <merge-base>` against
  `.github/money-path-globs.json` names the hosted completion module
  `packages/mcp-server/src/tools/paid-mcp-completion.ts` (and its test) on
  the `packages/mcp-server/src/**` runtime glob — the S5 fix below — so a
  dev → main promotion needs a covering green money-flow QA run. Before that
  fix the diff was SDK-only and no touched file matched a glob; the
  classifier prints the denominator at each head.**
  Before this change `quoteX402` rejected a profile merchant's challenge with
  "Expected an x402 quote response with HTTP 402, got HTTP 200", the paid
  retry delivered the payment only in HTTP headers a profile merchant never
  reads, and a profile merchant's in-band refusal (an `isError: true` result
  under HTTP 200) would have been recorded as a successful paid call. Now
  `packages/sdk/src/mcp-merchant-transport.ts` reads the challenge from the
  tool result (`structuredContent` first, JSON text fallback second, both
  through `normalizePaymentRequired`, so an ordinary tool error or a
  successful result that resembles a challenge is never a payment demand),
  adds the decoded envelope to a `tools/call` body's `_meta` (any other body
  is sent byte-for-byte), and reads the `_meta` settlement; `client.ts`
  quotes it in `quoteX402` / `quoteMcpX402` / `fetch()`, and
  `completeX402MerchantCall` treats an in-band challenge or a `success: false`
  settlement as a rejection (`ok: false`, no success evidence, no receipt
  capture; the funded-but-rejected reconciliation event is recorded as for a
  non-2xx answer); `merchant-completion.ts`'s local paid retry throws the
  same post-funding rejection (status 402, `merchant_status` 200 kept in the
  details) for an in-band refusal. Perimeter argument: no new signing path
  and no new authority — the `_meta` value is the decoded content of the
  header the edge signer already produced, delivered to the same merchant
  URL in the same request; only a JSON or SSE body is ever read when probing
  a non-402 answer for a challenge (and the local paid retry reads a JSON or
  SSE answer once for its tool result), so a binary or otherwise-typed paid
  resource is returned untouched as before; Haven still holds no key and no
  funds; the
  merchant's settlement statement stays a CLAIM the backend verifies on-chain
  before confirming anything (#2092), reached through the one existing
  receipt decoder because the `_meta` form is re-encoded as base64 JSON; a
  settlement object without a boolean `success` yields no transaction. The
  hosted server (`packages/mcp-server`) inherits all of this through the SDK
  (one change of its own, the S5 status mapping); its rejection message names
  the status the merchant
  really returned — and, since review round 1, its refusal is thrown as 402
  rather than carrying HTTP 200 as the status of a failure object (the local
  retry's mapping). Mutation-tested (each restored byte-identically): the
  `isError` gate dropped (two red); `_meta` never injected (three red); the
  text fallback dropped (red); the completion's in-band rejection ignored
  (two red); the `_meta` settlement never read (three red); the
  `quoteX402` tool-result branch dropped (two red); the local retry's
  in-band rejection dropped (red); `success: false` no longer a rejection
  (red); `fetch()`'s native challenge ignored (red). After review round 1
  (PR #3155): SSE collapsed only under a session (three red — a plain-URL
  profile merchant's SSE-framed refusal was invisible); `success: false`
  ignored on the local retry (red); the local retry's `_meta` receipt
  dropped (red); the content-type guard on the challenge probe removed
  (red — a streaming 200 was buffered); a transaction beside a rejection
  reported as settled (red); the hosted refusal carrying HTTP 200 as its
  status (red — now 402, message names the real status). Characterized first:
  the HTTP-402 quote over an MCP session, the `PAYMENT-RESPONSE` header
  winning over `_meta`, and the header form still sent on every paid retry.
  Custody unchanged — Haven still holds no key and no funds. Perimeter
  unchanged.
