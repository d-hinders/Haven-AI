- **#3170** — **The demo merchant explains an ERC-7710 redemption that reverts
  at submit as a payer-side decision, mirroring the EIP-3009 rail's #1519
  pre-submit explanation.** Money-path by file (`packages/demo-merchant-mcp/src/**`,
  #3098); no funds move differently — only what the buyer is told.
  Before this change `submitRedeemDelegations` was a bare `writeContract`:
  a revert there raised viem's `ContractFunctionExecutionError`, which is not
  a `PaymentError`, so `handlePaymentGate` took the FAULT branch and answered
  `Payment failed — merchant-side fault (ContractFunctionExecutionError); see
  merchant logs` with `reason_code: merchant_fault` (`http.ts`'s #1517 fault
  template) — the same response the `qa-dev` `x402-erc7710-hosted` run of
  2026-09-19 (#2769) logged, truncated there by the qa-agent's 600-char slice
  at `ContractFunctionExecutio`, so the tail and the `reason_code` are inferred
  from the template, not observed in the run. The
  likeliest causes are facts about the payer (the settlement child's
  exact-amount caveat exhausted, the delegator short of the price, the child
  redeemed elsewhere between simulate and submit), and the merchant already
  owned the code to say so on the simulate branch (`erc7710AlreadyRedeemed`,
  #1515) but never ran it on this one; the erc7710 `submit` had no rejecting
  test at all (`erc7710.test.ts` only ever rejected `simulateRedeemDelegations`)
  while the EIP-3009 `submit` mock rejects across `http.test.ts` and
  `x402.test.ts`. Now the erc7710
  `submit` closure catches the rejection, first asks the chain whether the
  child already moved the money (served as `already_settled_earlier`, the
  #1515 decision), then classifies a PROVEN contract revert (`isContractRevert`:
  a `ContractFunctionRevertedError` carrying decoded data, an error signature
  or an "execution reverted" reason, the node's `ExecutionRevertedError`
  except geth's "gas required exceeds allowance" (the merchant's key short of
  gas, which viem files under that class — review round 2), or an
  enforcer/revert string from a custom client) as a `PaymentError` naming the
  revert, the next action (nothing settled; re-quote, fresh authorization) and
  the payer-side causes. viem wraps every `writeContract` failure in
  `ContractFunctionExecutionError`, so the wrapper is not proof: nonce, fee,
  "already known", JSON-RPC rate-limit/internal, HTTP, timeout and gas failures
  on the merchant's own key or node stay faults and keep #2979's reason codes
  (review round 1 caught the wrapper being treated as proof — it mislabelled a
  merchant nonce fault as "a fact about the payer" and, for an in-flight
  "already known" transaction, told the buyer to pay again with a fresh
  authorization). The next action precedes the cause list and the revert
  reason is flattened to printable ASCII and capped at 120 characters (so
  the cap survives JSON escaping) so the hosted relay's 500-character window
  (`paid-mcp-completion.ts`) always carries it. Perimeter argument: no
  new authority, no change to what is settled or when — a refused payment is
  refused with a truer sentence, and a settled one is served instead of
  refused; the chain-truth check reads only the pinned enforcer (#1515's three
  binds unchanged). Mutation-tested (each restored byte-identically): the
  revert classification dropped (red — the buyer is told "merchant fault"
  again); the already-redeemed check at submit dropped (red — a settled
  purchase is refused again); the classifier calling every failure a revert
  (four red at the final head — the RPC-failure, nonce-fault and both
  classifier unit tests; it was two before round 1 added tests); the
  `ContractFunctionExecutionError` wrapper accepted as proof again (two red —
  a merchant nonce fault is told as the payer's); the `ContractFunctionRevertedError`
  data/signature/reason guard dropped (one red — a bare JSON-RPC internal error
  becomes a revert); the reason cap raised or the next action moved after the
  causes (one red each — the instruction falls outside the relay window);
  the gas-allowance exclusion dropped, the reason guard loosened to `/revert/`
  and the ASCII flattening removed (one red each, round 2); the decoded
  custom-error name fallback dropped (one red, round 3).
  Errors in those tests are built with viem's own `getContractError`, the shape
  `writeContract` really throws. Custody unchanged — Haven
  still holds no key and no funds. Perimeter unchanged.
