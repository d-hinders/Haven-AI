- **#3171** — **The demo merchant's unknown-session 404 carries the recovery
  machine-readably, and the SDK's paid retry acts on it.** Money-path by file
  (`packages/demo-merchant-mcp/src/**`, `packages/sdk/src/**` is not on the
  perimeter but the seam is the paid retry); no funds move differently — what
  changes is what the buyer is told and whether it recovers on its own. Before:
  a paid `tools/call` on a session the merchant no longer held answered a bare
  `404 {"error":{"code":-32001,"message":"Session not found"}}`; the remedy
  ("re-initialize, then retry the SAME payment header; nothing was settled, so
  the retry settles exactly once") lived in a code comment, the buyer holding
  a one-use authorization could not tell whether it was charged, and the SDK
  surfaced it as `merchant_status=404` after funding (the `qa-dev`
  `x402-delegation-3009-sweep` failure of 2026-09-16, #2769). The session
  store had no TTL: every `initialize` stayed resident until its client closed
  it. Now: the 404's message begins "Session not found. Nothing was settled
  here" and `error.data = { reason: 'session_expired', settled: false,
  next_action: 'reinitialize_then_retry_same_payment_header' }` — the
  merchant's own guarantee, which is true because the #1578 guard runs BEFORE
  the payment gate. The SDK's one delivery seam
  (`deliverPaymentRecoveringSession`, used by `MerchantCompletion.retryRequest`
  for `fetch()`/`payX402Quote()`/`resumeX402Payment()` and by
  `completeX402MerchantCall()` for the hosted twin) re-initializes once and
  resends the SAME header on the new session when, and only when, that exact
  shape is present; a bare `-32001`, any other 404, a failed re-initialize or
  a second 404 is returned unchanged and recorded as a rejection as before.
  Sessions idle longer than `sessionIdleTtlMs` (default 30 minutes) are swept
  lazily and answer the same 404. Perimeter argument: the resend carries the
  same signed header — no new authorization, no new signature, no funding
  leg — and is licensed only by the merchant's explicit settled-nothing
  statement, never inferred; the merchant's #1519/#1515 chain-truth checks
  still cover a replay of an already-settled header. Mutation-tested (each
  restored byte-identically): `error.data` dropped from the 404 (red — the
  restart test and the SDK recovery test); the idle sweep disabled (red — the
  TTL test); `retryRequest` and `completeX402MerchantCall` wired back to the
  plain `deliverPayment` (red each — the end-to-end recovery tests); the
  recovery parser accepting a bare `-32001` (red — the guarantee-only test).
  Custody unchanged — Haven still holds no key and no funds.
