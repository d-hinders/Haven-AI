# 2026-09-20 — #3019: Accounted webhook receiver (epic #3016 slice 3)

**Change:** the receiving half of the Accounted integration. Connect now
registers three event subscriptions at the provider
(`journal_entry.committed`, `period.locked`, `document.uploaded`) pointing at
a per-connection capability URL the new public route answers
(`POST /accounting/webhooks/accounted/<token>`,
`routes/accounting-webhooks.ts` + `modules/accounting/accounted-webhooks.ts`,
migration 092). Deliveries are HMAC-verified against per-subscription secrets
stored in the connection's encrypted blob, deduped durably in
`accounting_webhook_deliveries`, and REDACTED before anything is stored: only
a size-capped, sensitive-key-stripped `journal_entry.committed` `data.object`
is kept (the probe's raw material), every other event type is counted only.

**Perimeter: nothing in the payment path moved.** The webhook receiver is
read-back plumbing beside the feed: it observes provider events, it never
initiates a transfer, signs anything, or changes what an agent may spend. The
money-path-relevant surfaces are unchanged in kind:

- **No new authority.** Connect's webhook step runs AFTER the same
  validate-then-store flow as before, with the user's own pasted key; a
  registration failure stores NO secret and flags the connection
  `needs_attention` (user-resolvable by reconnect). Nothing about the
  registration makes API credentials sufficient to spend — the key already
  could feed documents, and subscriptions only let the provider TELL Haven
  what it did.
- **No new key custody.** The three `(subscription_id, event_type, secret)`
  triples are provider-issued HMAC secrets stored with the API key under the
  same AES-256-GCM blob (`HAVEN_SECRETS_KEY`, `infra/secrets.ts`) — same
  encryption, same key versioning, never logged or echoed (pinned by tests:
  the rollback error message carries no fixture secret).
- **No payment data flows in unredacted, but what is stored is a DENYLIST
  cut, not an allowlist guarantee.** `document.uploaded` confirms a sync
  row's delivery (a counter + a `delivery_confirmed_at` timestamp on the
  row); `period.locked` and unknown types are counted only. For
  `journal_entry.committed`, the stored `data.object` is the envelope object
  with 13 named keys STRIPPED (`attachments`, `attachment_urls`,
  `download_url`, `presigned_url`, `url`, `urls`, `file`, `file_content`,
  `content`, `notes`, `comment`, `description`, `metadata`) by a SHALLOW
  walk, then size-capped at 16 KB (over cap → nothing stored). What is NOT
  guaranteed: any key outside that list is kept verbatim — a
  `journal_entry.committed` object whose lines carry amounts, accounts or
  counterparties under other key names WOULD be stored with them — no
  nested object or array element is redacted (the walk is one level deep),
  and no schema pins what the provider puts in `data.object` (no per-event
  payload schema is published). The 13-key list and the cap are test-pinned;
  the redaction is evidence-first by design — the raw payload lands on the
  epic BEFORE any widening of the list — so treat the stored payload column
  as potentially sensitive and read it only through the runbook's redacted
  handling.
- **The route is deliberately unauthenticated-by-session and public**, because
  the caller is the provider's dispatcher. Its two credentials are the
  256-bit capability token (stated entropy, per connection, rotated at every
  reconnect) and the HMAC over the raw bytes with a 5-minute replay window;
  wrong → 400, unknown token → 404, and every refusal is counted. The route
  NEVER answers 410 or any 3xx (either would auto-disable the subscription at
  the provider), pinned by a test enumerating every answer path on both path
  spellings.
- **Non-asserting doctrine intact (#491):** receiving a `journal_entry.committed`
  event changes NO accounting state in Haven this slice — no sync row moves,
  nothing is booked, nothing is claimed from the payload. Whether a *booked*
  state is derivable is deferred to the owner's probe (epic #3016); the
  product decision, if any, lands in a follow-up slice.

**Contract docs:** the route is documented in `openapi/spec.ts` (Webhooks
tag, both path spellings); the runbook section and the product doc's
"what the confirmations show" section carry the operational and product
statements. No SDK, MCP, or agent-authority surface changed.

**What is pinned:** the full answer matrix (400/404/200 classes, no 410, no
3xx, both spellings), signature verification (wrong secret, tampered body,
stale window, malformed headers, bytes-not-JSON), all-or-nothing registration
with the orphan sweep, reconnect teardown of the previous three
subscriptions, disconnect teardown best-effort, durable dedupe on the
real-Postgres harness (replayed id across "restart"), and redaction
(the 13-key denylist drop, oversize stored as nothing — a denylist, stated
as such above, never an allowlist).
