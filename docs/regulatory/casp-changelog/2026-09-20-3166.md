- **#3166** — Edit budget limits in place on the agent budget card (REPLACE composition, delegate key untouched). The dashboard gains a guided modify flow for one active budget delegation: prefill the current limits (amount, token, period, recipient), a review step diffing current vs new with an explicit Raise badge, then the composition the lifecycle API's header comment already defines — `POST /agents/:id/delegations/build` (existing route), the OWNER signs the new delegation client-side (same ceremony as the first grant, passkey or EOA), `.../activate` replaces the grant in the same (token, recipient) slot atomically, and the per-hash `.../revoke` prepare/submit (existing routes) kills the old delegation on-chain with ONE more owner signature.

  **Authority and custody: what moved, what did not.** No backend file is touched at all — the diff is one hook function (`editBudget` in `packages/frontend/src/hooks/useDelegationBudget.ts`, a covered file), one new modal, and card wiring. The perimeter question is whether a dashboard surface can now change spend authority without an owner signature, and the answer is no, four ways: (1) every authority step in the composition is signature-gated exactly as before — activate demands the owner WebAuthn/ECDSA signature at the route, and the revoke UserOp is signed by the owner through the same treasury prepare/submit the standalone Stop button uses; (2) the delegate key and local signer are never touched — no rotate/rekey/recover endpoint appears anywhere on the flow's wire order (pinned by the hook test asserting the exact URL sequence and the absence of any such call); (3) Haven still cannot revoke by itself, which is WHY the ordering is activate-then-revoke: revoking first would require Haven to destroy existing authority before replacement authority is signed, leaving the agent with no budget if the flow is abandoned — the abandoned-at-any-point outcome leaves the old budget live and untouched (pinned by test); (4) the in-flight re-key guard (`IN_FLIGHT_REKEY_REFUSAL`) refuses the build step before anything is constructed, surfaced verbatim.

  **The one window, stated rather than hidden.** Between the two signatures both delegations exist on-chain — total exposure = the sum of the two grants, each independently bounded by its own caveat enforcers (period budget, recipient pin, expiry). From Haven's mirror the old grant is retired atomically at activation (`activatePendingDelegationInSlot`), so payment selection never sees two live grants in one slot. Revoke-then-grant was rejected because its failure mode is an unbounded spending gap (old dead, new never signed) rather than this brief, bounded overlap; the window is disclosed in the review-step copy, which also states that limits change only after the owner signs.

  **What is mutation-tested / pinned:** the hook suite pins the exact wire order (build → activate → revoke → revoke/submit, the old hash on the revoke routes only, no rekey/rotate call ever), the four failure shapes (cancelled at the new-grant signature → nothing granted, nothing revoked; build refused → the backend's named 409 verbatim; activation raced a revoke-all → old state untouched; stop signature cancelled or submit failed after the new grant is live → `revoke_unfinished` partial state naming the live budget and pointing at the card's Stop button), the already-reconciled old row → success (`oldDelegationRevoked: false`), and expiry passthrough on the build body. The modal suite pins prefill, the disabled-until-changed review gate, the Raise/Lower badges, the two-grants-window disclosure, the abandoned-flow guarantee (close never calls the composition), and outcome-language-only copy (no delegation/caveat/UserOp jargon, asserted).
