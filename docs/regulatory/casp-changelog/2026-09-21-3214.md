- **#3214** — the hosted MCP's three generic refusal branches in
  `normalizeError` (`packages/mcp-server/src/tools/support/errors.ts`, a
  money-path file, so this shard) — `HavenApiError`, `HavenError` and the
  `UNKNOWN_ERROR` fallback — gain a typed next step through the same builder
  and `nextStepWireFields` spread #3102 gave the payment-state branch: a 5xx
  (or status-less) `HavenApiError` says retry the same tool with the same
  arguments (and the same idempotency key) once; a 4xx `HavenApiError`, a
  `HavenError` and a thrown non-Error say stop and tell the user with
  `next_tool_omitted_reason`. This is agent-guidance metadata on the failure
  envelope only: nothing changes which errors are thrown, nothing reads the
  new fields to make a payment decision, no signed intent, amount, token,
  recipient, route or timing moves, and no allowance, delegation or custody
  surface is touched — the on-chain allowance remains the real spend control
  and an API credential remains insufficient to spend. The step content is
  deliberately conservative: the retry branch preserves the idempotency key,
  so a retried quote cannot double-charge (the same double-charge-safety the
  window-expired refusal has carried since #3102), and the stop branches
  never send an agent into a doomed retry. Characterization-tested first
  (the four bare shapes pinned green on unmodified dev before the change),
  mutation-proven (deleting one added spread turns a ratchet test red), and
  the live 500 that filed the issue is replayed as a unit case through the
  real quote handler. Perimeter unchanged.
