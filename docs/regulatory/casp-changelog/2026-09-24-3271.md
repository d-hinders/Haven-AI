- **#3271** — a direct payment (`haven_send` / `haven_pay`, plain `POST /payments`) can now be signed by `payment_id` instead of by an agent hand-relaying a base64 typed-data blob between tools, the relay that corrupted payment `291c33a8…` and failed on-chain with AA24. **No custody or authority boundary moves.** Two changes:
  - **Backend: `GET /payments/:id/sign-context` (`modules/payments/direct-sign-context.ts`).** A read-only, agent-authenticated route that serves the stored `prepared_user_op` of the caller's OWN `pending_signature` delegation-rail intent as the account's exact EIP-712 typed data, with its hash and `direct_sign_context_version`. Not-found and not-yours are one 404; retired-rail rows answer the same 410 tombstones `POST /payments/:id/sign` answers, checked before any status branch; confirmed, non-pending and expired rows are refused (409 / 410). It writes nothing beyond the lazy expiry the x402 sibling already performs. It returns bytes Haven already handed the agent in the `POST /payments` result, so it adds no disclosure.
  - **SDK + signer: the UserOp binding check (`packages/sdk/src/userop-binding.ts`).** Before signing a direct payment's UserOp typed data, whether fetched or relayed, the edge signer's `haven_sign` recomputes the ERC-4337 v0.7 UserOp hash from the typed data's own message and domain, pins the domain exactly (HybridDeleGator name and version, `verifyingContract` equal to the sender, no extra keys) and the v0.7 EntryPoint, and refuses a mismatch with `payload_hash` with `USEROP_BINDING_MISMATCH`, signing nothing. A fetched direct context that is not a `PackedUserOperation` is refused the same way. The SDK's `signForData` runs the same check on every `eip712_userop` payload, which includes the x402 EIP-3009 funding leg (`sign_data.hash` is `fundingAuth.prepared.userOpHash`); in the edge signer that leg keeps its existing digest check against the Haven-signed expected context. This narrows what gets signed; it widens nothing.

  The hosted MCP's direct-payment result is unchanged here: it still hands the agent the `payload_hash` + `typed_data_b64` relay, which a current `@haven_ai/signer` now checks (an older installed signer does not). Pointing agents at `payment_id` ships separately, after the signer release.

  Enforcement is unchanged: budget, recipient pin and expiry are still enforced by the caveat enforcers during gas estimation and redemption, and the agent's delegate key stays local. The binding check is a **corruption** check, not a provenance check: it proves the typed data and `payload_hash` describe the same operation, never that Haven prepared it. When the agent passes `payment_id` alone, both values come from the sign-context response, so a compromised backend (or a man-in-the-middle on the agent's authenticated HTTPS fetch) that serves a different, self-consistent UserOp for that `payment_id` would get it signed. That is the same trust the typed-data relay already placed in the backend's `POST /payments` result, so no new exposure is added, and the caveat enforcers still bound whatever is signed: a redemption outside the budget, recipient pin or expiry reverts on-chain. An agent that still holds `payload_hash` from its own `POST /payments` result can pass it beside `payment_id`, and the signer refuses a fetched hash that differs from it. Tested: the route's refusal matrix on the real-DB harness (`payments-direct-sign-context.test.ts`), the binding check's refusal on each corrupted field (`userop-binding.test.ts`), and the signer's fetch, fallback and mismatch refusal (`direct-sign-fallback.test.ts`, `hosted-signer-integration.test.ts`). The edge signer gains a second authenticated outbound READ: `GET /payments/:id/sign-context`, made by `haven_sign` only after the x402 sign-context route answers 409 `sign_context_unavailable`, with the same agent credential and 15 s timeout, and never sending the key or a signature. Perimeter unchanged in authority; widened by one authenticated outbound READ route; the signer's refusal surface narrows.
