- **0.5.0-alpha.0 release** — **a MINOR bump whose breaks all run one way: the
  agent's local delegate key will sign strictly fewer things.** Epic #3284 closes
  the paths by which a caller could obtain a signature over bytes Haven did not
  prepare — a bare hash, an arbitrary EIP-712 payload, a validly-bound x402
  shape that pays someone other than the agent's own delegate — and retires
  x402 expected-context v1. Nothing gains authority. Cut against `origin/main`
  (`fe717b58`); the promotion range is 77 commits (`origin/main..origin/dev`,
  `ca00fdaa`).

  **Shipped delta, measured: 46 files, +3787/-462** — read out of `dist/` by
  `npm run release:scope` after a full build. It excluded **612** files: 555
  outside a published package, 49 test files unreachable from any bundle entry,
  8 inside a package but outside the tarball. All five published packages are
  affected — `@haven_ai/sdk` **22** files, `@haven_ai/signer` **15**,
  `@haven_ai/connect` **7**, `@haven_ai/mcp` **1**, `@haven_ai/cli` **1**,
  which sums to the 46 (counted from the per-file attribution lines, not the
  `Published packages affected:` summary line the 0.4.0 shard's first draft
  miscounted). The run exits 1, not 0: three files under
  `packages/sdk/src/__fixtures__/` are unclassified. All three are imported only
  by tests — the script's cause 2, benign, and a rebuild does not change it —
  so the delta is complete for this record. Measured at `origin/dev`
  `ca00fdaa`, the at-the-cut figure; the instrument reads refs and cannot see
  the uncommitted bump.

  ## Why MINOR

  Every break is a **runtime refusal**, and each one narrows what the delegate
  key signs:

  - **#3169** — `haven_sign` refuses a bare `payload_hash`. Given no
    `payment_id`, typed data or x402 context, it used to return raw secp256k1
    over the caller's bytes: a blind-signing oracle for the delegate key.
  - **#3272** — `haven_sign`'s unbound branch signs only a bound direct-payment
    UserOp, where it used to sign any well-formed EIP-712 payload. Separately,
    x402 expected-context **v1** is retired (`SUPPORTED_X402_EXPECTED_VERSIONS`
    `[1, 2, 3]` → `[2, 3]`; `EdgeSigner.signX402FundingHash` removed). v1 is
    Haven's internal bare-hash binding inherited from the retired Safe rail, not
    the x402 protocol version.
  - **#3281** — the x402 arm signs exactly two shapes: a funding leg whose
    single execution transfers the quoted amount of the quoted token to **this
    signer's own delegate EOA**, or an erc7710 settlement child delegated by
    this signer's own account. A `TransferWithAuthorization`, a `Permit`, an
    empty-context redemption, or a funding leg paying anyone else is refused,
    however validly Haven's binding key declared it.
  - **#3283** — the same guard now runs inside `HavenClient.signForData` in
    `@haven_ai/sdk`, so `pay()`, the EIP-3009 funding leg and
    `settleX402Erc7710()` refuse what the signer refuses. `@haven_ai/mcp`
    inherits this through its SDK pin.
  - **#3173** — the signer CLI refuses unknown options instead of ignoring
    them.

  Under the 0.x convention that made 0.2, 0.3 and 0.4 MINOR, a break takes the
  minor step.

  **The declaration surface again says nothing about these breaks.** A
  name-level diff of each package's public `.d.ts` against the published
  `0.4.0-alpha.0` tarball shows **zero removals across all five packages**, 52
  names added to `@haven_ai/sdk` and 10 to `@haven_ai/signer` (mcp, connect and
  cli are unchanged). The SDK additions come mostly from two new subpath
  entries — `@haven_ai/sdk/edge` (#3173, the ethers-free signer entry that the
  guard modules moved into under #3283) and `@haven_ai/sdk/test-support`
  (#3283, test fixture builders). Nine of the signer's ten additions are the
  audit-sidecar permission helpers (#3172). The tenth,
  `deriveDelegateAccountAddress`, comes from #3272. None of the five breaks above appears in that
  diff. Four are refusals with unchanged signatures. The fifth,
  `EdgeSigner.signX402FundingHash`, is a class **member** removed from a
  surviving type, which is the blind spot the 0.3.0 shard recorded. The
  CHANGELOGs name all five, which is what the 0.4.0 shard's standing lesson
  requires.

  **Mixed-version skew verified, not assumed.** A 0.5 signer facing a backend
  still on `main` could meet a v1 context only where `main` selects v1:
  `payerDelegate ? 3 : typedDataHash ? 2 : 1`. At `fe717b58` there are three
  call sites. `delegation-authorize.ts:398` and `:817` always pass the typed-data
  digest. `replay.ts:205` passes `typedDataDigest(sign_data.typed_data)`, and
  that value is always built too. The function returns `null` early when
  `prepared_user_op` is null. Otherwise both of its branches set `typed_data` to
  an object, and `typedDataDigest` throws on unhashable input rather than
  returning `undefined`. So `main` cannot produce v1 at any of its three sites,
  and the runtime-compatibility doc's claim holds.

  ## Why the perimeter is unaffected — and, on the signing path, narrower

  **159 of the 661 changed files match the `globs` list in
  `.github/money-path-globs.json`** (161 if its `controlGlobs` are counted too), and
  the range carries five new migrations. Each class is addressed:

  - **Authority-path files.** Every commit touching `rails/`, the x402
    delegation modules, the budget reader, `agent-delegations`, `agent-rekey` or
    either sweep module is one of the signer-narrowing commits above, a
    Safe-to-account rename or doc correction (#3264, #3279, #3287), #3271, #3031
    or #3255. **#3271** adds the direct-payment UserOp binding check and
    `GET /payments/:id/sign-context`, which serves the signer the typed data
    Haven prepared for a payment it already holds. The route is agent-scoped and
    read-only, except that it marks an already-expired intent as expired. The
    signer re-checks what it fetches for consistency with the payment's own
    `payload_hash`. It has its own shard (`2026-09-24-3271.md`). **#3031** makes
    `routes/x402.ts` validate its requests against the spec schema. That refuses
    more than before (e.g. a `maxTimeoutSeconds` of `-1` or `0.5`). The only
    inputs it newly admits are type-coerced equivalents of values already
    accepted, such as a numeric `amount` or a string `maxTimeoutSeconds`, because
    enforce mode coerces the body. It is recorded in `2026-09-22-3031.md`.
    #3255 adds a shared viem `fallback()` RPC transport so one provider's quota
    cut-off does not fail a payment. It changes which endpoint answers a read or
    carries a submission. Budget, recipient pin and expiry are still enforced by
    the caveat enforcers on-chain, and an RPC cannot relax them.
  - **Migrations 090–094 change bookkeeping and presentation data; none touches
    custody.** 090
    adds a nullable `sek_value` beside the existing USD/EUR figures on
    `payment_intents`, the portfolio snapshots and `payment_refusals`,
    backfilled from recorded evidence. 091 moves the display-currency default to
    SEK and rewrites data: it resets every stored `currency_preference = 'USD'`
    to NULL, because an inherited default could not be told apart from a
    chosen one, so a user who had chosen USD picks it again. 092 adds an
    accounting-webhook delivery log, replaces the `accounting_connections` status
    CHECK, and adds a `webhook_token` capability column for inbound accounting
    webhooks. 093 adds dashboard-side agent labels. 094 adds agent
    organisations, including a nullable `organization_id` FK column on `agents`
    that groups agents and grants none of them anything. No migration alters a delegation, budget, signer set or
    execution path, and all five are code-owner gated as direct migration files.
  - **#3307 returns addresses EIP-55 checksummed** on receipts, payment status
    and payment reads, matching the transactions feed since #3129. Storage stays
    lowercase. The resume path rebuilds the merchant-facing `accepted` /
    `paymentRequired` / MPP challenge from stored casing, pinned byte-identical.
    This changes the casing of a read, not what may be spent.
  - **Connector (#3251, #3259).** A retired agent directory can no longer keep a
    spendable key after a failed ledger mirror: the mirror is best-effort and no
    longer gates key teardown. The tombstone ledger follows the credential root.
    Both reduce key material left at rest.

  **No authority, custody or execution change.** No caveat enforcer, delegation
  shape, budget, recipient pin or expiry is touched. Haven gains no signing
  capability. Every money-path signature is still produced by an agent-held
  delegate key over the account's typed data, verbatim, and this release
  shrinks the set of typed data that key will accept. The retired Safe and
  session rails remain fail-closed at 410.

  ## What this release does NOT prove

  This section exists so a reader does not infer coverage from silence.

  - **Money-flow QA** for this promotion is a `workflow_dispatch` of
    `qa-dev.yml` on `dev`, dispatched after the release commit merges. The
    release commit edits `packages/signer/**` (a CHANGELOG), so any earlier
    run is stale by construction.
  - **The backend real-DB suites did not run** in the cutting environment
    (no Docker daemon). That is an environment limit, not a green result.
  - **The production smoke is an operator step.** The canary is a real
    payment, and no automated production smoke exists. Until someone runs it,
    it is outstanding, not implied by a green deploy.

  Perimeter unchanged. On the delegate-key signing path it is strictly narrower,
  and the version says so.
