- **#2769 (relayer broadcast when the RPC refuses `eth_sendRawTransaction`)**: which gateway carries a relayer broadcast changes, on one provider refusal. No authority, custody, route or signing change. The post-deploy qa-dev run of #3320 (36150884607) showed that dev's dRPC primary on Base Sepolia refuses `eth_sendRawTransaction` with the same "no available upstreams … No label `flashblocks`" body it gives the `pending` nonce read (shard `2026-09-25-2769-pending-nonce.md`). So after the nonce fix, the relayer's sends still failed at the broadcast: sweeps, account deploys at first budget activation and at a fresh agent's first erc7710 authorize, passport attestations and revokes, lane cancels and the bump worker's re-sends. dRPC had broadcast normally until midday on 2026-09-25; QA was green on it at 07:39. On that refusal only (`isPendingTagRefusal`), `broadcastSigned` (`packages/backend/src/infra/outbound-queue.ts`) sends the identical, already signed and already stamped raw transaction through the chain's configured second provider. That is `RPC_URL_BASE_SEPOLIA_FALLBACK` / `RPC_URL_BASE_FALLBACK`, Alchemy on dev, the same endpoint the viem read transport already fails over to (#3255). It never uses the public node. The hash the fallback returns must equal the signed transaction's own hash, or the send is refused. The transaction's bytes, nonce, destination and calldata are fixed before this point, and both providers forward to the same sequencer, so a second copy of the same transaction is a no-op. The returned response is built on the primary provider, so the receipt wait and every read stay on the single nonce view (#1533). Any other broadcast error propagates unchanged, and so does the refusal itself when no second provider is configured (Gnosis, or a deployment without the variable). The fallback URL carries a provider API key and is never logged. Budget, recipient pin and expiry are still enforced by the caveat enforcers on-chain. Perimeter unchanged.
