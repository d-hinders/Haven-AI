- **#3032** — **epic #3028 slice 4, the rollout's last slice: the five owner
  modules (`agents`, `agent-rekey`, `agent-connection-setups`,
  `agent-passports`, `hybrid-accounts`) enforce the OpenAPI request schemas,
  the handler-side shape rungs are deleted, and the mode default flips to
  `enforce`. No authority, custody, funding, signing or settlement boundary
  moves.** `routes/agents.ts`, `routes/agent-rekey.ts`,
  `routes/agent-connection-setups.ts`, `routes/hybrid-accounts.ts` and
  `openapi/request-validation.ts` (plus `config.ts`, whose mode parse moves)
  are money-path runtime globs, so this shard; `agent-passports.ts` carries no
  handler rung (its baseline typeof was already 0) and enforces without a
  handler edit. The #3276 prep shard declared the four spec loosenings and
  moved auth to `onRequest`; this shard does the enforcement itself.
  **Why enforcement is justified.** These are the 33 operations the 2026-09-22
  shadow reading printed NOT PROVEN for (24.41 h, zero `would_refuse`, zero
  `would_coerce`, pasted on epic #3028). The owner ruled on #3223 (2026-09-24,
  comment 5822491960, epic decision 8's instrument) that the routes a shadow
  reading can never prove — no traffic in any window, because agents do not
  call them until an owner installs a delegate — are enforced on TEST
  evidence: every operation of the five modules has a per-route pin that an
  off-spec body answers the 400 envelope before the handler and a conformant
  body reaches it (`auth-before-request-validation-3032.test.ts` for
  `agent-passports`/`agent-connection-setups`,
  `request-validation-3032.test.ts` for the other three), the same instrument
  slice 2's 22 modules enforce on. The gate contract (Antonio, 2026-09-22 on
  the epic) accepted exactly this: the reading + the owner's decision covers
  the unprovable remainder.
  **What moved.** 22 handler rungs across the four files (13
  `agent-connection-setups`, 6 `agent-rekey`, 2 `agents`, 1
  `hybrid-accounts`) are deleted because the schema states each one; the
  refusal code stays 400 and the body becomes the plugin's envelope, which
  names a field and never a rail. What JSON Schema cannot say stays in the
  handler: the MCP server-name regex (`^haven(-[a-z0-9]+)*$`, a pattern the
  spec's free-form string deliberately does not carry — the connector
  self-registers names like `haven-15`), API-key-hash/prefix hex shapes where
  the schema is open, and every semantic beyond shape (existence, ownership,
  spend authority, signature verification — untouched). The 23505
  unique-violation narrows move to `infra/pg-errors.ts` verbatim; the shared
  file is NOT a route module, so the typeof gauge does not scan it, and the
  deletions there are semantic narrowings the request schemas never claimed.
  **The default flip.** `parseRequestValidationMode` returns `enforce` for an
  unset/empty `HAVEN_REQUEST_VALIDATION` (was `shadow`): every constrained
  module is listed in `index.ts`'s `enforcedModules`, so an operator who sets
  nothing gets the gate. The kill switches become GLOBAL — `off` and `shadow`
  ignore `enforcedModules` entirely, inverting the pre-flip precedence the
  plugin tests pinned (the "off does not disable an enforcedModules module"
  pin is rewritten to assert the opposite, with its mutation note). A per-module
  rollback stays a list edit (epic decision 6): removing one route file from
  `enforcedModules` returns exactly that module to shadow behaviour, because
  under `enforce` an UNLISTED module observes instead of refusing — the one
  sibling behaviour the flip did not change (the module-fallback test that
  proved it pre-flip proves it again under `mode: 'enforce'` + one listed
  file).
  **Widening, recorded rather than left as an equivalence.** With the plugin's
  `coerceTypes: 'array'`, wrong-TYPED required fields that the deleted rungs
  refused outright now convert: a numeric `chain_id` on the hybrid-account
  body becomes a string; a numeric agent `name`… does not (strings do not
  coerce from numbers under ajv by default), but `setup_token: 12345` on the
  register route would convert to `"12345"` before the pattern refuses it.
  The rekey-start body schema is deliberately OPEN (`additionalProperties`
  unset — none of the five #3032 corrections closes it), so an unknown extra
  field still passes; the handler destructures only known keys, as before.
  No would-refusal or would-coercion was logged for any of the five modules'
  operations in the reading window, so no dev traffic exercised any of this.
  **One enforcement answer-ordering note, as in slice 3:** anonymous callers
  on `agent-passports` and the four owner routes of
  `agent-connection-setups` meet 401 before any 400 (#3276 moved auth to
  `onRequest` and pinned it against both modules ENFORCED); the connector
  routes keep in-handler setup-token/API-key auth by design and their schema
  declares `setup_token` optional precisely so a missing token stays a 401,
  not a 400.
