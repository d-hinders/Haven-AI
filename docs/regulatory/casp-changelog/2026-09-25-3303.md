- **#3303** (epic #3302): published clients name themselves, and the backend can tell an outdated one what to run. **No custody or authority boundary moves.** Every published client sends `X-Haven-Client: <package>/<version>`: `@haven_ai/sdk`, `mcp`, `cli`, `connect` (its API client; its read-only `--doctor` / `--unwire` identity probe does not), and the signer on its two sign-context reads. The hosted `mcp-server` sends one too, and it is exempt. The backend reads the header against one hand-edited table, `packages/core/src/client-compat.ts` (`CLIENT_COMPAT`), in `packages/backend/src/middleware/client-compat.ts`:
  - **Hint.** A client below `recommended_version` gets a `client_update` object on any JSON-object response. It has no other effect.
  - **Refusal.** A client below a SET `min_version` is answered 426 `client_outdated` before the handler runs. This applies only at `POST /payments`, `POST /machine-payments/send`, `POST /x402` and `POST /x402/authorize` for the API clients, and at `GET /payments/:id/sign-context` and `GET /x402/:id/sign-context` for the signer.

  The shipped table sets **no** threshold for any package, so on merge the behaviour is exactly today's; the first value is an owner decision recorded on #3302. Owner decision (2026-09-25, on #3302): warn by default, refuse only when flagged. A request is never refused when it has no header, an unparseable one, a package outside the published five, or a `0.0.0-dev.*` snapshot version. None of these is hinted as required either.

  The refusal can only **withhold** service. It never widens it, and it never touches spend authority. The on-chain delegation and its caveat enforcers remain the only spend control. The header is self-reported and unauthenticated, so it is a compatibility signal, not a security control: a client that lies about its version gets exactly today's behaviour. The routes it can refuse are chosen so that a refusal never strands funds or a prepared payment:
  - never sweep (`/machine-payments/sweep/*`);
  - never the sign or settle legs of an already-prepared payment (`/payments/:id/sign`, `/x402/:id/settle`);
  - never evidence or reconciliation reports, and never a status read;
  - never an idempotent replay of an already-accepted request. The exemption mirrors each handler's own replay rule, so it covers only a request the handler answers from the existing row without preparing anything. For a send, that is a row in any status except a `pending_signature` row past its `expires_at`. For x402, that is a `confirmed` row with a tx hash, or an in-window `pending_signature` row with its prepared UserOp. A time-expired pending row, which the handler would lazily expire and then replace with a fresh payment, is refused like any new request (review finding on #3303, proven on real Postgres for both routes);
  - never an agent on a retired rail. That agent keeps its 410, read from the same `loadExecutionRailState` / `resolveExecutionRail` seam the handlers use.

  At an initiating route the refusal writes no payment state. That is proven on the real-Postgres harness by counting every table in the worker schema before and after, for all four routes (`routes/__tests__/client-compat-refusal.test.ts`, which registers the payment routes and not the audit hooks). As for any other refused agent request, the app-wide `agent_tool_invocations` audit row (when `X-Haven-MCP-Tool` is sent) and `agents.last_seen_at` are still written. A signer minimum governs only the signer's `payment_id` path. A signer that is handed `typed_data_b64` / `x402_expected` instead never meets the backend before signing, and `/payments/:id/sign` and `/x402/:id/settle` are deliberately never refused. So a signer minimum is a strong nudge on the default path, not a guarantee that no older signer signs. The signer first meets the backend after prepare, so for the signer the contract is **nothing signed or submitted**: the prepared row is byte-identical after the refusal and takes the existing unsigned/abandoned path (owner decision 2026-09-25, recorded on #3303). The signer maps the refusal to a structured `SIGN_CONTEXT_REFUSED` with `backend_error_code: 'client_outdated'`, the update command as data, `next_action: stop_and_tell_user`, and a `next_tool_omitted_reason`. It carries no `fallback`, because no relayed bytes can help. The update command comes from the deployment's own `config.connectorChannel`. No key material, signing path, delegation, caveat, fee, relayer or nonce behaviour changes. Perimeter unchanged.
