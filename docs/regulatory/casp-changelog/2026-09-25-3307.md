- **#3307:** Haven-owned addresses are EIP-55 checksummed at the agent-facing read boundaries. **No custody or authority boundary moves. This is a value-casing change on read surfaces.**
  - **What changed.**
    - **Receipt.** `mapEvidence` (`modules/mpp/evidence.ts`) checksums `merchant_address`, `payer_address`, `settlement_address`, `token_address` and every `parties` entry.
    - **Payment status.** `getAgentPaymentStatus` (`modules/payments/agent-payment-status.ts`, an owner decision on #3307) checksums every address it returns: top level, rail context and `parties`.
    - **Payment reads.** `GET /payments/:id` and `GET /payments` (`routes/payments.ts`) checksum `to`.
    - For one payment, the receipt and the status carry the same checksummed `merchant_address`, token address and `parties`; a cross-surface real-Postgres test proves it. The transaction row (#3129) uses the same `toCanonicalAddress` for its merchant and token addresses.
  - **Untouched.**
    - Storage stays `LOWER(...)`, and `tx_hash` is unchanged.
    - The relayed merchant objects stay byte-for-byte (#3125).
    - **The resume state's rebuilt payment objects.** `accepted`, `paymentRequired`, the MPP `challenge` and `merchantAddress` are built from the row in stored casing. The payloads that go back to merchants and signers are byte-identical, pinned by the existing resume tests and a new one. Every address `GET /payments/:id/resume_state` returns stays in stored casing; the status the lookup reads internally is checksummed, but it is not part of the response.
    - The signed receipt bundle is unchanged: its content is signed, and its verifier compares lowercased.
    - The x402 authorize payloads are unchanged, including `merchant_to`, which sits inside the Haven-signed binding.
  - **One declared asymmetry.** The SDK's `X402Receipt.merchantTo` is checksummed on the resume path and lowercase on a fresh payment. It is agent-facing only.
  - **No behavioural change.** No execution path, signing input, spend check, allowance, fee or accounting entry changes. The OpenAPI `address` pattern is case-agnostic, so no wire schema moves.

  No route, credential scope, key-material handling, signing path or spend authority is added or widened. Perimeter unchanged.
