- **#3317 (follow-up to #3295)** — the funding endpoint joins the degraded-balance read: `GET /user/accounts/{accountId}/funding` (`packages/backend/src/routes/user-accounts.ts`, `packages/backend/src/openapi/spec.ts`, the regenerated `packages/core/src/api-types.ts`) no longer maps a failed on-chain balance read to a fabricated `'0'`. A rejected leg now serves the last-known balance for that (chain, account, token) from the same in-process store #3295 landed, marked stale with its as-of time, or `'0'` marked `unavailable` when no balance has ever been read; the additive optional `balanceFreshness` marker rides on each degraded token entry, the native block, and the response envelope (worst-of via `combineBalanceFreshness`). `funded` is computed only from KNOWN values — a fresh read or the stale last-known one — so an RPC blip (#2769's failure class) can no longer unfund a funded account, and a token with no known value can never make the answer true or false (unknown is not unfunded). A clean read is byte-identical to the pre-#3317 response.

  Authority and custody argument: the diff touches one read-only display/decision route for the human funding hand-off. No key material, signing, binding, verification, relaying, or payment execution moves; no new spender, approval, or credential surface is created. The endpoint constructs no transfer and grants no authority — it tells a human (or the agent relaying to them) what to fund, where, and whether the account already counts as funded, and the previous behaviour could lie in the UNFUNDED direction only after this fix (it never claimed funded off a fabricated figure; it claimed unfunded off one). Budget, recipient and expiry remain enforced on-chain by the caveat enforcers, exactly as before; a wrong `funded` answer moves no money and blocks none. The wire changes are additive OPTIONAL markers on one read-only GET route; every token entry stays present with `balance_human` a decimal string plus address and decimals, and every previously-required field stays required — the published CLI's `wallets funding` passthrough and `--wait` poller (`packages/cli/src/commands.ts`) keep working unchanged, and the dashboard's funding card renders the same instruction text it always did. The response is deliberately NOT cached (this route has no cache), so no degraded answer outlives its request.

  Tests: `routes/__tests__/user-accounts-funding.test.ts` pins all three states at the route level — failed-after-good serves the stale last-known figure and stays `funded: true`; never-read reports `unavailable` with the `'0'` filler and cannot answer the comparison; stale-known still counts toward `funded` (option (a) wording: known-fresh OR known-stale); and a clean read is pinned byte-identical (whole-body `toEqual` plus a no-`balanceFreshness`-key census at all three levels). Perimeter unchanged.
