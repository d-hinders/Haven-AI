# CASP shard — #3277: hosted direct-payment results name the `haven_sign({ payment_id })` handoff

- **#3277** — the hosted `haven_send` / `haven_pay` delegation-rail success results now carry the
  structured signing handoff (`next_action: sign_and_submit_payment`, `next_tool: haven_sign`,
  `next_arguments: { payment_id }`, a reason, an agent summary and warnings via the shared
  `buildAgentGuidance` builder) plus a `signer_compatibility` notice with the recovery route for a
  pre-#3271 signer: on its `SIGN_CONTEXT_REFUSED` refusal with
  `backend_error_code: 'sign_context_unavailable'` — which means it signed nothing — re-sign with
  `{ payload_hash, typed_data_b64 }` from the same result, passed through unchanged, then update the
  connector. The relay fields (`payload_hash`, `signature_scheme`, `typed_data`, `typed_data_b64`)
  stay on every delegation-rail result unchanged; the notice never asks the agent to compare a
  version against `initialize` instructions (#1547 pattern), and the handoff shape is never widened
  beyond `{ payment_id }` (`SIGNER_HANDOFF_SHAPES`, compile-pinned).

  Authority and custody argument: this change alters only what the hosted server TELLS the agent
  after the backend has already prepared a payment under the on-chain budget, recipient and expiry
  checks. It creates no new signing capability, no new credential surface, and no path on which the
  hosted server or an API credential can move money: the hosted server stays keyless (it constructs
  intents and relays signatures; it cannot sign), the delegate key never leaves the local signer,
  and the signature is still produced locally over typed data the signer validates against the
  payment's hash (the #3271 UserOp binding check runs on both the fetched and the relayed path).
  Naming `haven_sign({ payment_id })` steers agents onto the path where the signer fetches the
  exact bytes from Haven itself — strictly less caller-supplied signing material than the relay it
  recovers to, and the recovery route hands the signer no bytes the result did not already carry.
  The refusal the recovery route is keyed to is emitted before anything is signed, so the retry can
  never double-sign or double-submit; the payment row is unchanged by the refused call.

  Deliberately untouched: the delegation rails, budget/authority enforcement at prepare, the
  sign-context endpoint and its versioning, the signer's allowlist and binding checks, `haven_submit`
  and the settlement paths, and every x402 surface. Old signers are not forced to upgrade and are
  never pointed at a call they cannot complete without being told the relay fallback in the same
  breath; no gate upgrades existing installs (production pins the signer through
  `@haven_ai/connect@alpha`), which is why the recovery route is the compatibility mechanism rather
  than an update requirement.

  Tests: handler-level tests drive `haven_send` and `haven_pay` and assert the handoff fields, the
  recovery text, and that the relay fields remain present and verbatim alongside them (a
  typed-data-carrying stub, so the delegation fields are actually exercised); the next-step census
  and fixtures count the two new emission sites (17→19 sites, 19→21 fixtures); the ownership map
  records the new notice builder; a cross-package integration test drives the new hosted result into
  a pre-#3271-shaped signer (the real `@haven_ai/signer` handler, its x402 context fetch answered
  with the backend's real 409 `sign_context_unavailable`), shows the refusal, and shows that
  following the notice re-signs through the relay and completes. Mutations that drop the relay
  fields, widen the arguments shape, or name the retired initialize-comparison route turn these
  tests red. Perimeter unchanged.
