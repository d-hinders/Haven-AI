- **#3331 (epic #3328), backend slice** — **merchant-locked budgets: the owner can issue a budget delegation whose recipient pin is a marketplace merchant's verified payTo. The pin is the existing `AllowedCalldataEnforcer` on `transfer(to)`. The grant is still one owner signature over a delegation Haven builds and never signs. No authority widens, and no route gains spend power.**
  - **What changed.** Migration `096_merchant_pay_to` adds `merchant_catalog.pay_to`, which the read-only catalog probe fills from the merchant's own 402 challenge. It also adds `agent_delegations.merchant_id`, which labels a pinned budget with the merchant it was issued for (a CHECK refuses the label on an open budget; a deleted merchant only drops the label). `POST /agents/{id}/delegations/build` takes an optional `merchant_slug`. With it, the SERVER sets the recipient to the merchant's verified payTo on the agent's chain and refuses (409) when there is none, when the offers disagree, or when any offer there lacks ERC-7710. A client-sent recipient that differs is also refused (409), never silently re-pointed. `GET /merchants/{slug}` gains `funding`, and `GET /merchants/{slug}/budgets` (dashboard session only) reads the owner's pinned budgets for that merchant, with the remaining amount from the enforcer's own storage.
  - **Authority argument.** A merchant-locked budget is a recipient-pinned budget, a shape the rail has carried since #829. The only new input is WHICH address fills the pin, and it narrows: the build path already accepted any recipient the owner typed, and this path accepts only the one address the merchant's own challenge names on every active offer. `merchant_id` is a label. Payment selection (`SELECT_DELEGATION_FOR_PAYMENT_SQL`) does not read it and is unchanged; a characterization test pins that a pinned budget and the open budget coexist, and that the merchant is paid from the pinned one and anyone else from the open one. `pay_to` is never payment authority. It is written as seen, so a merchant that stops naming one loses the action, and a rotation shows the old pin as `stale` rather than re-pointing a signed grant.
  - **Tests.** Real-Postgres tests cover migration 096, the per-network agreement rule, the budgets route and merchant-scoped build reuse; route tests cover the build refusals and the spec shape, including one run through enforced request validation. 24 mutations were applied one at a time, and each turned at least one test red. They covered the reuse scoping, the as-seen `pay_to` write, the probe's agreement and address-shape checks, the `unstated`/`active`/`x402`/exact-`erc7710`/all-offers rules, the build's live, ERC-7710 and recipient-equality refusals, the recipient override, the stored merchant, the stale, unverified and agent-403 rules on the budgets route, its revoked-agent and active-only filters, and the migration's CHECKs, `ON DELETE SET NULL` and `down()`.
  - **Perimeter.** The recipient a pinned budget can carry narrows to a merchant-attested address; Haven's own perimeter does not move. Perimeter unchanged.
