- **#3331 (epic #3328), backend slice** — **merchant-locked budgets: the owner can issue a budget delegation whose recipient pin is a marketplace merchant's verified payTo. The pin is the existing `AllowedCalldataEnforcer` on `transfer(to)`. The grant is still one owner signature over a delegation Haven builds and never signs. No authority widens, and no route gains spend power.**
  - **What changed.**
    - Migration `096_merchant_pay_to` adds `merchant_catalog.pay_to`, which the read-only catalog probe fills from the merchant's own 402 challenge, using the options on the offer's recorded network only.
    - It also adds `agent_delegations.merchant_id`, which labels a pinned budget with the merchant it was issued for. A CHECK refuses the label on an open budget, and a deleted merchant only drops the label.
    - `POST /agents/{id}/delegations/build` takes an optional `merchant_slug`. With it, the SERVER sets the recipient to the merchant's verified payTo on the agent's chain: the one address every active, verified x402 operator offer of the merchant there names.
    - That build refuses (409) when there is no such address, when the offers disagree, when another merchant's non-delisted offer on that network names the same address (`shared`), when any offer there lacks ERC-7710, when the payTo is one of the agent's own addresses (delegate key, delegate account, treasury), or when a client-sent recipient differs. It never silently re-points.
    - `GET /merchants/{slug}` gains `funding`. `GET /merchants/{slug}/budgets` (dashboard session only) reads the owner's active, unexpired pinned budgets for that merchant, with the remaining amount from the enforcer's own storage.
  - **Authority argument.**
    - A merchant-locked budget is a recipient-pinned budget, a shape the rail has carried since #829. The only new input is WHICH address fills the pin, and it narrows: the build path already accepted any recipient the owner typed, and this path accepts only an address the merchant alone is paid at.
    - The own-address refusal closes the one way a merchant's word could widen a pin. A payTo equal to the agent's delegate key would pin the grant to the EIP-3009 funding leg's recipient, which payment selection prefers over the open budget, and so fund payments to any merchant. The `shared` refusal stops one merchant's pin from also paying another.
    - `merchant_id` is a label, not a caveat. Payment selection (`SELECT_DELEGATION_FOR_PAYMENT_SQL`) is unchanged. A characterization test pins that a pinned budget and the open budget coexist, with the merchant paid from the pinned one and anyone else from the open one.
    - `pay_to` is never payment authority. It is written as seen, so a merchant that stops naming one loses the action, and a rotation shows the old pin as `stale` rather than re-pointing a signed grant.
    - A merchant-locked budget and a plain budget pinned to the same address share one slot and replace each other on activation. Both carry the same on-chain authority.
    - A re-key carries the recipient pin but not the merchant label (#3386). The replacement's authority is unchanged; only the label is lost.
  - **Tests.** Real-Postgres tests cover migration 096, the per-network agreement and `shared` rules, the budgets route and merchant-scoped build reuse. Route tests cover the build refusals, including all three own addresses, and the spec shape, with one run through enforced request validation. Each of the following mutations, applied one at a time, turned at least one test red:
    - build reuse without merchant scoping;
    - `pay_to` COALESCEd instead of written as seen;
    - the probe's agreement check, its address-shape check and its recorded-network filter;
    - the `unstated`, `active`, `x402`, exact-`erc7710`, all-offers and `shared` rules (the last including its network scoping, its delisted-only exclusion, and that a degraded or unverified offer still counts);
    - the build's live-merchant, ERC-7710, recipient-equality and both own-address refusals;
    - the recipient override and the stored merchant;
    - `merchant_slug: null` treated as a lookup;
    - the budgets route's `stale`, `unverified`, `not_erc7710` and agent-403 rules, its every-chain target read, and its revoked-agent, active-only and unexpired filters;
    - the migration's two CHECKs, `ON DELETE SET NULL` and `down()`.
  - **Perimeter.** The recipient a pinned budget can carry narrows to a merchant-attested address that is not the agent's own; Haven's own perimeter does not move. Perimeter unchanged.
