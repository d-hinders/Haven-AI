# 2026-09-26 — #3343: owner revoke submit routes bound to the signed calldata they execute

**What changed.** The three owner revoke submit routes — per-hash
`POST /agents/:id/delegations/:hash/revoke/submit`, batch
`POST /agents/:id/delegations/revoke-all/submit`, and re-key
`POST /agents/:id/rekey/:rekeyId/revoke/submit` — used to mark delegations
`revoked` as soon as the client-supplied `user_operation` was included with
`receipt.success`, without checking that the signed calldata disables those
delegations. The re-key additionally trusted a client-supplied
`delegation_hashes` list and skipped `replaced` rows. They now verify, before
`submitCall`, that the signed UserOp's calldata — decoded from the Hybrid
account's `execute` envelope (selector-checked; try-execType batches refused),
each inner call selector-checked as `disableDelegation` on the PINNED
DelegationManager — disables exactly the delegation(s) the route is about to
record, compared by `delegationIdentity` (signature excluded) against the
row's own stored JSON. The per-hash route derives its expectation from the row
its URL names (400 on mismatch, 404 on a missing row, `HASH_RE` validation as
its prepare has always done); revoke-all and the re-key derive the set
SERVER-side from `listNonRevokedDelegationsForAgent`, whose SQL now spans
`pending`, `active` AND `replaced` rows, and refuse an op that does not
disable exactly that set (409 re-prepare; the re-key stays at `preflight` —
its point of no return — with no `markRevoked`, no meter read, no carry
snapshot). The client's pairing of a userop with delegation hashes, and any
client-supplied hash list, are no longer inputs the record depends on.

**Authority / custody argument — the perimeter does not move.** The owner's
signature remains the only thing that can move the DelegationManager: Haven
still signs nothing on these routes (#824 invariants 5/12 unchanged), the
bundler's `receipt.success` is still only an inclusion signal, and the
non-custody boundary — Haven never holds the owner key, the passkey half, or
any key at all — is untouched. What changed is which party the RECORD trusts:
previously the backend trusted the client's pairing of a userop with hash
list (an input an owner-side script could mis-pair), now it trusts only
calldata the owner actually signed, re-derived from Haven's own stored
delegations. This is the same posture the other two owner-submit sites have
held since #906 ("so the stored signer set can never diverge from what was
signed on-chain") extended to the delegation rail. The invariant the change
enforces — a delegation is recorded `revoked` only if the included userop's
calldata targets the pinned manager and disables that delegation — NARROWS
no one's authority: the owner could always sign exactly such an op, and the
delegate key's caveats, the spend guards and every enforcer are byte-identical
before and after. The `replaced`-row inclusion means a re-key or revoke-all
can now REQUIRE one more disable than before — the owner signs one op
covering the replaced-but-still-enabled delegation the edit flow leaves
behind; that is a stricter pre-condition on completing a re-key, never a new
capability. No installed client is affected (`middleware/owner-cli.ts`
refuses these submits for owner CLIs, and the first-party dashboard/qa
callers always pair each prepare with its own freshly prepared op, whose
calldata is unchanged).

**What is mutation-tested.** The binding assertion is proven independent of
the encoder it polices: `delegation-policy.test.ts` decodes
`buildRevocation`'s output and pins the hand-declared ABI byte-equal against
the kit's encoding, and the mutation `disableDelegation` → `enableDelegation`
in `rails/delegation-policy.ts` turns five tests red (previously the entire
backend suite survived it). Route tests encode their userops straight from
`@metamask/delegation-abis` ABIs, not through `buildRevocation`; the re-key
revoke/submit route gains its first route tests; the `replaced`-row inclusion
is proven on the real-DB harness.

**Verdict: Perimeter unchanged.** Custody, signing and execution boundaries
are identical before and after; the change only stops Haven's ledger from
recording revocations the signed calldata does not perform.
