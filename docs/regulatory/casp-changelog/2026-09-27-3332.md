- **#3332** — owner company details + VIES validation, dark by default behind `HAVEN_OWNER_COMPANY_DETAILS`. Migration 098 adds one table, `owner_company_details` (PK `user_id`, `ON DELETE CASCADE` on `users(id)`; legal name, ISO2-shaped country, org number, VAT number, VIES status/checked-at, CHECK constraints on country, legal name, org number, VAT number and VIES status). A new, owner-scoped route module (`routes/owner-company-details.ts`: `GET`/`PUT`/`DELETE /user/company-details`, `POST /user/company-details/vies-check`) lets the signed-in dashboard owner save these details and re-run the VIES check; an agent API key is refused with a named 403 on every route in the module, including `DELETE`. `modules/owner-profile/vies-client.ts` is Haven's one new OUTBOUND network call in this diff — a read against the EU Commission's VIES REST API, through the existing SSRF guard (`infra/http/ssrf-guard.ts`), never given a signing key or any payment-adjacent capability; it reports `valid`/`invalid`/`not_verifiable` and nothing else reaches Haven's state from it.

  Additive read surface: when the flag is on and the paying agent's owner has saved details, `parties.buyer` (`openapi/party-model.ts`'s `withParties`) is added to the two receipt surfaces that already emit `parties` — `GET /payments/:id/receipt` (`modules/payments/receipt.ts`) and the agent's receipts list (`modules/mpp/evidence.ts`'s `mapEvidence`) — via a read-only `LEFT JOIN owner_company_details ocd ON ocd.user_id = <the row's own owner>` in `infra/repositories/payment-intents.ts`'s `FIND_SETTLED_PAYMENT_RECEIPT_SQL` and `infra/repositories/machine-payments.ts`'s `LIST_EVIDENCE_RECEIPTS_SQL`. Both joins are scoped to the row's own `user_id`/owner, never a caller-suppliable value. No write path into `machine_payment_evidence` or `payment_intents` was added or changed by this diff — the two `infra/repositories/*.ts` edits are additive `SELECT` columns and a `LEFT JOIN` only. The SDK gains the mirror of this: an optional `PaymentParties.buyer`/`RawPaymentParties.buyer` (`packages/sdk/src/types.ts`, `payment-mappers.ts`), additive and present only when the backend emits it.

  Authority and custody argument: nothing here touches a delegation, a signed payment intent, a rail selection, settlement, a spend authority, or a credential. `parties.buyer` is outside `receipt.authorization` — `verifyPaymentReceipt` (`packages/sdk/src/receipt.ts`) reads only `receipt.authorization`, never `payment` (and `parties`, buyer included, lives under `payment`), so a receipt's cryptographic verification is unaffected by this field's presence, absence, or content. `routes/x402.ts`, `x402-delegation.ts`, `payments.ts` and `machine-payments.ts` themselves are unchanged — only the two repository SQL statements named above gained the join, and only `modules/payments/receipt.ts` / `modules/mpp/evidence.ts` gained the mapping. The new route module has no live caller yet (it is a brand-new surface, born request-validation-ENFORCED per `docs/operations/dev-environment.md`'s rule for genuinely new modules) and moves no money — `PUT`/`DELETE`/`POST vies-check` write only to `owner_company_details`, never to any payment, budget, or entitlement table.

  The classifier (`scripts/ci/money-path-classify.mjs`) flags this diff MONEY-PATH because it touches `infra/repositories/machine-payments.ts` and `infra/repositories/payment-intents.ts` — both edits are the additive `SELECT`/`LEFT JOIN` columns described above, not a change to any write, claim, settlement, or reconciliation statement in either file.
