- **#3395 (a #3388 post-merge review follow-up) — the anchor-UID repair sweep now DRAINS: every row it cannot answer is paced out of the head on a dedicated column, and the #1043 recovery's refusal is tested end to end.** #3342 bounded the sweep's reads per tick but left a drain hole: only a repair that THREW was deferred, so every non-throwing `unrepairable` outcome (`refused`, `no-candidate`, `no-receipt`, `reverted`, `tx-body-unavailable` on a pruned node) wrote nothing, and N ≥ `limit` persistently unanswerable rows re-took the whole oldest-first batch on every tick — a live phantom behind them was never reached (real-DB probe: 5 ticks of `{"attempted":4,"repaired":0,"unrepairable":4}`). The fix: `deferAnchorRepair` stamps `uid_repair_next_at` (migration 099, one nullable TIMESTAMPTZ, no backfill) guarded by `status = 'anchored'` and the row's own `tx_hash`, and the selector skips a row whose stamp is still in the future. The stamp replaces #3342's `updated_at` bump — that column is the receipt's monotonic epoch and `FIND_BY_AGENT_ADDRESS_SQL` breaks the merchant verifier's ties on `updated_at DESC`, so a state stamp there would reorder what a merchant is handed; the pacing write cannot. The #1043 recovery refusal keeps refusing with an accurate reason: the candidate-equality refusal that misnamed its cause is restructured so the reader returns OURS when a same-schema foreign-attester log precedes it (#3342's own criterion — the equality half was dead code), and what remains refused is a receipt where every pinned-schema log is attested by someone else, named as exactly that. `confirmAnchorUid` gained the `attestation_uid` compare-and-set `repairAnchoredUid` already had.

  **No custody or authority change.** No key material, signing, relaying, or payment execution moves; no spender, approval, or credential surface is created or widened. The sweep's writes stay on `agent_passports` alone (CAS UID swap, confirmation stamp, pacing stamp); nothing signs, nothing broadcasts, no client request gains a power. The pacing stamp is not readable as "verified" by any surface — `FIND_BY_AGENT_ADDRESS_SQL` is untouched — so the merchant verifier's answers cannot churn on it. The refusal restructuring NARROWS nothing that was accepted: a proven log was and is the only writable evidence; the change is which refusal reason names the failure and that a preceded-by-foreign-log tx now yields OURS instead of refusing the whole tx.

  **Chain reads:** an unanswerable row costs one bounded attempt per hour instead of the whole budget per tick (the drain); paced rows are billed zero reads inside their window. Everything else is unchanged in shape: receipt + tx body per attempted row, exactly as #3342 left it.

  **Corrections this entry makes to the #3342 shard (2026-09-26) below**, which the #3395 review found inaccurate: (1) "the mint path's reader semantics [are] deliberately untouched" — they were not: #3342 moved `readMinedAttestationUid`'s field reads inside the parse guard, so a lazily-failing log is now skipped as absence of evidence rather than thrown; (2) "the chain reads stay exactly what they were" — recovery grew a second `getTransaction` (one inside `readProvenAnchorUid`, one for calldata attribution); (3) the round-robin claim held only for rows the sweep can answer — the unanswerable class kept round-robining until this change; (4) "ours is chosen when a foreign log precedes it" held only for a foreign-SCHEMA log until this change enforced the criterion for the same-schema case.
