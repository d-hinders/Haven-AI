- **#3386** — two label/read-scoping fixes on the #3331 merchant-locked budget slice, found by independent review; neither widens authority. (1) A re-key's replacement grants (carry/steady/reanchor) now carry the old delegation's `agent_delegations.merchant_id` — a label only, never a caveat, never read by payment selection (`SELECT_DELEGATION_FOR_PAYMENT_SQL` is unchanged). The label is no longer frozen into the `carry_snapshot` at revoke/submit; the issue step resolves it unconditionally, once per replacement-producing entry, with a fresh by-hash read of the old row (`findDelegationTerms`), which survives the revoke (marked `revoked`, never deleted) and whose foreign key to `merchants` stays current (`ON DELETE SET NULL`) all the way to issue — including through `adoptAbandonedCarry`'s wholesale snapshot copy. `INSERT_REKEY_DELEGATION_SQL` additionally writes `merchant_id` through a `SELECT ... FROM merchants WHERE id = $N` subselect rather than the raw value, so a merchant deleted in the window between that read and this statement resolves to `NULL` instead of throwing an FK violation (23503) that would otherwise wedge the agent with no authority after the revoke, on every retry. `FIND_REUSABLE_PENDING_DELEGATION_SQL` excludes `rekey_id IS NOT NULL`, so carrying the label does not make an abandoned re-key's inert pending rows eligible for merchant-scoped build reuse. (2) `collectAssetTransferMethods` now scopes to the offer's recorded network (`accepts[0]`'s), the same scoping `collectPayTo` already used — narrowing what `merchant_catalog.asset_transfer_methods` records, never widening it. Existing rows keep their wide value until their next successful probe. A merchant-locked build now refuses (409) an offer whose ERC-7710 option sits on a different network than the one the row records; before this it could be issued and then strand rather than misdirect.

  Real-Postgres tests cover: a merchant-locked budget still listed by `GET /merchants/{slug}/budgets` after a full re-key walk (revoke → meter → issue → complete) resolves the label by the fresh by-hash read; a merchant deleted between metering and the replacement insert still lets issuance succeed with `merchant_id: null` (and, as a companion, that a merchant still present is still carried through the same subselect); the `rekey_id` reuse exclusion; `findDelegationTerms` reading `merchant_id` off both a merchant-locked and an ordinary row; and a two-network challenge driving the build route's 409. Mocked route tests cover what real Postgres cannot reach without standing up Fastify: the issue step reads `findDelegationTerms` exactly once per snapshot entry that produces a replacement piece, never for an entry that produces none (e.g. already expired), and ignores any `merchant_id` still present on a persisted `carry_snapshot` — only the fresh by-hash read decides the label now. Perimeter unchanged.
