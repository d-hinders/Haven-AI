- **#3386** — two label/read-scoping fixes on the #3331 merchant-locked budget slice, found by independent review; neither widens authority. (1) A re-key's replacement grants (carry/steady/reanchor, including through `adoptAbandonedCarry`'s wholesale snapshot copy) now carry the old delegation's `agent_delegations.merchant_id` — a label only, never a caveat, never read by payment selection (`SELECT_DELEGATION_FOR_PAYMENT_SQL` is unchanged). A snapshot persisted before this field existed falls back to a by-hash read of the old row (still present, marked `revoked`, never deleted) at issue time. `FIND_REUSABLE_PENDING_DELEGATION_SQL` now excludes `rekey_id IS NOT NULL`, so carrying the label does not make an abandoned re-key's inert pending rows eligible for merchant-scoped build reuse. (2) `collectAssetTransferMethods` now scopes to the offer's recorded network (`accepts[0]`'s), the same scoping `collectPayTo` already used — narrowing what `merchant_catalog.asset_transfer_methods` records, never widening it. Existing rows keep their wide value until their next successful probe. A merchant-locked build now refuses (409) an offer whose ERC-7710 option sits on a different network than the one the row records; before this it could be issued and then strand rather than misdirect. Real-Postgres tests cover a merchant-locked budget still listed by `GET /merchants/{slug}/budgets` after a re-key completes, the pre-fix-snapshot fallback read, the `rekey_id` reuse exclusion, and a two-network challenge driving the build route's 409. Perimeter unchanged.
