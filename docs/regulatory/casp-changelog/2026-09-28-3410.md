- **#3410 — the local MCP consent screen renders the agent's budget in whole tokens instead of atomic units, and the consent hash is untouched.** The first-launch screen (and the connector's setup-time consent through the same renderer) printed `up to 1000000 USDC` for a 1 USDC/day agent — an atomic number labelled as whole tokens on the one surface whose job is informed consent. Both reachable producers are atomic (the live read's `onchain.amount` = the backend's `budget_atomic`; the credential seed's `allowance_amount`, written by the connector from the setup response), so the fix is DISPLAY-ONLY conversion at render time: `renderConsentBlock` resolves decimals through the SDK token registry by symbol + chain (`resolveTokenBySymbol`, new additive `@haven_ai/sdk` export reading the same registry `resolveTokenFromAddress` uses) and formats through `formatTokenAmount` (new additive export, the atomic→human counterpart of `formatRemainingDisplay`). When the token cannot be resolved — an unknown symbol, or a known symbol on a chain that registers a different token (Gnosis carries USDC.e, not USDC) — the screen prints an explicit `25000000 FOO (atomic units)` label in connect's `describeApprovedBudget` fallback style, never a bare atomic number. The unreachable human-decimal `configuredAmount` fallback in the live-read mapping was removed (`onchain.amount ?? '0'`), so no human-decimal value can reach the atomic field.

  **No custody or authority change.** No key material, signing, relaying, payment execution, or spend path moves. The on-chain limit is enforced exactly as before by the agent's signed budget delegation — the screen merely describes it honestly now. The consent hash keeps covering the RAW ATOMIC strings (`computeConsentHash` hashes identity, tool names and `allowanceSummary` verbatim; nothing about its input moved), pinned two ways in `packages/mcp/src/consent.test.ts`: a literal hash for a fixed Earner-shaped input (`f91aa898426206cb`, computed against the pre-fix head) and a live≡seed byte-equality test. No installed sidecar `.ack.json` or `HAVEN_MCP_ACK` value is invalidated, and no consent re-prompt is triggered. No `ConsentInput`, `CredentialIdentitySeed`, `HavenCredentialAllowance` or `computeConsentHash` type or signature change — the only published-type edits are doc comments (`HavenAgentAllowanceSummary.configuredAmount` corrected from "atomic" to human-decimal; the value, wire and shape unchanged) and additive SDK exports. One decision recorded for the record: decimals resolve by SYMBOL + chain from the existing registry; the connector still writes no `token_address` into `agent_budget` (the alternative from the issue), and tokens outside the registry fall back to the explicit atomic label rather than a guessed conversion — stated here because the issue asks the choice be stated in the PR.

  Known limitation, stated not fixed: the seed is setup-time data; if the wallet owner edits the budget after setup and the live read then fails, the screen shows the stale seed budget as current.
