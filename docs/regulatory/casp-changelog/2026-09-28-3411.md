- **#3411 — `@haven_ai/mcp`'s legacy `idempotencyKey` argument spelling is refused by name, closing the #2366 window (money-path via the hosted `contracts.ts` copy fix).** The #2366 transition window — accept both `idempotency_key` and `idempotencyKey`, warn on the legacy spelling, drop it later — had a met but unrecorded removal condition: the warning first shipped on the `alpha`/`latest` channel in `0.1.35-alpha.0` (npm, published 2026-09-07) — a day after it first shipped on the `dev` channel, in `0.0.0-dev.202609061923.f3d53db` — and `latest` is several releases past it. The five local tools that take an idempotency key (`haven_send`, `haven_pay_mcp_tool`, `haven_quote_x402`, `haven_pay_x402_quote`, `haven_pay_x402`) now **refuse** any call that sets `idempotencyKey`, alone or alongside `idempotency_key`, with `IDEMPOTENCY_KEY_RENAMED`, before anything is contacted or spent. `idempotencyKey` stays **declared** in every schema rather than being deleted: the local MCP registers tools with a plain `z.object`, whose default strip mode would otherwise silently drop the undeclared key before the handler ran — the exact #2348 failure (a dropped idempotency key turns a retry into a second spend) this refusal exists to prevent. This is money-path because it also fixes the stale hosted-server copy in `packages/mcp-server/src/tools/contracts.ts`, which told a caller refused for sending `idempotencyKey` to the hosted surface that "the local MCP spells it idempotencyKey" — now false. The refusal message there is reworded to say the local surface refuses that spelling too and takes `idempotency_key`.

  **Perimeter unchanged.** No key material, signature, spend path, budget, recipient pin, delegation or on-chain enforcement changes. No route, schema field, or database migration changes. The public `toolSchemas` export changes MEANING — `idempotencyKey` was an accepted input and is now a refused one — but the export's shape (the set of declared keys per tool) does not change, so no consent-hash or advertised-schema recompute follows; `computeConsentHash` hashes identity, tool names and the allowance summary, never per-argument schema detail.

  **Not converged further.** The `quote` (local) vs `payment_required` (hosted) `haven_pay_x402_quote` divergence is a different-value-not-a-spelling case, unaffected and out of scope (owner decision 2026-09-06, recorded in `docs/architecture/08-local-vs-hosted-mcp.md`). The SDK's published LLM tool schemas and the REST `/x402/authorize` endpoint still take `idempotencyKey` — explicitly out of scope here, and the refusal message on this change does not claim otherwise (the prior "every other Haven wire contract uses idempotency_key" claim in the warning text and README is removed as false).

  Tests: `packages/mcp/src/spelling-window.test.ts` — inverted from proving the window to proving the refusal, over a real `Client` on `InMemoryTransport` (never the handler directly, since the MCP SDK strips undeclared keys before a handler runs and a handler-level test cannot tell a declared key from an undeclared one): legacy alone refused, modern alone accepted, both together refused (equal or not), and a per-tool regression proving `idempotency_key` reaches `haven.pay` / `haven.fetch` / `haven.quoteX402` on all five tools that take it (previously only `haven_send` was pinned). Both new guards — the refusal itself and the renamed internal carrier (`resolvedIdempotencyKey`, replacing the reused `args.idempotencyKey` field) actually forwarding the snake_case value — were mutation-proven red. `packages/mcp-server`'s contracts tests covering `haven_send`/`haven_pay_mcp_tool`/`haven_quote_x402`/`haven_pay_x402_quote` refusal copy were re-run and pass unchanged (no test pinned the exact stale sentence).
