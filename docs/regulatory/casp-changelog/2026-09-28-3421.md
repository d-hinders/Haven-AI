- **#3421** — Haven's catalog stops advertising the dev demo merchant's
  skip-settle QA fixture as a purchasable offer. **No authority, custody or
  execution boundary moves and nothing new is grantable** — one operator
  catalog row's `status` changes from `active` to `delisted` (migration
  `102_delist_skip_settle_catalog_row`), matched on its full unique key
  (`resource_url`, `tool_name`, `tool_arguments`) PLUS `network`, so only the
  Sepolia `CloudNest 50 GB — demo merchant (Base Sepolia)` row
  (`buy_cloud_storage {"tier":"50gb"}` at `eip155:84532`) is touched — never
  its Base-mainnet twin (settles normally), never the Sepolia 200 GB / 1 TB
  siblings, never a hand-edited row. `GET /catalog` (`routes/catalog.ts`) and
  `refreshCatalog` (`modules/catalog/merchant-catalog.ts`) both already filter
  `status != 'delisted'`, so this one `UPDATE` removes the row from discovery,
  quote and prepare (`CATALOG_ENTRY_NOT_FOUND`) and the hourly probe in one
  step; `down()` restores only that row, for symmetry. The row was the dev
  merchant's `MERCHANT_SKIP_SETTLE_PRODUCT` fixture (`storage_50gb`,
  chain-gated to 84532 in code) surfacing as an ordinary catalog offer — an
  agent reaching it through `GET /catalog`/`haven_discover_tools` rather than
  the merchant's own disclosed `qa_fixture` marker (#2989) had no way to know
  its purchase would never settle on-chain. Owner decision: delist, not
  relabel in migration 064's Minifetch style — this fixture is not meant to
  stay catalog-reachable. A new qa-dev tripwire in
  `x402-catalog-guided-purchase` (`packages/qa-agent/src/scenarios/
  x402-catalog-guided-purchase.ts`) now fails any run where a product the
  merchant's own `/.well-known/haven-demo-merchant` document marks
  `qa_fixture` has a listed catalog row on that host, so a future re-seed,
  hand-edit, or `MERCHANT_SKIP_SETTLE_PRODUCT` reassignment cannot drift back
  silently. Mutation-tested: widening the migration's `WHERE` to drop the
  `tool_arguments` predicate lets it also delist the Sepolia 200 GB sibling
  (caught by the "other rows unchanged field-by-field" migration test); the
  `network` predicate, kept to match the spec's full-key instruction exactly,
  cannot currently diverge from `resource_url` alone — 058's own unique index
  has no `network` column, so two rows sharing this migration's
  `resource_url`/`tool_name`/`tool_arguments` cannot coexist, and the
  Sepolia/mainnet rows already differ by `resource_url` (different hosts) —
  recorded in the migration's own doc comment rather than asserted by a test
  that cannot fail. Disabling the qa-dev tripwire's check lets a listed
  `qa_fixture` product pass (caught by the new scenario unit test asserting a
  FAIL detail on a listed fixture row).
  No route, no probe, no settlement, no wallet or delegation code changed —
  `routes/catalog.ts`, the MCP server and `packages/demo-merchant-mcp/src/*`
