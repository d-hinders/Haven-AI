# CASP shard — #3439: a re-key's own pending row is refused outside that re-key's completion, and the stalled-issue race that could plant one is closed

- **#3439** — two related gaps on the delegation rail's re-key path, closed together
  because both bear on which grant is live for an agent. (1) The ordinary
  `POST /agents/:id/delegations/:hash/activate` route selected `agent_delegations`
  rows by `(agent_id, delegation_hash)` and `status = 'pending'` only — nothing
  excluded a re-key's own replacement row (`rekey_id IS NOT NULL`), which is
  activated correctly only by that re-key's own completion
  (`ACTIVATE_REKEY_DELEGATION_SQL` inside `completeRekey`). The route now selects
  `rekey_id` and refuses any row that carries one, with a structured
  `REKEY_DELEGATION_NOT_ACTIVATABLE` error, before the slot sweep runs; the same
  filter (`AND rekey_id IS NULL`) is added to `ACTIVATE_PENDING_DELEGATION_SQL` as
  a backstop. (2) `insertRekeyDelegation`'s existing lock,
  `lockOwnedAgentForRekeyDelegation`, only proved that SOME re-key of the agent was
  in flight, not the one calling it — so a re-key R1's issue request, stalled after
  passing its own stage check and then abandoned by the owner, could resume and
  insert rows while a DIFFERENT, successor re-key R2 was the one actually in
  flight (past R2's own revoke step). Those rows landed `pending` under the key R2
  eventually installs and were never revisited by anything in the re-key
  lifecycle. `insertRekeyDelegation` now re-checks, under the same agent-row lock,
  that THIS re-key's own row is still `stage = 'metered'` — the stage its issue
  request checked before building rows, and the only stage `markIssued` itself
  expects.

  Reaching either gap requires a `pending` row whose `delegate` field already
  matches the agent's CURRENT key — which needs a re-key to have reused an
  abandoned predecessor's parked address, itself requiring the owner's
  cooperation and time (a stalled network round trip, then an explicit abandon).
  No shipped UI reaches it: build reuse never hands out a `rekey_id` row (#3386),
  the dashboard activates only the hash its own build returned, and the re-key issue/complete flow is the only path that ever presents a
  `rekey_id`-bearing row for signing.

  Authority and custody argument: both fixes only narrow WHICH already-existing,
  already-signed-off row a request may act on and WHEN a write may land — neither
  changes who can sign, what a signature authorizes on-chain, or the caveat stack
  a redeemed delegation is checked against. The route guard is a refusal added
  before an activation that would otherwise proceed exactly as before for every
  non-re-key row (`error_code` addition only; no new success path). The repository
  guard removes a write that should never have been possible under the documented
  re-key ordering ("revoke must precede issue, never the reverse" — #1694), not a
  write anything currently depends on: it does not touch `completeRekey`, which
  activates only the rows the complete route lists for that `rekey_id` via
  `listPendingRekeyDelegations`. Both changes are
  DB-transaction-local; nothing on-chain is touched, retried, or re-ordered.
  Perimeter unchanged.

  Tests: real-Postgres. The route guard is proven twice — a pattern-mocked route
  test (`agent-delegations.test.ts`) pinning the exact refusal shape and that the
  activation transaction and every network read (account derivation, deploy) are
  never reached, and a full real-DB route test
  (`agent-delegations-rekey-row-guard.test.ts`) that seeds an abandoned re-key's
  `pending` row with `delegate` matching the agent's current key and drives
  `POST .../activate` through the real Fastify route with real Postgres — plus a
  same-file characterization proving the ALREADY-closed path (a row revoked by a
  successor's own revoke step) is refused on `status`, not this guard, so the new
  test cannot be satisfied by the old barrier alone. The SQL backstop is proven in
  isolation, calling `activatePendingDelegation` directly with no route in front
  of it (`delegation-budgets.test.ts`), alongside a control asserting an ordinary
  `rekey_id: NULL` row still activates. The stalled-issue race is proven by
  constructing the exact interleaving from the issue body — R1 reaches `metered`,
  is abandoned, R2 opens and reaches `metered` itself, then R1's insert is
  attempted — asserting it is refused and no row exists
  (`agent-rekeys.test.ts`), alongside a control proving R1 can still insert while
  R1 itself is the metered re-key in flight (the guard is scoped, not a blanket
  refusal). All three guards are mutation-proven: removing the route check,
  removing the SQL backstop, and removing the stage re-check each turn their
  respective test red on an isolated, restored `cp` backup of the file (never
  `git checkout`/`stash`). The existing re-key activation, completion (including a
  normal non-abandoned completion) and merchant-carry real-DB suites stay green
  unmodified in substance (five pre-existing repository tests were updated to
  progress their seeded re-key to `metered` before calling
  `insertRekeyDelegation` directly, since that is now a real precondition the
  production issue route already satisfied — not a relaxed assertion).
