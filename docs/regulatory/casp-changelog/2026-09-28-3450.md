# CASP shard — #3450: two concurrent re-key issue calls on one re-key can no longer both insert replacement rows

- **#3450** — closes the concurrent-issue race #3439's own review flagged as a
  tracked follow-up. Two concurrent `POST /agents/:id/rekey/:rekeyId/issue`
  calls on the SAME re-key both pass `assertStageAllows('issue')` on the stage
  `loadStep` reads without a lock, and — before this fix — each call's
  `insertRekeyDelegation` ran in its OWN transaction per piece, with the stage
  flip to `issued` (`markIssued`) running once, separately, after a call's
  whole piece loop. A second call whose `nextDelegationVersion` read landed
  after the first call's own insert had already committed, but before that
  first call reached `markIssued`, built a DIFFERENT hash for the same piece
  (the #827 salt is a function of `version`) and landed a genuine second
  `pending` row — #3439's own stage re-check (`agent_rekeys ... stage =
  'metered' FOR UPDATE` inside `insertRekeyDelegation`) did not stop this,
  because the stage stays `metered` until ONE of the two calls reaches
  `markIssued`. Per the #3450 spec review's uncommitted scratch test against a
  fresh checkout of both trees (40 staggered 0–19ms trials each): `origin/dev`
  left an extra row in 23/40 trials, #3439's own head in 11/40 — and
  completion with the "winning" call's signatures then answered `400
  missing_signature`, naming a hash the caller never received, in every one of
  those trials. The only way out was abandoning the re-key. The shipped suite
  reproduces the same defect deterministically rather than statistically —
  see the Tests paragraph below, `agent-rekey-issue-concurrent.test.ts`.

  The fix: the issue route's whole piece-build loop plus `markIssued` now run
  inside ONE transaction
  (`withRekeyIssueTransaction`/`infra/transaction.ts#withTransaction`). Every
  DB call the loop makes — `findDelegationTerms`, `nextDelegationVersion`,
  `insertRekeyDelegation`, `markIssued` — is threaded through that SAME
  transaction client, so a `steady` piece can see its own call's earlier
  `carry` piece's still-uncommitted insert (unchanged version reuse would have
  corrupted the #827 salt), and a concurrent second call blocks on the first
  insert's `agents` row lock until the whole transaction commits or rolls
  back. Once released, the second call re-runs #3439's own `stage = 'metered'`
  re-check as a fresh READ COMMITTED statement against the now-committed row —
  unchanged code, just now correct because of where it runs — and finds it
  `issued`, inserting nothing. A failure part-way through a single call's own
  loop (a thrown DB error, or a later snapshot entry's `carry_refused` after
  an earlier entry already inserted) now rolls back every piece that call
  built, rather than leaving them committed for a retry to orphan.

  This required `withTransaction` to recognise an executor that is already a
  checked-out transaction client, which it did not: it treated ANY executor
  with a `connect` method as poolable, and a real `pg.PoolClient` has
  `connect` (inherited from `Client.prototype`) as well as `release` — so
  nesting `insertRekeyDelegation(row, tx)` inside the new outer transaction
  rejected with "Client has already been connected. You cannot reuse a
  client." (reproduced on real Postgres). `withTransaction` now checks
  `release` first: present means already checked out, run inline; the
  poolable case (has `connect`, never `release`) is unchanged. No other
  caller of `withTransaction` changes behaviour — every existing call passes
  either a genuine pool (no `release`) or an executor with neither method —
  `withDelegationBuildSlotLock`'s query-only `joined` view in production, and
  the fake in the unit test — both of which ran inline before and after
  #3450. The only raw checked-out `PoolClient` passed into a
  `withTransaction`-wrapped repository is this change's own issue route.

  Authority and custody argument: no signature, key role, delegation shape or
  caveat enforcer changes. This closes a WRITE race that could otherwise land
  an authority-bearing `pending` row the owner never saw a signing payload
  for and can never complete (only abandon); the fix narrows WHEN a write may
  land and WHERE it commits, not who can sign or what a signed delegation
  authorizes on-chain. `#3439`'s stage re-check is kept verbatim, not
  replaced — this issue changes only the transaction boundary it runs inside.
  The one network call this route makes (`computeHybridAccountAddress`) is
  unchanged: it still runs before the transaction opens, so no RPC round trip
  is held under a lock. Lock order (`agents` then `agent_rekeys`) is
  unchanged; `abandonRekey` and `completeRekey`'s own lock orders are
  untouched, so no new cycle is introduced. DB-transaction-local; nothing
  on-chain is touched, retried, or re-ordered. Perimeter unchanged.

  Tests: real-Postgres throughout, only `computeHybridAccountAddress` mocked.
  A deterministic (not statistical) concurrency test
  (`agent-rekey-issue-concurrent.test.ts`) pins the interleaving with a
  control point on `insertRekeyDelegation` — the first call across both HTTP
  requests pauses immediately after its own first insert resolves, until the
  test explicitly resumes it, which is the exact window the corrected issue
  body requires. The two calls are synchronised by polling for a backend
  blocked SPECIFICALLY by the winner's own captured pid
  (`$1 = ANY(pg_blocking_pids(pg_stat_activity.pid))`, `$1` = the winner's
  `pg_backend_pid()`), not a fixed sleep and not "any lock in the database,"
  bounded at 2s. It asserts the outcome shape (exactly one 201, its
  `delegations`' roles and hashes checked, one 409 with the WHOLE body
  checked against `origin/dev`'s exact reply, the committed row count and
  version numbers matching only the successful call's own built delegations,
  and completion with that call's signatures returning 200) without assuming
  which of the two HTTP calls wins, since that answer differs between the
  buggy and fixed trees. A partial-failure suite
  (`agent-rekey-issue-partial-failure.test.ts`) covers a thrown DB error, a
  later-entry `carry_refused` after an earlier entry already inserted, and a
  later-piece 502 build failure after an earlier piece already inserted —
  each asserting zero rows, the stage still `metered`, and (for the two
  structured refusals) the WHOLE reply body against `origin/dev`'s exact
  shape. A real-`pg.PoolClient`
  test (`agent-rekeys.test.ts`) calls the transactional insert path with a
  genuine checked-out client, not a fake, and proves the insert ran INLINE on
  it (visible on that client's own open transaction, absent on a fresh
  connection until `COMMIT`) rather than opening a second, independent
  transaction. A mocked-shape unit test
  (`infra/__tests__/transaction.test.ts`) proves the `release`-based
  discrimination directly. All four new/changed guards are mutation-proven
  against isolated, restored `cp` backups of the pre-fix files (never `git
  checkout`/`stash`): the loop moved outside the transaction, a version read
  left on `pool` instead of the transaction client, the `PoolClient`
  discrimination reverted to checking `connect` alone, and one early return
  left as a `return` instead of a thrown sentinel. The existing re-key
  suites (issue-clock, merchant-label, revoke-submit, signing,
  `request-validation-3032.test.ts`, agent-rekeys, rekey-\*,
  merchant-budget-survives) and `transaction.test.ts` stay green. Two mocked-
  route suites (`agent-rekey-issue-clock.test.ts`,
  `agent-rekey-issue-merchant-label.test.ts`) were updated to mock
  `withRekeyIssueTransaction` too, so they stay DB-free; merchant-label's one
  exact-call-argument assertion (`findDelegationTerms`) was additionally
  updated to expect the transaction-client argument now threaded through it,
  not relaxed. `agent-rekey-issue-clock.test.ts` also gained a whole-body
  test for the `IssueMarkIssuedFailedError` mapping (`markIssued` returning
  `null` → `{ error: 'rekey_out_of_order' }`, no other fields) — the fourth
  and last of the four sentinel-mapped replies to get that treatment.

  **Round-1 review findings, fixed in this same change:** (F1, blocker) the
  `carry_refused` 409 mapping sent `detail: err.message` against the
  SENTINEL error (whose `message` is the literal class-tag string
  `"carry_refused"`, from `super('carry_refused')`), not the sentinel's own
  `detail` property carrying `planCarry`'s real, owner-facing explanation —
  fixed to `detail: err.detail`, and every refusal-body assertion in the
  partial-failure and concurrency suites now checks the WHOLE reply body with
  `toEqual` against `origin/dev`'s exact shape, not one field. A new 502
  build-failure test covers the previously-untested rollback path. (F2,
  medium) the concurrency test synchronised the two HTTP calls with a fixed
  `setTimeout(20)`, which is flaky under load — proven by re-running it with
  the second call's own `findRekey` read artificially delayed, which
  reproduced a false failure on the FIXED tree every time with the fixed
  sleep. Replaced (round 1) with a poll on
  `pg_stat_activity.wait_event_type = 'Lock'`.

  **Round-2 review finding, fixed in this same change:** (F2', blocker) the
  round-1 poll counted ANY backend blocked on ANY lock in the shared database
  — vitest workers share one Postgres role and database, and
  `db-harness-reset-contention.test.ts` deliberately creates lock waits of
  its own — so a foreign session merely waiting on an unrelated table made
  the poll return `true` immediately, before the second HTTP call had even
  reached Postgres, and `resumeWinner()` fired too early. Per the round-2
  code review's reproduction (setup not committed: a second `haven` session
  waiting on an unrelated `ACCESS EXCLUSIVE` lock, plus a delayed
  `findRekey`), the round-1 poll failed 3/3 with `rekey_out_of_order`. Fixed by scoping the poll to the WINNER's own
  backend pid: `insertRekeyDelegation`'s wrapper captures
  `SELECT pg_backend_pid()` on the winner's own still-open transaction client
  the moment it pauses, and the poll becomes
  `SELECT 1 FROM pg_stat_activity WHERE $1 = ANY(pg_blocking_pids(pid))` with
  that pid — true exactly when some backend is blocked BY the winner, not by
  anything else in the shared database. Under the same uncommitted setup the
  builder's re-run passed 3/3 with the scoped poll, and the round-3 code
  review independently reproduced it (3/3 with a 300 ms-delayed loser, 2/2
  undelayed, a 2 s hard bound) and saw the pre-fix route and repository
  files still fail 3/3 (`cp` swap).
