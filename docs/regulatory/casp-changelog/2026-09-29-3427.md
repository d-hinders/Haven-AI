- **#3427** — the agent's payment key signs a buyer-side x402 tax
  declaration (wg-tax #5 §2.2) and the paid EIP-3009 merchant retry gains
  `X-Tax-Declaration: <base64url(JSON)>`. **No authority, custody or
  execution boundary moves and nothing new is grantable** — the signature is
  produced locally by the same delegate EOA that already signs the EIP-3009
  payment authorization (§2.2 signer-is-payer; no new key holder, no new
  spending ability), through a builder that lives on the SDK edge beside the
  other signing guards (`packages/sdk/src/tax-declaration.ts`, re-exported
  from `@haven_ai/sdk/edge`) and builds the EIP-712 typed data locally from
  exactly the §2.1 fields: content arriving with `principalId` or
  `principalAttributionHash` pre-set, with any field beyond the five §2.1
  fields, or on a settlement network the SDK cannot name as CAIP-2 eip155 is
  REFUSED, never stripped and signed — each refusal mutation-proven (removing
  the guard reddens `tax-declaration` in the SDK suite). `principalId`'s
  chain comes only from the accepted payment option's `network`
  (Base → `eip155:8453`, Gnosis → `eip155:100`), never from configuration,
  and `principalAttributionHash` is `sha-256:<hex>` over the JCS bytes of
  `{ principalId }`, pinned to a fixed test vector. The header attaches only
  in `MerchantCompletion.retryRequest` — the one seam `fetch`,
  `payX402Quote` and `resumeX402Payment` all reach — only on the EIP-3009
  scheme (told apart the same way `x402PaymentHeaderNamesFor` does), only
  after the payment payload was built, and is deleted rather than left stale
  when not minted; an erc7710 payment, the first unpaid request, a "not
  available" content answer, a 404 (older backend), or any endpoint failure
  proceeds without the header. The hosted, keyless `completeX402MerchantCall`
  construction binds neither the resolver nor a delegate key, so it is
  structurally header-free, and `deliverPayment` (shared with that keyless
  path) is untouched. Census-tested: no request to Haven's API and no
  payment-payload body carries the header value or the declaration fields
  (seller-only per §2.3 — never `resource_url`, `description` or `reason`,
  never any facilitator-visible field). No route, no probe, no settlement,
  no wallet, delegation or catalog code changed. Perimeter unchanged.
