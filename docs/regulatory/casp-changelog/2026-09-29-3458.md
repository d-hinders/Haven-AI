- **#3458** (epic #3457) — the delegate balance monitor reads balances in
  batches. It used to await one `balanceOf` `eth_call` per active agent, every
  hour and at every boot. It now makes one Multicall3 `aggregate3` request per
  chunk of 200 delegates per chain (`infra/chain/batched-token-balances.ts`).
  **The DETECT control is unchanged in what it sees:**
  - the same delegates are scanned (every active agent with a delegate; the
    scan is deliberately not narrowed, so a balance Haven never sent is still
    found);
  - the same four states are classified, and the same lingering and dust
    alerts fire.

  Three properties keep it a faithful read:
  - **Only the dedicated RPC endpoint answers.** There is no fallback node, as
    before: the monitor read through the single-node ethers provider, and a
    lagging second node answering "zero" would be a silent miss.
  - **Chunks go out one at a time,** never as a burst.
  - **A failed read skips only the delegates it covered, for that round.** A
    reverted sub-call skips its one delegate; a failed request skips its
    chunk. Before, a failed read skipped its one delegate. The next hourly
    tick reads them again.

  **No custody, authority or execution change:** the monitor stays read-only
  and moves no funds; no key, delegation, budget, route or signing surface is
  touched.

  **Tests.** The request count, the peak concurrency, and each failure mode
  are pinned against a real viem client in
  `infra/chain/__tests__/batched-token-balances.test.ts`. The one-read-per-chain
  grouping is pinned in `infra/__tests__/delegate-balance-monitor.test.ts`.
  Each guard was removed in turn and its test went red. Perimeter unchanged.
