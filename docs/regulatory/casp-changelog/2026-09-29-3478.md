- **#3478 (slice 2)** — `packages/frontend/src/components/AddFundsModal.tsx` gains a
  faucet link and stops offering Coinbase Onramp on testnet accounts. Both are gated
  on the same fact: `chainId != null && isTestnetChain(chainId)` (`AddFundsModal.tsx:67`,
  reusing `isTestnetChain` from `packages/frontend/src/lib/marketplace.ts`, itself
  `isRegisteredChain(chainId) && getFaucetUrl(chainId) !== undefined` from
  `@haven_ai/core`). **The gate reads the selected ACCOUNT's `chainId`** —
  `DashboardClient.tsx:1193` passes `selectedActionAccount?.chain_id` in as the prop —
  **never the deployment's `NEXT_PUBLIC_HAVEN_CHAIN_ID`**, which only sets the default
  pre-selection; Base (8453) and Base Sepolia (84532) are both offered as an account
  chain in every environment, so a deployment-keyed gate would show a faucet for a
  Base-mainnet account on dev and hide it for a Base Sepolia account on production.
  `AddFundsModal.test.tsx` proves this directly: `NEXT_PUBLIC_HAVEN_CHAIN_ID=84532` is
  set at module scope for the whole file (`vi.hoisted`, before import) while the named
  8453 test renders `chainId={8453}` and asserts the onramp shows and no faucet
  renders — a gate that read the env var instead would fail exactly that test, and a
  mutation forcing the gate to `true` was run and reverted to confirm it (all four other
  tests in the file, which assert no-onramp/no-faucet states, turn red under that
  mutation).

  **No authority, custody or execution boundary moves.** The faucet link is a plain
  `<a target="_blank" rel="noopener noreferrer">` to `https://faucet.circle.com`
  (`getFaucetUrl`, core's existing testnet-only field, unchanged) — Haven originates no
  request to it, holds no funds, and the copy states plainly that Circle is the source
  and the funds are test funds with no value; it never says Haven sends or holds funds
  (`AddFundsModal.tsx:232-260`, `docs/regulatory/casp-risk-guardrails.md` § Product
  Copy Rules). Hiding the onramp on testnet accounts is strictly **subtractive**: the
  onramp's own gate (`ONRAMP_APP_ID && accountAddress && chainConfig`) is unchanged and
  only gains one more `&&` conjunction, so it can only ever narrow when the control
  renders, never widen it. `getFaucetUrl` throws on an unregistered chain id
  (`core/src/chains.ts:221-225`), same as `getChainConfig`; the faucet gate only calls
  it once `isTestnetChain` has already confirmed the id is registered
  (`isRegisteredChain` short-circuits first), so the throwing path is structurally
  unreachable from this component, verified by a passing test that renders an
  unregistered chain id (999999) without throwing and asserts no faucet link.

  Reachable states covered: a Base mainnet account (8453, onramp shown, no faucet), a
  Base Sepolia account (84532, faucet shown, no onramp), a registered chain with no
  faucet (Gnosis, 100 — `isTestnetChain` requires both `isRegisteredChain` AND a
  `faucetUrl`, so a testnet-less registered chain gets neither control), an unresolved
  chain (`chainId` absent) and an unregistered chain (present but not in either
  registry) — all four render no faucet and no crash.

  Perimeter unchanged: no route, key, signer, or delegation touched; this changes only
  what a dialog links to and which button it shows.
