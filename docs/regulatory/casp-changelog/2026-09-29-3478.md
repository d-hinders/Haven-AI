- **#3478 (slice 2)** — `packages/frontend/src/components/AddFundsModal.tsx` gains a
  faucet link and stops offering Coinbase Onramp on testnet accounts. Both are gated
  on the same fact: `chainConfig != null && isTestnetChain(chainConfig.chainId)`
  (`AddFundsModal.tsx:70`, reusing `isTestnetChain` from
  `packages/frontend/src/lib/marketplace.ts`, itself
  `isRegisteredChain(chainId) && getFaucetUrl(chainId) !== undefined` from
  `@haven_ai/core`). Gating on `chainConfig` rather than the bare `chainId` means
  `isTestnetChain` only ever runs on an already-resolved chain, so `chainName` is
  never null wherever the faucet card renders and the copy needs no null fallback.
  **The gate reads the selected ACCOUNT's `chainId`** — `DashboardClient.tsx:1193`
  passes `selectedActionAccount?.chain_id` in as the prop — **never the deployment's
  `NEXT_PUBLIC_HAVEN_CHAIN_ID`**, which only sets the default pre-selection; Base
  (8453) and Base Sepolia (84532) are both offered as an account chain in every
  environment, so a deployment-keyed gate would show a faucet for a Base-mainnet
  account on dev and hide it for a Base Sepolia account on production.

  `AddFundsModal.test.tsx` proves this directly: `NEXT_PUBLIC_HAVEN_CHAIN_ID=84532`
  is set at module scope for the whole file (`vi.hoisted`, before import) while the
  named 8453 test renders `chainId={8453}` and asserts the onramp shows and no
  faucet renders. Two mutations were run and reverted (`cp` backup, not
  `git checkout`) to prove both gates are load-bearing:
  - Gating on the deployment's chain instead of the account's
    (`isTestnetChain(Number(process.env.NEXT_PUBLIC_HAVEN_CHAIN_ID))`, or
    `isTestnetChain(DEFAULT_CHAIN_ID)`) turns 2 of 7 tests red: the named 8453
    test (`offers the onramp and shows no faucet on a Base mainnet account
    (8453)...`) and the Gnosis test (`shows the onramp and no faucet link on a
    Gnosis account (100, a mainnet)`). A variant that also dereferences a null
    `chainConfig` crashes three more tests with a TypeError, which is not a gate
    assertion.
  - Dropping the `depositInstructionsAvailable` conjunct from the faucet card's
    render condition turns exactly 1 test red: `shows no faucet card on a Base
    Sepolia account with no address yet` — the one test built to catch it.

  **No authority, custody or execution boundary moves.** The faucet link is a plain
  `<a target="_blank" rel="noopener noreferrer">` to `https://faucet.circle.com`
  (`getFaucetUrl`, core's existing testnet-only field, unchanged) — Haven originates
  no request to it and holds no funds. The copy (`AddFundsModal.tsx:251-254`) is:
  "Get free {chainName} USDC from Circle's faucet. It's test money with no value,
  and it comes from Circle, not Haven. Pick USDC and {chainName} there, then paste
  your account address from above." It names Circle as the source and states the
  money has no value; the "comes from Circle, not Haven" claim is scoped to this
  link, not restated as a Haven-never-touches-funds product-wide claim (review
  round 1 M1 — `docs/regulatory/casp-risk-guardrails.md` § Product Copy Rules).
  The "from above" reference is gated on `depositInstructionsAvailable`
  (`AddFundsModal.tsx:243`) — the SAME condition that renders the address card
  above it — so the faucet card never promises an address that is not on screen
  (review round 1 M2).

  Hiding the onramp on testnet accounts is strictly **subtractive**: the onramp's
  own gate (`ONRAMP_APP_ID && accountAddress && chainConfig`) is unchanged and only
  gains one more `&&` conjunction (`&& !isTestnet`), so it can only ever narrow when
  the control renders, never widen it. `getFaucetUrl` throws on an unregistered
  chain id (`core/src/chains.ts:221-225`), same as `getChainConfig`; the faucet
  gate only calls it once `isTestnetChain` has already confirmed the id is
  registered (`isRegisteredChain` short-circuits first), so the throwing path is
  structurally unreachable from this component, verified by a passing test that
  renders an unregistered chain id (999999) without throwing and asserts no
  faucet link.

  Reachable states covered: a Base mainnet account (8453, onramp shown, no
  faucet), a Base Sepolia account (84532, faucet shown once an address is on
  screen, no onramp), a Base Sepolia account with no address yet (no faucet card,
  no "from above" claim), a registered MAINNET chain with no faucet (Gnosis, 100
  — `isTestnetChain` requires both `isRegisteredChain` AND a `faucetUrl`, so it
  gets no faucet and keeps the onramp when configured, exactly like Base), an
  unresolved chain (`chainId` absent) and an unregistered chain (present but not
  in either registry) — the last two render no faucet, no onramp and no crash.

  Perimeter unchanged: no route, key, signer, or delegation touched; this changes
  only what a dialog links to and which button it shows.
