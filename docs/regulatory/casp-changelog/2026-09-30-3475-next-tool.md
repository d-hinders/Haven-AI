- **#3475 follow-up** — `haven_report_x402_outcome` names
  `haven_report_settlement_evidence` as the next tool on an eip3009
  acceptance with no merchant settlement recorded yet, instead of answering
  "no tool follows" unconditionally.

  A live purchase on #3479's own eip3009 canary showed the gap: an agent
  without the Haven skill never learns it can hand Haven the merchant's
  `PAYMENT-RESPONSE.transaction`, because the server's own next-step fields —
  which the hosted instructions tell every agent to follow before prose —
  said `next_action: none` and omitted `next_tool` on every `accepted`
  outcome. Only the skill's prose paragraph carried the hint.

  Per the owner decision (2026-09-30, review round 1 final shape): an
  `accepted` outcome on a plain-HTTP eip3009 payment with no merchant
  settlement recorded yet now returns `next_tool:
  haven_report_settlement_evidence`, `next_arguments: { payment_id }`, and a
  reason naming the conditional (pass `PAYMENT-RESPONSE.transaction` as
  `settlement_tx_hash` if the merchant returned one; otherwise the purchase
  is already complete). `next_action` is UNCHANGED by the offer — it stays
  the status re-read's own answer (or the pre-existing per-outcome default,
  `none` on acceptance): review round 1 rejected reusing
  `AgentPaymentNextAction.AwaitingSettlementEvidence`, whose published
  meaning (an erc7710 payment past its settlement window with no verified
  evidence) is a different fact, so the offer rides `next_tool` /
  `next_arguments` / `reason` only and the enum's meaning needs no change.
  `haven_report_x402_outcome` itself is unchanged — still no `tx_hash`
  argument, per its #2292 contract. Rejected outcomes, erc7710 payments, a
  non-eip3009/unknown scheme, and a payment whose settlement is already
  recorded all keep the pre-existing "no tool follows" answer.

  **What decides the branch:** `GET /machine-payments/:id/status`
  (`packages/backend/src/modules/payments/agent-payment-status.ts`) gains two
  additive, read-only fields — `settlement_scheme` (`'eip3009' | 'erc7710' |
  null`; from `machine_metadata.settlement_scheme`, the same read
  `isFundedX402AwaitingMerchantLeg` already performs, narrowed to `null` for
  any stored value outside the declared enum) and
  `merchant_settlement_recorded` (`true`, omitted otherwise, from the same
  `machine_metadata.merchant_settlement_tx_hash` #3475 introduced). Nothing
  is written by this read; it exposes an existing internal fact. The hosted
  tool reads both off the SAME status re-read it already performed after
  writing the report — no second backend call.

  **Why `haven_report_settlement_evidence`'s `settlement_tx_hash` became
  optional:** Haven does not hold a settlement hash at report-outcome time,
  so the offered `next_arguments` can only carry `payment_id`. Making the
  argument optional on the schema is what makes that a genuinely callable
  next step rather than a hint the strict argument-shape validation would
  reject. A call that omits `settlement_tx_hash` SUCCEEDS as a no-op
  (`recorded: false`, `next_action: none`, zero backend calls) rather than
  refusing — review round 1's S3: an agent following `next_tool` /
  `next_arguments` verbatim must never get an error for doing exactly that,
  and the merchant may simply have returned no hash, which is not an error
  condition. The tool still never records evidence without an actual hash to
  verify; nothing is written on that path.

  **No custody or authority change:** nothing is signed, submitted or moved.
  This is a response-shape and next-step-routing change over data Haven
  already held; the two new status fields are read-only projections of
  existing `machine_metadata`, and the loosened tool argument only changes
  which shapes are well-formed input, not what a well-formed call with a real
  hash does (unchanged: `observeEip3009MerchantSettlement`,
  `verifySettlementTransferTx`, the per-hash advisory lock). No key,
  signature, delegation, caveat, budget or recipient pin changes.

  Perimeter unchanged.
