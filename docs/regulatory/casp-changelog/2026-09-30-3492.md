- **#3492** — a replayed x402 idempotency key whose erc7710 payment had
  already SETTLED could still be refused as over-budget by the #3054
  server-side pre-check `POST /machine-payments/budget-precheck`: step 5b of
  `haven_prepare_catalog_purchase` ran the pre-check before authorize, and
  the pre-check had no idempotency key to look the intent up by, so it
  compared the quote against the now-lower remaining budget and could refuse
  a purchase that had already moved money — recording a false
  `delegation_budget_exceeded` row in the `payment_refusals` ledger
  (`source: 'hosted_prepare'`) for money that already settled.
  `haven_pay_mcp_tool` never had this bug: its authorize call runs the #961
  replay lookup (`findX402IntentByIdempotencyKey`) before its own #2082
  pre-check, so it always answered from the stored settlement first.

  **The fix is server-side, scoped to erc7710.** `budget-precheck` accepts
  an optional `idempotencyKey`. It runs the SAME lookup authorize's replay
  uses, and when the row is a SETTLED erc7710 payment matching the exact
  quote being pre-checked — `confirmed` + a `tx_hash`,
  `settlement_scheme: 'erc7710'`, same token/amount/payee/resource, no
  task- or sub-budget pin — it answers `{ sufficient: true, replay: true }`
  WITHOUT calling `refuse()`: no ledger write, and no fabricated remaining
  figure (`remaining_atomic` still reports the true, now-spent number; only
  the refusal write is skipped). Every other shape — no row, an unexpired
  `pending_signature` child (which WOULD still revert on-chain against a
  spent budget, so it must still refuse here), a key collision against a
  different payee/resource/token/amount, a task/sub-budget-scoped row, or a
  settled EIP-3009 row — falls through to today's compare unchanged,
  refusal branch included. EIP-3009 was deliberately out of scope for THIS
  fix, not because the authorize-side replay would refuse it — it would
  not: `delegationReplay`'s confirmed+tx_hash branch (`replay.ts:89-110`)
  answers its stored 200 for ANY settlement scheme, so a settled 3009
  replay never reaches a second authorize either. The pre-check's false
  over-budget refusal and ledger row on a settled 3009 replay was the SAME
  bug this issue fixes for erc7710 — left open deliberately, as a known
  follow-up, closed by #3527 (see its own CASP shard).
  `haven_prepare_catalog_purchase`'s step 5b forwards `args.idempotency_key`
  onto the pre-check call; the authorize step afterward is untouched and
  still answers the #3417 done state for the same settled replay.

  **No custody, authority or execution change.** The on-chain caveat
  enforcers are the only real budget gate and are untouched; this change
  only decides whether Haven's OWN mirrored pre-flight refusal fires for a
  quote whose money has already moved under a budget that was live at
  authorization time. Nothing here grants authority, creates a payment,
  signs anything, or moves money — the endpoint remains read/decide-only,
  and the bypass activates only after independently verifying the payment
  already settled through the same lookup the authorize replay trusts.

  and its CHANGELOG entry; `packages/mcp-server/src/tools/catalog-purchase.ts`

  **Tests.** Real-DB (`routes/__tests__/budget-precheck.test.ts`, 16
  `#3492` cases): a confirmed keyed erc7710 row with a LOW remaining budget
  answers sufficient with no 403 and no `payment_refusals` row, pinned
  against the OpenAPI response shape (`expectMatchesSpec`); the true
  (spent) `remaining_atomic` is still reported; an unexpired
  `pending_signature` child is still refused; a key collision on a
  different payee, resource, token or amount, a settled EIP-3009 row, and a
  row scoped to a task budget OR a sub-budget are each still refused; a
  `confirmed` row with a NULL `tx_hash` (confirmed alone is not settled) is
  still refused; a request that otherwise matches a settled row but OMITS
  `resourceUrl` or omits `merchantTo` is still refused (N1: both are
  required for a replay match); a settled row under the same key text but a
  DIFFERENT agent never replays for the calling agent (the lookup is
  agent-scoped); no `idempotencyKey` or a non-matching key runs today's
  compare unchanged; a settled replay with sufficient budget still answers
  sufficient, also pinned against the response shape. Hosted
  (`mcp-server/src/tools/catalog-purchase.test.ts`): `args.idempotency_key`
  is forwarded onto the pre-check body and omitted when absent; a keyed
  twin of the existing over-budget refusal test proves a FRESH key over
  budget is still refused with no `POST /x402`; the existing #3417
  settled-replay test now also asserts the forwarded key. SDK
  (`client-boundaries.test.ts`) pins the widened `precheckBudget`
  signature.

  Mutation-proven (cp-backup before each, restored and re-verified green
  after, per-case with `-t` to isolate the failing assertion): the
  settled-replay branch itself (dropping `|| settledReplay` from the final
  compare turns the sufficient answer back into a 403); each of the SEVEN
  match guards in `isSettledErc7710Replay` — payee, resource, settlement
  scheme, token, amount, task-budget pin, sub-budget pin — independently
  (removing any one turns its own still-refused mismatch case into a false
  `sufficient: true`); the `confirmed` + `tx_hash` requirement narrowed to
  `confirmed` alone (turns the NULL-`tx_hash` case into a false
  `sufficient: true`); and the N1 requiredness of `resourceUrl` and
  `merchantTo` independently (reverting either back to "compare only if
  present" turns its own omitted-field case into a false
  `sufficient: true`). Eleven mutations, eleven catches.

  Perimeter unchanged.
