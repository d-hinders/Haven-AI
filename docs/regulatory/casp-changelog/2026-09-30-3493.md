- **#3493** — `haven_pay_mcp_tool`'s erc7710 branch
  (`packages/mcp-server/src/tools/catalog-purchase.ts`) never passed
  `mcpCallContext` to `haven.prepareX402Erc7710`, unlike its EIP-3009 sibling
  in the same tool and both branches of `haven_prepare_catalog_purchase`,
  which have persisted it since #1307/#1547. A settlement child authorized
  through this one code path carried no stored merchant call, so
  `haven_settle_mcp_tool` with only `payment_id` + `signature` had nothing to
  rehydrate for it — the agent had to re-thread `merchant_url` / `tool_name` /
  `arguments` / `mcp_transport` explicitly, the version-skew fallback path,
  on every call. The erc7710 pay reason text is corrected to match: it now
  states those four fields are OPTIONAL at settle (rehydrated by
  `payment_id`), mirroring the wording the catalog erc7710 branch already
  carries. This adds no new authority, custody boundary, or settlement route:
  `mcpCallContext` is convenience metadata for retrying the merchant's own
  JSON-RPC call — it constructs nothing, signs nothing and cannot redirect
  funds; it only lets the settle leg find the same three (or four) fields the
  agent already supplied at authorize instead of requiring them a second
  time. The settlement child's caveats, amount, payee pin and expiry are
  unchanged, and the signer still fetches and verifies the child itself
  before signing. Mutation-tested: removing the added `mcpCallContext` block
  reddens the new authorize-body assertion (pinning `POST /x402`'s body) on
  this branch alone, and reverting the reason-text edit reddens the new
  reason-text assertion alone; both were confirmed red under the mutation and
  green after restore. Perimeter unchanged.
