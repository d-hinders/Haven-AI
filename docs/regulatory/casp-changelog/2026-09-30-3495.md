# CASP shard — #3495: hosted direct-payment results compact by default, relay behind an opt-in

- **#3495** — the hosted `haven_send` / `haven_pay` results are now compact by default: they keep
  everything they returned before EXCEPT `typed_data`/`typed_data_b64` (`payment_id`, `status`,
  `idempotency_key`, `payload_hash`, `expires_at`, the byte-free `haven_sign({ payment_id })`
  handoff, `signer_compatibility`, and send's `asset`/`amount`/`recipient` or pay's `meta`), mirroring
  the x402 quote tools' existing #1272 compact contract on the same shared helper
  (`delegationSignFields`, `tools/support/mcp-context.ts`). This supersedes the #3277 owner decision
  of 2026-09-24 ("the relay fields stay") and its CASP shard
  (`docs/regulatory/casp-changelog/2026-09-26-3277.md`), which this shard does not delete — it
  records what changed and why.

  When the caller passes no `idempotency_key`, the hosted tool now generates one FRESH AND RANDOM
  per call (`generateDirectIdempotencyKey`, `tools/support/mcp-context.ts` — `direct:` +
  `crypto.randomUUID()`) and echoes it on every result, success or `pending_approval`. This is a
  review correction: the first design hashed token/amount/recipient/`task_budget_id`/
  `sub_budget_id` into a 5-minute bucket, mirroring the x402 tools' `buildX402IdempotencyKey`
  (`@haven_ai/sdk`'s `x402.ts`) — but x402's key identifies a quote for one paid resource, where two
  calls with the same parameters inside the bucket really are the same purchase, and a direct send
  has no such identity: two separate tips or payouts of the same amount to the same recipient within
  five minutes are routinely two DIFFERENT payments. Bucketing them onto one key would have made the
  backend's idempotency replay (`findPaymentReplay`, `payments.ts`) return the FIRST payment for the
  SECOND call — silently never sending the second transfer while the agent was told it succeeded. A
  new optional input, `include_signing_payload: true` (`tools/contracts.ts`), on a re-run naming the
  SAME (echoed) `idempotency_key` returns the relay pair (`typed_data` + `typed_data_b64`) from the
  stored payment — a true replay, never a new charge, ONLY because the caller deliberately echoes
  the key back, and PROVIDED the re-run also repeats the original
  token/amount/recipient/`task_budget_id`/`sub_budget_id` — a mismatch answers 409 rather than
  silently settling under different terms.

  **Replay semantics, precisely** (`findSendIntentByIdempotencyKey`'s `FIND_SEND_INTENT_BY_KEY_SQL`
  and `findPaymentReplay`, `packages/backend/src/infra/repositories/payment-intents.ts` /
  `packages/backend/src/routes/payments.ts`): the outcome depends on the stored row's own state, not
  on `include_signing_payload` alone, and on whether the lookup query finds a row AT ALL —
  `FIND_SEND_INTENT_BY_KEY_SQL` excludes `status IN ('failed', 'expired')` from its `WHERE` clause
  outright. A matching key against a row still `pending_signature` AND within its `expires_at` window
  is a TRUE replay — the same `payment_id`, the same stored `sign_data`, no new chain read. A matching
  key against a row `pending_signature` but PAST `expires_at` is lazily expired IN PLACE and a FRESH
  intent is created under the SAME key (the dead row frees it — pre-existing #961 behaviour, untouched
  here). A key that already belongs to a row with status `failed` or `expired` matches NOTHING in the
  query (the exclusion above) — the lookup returns as if no row exists, and a FRESH intent is created
  immediately, with no lazy-expire step. A matching key against a row already `confirmed` (or any
  other terminal, non-`failed`/`expired` status the query does return) answers a STATUS replay with no
  `sign_data` at all — nothing to sign, nothing new charged. A mismatched key (different
  token/amount/recipient/`task_budget_id`/`sub_budget_id`) answers 409 rather than silently settling
  under different terms or rerouting to a different payment.

  Authority and custody argument: this change alters only what the hosted server returns from a
  payment the backend has already prepared under the on-chain budget, recipient and expiry checks,
  and only how an agent reaches the RELAY form of bytes it already had unconditional access to. It
  creates no new signing capability, no new credential surface, and no path on which the hosted
  server or an API credential can move money: the hosted server stays keyless, the delegate key
  never leaves the local signer, and every signature — reached via the byte-free `payment_id` fetch
  or via the opt-in relay — is still checked against the payment's `payload_hash` by the signer's
  #3271 UserOp binding check before it is produced. At any moment a given `idempotency_key` names AT
  MOST ONE live (non-terminal) intent — a true replay while it is signable, a status read once it is
  not, a fresh intent only after the old one has died (expired) — so the opt-in re-run cannot create
  a second CONCURRENT charge under the same key.

  Two review-round-1 corrections to the shape above, both fixed in this same PR:
  - **S5 — a same-key re-run of a CONFIRMED payment used to crash.** `HavenClient.createIntent`'s
    return type hardcodes `status: 'pending_signature'`, so a status-replay body with no `sign_data`
    reached `intent.signData.hash` and threw (`UNKNOWN_ERROR`) instead of surfacing the real state.
    `haven_send`/`haven_pay` now detect a missing `sign_data.hash` and answer with the REAL status
    (read via `haven.getPaymentStatus`), the tx hash when Haven has recorded one, no signing fields,
    and a `next_action` of `none` (confirmed) or `check_status_later` (any other status the backend's
    `agentPaymentStatusHttpCode` still answers 200 for, e.g. `rejected`) — never the crash. A status
    that maps to a non-2xx code there (`pending_signature`/`submitted` → 409, `expired` → 410,
    `failed` → 502) never reaches this branch at all: the SDK transport throws on the non-ok response
    before `createIntent` returns, so that case surfaces as an ordinary API error, not this guard.
  - **N3 — the opt-in re-run's own reason now tells the agent to relay directly.** The default
    reason (`DIRECT_SIGN_REASON`) still points at `haven_sign { payment_id }` first; a result that IS
    the `include_signing_payload: true` re-run instead carries `DIRECT_SIGN_REASON_WITH_RELAY`,
    which says to sign `{ payload_hash, typed_data_b64 }` from THIS result directly rather than
    looping back through `payment_id`.

  The recovery guidance (`directSignerCompatibilityNotice`, `support/signer-compat.ts`;
  `DIRECT_SIGN_REASON`, `state-direct-recovery.ts`; `HOSTED_INSTRUCTIONS`, `server.ts`; the
  `PAY_DESCRIPTION` tool description, `tools/contracts.ts`) now routes a refusal through the opt-in
  re-run before naming the relay fields — on TWO DISTINCT trigger shapes, named separately rather
  than conflated into one (review round 1 caught the conflation in the PR's first pass): (1) any
  `haven_sign` refusal carrying `fallback: 'typed_data_b64'`, whatever its code — a currently-
  published `@haven_ai/signer` (0.5.0-alpha.1 through current) sets that field only on
  `SIGN_CONTEXT_TIMEOUT` / `SIGN_CONTEXT_UNREACHABLE` / `SIGN_CONTEXT_MALFORMED`, or
  `SIGN_CONTEXT_REFUSED` with `http_status: 404` against an older backend; (2) `SIGN_CONTEXT_REFUSED`
  with `backend_error_code: 'sign_context_unavailable'` and NO `fallback` field, which only a signer
  predating #3271 produces (it has no direct-fetch fallback of its own to try). It never suggests a
  `payload_hash`-only call. The signer's own messages (`sign-context.ts`'s timeout/unreachable/
  malformed/404 throws, `tools.ts`'s `USEROP_BINDING_MISMATCH` remedy) and the backend's own 409 text
  (`modules/x402/sign-context.ts`) are updated in the same PR to match — the 404 case names BOTH
  routes (the original result, on a backend old enough to predate #3495 too; or a same-key opt-in
  re-run, on a newer one) since the signer cannot tell which backend it is talking to. `@haven_ai/signer`'s
  `DIRECT_RELAY_FALLBACK` text ships with the next signer release; no gate upgrades an existing
  installed signer, and the hosted-side prose above covers every version already published in the
  meantime.

  **Skew, both directions.** Against a Haven deployment that has shipped #3495: an old signer
  (`<= 0.4.0-alpha.0`) or a current signer hitting either trigger shape above both now need ONE EXTRA
  hosted call (the opt-in re-run) before they can relay, where #3277 let them relay straight from the
  original result — no code change needed on either signer, since both already read `fallback` /
  `next_tool_omitted_reason` as data. Against an OLD (pre-#3495) Haven deployment the result still
  carries the relay fields unconditionally, so the extra call is simply unused guidance. The OTHER
  direction: a caller running #3495-aware guidance against a PRE-#3495 hosted server — `include_signing_payload`
  is new schema surface the old server's strict input validation (`STRICT_INPUT_TOOLS`) does not
  declare, so it refuses the argument outright rather than silently ignoring it; on that old server
  the pair is already on the original result, so the re-run was never needed there in the first place.

  Deliberately untouched: the delegation rails, budget/authority enforcement at prepare, the
  sign-context endpoint and its versioning, the signer's allowlist and binding checks, `haven_submit`
  and the settlement paths, every x402 surface (`buildX402SigningContext`'s own compact/opt-in
  contract is unchanged — only its stale comment claiming direct payments were exempt is corrected),
  and the backend's idempotency-replay mechanics (`findPaymentReplay`, `payments.ts`), which this
  change reuses rather than modifies.

  Tests: handler-level tests drive `haven_send` and `haven_pay` and assert the negative default (no
  `typed_data`/`typed_data_b64` in the compact result), the `idempotency_key` echo, that TWO no-key
  calls with IDENTICAL arguments get TWO DIFFERENT generated keys and hit the backend twice as two
  separate payments (the property the bucketed design would have violated), that a same-key
  `include_signing_payload: true` re-run returns the relay pair while hitting the backend with the
  identical key (never a second intent — proven by the replayed `payment_id` staying the same across
  both calls), and that a same-key re-run of a CONFIRMED payment (S5) returns status + tx hash with no
  crash and no signing fields; a dedicated unit suite (`tools/support/direct-idempotency-key.test.ts`)
  proves the generator's own shape and non-collision across 1000 calls; the #3277 cross-package
  integration test is rewritten as the two-hop route (refusal, opt-in re-run on the same key, relay,
  completes), and a SECOND composed test covers the other trigger shape — a current signer's
  `SIGN_CONTEXT_UNREACHABLE` — end to end on the real `@haven_ai/signer` package; the #1591
  description-size pin is re-derived for the changed `PAY_DESCRIPTION`. Mutations that restore the
  unconditional relay, drop the key echo, make key generation deterministic again, restore the S5
  crash, or restore the conflated single-trigger reason text turn these tests red. The 409-mismatch
  path itself (mismatched token/amount/recipient/budget id on a replay) is PRE-EXISTING backend logic
  this PR does not modify and does not add new coverage for — see `payments.test.ts`'s existing
  idempotency suite and `payments-task-budget-replay.test.ts` for that behaviour's own tests. Perimeter
  unchanged.
