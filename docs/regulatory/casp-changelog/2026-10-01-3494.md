- **#3494** — `POST /payments/:id/sign`'s failure catch
  (`packages/backend/src/routes/payments.ts`) now answers its 502 with a
  typed `error_code` and a bounded, redacted `message`, instead of one
  untyped "On-chain execution failed" carrying the raw bundler/viem error.
  The route relays every rail that reaches this catch — a direct payment and
  the EIP-3009 funding leg (`POST /x402/authorize`'s `sign_data.instructions`
  names this route for the funding leg) — so the typed codes apply uniformly.
  Four cause classes, checked in order: `signature_rejected` (the account
  rejected the UserOperation signature during on-chain validation — ERC-4337
  AA2x, most often `AA24 signature error`; a NEW signature on a NEW payment is
  the only remedy, since this `payment_id` is already `failed`);
  `task_budget_exceeded` / `delegation_budget_exceeded` (a budget revert
  caught at submit — a payment that raced past the #3500/#3503 create-time
  pre-check, or whose pre-check read failed open — re-confirmed from the
  enforcer's own current figure, via `findForAgent` (`infra/repositories/
  task-budgets.ts`) + `checkTaskBudgetCap`, or `selectActiveDelegationByHash` +
  `readRemainingBudget`, before answering — never on the revert text alone);
  and `onchain_execution_failed` for everything else, with the bundler's
  message bounded to 300 characters (`boundFailureMessage`,
  `modules/payments/agent-payment-status.ts`) rather than relayed raw. The
  classification helpers (`isAccountValidationRevert`, alongside the existing
  `isPeriodBudgetRevert`/`isTransferCapRevert`) live in
  `modules/payments/refusal-ledger.ts`; no ledger row is written for any of
  these four — the route already books the failure on the intent row
  (`failSubmittedIntent`) before classifying, the same contract the comment
  this replaces stated.

  Two status-surface gaps close in the same diff. `FIND_INTENT_STATUS_ROW_SQL`
  (`infra/repositories/payment-intents.ts`) now selects `error_message` and
  `send_idempotency_key`, which it never did before. `agent-payment-status.ts`
  surfaces the former as a bounded, redacted `failure_reason` on a `failed`
  intent's `/machine-payments/:id/status` (additive: present, possibly `null`,
  only when `status === 'failed'`), and the latter as `idempotency_key` for a
  direct (non-x402/mpp) row — `railContext` answered `{}` for the direct rail
  before this, so a direct payment's own idempotency key never appeared on
  status despite being persisted and echoed at send time. `GET /payments/:id`
  bounds its own `error_message` at the same read, for the same reason: the
  stored value is scrubbed of vendor secrets (`redactVendorSecrets`) but was
  never length-capped, and a viem/bundler failure can carry its full callData
  or ABI in `.message`.

  The hosted MCP's `normalizeError` (`packages/mcp-server/src/tools/support/
  errors.ts`) gains two more typed branches, next to #3416's/#3500's/#3504's:
  `signature_rejected` and `onchain_execution_failed` both become
  `next_action: stop_and_tell_user` — an already-failed intent is not
  "transient, retry once" — with the signature case's reason naming its own
  remedy (update the signer, sign a NEW payment, never resubmit the same
  `payment_id`). The two budget codes needed no new branch: #3500's and
  #3504's existing branches key on `error_code` alone, not the route or
  status code that produced it, so a budget revert caught at submit already
  reaches the agent under the same typed code a create-time refusal does.

  **No custody or authority change.** This is response-shape and status-read
  work on failures and refusals the chain, the caveat enforcers and the
  intent-claim/fail writes already decided — no key, signature, delegation,
  caveat, budget, recipient pin or on-chain surface moves, and nothing is
  signed, built, relayed or retried differently. The account's own
  `validateUserOp` remains the actual signature gate; the
  `ERC20PeriodTransferEnforcer`/`ERC20TransferAmountEnforcer` remain the
  actual budget gates. The route still claims the intent before executing and
  still fails it closed on any execution error, unconditionally — the typed
  code and the bounded message are read AFTER that decision, never a factor
  in it. Every length-bounding path reuses the existing
  `redactVendorSecrets` scrub (never a new redaction rule), and the bound is
  length only — a secret surviving redaction is unaffected by the cap.
