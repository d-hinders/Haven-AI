- **#3494** — `POST /payments/:id/sign`'s failure catch
  (`packages/backend/src/routes/payments.ts`) now answers its 502 with a
  typed `error_code`, instead of one untyped "On-chain execution failed"
  carrying the raw bundler/viem error. The route relays every rail that
  reaches this catch — a direct payment and the EIP-3009 funding leg
  (`POST /x402/authorize`'s `sign_data.instructions` names this route for
  the funding leg) — so the typed codes apply uniformly. Six cause classes,
  checked in order:
  - `submission_outcome_unknown` — checked FIRST, ahead of every
    text-based classification below, because it is the one double-pay-risk
    case (review round 1, B1; remedy corrected in review round 2, B1'):
    `sendUserOperation` resolving is the one irreversible step, so a throw
    AFTER it where the receipt wait itself errored or timed out —
    `SubmittedUserOpFailedError` with `reverted: false`, the default
    (`rails/delegation-rail.ts`'s own post-send-only contract) — means the
    UserOp MAY have landed and Haven never learned the outcome. The body
    carries the `user_op_hash`. The remedy is "do NOT create a new payment;
    check the account's real activity (Haven's activity view, or the
    UserOperation hash on a block explorer)" — NEVER "poll this
    payment_id's status", because `failSubmittedIntent` already marked the
    intent `failed` before this response is built, so this payment_id's own
    status can never come back "landed" (round 1's "poll status, pay again
    once it confirms this one did not settle" wording was itself a
    double-pay risk: the permanent "failed" answer could be misread as that
    confirmation).
  - `signature_rejected` — AA24 only (review round 1, S1): the one
    ERC-4337 AA2x code this backend attributes to the signer. A NEW
    signature on a NEW payment is the remedy.
  - `account_validation_failed` — every OTHER AA2x code (AA20/21/22/23/25/26,
    review round 1, S1): a real `validateUserOp` rejection, but NOT
    evidence the signature is wrong — this code deliberately never names
    the signer, only "create a new payment".
  - `task_budget_exceeded` / `delegation_budget_exceeded` — a budget
    revert caught at submit — a payment that raced past the #3500/#3503
    create-time pre-check, or whose pre-check read failed open —
    re-confirmed from the enforcer's own current figure, via `findForAgent`
    (`infra/repositories/task-budgets.ts`) + `checkTaskBudgetCap`, or
    `selectActiveDelegationByHash` + `readRemainingBudget`, before
    answering — never on the revert text alone. Same body shape the
    create-time 403 answers — `asset` on `delegation_budget_exceeded` only
    (review round 1, S2; `task_budget_exceeded`'s create-time body never
    carried it either, corrected in review round 2, R2-9); like create
    time, neither carries a `message` field.
  - `onchain_execution_failed` — everything else, INCLUDING (review round 2,
    N3) a `SubmittedUserOpFailedError` with `reverted: true` — the op
    executed and reverted, a KNOWN, confirmed outcome (the execution call reverts, so no token transfer and no delegation spend; only the EntryPoint nonce and the paymaster's sponsored gas are consumed), strictly distinct from
    `submission_outcome_unknown`'s truly-unknown case above. The
    `SubmittedUserOpFailedError` class (`rails/delegation-rail.ts`) gained
    the `reverted` field in this round for exactly this split; its two
    throw sites set it `true` only when a receipt actually arrived and
    reported failure.

  The four non-budget codes carry the bundler's message bounded to 300
  characters plus an ellipsis if longer (`boundFailureMessage`,
  `modules/payments/agent-payment-status.ts`) in `details`, rather than
  relayed raw; `details` is `null` when nothing was recorded. Three of the
  four (`submission_outcome_unknown`, `signature_rejected`,
  `account_validation_failed`) carry a FIXED remedy `message` independent
  of the on-chain text; `onchain_execution_failed`'s `message` carries the
  bounded text itself (or the literal fallback "On-chain execution
  failed"). The classification helpers (`isSignatureRejectedRevert`,
  `isAccountValidationFailedRevert`, alongside the existing
  `isPeriodBudgetRevert`/`isTransferCapRevert`) live in
  `modules/payments/refusal-ledger.ts`. The two budget re-reads (DB +
  chain) are wrapped in a try/catch (review round 1, S2): a failure WHILE
  classifying — never the original on-chain cause — falls through to the
  generic `onchain_execution_failed` answer, never a 500. No ledger row is
  written for any of the six — the route already books the failure on the
  intent row (`failSubmittedIntent`) before classifying, the same contract
  the comment this replaces stated; this PR does not change that booking —
  a submission whose outcome is unknown is still marked `failed` even
  though the on-chain state may disagree, a reconciliation gap the owner
  will file as a separate follow-up.

  Two status-surface gaps close in the same diff. `FIND_INTENT_STATUS_ROW_SQL`
  (`infra/repositories/payment-intents.ts`) now selects `error_message` and
  `send_idempotency_key`, which it never did before. `agent-payment-status.ts`
  surfaces the former as a bounded, redacted `failure_reason` on a `failed`
  intent's `/machine-payments/:id/status` (additive: present, possibly `null`,
  only when `status === 'failed'`), and the latter as `idempotency_key` for a
  direct (non-x402/mpp) row — `railContext` answered `{}` for the direct rail
  before this, so a direct payment's own idempotency key never appeared on
  status despite being persisted and echoed at send time. `GET /payments/:id`
  bounds its own `error_message` at the same read (same 300-character-plus-
  ellipsis cap), for the same reason: the stored value is scrubbed of vendor
  secrets (`redactVendorSecrets`) but was never length-capped, and a
  viem/bundler failure can carry its full callData or ABI in `.message`.

  The hosted MCP's `normalizeError` (`packages/mcp-server/src/tools/support/
  errors.ts`) gains four new typed branches, next to #3416's/#3500's/#3504's:
  all four map to `next_action: stop_and_tell_user` — an already-failed
  intent is not "transient, retry once", and (review round 2, B1')
  `submission_outcome_unknown` is NOT `check_status_later` either, for the
  same reason the backend's own remedy changed: this payment_id's status is
  permanently `failed`, so naming the status tool would promise a
  resolution it cannot deliver. The two budget codes needed no new branch:
  #3500's and #3504's existing branches key on `error_code` alone, not the
  route or status code that produced it, so a budget revert caught at
  submit already reaches the agent under the same typed code a create-time
  refusal does.

  **No custody or authority change.** This is response-shape and status-read
  work on failures and refusals the chain, the caveat enforcers and the
  intent-claim/fail writes already decided — no key, signature, delegation,
  caveat, budget, recipient pin or on-chain surface moves, and nothing is
  signed, built, relayed or retried differently. The account's own
  `validateUserOp` remains the actual signature gate; the
  `ERC20PeriodTransferEnforcer`/`ERC20TransferAmountEnforcer` remain the
  actual budget gates. The route still claims the intent before executing and
  still fails it closed on any execution error, unconditionally — the typed
  code and the bounded message are read AFTER that decision, never a factor
  in it. Every length-bounding path reuses the existing
  `redactVendorSecrets` scrub (never a new redaction rule), and the bound is
  length only — a secret surviving redaction is unaffected by the cap.
