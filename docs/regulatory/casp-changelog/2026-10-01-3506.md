- **#3506 (epic #3328)** — sub-budgets become completable by a real user. The files in scope:
  - **Owner issue flow** on the dashboard agent page: `IssueSubBudgetModal`, the "Issue sub-budget" action on `DelegationBudgetCard`, and `POST /agents/:id/sub-budgets` with the owner JWT.
  - **The agent completes it itself:**
    - `haven_submit { sub_budget_id, signature }` on the hosted and the local MCP runtime, through the SDK's `submitSubBudget`, to the existing agent route `POST /sub-budgets/:id/submit`;
    - discovery of pending sign targets with `GET /sub-budgets?status=awaiting_signature`, surfaced as `haven_get_agent` `pendingSubBudgetSignatures[]`.
  - **Issuance responses** answer `next_action: 'agent_signs_then_submits'`.
  - **The signer's consent summary and `initialize` block** name sub-budget signing and its sign-context versions.
  - **The `next-step-signer-parity` drift guard** now pins both `haven_submit` handoffs.
  - **Close recovery in `haven_submit { sub_budget_id }`:** a `close_needs_reprepare` (409) answer re-prepares through the SDK's `closeSubBudget` and returns `closed`, or a `CLOSE_NEEDS_REPREPARE` refusal naming `haven_sign` for the fresh op; a `close_outcome_unconfirmed` (502) answer returns a `CLOSE_OUTCOME_UNCONFIRMED` refusal that retries the same `haven_submit` later.

  Authority and custody argument: no new authority is created and no existing check moves.
  - **Issuance:** it stays owner-only, and the owner's dashboard action calls the same owner route the API already exposed. That route still decodes A's own budget delegation and refuses a child wider than it in amount, expiry or recipient before anything is built or signed (`sub_budget_wider_than_parent`, `sub_budget_exceeds_remaining`). It is JWT-authenticated and needs no passkey, because Haven only builds the unsigned children; nothing moves on-chain at issuance.
  - **Owner relay:** the agent route that now carries A's signature already required it to recover A's own delegate key over the exact bytes Haven built before opening a row. Routing the signature there instead of through the owner's relay (`POST /agents/:id/sub-budgets/:id/sign`, kept and unchanged) removes a manual step, not a check. The decision log's new 2026-10-01 line records that the relay was transport, not governance; the 2026-09-27 governance decision stands.
  - **Agent B:** it still never signs and can never widen its grant.
  - **Discovery:** it is scoped to rows the calling agent delegates.
  - **Close recovery:** the re-prepare is the agent's own `POST /sub-budgets/:id/close`, which checks the chain first and returns `closed` when the child is already disabled; the prepared op is authority-reducing only (`assertOwnSubBudgetCloseUserOp`); the recovery relays nothing further on either refusal.
  - **Haven:** it still signs nothing, holds no key and moves no funds.
  - **Consent:** the change is copy-only (owner decision 2026-09-30). `SIGNER_CONSENT_SURFACE_VERSION` stays 2 and a test pins the consent hash for a fixed identity, so the signer's signing surface is unchanged. It already signed sub-budgets since 0.7.0, and the text now says so.
  - **Threat model** confirmed by the owner on 2026-10-01: a compromised owner session can grant a sub-budget, the same residual as granting any budget today.
