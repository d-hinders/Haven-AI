- **#3510** — the ops console's read-only database role (epic #3507). The
  console's data reads now go through a separate login (`OPS_DATABASE_URL`)
  for a role that can read a positive allowlist of columns and nothing else:
  column-level `GRANT SELECT` only, no table-level grant, no write privilege,
  `default_transaction_read_only`, a 5 s statement timeout and a connection
  limit of 5. Credential material stays unreadable — `users.password_hash`,
  `agents.api_key_hash` / `api_key_prefix`, `payment_intents.signature` and
  its idempotency keys, and whole tables such as `agent_connection_setups`,
  `device_authorizations`, `accounting_connections`, `user_passkeys`,
  `rate_limit_counters`, `owner_company_details` and `ops_access_log`.
  `delegation_json` is readable by owner decision (2026-09-30): it is a
  delegation to a named delegate, so holding it confers no spend authority
  without that delegate's key. An erc7710 settlement child is stored unsigned
  (`payment_intents.prepared_user_op`, granted) and the agent's signature
  over it separately (`payment_intents.signature`, withheld and on a
  never-grant list the role builder enforces), so the role cannot assemble a
  signed child; the child is also short-expiry and facilitator-pinned. The
  role is created by an operator-run script
  (`npm run -s ops:readonly-role-sql -w packages/backend`), not a migration,
  with steps in `docs/operations/ops-readonly-role.md`. It refuses while any
  granted free-text column still holds an unredacted vendor secret (a
  generated `--scrub` rewrites old rows exactly as `redactVendorSecrets`
  would) or while the role could CREATE in the schema. The backend refuses to
  boot when `OPS_DATABASE_URL` logs in as the `DATABASE_URL` user, and checks
  the login's actual privileges before its first read: a login that can read
  any never-grant column, write any table in its schema, create there, or
  run without `default_transaction_read_only` turns the ops data routes off
  (404).
  With `OPS_DATABASE_URL` set, `POST /ops/reveal` (#3509's closed
  `users.email` / `users.name` set) now answers, reading through this role
  and auditing on the main pool; unset, it stays 404. The one runtime change on the money path:
  `markOutboundTxFailed` now applies `redactVendorSecrets` (moved to
  `domain/` and re-exported from `rails/execution-rail.ts`, unchanged) to the
  failure reason before it is stored — ordinary reasons are stored byte for
  byte as before (characterisation test), a keyed URL is stored redacted.
  Nothing here signs, moves funds or changes any authority; the role reads
  less than the backend already can. Perimeter unchanged.
