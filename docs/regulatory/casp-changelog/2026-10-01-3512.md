- **#3512** — the ops console's first data reads (epic #3507):
  `GET /ops/overview` (platform counts), `GET /ops/search?q=` (a pasted
  UUID, address, tx hash or email prefix) and `GET /ops/users/:id` (one
  customer's record). They are cross-tenant by design, for founder support,
  and read-only: the SQL lives in `infra/repositories/ops-reads.ts`, where
  every function takes the executor as a required argument, so the routes
  read through the read-only ops role (#3510) and never default to the main
  pool. Every statement is an explicit column projection over columns that
  role is granted; a real-DB test runs each one as the role. Responses mask
  the customer's email and name (the raw values leave only through the
  audited `POST /ops/reveal`). They return no hash, signature, delegation
  body, `machine_metadata` or company detail, which a serializer test pins
  over every route. Every call writes one `ops_access_log` row through the
  main pool before anything is sent; a failed write answers 503 with nothing
  returned. A search's audit row stores the key type and the masked term,
  never the raw query (real-DB test). Search runs its lookups one at a time
  inside a 5 s budget, so one request holds at most one of the role's five
  connections. Mutation-tested: routing reads to the main pool, writing the
  audit through the ops executor, storing the raw search term, returning an
  unmasked email, and dropping the search budget each turn a test red.
  Nothing here signs, moves funds, changes a delegation or acts as a user.
  Perimeter unchanged.
