- **#3527** — the #3492 follow-up: a replayed x402 idempotency key whose
  EIP-3009 payment's FUNDING leg had already confirmed could still be refused
  as over-budget by the #3054 server-side pre-check
  `POST /machine-payments/budget-precheck`. #3492 fixed this for a settled
  erc7710 replay only (no funding leg, so `confirmed` + `tx_hash` IS the
  settlement); this closes the same gap for EIP-3009, where `confirmed` +
  `tx_hash` is only the FUNDING leg (treasury → delegate,
  `x402-authorizations.ts:455-458`) — but it is exactly the fact
  `delegationReplay`'s own confirmed+tx_hash branch (`replay.ts:89-110`)
  already treats as replayable for every settlement scheme, so the
  pre-check's refusal was always false there too, the same argument #3492
  made for erc7710.

  **The pre-check fix is server-side.** `isSettledErc7710Replay` is renamed
  `isSettledX402Replay` and its scheme guard widens from `'erc7710'` to
  `'erc7710' | 'eip3009'`; every other guard (confirmed + `tx_hash`, no
  task-/sub-budget pin, same token/amount/payee/resource as the request —
  both of the latter two REQUIRED) is unchanged and scheme-agnostic by
  construction: it compares the request's `resourceUrl` against whichever
  value the stored row's `x402_resource_url` column holds, and that storage
  was already scheme-aware at authorize time before this change (erc7710
  persists the caller's `resourceUrl`; eip3009's `createX402Intent` always
  persists `paymentRequired.resource.url`, SDK `client.ts:452-453`). A
  confirmed, correctly-matched EIP-3009 row now answers
  `{ sufficient: true, replay: true }` WITHOUT calling `refuse()` — same
  no-fabrication rule as erc7710 (`remaining_atomic` still reports the true,
  now-spent figure; only the refusal write is skipped).

  **The caller-side half closes the resource gap #3492's own review found
  but did not need to fix (erc7710 only).** `haven_prepare_catalog_purchase`
  step 5b sent `resourceUrl: merchantUrl` unconditionally — correct for
  erc7710 (step 8 authorizes with the same value), but potentially wrong for
  eip3009, whose stored row carries `paymentRequired.resource.url`, a value
  that can differ from the discovered merchant URL. Step 5b now sends
  `merchantUrl` on the erc7710 branch (unchanged) and
  `paymentRequired.resource.url ?? merchantUrl` on the eip3009 branch. It
  also now forwards the EFFECTIVE idempotency key
  (`args.idempotency_key ?? quote.idempotencyKey`) on the eip3009 branch
  instead of the explicit key only — the same key step 9's
  `createX402Intent` authorizes with, so an agent that never named a key
  still has its auto-derived 5-minute-bucket key checked against the row
  step 9 will replay. The erc7710 branch still forwards the explicit key
  only, unchanged (its own key is never auto-derived on this path).

  **The hosted done-state split is new.** Before this fix, a confirmed
  EIP-3009 replay reaching `createX402Intent`'s own confirmed-status branch
  (now reachable at all, since the pre-check above no longer refuses it
  first) surfaced as a bare `HavenPaymentStateError` → `normalizeError`
  `API_ERROR` with no useful next step (the spec review's finding). The
  #3417 erc7710 helper (`settledReplayResponse`) could not be reused: it
  hardcodes `settlement_scheme: 'erc7710'` and reports its replayed
  `tx_hash` AS the settlement hash — correct there (no funding leg; the
  confirmed intent IS the settlement) and WRONG on eip3009, where that hash
  is only the FUNDING leg and the merchant leg is a separate fact. A new
  helper, `eip3009ConfirmedReplayResponse`
  (`packages/mcp-server/src/tools/support/guidance.ts`), re-reads
  `haven_get_payment_status` (the state error's own `state` carries only the
  funding leg's facts) and splits on the #3475-follow-up merchant-leg
  evidence it exposes:

  - A verified merchant settlement (`merchant_settlement_recorded`) OR a
    reported merchant leg (`delivered`, `merchant_leg_reported`'s wire name)
    → a DONE state: `funding_tx_hash` is the row's own (funding) hash,
    `settlement_tx_hash` is the verified hash when the wire carries one, else
    `null` — `getPaymentStatus` exposes only a verified BOOLEAN today, never
    the merchant's own settlement hash, so this never backfills one from the
    funding hash.
  - Neither → the #2290 funded-awaiting-merchant remedy
    (`isFundedX402AwaitingMerchantLeg`'s producer), forwarding the re-read
    status's own `next_action`/`message` VERBATIM rather than re-deriving
    them, pointed at `haven_get_payment_status` — NEVER a fresh funding sign
    for an idempotency key that already funded a payment.

  Both hosted 3009 paths that reach `createX402Intent` with a replayed key —
  `haven_prepare_catalog_purchase` step 9 and `haven_pay_mcp_tool`'s 3009
  branch — catch the confirmed state error and call this helper instead of
  rethrowing; `haven_pay_mcp_tool` has no pre-check (same as #3492: its
  authorize call runs the replay lookup before any budget compare), so only
  its `createX402Intent` catch changes.

  **No custody, authority or execution change.** The on-chain caveat
  enforcers remain the only real budget gate. This change only widens an
  existing Haven-side mirror refusal's exception (money that already moved
  must not be re-refused as over-budget) to a second settlement scheme, and
  adds agent-facing reporting for a state that already existed server-side
  (`delegationReplay`'s confirmed branch always answered this replay's
  authorize call with its stored 200 — the hosted surfaces simply described
  it wrong). Nothing here grants authority, creates a payment, signs
  anything, or moves money.
