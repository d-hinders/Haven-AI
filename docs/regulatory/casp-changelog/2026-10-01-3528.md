- **#3528** — the payment prepare response now carries a WARNING-GRADE,
  ADDITIVE hint when the recipient is one of the owner's own Haven accounts
  (code `SELF_TRANSFER`, one sentence naming the situation). Split out of
  #3518 item 5; the trigger is #3328's live verification, where a direct send
  to the owner's second account (`0x6d01…081e`) looked exactly like a send to
  a stranger — empty `warnings`, `safe_to_continue: true`.

  The chain of custody of the signal: the backend resolves the owner's
  accounts where it already resolves them — one new owner-scoped, read-only
  query (`listOwnerAddressesForUser`) over the existing `smart_accounts`
  directory, selecting each `delegator_hybrid` account's `account_address`
  plus its current `owner_address` (the two addresses an ownership transfer
  can move), `UNION`-deduplicated, `WHERE user_id = $1` on both arms, and the
  recipient compared case-insensitively against that set. The hint attaches on
  three prepare responses (`POST /payments`, both `POST /x402` legs behind
  `runDelegationAuthorize`), the SDK relays it verbatim on the typed prepare
  results (`PaymentIntent`, `X402Intent`, `prepareX402Erc7710`; absent — never
  an empty array — when the backend sent none, and unknown warning codes
  relay as-is per the #1308 advisory-by-contract rule), and the MCP surfaces
  merge it into the warnings envelope their results already carry
  (`plain-http-x402`, `state-direct-recovery`). `safe_to_continue` is not
  consulted, not produced, and not altered on this path; the refusal-ledger
  seam is not imported on the hint path and the routes' refusal writers run
  exactly as before.

  **No custody or authority change:** the comparison is a pure equality
  against addresses the backend already owns in its owner directory — no new
  authority, no chain read, no heuristic, no signature, no delegation, caveat,
  budget or recipient-pin change. The hint is advisory telemetry that narrows
  nothing and authorises nothing: a self-transfer is legitimate (sweeping
  between own accounts), and the on-chain authority for the send is unchanged
  either way — the budget delegation's caveat enforcers remain the only gate.
  The new read deliberately FAILS OPEN: a degraded directory read yields no
  warning and a byte-identical prepare, so the hint can never refuse, warn-spam
  on degraded infra, or otherwise perturb a payment the enforcers would allow.
  No refusal is added anywhere; nothing that previously refused changes shape,
  and `POST /payments`' `warnings` contract is declared additive in the spec.
  Perimeter unchanged.

  **Verified:** mapping contract in
  `packages/backend/src/domain/__tests__/self-transfer.test.ts` (owner-owned
  warns / stranger doesn't, absent-not-empty on a stranger's prepare, fails
  open on a thrown read, non-address short-circuits without a directory read);
  SQL scoping in `smart-accounts.test.ts` (`user_id = $1` on both UNION arms,
  `delegator_hybrid` only, executor-injected rows mapped verbatim); route
  behaviour in `payments-period-budget.test.ts` (the 201 carries the warning
  with the ordinary shape otherwise unchanged, a stranger's body has NO
  `warnings` key, the directory read runs exactly once per prepare scoped to
  the agent's user, a degraded read never blocks the 201, and no
  `INSERT INTO payment_refusals` row is written on the hint path).
