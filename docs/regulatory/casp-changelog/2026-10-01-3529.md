- **#3529** — a refused evidence report whose backend relayed a refusal
  `reason` is no longer classified `DELIVERED_UNSETTLED` with the transfer-
  shape wording. On eip3009 "confirmed" means the FUNDING leg confirmed, so a
  refused report on an already-funded payment was indistinguishable from the
  funding-confirmed-but-undelivered erc7710 case `DELIVERED_UNSETTLED` was
  written for — and until #3475's backend is everywhere, the wording claimed
  "does not match this payment's transfer shape or window" about a
  transaction that does match, only because the backend could not take the
  evidence yet.

  The chain of custody of the signal: the backend's evidence seam
  (`packages/backend/src/modules/mpp/evidence.ts`, #3475) already puts a
  `reason` in the 409 body of the eip3009 settlement-report refusal
  (`SettlementReportRefusal`) and nowhere else — this change adds the backend
  negative pins proving the two ordinary refusals stay reason-free (a
  `payment_not_confirmed` 409 and the erc7710 seam's plain
  `settlement_unverified` 409), because the hosted tool keys its new
  classification on the reason's PRESENCE and the discriminator collapses if
  a reasonless refusal ever gains one. The SDK
  (`EvidenceReportOutcome`, `MerchantCompletion.reportSettlementEvidence`)
  carries that reason verbatim on the `refused` outcome, absent (never
  empty) when the body has none — a pre-#3475 backend reads as the old
  shape. The hosted classifier
  (`packages/mcp-server/src/tools/paid-mcp-completion.ts`) grows the
  reason-bearing arm: new code `SETTLEMENT_NOT_RECORDED`, the backend's
  sentence relayed verbatim as `refusal_reason`, and a reason that says what
  Haven actually knows — the payment's funding leg is confirmed and
  unchanged, and THIS transaction was not accepted as its settlement. The
  old transfer-shape claim leaves the reasonless arm too; its reworded
  answer is honest for every case that can reach it (real mismatch, foreign
  payment id, validation refusal, older backend). Keyed on the relayed
  reason, NEVER on payment status: a status-keyed code would also fire on
  ordinary, correct refusals, because every eip3009 payment it correctly
  refuses is confirmed.

  **No custody or authority change:** classification and prose over an
  answer the backend already refused. Nothing is signed, built, moved, or
  retried on a refused report; the new arm cannot admit a settlement the
  chain would refuse — it relays Haven's own refusal sentence and points at
  `haven_get_payment_status` exactly as before. No key, signature,
  delegation, caveat, budget, or recipient pin changes; the only backend
  diff is test code. The refusals themselves, their status codes, and the
  verifier's fail-closed ordering are untouched. Perimeter unchanged.

  **Verified:** backend negative pins in
  `eip3009-settlement-evidence.test.ts` (reason-free bodies on both ordinary
  refusals), SDK pins in `evidence-retry.test.ts` (reason carried verbatim;
  absent, not empty, on a plain 409; never lifted off a 503 exhaustion;
  non-string dropped), hosted pins in `packages/mcp-server/src/tools.test.ts`
  (`SETTLEMENT_NOT_RECORDED` + verbatim `refusal_reason` + truthful funding
  wording on a reason-bearing 409; `DELIVERED_UNSETTLED` with no
  `refusal_reason` and honest wording on a reasonless one). The strict
  coupling gate's two contract-doc implications are satisfied by this shard:
  `docs/architecture/04-x402-payment-sequence.md`'s refusal shapes describe
  the BACKEND bodies, whose contract this diff does not change (it pins the
  absence of a field on two of them); `docs/regulatory/casp-risk-guardrails.md`'
  invariants are untouched — the hosted tool still can only refuse, never
  admit. The hosted-surface contract record lives in
  `docs/operations/mcp-runtime-compatibility.md` (#3529 re-verification
  block, `last-verified` 2026-10-01), which this PR also edits.
