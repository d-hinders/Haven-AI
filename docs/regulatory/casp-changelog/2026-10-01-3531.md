- **#3531 — advisory, history-only `recipient.class` on the direct-payment
  prepare.** `POST /payments`'s 201 (and its idempotent replay) gains a
  top-level, OPTIONAL `recipient: { class: 'previously_paid' | 'new_address' }`
  — never inside `sign_data`, which the account validates and the signer
  checks byte-for-byte, and which a dedicated test pins byte-identical across
  both classes (moving the field into `sign_data` fails it). `previously_paid` is computed from a single
  read, `hasConfirmedPaymentToRecipient(agentId, chainId, toAddress)`
  (`infra/repositories/payment-intents.ts`): has THIS authenticated agent ever
  had a CONFIRMED `payment_intents` row to this exact recipient address, on
  this chain, in any token and on any rail (direct, x402 or MPP — an
  EIP-3009 funding leg's row points at the agent's own delegate, which is
  still only its own history) — `new_address` otherwise. The read is scoped by
  `agent_id` in its `WHERE` clause (tenant isolation by construction, not by
  convention), so no other agent's and no other owner's payment history can
  ever answer it. Real-DB tests pin that a confirmed payment to the same
  address by another owner's agent, AND by a sibling agent under the SAME
  owner, does not flip the first agent's `new_address` answer — the sibling
  case is what separates agent scope from owner scope (an owner-scoped query
  fails it). If the read itself throws, the field is omitted and the prepare
  proceeds; it can never fail a payment. A failed or still-pending earlier
  payment to the address does not count (`status = 'confirmed'` only), also
  pinned.

  This is the history-only shape the owner chose (2026-10-01) over the
  richer `own_account` / `contact` / `catalog_merchant` classes the original
  spec review proposed reusing from `findAccountOwnership` and the contacts
  table — out of scope here by owner decision, for the reason #3528's
  withdrawal (`2026-10-01-3528-withdrawn.md`) records: any class derived from
  the owner's own accounts or address book is a membership oracle an agent
  could probe with guessed addresses. `previously_paid` / `new_address`
  reveal nothing but the calling agent's own settled spend, which it already
  knows.

  It changes no refusal, no `safe_to_continue` value, no `next_action`, and
  no byte of `sign_data` — the only artifact the signer or the account ever
  acts on. It is advisory prose surfaced to the calling agent (and, since the
  hosted `haven_send`/`haven_pay` results now also carry it as a top-level
  `recipient_class`, to whatever the agent tells its own user), never a
  control. The budget delegation and its on-chain caveat enforcers remain the
  sole authority; this PR adds no code to that path. Mutation-tested: the
  `previously_paid` / `new_address` branch, agent-scoped isolation
  (including the same-owner sibling), the caller's lower-casing, the
  swallowed read failure, and the sign_data byte-identity assertion.

  Perimeter unchanged.
