- **#3544** — the owner's credential revoke accepts a `pending_approval` agent, retires its open connection setup in the same transaction, and refuses with a typed contract instead of one all-cases 404. The files in scope: `infra/repositories/agents.ts` (`REVOKE_AGENT_SQL` widened to `status IN ('active', 'paused', 'pending_approval')`; `revokeAgent` now runs the agent UPDATE and the open-setup cancel inside one `withTransaction`), `infra/repositories/agent-connection-setups.ts` (`CANCEL_OPEN_SETUPS_FOR_AGENT_SQL` + `cancelSetupsForAgent`; `ACTIVATE_AGENT_SQL` gained `RETURNING id` and `applyApprovalState` abandons when an intended activation matched zero rows), `routes/agents.ts` (typed revoke refusal), `openapi/spec.ts` + `packages/core/src/api-types.ts` (the 409 entry), and the Remove dialog's refusal classification (`RemoveAgentDialog.tsx`).

  - **The widen is safe because nothing re-activates a revoked agent.** An audit of every `UPDATE agents` writing `status = 'active'` found exactly three writers: `RESUME_AGENT_SQL` (requires `paused`), `ACTIVATE_AGENT_SQL` (requires `pending_approval`/`active`), and the first-budget activation in `routes/agent-delegations.ts` (requires `pending_approval`, behind the locked read `lockOwnedNonRevokedDelegationAgent`). None matches `revoked`, and a real-DB regression pin exercises both activation statements against a revoked agent. A `pending_approval` agent has no spend authority anyway — its key gets 403 `agent_pending_approval` at `agentAuth` — so the fix retires the one thing it could become instead of granting anything.
  - **Cancel-on-revoke closes the dangling-setup window.** The revoke transaction cancels the agent's setup while it is still `awaiting_connection`, `connected_local` or `awaiting_wallet_approval` with no approval transaction hash — before that, the setup hung indefinitely (expiry covered only `awaiting_connection`) and its `budget-approval` answered 409 with the misleading "The agent budget has not been approved yet". A setup that already carries an approval hash is left untouched for its existing refusal paths: the cancel never reclassifies evidence the setup state machine wrote. The setup-side half-apply is closed with it: `applyApprovalState` abandons its whole transaction when an intended `ACTIVATE_AGENT_SQL` matched zero rows, so an approval can never commit a setup `active` next to a revoked agent.
  - **Typed refusal.** `POST /agents/:id/revoke` answers 404 for an agent the owner does not have, and 409 with an `error_code` for an owned agent it will not revoke: `already_revoked` ("nothing to do") distinct from `not_revocable` (status outside the revocable set). The OpenAPI entry carries the 409 and `api-types.ts` is regenerated. The dashboard dialog classifies the refusal from status + `error_code` on the wire, never from message text — the old `/not found|already revoked/i` message match is what swallowed the real refusal in this issue. Installed CLIs are unaffected: 404 and 409 map to the same exit class (`packages/cli/src/errors.ts`).
  - **`api_key_hash` is kept on revoke**, so sweep recovery for a stranded delegate balance keeps working (revoked keys stay recognised on the exact sweep-recovery routes). The setup-cancel abort path's `REVOKE_PENDING_AGENT_SQL` still nulls the key inside that flow; the dashboard revoke deliberately does not fork toward it, and a real-DB regression pin holds the difference.

  Authority and custody argument: authority only narrows; nothing is granted.

  - **Invariant (owner-confirmed threat model, 2026-10-01):** an owner can always retire any agent they own that is not already revoked, whatever its lifecycle state; a revoked agent can never return to `active`, and neither can its open connection setup. Haven still signs nothing — the revoke is a database state change plus the existing best-effort passport revocation, and no new spender, signer or custody path is introduced.
  - **Unchanged:** the delegation-rail budget lifecycle (`revoke-all`, build and activate still guard as #2025 set them), the archive rule (`ARCHIVE_AGENT_SQL` still requires `revoked` — the dialog now reaches it because the revoke succeeds), `agentAuth`'s status allow-list (an unknown future status stays refused), and the half-revoked Finish-revoking flow from #3542.
  - **Residuals, accepted by the owner:** a setup that reached `proposed`/`approval_in_progress` (an approval transaction hash exists) is not cancelled by a revoke — it keeps its state and its existing refusals decide, which is the narrow-not-clever choice; the cancel is fire-and-forget by design (a zero count is a fact, not an error); the dialog's 404-as-already-done remains only under the #1437 stale-tab race, where the status it rendered cannot itself be `revoked`.

  Tests: a real-DB suite (`infra/repositories/__tests__/agent-connection-setups.test.ts`, `revoke accepts pending_approval (#3544, real DB)`), run in CI against the issue-dedicated Postgres — revoke+archive succeed for a `pending_approval` agent on a `delegator_hybrid` account (fails on `3739fd3b`); revoking cancels the open setup in the revoke transaction; a no-setup revoke and an idempotent re-revoke behave; `applyApprovalState` abandons on a zero-row activation with the setup left open and the agent still revoked (fails on `3739fd3b`); `applyApprovalState` still activates a genuinely `pending_approval` agent (guard is narrow); both activation statements never flip a revoked agent back (regression pin); `api_key_hash`/`api_key_prefix` survive revoke (regression pin). Route tests (`routes/__tests__/agents-characterization.test.ts`) pin the widened SQL, the in-transaction setup cancel, 200 for `pending_approval`, 409 `already_revoked`, 409 `not_revocable`, 404 unknown/not-owned, and the passport best-effort contract. Dialog tests (`RemoveAgentDialog.test.tsx`) use the real `ApiRequestError` wire shape — 409 `already_revoked` proceeds to archive, 409 `not_revocable` surfaces an error and skips archive, the #1437 stale-tab 404 still completes, and a `pending_approval` agent is removed end to end.

  Money-path by file (`infra/repositories/agents.ts` is on the runtime globs) and by label (agent-authority lifecycle). Perimeter unchanged: no new spender, no new key custody, no Haven-signed authority, no widening of any delegation — only the owner's ability to retire an agent that has none.
