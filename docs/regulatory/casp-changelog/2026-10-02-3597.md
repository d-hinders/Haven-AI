- **#3597** — `haven feedback submit "<text>"` adds a one-way CLI-to-backend
  feedback channel (a new `feedback` table, 7-day retention, user-JWT-only
  write route) with no payment, signing, authority, custody or route-pin
  surface: it stores a 4000-character text and nothing else, under the
  caller's own `user_id`, read by nobody today (`GET /feedback` does not
  exist; the founders-only masked read is #3602, filed separately). The
  authority model is unchanged — a user JWT authenticates exactly what it
  already authenticates everywhere else (`routes/contacts.ts`'s own
  pattern); no agent API key, no anonymous caller and no MCP tool can reach
  this route, so it adds no new agent-reachable surface at all. The custody
  argument is the reason this issue exists: a raw private key must never
  reach Haven, so every layer of the secret check — prefixed/labelled
  secrets, exact match against this machine's own stored credentials, 64-hex
  token-to-address derivation compared against this user's own key-backed
  addresses, and BIP-39 recovery-phrase detection — runs in the CLI BEFORE
  any request carrying the text is sent (`packages/cli/src/secret-check.ts`),
  with the backend re-running the address-derivation and labelled-secret
  layers again as a backstop against a caller that bypasses the CLI
  (`routes/feedback.ts`, `modules/feedback/secret-check.ts`). The
  address-derivation layer fails CLOSED: an unreadable address set refuses
  to send rather than silently skipping the one layer that stops a key
  reaching Haven. Mutation-proven: a derived address matching a key-backed
  address refuses (both an agent's `delegate_address` and an account's
  `owner_address`), a tx/delegation hash's derived address does not match
  and passes, a zero key and a key ≥ the curve order both fail to derive
  (and therefore pass, consistent with "not a valid key"), a 128-hex
  calldata run is not windowed into two 64-hex candidates, an 11-word BIP-39
  run does not refuse on length alone, and a tombstoned agent directory's
  key is still read by layer 2 (`secret-check.test.ts`, `feedback.test.ts`
  on both the CLI and backend sides). `redactVendorSecrets` runs once more
  at the repository write boundary as a third, independent backstop. The
  secret check's own residual risk — a custom `--credentials-dir`, keys for
  wallets that are not this user's, and a plain-password secret with no
  recognisable shape — is accepted and named (the CLI prints a one-line
  reminder before sending on that last case), per the owner's recorded check
  design. Perimeter unchanged.
