- **#3669 (epic #3634)**: the backend's supported chain set narrows to Base (8453) and
  Base Sepolia (84532). Gnosis Chain (100) becomes a **known, history-only** chain,
  following the owner's decision (c) on #3635. The production audit found 10 retired
  `legacy_safe` accounts, 7 payment intents and 7 passkeys on chain 100, and nothing else.

  `domain/chains.ts` now separates two sets.
  - **Known** is every registry chain, Gnosis included. `getChain`, explorer links
    and the Etherscan V2 history read keep resolving it. This is what keeps those
    accounts' transaction history and the explorer links on their persisted
    payment rows readable.
  - **Supported** is an explicit list of 8453 and 84532. It drives the following:
    - account deploys (`deployableChainIds` / `isDeployableChain`);
    - the relayer balance monitor;
    - price polling;
    - the outbound fee-bump loop;
    - catalog network acceptance;
    - `GET /chains` and discovery `supported`;
    - balances, portfolio, receive and an agent's delegate-balance read, which
      refuse 100 with a 4xx. Balances and portfolio now also refuse it when the
      chain is not named and is taken from a chain-100 account, so neither route
      makes a Gnosis RPC read.

  Creating an agent record on a chain-100 account is not refused, but such an
  agent cannot move funds. Every payment entry point answers the retired-rail
  410, and a budget grant requires the delegation rail, whose chain set
  (`DELEGATION_RAIL_CHAIN_IDS`) holds only 8453 and 84532.

  Chain 100 is made **read-only**. The history aggregation no longer ingests inbound
  transfers for a chain outside the supported set, so nothing is written for chain 100
  (production holds no such rows). The delegation rail's viem chain map drops Gnosis.
  The rail already refused chain 100, because `DELEGATION_RAIL_CHAIN_IDS` holds only
  8453 and 84532. The retired-rail 410 for chain-100 legacy agents is unchanged and
  stays pinned by #3640's test.

  Chiado (10200) leaves the mainnet gate's testnet list. An unlisted chain is
  classified value-bearing, so it fails closed.

  The passport receipt-key boot check now compares the receipt signing key against
  every `RELAYER_PRIVATE_KEY` / `RELAYER_PRIVATE_KEY_<n>` variable set in the
  environment. Before this change it compared only the supported chains' keys, so
  narrowing the set would have silently dropped a still-configured chain-100 key from
  the check.

  Perimeter NARROWED: one fewer network on which any account deploy, relayer, monitor
  or payment path can run. No new authority, signer or settlement path. Custody
  unchanged.
