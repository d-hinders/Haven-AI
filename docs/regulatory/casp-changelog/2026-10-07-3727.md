- **#3727** — the plain-HTTP x402 agent flow got shorter, and the perimeter
  did not move. Two additive surfaces, neither of which signs, spends, grants,
  or contacts anyone new:

  1. **`haven_report_x402_outcome` accepts optional settlement evidence**
     (`settlement_tx_hash` and/or the raw base64 `PAYMENT-RESPONSE` header as
     `payment_response`). On an `accepted` outcome Haven decodes the header
     taking its `transaction` field only — a `payer` inside is the merchant's
     claim and is never written (#3125 discipline) — and records the hash
     through the SAME seam `haven_report_settlement_evidence` has always
     used (`HavenClient.reportSettlementEvidence` →
     `POST /machine-payments/evidence` → the backend's on-chain verification
     of the delegate → merchant transfer). Nothing is trusted because the
     agent asserted it: a hash that does not match the payment on-chain is
     refused exactly as the standalone evidence tool refuses it, BEFORE the
     report is written, and the zero-hash "delivered, not settled" marker is
     refused the same way. The evidence remains caller-asserted and
     chain-verified; the payment's rail, amount and merchant are still read
     from Haven's own record. A `rejected` outcome records no evidence at
     all.
  2. **`retry_headers` ride every `payment_header` result** (signer
     `haven_sign_x402` / `haven_x402_sign_header`, hosted `haven_submit` on
     the erc7710 path): `{ <name>: <payment_header> }` derived from the
     SDK's live rule `x402PaymentHeaderNamesFor` — both names on eip3009,
     `PAYMENT-SIGNATURE` only on erc7710 (the #2341 rule, unchanged). A
     bookkeeping convenience about which header NAMES to set; the header
     value itself is unchanged and still crosses only from the agent's own
     signer to the merchant the agent itself retries.

  **The perimeter is unchanged.** Haven still never contacts the plain-HTTP
  merchant — the outcome report and the evidence report are agent-asserted
  claims about a retry the AGENT made, and the only network reads Haven
  performs are its own chain verification of the hash and its own backend.
  No new signing operation exists (the evidence path verifies, it never
  signs); no API credential becomes sufficient to spend (the flow still
  requires the agent's own merchant retry under its own signed header); no
  route, spender or authority surface moves. A user can still revoke Safe
  permissions and read every record outside Haven, unchanged.
