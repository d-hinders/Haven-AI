# 2026-10-07 — #3731: `funds_cover_remaining` coverage reporting and a funding-first underfunded prepare

- **#3731**: the `/machine-payments/allowances` rows (and the SDK's
  `HavenAllowance` / `haven_get_agent` summary rows) now carry
  `funds_cover_remaining: true | false | null` — whether the account's balance
  can back THAT row's whole remaining period budget, from one `balanceOf` read
  per distinct token. A `prepare_reverted` body whose revert was the token's
  own insufficient-balance error additionally carries
  `revert_cause: "insufficient_balance"` and a funding-first `message`, and
  the hosted `PREPARE_REVERTED` tool failure maps it to
  `next_action: fund_account_or_raise_allowance` with a funding-specific
  omitted reason. "ready means you can pay" copy is corrected to "readiness is
  authority" across the SDK guidance, skill bundle, CLI runbook, marketing
  pages and `types.ts`.

  Authority and custody argument: this is READ-ONLY reporting plus failure
  ATTRIBUTION — no new spender, no new authority grant, no new spend path. The
  boolean is the only new wire data; the balance itself never leaves the
  server (the `balance-coverage.ts` `covered` posture, #3126). The readiness
  value set is unchanged (`ready` / `needs_approval` / `revoked`) so installed
  consumers that switch on it do not break; `funds_cover_remaining: false` is
  documented as a heads-up to mention, NOT a refusal — the payment is still
  attempted and the chain still decides. No off-chain coverage gate is added
  before any prepare: gating a payment on a cached balance would be an
  off-chain policy controlling spend, against Red Line #4
  (`docs/regulatory/casp-risk-guardrails.md`). The refusal ledger is
  unchanged — the revert still refuses, still books `onchain_revert` (the
  reason set is fixed by the migration 086 CHECK), and `revert_cause` is
  computed inside `prepareFailureBody` so no refusal call site moves. The
  erc7710 settlement child remains never-simulated: on that scheme this field
  is the only signal, and a drained-between-prepare-and-sign treasury still
  surfaces at submit as `onchain_execution_failed` — the chain's own verdict
  stays the control, classified after the fact.

  Non-goals held: no `haven_check_funds` naming in the failure (the body
  carries no token or amount, and the revert already proves the shortfall);
  the `phase: insufficient_funds` taxonomy name (every live writer's
  budget-exceeded) is deliberately NOT put on this body.

  Perimeter unchanged.
