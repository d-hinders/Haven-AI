- **#3732** — the #1719 runtime picker never defaults: an empty answer at the
  installed-client prompt no longer accepts the first listed client; it
  re-asks (spending one of three attempts) and then aborts with
  `runtime_prompt_aborted`, having written nothing — no agent created, no
  credentials stored, the setup token still unused
  (`packages/connect/src/installed-clients.ts`). The list may still MARK the
  scan's suggested client, but only a typed number selects. Required
  alongside it: a user-scope `~/.claude.json` carrying an `mcpServers` key is
  now config-file evidence for Claude Code (via a separate `evidencePath`,
  because `configPath: null` still means "configured through its own CLI"),
  so a machine with both a Claude Code MCP config and a Codex config ties
  and produces NO suggestion, instead of suggesting Codex by construction —
  the field failure behind this issue. `--json` `suggested_runtime` and the
  refusal prose follow the same rule, and the prompt rung now receives the
  same `env` the hint scan got. The picker's chat-app row reads
  "Claude Desktop (chat app)" so it cannot be read as "where I am".

  - **No new spend path and no new authority surface:** the change decides
    only WHICH local client config receives the already-minted credentials,
    and it fails closed — an unanswered prompt writes nothing and leaves the
    setup token unused, strictly narrower than the old behaviour (Enter
    accepting the first candidate). No key is moved, minted or printed; no
    signature is created; the server-side flow is untouched. The scan stays
    read-only, and the new `mcpServers` check reads `~/.claude.json` and
    nothing else — an unreadable or unparsable file grants nothing beyond
    the directory marker it already was.
  - **Direction of travel is narrowing, not widening:** before, pressing
    Enter could plant an API key and a delegate key into whichever client
    sorted first — on any machine with a Codex config, that was Codex even
    when the user ran Claude Code (field evidence 2026-10-07, finding F6 of
    the production x402 field test). Now nothing is written until a runtime
    is explicitly chosen, by a typed number at the prompt or `--runtime` on
    the command line, exactly as the wiring-collision prompt (#2551) already
    behaved. The owner decision of 2026-10-07 is option (B): never a
    default, single candidate included — a scan finding one app says what
    exists, not where the user runs their agent.
  - **Tested:** `installed-clients.test.ts` asserts the claude-code
    `mcpServers` evidence over real paths, the codex/claude-code tie
    producing no suggestion, `~/.claude.json` without `mcpServers` (and an
    unparsable one) staying directory-tier, the empty answer re-asking and
    aborting after `MAX_PROMPT_ATTEMPTS` with nothing written (lone
    candidate included), the `(suggested)` marker never pre-selecting, and
    the label; `runtime.test.ts` pins `suggested_runtime` and the prose

    rung receives the hint scan's `env`. Hand-built candidates that state
    states the real scanner cannot produce (`claude-code` with config-file
    evidence built by hand) are kept and marked as pure-function tests of
    `installedClientHint`.

  Authority and custody argument: nothing is granted, signed, widened or
  moved. The change removes an implicit selection and corrects which client
  the evidence names; no agent, human or machine gains or loses any ability
  it had before, and the worst case goes from "live keys in the wrong
  client" to "nothing written". Perimeter unchanged.
