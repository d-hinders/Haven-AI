# 2026-10-07 — #3747: hosted merchant egress — a string-level policy for every hosted merchant request

- **#3747**: every hosted merchant request (quote, MCP session setup, tool
  call, paid delivery, discovery) now runs under a string-level egress policy
  installed by `createHostedHavenClient`
  (`strictMerchantEgressPolicy()`, SDK `merchant-egress.ts`): https-only
  public hosts — no IP literals (v4/v6, including `URL`-normalised exotic
  spellings), no `localhost`, no single-label hosts, none of
  `.internal`/`.local`/`.localhost`/`.test`/`.invalid`/`.example` — GET
  redirects followed only `redirect: 'manual'` with every hop re-checked (≤3;
  a redirect on any other method is refused, so a payment header is never
  sent to a redirect target), per-use response caps enforced WHILE reading
  (stream-level; never buffered past the cap — 256 KiB on quotes and MCP
  session setup, 64 KiB on discovery, 5 MiB on paid delivery), and per-use
  timeouts (15 s probes, 5 s discovery, 300 s paid delivery). The same policy runs at
  quote/prepare time (`haven_quote_x402`'s transport, the
  `quoteMcpToolCall` family before the probe and before the #1271 discovery
  fallback, and `haven_pay_x402_quote`'s pre-intent retry-target check), so
  a bad target is refused BEFORE funding — it can never surface only as a
  funded-but-undeliverable payment. A refusal during paid delivery AFTER the
  request was sent (a merchant redirect, a refused hop, a mid-read cap
  crossing) is routed through the existing #1300 verify-then-sweep handling —
  `haven_get_payment_status` first, sweep only if no settlement appears,
  never a blind sweep — and on erc7710 the existing no-sweep handling applies
  (nothing can strand). Without `merchantEgress` the SDK, local-MCP and
  embedder behaviour is byte-for-byte unchanged (characterization-pinned);
  the field is optional and additive.

  Authority and custody argument: this is NETWORK policy on the hosted
  server's own outbound connections — it gates where a request may CONNECT,
  not whether money moves and not who may spend. No new spender, no new
  authority grant, no new spend path, no mutation of signed payment intent
  (a refusal happens before signing or after an already-signed header was
  relayed; the intent itself is never altered). Off-chain policy is not the
  real spend control here or anywhere: the on-chain allowance and the caveat
  stack remain the only spend authority (Red Line #4,
  `docs/regulatory/casp-risk-guardrails.md`), and the hosted server remains
  keyless — the policy touches no key material and no signing path. The
  refusal envelopes are structured tool failures with
  `next_tool_omitted_reason`, name the agent-chosen URL only, and never
  carry a resolved address (the policy never resolves DNS) or a non-402
  response body (the `merchant_not_ready` 503 shape stays the one
  exception, pinned).

  Measured: the refusal-before-connection matrix (each of `http`, IPv4,
  IPv6, `localhost`, single-label, `*.railway.internal` across each hosted
  path, asserting zero merchant fetches) lives in
  `packages/mcp-server/src/hosted-egress.test.ts`; the transport rules
  (re-checked hops, POST-redirect refusal, while-reading cap on an endless
  body, per-use budgets, `MerchantTimeoutError` classification) in
  `packages/sdk/src/merchant-egress.test.ts`; the money-path cases
  (pre-funding refusal with no intent row, eip3009 mid-flight
  verify-then-sweep, erc7710 mid-flight no-sweep) one test per case in the
  hosted suite. Accepted residual, stated in
  `docs/security/hosted-egress.md`: a public host name whose DNS ANSWER
  points at private space is not blocked — that is the resolution-time work
  parked in #3742–#3744.

  Perimeter unchanged.
