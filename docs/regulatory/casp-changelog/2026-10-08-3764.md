# 2026-10-08 — #3764: the SDK reports the merchant's EIP-3009 settlement hash

- **#3764** — `packages/mcp-server/src/tools/paid-mcp-completion.ts`: the
  hosted eip3009 tools now surface the outcome of the merchant-settlement
  evidence report the SDK posts after an accepted purchase.

  The SDK (`completeX402MerchantCall`) already held the merchant's
  `PAYMENT-RESPONSE` settlement hash on the funding-leg path and reported
  only the funding hash. It now posts a SECOND evidence report — one attempt,
  no backoff — gated on a well-formed, non-zero hash different from the
  funding hash (case-insensitively). The backend verifies the delegate →
  merchant transfer on-chain before recording
  (`machine_metadata.merchant_settlement_tx_hash`, #3475); the SDK hands
  Haven a claim, not an authority. No money, authority or signature moves.

  Tool-level changes, both additive:
  - `deliverMerchantPayment` passes `settlement_evidence_outcome` through.
  - `haven_complete_mcp_tool` — which still drops the FUNDING
    `evidence_outcome` (#2970 review) — maps the SETTLEMENT outcome the way
    #3727's `evidenceHandoff` does: recorded (or nothing posted) answers the
    pre-#3764 shape byte-for-byte (no guidance block); retryable names
    `haven_report_settlement_evidence` with `payment_id` and the hash
    prefilled; refused names no tool with the reason (re-reporting the same
    hash re-refuses).
  - `haven_settle_mcp_tool`'s eip3009 settled arm maps the same field through
    the same helper (`settlementEvidenceHandoff` / `settlementEvidenceReason`);
    the recorded arm's prose is unchanged.

  The erc7710 path is untouched: no funding leg means no second report, and
  its single settlement report (anchored on the merchant's hash) is exactly
  what #2092/#2970 landed. `lint:next-steps` stays at zero; the next-step
  census constants moved 29→30 sites / 33→35 fixtures for the one new
  conditional emission.
