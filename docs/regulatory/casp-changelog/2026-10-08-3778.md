- **#3778 — purchased redemption codes no longer live only in the agent's
  context** — evidence and guidance only; no custody change.
  - **The gap (prod, 2026-10-08, Bitrefill invoice `ff28c928…`, pay payment
    `a0b6ac90…`):** a plain-HTTP x402 purchase returned the gift-card code and
    PIN in the merchant's `invoice/status` body — to the agent only. Haven
    never sees a plain-HTTP merchant body, receipts hold payment and
    settlement evidence only, and the dashboard showed a settled 0.50 USDC
    payment with no indication a deliverable existed. If the session ended
    before relay, the owner had paid for goods they could not find (Bitrefill
    recovery: SIWX from the payer wallet, #3728, or a support ticket).
  - **The fix (issue options 1 + 2):**
    - *Guidance:* the haven-pay skill's "Reporting after a purchase" section
      now requires relaying any delivered code, key or credential to the owner
      immediately, verbatim, and documents the Bitrefill SIWX recovery path.
      Both byte-pinned copies edited identically.
    - *Deliverable pointer:* `haven_report_x402_outcome` and the hosted
      settle/complete tools accept an optional bounded `delivery_reference`
      (≤ 512 chars, migration 107 `machine_payment_evidence.delivery_reference`),
      persisted on the accepted arm's evidence write and shown on the receipt
      read, the transaction detail drawer and the activity feed — the owner's
      "a deliverable exists and where to recover it" signal.
  - **What Haven deliberately still does not do:** store the deliverable
    itself. `deliveryReferenceError` (@haven_ai/core, shared by every
    accepting surface) refuses credential-shaped values — JWTs, long
    hex/base64 token material, grouped uppercase gift-card codes — before any
    write; the SDK and backend layers enforce the same shape independently.
    The recognizer is deliberately conservative (honest order/invoice
    references pass); the primary control is the relay rule, not the refusal.
    Rejected outcomes record no reference (nothing was delivered), and the
    value is agent-asserted only — nothing financial keys off it.
  - **Perimeter:** no route signature payload, delegation, enforcer, budget,
    key custody or spend-authority change. The field is additive evidence
    about a payment that already happened; Haven gains no ability to read
    merchant bodies it does not already see and no new surface carries a
    secret.
  - **Money-path by file:** `packages/mcp-server/src/**`, backend evidence
    and a migration — the classifier marks this money-path; a `dev → main`
    promotion needs a covering green money-flow QA run. Migration 107 is a
    single nullable-column ADD on an existing table; CODEOWNERS gates
    `src/db/migrations/*.ts` directly.
  - **Pinned by:** `delivery-reference.test.ts` (core recognizer, code-shaped
    refusal), backend evidence-attach tests (code-shaped value refused 400;
    reference recorded and echoed on the receipts read), mcp-server handler
    refusals (pre-funding for settle), and the byte-parity skill tests
    (`skill-content.test.ts` with the frontend twin).
