- **#3927 — the eip3009 merchant-settlement writer locks the payment too** —
  a concurrency hardening of the record that says which on-chain transfer
  settled an x402 EIP-3009 payment; it moves no funds and touches no signing,
  authority, custody or key-management path. Money-path by file
  (`packages/backend/src/infra/repositories/x402-authorizations.ts`).
  - **Change:** `recordEip3009MerchantSettlement` took one advisory lock, keyed
    by the settlement hash. Two DIFFERENT verified hashes for one payment —
    the sweep's nonce-proven hash and an agent-reported sibling hash — took
    different locks, both pre-reads saw no recorded hash, and only the
    UPDATE's `merchant_settlement_tx_hash IS NULL` compare-and-set kept the
    second from overwriting the first; the loser answered `not_eligible`. The
    writer now also takes `pg_advisory_xact_lock(hashtext('eip3009-intent:' ||
    intent id))`, always after the hash lock (fixed order hash → intent), so
    the pre-read is authoritative for every race and the loser answers
    `conflict`. The prefixed key cannot collide with the bare-hash keyspace;
    no other site locks an intent id, and the erc7710 confirm takes only the
    hash lock, so no lock cycle exists. The compare-and-set stays as the
    backstop. The erc7710 confirm's own stance is unchanged (owner decision
    2026-10-14).
  - **Perimeter:** unchanged. The record decides which settlement hash
    receipts and the accounting feed book; the change makes the first
    verified hash win deterministically and the second be refused by name.
    No payment, budget, refusal or authority rule moves; no wire field
    changes (the 409 `settlement_unverified` code is unchanged).
  - **Verification:** two real-DB tests beside the writer. (1) The UPDATE
    run from two interleaved transactions on one funded payment with two
    hashes: the blocked one writes 0 rows — red with the `IS NULL` clause
    mutated to `AND TRUE`. (2) Two concurrent writers through the function,
    with a third connection holding the row until both are proven blocked
    (`pg_stat_activity`): exactly one hash recorded, the loser `conflict` —
    red on the previous code (`not_eligible`) and red again with the intent
    lock removed. The sweeper and settlement-evidence suites stay green
    (58/58 across the three files); the four statements PREPARE in
    `db:schema-smoke`.
  - **Verdict:** Perimeter unchanged.
