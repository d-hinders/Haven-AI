- **#3933 — a budget cannot be silently replaced: a plain grant into an
  occupied slot is refused** — narrows the authority left enabled after a
  budget replacement; it moves no funds and adds no authority. Money-path by
  file (`packages/backend/src/routes/agent-delegations.ts`,
  `infra/repositories/delegation-budgets.ts`).
  - **Change:** activating a grant into a (token, recipient) slot that held a
    live budget swept the old row to `replaced` in the database only. The old
    delegation stayed enabled on-chain — still redeemable by the agent's
    delegate key, or by a sub-budget grantee whose chain ends in it, outside
    Haven — and only the edit flow (grant, then the owner's Stop) ever
    disabled it. `POST /agents/:id/delegations/build` and `…/activate` now
    refuse such a grant with 409 `BUDGET_SLOT_OCCUPIED` (+
    `existing_delegation_hash` and `occupying_delegation_hashes`) unless
    `replaces` names exactly the slot's live rows — all of them, so a
    re-keyed carry/steady pair is replaced and Stopped as a whole, never half;
    activate checks under the agent lock, so the read is authoritative. The dashboard's budget form and fund-merchant flow open
    the edit of the matching budget instead of a plain grant; the edit flow
    names `replaces` on build and activate and then Stops each replaced row
    (one owner signature per row); an edit that changes the recipient is a
    new grant into the empty target slot followed by the Stop of the old
    slot's rows; an active agent with a
    `replaced`, unexpired grant is flagged on its page with a finish action
    that stops it. "Live" is `spendableDelegationSql` without the
    started-window clause (#3920): active and unexpired.
  - **Invariant (owner-confirmed threat model, 2026-10-14):** once any owner
    flow that replaces a budget completes, at most one unexpired budget
    delegation per (agent, token, recipient) slot is enabled on-chain; when
    the old grant's Stop does not land, the surface shows it as still enabled
    with a way to finish (`revoke_unfinished`). Residuals accepted: the
    two-prompt window between the new grant and the old one's Stop; an
    abandoned Stop is shown, not hidden; stopping the old grant ends open task
    and sub-budgets carved from it; the invariant is per slot and does not
    bound open-plus-pinned or shared-payTo authority; grants already left
    enabled by past replaces stay enabled until the owner uses the finish
    action — Haven cannot stop them itself (non-custody principle 1); a
    client that names `replaces` correctly and never Stops leaves the old
    rows enabled — the server cannot force the Stop, so the finish action is
    the control.
  - **Perimeter:** narrowed. No new signer, key or authority path; the only
    new request field (`replaces`) can only make a request that would
    otherwise be refused succeed when it names exactly the slot's own live
    rows,
    and that path is the existing edit composition.
  - **Verification:** real-DB route tests — the characterisation (activate
    → 200, old row → `replaced`) committed first, then flipped to the named
    409 with nothing written; empty slot, edit with the right hash, a wrong
    or stale hash, an expired row (does not occupy), build refusal and edit
    build; then the slot boundaries — a pinned grant beside a live open one
    (allowed), a not-yet-started row (occupies), another agent's hash
    (refused), a carry/steady pair (one half refused at build and activate,
    both allowed and both `replaced`), a recipient-change edit. Neutering the
    rule reds three, dropping the activate check reds two, `.every`→`.some`
    on the pair check reds two. The QA `delegation-lifecycle` leg now asserts the plain grant's 409
    live and proves BOTH grants disabled on-chain; the seed re-grants through
    the edit composition; the CLI names the refusal and its hash.
  - **Verdict:** Perimeter narrowed.
