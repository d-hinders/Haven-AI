# 2026-10-16 — #4023: per-account deploy salt + create additional account

**Perimeter: unchanged.** Nothing here moves funds on Haven's behalf, widens
any authority, or changes who can spend from which account. The change
re-derives *where* an owner's account lives (a per-account salt instead of the
literal `'0x'`) and lets the owner create a second account for a signer set
they already hold. The only new spend-capable surface is the user's **own**
additional account, spendable only by the passkey the user authenticated with
— an authority class the user already had. No agent, relayer or Haven-side
authority appears.

## What changed

- **A per-account deploy salt.** Until now every user account was derived at
  the literal salt `'0x'`, so one owner configuration could own exactly one
  address and a create request for the same owner answered 409. Migration 114
  adds `smart_accounts.deploy_salt` (`NOT NULL DEFAULT '0x'` — the default IS
  the backfill, so every pre-existing row keeps deriving its existing
  address) plus a `hybrid_deploy_salt_counters` table. The counter is per
  (user, passkey `key_id`) and global across chains, starts at 1, and is never
  reused — it lives outside `smart_accounts` so `unlink`'s hard DELETE can
  never hand a possibly-funded old address back out. The salt is threaded as a
  REQUIRED parameter through every user-account derivation and deploy path
  (`hybrid-provisioning.ts`, `delegation-rail.ts` and all ten
  `createTreasuryOps` callers). The forbidden fallback pattern is absent by
  construction: a forgotten caller fails to compile rather than silently
  deriving the salt-0 account.
- **`POST /accounts/hybrid` creates an additional account.** The server copies
  exactly one passkey's coordinates — the `key_id` the user authenticated with
  — from the **source account's** signer set, never from the request body;
  the new account's owner config is that passkey alone, `is_default` is always
  false, the route carries `moneyPathRateLimit` and a soft cap of 10 accounts
  per user per chain, and an idempotency key makes a replay return the same
  account. Row, copied passkeys and counter bump commit in one transaction.
- **The pre-spend guard.** `ensureHybridDeployed` now refuses with
  `HybridDerivationMismatchError` — before `assertRelayerBudget` /
  `recordRelayerSpend` — when the derivation does not equal the caller's
  expected address. This closes the failure mode where a missing salt would
  have deployed the salt-0 account (a real relayer spend on the wrong
  account) before erroring. Delegate accounts keep deriving at `'0x'`
  untouched (15 delegate derivation sites; the SDK and signer vendor the
  literal `'0x'` offline, pins unchanged), so installed clients and agent
  grant surfaces are unaffected.

## Why the perimeter is unaffected

Derivation stays **non-custodial and watch-only**: the address is computed
from the owner's public passkey coordinates plus a salt, exactly as before.
The salt is a public derivation parameter, not a credential — knowing it
grants nothing, and Haven still holds no key material for the owner's
accounts. **Factory deploy is still permissionless**: the relayer pays gas for
the counterfactual deploy exactly as before; the salt only selects *which*
counterfactual address is deployed, never who may deploy or spend. **No new
authority**: the additional account's signer set is the user's own
authenticated passkey, copied server-side from a source account the user
already owns; agents' delegate accounts remain at the literal `'0x'`, so no
grant, sub-budget or task-budget surface changes scope. The relayer-facing
edges actually tighten: the pre-spend mismatch refusal above, the rate limit
and per-chain cap on create, and the never-reused counter that stops a stale
funded address from being silently re-linked after unlink. Migration 114
changes no custody, balance or authorization state — it adds a column whose
default preserves every existing derivation.

Tested by the committed-first characterization fixture
(`hybrid-provisioning-salt.characterization.test.ts`), the deploy-mock suite
(`hybrid-provisioning-salt-deploy.test.ts`, including the
recordRelayerSpend-not-called pin), and the real-DB
`smart-accounts-deploy-salt.test.ts` (backfill, per-user address uniqueness,
counter non-reuse under unlink). Perimeter unchanged.
