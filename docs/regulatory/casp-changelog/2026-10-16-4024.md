# 2026-10-16 — #4024: the "New account" create dialog

**Perimeter: unchanged.** This is the frontend half of #4023's
create-additional account, plus a tightening of that route's refusal and
replay contract. It adds no route, no signer path and no authority: the
dialog calls the request #4023 analysed, with the fields #4023 defined, and
moves no funds. Money-path by intent (it creates a fundable account) and, for
the contract change, by file (`routes/hybrid-accounts.ts`).

## What changed

- **A "New account" action on the Accounts screen** (`PageHeader` actions
  slot, owner-chosen label) opens `components/NewAccountDialog.tsx`. It is
  hidden when the user has no account (there is no source to create from) and
  explains, instead of offering a form, when no account has a passkey.
- **One WebAuthn assertion, no new credential.** The dialog asks for a name
  and a network (the chains the backend serves deploys on, as signup offers),
  then runs one `navigator.credentials.get` restricted to the source
  account's passkey credential ids (source: the scoped account, else the
  default account, else the first account with a passkey). The returned
  credential id becomes `key_id`.
- **The create call** is `POST /accounts/hybrid` with `source_account_id`,
  `key_id`, `chain_id`, `name` and a client-minted `idempotency_key`: fresh
  for each new submission, and the recorded one for every retry while an
  outcome is unknown (below). The account list is then re-read, so the new
  account appears. Refusals are mapped by `error_code` first; until the
  backend sends codes, the status decides the message. A code-less 4xx is a
  definite refusal of that request (429: the rate limit; any other: a typed
  "couldn't create" with the backend's sentence, and no retry promise). No answer or a 5xx is an
  **unknown outcome**: the create may have committed behind a lost response.
  The dialog then holds one record — the idempotency key that was sent, the
  name, the network, and the account ids it saw when that attempt started —
  and locks the name, network and source, so every retry sends that same
  key and request — the network is the record's own, so a deployable-chains
  list that narrows later cannot change the retry's `chain_id`. Only a 201
  or detection (an account outside the baseline, on that network, with that
  name, seen whenever the account list changes between attempts — "Check
  again" or any other refresh) clears it; no
  refusal of any status and no early return does. (The route now replays
  before it validates — below — so a retry of a create that went through
  returns that account; the client rule costs nothing and also covers an
  older backend.) "Check again" and "Try again"
  never run at once, a failed re-read is reported as a failed read, and
  closing the dialog drops the record (the message tells the owner to check
  before trying again). If the pinned source stops being a source while the
  record stands, "Try again" is disabled with a message saying so; checking
  and closing remain.
- **The create-additional contract, tightened on the backend
  (`routes/hybrid-accounts.ts`, after #4023 merged without it).** Every
  refusal carries an `error_code`: 404 `SOURCE_ACCOUNT_NOT_FOUND`; 422
  `SOURCE_HAS_NO_PASSKEY` (its sentence no longer says "EOA-only"),
  `KEY_NOT_ON_SOURCE`, and `ACCOUNT_CAP_REACHED` with `cap` (10) and the
  `chain_id`. The idempotent replay now runs FIRST — after the shape checks,
  before the source, key and cap checks — so a retried 10th create whose
  response was lost gets its account (201) instead of a cap refusal. The
  replay is scoped to the caller, answers the STORED row's `chain_id`, and,
  as the `send_idempotency_key` pattern does, refuses a key reused with a
  different `chain_id` or `key_id` (409 `IDEMPOTENCY_KEY_REUSED` with the
  existing id); the source account is not stored on the new row, so it is
  not pinned. The in-flight race gets the same answer: a retry that loses on
  the key's unique index inside its transaction re-reads the committed winner
  and answers it (201, or that 409) instead of a bare "Account already
  registered", and its counter bump rolls back with it. `idempotency_key` is
  capped at 128 characters (its column), so a longer one is a 400. The
  dialog binds a retry to the recorded passkey (its prompt offers only that
  one) and maps `IDEMPOTENCY_KEY_REUSED`: it re-reads the list and shows the
  named account as created, or says the earlier try created it.

## Why the perimeter is unaffected

**No key material leaves the client and none is accepted from it**: the
request names a credential; the server copies that passkey's public
coordinates from the source account's own signer-set row (#4023). **The
assertion is a choice of key, not a proof to Haven**: the server checks that
`key_id` is one of the source account's passkeys and does not receive or
verify an assertion; the dashboard session JWT is the authentication, as on
every owner route. A session holder can therefore make only a key the user
already holds on one account the sole signer of a new, empty account the
user also owns: no new key enters any signer set, nothing is funded, no
delegation, agent or budget is copied, and the account is never the default,
so no agent falls back to it. **Haven still signs nothing** and holds no key.
The residual the owner accepted for route B is stated, not changed: accounts
that share a passkey share its compromise
(`docs/security/delegation-rail-security-model.md` §6b). Backups are not
copied, so the new account starts single-signer, which §7 already permits.
The backend change moves no authority either: the refusal codes are labels on
refusals that already existed, and running the replay first can only return
one of the caller's OWN accounts that carries the key, on the same chain and
with the same passkey — the read is scoped to the caller, and a key reused for
a different chain or passkey is refused. Normally that is the first attempt
of the same create; the signup shape also stores a key it is sent (and never
replays it), so an additional create reusing such a key with that account's
passkey would replay that signup account — still the caller's own, already
created through its own checks. It can neither hand one user another's
account nor skip a check for an account that did not already pass it.

Perimeter unchanged.
