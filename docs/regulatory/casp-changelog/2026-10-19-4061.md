# 2026-10-19 — #4061: settlement reports carry the payment header, and a lifted header is refused

**Perimeter: unchanged; the evidence check narrows.** Nothing here moves
funds, signs anything for Haven, or widens any authority. The change does
three things:

- it lets every EIP-3009 merchant-settlement report carry the proof #3925
  already requires;
- it gives that refusal a machine code, so a report missing the proof can be
  told apart from a wrong one;
- it refuses one more misattribution the #3925 checks let through.

The record involved is `payment_intents.machine_metadata.merchant_settlement_tx_hash`.
It feeds receipts, the bookkeeping feed and transaction history, and moves no
money by itself.

## What changed

- **The proof header reaches the backend.** Since #3925 an agent-reported
  EIP-3009 merchant settlement is recorded only when the report carries the
  payment header that was sent to the merchant (`paymentProofHeader`). Two
  paths never sent it:
  - **The hosted plain-HTTP tools.** `haven_report_x402_outcome` and
    `haven_report_settlement_evidence` had no parameter for it, so every such
    report through hosted MCP was refused. Live: dev payment
    `0d8099b4-dc9a-4f17-8358-03fdc9695bfd`.
  - **The SDK's own #3764 settlement report.** The SDK posted the header with
    its funding report only. This covers `completeX402MerchantCall` (which
    the hosted settle/complete tools use) and the local paid retry.

  Both report tools now take an optional `payment_header`, the base64 header
  the agent retried the merchant with, bounded at the backend's 16 KiB
  stored-header cap. Both SDK paths now post the header their retry sent.
  Every path forwards it the same way: `paymentProofHeader`, plus the names
  `x402PaymentHeaderNamesSent` derives from that payload.
- **The missing-header refusal is typed.** The backend's 409 now carries
  `error_code: "settlement_proof_header_missing"`, and only on that refusal.
  It is the one settlement refusal that a report repeated WITH the header can
  clear. The hosted tools branch on the code, never on the sentence:
  - their answer is code `SETTLEMENT_PROOF_HEADER_MISSING`;
  - `next_tool` names `haven_report_settlement_evidence` with the hash
    prefilled;
  - the reason says to add `payment_header` and that the hash was not judged.

  Before this, the outcome report's top-level reason told the agent the hash
  did not match the payment on-chain, which was false.
- **A header lifted from a same-agent sibling is refused.** Two payments of
  one agent share a delegate. So payment B's report could carry sibling A's
  header together with A's settlement:
  - the payer and signature checks passed (same delegate);
  - the burned-nonce check passed too, because A's settlement really burned
    the nonce in A's header;
  - the hash was recorded on B. This was measured before the fix: 202, and
    the hash was written.

  `observeEip3009MerchantSettlement` now refuses a non-derived proof whose
  nonce is another payment's derived nonce. It does this before the chain is
  read. The refusal carries no `error_code`, because re-reporting it
  re-refuses.

## Correction to the #3925 shard (`2026-10-14-3925.md`)

That shard was wrong when written in two places. Per the immutability rule,
this shard corrects it.

1. *"the agent-reported path reads the nonce from the X-PAYMENT header the
   SDK already posts with the evidence"*. The SDK posted the header with its
   FUNDING report, not with the settlement report the eip3009 branch reads.
   The hosted plain-HTTP tools posted none. So the agent-reported path had no
   header to read on any client. This change makes the sentence true.
2. *"a same-shaped sibling report is now refused"*. That holds when the
   report carries its own payment's header. It did not hold when the report
   carried the sibling's header with the sibling's settlement; see above.
   That case is now refused too.

## Why the perimeter is unchanged

- **The trusted set stays the chain and Haven's own payment row.** The
  header, `payment_id` and `txHash` remain untrusted inputs that only NAME
  what to verify. The header is a signed payment authorization the agent
  already sent the merchant. It is not a credential. Haven reads it, and on
  this branch never stores it.
- **No signature, key role, enforcer, budget or custody path moves.** The
  record still decides what is BOOKED, not what can be SPENT.
- **The new check only refuses.** It cannot turn any refusal into a record.
- **Residual (accepted, unchanged).** A non-deriving client's random nonce
  cannot be tied to a sibling this way. For those, the burned-nonce check
  still binds the record to a header the delegate signed. A merchant that
  never settles still records nothing.
- **Older backends are unaffected.** `main` predates #3925, and there the
  added `paymentProofHeader` on a settlement report is accepted by the
  request schema and not read on that branch.

## Verification

Each fix was committed after a characterization test of the behaviour it
changes:

- the hosted pre-fix refusal: it posted no header, and its reason blamed the
  hash;
- the code-less backend body;
- the sibling-lifted header being recorded.

Each characterization test was then flipped.

- **Backend, real Postgres** (`modules/mpp/__tests__/eip3009-settlement-evidence.test.ts`):
  40/40 pass, and the x402 module suites pass.
  - Dropping the code from the proof refusal turns one test red. So does
    dropping it from the handler.
  - Emitting a code on every refusal turns two tests red: the
    already-recorded refusal and the lifted-header refusal.
  - Disabling the sibling check turns the lifted-header test red.
- **SDK.**
  - Removing the proof fields turns six tests red.
  - Removing the hosted call site's header turns two tests red. Removing the
    local call site's header turns two tests red.
  - Dropping `errorCode` turns one test red.
- **Hosted MCP** (`settlement-proof-header.test.ts` plus the report suites).
  Each of these mutations turns its pinning tests red:
  - not forwarding `payment_header` from either tool;
  - removing either missing-header handoff or reason arm;
  - matching on the reason's presence instead of the code;
  - removing the 16 KiB bound;
  - reverting the signer's or `haven_submit`'s report guidance.

**Verdict:** Perimeter unchanged. The evidence a settlement record may be
written on narrows: one more misattribution is refused, and no refusal turns
into a record.
