- **#4062 — a plain tool error after funding is a rejection, never
  `settled: true`** — closing a false-success on the EIP-3009 funding-leg
  shape; no perimeter change.
  - **The defect (live mainnet run 2026-10-19, prod agent `1c92bc52`,
    hosted MCP `0.10.0-alpha.0`, payment `5ac0077e`, Soundside
    `create_text`, 0.01 USDC):** the merchant answered the paid `tools/call`
    with a plain `isError: true` tool result ("Text generation failed") and
    no settlement receipt. The in-band refusal detection (#3118) recognised
    only two signals — a payment-required challenge and
    `_meta["x402/payment-response"].success === false` — so the plain tool
    error fell through as a success: `haven_settle_mcp_tool` returned
    `settled: true` with `settlement_tx_hash: null`, "Funding and merchant
    settlement both succeeded", and `next_action: none`, while the funded
    USDC sat on the delegate EOA (`balanceOf` 10000; the merchant never
    pulled the authorization). Nothing told the agent or the owner to
    recover it.
  - **The fix (both delivery seams, one rule):** a settlement receipt — a
    `PAYMENT-RESPONSE` header or the `_meta` settlement's own transaction —
    is read BEFORE the acceptance decision, and a plain `isError: true`
    tool result with no receipt is a rejection after funding, exactly like
    the two #3118 signals: `packages/sdk/src/client.ts`
    (`completeX402MerchantCall`, the hosted leg) no longer reports
    `merchantAccepted`, records the reconciliation event, and returns
    `ok: false`; `packages/sdk/src/merchant-completion.ts`
    (`MerchantCompletion.retryRequest`, the local paid retry) adds the same
    condition to `inBandRejection`, records
    `merchant_retry_rejected_after_payment`, and throws the 402
    `x402_retry_rejected_after_funding`. `haven_get_payment_status` then
    shows the stranded balance instead of `next_action: none`.
  - **The boundary is the receipt:** a tool error BESIDE a verified
    settlement hash is delivered, not refused — the money moved, so the
    errored result is evidence. A JSON-RPC `error` envelope (no `result`)
    after payment stays `ok` on the HTTP status, unchanged (#3155 S4
    scope): it carries no settlement statement and no `isError` result.
  - **Verify-then-sweep (scope 3):** the MERCHANT_REJECTED_AFTER_FUNDING
    refusal now says to check `haven_get_payment_status` before
    `haven_sweep_delegate` — an answering merchant still holds a
    single-use EIP-3009 authorization for the payment window and may
    redeem it AFTER refusing (the same rule
    MERCHANT_UNRESPONSIVE_AFTER_FUNDING uses; the #3102 state-driven next
    step already sweeps only when live state says sweep). The tool
    contract descriptions for both settle/complete tools were updated to
    match (description-payload ratchet re-derived: 31,350 / 29 =
    1081.04).
  - **Deliberately out of scope (owner question, flagged not guessed):**
    scope item 2 of the issue — a merchant 2xx with CONTENT and no
    settlement hash currently still returns `settled: true`. Making that
    `SETTLEMENT_UNCONFIRMED` per the contract's flat text would flip every
    normal async-settlement purchase to `settled: false`, which is a
    product decision (agents could re-pay) reserved to the owner. The
    error-path fix above does not depend on it.
  - **Perimeter:** no route, signature payload, delegation, enforcer,
    budget, key custody or API call changes. The refusal moves no money —
    it stops the agent from believing a stranded balance is settled and
    hands it the recovery path (`haven_sweep_delegate`, verify first).
  - **Money-path by file:** `packages/sdk/src/**` and
    `packages/mcp-server/src/**` — the change alters when a purchase is
    reported settled, never who can spend.
  - **Pinned by:** `paid-mcp-completion.test.ts` (fake MCP merchant
    answering the paid call with a plain isError result and no settlement
    through the REAL `completeX402MerchantCall` → MERCHANT_REJECTED_AFTER_FUNDING,
    402 in-band status, verify-then-sweep message, reconciliation event
    recorded) and `mcp-x402-native-profile.test.ts` (local paid retry →
    402 marker, reconciliation event, no evidence; the errored-result-
    beside-a-receipt control stays delivered with both evidence reports).
    Restoring the unconditional `settled: true` reds the hosted test.
