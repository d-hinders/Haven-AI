- **#4094** — `packages/frontend/src/components/ReceiveDialog.tsx` replaces the
  two funding dialogs, `AddFundsModal.tsx` ("Add funds") and
  `ReceiveFundsModal.tsx` ("Deposit address"), which are deleted, and the
  dashboard money card's actions become **Send / Receive**. **No authority,
  custody or execution boundary moves and nothing new is grantable.** The
  dialog tells a human where to send funds and which outbound links to click;
  it signs nothing, submits nothing, and reads no credential. The one
  authority-shaped change in the diff is the dashboard's new **Send** button:
  it renders `DelegationSendModal` — the delegation rail's EXISTING owner-send
  component, byte-unchanged, the same component the account detail page mounts
  with the same props (`accountAddress`, `chainId`, `onSent`) — through the
  existing `DashboardActionPickerModal` when there is more than one account.
  No new signing path, no new route, no changed request: the dashboard gains a
  second entry point to a surface that already existed, and the retired legacy
  Safe send stays retired (#1989) — `SendModal` and its hook remain deleted.
  The modal mounts only for an account with BOTH an address and a resolved
  `chain_id` (`DashboardClient.tsx`, guarded as `chain_id != null`), so #1844's
  rule holds at the new entry point too: an unresolved chain is never
  defaulted into a signing surface, and the unit test for it asserts no modal
  mounts.

  The dialog's network instruction narrows, never widens. The old receive
  screen listed every registry token for the chain (ETH and USDC); the merged
  dialog names ONE token and ONE network — "Send USDC on `<network>` only." —
  and ETH is not listed (asserted in `ReceiveDialog.test.tsx` over the
  dialog's whole text). #1844's refusal is carried over intact and now shared
  by every entry point: an unresolved chain (`chain_id` absent OR present but
  unregistered, via `resolveChainOrNull`) gets no network rule, no address, no
  QR, no explorer link, no faucet and no onramp — an `ApprovalRequiredBanner`
  warning and a `Refresh page` action instead. The `?? DEFAULT_CHAIN_ID`
  fallback at `AccountsOverviewClient.tsx` is dropped: the accounts overview
  passes the account's chain unfallbacked, so the same refusal renders there
  rather than a silent default to Base mainnet. Both "other ways to add money"
  cards stay gated exactly as #3478 slice 2 left them — on the SELECTED
  account's chain (`chainConfig != null && isTestnetChain(...)`, faucet on a
  testnet, Coinbase Onramp on Base only when the build carried
  `NEXT_PUBLIC_COINBASE_ONRAMP_APP_ID` and never on a testnet) — the gates
  moved with the merge; every predicate is a conjunction, so each can only
  remove an offer. The faucet copy is carried over verbatim, including the
  Circle attribution scoped to that link and the "no value" statement.

  Reachability: unchanged in kind. `chain_id` is non-nullable in
  `SmartAccount` (`packages/frontend/src/context/AuthContext.tsx`), so the
  unresolved states remain wire-shaped conditions a partially loaded account
  could produce, not states the shipped UI reaches today — the same latent-not-
  live statement #1844 and #1852 recorded, re-derived for the merged dialog
  and asserted by its own test battery: resolved mainnet (8453, onramp, no
  faucet), resolved testnet (84532, faucet, no onramp), Gnosis (100, a
  registered mainnet with no faucet — the onramp's positive control), both
  unresolved shapes (absent and unregistered 999999, rendered without
  throwing, no network named, no address affordance), Copy, the QR reveal,
  and a resolved chain with no address (known network, honest retry, no
  "Network not confirmed" banner that would lie). `DashboardClient.test.tsx`'s
  #1987 guard is REWRITTEN, not deleted: the delegation Send's PRESENCE is the
  new positive assertion and the retired-rail absences (no approvals row, no
  "Open approvals" link, no `/approvals` href) still hold on the same funded
  fixture; the wiring suite adds single-account vs multi-account picker paths
  for both verbs and the no-Send-without-a-chain case. The e2e and visual
  guards tied to the old dialogs are retargeted, not removed
  (`openReceiveDialog` and its callers, `auth.spec.ts`, and the visual spec
  renamed to `receive-dialog.visual.spec.ts` with its #3483 chain-gating
  assertions intact). Rendered evidence: the `scripts/screenshot.mjs`
  receive-dialog scenarios capture the resolved pair (with the QR shown) and
  the unresolved refusal, and the nine visual baselines are regenerated under
  the renamed stems and listed in the PR.

  Perimeter unchanged.
