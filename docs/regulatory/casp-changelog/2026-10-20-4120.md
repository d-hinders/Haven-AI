- **#4120**: the SDK's post-funding merchant-answer decision now lives in ONE
  module — `packages/sdk/src/merchant-answer.ts` — shared by the hosted
  `completeX402MerchantCall` and the local `MerchantCompletion.retryRequest`,
  and that module joins the money-path perimeter. Control surface touched:
  `.github/money-path-globs.json`, `.github/labeler.yml`,
  `scripts/ci/money-path.test.mjs`, and the ship-next Merge Gate.

  One runtime glob is added: `packages/sdk/src/merchant-answer.ts` (owner
  decision 2 on #4120, 2026-10-20 — the PR adds its own new module to the
  perimeter). The module decides, after the funding leg has moved USDC, whether
  the merchant accepted or the payment is a rejection after funding, and which
  settlement hash Haven is told — the same decision class the #3283 rule and
  #4122 already list for the SDK. It moved OUT of the already-listed
  `merchant-completion.ts` in the same PR, and the move would otherwise have
  taken the decision off the perimeter silently (the accident-of-location
  shape #1892 fixed, #3283 re-fixed, #4122 applied to the SDK).

  **The one behaviour change (owner decision 1 on #4120): the LOCAL hash rule
  now governs both paths.** A `PAYMENT-RESPONSE` header's transaction wins when
  the header carries one; a header WITHOUT a transaction (or an empty header)
  falls back to the `_meta["x402/payment-response"]` settlement's transaction.
  On the hosted path this flips exactly the D1 input the quality scan measured
  (`docs/bug-reports/quality-scan-2026-10-19-whole-repo.md`, candidate C3): a
  hosted `isError` answer carrying a `_meta` settlement is no longer
  `MERCHANT_REJECTED_AFTER_FUNDING` — it is accepted, the `_meta` transaction
  is the settlement hash, the #3764 second report is posted with it, and an
  erc7710 (`noFundingLeg`) completion anchors its evidence on it. Every local
  case, the D2 divergence (a 200 `text/plain` `isError` body: still rejected on
  hosted, still accepted on local — tool-result parsing stays per caller) and
  the header-wins precedence case are unchanged, pinned by the characterization
  tests in `packages/sdk/src/x402-merchant-answer.test.ts`.

  **What this does NOT change, stated because this file is the perimeter
  record:** nothing about who can sign, move or authorise anything. The
  decision classifies a merchant ANSWER to a call the funding leg already paid
  for; it does not construct, sign, or alter payment intent, and it grants no
  capability. The backend still verifies every reported settlement hash
  on-chain before recording it (`observeEip3009MerchantSettlement` /
  `observeErc7710Settlement`), so a wrong hash is a refused report, not a
  recorded settlement. The rejection reconciliation is still recorded before
  the local path throws `x402_retry_rejected_after_funding`; the funding
  report still goes before the settlement report; `parseMerchantSettlement` is
  byte-identical (the `_meta` fallback deliberately did NOT go into it — it is
  public and shared with `packages/mcp-server/src/tools/plain-http-x402.ts`).

  The new module was already in this document's `covers:` through
  `packages/sdk/src/**`, so the coupling gate asked a change to it for a shard
  from its first commit. `packages/sdk/src/client.ts` stays OFF the perimeter,
  pinned off by a named test (#3283, re-taken on #4120).
