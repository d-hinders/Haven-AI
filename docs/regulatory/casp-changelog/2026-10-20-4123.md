- **#4123** — **The hosted retryable settlement-evidence guidance tells the agent to add `payment_header` when it reports the merchant's settlement again. Agent-facing reason text only — no payment, signing, custody or authorization behaviour moved.**
  What changed. When an EIP-3009 merchant settlement report comes back
  retryable (Haven could not read the settlement transaction yet), three hosted
  reasons told the agent to report "the same hash" again without saying that
  the backend refuses an EIP-3009 settlement report lacking the payment header
  the merchant was retried with (#3925), before it judges the hash. They now
  say to report with `next_arguments`, adding `payment_header`, in the
  wording the missing-header arms already use: the
  `haven_settle_mcp_tool` / `haven_complete_mcp_tool` eip3009 settled arm and
  the `haven_report_x402_outcome` folded-evidence arm unconditionally (the
  first is eip3009-only; on the second a pending erc7710 report is refused
  before the evidence report, and a confirmed one, which does reach it, cannot
  come back retryable: the backend answers 503 only for
  `settlement_unobservable`, from the pending-erc7710 seam or the eip3009
  branch, while the confirmed-erc7710 attach path answers 202/409; even a
  stray 503 is harmless, because the report tool it names drops the header on
  any non-eip3009 payment), and the `haven_report_settlement_evidence`
  `SETTLEMENT_PENDING` reason scoped to EIP-3009 (an erc7710 report reaches it
  too). A known fourth copy, the `haven_report_settlement_evidence` description
  in `packages/sdk/src/tool-descriptions.ts` ("report the same hash again
  shortly"), is left as it is (the description budget is at its cap) for the
  post-promotion `payment_header` prefill follow-up. The files are `packages/mcp-server/src/tools/paid-mcp-completion.ts`
  and `packages/mcp-server/src/tools/plain-http-x402.ts`.

  Why the perimeter is unaffected. The change rewrites strings on an
  already-funded purchase whose merchant settlement is merely not yet
  verifiable. `next_tool`, `next_action` and `next_arguments` are
  byte-identical, so the corpus and the stale-client check do not move; no
  request is sent that was not sent before, no header is prefilled or stored by
  Haven (the agent still supplies its own value, which the backend
  signature-checks against the payment's delegate before attributing a
  settlement), and no tool description, input schema or signer contract
  changes. Haven still holds no key and gains no authority; nothing is signed,
  authorized or moved on any path this touches. Each new assertion is
  mutation-proven: reverting each reason to its old text turns its test red
  (`tools.test.ts`'s complete and settle retryable cases, its
  `SETTLEMENT_PENDING` case, and a new `report-x402-outcome.test.ts` case that
  passes `payment_header`), as do dropping the EIP-3009 scope, dropping the
  header's forwarding, prefilling it into `next_arguments`, and changing the
  pending arm's `next_tool`.

  Perimeter unchanged.
