# 2026-10-20 — #4167: Receive dialog to mockup note 9; one primary-button rule

- **#4167 — the Receive dialog's chrome narrows and the dashboard money card
  follows the account page's primary-button rule.** Money-FACING, not on the
  money-path perimeter (no covered file in
  `.github/money-path-globs.json`); analysed because the dialog is where a
  human is told where to send funds.
  - **What changed, presentationally:** `ReceiveDialog.tsx` loses the old
    Deposit-address chrome — the "On-chain receive" chip, the "Show QR code"
    toggle (the QR is now inline and generated when the dialog opens), the
    "View on explorer" button (the account page's Account details keeps an
    explorer link) and the "Before you send" box, whose two lines collapse
    into the mockup's ONE network-rule sentence ("Send USDC on `<network>`
    only. It arrives in about a minute and shows in Activity."). The account
    card becomes a picker ONLY when the caller hands the dialog several
    accounts; with one account no account card renders. `MoneyPanel.tsx`
    gains a `usdcFunded` tri-state prop wired from the dashboard's existing
    `firstRunSetupState` signal: Send primary once any account holds USDC,
    Receive primary with Send disabled when known empty, Send primary and
    enabled while the read is loading or failed — the account page's rule
    (`AccountDetailClient.tsx`), a variant change only.
  - **No authority, custody or execution boundary moves and nothing new is
    grantable.** The dialog still signs nothing, submits nothing, and reads
    no credential; it renders an address, a QR, one sentence and outbound
    links. `DelegationSendModal` is untouched — the Send button's disabled
    state is a CSS variant and a `disabled` attribute, not a new gate and
    not a removed one (an account KNOWN empty cannot send; an unknown state
    keeps Send enabled, so no funded user loses the send path).
  - **The #1844 and #3478 guards are untouched and re-asserted.** The
    unresolved-chain refusal (`resolveChainOrNull`) still renders instead of
    the address, QR, rule and both "other ways" cards, naming no network
    (word-anchored text-scan assertions over the dialog, retargeted to the
    inline QR image). The faucet/onramp gating still reads the SELECTED
    account's chain — now re-proven through the new in-dialog account
    picker: switching the selection to a testnet account brings the faucet
    and removes the onramp (`ReceiveDialog.test.tsx`), so the gate follows
    the selection, not the first account. Every predicate is a conjunction;
    each can only remove an offer.

  **Perimeter unchanged.**
