# 2026-10-21 — #4215: the local EIP-3009 settlement-evidence report is retried on a `retryable` answer

- **#4215 — `MerchantCompletion.retryRequest` (local `fetch` / `payX402Quote`
  / `resumeX402Payment`) now posts the merchant's EIP-3009 settlement report
  through `reportEvidence`'s bounded loop instead of the one-shot
  `reportSettlementEvidenceOnce`.** While Haven answers `retryable`
  (503 `settlement_unobservable` — its on-chain read came back
  `rpc_unavailable` or `not_found`), the same body is re-posted on the
  existing `EVIDENCE_RETRY_DELAYS_MS` schedule (four attempts over ~7 s); any
  refusal (409 `settlement_unverified`, the #4061
  `settlement_proof_header_missing` refusal, a validation error, a transport
  failure with no HTTP status) ends the loop on the first attempt. This
  revisits #3764's D2 for the local path only, on the owner's decision
  (option (a) on #4215): the qa-dev EIP-3009 SDK-direct legs red against
  #4144's 45 s settlement-record window because the backend's node sees the
  merchant transaction only seconds after the funding confirm, and the
  swallowed one-shot 503 never re-posted. Money-path by file
  (`packages/sdk/src/merchant-completion.ts`, a runtime glob).
  - **No authority, custody or spending surface changes.** The remedy
    repeats an evidence WRITE after an already-completed purchase — the same
    claim the SDK already handed Haven once, which the backend verifies
    on-chain (checks 1–7) before recording. The SDK hands Haven a claim, not
    an authority (#3764). No signature, budget, recipient, amount or
    authorization changes; the #3764 pre-post gates (well-formed, non-zero,
    different from the funding hash in any letter case) are untouched and run
    before any post; D3's order (funding first, settlement second) is
    unchanged; the #4061 proof header rides the report exactly as before.
  - **A refusal is still never retried** — pinned by five refusal tests
    (409 with a reason, 409 with `error_code:
    settlement_proof_header_missing`, a transport failure with no status, a
    408, a non-JSON 503), each asserting exactly one settlement post, and by
    a mutation check: widening the loop's retry predicate to
    `outcome !== 'confirmed'` turns all five red.
  - **The hosted path is byte-identical**: `completeX402MerchantCall` keeps
    its single `reportSettlementEvidenceOnce` attempt (D2), pinned unedited
    by `x402-erc7710-evidence.test.ts` ("the settlement report is ONE
    attempt"), and the D1 outcome mappings are unchanged. Locally the
    outcome stays swallowed (D1): nothing about who can sign, move or
    authorise changes, and the caller-visible result of a completed purchase
    is unchanged — bounded tests assert the merchant's own answer returns
    verbatim after every schedule shape.
  - **Mutation-tested:** restoring the one-shot call turns the retry tests
    red (one settlement post instead of two; the bounded test sees fewer
    than `1 + delays.length` posts); the schedule is asserted under fake
    timers (no second post before 1 000 virtual ms; exactly four posts when
    every attempt answers 503).

  Perimeter unchanged.
