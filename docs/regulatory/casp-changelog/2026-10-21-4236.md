- **#4236** — **a change to the QA control surface only: `.github/workflows/qa-dev.yml` (a `controlGlob`) gives its `money-flow` job a job-level `permissions:` block that adds `actions: read`, and passes the dispatch's `haven_api_url` input to the failure step through env, so `scripts/ci/qa-failure-issue.mjs` can name the last-green → first-red window in the standing `qa-failure` issue. No payment, signing, custody or authorization code moved; the perimeter is unchanged.**
  What changed in the control surface. On every failure the standing issue's
  body and comment now carry one `window:` line naming the last money-flow
  JOB success before the episode, the first red run, and the first-parent PRs
  between them. Each PR is marked for whether it touches a money-path file
  (`moneyPathFiles` over `.github/money-path-globs.json`'s `globs`) or the
  harness (`packages/qa-agent/`). The opening comment of an episode
  @-mentions a single PR's author only when that PR touches one of the two
  and the run class is `haven`, `harness` or `unclassified` (captain decision
  on #4236, 2026-10-21). The green run is admitted by `qa-freshness.mjs`'s own
  `selectGreenRun`, imported and not edited: an evidence event, a
  branch-labelled event on `dev`, a commit in the failing commit's history
  (through the compare API, since the checkout is depth 1), and a
  `money-flow` job conclusion of `success`. `preFilterHarnessCandidates`
  runs before any jobs read, and `dev-push-health.mjs`'s `evaluate` derives
  the endpoints, so a `skipped` or `cancelled` job never moves the state.
  The grant: a job-level block REPLACES the top-level one for that job, so it
  restates `contents: read`, `issues: write` and `deployments: read`
  unchanged and adds only `actions: read`, which lists qa-dev's own runs and
  reads their jobs (the grant `dev-push-health.yml` declares for the same
  reads). The `gate` job keeps the top-level block and gains nothing. No
  `pull-requests` grant is added, because the author comes from the compare
  API's commit data. Every read is time-bounded (30 s a call; one lookup is
  capped at 80 calls and 120 s), because the step runs inside the
  `money-flow` job, which holds the `qa-dev-money-flow` concurrency group
  and has no `timeout-minutes`. A failed or timed-out read is one
  "window: unavailable" line, and the body edit, comment and reopen still
  happen. What did NOT change, stated because this file is a control surface
  the promotion gate reads: the triggers, the `gate` job and its refusals
  (#2273), the #1047 override validation, the money-flow step and its flake
  budget, Coverage completeness (#1044/#1066), the green close step (#4069),
  every `QA_*` secret and variable, and the `money-flow` job's conclusion.
  The failure step already runs only after the job has failed (`if:
  failure()`), and `qa-freshness.mjs` and `guard-freshness.mjs` read the run
  and that job, never the issue, so nothing the window says can admit or
  refuse a promotion. The harness (`packages/qa-agent/**`) is untouched.
  Mutation-tested in `scripts/ci/qa-failure-issue.test.mjs`, which drives the
  CLI with the recording `gh` stub and the 2026-10-20 episode as its fixture
  (green run 39419894807 at `84f347f0a`, red run 39421603625 at `aa818795d`,
  one PR, #4144, read from the live API). Each of these reddens a test:
  reading green from `run.conclusion`, treating a `skipped` job as green,
  admitting a feature-branch dispatch, counting a `diverged` commit as an
  ancestor, dropping the per-call timeout, dropping the run-class or
  touched-file gate on the mention, mentioning on a later failure, and
  removing `actions: read` or moving it to the top level. Each was restored
  byte-identical (`cmp`) after. Perimeter unchanged.
