- **#4242 — the signer builds an EIP-3009 merchant header only from a
  funding-leg binding.** This narrows what the local signer
  (`packages/signer/src/core.ts`, `packages/signer/src/tools.ts`) will sign
  with the delegate key. No backend, relay, custody or hosted-tool code moved,
  and nothing Haven signs changed. The perimeter narrows.
  The invariant. The signer's x402 arm signs two shapes: a funding-leg
  PackedUserOperation, which moves the quoted amount from the agent's account
  to its own delegate EOA, and an erc7710 settlement child, through which the
  agent's account pays the merchant directly. Only the first has a funding
  leg. An EIP-3009 merchant header is a transfer from the delegate EOA, so it
  is backed only when a funding leg put that amount there.
  The prior exposure, recorded as it stood. After either shape was signed the
  signer kept the same in-memory binding: a copy of the Haven-signed expected
  context, which carries no settlement scheme. `buildX402PaymentHeader`
  compared resource, payee, amount, asset and network against that copy and
  nothing else, so it could not tell a settlement-child binding from a
  funding-leg one. A settlement-child payment could therefore be followed by a
  delegate-EOA header for the same payment, paid from whatever balance the
  delegate EOA held, with no funding intent behind it and outside the eip3009
  settlement attribution. Hosted guidance routed erc7710 away from the header
  tools; the signer itself enforced nothing. What is NOT verified: whether any
  live merchant advertises both options in one 402, whether delegate EOAs held
  such a balance at erc7710-payment time, and whether this ever happened.
  These stay open as read-only owner checks on #4242.
  What changed. The signing branch now records which shape it verified
  (`funding_leg` or `settlement_child`) beside the binding. This is a local
  fact about what the signer just signed, kept out of `X402ExpectedPayment`,
  which is the Haven-signed message and is unchanged on the wire.
  `buildX402PaymentHeader` refuses any binding that is not a funding leg,
  before selecting an option or touching the key, and retires the binding
  with its own reason so a retry gets the same answer. `haven_sign_x402`,
  which signs and then builds the header in one call, refuses a settlement
  child before signing anything, so no child signature is produced only to
  be dropped. The supported erc7710 path is untouched: `haven_sign` still
  signs the child, and `haven_submit` with `settlement_scheme: 'erc7710'`
  returns the merchant header. Funding-leg bindings build their header
  exactly as before.
  Tested in `packages/signer/src/x402-binding-rail.test.ts`, every context a
  valid v3 Haven binding so a refusal can only come from the rail check: a
  funding-leg binding still builds its header (characterization); a
  settlement-child binding is refused at header time and again on retry;
  through the tools layer, `haven_sign` then `haven_x402_sign_header` returns
  no header, and `haven_sign_x402` refuses with zero signing calls and no
  audit entry. Each of these mutations reddens a test: removing the header
  guard; recording a settlement child as a funding leg; inverting the rail
  comparison; retiring the refused binding under the header-built reason;
  removing the early refusal in `haven_sign_x402`. Each was restored
  byte-identical (sha256) by the mutation runner. Perimeter narrowed.
