- **#4243 — erc7710 x402 authorize records the paid address as the merchant.**
  A validation change in `packages/backend/src/modules/x402/scheme-selection.ts`
  (`validateDelegationSchemeShape`) and a persistence change in
  `packages/backend/src/modules/x402/delegation-authorize.ts`. No funds,
  signing, custody or relay behaviour moved. The perimeter narrows: one more
  request shape is refused before anything is built.
  The prior gap, recorded as it stood. On the erc7710 direct-settlement shape
  (`payTo` = the merchant) `POST /x402/authorize` accepted an optional
  `merchantPayTo` from the agent-authenticated body and never compared it with
  `payTo`. The settlement child's `allowedCalldata` caveat pins the transfer
  to `payTo`, but the intent persisted `merchantAddress: merchantPayTo ?? payTo`.
  Everything that reads the merchant downstream (evidence rows, receipts, the
  dashboard and the accounting feed's `counterparty.address`) could therefore
  name an address that was never paid, and settlement confirmation
  (`observeErc7710Settlement`, bound to `to_address`) succeeded regardless.
  Funds were not at risk: the recipient was pinned on-chain and spend stayed
  bounded by the budget delegation's enforcer. The integrity of the owner's
  ledger and bookkeeping feed was. Haven's SDK, hosted MCP server and QA
  scenarios never send `merchantPayTo` on this shape, so only a caller writing
  the request body directly could reach it. What is NOT verified: whether any
  stored erc7710 intent has `merchant_address <> to_address` (owner follow-up,
  read-only query on dev and prod).
  What changed. `validateDelegationSchemeShape` now takes the payee pair and,
  when the shape is not the EIP-3009 funding leg, refuses with 400 a
  `merchantPayTo` that differs from `payTo` (case-insensitive). The check runs
  with the other shape checks, before delegation selection, the budget
  pre-check, any settlement child, any intent row and any delegate-account
  deploy, so nothing is written on the refusal. An absent `merchantPayTo`, or
  one equal to `payTo`, is unchanged. The erc7710 intent now persists `payTo`
  as `merchantAddress` directly. That line is defence in depth behind the
  guard: the guard lets only an absent or equal value reach it. The EIP-3009
  two-leg path, where `payTo` is the delegate EOA and `merchantPayTo`
  legitimately names the merchant, is untouched.
  Side effect, intended. A pre-#1360 SDK that sends a stale delegate address
  as `payTo` with `merchantPayTo` = the merchant and no explicit scheme used to
  reach the erc7710 selector (and, on an open budget, could build a real
  settlement child to the stale address). It now gets the 400. The #1360
  characterization test anticipated this guard and is updated, not deleted.
  Characterization first: commit `f2c746b1f` pins the absent and equal cases
  and the pre-fix world (a differing `merchantPayTo` returned 201 and became
  the recorded merchant) before the fix commit flips that case to 400.
  Mutation-proven with cp-restored, sha256-checked mutants over
  `scheme-selection.test.ts`, `x402-delegation.test.ts` and `x402.test.ts`
  (163 tests): guard removed → 3 red; case-sensitive comparison → 1 red;
  guard moved to the funding leg → 38 red. Reverting the persistence line
  survives, as a shadowed mutant behind the guard, recorded rather than
  hidden. OpenAPI `X402AuthorizeRequest.merchantPayTo` and
  `docs/architecture/04-x402-payment-sequence.md` describe the contract.
