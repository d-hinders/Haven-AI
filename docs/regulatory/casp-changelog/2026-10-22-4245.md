- **#4245** — catalog provenance: rows the x402 Bazaar discovery cron writes
  into `merchant_catalog` are labelled as such. Before this change the table
  had no column that told an operator-curated row from a discovered one, and
  `serialize()` in `packages/backend/src/routes/catalog.ts` hard-coded
  `source: 'operator'`. A third party's self-chosen name and description could
  therefore reach agents as operator-curated, and pass the SDK's
  `discoverTools({ verified: 'operator' })` provenance filter. Reachable only
  where a deployment sets `CATALOG_DISCOVERY_ENABLED=true` (default false);
  whether any environment did, and how many rows came from it, is not
  verified here (owner follow-up).
  What changed. Migration 117 adds `merchant_catalog.source TEXT NOT NULL
  DEFAULT 'operator'` with a closed CHECK (`'operator'`, `'bazaar'`). The
  discovery INSERT (`modules/catalog/catalog-discovery.ts`) writes `'bazaar'`;
  every other writer keeps the default. `serialize()` reads the column and
  fails closed: only a row that says `'operator'` is labelled operator, and a
  row read without the column gets `'bazaar'`, the least-trusted label. A
  Bazaar row is `domain_verified: false`, and `GET /catalog` sorts it after
  ingestion rows. `verified_payable` keeps its #2978
  meaning (the refresh probe runs on every row). The OpenAPI enum, generated
  core types and SDK types gain `'bazaar'`. `verified: 'operator'` already
  keeps `source === 'operator'` only, so every published SDK excludes Bazaar
  rows without an upgrade. The `haven_discover_tools` description's
  `verified=verified` clause now reads "(any source; bazaar seller-asserted)"
  instead of naming two of three.
  No backfill: a discovery row is not identifiable from existing data
  deterministically, so existing rows stay `'operator'` pending an owner
  decision recorded on the PR.
  Read-only discovery surface: no payment, signature, settlement, custody or
  authority change. The money-path classifier matches this change on the
  migrations glob and the MCP tools snapshot only.
  Tested against real Postgres
  (`src/db/migrations/__tests__/117_merchant_catalog_source.test.ts`): the
  default, the closed CHECK, `down()`, pre-existing rows, and the discovery
  cron end to end through `serialize()`. Route and unit tests pin the label,
  the public shape, the detail route and the sort. Mutation-tested with
  `scripts/ci/prove-red.mjs` (author cells, plus reviewer cells reproduced by
  `prove-red verify`): restoring the hard-coded label, failing the label
  open, writing `'operator'` from discovery or omitting the column from its
  INSERT (unit and real DB), ranking Bazaar rows with operator rows, widening
  the CHECK, making `down()` a no-op, guessing a backfill, and an SDK
  `verified: 'operator'` filter that excludes one third-party source (`'ingestion'`
  or `'bazaar'`) instead of keeping `'operator'` each redden a test. Changing the column default is refused at harness start by the
  schema-drift guard (#2622) before any test runs. Perimeter unchanged.
