# 2026-10-23 — #4319: the eip3009 settlement record's proof strength becomes a ladder — a stored signed header first, the merchant receipt's hash under a default-off flag and seven fail-closed limits

**Perimeter: unchanged; the evidence check widens only along an owner-approved path.** Nothing here moves funds, signs anything for Haven, or widens any authority. The change does three things:

- it records the EIP-3009 merchant settlement for payments the derived-nonce sweep (#3888) cannot attribute, starting with the strongest proof Haven already holds (the stored X-PAYMENT header);
- it adds an owner-approved relaxation — the merchant receipt's transaction hash — behind `HAVEN_EIP3009_RECEIPT_ATTRIBUTION` (default off) and seven limits, every one of which fails closed;
- it tells the frontend what Haven knows (`settlementTracking` / `settlementProof`), computed from stored state only.

The record involved is `payment_intents.machine_metadata.merchant_settlement_tx_hash`. It feeds receipts, the bookkeeping feed and transaction history, and moves no money by itself. The #3475 double-pay hazard is the reason the limits exist: a wrongly matched sibling hash could offer a re-sign from the shared delegate.

## What changed

- **Tier 1 — the stored signed header (#3925 standard, ungated).** When a payment's `machine_payment_evidence` row stores the X-PAYMENT header, its delegate-signed authorization nonce is used exactly as the sweep uses the derived one: the settlement is FOUND by `AuthorizationUsed(delegate, headerNonce)` and recorded through `observeEip3009MerchantSettlement` — `nonce_bound`, and `nonce_derived` only when the header nonce equals the derived one. Runs on the generic evidence-attach path (`modules/mpp/evidence.ts`, the funding-hash report shape), in the sweep tick (for unrecorded payments with a stored header, inside the 24-hour horizon), and in the backfill. `observeEip3009MerchantSettlement`'s `!nonceProof` refusal is UNCHANGED — the agent-reported path is not weakened.
- **Tier 2 — the receipt hash (owner-approved, flag-gated).** A separate entry point, `observeEip3009ReceiptSettlement` (`modules/x402/eip3009-receipt-settlement.ts`), takes the stored `protocol_receipt_payload.transaction` and applies the seven limits:
  1. **Fallback only** — the existing compare-and-set writer is unchanged; a record landing between selection and write answers `conflict`, nothing written.
  2. **Exactly one burn** — the candidate's receipt must carry exactly one `AuthorizationUsed(delegate, *)` from the payment's token; several is a batch, refused as ambiguous. That single nonce is fed to `verifySettlementTransferTx`, so checks 1–7 AND check 9 (the #4061 pairing) apply: exact amount and token, delegate → merchant, `confirmed_at − 120 s`.
  3. **Sibling nonce** — a burned nonce that is any sibling's DERIVED nonce is refused ("settles another payment"); one equal to this payment's own derived nonce is Tier 1-strength and is recorded as a nonce record.
  4. **Symmetric ambiguity guard, by block** — every same-shape sibling (same agent, delegate, merchant and amount) funded at or before the candidate's block must be PROVABLY settled before this payment's funding (its own recorded settlement's block, read over RPC). Siblings both earlier and later are covered; the A-B-swap counter-example is refused. Funding blocks are read over RPC under a per-candidate cap (`MAX_FUNDING_BLOCK_READS_PER_CANDIDATE = 12`); an unreadable block refuses retryable.
  5. **Before the next funding** — the candidate's block is before the same delegate's next funding block after this payment's.
  6. **Derived nonce burned elsewhere** — refused while `authorizationState(delegate, deriveX402PaymentNonce(id))` is true: the sweep's stronger attribution outranks the weaker proof (#3888, owner question 2).
  7. **Persisted verdict** — `machine_metadata.merchant_settlement_receipt_verdict` (`recorded` / `refused_ambiguous` / `refused_mismatch` / `retryable`; JSONB, no migration). Refused is final; retryable is re-checked with backoff (each evidence attach, each backfill run).

  The record is labelled `merchant_settlement_proof: 'receipt'` and NEVER stamps `merchant_settlement_nonce_bound`. Every RPC failure is retryable and records nothing. `protocol_receipt_header` is deliberately NOT decoded as a fallback in this slice; the dry run counts those rows instead.
  Tier 2 runs ONLY when no header is stored (owner decision, rework): Tier 1 is preferred wherever a signed header exists — input or stored — so a header-holding payment gets Tier 1 or nothing, on the arrival path AND in the backfill. The CAS writer allows ONE hash per payment, so a weaker receipt record would pin the settlement hash and permanently pre-empt a later Tier 1 sweep/backfill (`hash_taken`) — the same hazard limit 6 exists to prevent.
- **Where it runs.** The generic attach path is restructured: base row (feed SUPPRESSED) → attach header + receipt → Tier 1 → Tier 2 (only when no header is stored) → ONE feed fire — #3767's "hash before feed" rule now holds on that path for every rail (the other rails' only change is the feed firing after the attach instead of before). Tier 2 never runs in the sweep tick. The backfill script (`packages/backend/scripts/eip3009-settlement-backfill.ts`, `npm run x402:eip3009-backfill -w @haven/backend`) is `--dry-run` first (counts per tier and verdict, nothing written), then `--write`: idempotent, honours the kill switch, never re-checks a final refused verdict (limit 7), and fires `feedSettledPaymentBestEffort` after each record (S9).
- **Tracking state for the frontend (#4320).** `settlementTracking` (`verified` / `checking` / `untracked`) and `settlementProof` (`nonce` / `signed_header` / `receipt` / `legacy`) — camelCase on the transactions feed through `ApiSchema<'Transaction'>`, snake_case on the agent activity read — computed from stored state only (`domain/settlement-tracking.ts`). OpenAPI and the generated `core/api-types.ts` updated.

## What did NOT change

- `observeEip3009MerchantSettlement`'s refusal of a nonce-less report, its verifier checks, its CAS writer, its hash→intent advisory locking: untouched.
- No migration: the new fields are JSONB on `machine_metadata` (flags merged, per the existing writer's pattern).
- The agent-reported eip3009 branch, the erc7710 seam, the sweep's derived-nonce attribution and its owner-question-2 precedence: unchanged.
- `GET /receipts`: out of scope, as the issue states.

## Residual risk

- Tier 2's proof is weaker than a nonce proof by construction; the owner accepted it for clients whose nonce Haven cannot prove, with the limits above as the mitigation. It is off until the operator turns it on, per the rollout order (merge → dev dry run → dev write → dev flag → prod).
- A same-shape sibling storm over the block-read cap refuses retryable (bounded cost over an unbounded walk); the backoff retries it.
- A random-nonce payment with no header cannot be distinguished from a deriving one by stored state alone; its honest tracking state is `checking` inside the 24-hour window and `untracked` after, because the derived-nonce scan is the only remaining source.
