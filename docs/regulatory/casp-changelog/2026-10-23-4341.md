- **#4341** — follow-up to #4300 (PR #4317): a probe result the database
  cannot store no longer leaves its row unchanged forever, and a parse
  failure in the probe is logged instead of silent. Refusal and payTo
  contracts unchanged.
  What changed:
  - **Verified-write failure degrades the row.** In
    `refreshCatalog` (`packages/backend/src/modules/catalog/merchant-catalog.ts`),
    when `persistVerified` throws (the reviewer's repro: a well-formed 402
    whose string field carries a NUL byte — Postgres rejects `0x00` in text
    with `invalid byte sequence for encoding "UTF8": 0x00`), the failure is
    logged and the row is recorded as a MISS, so `consecutive_failures`
    moves and the row degrades after the usual three (`DEGRADE_AFTER_FAILURES`).
    Before, the row kept its `status`, `consecutive_failures` and `pay_to`
    forever, against the #3331 doctrine that an unverifiable merchant
    degrades. A miss never writes `pay_to`, so the row keeps its stored
    `pay_to` through the misses; the next VERIFIED run still rewrites it as
    seen. A row whose MISS write itself fails is logged, not counted, and
    keeps its streak — that behaviour is unchanged.
  - **Parse failures are surfaced.** `probeCatalogEntry`'s `catch` around
    `readProbeChallenge` now logs the row's `resource_url` and
    `err.message` — nothing from the merchant payload — instead of
    returning `{ ok: false }` silently. A parser bug can no longer masquerade
    as "every merchant missed" and degrade the whole catalog with logs
    showing only counts.
  - **Discovery survives a failing candidate.** In
    `ingestDiscoveredCatalog` (`modules/catalog/catalog-discovery.ts`), the
    merchant upsert and insert of one candidate are wrapped: a failing
    write (e.g. a Bazaar index entry whose name carries a NUL byte) is
    logged, counted in a new `failedWrite` result field, and the run moves
    on to later candidates instead of throwing out of
    `ingestDiscoveredCatalog` at the same candidate every run.
  - **Unchanged.** Which rows are probed, the probe budgets, the run
    budgets, what a successful probe writes (`pay_to` as seen, never
    COALESCEd) and every refusal are as #4300 and #4281 left them. The
    probe is still read-only: it never pays, signs, or follows the
    challenge.
  Tests:
  - `modules/catalog/__tests__/merchant-catalog.test.ts`: a row whose
    verified write fails is recorded as a miss and its degrade is counted;
    `degraded` is NOT counted when the miss write itself fails (#4317
    reviewer cell); a thrown parse error is logged with the URL and the
    message and nothing from the payload; a parsing challenge logs nothing.
  - `modules/catalog/__tests__/catalog-discovery.test.ts`: a candidate
    whose write fails does not stop discovery from reaching later
    candidates, and is counted `failedWrite`.
  - `modules/catalog/__tests__/catalog-refresh-rotation.db.test.ts`,
    against real Postgres: a row whose verified write fails (NUL-bearing
    `asset`) is counted as a miss on each of three runs and reaches
    `degraded`, while its clean neighbour verifies normally.
  - `infra/http/__tests__/ssrf-guard.test.ts`: the binary shape survives an
    address-fallback attempt (#4317 reviewer cell) — the fallback attempt
    still asks for raw bytes, so a PDF is never utf8-decoded.
  Perimeter unchanged: catalog metadata and observability only; no
  authority, no key material, no payment path, no refusal changed.
