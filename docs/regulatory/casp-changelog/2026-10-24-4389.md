- **#4389** — the catalog judges a merchant's 402 the way the pay path does:
  the refresh probe and the discovery pre-filter use the pay path's own scheme
  selection over every `accepts[]` option instead of `accepts[0]`, and an
  asset the chain registry does not know is no longer labelled USDC.
  Refusal and payTo contracts unchanged.
  What changed:
  - **One payability verdict.** `selectCatalogPaymentOption` in
    `packages/backend/src/modules/catalog/merchant-catalog.ts` runs
    `selectX402SettlementScheme` from `@haven_ai/sdk` with
    `delegationRail: true` over every well-typed `accepts[]` option. That is
    the selector `haven_quote_catalog_purchase` uses, and every live account
    is on the delegation rail. A challenge with no option it accepts (a
    scheme other than `exact`, a network other than Base or Base Sepolia, an
    asset other than their USDC, or a non-positive amount) is a probe miss.
    Before, `accepts[0]` was recorded whatever its scheme, network or asset.
  - **Recorded network.** The row's `network` is the selected option's
    network, written as CAIP-2 (`base-sepolia` is recorded as
    `eip155:84532`), and `pay_to` and `asset_transfer_methods` are scoped to
    that network rather than to `accepts[0]`'s. A merchant that offers
    EIP-3009 first and a payable erc7710 option on the other Base network is
    now recorded on the erc7710 option's network, the one a delegation-rail
    agent is quoted on.
  - **Recorded methods.** `asset_transfer_methods` counts an option only when
    the SDK's erc7710 or EIP-3009 selector accepts it on the recorded network,
    so a `permit2` option is no longer counted as EIP-3009.
  - **Asset label.** The symbol and decimals come from the `@haven_ai/core`
    chain registry. An asset the registry does not know is not payable; the
    old fallback named any unknown asset USDC.
  - **Discovery.** `ingestDiscoveredCatalog`
    (`modules/catalog/catalog-discovery.ts`) applies the same verdict to the
    index entry's options before spending a probe, so a payable Base option
    listed after an unsupported one is probed, and an index entry with no
    payable option is skipped (`skippedUnsupported`) without a probe.
  - **Unchanged.** Which rows are probed, the rotation, the probe and run
    budgets, the SSRF guard, `http_method`, and the MPP branch are as before.
    `pay_to` is still written as seen from the challenge, never COALESCEd,
    and still refused when the options on the recorded network disagree.
    The probe is still read-only: it never pays, signs, or follows the
    challenge.
  Tests:
  - `modules/catalog/__tests__/catalog-payability.test.ts`: the
    characterized `accepts[0]` cases now flip (a payable option after an
    unsupported one is recorded; `upto`, EURe on Gnosis and an unknown Base
    asset are misses); erc7710 is preferred; `permit2` and a payable scheme on
    the other Base network are not counted as methods; a mistyped option is a
    clean miss with nothing logged; twelve cases hold the catalog's selection
    equal to `selectX402SettlementScheme` with the delegation rail; discovery
    ingests the second-listed Base option and skips an unpayable entry
    without probing it.
  - `modules/catalog/__tests__/catalog-payability-registry.test.ts`: with the
    registry mocked, an asset it does not know is a miss, and the label and
    decimals are read from it.
  - `routes/__tests__/agent-delegations-build-network-scoped-methods.test.ts`
    (#3386, real Postgres): a payable erc7710 option is now always the
    selected one, so the fixture's 8453 erc7710 option names an asset the
    pay path cannot settle. The row stays on 84532 with `eip3009`, and the
    build route still refuses the 84532 agent's merchant-locked budget for
    lacking ERC-7710.
  - Eight mutation cells (prove-red, author run): reading `accepts[0]` in the
    probe or in discovery, a USDC fallback, a hardcoded USDC label, dropping
    either per-network filter, `delegationRail: false`, and a hand-rolled
    filter instead of the SDK selector. Each turns its named tests red.
  Perimeter unchanged: catalog metadata only. The probe signs and pays
  nothing. A row that no longer verifies degrades and leaves its merchant's
  active offers exactly as any other degraded row does (#3331), and the
  merchant-locked budget's pin is still derived from those offers' `pay_to`
  under the same agreement rule. No key material, payment path or refusal
  changed.
