- **#4389** — the catalog judges a merchant's 402 the way the pay path does:
  the refresh probe and the discovery pre-filter keep the options the pay
  path keeps and use its own scheme selection over all of them instead of
  `accepts[0]`, and an asset the chain registry does not know on the
  option's own chain is no longer labelled USDC. The refusal contract is
  unchanged; the payTo contract changes in one respect, stated under
  Unchanged.
  What changed:
  - **One payability verdict.** `selectCatalogPaymentOption` in
    `packages/backend/src/modules/catalog/merchant-catalog.ts` first runs the
    `accepts[]` through `normalizePaymentRequired` from `@haven_ai/sdk`, the
    per-option rule every pay path applies before it selects, then runs
    `selectX402SettlementScheme` with `delegationRail: true` over the options
    it keeps. That is the selector `haven_quote_catalog_purchase` uses, and
    every live account is on the delegation rail. The full list of reasons
    an option is not payable:
    - the SDK normalization drops it: its `scheme`, `network`, `asset` or
      `payTo` is not a string; its amount (`amount`, else
      `maxAmountRequired`) is not a positive decimal string; or its
      `maxAmountRequired` is present but not a positive decimal string
      (`null` included);
    - neither SDK selector accepts it: a scheme other than `exact`; a network
      other than Base or Base Sepolia (CAIP-2 or the x402 short name); an
      asset other than either Base network's USDC address; an
      `extra.assetTransferMethod` other than `erc7710` or `eip3009` (for
      example `permit2`); or, for an EIP-3009 option, an `extra.paymentFlow`
      other than `authorization`;
    - the catalog's own checks after selection: the selected asset is not in
      the `@haven_ai/core` registry on the selected option's own chain (for
      example Base USDC named on a Base Sepolia option, which the SDK
      selector accepts), or the selected network is not one the catalog maps
      to a chain.
    A challenge with no payable option is a probe miss. The selector picks one
    option and the catalog does not fall back to another when its own checks
    refuse that one. Before, `accepts[0]` was recorded whatever its scheme,
    network or asset, and an option with no `payTo` still verified the row.
  - **Stricter than the SDK selector on the asset's chain, deliberately.**
    The SDK selector accepts either Base network's USDC address on either
    Base network. The backend's authorize step resolves the asset on the
    agent's own chain only (`resolvePaymentToken(agent.chain_id, asset)`
    in `modules/x402/authorize.ts`), so no agent on that option's chain can
    pay it, and the catalog records a miss instead of a USDC row.
  - **Recorded network.** The row's `network` is the selected option's
    network, written as CAIP-2 (`base-sepolia` is recorded as
    `eip155:84532`), and `pay_to` and `asset_transfer_methods` are scoped to
    that network rather than to `accepts[0]`'s. A merchant that offers
    EIP-3009 first and a payable erc7710 option on the other Base network is
    now recorded on the erc7710 option's network, the one a delegation-rail
    agent is quoted on. A row stored before as `base` or `base-sepolia` was
    left out wherever rows are filtered by CAIP-2 network: an agent's catalog
    view, a chain-scoped marketplace listing, and merchant funding targets.
    Its first successful refresh after this change rewrites it as CAIP-2, and
    from then on it shows up in all three.
  - **Recorded methods.** `asset_transfer_methods` counts an option only when
    the SDK's erc7710 or EIP-3009 selector accepts it on the recorded network.
    Before, every option on that network was recorded by its
    `extra.assetTransferMethod`, defaulting to `eip3009`: a `permit2` option
    was recorded as `permit2`, and an option with no method but an
    unsupported `extra.paymentFlow` was counted as `eip3009`. Options the pay
    path cannot settle (an unsupported transfer method or payment flow) are
    now not recorded at all.
  - **Asset label.** The symbol and decimals come from the `@haven_ai/core`
    chain registry, on the selected option's own chain. An asset the
    registry does not know there is not payable; the old fallback named any
    unknown asset USDC.
  - **Discovery.** `ingestDiscoveredCatalog`
    (`modules/catalog/catalog-discovery.ts`) applies the same verdict to the
    index entry's options before spending a probe, so a payable Base option
    listed after an unsupported one is probed, and an index entry with no
    payable option is skipped (`skippedUnsupported`) without a probe.
  - **Unchanged.** Which rows are probed, the rotation, the probe and run
    budgets, the SSRF guard, `http_method`, and the MPP branch are as before.
    The catalog does not apply the SDK's envelope checks (`x402Version`, a
    resource URL); only its per-option rule. `pay_to` is still written as
    seen from the challenge, never COALESCEd, and still refused when an
    option on the recorded network names none or the options there
    disagree. One consequence is new: a challenge this change turns into a
    miss (its only option names no `payTo`, or every option is now
    unpayable) no longer rewrites `pay_to`. Like every miss, `persistMiss`
    leaves the stored `pay_to` and status alone, so an `active` row keeps
    its last verified `pay_to` until it degrades after
    `DEGRADE_AFTER_FAILURES` (3) failed refreshes. Before, a challenge whose
    only option named no `payTo` verified the row and cleared `pay_to` on
    the first refresh. A pin can still pay only the address it was signed
    for. The probe is still read-only: it never pays, signs, or follows
    the challenge.
  Tests:

  Perimeter unchanged: catalog metadata only. The probe signs and pays

  under the same agreement rule. No key material, payment path or refusal
  changed.
