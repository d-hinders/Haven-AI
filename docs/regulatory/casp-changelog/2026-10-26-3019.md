- **#3019 (delta)** — the Accounted endpoint-verification handshake. The
  document push landed in Accounted but `journal_entry.committed` was never
  delivered: the provider dispatches nothing to an endpoint whose
  `verification_status` is `pending` or `paused`, and our receiver answered the
  provider's verification delivery with a generic `{status:'ok'}` instead of
  echoing `data.object.challenge`, so the handshake failed `challenge_missing`.
  This PR adds the two halves of the handshake and nothing else.
  What changed:
  - **The receiver echoes the challenge.** `routes/accounting-webhooks.ts`
    answers a signed `webhook.verification` delivery with
    `{"challenge": "<data.object.challenge>"}` at the top level of the 200
    body, BEFORE the dedupe short-circuit so a retry of the same delivery id
    still echoes. The delivery is still recorded in
    `accounting_webhook_deliveries` for audit and counted as `verification`
    (`ops-signals.ts`). A verification delivery with no challenge answers 200
    without one — the provider's own `challenge_missing` verdict is the correct
    outcome, and a 400 would be retried for ~87 h over a delivery we will never
    accept. The answer matrix is otherwise untouched: 400 bad/malformed/stale
    signature, 404 unknown token, 200 for everything else, never 410, never a
    3xx on either path spelling.
  - **A new client call.** `accountedVerifyWebhook`
    (`modules/accounting/accounted-client.ts`) POSTs
    `/api/v1/companies/{companyId}/webhooks/{webhookId}/verify` with the
    bearer and a fresh `Idempotency-Key`, returns `data.verification_status`,
    and on non-2xx throws a `ProviderError` carrying the provider's
    `error.code` and `details.reason` — never the key.
  - **The connect flow runs it, best effort.** `api-key-flow.ts` calls verify
    once per subscription, in creation order, AFTER `updateSecrets` persists
    the three triples — and only when that write actually landed (verifying a
    subscription whose signing secret Haven failed to store would make the
    provider dispatch events we could never verify). A failure does NOT fail
    the connect and does NOT change the connection status; it emits one
    `accounting.webhook.verification_failed` `warn` line carrying the
    provider's error code only. The provider's own 8-attempt retry
    (1 m, 5 m, 30 m, 2 h, 12 h, then daily) is the safety net.
  - **Docs.** `docs/operations/accounting-feed.md` gains the handshake section
    (the event, the echo, the four `verification_status` states, the 8
    retries, the live-key requirement, the manual verify command), the route
    row and the counters row.
  Authority and custody argument:
  - **No new authority, no new credential.** The verify call carries the
    user's OWN Accounted API key — already stored encrypted in
    `accounting_connections.secrets_ciphertext` and already used for the
    document push — to the provider's own API. It grants Haven nothing it did
    not hold, and it creates no grant, token or scope.
  - **The challenge is not a secret and cannot be spent.** It is a value the
    provider generated and sent over the same HMAC-signed channel; echoing it
    back proves the endpoint is ours. It is not stored, not logged, and not
    usable against any Haven or provider surface. The signing secrets stay in
    the encrypted blob and are never echoed, logged or returned.
  - **No money moves and no state is asserted.** The change touches the
    inbound read-back and the connect-time handshake only: no payment path, no
    settlement, no budget, no delegation, no signing, no custody. The feed
    stays non-asserting — the handshake makes the provider's own notifications
    arrive, it does not book anything.
  - **No new route, no wire field, no migration.** The callback route and its
    two path spellings are unchanged; the only new outbound call is to the
    provider's documented verify verb. `accounting_webhook_deliveries` is
    reused as-is (migration 092), and the new counter is in-process.
  - **A failed handshake degrades to "no notifications", never to a wrong
    number.** The connection stays `connected`, the feed keeps feeding, and
    the subscription's own `verification_status` is the source of truth — the
    failure is visible as a `warn` line and in the provider's dashboard, not
    as a silent authority change.
  Mutation-tested:
  - `routes/__tests__/accounting-webhooks.test.ts` — the echo is asserted
    signed with EACH of the three stored secrets (the event type is not one of
    the triples, so the candidate loop must fall through to every secret); a
    duplicate retry of the same delivery id still echoes; no challenge answers
    200 without one; a non-string challenge is not echoed; the audit row is
    written with `payload: null`; the feature-off check still wins; and the
    no-410/no-3xx enumeration now includes the verification scenario on both
    path spellings.
  - `__tests__/accounted-client.test.ts` — the exact path, the bearer, a fresh
    `Idempotency-Key` per call, the parsed `verification_status`, and a 422
    `WEBHOOK_VERIFICATION_FAILED` surfacing `details.reason` without the key.
  - `__tests__/api-key-flow-webhooks.test.ts` — verify runs once per
    subscription in creation order AFTER `updateSecrets`; a verify failure
    leaves the connection status untouched and the connect succeeds, with one
    warn line carrying the provider's code; a registration failure runs no
    verify at all.
  Perimeter unchanged: no authority, custody, signing, settlement, funding,
  budget or refusal surface moved; the change makes the provider's own
  notifications arrive and adds no way to spend.
