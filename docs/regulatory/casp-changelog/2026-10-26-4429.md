- **#4429** — epic #4428 slice 1: a stored display colour per agent
  (`agents.avatar_tint`, migration 121), assigned by the database on insert,
  backfilled once, and served on the agent reads. The column is
  `SMALLINT NOT NULL CHECK (avatar_tint BETWEEN 1 AND 6)`; a `BEFORE INSERT`
  trigger fills a NULL from the lowest tint no *held* agent of that user holds
  (`archived_at IS NULL AND superseded_by_agent_id IS NULL`), an
  `AFTER UPDATE OF superseded_by_agent_id` trigger hands a predecessor's tint
  to its replacement unless another held agent holds it, and the backfill
  colours held agents first (oldest first per user) then released ones by
  least-used/lowest number. The reads that carry it are display projections
  only: `LIST_AGENTS_FOR_USER_ALL_STATUSES_SQL` /
  `FIND_AGENT_FOR_USER_ALL_STATUSES_SQL` / `INSERT_AGENT_WITH_KEY_SQL` /
  `UPDATE_AGENT_PROFILE_SQL` in `infra/repositories/agents.ts`,
  `PER_AGENT_SPEND_SQL` in `infra/repositories/analytics.ts`, and
  `LIST_DASHBOARD_AGENTS_SQL` in `infra/repositories/dashboard.ts`, surfaced as
  `avatar_tint` on `Agent` and the `/analytics/overview` agent items and
  `avatarTint` on `DashboardAgentPreview`.
  - **Authority and custody.** The column carries no authority, custody,
    allowance or budget weight. Nothing on the payment path, the delegation
    path, the budget pre-check, the enforcers or the settlement path reads it;
    it is the same boundary as `labels` (#3167) and `organization_id` (#3164).
    The two triggers write only `avatar_tint` — the insert trigger fills a NULL
    on the row being inserted, and the inherit trigger's `UPDATE` is scoped to
    `id = NEW.superseded_by_agent_id AND user_id = NEW.user_id AND
    agent_holds_avatar_tint(...)`, so it can never recolour a released agent or
    cross a tenant. No route code changes: `POST /agents/retired` still only
    stamps `superseded_by_agent_id`, and the tint follows in the database.
  - **Refusals held.** The `CHECK` refuses any value outside 1..6 (proven
    against real Postgres). The insert trigger keeps an explicit tint rather
    than overwriting it, so the 127 existing `INSERT INTO agents` sites — the
    two runtime ones, the migration tests and `scripts/db-schema-smoke.ts` —
    keep working unchanged, and an old replica inserting without the column
    during a rolling deploy cannot fail on `NOT NULL`. Two agents created for
    one user at the same instant may share a tint; that is accepted and
    documented in the migration, with no unique constraint, because the tint is
    a display hint and a unique index would turn a cosmetic collision into a
    failed agent creation.
  - **Mutation-proven.** `db/migrations/__tests__/121_agents_avatar_tint.test.ts`
    pins the column shape, the CHECK, both triggers, all five functions, the
    down/up cycle and `assertWorkerSchemaAtHead` against real Postgres;
    `infra/repositories/__tests__/agents-avatar-tint.db.test.ts` proves the
    backfill order (held before released, oldest first, per user), the
    least-used fallback past six agents, the trigger's fill/keep/no-recolour
    behaviour, archived and superseded tints freeing for the next new agent,
    `pending_approval` and revoked agents holding theirs, inheritance on
    supersession, the blocked-inheritance case, and that a rename does not
    recolour. `scripts/db-schema-smoke.ts` and migrations 093/094/096/101 pass
    unchanged. The ops read-only role gains the column
    (`infra/ops-readonly-role.ts`), which is display data and grants no new
    table.
  Perimeter unchanged.
