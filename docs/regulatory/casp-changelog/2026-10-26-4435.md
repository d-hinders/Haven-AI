- **#4435** — the agent Settings tab's tax-declaration toggle is now disabled
  for an agent whose payments cannot carry a declaration, with a one-line
  reason. This PR adds a display-only field to the agents list read and a
  disabled state to one control: no runtime behaviour, no migration, no
  refusal, no key material, no wire field the payment path reads.
  What changed:
  - **The signal is the setup row the backend already stores.** The agents
    LIST read (`packages/backend/src/infra/repositories/agents.ts:319`) now
    selects `install_status->>'runtime_mcp_mode'` from the agent's most recent
    `agent_connection_setups` row (`ORDER BY created_at DESC LIMIT 1`) as
    `runtime_mcp_mode`. The connector writes that key at
    register/install-status time (`packages/connect/src/api.ts:297`), the
    backend sanitizes it into a closed key list
    (`packages/backend/src/modules/agents/agent-connection-setup.ts:124`), and
    its values are `local_stdio`, `hosted_plus_signer` and `manual`
    (`packages/connect/src/config-writers.ts:10`). No new column, so no
    migration, no `ops-readonly-role` allowlist change and no new reader of
    owner data.
  - **`hosted_plus_signer` disables the toggle; everything else leaves it
    enabled.** `TaxDeclarationToggle` disables the checkbox when the mode is
    `hosted_plus_signer` AND the opt-in bit is OFF, and renders the reason as
    a sibling paragraph below the checkbox row — not as the checkbox's helper
    text, which sits inside the `<label>` and is never announced for a
    disabled control. `local_stdio` (the local MCP server holds the delegate
    key), `manual` (a developer's own SDK client with a delegate key can send
    one, and Haven cannot know) and unknown (no setup row, an `agent_id` set
    to NULL by a delete, or a setup that never reported the key) all stay
    enabled: "cannot tell" is not "cannot send", and disabling every agent
    that predates the signal would be a user-visible regression on deploy.
  - **An agent whose bit is already ON stays interactive** even on
    `hosted_plus_signer`, so the owner can still switch it off. The PUT is
    deliberately never gated on OFF
    (`packages/backend/src/routes/agent-tax-declaration.ts:118-121`); a
    disabled control would trap an opt-in the owner cannot undo.
  - **The field is display-only.** `runtime_mcp_mode` is optional on the
    `Agent` schema (`packages/backend/src/openapi/spec.ts`, regenerated into
    `packages/core/src/api-types.ts`) and is read by exactly one component,
    `TaxDeclarationToggle`, through `AgentSettingsTab`. Nothing in the
    delegation, budget, enforcement or client-compat path reads it — the same
    boundary `tax_declaration_enabled` and `organization_id` already carry.
  Authority and custody argument:
  - **No authority moves.** The toggle still writes the same
    `PUT /agents/:id/tax-declaration` body, and the route's own gates (owner
    session, feature flag, saved VAT number, VIES `valid`) are untouched. The
    new field only decides whether the control is interactive; it authorizes
    nothing and refuses nothing.
  - **No custody moves.** The declaration is still built at read time from the
    owner's company-details row and signed by the delegate key in the client
    that holds it (`packages/sdk/src/tax-declaration.ts`). Haven still holds
    no key, and the disabled state removes an opt-in that could not have
    produced a declaration anyway.
  - **The signal is self-reported but not trusted for anything but display.**
    `runtime_mcp_mode` comes from the connector's own report, sanitized to a
    closed key list and capped at 120 characters. It is not an authorization
    input: a wrong value can only show or hide a reason line and enable or
    disable a checkbox whose write path is unchanged. The header-based
    alternative (`X-Haven-Client`) was rejected in the issue because it is
    evaluated per request and never persisted.
  Mutation-tested:
  - `packages/frontend/src/components/agent-panel/__tests__/TaxDeclarationToggle.test.tsx`
    — the disabled state, the reason literal with `toBe`, the reason being
    outside the checkbox's label and reachable by role, `local_stdio` /
    `manual` / unknown staying enabled, and the bit-ON case staying
    interactive and PUTting `false`.
  - `packages/backend/src/infra/repositories/__tests__/agents.test.ts` — a
    `local_stdio` agent and a `hosted_plus_signer` agent read different
    values, the most recent setup wins, and no setup row / a NULL `agent_id` /
    a setup without the key all read NULL.
  Perimeter unchanged: a display-only field on the agents list read and a
  disabled state on one settings control; no runtime behaviour, wire field,
  migration, custody, signing, settlement, funding or refusal change.
