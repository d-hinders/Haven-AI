- **#4443** — documentation correction: the #4429 shard and migration 121's
  header comment named an endpoint that does not exist. Both said the
  inheritance trigger fires on `POST /agents/retired`; the real route is
  `POST /agent-connection-setups/{setupId}/retired-agents`. No route, schema,
  migration or trigger change — the migration comment is corrected in place and
  the merged shard is corrected by this new one; nothing else moves.
  - **The wrong claim, quoted.** The #4429 shard
    (`2026-10-26-4429.md`, merged as `4a3f56847`) says: "No route code changes:
    `POST /agents/retired` still only stamps `superseded_by_agent_id`, and the
    tint follows in the database." Migration 121's *Inherited* bullet said the
    same. It was wrong when written: `POST /agents/retired` exists nowhere in
    `packages/backend/src/routes`, so a reader following either file gets a
    404. The error came from issue #4429's own text, which named that path in
    its inheritance bullet; the build followed the spec faithfully, so this is
    a spec-text error that propagated into a code comment and a compliance
    record, not a build error.
  - **The correct fact.** The route is
    `app.post('/:setupId/retired-agents', …)` in
    `packages/backend/src/routes/agent-connection-setups.ts:795`, published as
    `/agent-connection-setups/{setupId}/retired-agents` in
    `packages/backend/src/openapi/spec.ts:7061` with request schema
    `RecordRetiredAgentsRequest`. It stamps `superseded_by_agent_id` on each
    retired id owned by the caller's user; the `AFTER UPDATE OF
    superseded_by_agent_id` trigger then hands the predecessor's tint to the
    replacement. The #4429 shard's substantive claims — no route code change,
    the tint follows in the database, the trigger's `UPDATE` is scoped to
    `id = NEW.superseded_by_agent_id AND user_id = NEW.user_id AND
    agent_holds_avatar_tint(...)` — were and remain true; only the endpoint
    name was wrong.
  - **Why a new shard rather than an in-place edit.** The #4429 shard was
    wrong when written, not stale via a later change, and it is a merged
    compliance record. Per this directory's README (*Once merged, a shard is
    immutable*, the "wrong when written" case) the correction is a new dated
    shard that quotes the wrong claim and states the correct one; rewriting
    the original would remove the evidence that the error was made. The
    original shard is byte-identical to what merged. Migration 121's comment is
    not a compliance record, so it is corrected in place.
  - **Perimeter.** Documentation only. No route is added, removed or
    re-scoped; no request schema, migration, trigger, function or grant
    changes; no key material, signing, relaying, payment execution, allowance
    or budget surface is touched. The corrected string names an endpoint that
    already existed and already behaved as described. Verified by grep: the
    wrong string appears in no file under `packages/backend/src`, and under
    `docs/` only in the #4429 shard this correction answers and in this
    correction's quotation of it; the corrected string matches the route
    registration and the OpenAPI path exactly. Perimeter unchanged.
