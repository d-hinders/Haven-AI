- **#4449** — the edge signer's SUCCESS results now name the agent's next step,
  and its settlement-child guidance names the MCP-merchant settle beside the
  plain-HTTP one. Guidance fields and text only.
  What changed:
  - **Six success sites, one step each.** `haven_sign` on a direct payment,
    `haven_sign` on an x402 context, `haven_sign_x402`,
    `haven_x402_sign_header`, `haven_sign_sweep_delegate` and
    `haven_sign_siwx` each now carry either `next_tool_name` +
    `next_tool_server_role: 'hosted'` + `next_arguments`, or a literal
    `next_tool_omitted_reason`. Before this, only the signer's REFUSALS carried
    the next-step family (#3103), so `CLAUDE.md`'s "every MCP payment-flow
    response names its next tool" was false for these six sites and
    `scripts/lint-next-steps.mjs` could not see them — its numerator is
    emission blocks that carry a `next_action` decision, and a success result
    carries none.
  - **The `next_tool` family only.** No success result gains `next_action` or
    `safe_to_continue`; those stay on refusals, and the task-budget and
    sub-budget successes have never carried them either. `signerSuccessWireFields`
    (`packages/signer/src/next-step.ts`) renders the builder's output through
    `nextStepWireFields`, so a decision cannot reach a success wire.
  - **Where the signer knows the tool, it names it.** A direct-payment
    `haven_sign` hands off to the hosted `haven_submit` with
    `{ payment_id, signature }` — the `haven_submit#payment` variant beside the
    existing `#task_budget` / `#sub_budget` ones. `haven_sign_sweep_delegate`
    hands its signature back to the hosted `haven_sweep_delegate` phase 2 with
    `{ authorization, signature }` — the `haven_sweep_delegate#sweep` variant.
    Both are `SIGNER_HOSTED_HANDOFF_SHAPES` entries with strict shapes, both are
    registered in `SIGNER_NEXT_STEP_TARGETS`, and both are pinned to the hosted
    schemas by `packages/mcp-server/src/next-step-signer-parity.test.ts`. No
    bare `haven_submit` / `haven_sweep_delegate` key with an all-optional union
    shape is added.
  - **Where it cannot know, it says why instead of guessing.** The three x402
    success sites (`haven_sign` on an x402 context, `haven_sign_x402`,
    `haven_x402_sign_header`) cannot tell an MCP merchant from a plain-HTTP one,
    nor a fresh signature from a funded-retry resume: the fetched sign context
    keeps only `paymentId`, `payloadHash`, `typedData`, `x402Expected`,
    `paymentRequired` and `clientUpdate` (`sign-context.ts`), and the
    caller-supplied `x402_expected` path has no context at all. A guessed
    `haven_submit` would be wrong on an MCP merchant and on the resume path, so
    each reason names BOTH settle routes — `haven_submit` with
    `settlement_scheme: 'erc7710'` for a plain-HTTP merchant,
    `haven_settle_mcp_tool` with no `payment_header` for an MCP merchant.
    `haven_sign_siwx` names no tool because no hosted tool follows a sign-in.
  - **Settlement-child text names both routes.** `NO_FUNDING_LEG_MESSAGE` and
    both `NO_FUNDING_LEG_NEXT_STEP_REASONS` (`no-funding-leg.ts`), and the
    `haven_sign`, `haven_sign_x402` and `haven_x402_sign_header` descriptions
    (`tools.ts`), now name `haven_settle_mcp_tool` with no `payment_header`
    beside `haven_submit` with `settlement_scheme: 'erc7710'`. The `one_shot`
    reason fires on `haven_sign_x402` — the MCP-merchant tool — so before this
    it sent an MCP agent down the HTTP route. The `haven_sign` description also
    says a settlement child's returned `x402_binding` is already retired
    (#4256), so the id is unusable.
  - **One SDK builder field, additive.** `NextStepTarget` gains an optional
    `name`, so a `<tool>#<variant>` target key selects the argument shape while
    the rendered `next_tool_name` stays the bare tool. Absent → the key is the
    name, which is every other target; no existing caller changes.
  Authority and custody: the change writes guidance fields onto results the
  signer already returns, and rewrites prose. It does not touch a signing
  decision, a typed-data check, an allowlist, a binding, a key, a delegation, a
  transfer or a relay. No field is removed — `x402_binding` stays on the
  erc7710 `haven_sign` result — and `SUPPORTED_X402_EXPECTED_VERSIONS` is
  untouched, so an old hosted server and an old client keep working. The
  signer's single-read network posture is unchanged: no new backend
  sign-context field and no new signer network read. Installed signers
  (`0.10.0-alpha.0`, `0.8.1-alpha.0`, observed live 2026-10-26) never emit
  these steps, so the hosted prepare and pay guidance stays authoritative and
  is not trimmed in favour of the signer step.
  Tests:
  - `packages/signer/src/next-step-success.test.ts` — a success-path walk beside
    `next-step-characterization.test.ts`, keyed per fixture like that file's
    `STEP` table: ten fixtures covering all six sites, including both the
    `{ payment_id }` and caller-supplied `x402_expected` paths for the x402
    sites, the EIP-3009 funding leg and the erc7710 child for `haven_sign`, and
    the direct-payment `{ payment_id }` and caller-supplied `typed_data` paths.
    Each pins the exact step — tool + arguments, or the literal reason string.
    The walk fails on a reason matching
    `/not a registered next-step target|do not parse under/`, the SDK builder's
    silent fallback, so a misspelled or unregistered target cannot pass as "a
    reason". It also asserts no success result carries `next_action` or
    `safe_to_continue`.
  - Mutation-tested, both recorded in the test file's header: deleting the step
    from the `haven_sign_siwx` success site turns two tests red; misspelling
    `payment_id` as `paymentId` in the direct-payment handoff turns two tests

    `next_arguments do not parse under haven_submit#payment` fallback.
  - `packages/mcp-server/src/next-step-signer-parity.test.ts` — the two new

  - `packages/sdk/src/next-step.test.ts` — the `name` override renders the bare

  - The no-funding-leg literal pins in
    `packages/signer/src/x402-binding-rail.test.ts` are updated to the new

  - The new description sentences are pinned WHOLE in

    `haven_sign_x402`, `haven_x402_sign_header`, `NO_FUNDING_LEG_MESSAGE`). A

  - Full suites: `packages/signer` 423 passed, `packages/mcp-server`
