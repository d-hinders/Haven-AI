- **#4468** — the hosted MCP now answers the ten task-/sub-budget
  payment-scope refusals with their own typed codes and relays the backend's
  `error_code`, and answers three siblings of the same shape. This PR changes
  the SHAPE of a refusal and the client's reading of it; the refusal decision
  itself is untouched.
  What changed:
  - **The ten codes stop being `API_ERROR`.** `normalizeError`
    (`packages/mcp-server/src/tools/support/errors.ts`) gains one table-driven
    branch ahead of the generic `HavenApiError` pair. `task_budget_` and
    `sub_budget_` × `not_found` (404), `not_open`, `token_mismatch`,
    `recipient_mismatch` and `parent_mismatch` (409) now answer their own
    hosted `code` (the backend code upper-cased), the backend's `error_code`
    at the top level, `next_action: stop_and_tell_user`, and a reason naming
    that code's real remedy. Before, all ten fell into the generic 4xx branch:
    `code: "API_ERROR"`, the generic "refused as made" reason, and no
    `error_code` — the backend's typed reason survived only as English in
    `message`.
  - **Every payment-scope refusal keeps `stop_and_tell_user`.** Re-making a
    payment without `task_budget_id` / `sub_budget_id` draws from the agent's
    WHOLE budget instead of the scope the caller chose — the silent re-scoping
    #3378 fixed. The agent may never do that on its own, so each reason that
    mentions paying without the id ends "after telling the user", and none of
    them names a tool: the remedy is a decision the user makes.
  - **The reasons follow production, not the names.** `task_budget_not_open`
    covers `pending` too, so its reason names `haven_get_task_budget` and both
    states — a pending row is the agent's own unsigned one (sign it and submit
    it with `haven_submit`), a closed or expired one needs a new task budget.
    `task_budget_parent_mismatch` comes only from the resolver's parent lookup
    by the row's OWN `parent_delegation_hash`, so there is no "right id" to
    offer: the owner has to restore that delegation. The sub-budget codes are
    about a grant the ISSUER holds, not the paying agent.
  - **Three siblings.** `task_budget_exceeds_remaining` (409, from
    `haven_open_task_budget`) gets its own branch relaying `remaining_atomic`,
    `reserved_atomic` and `requested_atomic` and keeping
    `stop_and_tell_user`. On `haven_submit`'s TASK-budget path,
    `close_needs_reprepare` (409) and `close_outcome_unconfirmed` (502) now map
    to typed refusals naming `haven_close_task_budget` with `task_budget_id` —
    the shape the sub-budget path has had since #3506. Before, the task-budget
    path had no catch at all, so an unconfirmed close read as the generic 5xx
    "retry once" and a stale close op as a generic 4xx stop.
  - **One artifact, two readers.** The code unions and their status tables
    moved to `packages/core/src/budget-refusal-codes.ts`; the backend's
    `modules/budget-scope/resolver.ts` re-exports them (its wire statuses are
    unchanged) and the hosted answer table is typed `Record<Union, …>` off the
    same union. The hosted test walks `PAYMENT_SCOPE_REFUSAL_CODES`, so a
    member added on either side without an answer fails a test instead of
    reaching an agent as `API_ERROR`.
  Authority and custody argument:
  - **Authority narrows, never widens.** No payment is re-scoped: every one of
    these refusals still stops and tells the user, and the agent is never told
    to re-make the payment without the id on its own. Nothing signs, moves,
    authorises or deploys differently — the change is the guidance attached to
    a refusal the backend already decided.
  - **No custody moves.** All thirteen refusals are pre-funding and
    pre-prepare; the bodies carry no signing material, and Haven still holds no
    key.
  - **No new reader of owner data.** The relayed fields (`error_code`,
    `remaining_atomic`, `reserved_atomic`, `requested_atomic`) are the ones the
    backend already sends on the refusal it already decided.
  - **Additive on the wire, with one value change.** `ToolFailure` gains an
    optional `error_code`; `code` changes from `API_ERROR` to a typed value for
    these ten codes, which is why this shard and the
    `mcp-runtime-compatibility.md` re-verification exist. The generic branch
    deliberately does NOT relay `error_code` — that decision belongs to #4470,
    which edits the same branch.
  Mutation-tested:
  - `packages/mcp-server/src/next-step-refusal.test.ts` — one test per code,
    built the way the SDK transport builds the error (message = the backend's
    `error`, the shared status table's status, body `{ error, error_code }`),
    pinning with `toBe`: the typed `code` (never `API_ERROR`), the top-level
    `error_code`, `stop_and_tell_user`, and the code's own
    `next_tool_omitted_reason`. Plus the `task_budget_not_open` two-state
    reason, the "pay without … after telling the user" rule, a negative
    control (an unrelated `error_code` still takes the generic `API_ERROR`
    stop with no `error_code`), and the `task_budget_exceeds_remaining`
    figures.
  - `packages/mcp-server/src/tools/task-budgets.test.ts` — the two close codes
    through the real `haven_submit` handler: `CLOSE_NEEDS_REPREPARE` and
    `CLOSE_OUTCOME_UNCONFIRMED` each name `haven_close_task_budget` with
    `task_budget_id`, and any other submit failure is relayed unchanged.
  - `packages/mcp-server/src/next-step-refusals-characterization.test.ts` and
    `next-step-signer-parity.test.ts` — thirteen new `REFUSAL_SITES` rows; the
    census is re-counted, not incremented: `REFUSAL_SITE_COUNT` 65 → 78 and
    `REFUSAL_STEP_CALLS` 75 → 79 (the ten codes share ONE table-driven
    `refusalNextStep` call). `lint:next-steps` stays at zero.
  - `packages/core/src/budget-refusal-codes.test.ts` — the artifact is exactly
    ten codes, the two scopes are disjoint, and every member has a status.
  - Prove-red, run: (1) making the answer lookup skip `task_budget_not_open`
    reddens three tests — that code's per-code test, its two-state reason test,
    and its characterization fixture — at RUNTIME, not as a compile or import
    error; (2) swapping the `task_budget_token_mismatch` and
    `task_budget_recipient_mismatch` reasons reddens both codes' per-code tests
    and both characterization fixtures (4 failures).
  Perimeter unchanged: the refusal decision, the ledger rows, the custody model
  and the on-chain gate are all as they were; the wire shape of thirteen
  refusals and the client's reading of them change, and no payment is ever
  re-scoped without the user.
