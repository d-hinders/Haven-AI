- **#4470** — what an agent is told after a failure is decided by the
  failure's cause, not its HTTP status alone. This PR changes refusal
  guidance and two typed errors; nothing signs, moves or authorises
  differently.
  What changed:
  - **A non-answer is not a refusal.** The SDK transport
    (`packages/sdk/src/haven-api-transport.ts`) marks its own 408 timeout and
    its status-0 errors (`fetch` threw, or the body was not JSON — a
    gateway's HTML 502 arrives this way) with
    `failureCause: { kind: 'no_answer', method }`. The hosted `normalizeError`
    (`packages/mcp-server/src/tools/support/errors.ts`) read both as "refused
    as made (4xx)". It now tells a read (`GET`: re-call once) from a write
    (`POST`: the outcome is unknown, so never re-call it or create a new
    payment). The two submit wrappers that know the payment id
    (`submitSignatureWithExpiryMapping`, `submitErc7710WithExpiryMapping` in
    `tools/support/mcp-context.ts`) answer a write's non-answer with the
    status read for that id, code `NO_ANSWER_OUTCOME_UNKNOWN`. That follows
    the `MerchantTimeoutError` and `SUBMISSION_OUTCOME_UNKNOWN` precedents. A
    re-sent erc7710 settle 409s and its `payment_header` cannot be recovered,
    so "re-call" was the harmful answer there.
  - **The settlement report stops claiming an on-chain mismatch.** The SDK
    evidence classifier (`packages/sdk/src/merchant-completion.ts`) classed a
    non-answer and any 408 as `refused`. The hosted tools word that as "the
    hash does not match this payment on-chain", a claim about the chain that
    nothing had checked. They now class as `retryable`, and the hosted
    pending texts name "Haven did not answer" as a cause. Only the backend's
    own 503 is re-attempted inside the call, so the number of posts is
    unchanged. The status read before a hosted settlement report keeps a
    timed-out read as `unavailable` (nothing posted), not `drop`.
  - **The funding wait answers both its outcomes.** ethers 6.16's
    `waitForTransaction` rejects with `TIMEOUT` instead of resolving null, so
    the timeout escaped `waitForFundingTx`
    (`packages/sdk/src/x402-funding-leg.ts`) as a plain `Error`. The hosted
    tool then told the agent "re-calling it the same way will fail the same
    way", after Haven had submitted the funding leg. The timeout is now
    `FundingConfirmationUnknownError` and a reverted receipt is
    `FundingRevertedError`. The hosted delivery step
    (`tools/paid-mcp-completion.ts`, `ensureFundingConfirmedOrRefuse`) answers
    them, before any merchant call:
    - `FUNDING_CONFIRMATION_UNKNOWN`: check status, complete once, and sweep
      only if the funding is confirmed and delivery still fails;
    - `FUNDING_REVERTED`: stop, because nothing reached the delegate.
  - **A deterministic SDK failure is not transient.** Nine SDK sites threw a
    literal 500/502 for an answer that a retry cannot change, so the hosted
    step read "failed transiently; re-call … once". They now use
    `HavenApiError.deterministic(...)` and get "re-calling it the same way
    gets the same answer, so tell the user". Two payment-state throws are
    marked too: `pending_approval`, and the 5xx fallback for `failed` or an
    unknown status. The mark survives the hosted discovery rebuilds in
    `mcp-context.ts`. A census
    (`packages/sdk/src/haven-api-error-census.test.ts`) requires every
    literal 5xx `new HavenApiError(` site to be marked or allowlisted with a
    reason. Five are allowlisted: four that one re-call may fix, and one
    unreachable.
  - **A genuine upstream 5xx stays transient.** Example: `prepare_failed`,
    which has no recognised `error_code`. The existing fixture row is
    unchanged.

  Perimeter: no route, policy check, delegation, signature, funding leg,
  sweep or ledger write changes. The payment a non-answer concerns is
  untouched. The agent is told to read its status instead of re-sending it,
  which narrows the double-submission risk rather than widening it. The
  on-chain gate is as it was.

  Evidence:
  - `packages/mcp-server/src/retry-by-cause.test.ts` drives real SDK code
    over a stubbed `fetch`, and real ethers over a local JSON-RPC server.
    It covers:
    - each non-answer on a read and on a write;
    - `haven_submit` on both schemes;
    - both settlement-report tools, and the status read before them;
    - the funding wait's TIMEOUT and reverted receipt, with the merchant
      never called;
    - each of the nine deterministic sites;
    - the discovery rebuild, the payment-state throws, and the transient
      regression pin.
  - `packages/sdk/src/haven-api-transport.test.ts` pins the cause and the
    method on each non-answer. It also pins that a server's JSON 408 carries
    none.
  - `packages/sdk/src/x402-race-condition.test.ts` and `x402.test.ts` pin the
    typed funding outcomes and the evidence classes. In `x402.test.ts` the
    `#4215` refusal rows for a transport failure, a non-JSON 503 and a 408
    moved to the no-verdict rows, on purpose.
  - The census `REFUSAL_STEP_CALLS` is re-counted to 81 and
    `REFUSAL_SITE_COUNT` to 71 (six new steps, six new fixture rows).
