- **#4517** — opt-in PKCE (RFC 7636, `S256`) in the generic accounting OAuth2
  flow, slice 1 of the Igdrasil epic #2875. No provider turns it on in this
  change: Fortnox's config does not set the flag, and Igdrasil's connector is
  the next slice.
  What changed:
  - `packages/backend/src/modules/accounting/oauth-pkce.ts` (new): the
    verifier is `base64url(HMAC-SHA256(key, "accounting-pkce:" + jti))` and
    the challenge is `base64url(SHA-256(verifier))`.
  - `oauth-flow.ts`: `OAuth2ProviderConfig` gains `pkce?: 'S256'`. When it is
    set, `buildAuthorizeUrl` appends `code_challenge` and
    `code_challenge_method` after every other parameter, `exchangeCode` adds
    `code_verifier`, and both throw, before any request, when no verifier is
    given. `completeOAuth2Connect` passes the verifier through.
  - `connections.ts`: `connectUrlFor` and `completeProviderOAuthCallback` take
    the state's `jti` and derive the verifier under `config.jwtSecret`, only
    for a config that sets `pkce`.
  - `routes/accounting-connections.ts`: the connect-url route keeps the claims
    object it signs and passes its `jti`; the callback passes the `jti` of
    the state it has already verified and consumed. Nothing about the state
    itself changes: same claims, same purpose, same single-use consumption,
    same ten minutes.
  Authority and custody argument: the change concerns the user's grant to
  their own ledger, never a Haven key, delegate key, delegation, allowance,
  relayer or signer. It constructs no transaction and adds no write path to
  any money table. It is a narrowing for a PKCE provider: an authorization
  code that leaks from the redirect can no longer be exchanged without the
  verifier, which is derived server-side and leaves the backend only in the
  back-channel token exchange to the provider. The
  verifier is not a claim of the state, which is signed but not encrypted and
  travels in the consent URL; a test decodes the state and asserts the
  verifier is absent from both the claims and the URL. `JWT_SECRET` was
  already required at boot and already signs the state, so no new secret is
  introduced. `HAVEN_SECRETS_KEY` is not touched (`infra/secrets.ts` remains
  its only reader). For Fortnox the change is a no-op on the wire: tests pin
  the exact pre-change consent URL and exchange body for a config without
  the flag, and the existing Fortnox suites run unchanged. No migration, no
  schema, no env var, no wire field. Perimeter unchanged.
