- **#4530** — evidence and guidance only: the settlement-evidence handoffs now
  prefill the agent's own `payment_header` in `next_arguments`, the payment
  status read names the merchant settlement transaction it recorded, and the
  hosted server instructions gained two sentences about a cached tool list. No
  custody, signing, spend authority, allowance, budget or refusal semantics
  change; nothing moves funds.
  What changed:
  - `packages/mcp-server/src/tools/paid-mcp-completion.ts`: the retryable arm
    of `settlementEvidenceHandoff` (reached from `haven_complete_mcp_tool` and
    `haven_settle_mcp_tool` on EIP-3009) and
    `haven_report_settlement_evidence`'s status-unreadable arm now carry
    `payment_header` in `next_arguments` — the header the call itself
    forwarded, so the agent re-supplies nothing. The `SETTLEMENT_PENDING` arm
    keeps naming `haven_get_payment_status` (decided per arm: the status read
    is non-mutating and, with the field below, now names the recorded hash).
  - `packages/mcp-server/src/tools/plain-http-x402.ts`: the folded-evidence
    retryable arm prefills the header the call FORWARDED as `proofHeader`
    (never the raw argument, so a deliberately withheld header is never handed
    back), and the offer arm prefills the header the call carried.
  - `packages/mcp-server/src/tools/support/guidance.ts`: one shared helper,
    `prefillablePaymentHeader`, omits the header when it exceeds the report
    tools' 16,384-character cap — a `next_arguments` the named tool would
    refuse is never emitted.
  - `packages/backend/src/modules/payments/agent-payment-status.ts` +
    `packages/backend/src/openapi/spec.ts`: the status read gains
    `merchant_settlement_tx_hash`, present only when
    `merchant_settlement_recorded` is, carrying the
    `machine_metadata.merchant_settlement_tx_hash` string the flag already
    keys on. It is the RECORDED, on-chain-verified transaction — never the
    merchant's unverified echo, which is why it is not named
    `settlement_tx_hash` (that name, on receipts and the transactions feed,
    includes the echo).
  - `packages/sdk/src/payment-mappers.ts` + `types.ts`: the SDK maps it to
    `merchantSettlementTxHash`, absent when the backend sends no key.
  - `packages/mcp-server/src/server.ts`: two sentences added to
    `HOSTED_INSTRUCTIONS` — a `next_arguments` Haven returned may be sent
    verbatim even when a key in it is missing from the client's loaded schema,
    and a reconnect or restart that does not change the tool list is remedied
    by removing and re-adding the hosted MCP server entry.
  Authority and custody argument: every edit is a value the agent already
  supplied being echoed back to it, a public on-chain transaction id being
  named on a read the agent already performs, or instructions prose. No
  signing path, key material, delegate balance, budget cap, allowance,
  refusal code or settlement decision is touched; the prefill is bounded by
  the report tools' own schema cap, and the status field is derived from the
  same predicate the existing flag uses. The change neither widens nor
  narrows who can sign, move or authorise anything. Perimeter unchanged.
