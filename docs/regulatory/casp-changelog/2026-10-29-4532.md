- **#4532** — descriptive metadata only: the accounting feed's receipt underlag
  and feed payload now say WHAT KIND of transaction a settled payment is. One
  BikBok gift-card purchase through Bitrefill's plain-HTTP x402 route settled
  three payments on production 2026-10-29 (`POST /x402/invoice/create`,
  `POST /x402/invoice/pay`, `GET /x402/invoice/status`) and all three receipts
  rendered the same field set, so an accountant could not tell the purchase
  from the merchant's per-call API fees.
  What changed:
  - `packages/backend/src/modules/accounting/transaction-kind.ts` (new): the
    closed enum `purchase | api_fee | transfer | refund | unknown`, the
    derivation ladder and the one-line description. Pure functions over facts
    Haven already stores — the payment direction, the x402 resource route, the
    intent's `mcp_call_context.toolName`, the captured merchant document and
    the delivery reference. No route accepts a kind, so an agent cannot set it;
    a payment with no derivable signal is `unknown`, never a guess.
  - `packages/backend/src/modules/accounting/entry.ts`: the source row gains
    `mpe.delivery_reference` and
    `pi.machine_metadata->'mcp_call_context'->>'toolName'` (both already
    stored, no migration), and `toAccountingEntry` derives
    `transactionKind` / `transactionDescription` once.
  - `packages/backend/src/modules/accounting/feed-transaction.ts`: the feed
    payload carries the same two values (`transactionKind`, `description`).
  - `packages/backend/src/modules/accounting/receipt-underlag.ts`: the PDF
    renders `Transaction` and `Description` beside `Resource`.
  - `packages/backend/src/modules/accounting/fortnox-connector.ts`: the
    description rides the free-text `Comments` field, with `/` folded to `-`
    for Fortnox's character restriction (error 2000359).
  - `packages/backend/src/modules/accounting/accounted-connector.ts`: comment
    only — Accounted's upload takes exactly `file` + `upload_source`
    (`additionalProperties: false`), so the PDF is the carrier.
  - `docs/operations/accounting-feed.md`: the new fields, the ladder and the
    per-connector carrier.
  Authority and custody argument: every edit is a read of an already-stored
  payment fact and a string on a document the feed already produces. No
  payment, signing, key, custody, settlement, funding, budget, allowance,
  authority or merchant-acquiring surface is touched; no amount, rate, hash or
  status is recomputed; no route, wire contract or schema changes; no
  migration. The classifier cannot move funds, cannot alter a signed payment
  intent, and cannot make an API credential sufficient to spend — it labels a
  receipt. Existing stored receipts are untouched: the kind renders at push
  time and nothing re-renders a delivered document.
  Mutation-tested: the three Bitrefill routes are pinned to `api_fee`,
  `purchase`, `api_fee` at both the classifier and the entry builder, with a
  CONTROL asserting the three routes really do differ; a smuggled
  `transactionKind` on the signals object is ignored; an ambiguous verb
  (`price`) and an unparseable URL stay `unknown`; the PDF and the Fortnox
  comment each assert the two kinds render differently.
  Perimeter unchanged.
