- **#4550** — the EIP-3009 bridge's wire signature is now PINNED low-s, and the `@x402/*` v2 packages move 2.17.0 → 2.29.0. x402 facilitators reject a non-canonical (high-s) 65-byte EOA signature in `exact` EIP-3009 verify before settlement (x402-foundation/x402#2728, aligned across SDKs in x402-foundation/x402#3964; wire reason `invalid_exact_evm_non_canonical_signature`). Haven's bridge is exactly that case — the payer is the agent's delegate EOA — and it complied only because viem's `privateKeyToAccount().sign()` passes `lowS: true` to noble secp256k1. Nothing in Haven asserted it, so swapping the signing account (a KMS signer, a hardware key, a different library) could have shipped high-s headers that every facilitator rejects. Three regression tests now base64-decode the RETURNED header (v2 envelope included), read `payload.signature`, and assert 65 bytes, `v ∈ {27, 28}` and `s ≤ n/2` across 32 signatures each: the signer's `buildX402PaymentHeader` (`packages/signer/src/core.ts:501`, varying the payment id because the nonce is derived from it), the SDK's `paymentId` branch (`packages/sdk/src/x402-funding-leg.ts:375`) and the SDK's no-`paymentId` branch (`:378`). The shared assertion lives in `@haven_ai/sdk/test-support` (`low-s.ts`) so the other un-pinned ECDSA sites — sweep authorization, delegation/UserOp typed data, SIWX, the SDK's ethers signer — can be pinned cheaply later. **Mutation-proven, three cells, each emitting the malleable twin `(r, n − s, v ^ 1)` after the sign call:** cell 1 (signer) and cell 2 (SDK `paymentId` branch) redden ONLY the new test — the viem-based recovery tests accept the twin and recover the same address, which is the gap this closes; cell 3 (SDK no-`paymentId` branch) reddens the new test AND the five ethers-based recovery/asset tests, because ethers 6.16 rejects non-canonical `s` outright (`TypeError: non-canonical s`) — a stronger signal than the issue predicted, recorded as measured rather than as expected. **The dependency bump moves no authority or custody:** `@x402/*` is a devDependency in every published package, so it reaches no installed SDK or signer user, and the runtime dependency `x402@^1.2.0` in `packages/sdk` and `packages/signer` is unchanged. It does change the runtime of two PRIVATE packages. `demo-merchant-mcp` is unaffected — it imports only the header codecs (`decodePaymentSignatureHeader`, `encodePaymentRequiredHeader`, `encodePaymentResponseHeader`) and types, all unchanged in 2.29. `qa-agent`'s ERC-7710 pilot WOULD have broken: 2.29 always applies spend controls when selecting a requirement, and `@metamask/x402`'s erc7710 scheme client has no `findDefaultAsset`, so every 402 was rejected with "All payment requirements were rejected by spendControls…" whatever the price — the `as never` cast on the selector hid the drift. The pilot now configures spend controls explicitly (`x402Client.fromConfig({ …, spendControls })`) with an `allowedAssets` entry for the USDC it pays in, capped at its own `VPN_BASIC_PRICE` so a merchant quoting more fails loudly rather than silently overpaying; a new unit test builds the pilot's client against a canned 402 and gets a payment payload back, and a second asserts the cap rejects an overpriced requirement. Removing the spend controls reddens the first test with exactly the 2.29 rejection message. `packages/signer/src/siwx.test.ts` needed two test-only adaptations to `@x402/extensions` 2.29: `verifySIWxSignature` renamed its result fields (`valid` → `isValid`, `address` → `payer`) and `createSIWxPayload` now requires the response URL and asserts the challenge's domain/uri are bound to its origin. No new spender, no new key custody, no Haven-signed authority, no route, budget-check or settlement-timing change; the bridge still signs with the delegate EOA's own key and the tests only assert the bytes it already emits. Perimeter unchanged.
