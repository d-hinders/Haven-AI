- **#4552** — evidence and guidance only: the merchant's own reason for
  refusing a paid retry is now parsed into a code, recorded on the
  reconciliation event, and echoed on the hosted report. No custody, signing,
  spend authority, allowance, budget or refusal semantics change; nothing moves
  funds, and the handoff stays `haven_sweep_delegate` for every reason.
  What changed:
  - `packages/sdk/src/merchant-completion.ts`: one TOTAL parser,
    `merchantReportedError(body, headers?)`, returns a merchant-reported reason
    code or `null`. It accepts only a JSON object whose `error` is a string
    matching `^[a-z0-9_]{1,64}$` (the longest code in @x402/core and evm 2.29
    is 63 characters), read from the UNTRUNCATED body — up to 4096 characters
    on the report path, the SDK's captured body on the retry paths — and then
    falls back to `PAYMENT-RESPONSE.errorReason` and `PAYMENT-REQUIRED.error`,
    both base64 JSON, both under the same regex. Every failure path (non-JSON,
    a body cut at the snippet limit, the JSON literal `null`, a top-level
    string or array, a non-string `error`, free text in `error`, an empty body,
    an undecodable header) returns `null` and never throws. Totality is the
    load-bearing property: the parser runs inside `recordRetryRejected`'s
    swallowing `try`, where a throw would silently drop the stranded-funds
    event.
  - `packages/sdk/src/merchant-completion.ts`: both writers record
    `details.merchant_reported_error` — the code, or `null`, never absent.
    `recordRetryRejected` sets it AFTER the `...input.details` spread, so a
    caller cannot override it, and passes the merchant headers it already
    holds. `reportMerchantOutcome` parses the reported body (the report path
    holds no merchant headers; accepting them would be a tool-contract change)
    and returns the value as the optional `merchantReportedError` on
    `X402MerchantOutcomeReport`. `retry_body` is byte-equal to before.
  - `packages/mcp-server/src/tools/plain-http-x402.ts`: `haven_report_x402_outcome`
    echoes the SDK's parse result as `merchant_reported_error` on a rejected
    outcome only, and its `reason` says the value is the merchant's own claim,
    not something Haven verified. The MCP server never parses the body itself.
    The echo is the parse result, not a read-back: when the event was already
    resolved the backend stores nothing new yet still answers 202.
  - `packages/mcp-server/src/tools/contracts.ts`,
    `packages/mcp-server/src/tools/state-direct-recovery.ts`,
    `packages/mcp-server/src/server.ts`, `packages/sdk/src/skill-content.ts`,
    `packages/frontend/src/lib/agent-skill-bundle.ts` and
    `packages/sdk/README.md`: the report instructions now ask the agent to pass
    the merchant's body on a rejection — the only route by which the reason
    reaches Haven on the plain-HTTP path. The description payload stays under
    its shrink-only cap (31,803 / 31,812 UTF-8 bytes) by trimming inside the
    same description.
  Authority and custody argument: the new value is merchant-claimed data
  written into an open JSONB `details` field that no backend query selects, and
  echoed back to the agent that reported it. It is deliberately named apart
  from the Haven-observed `MerchantTimeoutError.merchantErrorCode`, and it
  changes no amount, recipient, status, settlement decision or next step. The
  parser reads untrusted merchant input and can only produce a bounded
  snake_case token or `null`; it cannot throw, so it cannot suppress the
  stranded-funds event it accompanies. No signing path, key material, delegate
  balance, budget cap, allowance or refusal code is touched. Perimeter
  unchanged.
