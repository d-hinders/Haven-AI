- **#4577** — read-side naming only: the purchase correlation key's parent
  value is named for what it holds on every surface. #4534 stored a fee's parent
  as the purchase's `machine_payment_evidence` row id, but exposed it as
  `parent_payment_id` / `parentPaymentId` beside a `payment_id` that is a
  **payment-intent** id, so a join on the two names found nothing. The owner
  decision (2026-10-30) is option (b): name the field for what it holds, add
  additively on the wire, and **do not change what is stored**.
  What changed:
  - `packages/backend/src/modules/mpp/evidence.ts`: `mapEvidence` emits
    `parent_receipt_id` with the same value it already emits as
    `parent_payment_id`, on the receipts list and the evidence POST response
    alike. `parent_payment_id` stays as a deprecated alias.
  - `packages/backend/src/openapi/spec.ts`: `MachinePaymentReceipt` declares
    `parent_receipt_id` (nullable uuid, described as the parent purchase
    receipt's `id`) and marks `parent_payment_id` `deprecated: true` with a
    description saying it holds a receipt id, not a payment id.
    `packages/core/src/api-types.ts` is regenerated; `check:api-types` is green.
  - `packages/sdk/src/types.ts` / `payment-mappers.ts`: `parentReceiptId` (raw
    `parent_receipt_id`) is added, mapped only when the raw key is present, in
    block form so `lint:vocabulary` sees it. `parentPaymentId` keeps mapping,
    now `@deprecated`. `scripts/ci/vocabulary-map.json` declares the new field.
  - `packages/backend/src/modules/accounting/{entry,feed-transaction,receipt-underlag}.ts`:
    the internal field is renamed `parentReceiptRef`, matching `receiptRef`,
    which is what it joins to. No alias — `FeedTransaction` is never sent as a
    whole and neither the Fortnox nor the Accounted connector reads the field.
  - `packages/backend/src/modules/accounting/receipt-underlag.ts`: the underlag
    prints `Parent receipt <id>` / `Parent receipt n/a` instead of
    `Parent payment`, and a protocol underlag gains `Receipt ref <its own
    evidence id>` so a fee's document and its purchase's document match by eye.
    A direct-payment underlag omits `Receipt ref`, because on that branch
    `receiptRef` is the intent id `Payment id` already prints.
  Authority and custody argument: nothing signs, moves, authorises or refuses
  differently. The stored column `machine_payment_evidence.parent_payment_id`
  is unchanged — **no migration** — and the value written by
  `recordPurchaseGroup` / `backfillPurchaseGroupParent` is byte-identical to
  before. The change adds one wire key that duplicates an existing one, renames
  three internal TypeScript fields with no external reader, and relabels two
  lines on a PDF. No amount, recipient, status, settlement decision, budget cap,
  allowance, delegation or refusal code is touched; no key material, delegate
  balance or signing path is read or written. The perimeter is unchanged.
  Mutation-tested: the new real-DB join test in
  `modules/accounting/__tests__/purchase-correlation.db.test.ts` goes red when
  `parent_receipt_id` is removed from `mapEvidence` (verified by removing it and
  re-running: `expected undefined to be null`), and the PDF pin was verified by
  rendering a fixed protocol `ReceiptUnderlagData` through the pre-change and
  post-change renderers — the content-line arrays differ in exactly the two
  intended lines (`Parent payment <id>` → `Parent receipt <id>`, plus
  `Receipt ref    <id>`).
  Accepted risk, stated in the PR: Accounted's idempotency key comes from
  `paymentId`, and re-filing a document with different bytes ends in a terminal
  `IDEMPOTENCY_KEY_REUSE` skip. A grouped row whose first upload reached
  Accounted but which is retried after this deploy re-renders with the two new
  lines and takes that skip. #4532, #4533 and #4534 accepted the same class;
  rows already `pushed` are final and are never re-rendered.
  Perimeter unchanged.
