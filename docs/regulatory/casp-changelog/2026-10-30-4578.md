- **#4578** — the accounting feed's transaction-kind classifier gains a rung so a settled **direct payment** (`haven_send`, the delegation-redemption rail behind `POST /payments`) classifies as `transfer` instead of `unknown`, and its `Description` names the counterparty's canonical address (`0x1517…799a (transfer)`) instead of `Unknown merchant (unclassified)`. Before this, the `payment_intents` branch of `ENTRY_SOURCE_SQL` (`modules/accounting/entry.ts`) emitted `NULL` for `resource_url`, `delivery_reference` and `merchant_receipt_json`, and `mcp_call_context.toolName` is written only by `x402/delegation-authorize.ts`, so every rung of `deriveTransactionKind` (`modules/accounting/transaction-kind.ts`) fell through to `{ kind: 'unknown', basis: 'none' }`. The change is additive and read-side: `TransactionKindSignals` gains an **optional** `directPayment` signal with a new `TransactionKindBasis` value `rail`; the direct branch of `ENTRY_SOURCE_SQL` emits it as the typed literal `TRUE::BOOLEAN` and the evidence branch as `FALSE::BOOLEAN` so the `UNION ALL` still unifies; the rung sits after rung 1 (`direction`) and before every other rung, whose order and outcome are unchanged; and `toAccountingEntry` passes the counterparty's canonical address as the description label for a direct payment only. **No migration, no schema change, no new column.** **Authority and custody are untouched:** the signal is a literal the SQL branch writes, never an intent column, so no agent-written metadata can set it and "an agent cannot set the kind" still holds — the classifier reads only Haven-held facts and no route accepts a kind. `counterparty.name` stays `null`, so Fortnox's booked supplier (`fortnox-connector.ts:121`) and the underlag's `Counterparty` line are unchanged; the underlag's label rule stays on `resourceUrl == null` (`receipt-underlag.ts:176`) and the new signal is not carried into `FeedTransaction`. The feed remains non-asserting and moves no money: it classifies a document it already produces, and no payment, settlement, amount, budget or authorization fact changes. Mutation-proven on real Postgres (`direct-payment-feed.db.test.ts`): a confirmed direct payment's rendered underlag contains `Transaction    transfer` and the exact `Description    0x1517…799a \(transfer\)` line, and the suite goes red with the signal reverted to `FALSE` and again with the address label reverted to `null`; the x402 CONTROL asserts the evidence branch's `FALSE` literal keeps a protocol payment's kind unchanged. Pure unit cases pin the three acceptance cases — the signal → `transfer`/`rail`, all signals null without it → still `unknown`/`none`, and direction `in` with it → still `refund` — and `transaction-kind.test.ts`, `entry.test.ts` and `receipt-underlag.test.ts` (including #4546's protocol CONTROL test) keep their expectations. Accepted risk, stated in the PR: the Accounted idempotency key is `uuid5(paymentId)`, so a direct payment whose upload reached Accounted before the deploy but whose row is still `failed` re-renders with different bytes and takes a terminal `IDEMPOTENCY_KEY_REUSE` skip (`accounted-connector.ts:243`; known and handled, `docs/product/accounting-connections.md:176-180`); rows already `pushed` are final and never re-render. Perimeter unchanged.
