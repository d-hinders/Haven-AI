- **#4654 — a malformed env private key is refused before a signer constructor
  sees it, so it can no longer be echoed into the backend logs** — parsing and
  error text only; the same signers stay in the same files and no authority
  moves.
  - **What changed:** one pure helper,
    `packages/backend/src/infra/chain/env-private-key.ts`
    (`parseEnvPrivateKey(name, raw)`), trims the value, accepts exactly
    `^(0x)?[0-9a-fA-F]{64}$` — the set ethers accepts today, so a deployed key
    without `0x` keeps working — and returns it `0x`-prefixed. Anything else
    throws an `Error` that names the variable and carries no part of the value
    and no `cause`. Quotes are refused, not stripped.
  - **Why it was needed:** ethers v6 echoes an unparseable input in
    `invalid BytesLike value (… value="<the input>")` and sets an enumerable
    `value` field. `infra/relayer-balance-monitor.ts` logs `err.message` and
    `infra/http-error-handler.ts` logs the whole error, whose pino `err`
    serializer emits both `message` and `value`. On 2026-11-04 that wrote a
    production `RELAYER_PRIVATE_KEY` into the backend logs during the #4487
    rotation, and the key had to be treated as exposed and rotated again.
  - **Sites, unchanged in location:** `infra/relayer.ts` (`getRelayer`),
    `infra/chain/x402-binding-signer.ts` (both the signing path and the
    address-derivation path), `rails/sweep.ts`, and
    `modules/passport/receipt.ts` (both `signReceipt` and
    `receiptIssuerAddress`). Each calls the helper on its key immediately before
    its existing constructor. No constructor moved, so the non-custody signer
    allow-list (`__tests__/non-custody.invariants.test.ts:67-70`) is untouched
    and passes unedited, as does
    `infra/chain/__tests__/x402-binding-signer-import-graph.test.ts` — the
    helper imports nothing at all, so it cannot reach `config.ts` or viem.
  - **Authority:** unchanged. The same keys sign the same messages and
    transactions in the same files; the helper validates a string and constructs
    nothing. No new signer, no new route, no change to who can sign, what is
    signed, or any payment flow. The one behavioural lever is intended and
    recorded on the issue: a deployment whose key fails today only because of
    surrounding whitespace starts signing on deploy.
  - **Per-chain isolation preserved:** a whitespace-only
    `RELAYER_PRIVATE_KEY_<chainId>` is truthy, so `config.ts:576` still selects
    it and the refusal names that variable. It errors rather than falling back
    to the global key, so per-chain relayer isolation (#640) cannot collapse
    silently. The `||` in `config.ts` is unchanged.
  - **Fail-closed paths preserved:** `receiptIssuerAddress()` and the
    `x402-binding-signer.ts` address derivation still return `null` for a bad
    key, with the same value-free warning, and never throw.
  - **Mutation-tested:** the "no value in errors" cells were proven with a
    `prove-red` run that bypasses the helper (passing the raw value straight to
    the constructor); the cells listed in the PR body each went red. The
    monitor case runs the real `getRelayer` with only the spend summary stubbed,
    so it exercises the constructor path the incident took. Perimeter unchanged.
