- **#4521** — the Igdrasil connector late-attaches a merchant receipt that
  arrives after the push, as Fortnox (#956) and Accounted (#3918) already do.
  Slice of the Igdrasil epic #2875. No signing, custody, authorization or
  payment behaviour moves.
  What changed:
  - `packages/backend/src/modules/accounting/igdrasil-connector.ts`:
    `lateAttachIgdrasilMerchantReceipt(userId, paymentId, receipt)`. It returns
    before any request unless the payment's Igdrasil underlag sync row is
    `pushed` and no merchant-invoice row is recorded, the deployment has the
    Igdrasil app configured, and the connection has a company. It then reads
    the access token through the generic row-locked refresh, so the rotating
    refresh token has one path; an expired token makes that refresh request.
    It uploads the receipt with the existing `igdrasilUploadDocument`
    (`POST …/uploads`, sha256-proven) and records `igdrasil:document:<id>`
    with `recordMerchantInvoiceSync`. A failure in the token read, the receipt
    fetch, the upload or the record is caught and written as a note on the
    pushed row via `markPushed`. A failure in the guard reads before that is
    not caught there; the capture route's `.catch(() => {})` swallows it.
  - `packages/backend/src/modules/mpp/merchant-receipt.ts`:
    `handleMerchantReceiptCapture` fires the Igdrasil call fire-and-forget with
    `.catch(() => {})` after a stored capture, next to the two existing calls,
    with the same arguments.

  Why the perimeter is unaffected. The capture handler's own behaviour is
  byte-identical: the receipt row is written first, the response is decided
  before any destination runs, and the new call can neither delay nor fail it
  (its rejection is swallowed, proven by a route test that makes it reject and
  still sees 201 and the other two calls). The new function reads sync rows
  and the connection. It writes `accounting_feed_syncs` (the merchant-invoice
  row or the underlag row's note), and, through the existing generic refresh,
  `accounting_connections` (the refreshed secrets, or the
  `needs_reauthorisation` flag on a refused grant). It touches no payment
  intent, evidence row, delegation, allowance, relayer, signer or chain call.
  Its outbound requests are the token refresh, the merchant receipt URL fetch
  through the existing SSRF guard when the receipt names a URL, and the upload
  endpoint the connector already uses. The bytes it sends are the merchant's
  own receipt, which the agent already reported.

  Tests: `modules/accounting/__tests__/igdrasil-late-attach.db.test.ts` on the
  real database (attach once, a repeat makes no request, no request for a
  payment not pushed to Igdrasil or not `pushed` even with an expired token,
  no request without a company or without a grant, a refused upload resolves
  with a note); `routes/__tests__/machine-payments.test.ts` (all three
  destinations fire with the same receipt; a rejecting Igdrasil attach leaves
  the 201 and the other two calls intact, with no unhandled rejection).
  Mutation cells in the PR body.

  Perimeter unchanged.
