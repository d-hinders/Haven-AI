- **#4721** — the agent can read its own Agent Passport reference. Slice 3 of
  epic #4718.
  What changed:
  - `GET /machine-payments/agent` (agent-authenticated) gains `passport`:
    `{ attestation_uid, chain_id, verify_url? }` for an anchored passport, and
    `null` otherwise. The value comes from the existing
    `passportReferenceFor`, which is bounded to 1500 ms and never throws.
  - The route's four reads (delegate-account derivation, sub-budget grants,
    supersession, passport) now run concurrently, so the lookup adds no
    sequential time to this read on the paid path.
  - `@haven_ai/sdk` maps the field onto `HavenAgent.passport`, so
    `haven_get_agent` carries it in both MCP servers. The skill text tells
    agents to hand `attestationUid` + `chainId` to a merchant that asks, never
    to present `verifyUrl` as proof, and never to call a passport "verified".
  - The settle response's existing `passport` field is now typed in OpenAPI.

  Why the perimeter is unaffected. This is a read. The agent learns a public
  on-chain attestation UID that its owner's dashboard could already read, and
  that the public verifier serves by address. Nothing is signed, granted,
  moved or queued. The value is metadata, never authority: a lookup failure
  reads `null`, and no payment path consults it. No key, delegation, caveat,
  budget or recipient pin changes.

  Tests:
  - `routes/__tests__/machine-payments.test.ts`: an anchored reference is read
    for this agent only; a pending or failed passport reads `null`; a failed
    lookup still answers 200; and the passport lookup is issued concurrently
    with the supersession read.
  - `packages/sdk/src/agent-info.test.ts`: the mapping, including `null` for
    an older backend and for every malformed body.

  Perimeter unchanged.
