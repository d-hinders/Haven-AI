- **#4722** — the agent's passport reference rides an x402 payment, but only
  inside a `haven-passport` extension the merchant's own 402 advertised. Slice 4
  of epic #4718. Owner decision 2026-11-06 on the issue.
  What changed:
  - `packages/sdk/src/x402.ts` adds `withHavenPassportExtension`, the one merge
    rule both paths use. It appends `attestation_uid` + `chain_id` only to an
    advertised plain-object value (inside its `info` when present), never
    overwrites an existing field, and returns the extensions unchanged in every
    other case. `x402V2PaymentEnvelope` takes the passport as an optional fourth
    argument; a three-argument call, the signer's, is byte-identical.
  - `packages/sdk/src/x402-funding-leg.ts` reads the agent's reference
    (`GET /machine-payments/agent`) only when the 402 advertises the key, bounded
    to 1500 ms, and only before a fresh authorization is minted. It reads nothing
    on an executed replay or in `resumeAuthorizedX402`, so the read never widens
    a window in which the delegate already holds funds.
  - `packages/backend/src/modules/x402/settle.ts` computes the reference before
    assembling the erc7710 header, still before the intent is marked submitted
    (the #976 ordering rule), and applies the same rule to the stored
    challenge's extensions.

  Why the perimeter is unaffected. x402 extensions sit outside the signed
  EIP-3009 authorization (`authorization` + `signature`) and outside the erc7710
  `payload` (`delegationManager`, `delegator`, `permissionContext`). The added
  fields therefore cannot change what is paid, to whom, from which budget, or
  under which caveats. No key, delegation, allowance, caveat, budget, signer or
  relayer behaviour changes. The fields are agent-supplied metadata a merchant
  must resolve against a Haven verifier it pins, and the docs say so. A merchant
  that did not advertise the key receives a byte-identical envelope, which is
  what protects live payments. The signer (`packages/signer`) is untouched.

  `casp-risk-guardrails.md`'s passport note, which said the reference is never
  placed in the `X-PAYMENT` payload, is rewritten in this PR to the new rule.

  Tests:
  - `packages/sdk/src/x402-haven-passport.test.ts`: the merge rule's case table,
    including byte identity for `true`, a string, an array, `null`,
    `{info:null}`, `{info:[]}`, and existing `chain_id` / `attestation_uid` at
    both levels; the signer's three-argument envelope; zero reads when the key
    is not advertised or the challenge is v1; null on a failed read and at the
    1500 ms bound; the fresh mint receives the passport and an executed replay
    neither reads nor passes one.
  - `packages/backend/src/routes/__tests__/x402-delegation.test.ts`: the header
    key-set characterization and the "OUT of the header" guard are scoped to a
    merchant that did not advertise the key and run with an anchored passport;
    new cases cover byte identity for other extensions, the fields added inside
    `info`, no passport, no overwrite, and the lookup ordered before the
    submitted UPDATE.
