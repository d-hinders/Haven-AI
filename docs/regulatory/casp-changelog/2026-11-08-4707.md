- **#4707** — the first agent payment gets its own dashboard card. The
  "You're set up" line moves out of "Needs attention" into a card fed by a new
  read, `GET /dashboard/first-agent-payment`, backed by
  `FIND_FIRST_AGENT_PAYMENT_SQL` in `infra/repositories/dashboard.ts` (the file
  that puts this change on the money-path perimeter). **Read-only: no new
  authority, custody, route that moves money, or address handling.** The
  statement is a per-user `SELECT … LIMIT 1` over `payment_intents` joined
  through `DELEGATION_RAIL_JOIN`; it writes nothing, signs nothing, and grants
  nothing. It is deliberately STRICTER than the existing boolean
  `HAS_FIRST_AGENT_PAYMENT_SQL`, which is unchanged: the card claims a real
  event, so a row qualifies only when the merchant leg is proven — a recorded,
  on-chain-verified `machine_metadata.merchant_settlement_tx_hash`, or a
  `machine_payment_evidence` row recording the merchant's answer — using the
  same facts `isFundedX402AwaitingMerchantLeg` reads. A confirmed EIP-3009 row
  whose merchant has not pulled yet is excluded, as is a funded-but-unsettled
  row (an open `merchant_retry_rejected_after_payment` event), a retired-rail
  agent's row, and another user's row. The counterparty is
  `COALESCE(merchant_address, x402_merchant_address, to_address)` resolved to a
  contact name, else a receipt-merchant name, else the x402 resource HOST; the
  raw address is a lookup key only and never reaches the wire (#3810 rule 4).
  The client renders nothing for a `null` row, a loading state, an error or a
  404 from an older backend — no card, no success copy, no Peak, no marker
  written — and stops polling once a row arrives. Peak is a per-user,
  per-device browser marker, never for a payment more than seven days old
  (owner decision 1 on #4701), and the card is a `role="status"` region exactly
  when it plays. The dismissal keeps the line's existing key
  (`haven-onboarding-complete-dismissed:<userId>`), so an owner who dismissed
  the line stays dismissed; `attention_dismissals` is untouched (its `CHECK`
  and `DISMISSIBLE_ATTENTION_KINDS` would need a migration). No migration: the
  real-DB test's `EXPLAIN` shows a `Limit` over an anti-join that reaches
  `idx_agents_user_id` and `idx_payment_intents_agent_id` — no new index is
  needed. Mutation-proven: 15 real-DB cells over the qualifying predicate
  (earliest-by-`confirmed_at`, pending/failed/no-`tx_hash`, funded-but-unsettled
  open vs resolved, EIP-3009 unproven vs settlement-hash vs merchant-answer vs
  the funding-confirm base row, erc7710, direct, retired rail, tenant scope,
  counterparty fallback) plus the client's unsettled → settled walk, the
  sub-cent token-amount rule, the seven-day Peak bound and the reduced-motion
  case. Perimeter unchanged.
