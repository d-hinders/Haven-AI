- **#4754**: the merchant payment header names now follow the payload's
  `x402Version`. Owner decision 2026-11-09 on the issue; for EIP-3009 it
  supersedes the 2026-08-31 decision to always send both names.

  What changed:
  - `packages/sdk/src/x402.ts`, `x402PaymentHeaderNamesFor`. An x402 v2 payload
    is sent under `PAYMENT-SIGNATURE` alone, on either scheme. A v1 payload, or
    a header the rule cannot read, is still sent under both `PAYMENT-SIGNATURE`
    and `X-PAYMENT`. Before this, EIP-3009 always got both names; erc7710
    already got the v2 name alone (#2341).
  - The reason for the change: the #2361 extensions echo had grown EIP-3009
    headers to 5–6.5 KB. On 2026-11-09 a doubled 4,969-byte header got HTTP 431
    from a live merchant after the funding leg had confirmed, which left the
    funded amount on the delegate.
  - `x402PaymentHeaderSchemeOf` (new, same file) reads the settlement scheme
    from the payload's `accepted` entry.
    - `packages/sdk/src/merchant-completion.ts` used to infer EIP-3009 from
      "two header names", at two sites: the #3427 tax-declaration gate and the
      paid-delivery redirect refusal. Both now use `x402PaymentHeaderSchemeOf`.
    - Without this, every v2 EIP-3009 retry would have been read as erc7710.
      The buyer tax declaration would have been dropped, and the agent would
      have been told there is no funding leg to sweep on a payment whose
      funding leg confirmed.
    - A payload with no readable `accepted` (every v1 payload, or an unreadable
      header) still reads as EIP-3009, as before.
  - Agent guidance now says "set exactly the headers in `retry_headers`", or
    `PAYMENT-SIGNATURE` with `X-PAYMENT` added only for an x402 v1 challenge.
    It was updated in:
    - the hosted server instructions;
    - the `haven_pay_x402_quote` description;
    - the post-funding recovery reasons;
    - the SDK tool descriptions;
    - both published skill copies;
    - the signer description and README;
    - the SDK README samples.
  - The `expected_amount` stop reason names the token symbol instead of the
    asset contract address, in both the hosted and the local MCP. This is a
    copy change only; the stop decision is unchanged.

  Why the perimeter is unaffected:
  - Only the header **name** under which the same signed value travels
    changes. The value itself is unchanged: the same EIP-3009 authorization or
    erc7710 delegation, signed by the same local delegate key.
  - Nothing changes in what is paid, to whom, from which budget or under which
    caveats. No key, delegation, allowance, caveat, budget, signing, relayer or
    backend behaviour changes. The signer's `retry_headers` output changes the
    same way, since it is built from the same rule; what the signer signs does
    not.
  - The stored evidence field `paymentProofHeaderName` now records
    `PAYMENT-SIGNATURE` for a v2 EIP-3009 payment, because it records what was
    sent. The backend stores it as free text and never compares it.

  Accepted residual, named in the owner decision: a merchant that issues a v2
  challenge but reads only `X-PAYMENT` now fails after funding. That failure is
  recoverable by sweep, as the 431 it replaces was. No such merchant has been
  observed; Anchor and CoinGecko accepted the v2 name alone in live settlements.

  Tests:
  - `packages/sdk/src/x402-erc7710-header-size.test.ts`:
    - the version table: 2, 3, a v2 payload without `accepted`, 1, missing,
      string and null;
    - the erc7710 no-version case;
    - a real-envelope v2 EIP-3009 header carrying a bazaar echo of at least
      5 KB is sent once;
    - `x402PaymentHeaderSchemeOf` for erc7710, v2 EIP-3009, v1 and unreadable
      input.
  - The tax-declaration and redirect-refusal tests, which use v2 EIP-3009
    payloads, pass unchanged. They are the decoupling's guard.
  - Retry-header assertions in the SDK, signer and local-MCP tests are
    re-scoped to the version rule. The v1 cases keep both names.
  - The copy fix is pinned in `plain-http-x402.test.ts` and
    `packages/mcp/src/tools.test.ts`.

  Mutation cells in the PR body.

  Perimeter unchanged.
