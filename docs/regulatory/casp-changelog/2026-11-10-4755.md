- **#4755 — the Anchor calldata-decode catalog row now declares its call
  shape** — changes what a guided purchase CAN pay for (a row that previously
  suggested a bodiless GET now suggests the POST the merchant answers), not who
  can pay and not how much authority a call carries. Money-path by file
  (`packages/backend/src/db/migrations/**`).
  - **Change:** migration 125 is a data-only `UPDATE` of one
    `merchant_catalog` row, `WHERE resource_url =
    'https://api.anchor-x402.com/v1/decode/calldata'`. It sets
    `http_method = 'POST'`, `body_type = 'json'`, `body_example` to the
    merchant's own example from its 402 (verbatim:
    `{"chain":"ethereum","calldata_hex":"0xa9059cbb…"}`), and the description
    to "Decode raw EVM calldata into a named function call with typed
    parameters (4-byte selector lookup via openchain.xyz). Pay per decode."
    Migration 035 seeded the row with all three call-semantics columns NULL
    (they were added by 108, which pinned only the sibling token-price row), so
    the hosted `haven_discover_tools` turned it into `suggested_arguments
    { url }` only and an agent that followed it quoted and paid a bodiless GET.
    The merchant's OpenAPI has only `post` on that path, and its 402 to an
    unpaid POST carries `extensions.bazaar.info.input = {type: http, method:
    POST, bodyType: json, body: {…}}`; the unpaid GET's 402 carries no `input`
    and calls itself a "GET wrapper".
  - **`chain: "ethereum"` is the merchant's decoder selector** (an enum of
    `ethereum|solana`), not the settlement network. It is copied verbatim and
    must not be "corrected" to `base`; the row's `network` stays
    `eip155:8453`.
  - **`updated_at` is left alone**, as 108 does. It only affects the order in
    which `refreshCatalog` probes rows (`merchant-catalog.ts:574`).
  - **Nothing overwrites the update:** the refresh probe writes
    `http_method = COALESCE($8, http_method)` (`merchant-catalog.ts:626`) and
    `$8` is only set from a structured `resource.method`, which this merchant's
    402 does not carry (`:526-538`); bazaar discovery inserts with `ON CONFLICT
    DO NOTHING` and never updates (`catalog-discovery.ts:202-205`,
    `:326-331`); there is no admin edit path.
  - **`down()`** sets the three columns back to NULL and restores 035's
    description, matching only a row that still carries every value `up()`
    wrote — the same "only the rows this migration changed" rule 102's `down()`
    follows.
  - **Perimeter:** no authority surface moves. The amount, asset, network,
    `payTo` and scheme still come exclusively from the LIVE merchant 402
    (`accepts[]`), never from the catalog row or the new columns. The change
    adds no budget pin, no caveat, no signing input and no fund-movement path;
    it only tells the guided path which HTTP call the merchant can answer.
  - **Mutation-tested** (`packages/backend/src/db/migrations/__tests__/125_anchor_calldata_call_semantics.test.ts`,
    real Postgres, no mocks):
    - the four values after `up()`, with the row's identity and money fields
      unchanged;
    - the sibling Anchor token-price row (seeded with its 108 values) is
      unchanged field-by-field INCLUDING `updated_at` — dropping the `WHERE`
      fails this;
    - a second `up()` changes nothing at all, `updated_at` included;
    - `down()` restores the NULLs and 035's description and leaves the sibling
      row alone;
    - `down()` leaves a row someone else edited after `up()` untouched —
      dropping the value predicates from `down()`'s `WHERE` fails this.
  - The generic mapping from `body_example` to `suggested_arguments` is already
    covered by `packages/mcp-server/src/tools/catalog-purchase.test.ts:182-242`
    (#3769); no new MCP test is needed.
  - **Verdict:** Perimeter unchanged — a data-only catalog-row correction on
    the guided path, no new spend authority, no new fund-movement path.
