- **#4765** — `payment_intents.machine_metadata` gets one reader
  (`domain/machine-metadata.ts`). Fifteen parse sites and eight
  `settlement_scheme` reads across twelve `modules/` files now go through it.
  Behaviour is unchanged: every call site keeps the value it read before, cell
  by cell.

  What changed:
  - `domain/machine-metadata.ts` holds four parsers — `machineMetadataOrNull`,
    `machineMetadataObjectOrEmpty`, `machineMetadataRecord`,
    `machineMetadataObject` — and three scheme readers — `settlementSchemeOf`,
    `settlementSchemeOfStrict`, `settlementSchemeOfNarrowed`. They are NOT one
    parser with options: today's readers disagree on what an unusable value
    becomes (`null`, `{}`, or a throw at the call site), and the issue forbids
    silently unifying them.
  - `mpp/budget-precheck.ts`, `mpp/evidence.ts`, `payments/agent-payment-status.ts`,
    `x402/eip3009-receipt-settlement.ts`, `x402/eip3009-settlement-evidence.ts`,
    `x402/helpers.ts`, `x402/intent-by-key.ts`, `x402/merchant-call-context.ts`,
    `x402/settle.ts`, `x402/settlement-observed.ts` and `x402/sign-context.ts`
    each lose their private parse and call the reader.
  - `mpp/rail-dispatch.ts`'s `metadataObject` had no callers and is deleted; the
    comment that claimed `payments/agent-payment-status.ts` read it is corrected
    (that file had its own private copy).
  - `x402/intent-by-key.ts` keeps `parseObject` for `prepared_user_op`; only its
    `machine_metadata` read moved.
  - `payments/agent-payment-status.ts`'s `narrowSettlementScheme` stays: it
    narrows an already-read wire value, not the column, and must not gain the
    `{child, budget}` fallback the narrowed variant carries.

  Why the perimeter is unaffected:
  - Nothing about who may sign, move or authorise changes. `settlement_scheme`
    still selects erc7710 vs the EIP-3009 bridge exactly as before; the
    characterization table pins every call site's read for sixteen input shapes,
    including the three cells that throw today (the two inline parses in
    `mpp/evidence.ts` and `eip3009-receipt-settlement.ts`'s `metadataOf` at its
    `:434` call site, all on the JSON text `null`).
  - The reader is a pure parser: no framework, no `pg`, no chain SDK, no
    `modules|infra|http|rails` import (`domain-stays-pure`). It moved the
    decision out of `modules/x402/**` and `modules/mpp/**` (both listed whole)
    into `domain/`, so the glob follows it in the same PR — the #1892
    accident-of-location rule. It joins `.github/money-path-globs.json`,
    `.github/labeler.yml`, the ship-next perimeter reference and this document's
    `covers:`.

  Tests:
  - `src/__tests__/machine-metadata-reader.characterization.test.ts` is a
    table-driven characterization: sixteen input shapes × eighteen call-site
    columns, each cell the value the call site reads or the error it throws. It
    was committed first, green on its own, with `export` keywords as its only
    non-test change; the same table then ran against the reader and passed with
    the same expected column.
  - The backend suite (570 files, 7190 tests) and `tsc --noEmit` are green.

  Mutation cells in the PR body: the shared scheme reader returning `null` for
  `'erc7710'`; the `{child, budget}` fallback removed from the narrowed variant;
  and the reader `settle.ts` uses returning `null` for `'erc7710'` — each turns
  the characterization table red.
