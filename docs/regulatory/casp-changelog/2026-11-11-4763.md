- **#4763** — the SDK's one runtime import cycle is broken, and rule 7 of
  `docs/architecture/10-module-boundaries.md` now covers all thirteen packages
  instead of two. `parseMerchantSettlement` and `parseProtocolReceiptHeader`
  move from `packages/sdk/src/merchant-completion.ts` into
  `packages/sdk/src/merchant-answer.ts`; `merchant-completion.ts` imports them
  from there and re-exports both, so its surface is unchanged. Behaviour is
  unchanged: the two functions are moved verbatim, and the SDK's existing
  suite (71 files, 1162 tests) passes unedited.

  What changed:
  - The cycle was two VALUE imports pointing at each other:
    `merchant-answer.ts` imported `parseMerchantSettlement` from
    `merchant-completion.ts`, and `merchant-completion.ts` imported
    `decidePostFundingMerchantAnswer` from `merchant-answer.ts`. Moving only
    the first would have kept it (`answer → leaf → completion → answer`), so
    both parsers moved together into `merchant-answer.ts` — no new file, so
    the money-path perimeter gains no entry and loses none.
  - `packages/sdk/src/index.ts` re-exports `parseMerchantSettlement` from
    `merchant-answer.js` instead of `merchant-completion.js`. Same name, same
    signature, same entry point.
  - `scripts/dep-cycles.mjs` (new, `npm run lint:dep-cycles`) runs a one-rule
    `no-circular` pass over the eleven packages `scripts/dep-lint.mjs` does not
    scan, with `tsPreCompilationDeps: false` — the owner's 2026-11-10 decision
    that only RUNTIME cycles are enforced outside backend and core. It resolves
    each package's own `tsconfig.json` (so the frontend's `@/` alias is a real
    edge) and reads `.tsx` as well as `.ts`.
  - CI: a new `packages_checks` job gated on a new `packages` classifier flag,
    which every `packages/*` arm sets. Before this, `npm run lint:deps` ran only
    in `backend_checks`, so a PR touching only `frontend`, `ui`, `ops`,
    `connect`, `mcp`, `mcp-server`, `signer`, `cli`, `demo-merchant-mcp` or
    `qa-agent` never ran any cycle check at all.

  Why the perimeter is unaffected:
  - Nothing about who may sign, move or authorise changes. The two parsers are
    pure: `parseProtocolReceiptHeader` decodes a base64-or-JSON receipt header,
    `parseMerchantSettlement` reads the transaction out of it under the three
    spellings the protocol uses. Neither reads a key, signs, or decides
    anything; the decision they feed (`decidePostFundingMerchantAnswer`) is
    untouched, and the backend still verifies every reported hash on-chain
    before recording it.
  - Both files were already on the runtime money-path list
    (`packages/sdk/src/merchant-answer.ts` since #4120, `merchant-completion.ts`
    since #4122), and both stay on it. No file is created, so
    `.github/money-path-globs.json`, `.github/labeler.yml` and the ship-next
    perimeter reference need no edit — the perimeter neither shrinks nor grows.
  - The new lint is a CI control surface, not runtime code: it reads the import
    graph and refuses a cycle. It is not on either money-path list, and it
    cannot move money.

  Tests:
  - `scripts/dep-cycles.test.mjs` proves coverage rather than assuming it: the
    scan reads at least one file from every one of the eleven packages, reads
    `.tsx`, and resolves at least one `@/` alias edge in the frontend.
  - Two live-scan tests pin the boundary of the owner's decision: a planted
    two-file VALUE-import cycle in `packages/cli/src` is reported (and is still
    reported with a `dep-lint-exempt` comment on the import — `no-circular` is
    unwaivable), while a planted TYPE-ONLY two-file cycle is not.
  - Mutation, run with `prove-red`: with the parser move reverted the pass exits
    1 and names `packages/sdk/src/merchant-answer.ts` and
    `packages/sdk/src/merchant-completion.ts`; with it applied the pass is
    green. The SDK suite and `tsc --noEmit` are green.

  Perimeter unchanged.
