- **#4817** — the delegation rail's two submit functions now say "sent, outcome
  unknown" for every post-send failure, with the operation hash, and keep
  "failed" for the two known outcomes only. No route's answer is rewritten in
  this slice; three behaviours change through branches that already test for
  the typed error.

  What changed:
  - `packages/backend/src/rails/delegation-rail.ts`. `submitRedemption` used to
    treat every throw from `client.sendUserOperation` as "it never entered the
    mempool". That holds for an explicit bundler rejection and not for a lost
    answer. The throw is now classified: a JSON-RPC error the bundler ANSWERED
    with, an HTTP 4xx from the bundler (a revoked or rate-limited key), and a
    failure in the client's prepare step before the `eth_sendUserOperation`
    request was dispatched all stay ordinary pre-send errors; a dispatched
    request whose answer never arrived (a transport timeout, a reset
    connection, a body that is not a JSON-RPC answer, an HTTP 5xx) throws
    `SubmittedUserOpFailedError` with the outcome-unknown variant
    (`receipt_unconfirmed`) and the operation hash.
  - "Dispatched" is decided by the bundler transport, not by an error class:
    the client's prepare step raises the same transport errors the send does,
    so `http(cfg.bundlerUrl, { onFetchRequest })` records the formatted
    operation of every `eth_sendUserOperation` request it hands to `fetch`, and
    a submit compares the record before and after its own send. One rail serves
    one operation — every caller builds a fresh rail per prepare/submit pair —
    so the record holds at most one in-flight send.
  - The hash is computed from the operation the bundler RECEIVED, not from the
    prepared object: every caller of both submit functions passes
    `userOpHash: '0x'` as a placeholder, and the client re-runs its prepare
    step inside `sendUserOperation` (paymaster data is re-fetched), so the
    operation that went out is not necessarily the one that was prepared. The
    hash a caller records must be the one the bundler indexes.
  - `submitCall` had no post-send distinction at all. It gets the same send
    classification; a throw from the receipt wait now throws the typed error
    with the hash the send returned, and included-and-reverted (today a plain
    `Error`) throws the typed error's `included_reverted` variant carrying the
    receipt's `actualGasCost`.
  - No migration: the sponsored-gas ledger's outcome column accepts
    `confirmed`, `included_reverted` and `receipt_unconfirmed` only
    (`packages/backend/src/db/migrations/110_sponsored_userop_gas_events.ts`),
    so a new outcome name would need one. Reusing `receipt_unconfirmed` for a
    lost send answer avoids it.
  - Every statement of the rule now says what is implemented:
    `delegation-rail.ts` (the class doc and both submit bodies),
    `modules/payments/sign-payment.ts` (the sponsored-gas comment and the
    outcome-pending booking comment), `infra/repositories/payment-intents.ts`
    (the booking block), `modules/payments/submission-reconciler.ts` (the gap),
    `modules/payments/sponsored-gas.ts` and `docs/operations/sponsored-gas.md`.
    Migration 110's header is history and stays.

  Why the perimeter is unaffected:
  - No signing, custody or spend-authority code is edited. The rail still holds
    no key: the delegate account is constructed with a watch-only owner that
    refuses to sign, the agent signs the userOpHash client-side, and the
    backend only relays. The change is which ERROR a failure raises, not what
    is submitted, who may submit it, or what the caveat stack enforces.
  - The typed error is strictly narrower than "everything failed": it is raised
    only when the `eth_sendUserOperation` request was dispatched and no answer
    came back. An explicit rejection — the bundler's own JSON-RPC error, an
    HTTP 4xx, a prepare-step failure — still raises the ordinary pre-send error
    the routes already answer `409 close_needs_reprepare` / `502 … failed` for.
    The acceptance criteria pin both directions.
  - The three downstream behaviours that change are the ones the typed error
    already existed for: the sign module books outcome-pending instead of
    `failed` (so a funds-moved payment is no longer recorded as failed
    forever), and the task-budget and sub-budget close submits run their
    on-chain disabled check and answer `closed` or `502
    close_outcome_unconfirmed` instead of `409 close_needs_reprepare`. The five
    `submitCall` callers keep answering `502 … failed` until #4820 and #4821 —
    this slice does not widen scope into them.
  - No new authority, no new route, no new accepted input, no stored value
    changes shape. The hash recorded is the one the bundler received, which is
    what the reconciler already looks up.

  Tests:
  - Characterization first, in its own commit that changes no non-test line:
    `packages/backend/src/rails/__tests__/delegation-rail-submit-outcome.test.ts`
    runs both submit functions through the REAL rail against two loopback
    stand-ins (a chain RPC and a bundler that answers, rejects, hangs, resets
    or returns a non-JSON body per case) and pins today's reading — a lost send
    answer and a receipt-wait throw are ordinary errors, and `submitCall`'s
    included-and-reverted case is a plain `Error`. The cases that must NOT
    change (an `AA25` JSON-RPC rejection, HTTP 429/401, a prepare-step failure)
    are pinned there too, so the change cannot quietly widen the typed error
    over them.
  - After the change the same file asserts the new reading, and the hash
    criterion is answered by the stand-in itself: it hashes the operation it
    RECEIVED, so a hash computed from the prepared object would not match.
  - `packages/backend/src/modules/payments/__tests__/sign-payment-outcome-unknown.db.test.ts`
    is the end-to-end criterion on the real-DB harness: the real `signPayment`,
    the real rail and a never-answering bundler answer `502
    submission_outcome_unknown` with a `user_op_hash`, the row stays
    `submitted` with `submission_outcome: 'unknown'`, and
    `findOutcomePendingIntents` returns it once it is past the minimum age.
  - `packages/backend/src/routes/__tests__/sub-budgets-close-submit.test.ts`
    pins the sub-budget close submit's characterization (`409
    close_needs_reprepare` for an ordinary error) and the two typed-error
    branches (`closed` when the child is disabled on-chain, `502
    close_outcome_unconfirmed` otherwise). The task-budget equivalents already
    existed in `routes/__tests__/task-budgets.test.ts` and are unchanged.
  - Mutation cells are in the PR body: dropping the dispatch comparison makes
    the prepare-step case raise the typed error; treating every transport
    failure as outcome-unknown makes the `AA25`/429/401 cases raise it;
    computing the hash from `prepared.userOpHash` reddens the hash assertion;
    removing the receipt-wait wrap reddens the `submitCall` receipt case.

  Perimeter unchanged.
