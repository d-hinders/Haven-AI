- **#4818** — the agent sign route booked a MINED payment `failed`, and a row
  claimed for submission could be invisible to the reconciler forever. Two
  changes on `POST /payments/:id/sign` and the submission reconciler's intake.
  **No custody or authority boundary moves. This is a booking correction on a
  payment whose operation was already broadcast: what may be signed, by whom,
  and under which caveats is unchanged.**

  What changed:
  - **Nothing after the submit books `failed`.** The submit, the fiat lookup
    and the confirm write shared one `try` in
    `packages/backend/src/modules/payments/sign-payment.ts`, so a throw from
    the confirm write landed in the catch that calls `failSubmittedIntent` —
    for a payment whose transaction hash had already come back, i.e. one that
    may have moved the funds. The route now marks the moment the submit
    returns a hash; a throw after it books outcome-PENDING
    (`bookSubmittedOutcomePending`, the row stays `submitted` with the
    dispatched operation hash and the observed transaction hash recorded in
    `machine_metadata`) and answers the existing outcome-pending body
    (`502`, `error_code: submission_outcome_unknown`, `status: submitted`,
    `user_op_hash`) that the hosted mapper and the SDK already handle. The
    submission reconciler resolves the row from the bundler's receipt.
  - **A missing fiat value never fails a mined payment.**
    `bookConfirmedPayment` (`modules/payments/confirm-booking.ts`) now catches
    a throw from `getFiatValuesForTokenAmount` and books the confirm with null
    fiat values. The helper already mapped a failed quote to nulls; this covers
    the helper itself throwing. The funds already moved — nothing about the
    price capture may decide the payment's fate.
  - **The claim records the operation hash.** `claimIntentForSubmission`
    (`infra/repositories/payment-intents.ts`) copies the row's own
    `sign_hash` — the prepared operation's hash, written by
    `modules/payments/create-payment.ts` and
    `modules/x402/delegation-authorize.ts` — into
    `machine_metadata.user_op_hash` and stamps `submission_claimed: true`
    beside it. A sign request that dies between the claim and the route's
    booking (a deploy, a crash, an abandoned request) therefore leaves a row
    the reconciler can find. The route upgrades the hash to the DISPATCHED one
    (`recordSubmittedUserOpHash`) the moment the submit returns, because #4817
    established the prepared and dispatched hashes can differ.
  - **The intake selects only what the new claim writes.**
    `FIND_OUTCOME_PENDING_INTENTS_SQL` admits a row carrying either the
    route's `submission_outcome: 'unknown'` marker or the claim's
    `submission_claimed` marker, and excludes
    `machine_metadata->>'settlement_scheme' = 'erc7710'` explicitly. erc7710
    settle rows are `submitted` with no `tx_hash` by design and are resolved by
    the settlement-observed confirm; they are claimed by
    `markIntentSubmittedForSettlement`, which writes no metadata, so they carry
    no marker either. A row claimed by the code that shipped before this slice
    — `submitted`, no hash, no marker — is never selected, however old (owner
    decision 2026-11-12 (b): kept out of the intake, listed by the census for
    manual resolution).
  - **The intake age sits above the route's longest wait.**
    `RECONCILE_MIN_AGE_SECONDS` moves from 60 s to 300 s. A claimed row can
    belong to a sign request that is still running: the route's worst case is
    the 10 s send timeout plus the 120 s receipt-wait timeout, plus the booking
    after it. Selecting a row inside that window would read the bundler
    mid-flight and could book `failed` under a live request.
  - **A lost confirm answers `200 confirmed`.** When the route's confirm
    compare-and-set is lost to the reconciler (or a concurrent settle), the
    route re-reads the row and answers `200 confirmed` with the ROW's hash
    instead of the old `409 … changed after on-chain execution`. The winner
    already ran the evidence hook, the accounting feed and the first-payment
    event, so the loser runs none of them. The reconciler's writes stay
    compare-and-set on `status = 'submitted' AND tx_hash IS NULL`.
  - **The failed arm keeps its cause.** `RECONCILE_OUTCOME_FAILED_SQL`
    concatenated `machine_metadata->>'user_op_hash'` straight into
    `error_message`, so a NULL column made the whole expression NULL: the row
    flipped `failed` with no cause recorded and the metadata write was a no-op.
    `COALESCE` on both sides keeps the cause (falling back to the row's own
    `sign_hash`, then to `unknown`) and still stamps the resolved marker.
  - **A read-only census ships with the slice.**
    `CENSUS_SUBMITTED_WITHOUT_HASH_SQL` /
    `censusSubmittedWithoutHash()` list every `submitted` row without a
    transaction hash on a non-erc7710 rail, classified `reconcilable` (the
    intake selects it) or `stranded` (pre-#4818 row, manual resolution). No
    index, no migration, no writer.

  Why the perimeter is unaffected:
  - The change is entirely on the BOOKING side of an operation that was
    already broadcast. It adds no signer, no key role, no relay discretion and
    no new authority over a payment: the signature the agent produced, the
    prepared UserOperation it covers, and the caveat enforcers that authorize
    it on-chain are untouched. Nothing that was refused becomes signable, and
    nothing that was signable becomes refused.
  - The new terminal answers are strictly more conservative than the ones they
    replace. A mined payment that used to be recorded `failed` (and whose
    idempotency key was therefore free again) is now recorded non-terminal and
    resolved from the chain; a payment the reconciler confirmed first now
    answers `confirmed` instead of a 409 that invited a retry. No path gains
    the ability to move funds, and no path loses the ability to stop.
  - The reconciler's lookup key is the operation hash the bundler indexes,
    read back through the SAME bundler credential the submit went through
    (`delegationRailBundlerUrl`, the choke point). There is no transfer-shape
    fallback and no explorer cross-check: a receipt the bundler does not name
    for that hash is "not known yet", never evidence of anything.
  - No schema change: `machine_metadata` already carries `user_op_hash`, and
    the new keys (`submission_claimed`, `tx_hash`) live in the same JSONB
    column. No migration, so no code-owner migration review is involved.
