- **#4819** — a payment the submission reconciler confirms is now booked by the
  same function the sign route uses, so a confirmed payment records the same
  thing whichever path confirmed it.

  What changed:
  - `packages/backend/src/modules/payments/confirm-booking.ts` (new). One
    `bookConfirmedPayment`: price the payment (`getFiatValuesForTokenAmount`),
    confirm the row with the three fiat values in the SAME write, then — only
    for the writer that won the compare-and-set — run the machine-payment
    evidence hook, the accounting underlag feed and the first-payment event.
    The side effects sit inside the winner branch on purpose: a loser that
    still fired the feed would push a second underlag for one payment, and a
    loser that still emitted the funnel event would double-count the user's
    first payment.
  - `packages/backend/src/modules/payments/sign-payment.ts`. The route's
    success path (fiat lookup, confirm write, evidence, feed, funnel) is
    replaced by the one call. Same order, same writes, same side effects; the
    existing characterization suite (`sign-payment.test.ts`) and the new
    real-DB characterization (`sign-payment-confirm-booking.db.test.ts`) pin
    that the row and the side effects are unchanged.
  - `packages/backend/src/modules/payments/submission-reconciler.ts`. A
    landed-and-succeeded receipt now runs the same booking instead of writing
    `status`/`tx_hash`/`confirmed_at` and emitting the funnel event alone. The
    evidence hook is a caller-supplied dependency (`recordEvidence`) because it
    lives in the mpp module, whose barrel imports the payments barrel — an
    import here would close a cycle `no-circular` refuses. `background-jobs.ts`
    supplies it.
  - `packages/backend/src/infra/repositories/payment-intents.ts`. The confirm
    statement is now the ONE confirm write: it carries the fiat triple, keeps
    the compare-and-set (`status = 'submitted' AND tx_hash IS NULL`, plus the
    route's `agent_id` tenant scope), and resolves the outcome-pending marker
    (`submission_outcome: 'resolved'`) when the row carries one — so a
    confirmed row no longer reads "unknown". The CASE leaves a route-confirmed
    row's `machine_metadata` byte-identical to before this slice. The
    reconciler's separate confirm statement and function are deleted; the
    candidate query now also returns the row's `user_id`, `token_symbol` and
    `amount_human`, which the booking needs.
  - The epic's second read-only census ships beside it:
    `COUNT_RECONCILER_THIN_BOOKINGS_SQL` / `countReconcilerThinBookings()`
    count `status = 'confirmed' AND machine_metadata->>'submission_outcome' =
    'unknown'` — the payments the old reconciler path already under-booked. No
    writer, no index, no migration; the owner decided no backfill in this
    issue.

  Why the perimeter is unaffected:
  - No signing, custody or spend-authority code is edited. Nothing here
    changes who may sign, what a signature authorises, or what the caveat
    stack enforces: the change is what Haven RECORDS after the signer has
    already signed and the operation has already landed. The reconciler still
    reads the bundler's receipt index for the recorded userOpHash and still
    refuses to guess — a receipt the bundler does not name for that hash stays
    "not known yet".
  - No new route, no new accepted input, no new authority. The confirm write is
    strictly narrower than before (it gains `tx_hash IS NULL`, which no
    reachable `submitted` row violates) and the reconciler's write keeps its
    compare-and-set, so exactly one writer books a payment.
  - The fiat capture is the same helper the route already used, with the same
    failure behaviour: a price-source failure yields nulls and never fails the
    booking. No later pass completes them (out of scope, as the issue states).
  - The sponsored-gas row is untouched: it is written on the submit seam
    (#3837), so a reconciled payment keeps its `receipt_unconfirmed` cost-NULL
    row (`docs/operations/sponsored-gas.md`).

  Tests:
  - Characterization first, in its own commit that changes no non-test line:
    `packages/backend/src/modules/payments/__tests__/sign-payment-confirm-booking.db.test.ts`
    runs the real `signPayment` against a real Postgres row and pins today's
    route booking — the fiat triple in the confirm write, one evidence call,
    one feed call, one funnel event, and the row enumerated by
    `listUnpushedPaymentIds`; plus the price-failure case (confirmed, nulls, no
    underlag candidate).
  - `packages/backend/src/modules/payments/__tests__/confirm-booking.db.test.ts`
    is the reconciler half on the same harness: a reconciler-confirmed payment
    makes the same assertions as the route control, the marker reads
    `resolved`, the price-failure case still confirms with nulls, BOTH
    directions of the race book once (one evidence call and one feed call in
    total, with both writers in the test), and the census counts exactly the
    thin-booked confirmed rows.
  - `submission-reconciler.test.ts` pins the decision layer: the booking is
    called once with the row's own ids and the injected evidence hook, a lost
    compare-and-set books nothing and counts unresolved, and a reverted receipt
    or an elapsed window never books.
  - Mutation cells: dropping the `if (!confirmed) return false` guard makes the
    race tests red (two evidence calls, two feed calls); removing the
    `submission_outcome` CASE leaves a confirmed row reading "unknown";
    dropping the fiat triple from the confirm write reddens the fiat
    assertions and the `listUnpushedPaymentIds` membership.

  Perimeter unchanged.
