- **#4820** — the owner's Send now answers "sent, outcome unknown" with the
  operation hash instead of "Transfer failed", and the dashboard stops offering
  a second send for that outcome. The submit route's failure body gains two
  additive fields; nothing about what is submitted, who may submit it, or what
  the account enforces changes.

  What changed:
  - `packages/backend/src/rails/hybrid-transfers.ts`. `submitTransfer` answered
    every throw from `treasury.submitCall` with `502 Transfer failed`, so a
    receipt-wait timeout and a pre-send `AA25` rejection were indistinguishable
    to the caller. It now branches on the typed error #4817 introduced: the
    `receipt_unconfirmed` variant answers `502` with
    `error_code: 'submission_outcome_unknown'`, the `user_op_hash` the bundler
    received, and the text "The transfer may have gone through". Every known
    failure — an explicit pre-send rejection, or an operation that landed and
    reverted — keeps today's status and text and gains
    `error_code: 'onchain_execution_failed'`.
  - `packages/backend/src/rails/hybrid-signer-actions.ts`. `SignerChangeFailure`
    is widened with the optional `error_code` and `user_op_hash`. Additive: the
    signer-change routes and every existing caller read `error`/`status`/`details`
    exactly as before. This slice owns the widened type; #4821 consumes it.
  - `packages/backend/src/routes/hybrid-accounts.ts`. The transfer submit route
    relays the two fields through one helper. The 502 keeps its status — the
    smallest change, and the same status the agent payment route answers
    `submission_outcome_unknown` with (`modules/payments/sign-payment.ts`).
  - `packages/frontend/src/hooks/useDelegationSend.ts`. A rejected submit is
    classified instead of folded into `failed`: the route's outcome-unknown
    answer, a request that got no HTTP answer at all, and a 5xx without the
    route's known-failure code are `unconfirmed`. A 4xx, the route's
    `onchain_execution_failed`, and every failure BEFORE the submit (prepare
    refused, signing failed or cancelled) keep today's reading.
  - `packages/frontend/src/components/DelegationSendModal.tsx`. The unconfirmed
    state is an `InlineAlert` on the Review screen with the footer reduced to
    one action, `Close` — not a fourth `DialogResult` state, which would be a
    new pattern. The "you approve it on the next step" note is dropped there
    because the approval already happened.
  - No migration, no new route, no new accepted input, no stored value changes
    shape. An unconfirmed send writes no `owner_transfers` row: the record is
    attribution for a landed transfer and needs its transaction hash, which an
    unknown outcome does not have. A landed transfer still appears in Activity
    without the record — the record is attribution only
    (`routes/hybrid-accounts.ts`), and the feed reads chain data.

  Why the perimeter is unaffected:
  - No signing, custody or spend-authority code is edited. The owner still signs
    the UserOperation on their own device; Haven prepares and relays and holds
    no key. The change is which ERROR a failure raises and which sentence the
    dialog shows, not what is submitted or who may submit it.
  - The new answer is strictly narrower than "everything failed": it is raised
    only for the typed outcome-unknown variant, which #4817 raises only when the
    `eth_sendUserOperation` request was dispatched and no answer came back. An
    explicit rejection still answers the known-failure code, and the acceptance
    criteria pin both directions.
  - The dashboard change REMOVES a spend path rather than adding one: before
    this slice a lost submit answer relabelled the button `Try again`, and
    pressing it prepared, signed and submitted a second operation with the same
    recipient and amount (the submit body carries no idempotency key). The
    unconfirmed state offers no retry at all.
  - No new authority, no new accepted input, no credential surface. The
    `user_op_hash` is a public 4337 operation identifier, not a transaction hash
    and not a secret; the dialog does not render it.

  Tests:
  - `packages/backend/src/routes/__tests__/hybrid-signers.test.ts` pins the
    three submit outcomes through the real route and the real typed error: the
    outcome-unknown answer carries `submission_outcome_unknown` and the hash and
    is not `Transfer failed`; an included-and-reverted and a pre-send rejection
    keep `Transfer failed` plus `onchain_execution_failed` and carry no hash.
    The outcome-unknown case also asserts no `owner_transfers` row is written.
  - `packages/frontend/src/hooks/__tests__/useDelegationSend.test.ts` pins the
    classification: `unconfirmed` for the route's code, for a request with no
    HTTP answer, for a 502 with no code and for a 5xx with an unknown code;
    `failed` for a 4xx, for `onchain_execution_failed`, and for a refused
    prepare or a signing failure; `cancelled` for a dismissed passkey prompt.
  - `packages/frontend/src/components/__tests__/DelegationSendModal.test.tsx`
    pins the dialog: the unconfirmed state shows the copy and one `Close`
    action, offers no `Back` and no `Try again`, and activating every rendered
    control makes no further send call (asserted by call count, not by label).
    The `failed` state still offers `Try again` and a second press submits.
  - Mutation cells are in the PR body: treating every submit rejection as
    `failed` reddens the three unconfirmed hook cases; treating every 5xx as
    `failed` reddens the no-code case; dropping the `instanceof` branch in
    `submitTransfer` reddens the backend outcome-unknown case; rendering the
    `Back`/`Try again` pair in the unconfirmed state reddens the dialog's
    control-count assertion.

  Perimeter unchanged.
