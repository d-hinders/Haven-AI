- **#4821** — the other owner-signed operations now answer "sent, outcome
  unknown" with the operation hash instead of "… failed", and the dashboard
  stops offering a second signature for that outcome. The five submit routes'
  failure bodies gain two additive fields; nothing about what is submitted, who
  may submit it, or what the account enforces changes.

  What changed:
  - `packages/backend/src/rails/owner-signed-failure.ts` (new). One place turns
    the typed error #4817 introduced into the wire shape, so the five handlers
    cannot drift apart: `submission_outcome_unknown` (the operation was SENT and
    its answer or its receipt was lost — it may have landed; `user_op_hash`
    names the operation the bundler received) and `onchain_execution_failed` (a
    KNOWN failure: an explicit pre-send rejection, or an operation that landed
    and reverted, so nothing moved). The vocabulary is the agent payment
    route's and the owner-send route's (#4820).
  - `packages/backend/src/rails/hybrid-signer-actions.ts`. `submitSignerChange`
    answered every throw from `treasury.submitCall` with `502 Signer change
    failed`. It now branches on the typed error: the `receipt_unconfirmed`
    variant answers `502` with `error_code: 'submission_outcome_unknown'`, the
    `user_op_hash`, and the text "The signer change may have gone through";
    every known failure keeps today's status and text and gains
    `error_code: 'onchain_execution_failed'`. The DB sync is now a SEPARATE
    step: a throw from it happens after the op landed, and the signer set has
    no on-chain reader (`modules/ops/onchain.ts`), so it answers "landed but
    Haven could not record it" with no code — which the dashboard reads as
    unconfirmed, never as a safe retry.
  - `packages/backend/src/routes/hybrid-accounts.ts` and
    `packages/backend/src/routes/agent-delegations.ts`. Both signer-change
    submit handlers relay the two fields through the shared body builder
    (before this slice they relayed only `error` and `details`).
  - `packages/backend/src/routes/agent-delegations.ts` (single and batch
    revocation) and `packages/backend/src/routes/agent-rekey.ts` (the re-key's
    revoke). Each answered any throw with `502 … failed`; each now answers the
    outcome-unknown variant as unconfirmed with the hash, and keeps its
    existing sentence plus the known-failure code for a pre-send rejection or
    an included-and-reverted receipt. The re-key route's comment now describes
    both cases: a pre-send rejection wrote nothing and retrying is safe; an
    outcome-unknown throw may have landed, so a retry must re-read the chain.
  - `packages/backend/src/openapi/spec.ts`. The five routes' 502 descriptions
    document the two shapes and what each means for a retry.
  - `packages/frontend/src/lib/submitOutcome.ts` (new). The submit classifier
    the owner-send hook carried (#4820) is now shared: the route's
    outcome-unknown code, a request that got no HTTP answer at all, and a 5xx
    without the route's known-failure code are `unconfirmed`; a 4xx and the
    route's `onchain_execution_failed` are `failed`.
  - `packages/frontend/src/hooks/useAccountSigners.ts`,
    `useDelegationBudget.ts`, `useAgentRekey.ts`. Each submit is classified
    instead of folded into `failed`. The budget hook's edit flow gains
    `revoke_unconfirmed` (distinct from `revoke_unfinished`), and the re-key
    hook gains an `unconfirmed` failure kind.
  - `packages/frontend/src/components/AccountSignersCard.tsx`,
    `DelegationBudgetCard.tsx`, `EditBudgetModal.tsx`,
    `agent-panel/RemoveAgentDialog.tsx`, `agent-panel/ReplaceSigningKeyModal.tsx`.
    Each renders the unconfirmed answer as its own state, never as the plain
    failure, and offers no control that signs the same operation again without
    a re-read: the signer card and budget card re-read their lists, the remove
    dialog's next press re-reads the chain at prepare, the edit modal offers
    only Close (the card's Stop re-reads first), and the re-key modal offers
    only Close (reopening runs preflight, which re-reads the stage).
  - No migration, no new route, no new accepted input, no stored value changes
    shape. An unconfirmed operation writes nothing: every handler's database
    write still runs only after `submitCall` returns.

  Why the perimeter is unaffected:
  - No signing, custody or spend-authority code is edited. The owner still
    signs the UserOperation on their own device; Haven prepares and relays and
    holds no key. The change is which ERROR a failure raises and which sentence
    the dashboard shows, not what is submitted or who may submit it.
  - The new answer is strictly narrower than "everything failed": it is raised
    only for the typed outcome-unknown variant, which #4817 raises only when
    the `eth_sendUserOperation` request was dispatched and no answer came back.
    An explicit rejection still answers the known-failure code, and the
    acceptance criteria pin both directions for all five handlers.
  - The dashboard changes REMOVE spend paths rather than adding one: before
    this slice a lost submit answer relabelled the control "Try again" (or left
    the Stop button live), and pressing it prepared, signed and submitted a
    second operation. The unconfirmed states either re-read first or offer no
    signing control at all.
  - The revocations already heal at prepare — they read the disabled hashes
    on-chain before preparing, and `disableDelegation` reverts on an
    already-disabled delegation — so a retry after a landed-but-unconfirmed
    revoke converges on the revoked database state without a second on-chain
    operation. That is pinned by tests for both the single and the batch
    revoke. The signer set has no on-chain reader, which is why its
    unconfirmed state offers no retry.
  - No new authority, no new accepted input, no credential surface. The
    `user_op_hash` is a public 4337 operation identifier, not a transaction
    hash and not a secret; no component renders it.

  Tests:
  - `packages/backend/src/routes/__tests__/hybrid-signers.test.ts` and
    `agent-delegations.test.ts` pin the signer-change submit through the real
    routes and the real typed error: the outcome-unknown answer carries
    `submission_outcome_unknown` and the hash and is not "Signer change
    failed"; a pre-send rejection keeps "Signer change failed" plus
    `onchain_execution_failed` and carries no hash. Both assert no storage sync
    ran.
  - `agent-delegations.test.ts` pins the single and batch revocations the same
    way, and pins the heal: after an unconfirmed revoke, a second revoke reads
    the delegation as disabled at prepare, heals the row to `revoked`, and
    never reaches the treasury a second time.
  - `agent-rekey-revoke-submit.test.ts` pins the re-key's revoke both ways and
    asserts nothing was written and the stage stayed `preflight`.
  - `packages/frontend/src/hooks/__tests__/useAccountSigners.test.ts`,
    `useDelegationBudget.test.tsx` and
    `components/agent-panel/__tests__/ReplaceSigningKeyModal.test.tsx` pin the
    classification and the states: `unconfirmed` for the route's code and for a
    request with no HTTP answer; `failed` for the known-failure code; the
    re-key modal's unconfirmed step offers no "Switch off the old key" and no
    "Try again".
  - `components/__tests__/AccountSignersCard.test.tsx`,
    `DelegationBudgetCard.test.tsx`, `EditBudgetModal.test.tsx` and
    `agent-panel/__tests__/RemoveAgentDialog.test.tsx` pin the rendered states:
    each says the operation may have landed, none says "nothing changed", and
    the edit modal's `revoke_unconfirmed` offers only Close.
  - Mutation cells are in the PR body: dropping the `instanceof` branch in any
    handler reddens its outcome-unknown case; treating every submit rejection
    as `failed` reddens the hook cases; rendering the plain failure copy in an
    unconfirmed state reddens the component cases.

  Perimeter unchanged.
