- **#4822** — the signed receipt bundle of an EIP-3009 payment named the agent's
  own delegate as the merchant. The bundle now names the merchant recorded at
  authorize and carries the merchant's settlement transaction as its own field.
  **No custody or authority boundary moves. This is an evidence-read correction
  on a bundle that was already Haven-asserted.**

  What changed:
  - **The merchant party** (`packages/backend/src/modules/payments/receipt.ts`,
    `packages/backend/src/infra/repositories/payment-intents.ts`). On the
    EIP-3009 bridge the intent row is the FUNDING leg: `to_address` is the
    agent's own delegate, and the merchant named at authorize sits in
    `merchant_address` / `x402_merchant_address`. `buildPaymentReceipt` set
    `payment.parties.merchant` from `to_address`, so the bundle named the
    delegate. `FIND_SETTLED_PAYMENT_RECEIPT_SQL` now selects the repository's
    counterparty expression — `COALESCE(pi.merchant_address,
    pi.x402_merchant_address, pi.to_address)`, the same one `dashboard.ts`
    uses — and the mapper reads it. A retired-rail row with neither merchant
    column still falls back to `to_address`, which is what the bundle named
    before.
  - **The merchant's settlement transaction** (`settlementTxHash`, additive).
    The bundle gains the field the OpenAPI operation description, the SDK's
    receipt docs and both receipt tool descriptions already named. For erc7710
    and direct payments it equals `onChain.txHash` (the one transaction settles
    the payment). For EIP-3009 it is
    `machine_metadata.merchant_settlement_tx_hash` — the hash Haven verified
    on-chain (#4530), the same key the status read returns — and `null` until
    recorded. The merchant's own unverified echo
    (`protocol_receipt_payload.transaction`, surfaced as `settlement_tx_hash`
    on the receipt list) is never selected and never read.
  - **The funding leg keeps its names** (owner decision 2026-11-12).
    `payment.recipient`, `authorization.signHash` and `onChain.txHash` still
    describe the funding leg — the delegate and the funding transaction — and
    `parties.merchant` / `settlementTxHash` describe the merchant leg. The
    `getPaymentReceipt` operation description (`openapi/spec.ts`, regenerated
    into `packages/core/src/api-types.ts`) now states which leg each field
    names.
  - **Untouched.** `packages/sdk/src/receipt.ts` is not edited: the published
    `PaymentReceipt` type is unchanged and the backend widens the literal with
    a type assertion, as #2907, #2960 and #3418 did. No schema, migration,
    signed payload, route, credential scope or spend check changes. `version`
    stays `haven-receipt-1`. The bundle keeps stored casing (#3307 kept the
    signed bundle unchanged); comparisons with the list and the status read are
    case-insensitive.

  Why the perimeter is unaffected:
  - The bundle is an evidence read, not an authorisation. `verifyPaymentReceipt`
    reads only `authorization` (plus `onChain.chainId` for the delegation
    digests), so an additive field and a corrected party change nothing about
    what a signature covers or what `verified: true` proves. The verification
    result per scheme is unchanged: erc7710 `verified: true`, EIP-3009
    `not_verifiable_offline`.
  - No signing input, spend check, allowance, fee, accounting entry or
    execution path is edited. `payment-intents.ts` is on the money-path glob
    because it is the intent store; this change adds two SELECT columns to one
    read and writes nothing.
  - The correction narrows what the bundle claims: it stops naming the agent's
    own delegate as the merchant, and it says nothing about the merchant's
    settlement until Haven has verified it on-chain rather than repeating the
    merchant's unverified echo.

  Tests:
  - Real Postgres (`infra/repositories/__tests__/payment-intents.test.ts`): a
    `confirmed` EIP-3009 intent with `to_address` = delegate and
    `merchant_address` = merchant, read through the real SQL and the real
    builder, asserts `payment.parties.merchant` is the merchant
    (case-insensitively) and `settlementTxHash` is null; a second row with
    `machine_metadata.merchant_settlement_tx_hash` recorded asserts the hash
    rides along while `onChain.txHash` keeps the funding transaction.
    Mutation-proven: removing the merchant column from
    `FIND_SETTLED_PAYMENT_RECEIPT_SQL` turns it red.
  - Builder (`modules/payments/__tests__/receipt.test.ts`): recorded,
    not-recorded and echo-only EIP-3009 rows; erc7710 and direct rows pinned
    field-for-field with `toEqual` (the only difference is the added
    `settlementTxHash`); a retired-rail row with no merchant column; stored
    casing kept; verification unchanged with the field present.
  - Party characterization (`openapi/party-characterization.test.ts`): two new
    fixtures for `GET /payments/:id/receipt`. The erc7710 one was recorded with
    the base-commit builder (`origin/dev` @ 65b1d7cb7) and replays with only
    `settlementTxHash` stripped; the EIP-3009 one pins the corrected merchant
    party and settlement hash.

  Perimeter unchanged.
