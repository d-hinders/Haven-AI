- **#4823** — the hosted `haven_discover_tools` hinted a verified
  self-submitted catalog row at `haven_quote_catalog_purchase { catalog_id }`,
  and that tool answered the row `CATALOG_ENTRY_NOT_FOUND`: the agent detail
  read serves `source: 'ingestion'` rows only to non-agents
  (`packages/backend/src/routes/catalog.ts`). Discovery guidance only — no
  input, schema, refusal code, signer surface or spend authority changes, and
  neither catalog read moves.

  What changed:
  - **The hint follows provenance** (`packages/mcp-server/src/tools/catalog-purchase.ts`,
    `discoveryHintFor`). A row with `source: 'ingestion'` now emits
    `haven_quote_mcp_tool { merchant_url: resource_url, tool_name }` — the same
    by-URL path the local runtime already names for the same row, and the one
    that works on both runtimes. An operator MCP row keeps
    `haven_quote_catalog_purchase { catalog_id }`; a degraded row or one with
    no `tool_name` keeps its `suggested_tool_omitted_reason`.
  - **The hint type gains the arm** (`packages/mcp-server/src/tools/contracts.ts`,
    `DiscoveryHint`), so the argument shape is checked at the emission site and
    the discovery parity test parses it under `haven_quote_mcp_tool`'s strict
    schema.
  - **Both reads stay as they are.** `GET /catalog`, `GET /merchants/:slug`
    and `GET /catalog/:id` are untouched: the self-submitted row is still
    listed to agents and still answers an agent 404 on the detail read. Only
    the hosted hint stops pointing at that dead end.
  - **The docs say which row gets which hint**
    (`docs/architecture/04-x402-payment-sequence.md`).

  Why the perimeter is unaffected:
  - This is discovery metadata, not payment authority. `haven_quote_mcp_tool`
    is a read-only live-price probe: it creates no intent, approval, signing
    context, allowance check, funding or paid retry, and the paid path
    (`haven_pay_mcp_tool` / `haven_prepare_catalog_purchase`) still re-quotes
    live and enforces its own cap.
  - No tool name, input schema, refusal code, `next_action` value, stored value
    or signer surface changes. The new hint names a tool that already exists on
    the hosted surface with the arguments it already accepts.
  - The change removes a dead end rather than widening anything: the row it
    redirects was previously unreachable through the hinted tool, and the
    redirect target is the same merchant URL and tool name the row already
    publishes.
  - The local runtime is unchanged; it already hints its own pay tool for this
    row.

  Tests: `packages/mcp-server/src/tools/catalog-purchase.test.ts` pins the
  ingestion row's hint (`haven_quote_mcp_tool`, `{ merchant_url, tool_name }`,
  parsed under that tool's strict schema, no `catalog_id`) and the operator
  control row keeping `haven_quote_catalog_purchase { catalog_id }`; the
  existing discovery parity test still parses every emitted hint under the tool
  it names.

  Perimeter unchanged.
