- **#4824** — the Accounted underlag's render inputs are pinned at the
  payment's first render, so a retry after a lost answer replays the first
  attempt's bytes instead of being refused as `IDEMPOTENCY_KEY_REUSE`.
  What changed:
  - `packages/backend/src/infra/repositories/machine-payments.ts`:
    `pinAccountingUnderlagInputs` writes the four mutable render inputs — the
    merchant receipt (the seller block **and** the transaction kind), the
    delivery reference, the purchase group / parent receipt, and the catalog
    country — to
    `payment_intents.machine_metadata->'accounting_underlag_inputs'`,
    first-writer-wins, the same JSONB and the same storage shape as #3767's
    booked-hash pin. `LOAD_RECEIPT_UNDERLAG_SOURCE_SQL` returns the pin beside
    the source row, so the renderer pays no second round trip. **No
    migration.**
  - `packages/backend/src/modules/accounting/receipt-underlag.ts`:
    `pinUnderlagInputs` freezes the inputs before the first upload request;
    `loadReceiptUnderlag` validates the pin field by field and renders every
    retry from it. A payment with no pin renders live, exactly as before.
  - `packages/backend/src/modules/accounting/accounted-connector.ts` and
    `igdrasil-connector.ts`: both call `pinUnderlagInputs` after the render and
    the local size gate, before the upload. A connector that fails before any
    upload request (no connection, no company id, a render failure) writes no
    pin, so its retry renders whatever the sources hold by then.
  - The "deterministic bytes" and "never retried" claims are corrected in
    `accounted-connector.ts`, `accounted-client.ts`, `igdrasil-connector.ts`,
    `machine-payments.ts`, `modules/accounting/README.md` and
    `docs/operations/accounting-feed.md`. The accepted-risk record at
    `accounting-feed.md` § *Accepted risk — Accounted write-once bytes* is left
    as written: template drift across a deploy is still accepted.
  Authority and custody argument: nothing signs, moves, authorises or refuses
  differently. The change writes one JSONB key on `payment_intents` (a row the
  feed already reads and the #3767 pin already writes) and reads it back in the
  renderer. No amount, recipient, status, settlement decision, budget cap,
  allowance, delegation or refusal code is touched; no key material, delegate
  balance or signing path is read or written. The pin is a fact about a
  document Haven already produces, not a new authority over the payment.
  Mutation-tested: `accounted-underlag-pin.db.test.ts` drives the real
  orchestrator, entry builder, renderer and connector on real Postgres. For
  each of the four sources it stores the first upload, loses the answer, writes
  the source, retries, and asserts the row is `pushed` with an `external_ref`,
  exactly one document under the underlag key, and the retry's SHA-256 equal to
  the first attempt's. Removing the pin write (or the pin read) turns every
  source case red with `IDEMPOTENCY_KEY_REUSE`. The suite also pins the
  regression controls: a retry with nothing changed ends `pushed` with one
  document; a receipt captured before the first render still puts the seller
  name, country and VAT number on the underlag (#3918); a first attempt that
  failed before any upload request writes no pin and its retry renders the
  current sources; and a row already `skipped` with `IDEMPOTENCY_KEY_REUSE` at
  deploy carries no pin and is left as it is (the provider's 409 names no
  document id, so Haven cannot recover a ref it never received).
  Perimeter unchanged.
