- **#4825** — on a `--local` install, the local MCP handed signing steps to a
  signer server the connector removed. `packages/mcp/src/tools.ts` named
  `mcp__haven-signer__haven_sign` at five result sites — `haven_open_task_budget`,
  `haven_close_task_budget`, every `pendingSubBudgetSignatures[]` row of
  `haven_get_agent`, and `haven_submit { sub_budget_id }` on success and on
  `CLOSE_NEEDS_REPREPARE` — while the local surface registers no signing tool
  (it signs in-process with the delegate key it holds) and the connector's
  local mode deletes the signer server on every runtime that supports local
  mode (`packages/connect/src/runtime-install.ts`,
  `packages/connect/src/config-writers.ts`). An agent following the tool's own
  next step called a tool that was not in its list. **No custody or authority
  boundary moves. This is a refusal where a dead handoff used to be: the
  runtime that cannot sign now says so instead of naming a signer it does not
  have.**

  What changed:
  - **`haven_open_task_budget` refuses before contacting anything.** It answers
    the typed code `TASK_BUDGET_SIGNING_UNAVAILABLE` with
    `next_action: stop_and_tell_user` and a `next_tool_omitted_reason`, and
    never calls `POST /task-budgets` — so no pending row is created and nothing
    is reserved. The arguments are not inspected: no argument makes this
    runtime able to sign.
  - **`haven_close_task_budget` reads the budget first.** A pending or expired
    budget still closes with `status: "closed"` (the backend's prepare is
    trivial, no signature). One that is open or closing refuses with the same
    code and **never calls `POST /task-budgets/:id/close`**, so the budget is
    not left `closing` (`routes/task-budgets.ts`). An already-closed budget
    answers `status: "closed"` without a call.
  - **Sub-budget rows name no next tool.** A `pendingSubBudgetSignatures[]` row
    and both `haven_submit { sub_budget_id }` results carry
    `next_action: stop_and_tell_user` and a `next_tool_omitted_reason` saying
    this runtime cannot sign a sub-budget and that the owner signs it from a
    hosted-plus-signer install. The `CLOSE_NEEDS_REPREPARE` message no longer
    says "sign it with haven_sign".
  - **The premise is gone from the text.** The local descriptions of
    `haven_open_task_budget`, `haven_close_task_budget` and `haven_submit` say
    the refusal instead of a signer step; the shared `haven_get_agent` fragment
    gains a per-surface form (`behaviorFor` in
    `packages/sdk/src/tool-descriptions.ts`) so the hosted text is unchanged;
    `description-tool-references.test.ts` rule (b) — a signer tool name is
    resolvable — now applies to the hosted surface only. The
    `signer_compatibility` notice is removed from the local handoffs and its
    local builder (`packages/mcp/src/signer-compat.ts`) is deleted with them.
  - **The tools are refused, not removed.** `local-tool-contract.golden.json`
    keeps its 20 tool names, so the local consent hash
    (`packages/mcp/src/consent.ts`) does not move; only the descriptions are
    regenerated. Spending through an open sub-budget (`sub_budget_id` on the
    pay tools) needs no signer and is unchanged.

  Why the perimeter is unaffected:
  - Nothing that was signable becomes refused, and nothing that was refused
    becomes signable. The local runtime never had a signer tool, so the five
    handoffs it emitted could not be followed; the refusal replaces a step that
    could not execute. The hosted surface — the one that does hand signing to
    the signer — is untouched: its descriptions, its `signer_compatibility`
    notice and its `haven_sign` handoffs are byte-identical.
  - No route, credential scope, spend check, allowance, fee, accounting entry,
    signed payload or execution path is edited. `POST /task-budgets` and
    `POST /task-budgets/:id/close` are not called on the refusal paths, so the
    change can only leave LESS state behind, never more: no pending row, no
    `closing` row.
  - No key role is added or widened, and no new authority exists over a
    payment. The local runtime's signing capability is unchanged — it still
    signs payments in-process with the delegate key it holds.

  Tests:
  - `packages/mcp/src/local-signer-refusal.test.ts` (new): drives all five
    sites and asserts every emitted `next_tool` is a name in the local tool
    list, that the signer namespace appears in no field of any result, that
    `tools.ts` contains zero occurrences of `mcp__haven-signer__`, and that the
    local tool list has no tool whose name contains `sign`.
  - `packages/mcp/src/task-budgets.test.ts`: the open refusal (stub fails the
    test if `openTaskBudget` is reached, and the allowance read is not made
    either), the close matrix (pending → closed, expired → closed, already
    closed → closed without a call, open and closing → refusal with the stub
    failing if `closeTaskBudget` is reached), and a failed budget read passing
    through.
  - `packages/mcp/src/sub-budgets.test.ts`: the sibling-pending and
    `CLOSE_NEEDS_REPREPARE` sites carry no `next_tool` and a reason naming the
    row; the `haven_get_agent` rows likewise.
  - `packages/mcp-server/src/description-tool-references.test.ts`: the signer
    exemption is hosted-only, plus a direct assertion that no local description
    names a signer tool.
  - `packages/mcp-server/src/local-hosted-contract-parity.test.ts`: the four
    changed description hashes are declared with reasons, including the new
    `haven_get_agent` pair.
  - Mutation-proven: restoring `next_tool: 'mcp__haven-signer__haven_sign'` in
    `subBudgetSignStep` turns the five-site test red on the tool-list
    membership assertion (and on the `tools.ts` source scan); disabling the
    pre-read's refusal branch in `haven_close_task_budget` turns the open,
    closing and older-backend rows red on the `closeTaskBudget` call
    assertion.

  Perimeter unchanged.
