- **#4826** — an x402 authorize replay whose idempotency key belongs to a
  `submitted` payment now answers a typed 409 carrying the payment's id and
  status, instead of an untyped "retry the original request". The change is a
  replay ANSWER: it issues no new sign context, writes nothing, and narrows
  nobody's ability to sign, move or authorise.

  What changed:
  - `packages/backend/src/modules/x402/replay.ts`. `delegationReplay` answered
    only `pending_signature` and `confirmed` rows; every other status returned
    `null`, so the authorize route ran its pre-checks, lost the unique-index
    race on the key, replayed again, got `null` again, and answered
    `409 {"error":"Idempotent replay in progress — retry the original request"}`
    with no `payment_id`, `status` or `error_code`. A `submitted` row — the
    agent settled and the outcome is not booked yet — now joins the statuses
    the function answers. It is compared with the SAME full pin a
    `pending_signature` row gets (resource, funding payee, merchant, amount,
    asset, network, facilitator set) plus the task-budget and sub-budget pins,
    so a replay naming a different one of those is still the existing mismatch
    409. A matching replay answers `409` with `error_code:
    "payment_already_submitted"`, `payment_id`, `status: "submitted"` and text
    that says to read the payment's status and not to authorize again. No sign
    context is issued: the settlement was already submitted, so there is
    nothing left to sign.
  - `packages/backend/src/modules/x402/delegation-authorize.ts` is unchanged.
    The answer is produced at the FIRST replay call (`:224`), which already
    sits before the hourly cap, scope resolution, the task-budget cap read, the
    period pre-check and the funding prepare / deploy check. Before this, a
    `submitted` replay answered the bare 409 only when every pre-check passed;
    otherwise it answered 429 or 403 for a payment already in flight.
  - `packages/backend/src/middleware/client-compat.ts`. `findReplay` counts a
    `submitted` x402 row as a replay, so a below-minimum client replaying its
    own key reaches the handler's typed answer instead of a 426. The
    "Mirrors `delegationReplay`" comment is corrected to match.
  - `packages/mcp-server/src/tools/support/errors.ts` and
    `packages/mcp/src/tools.ts`. Both mappers answer the new body with
    `check_status_later` and `haven_get_payment_status { payment_id }` taken
    from the body — never a retry, never a new payment. The hosted branch
    requires the body's `payment_id`; a body without one falls through to the
    generic 4xx answer, which also never retries.
  - `packages/backend/src/openapi/spec.ts`, the regenerated
    `packages/core/src/api-types.ts` and
    `docs/architecture/05-agent-api-openapi.md` describe the typed body on the
    409 of `POST /x402/authorize` and `POST /x402`.
  - No migration, no new route, no new accepted input, no stored value changes
    shape. The new code is `payment_already_submitted`; the existing
    `submission_outcome_unknown` (the sign 502) is untouched.

  Why the perimeter is unaffected:
  - No signing, custody or spend-authority code is edited. The replay path
    reads a stored row and returns an error body; it prepares nothing, deploys
    nothing, writes no intent and no refusal row, and issues no sign context.
  - The answer is strictly narrower than the bare 409 it replaces: it names the
    payment and its status, and it is produced EARLIER (before the cap and the
    budget reads), so a replay can no longer be refused 429/403 for a payment
    that already exists. It grants no authority and removes none.
  - The full pin still runs first, so a key collision naming a different
    resource, payee, amount, asset, network, facilitator set, task budget or
    sub-budget is refused exactly as before.
  - The budget pre-check's rule for a `submitted` key
    (`modules/mpp/budget-precheck.ts`) is unchanged: only `confirmed` with a
    hash is settled. `haven_prepare_catalog_purchase` reaches the new answer
    only when that pre-check passes.

  Tests:
  - `packages/backend/src/routes/__tests__/x402-submitted-replay.test.ts` (new,
    real Postgres and the real route): both legs answer the typed 409 with the
    row's id and status while the agent is AT its hourly cap and the remaining
    budget is BELOW the amount; zero calls to the remaining-budget read,
    `ensureDelegateHybridDeployed` and `prepareDelegationPayment`; no new
    `payment_refusals` row. A fresh key on the same agent answers 429, proving
    the cap is genuinely exceeded. A different task budget, sub-budget and
    resource URL each answer the existing mismatch 409 with no `error_code`.
  - `packages/backend/src/routes/__tests__/replay-rules-parity.test.ts` CELL 10
    and its header table are rewritten to the new rule on purpose: a
    `submitted` row (with and without a `tx_hash`) answers the typed 409, the
    pre-check still refuses 403, and `POST /payments` still replays its stored
    status.
  - `packages/backend/src/routes/__tests__/client-compat-refusal.test.ts`: a
    below-minimum client replaying a `submitted` key gets the handler's typed
    409, not 426, and writes nothing.
  - `packages/backend/src/modules/budget-scope/__tests__/entrypoint-matrix.ts`
    gains a `submittedReplay` state for every entrypoint × scope cell, run
    through the real routes by `entrypoint-matrix.db.test.ts`.
  - `packages/mcp-server/src/test-support/next-step-fixtures.ts` gains the
    `REFUSAL_SITES` fixture for the new body; the hosted characterization and
    the local ↔ hosted parity test hold both mappers to
    `check_status_later` + `haven_get_payment_status { payment_id }`.

  Perimeter unchanged.
