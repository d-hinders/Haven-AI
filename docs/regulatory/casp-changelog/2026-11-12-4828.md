- **#4828** — the hosted MCP's error mapper reported a rate limit as a
  permanent refusal. `normalizeError` split an upstream `HavenApiError` on the
  status alone: below 500 was `stop_and_tell_user` with "the upstream call was
  refused as made (4xx); re-calling it the same way cannot succeed". A 429 is
  below 500, no backend 429 body carried an `error_code`, and nothing in
  `packages/mcp-server/src` handled 429, so every rate limit an agent's hosted
  tool could meet — the plugin's per-route limit, the hourly x402 cap, the
  catalog submission queue, the two relayer sponsorship budgets, and a
  merchant's 429 on the unpaid MCP probe — reached the agent as a dead end and
  any stated wait was dropped. **No custody or authority boundary moves. This
  is retry guidance on a failed call plus one additive typed code; nothing
  that was refused becomes signable, and nothing that was signable becomes
  refused.**

  What changed:
  - **A 429 takes the transient step.** `next_action:
    retry_with_explicit_context` (the value the 5xx branch already uses; no new
    `next_action` value), with a reason that says the upstream call was
    rate-limited, to wait, then re-call the same tool with the same arguments
    (and the same `idempotency_key` where the tool has one) **once** before
    telling the user. The reason names neither Haven nor the merchant as the
    limiter, because both reach the branch: a merchant's 429 on the unpaid MCP
    probe arrives as a status-only `HavenApiError` (the discovered-endpoint
    rebuild in `tools/support/mcp-context.ts` drops the body), and no payment
    exists at that point.
  - **The sponsorship budget is the one 429 that stops.** The relayer's
    per-identity window cap (`hybrid_deploy`, 10 per user per 24 h; `sweep`, 30
    per agent per 60 min) now carries a typed
    `error_code: 'relayer_budget_exceeded'` on both bodies
    (`modules/x402/delegation-authorize.ts`, `modules/mpp/sweep.ts`), so the
    mapper answers `stop_and_tell_user` from the code rather than from English.
    Its reason names the budget and the window: a slot frees when the oldest
    counted operation ages out, up to 24 hours for an account deploy and up to
    60 minutes for a sweep. The sign route's 429
    (`modules/payments/sign-payment.ts`) carries the same code as a defensive
    case; it is unreachable in production, because
    `RelayerBudgetExceededError` is thrown only by `assertRelayerBudget`, whose
    two callers are the account-deploy and sweep paths.
  - **The additive field.** A rate-limit answer carries `retry_after_seconds`
    (the number the limiter stated) when its body has one — the hourly x402 cap
    sends `retry_after_seconds: 60`. It is absent on every other answer, and no
    existing field changes meaning. The plugin states its wait only in a
    `retry-after` header, which `HavenApiError` does not carry, so that wait
    stays unread here; carrying it is a change to the published SDK transport.
  - **Nothing else moves.** Every existing refusal code, step, reason and
    `error_code` branch is unchanged: the ten payment-scope refusals, the typed
    403/404/409/502 branches, the cause-first `no_answer` / `deterministic`
    branches, the generic 4xx stop and the generic 5xx retry. The hosted answer
    keeps `code: 'API_ERROR'` on both new branches. The local runtime's mapper
    (`packages/mcp/src/tools.ts`) is out of scope: it already answers a 429
    `stop_and_tell_user` and relays `body`, so the wait is not dropped there;
    the divergence in `next_action` and the additive field are recorded in
    `docs/operations/mcp-runtime-compatibility.md`.

  Why the perimeter is unaffected:
  - The change is entirely on the failure path of a call that already failed.
    It produces a different `next_action`, reason and (on one body) an extra
    number on a failure result; it produces no signature, no submission, no
    audit entry and no ledger row. The sponsorship 429s already refused before
    any write and released their claims, so the re-call the rate-limit step
    permits is safe on the backend side for every row: the plugin limit, the
    hourly cap and the catalog queue refuse before a write, and the merchant
    probe is unpaid.
  - No key role is added or widened, no relay discretion is introduced, and no
    new authority exists over a payment. The `error_code` is additive on two
    existing 429 bodies and is read only to choose a stop instead of a retry —
    it cannot make a refused operation succeed.
  - The one behaviour that could look like a widening — telling an agent to
    re-call a rate-limited tool once — is bounded to a single re-call with the
    same arguments and the same idempotency key, and every backend 429 it
    covers refuses before a write or releases its claim.
