- **#4829** — the local signer reported a gateway error or a rate limit on its
  signing-context fetch as "Haven refused". All four fetches in
  `packages/signer/src/sign-context.ts` (`/x402/:id/sign-context`,
  `/payments/:id/sign-context`, `/task-budgets/:id/sign-context`,
  `/sub-budgets/:id/sign-context`) swallowed a body that is not JSON to `{}`
  and threw every non-2xx as `SIGN_CONTEXT_REFUSED`. An HTML 502 from a
  gateway, a JSON 5xx and a 429 — the money-path rate limit every one of those
  four routes carries — therefore reached the agent as a refusal by Haven, for
  a payment Haven never looked at. **No custody or authority boundary moves.
  This is a classification correction on a failed READ: what the signer signs,
  and its checks on relayed bytes, are unchanged.**

  What changed:
  - **Two classes, not one.** A 4xx other than 429 whose body IS a JSON object
    stays `SIGN_CONTEXT_REFUSED` — the only shape that carries Haven's own
    `error` / `error_code`, and so the only one where "Haven refused" is a true
    statement. Everything else is the NON-ANSWER class: a body that is not a
    JSON object at any non-2xx status, any 5xx, and a 429. It is reported as
    `SIGN_CONTEXT_UNREACHABLE` — the code a transport failure already gets —
    with `http_status` carried so an agent can tell a gateway 502 from a rate
    limit.
  - **The step is the flow's existing transport step.** The x402 and direct
    fetches offer the existing `typed_data_b64` relay with their existing
    relay text; the task-budget and sub-budget fetches keep their no-fallback
    step, as they already do for a transport failure (there is nothing else to
    sign). A 429's reason additionally says to re-call the same signer tool
    with the same arguments once after the wait, citing `Retry-After` when it
    is whole seconds. No new result field, and the signer does not sleep or
    re-fetch: the agent's re-call is the retry.
  - **Nothing else moves.** Every existing refusal code, hint and
    `refusalOf` detail is unchanged: the x402 404/410 hints, the direct
    fetch's 404 and `expired` hints, the older-backend route-not-found 404
    (JSON `message`, no `error`) with its fallback, and the 426
    `client_outdated` / 409 `already_executed` / `not_signable` /
    `sign_context_unavailable` codes with their `next_action` and absence of
    `fallback`. Only a JSON 409 `sign_context_unavailable` on the x402 fetch
    reaches the direct fetch; a 5xx, a 429 or a non-JSON answer there makes
    exactly one request.
  - **Untouched.** No route, credential scope, spend check, allowance, fee,
    accounting entry, signed payload or execution path is edited. The signer
    still signs only bytes whose digest it re-derives and whose Haven binding
    it verifies (#1138); the widened class changes which failed READ points at
    the existing relay, not what may be signed. The hosted guidance that routes
    on `fallback` (`packages/mcp-server/src/server.ts`,
    `tools/support/signer-compat.ts`, `tools/state-direct-recovery.ts`) is
    updated to name a 5xx or 429 from Haven alongside the transport failure,
    malformed body and older-backend 404 it already named.

  Why the perimeter is unaffected:
  - The change is entirely on the read side of the signing handoff. A
    non-answer now produces a different `code`, `message` and `fallback` on a
    failure result; it produces no signature, no submission and no audit
    entry, exactly as the refusal it replaced did. Nothing that was refused
    becomes signable, and nothing that was signable becomes refused.
  - The `typed_data_b64` relay it now points at is the same relay the signer
    already offered for a timeout, an unreachable host and a malformed body.
    The relayed bytes still pass the same digest re-derivation and
    Haven-binding verification, so a relayed payload cannot authorise anything
    the fetched one could not.
  - No key role is added or widened, no relay discretion is introduced, and no
    new authority exists over a payment. The signer's one network capability
    remains an authenticated read.
