- **#4866** — the demo merchant reports Stripe's verdict on each recording,
  sends Stripe only payments to its current deposit address, and reads the
  chain in `eth_getLogs` windows its RPC provider serves. The merchant still
  sells only its own demo product; no third-party funds are received or moved,
  and Haven is not a party to the transfer.

  What changed (`packages/demo-merchant-mcp/src/`):
  - **`stripe.ts`.** Stripe verifies a `transaction_verification` PaymentIntent
    after create returns (`processing`, then `succeeded` or a decline), and
    allows one PaymentIntent per transaction, permanently (#4854 sandbox run).
    The recorder now reads the status — on the metadata search result, and
    after a create every 3 s for up to 60 s — and only a `succeeded`
    PaymentIntent counts as recorded. A decline is logged as
    `[stripe] record_declined` with Stripe's decline code, and an undecided one
    as `[stripe] record_pending`. A create refused with `resource_already_exists`
    reads the PaymentIntent Stripe names; only that `pi_…` ID is taken from the
    error, never the message. `recordStripePayment` sends only a payment whose
    transfer paid the current deposit address: a payment recovered to the
    previous address (`STRIPE_PREVIOUS_DEPOSIT_ADDRESS`) is logged as
    `[stripe] not_recorded … reason=paid_other_address` and not sent, because
    Stripe would decline it permanently.
  - **`stripe-reconcile.ts` / `reconcile-cli.ts`.** The report gains `pending`
    and `declined`; `recorded` and `already_recorded` hold only succeeded
    PaymentIntents. Exit 2 now also covers a decline; a new exit 3 covers an RPC
    or Stripe error that stops the run, printed as one line naming the error
    class — never a stack trace or an error message, which can carry the RPC URL
    and so an API key. The recorder's log lines go to stderr, the JSON report to
    stdout.
  - **`log-range.ts` (new), `cdp.ts`, `index.ts`.** `eth_getLogs` is read in
    windows of at most 500 blocks, narrowed by `ETH_GETLOGS_MAX_BLOCK_RANGE` and
    by the limit the provider names when it refuses — the backend's rule (#4012),
    mirrored. Reconciliation used to ask for the whole range in one call, and
    #4851's recovery search asked for 500-block chunks; the public Base Sepolia
    RPC serves 200.
  - **`http.ts`.** `/healthz`'s `stripe` block keeps `recorded` and
    `record_failures` and gains `pending` and `declined`. `recorded` changes
    meaning: it counts PaymentIntents Stripe accepted, not every create (#4853's
    shard describes the old meaning).

  Why the perimeter is unaffected:
  - Recording stays downstream of settlement and fire-and-forget: no Stripe
    answer, read or wait can delay or refuse the goods. Fewer PaymentIntents
    are created (none for a payment to the previous address), never more.
  - The Stripe key's use is unchanged: create and read PaymentIntents. The new
    read (`GET /v1/payment_intents/<id>`) is covered by the read permission the
    README already requires.
  - The one payment-path effect: #4851's recovery search can now complete on a
    provider that serves fewer than 500 blocks, so on the dev merchant a used
    authorization whose window is proven empty, or whose transaction paid
    someone else, is refused as #4851 intended instead of always served. On
    mainnet nothing changes unless the provider refuses a 500-block window. The
    rule for what is served or refused is #4851's, unchanged.
  - No key, route, scope, authority surface or settlement step changes.

  Tests: `stripe.test.ts` (declined after create, processing then succeeded,
  pending at the bound, a declined search hit with no create,
  `resource_already_exists` read back by the named ID, the verdict mapping, an
  unsafe decline code kept out of logs), `stripe-recording.test.ts` (a payment
  recovered to the previous address is served and not sent to Stripe),
  `stripe-reconcile.test.ts` (a declined PaymentIntent listed as declined; a
  1,001-block range through a real viem client on a node that refuses over 200
  blocks), `reconcile-cli.test.ts` (new: an RPC error is one line with exit 3 and
  no URL or key; declined exits 2; pending exits 0; stdout carries only the
  report), `cdp-chain-reader.test.ts` (a node that serves 200 blocks: the limit
  is learned, the window searched whole, `not_in_window` proven, the event
  found, and the limit kept for the next search) and `log-range.test.ts` (new).
  Mutation cells, each going red: the recovery search reverted to fixed
  500-block chunks (`cdp.ts`); every status treated as succeeded (`stripe.ts`);
  the deposit-address check removed (`stripe.ts`); reconciliation reverted to
  one `getLogs` over the whole range (`stripe-reconcile.ts`); the
  `resource_already_exists` ID dropped (`stripe.ts`); the CLI's catch removed
  (`reconcile-cli.ts`).

  Perimeter unchanged.
