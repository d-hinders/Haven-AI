- **#4856** — the demo merchant's receipt for the Stripe-recorded product says
  the Stripe reference is pending and states an indicative SEK amount; the
  seller block comes from configuration; the demo-merchant wording is brought
  up to date. The merchant still sells only its own demo products, and no
  third-party funds are received or moved.

  What changed (`packages/demo-merchant-mcp/src/`):
  - **`invoice.ts`** (the demo wrapper; the shared core in
    `packages/merchant-payments` is untouched). With a Stripe context, and only
    for a payment settled on chain, the receipt gains `stripe_referens`
    (`Väntar`, plus the receipt number and transaction hash the PaymentIntent
    is found by) and `belopp_sek` (amount, rate, source and time, or
    `Ej tillgängligt vid köptillfället`), in the JSON and as two sections of
    the rendered text. `resolveReceiptSeller` reads `MERCHANT_SELLER_*`: none
    set gives the demo seller unchanged; the four required values give that
    seller, with `iban` and `bic` only when each is set; a partial set warns
    and keeps the demo seller.
  - **`sek-rate.ts`** (new). A USDC→SEK rate cache from CoinGecko's public
    spot price (`coingecko_spot`, the backend's own provenance string),
    refreshed every 10 minutes in the background and stale after an hour. The
    purchase path only reads the cache, synchronously.
  - **`stripe.ts`.** `stripeRecordingDecision` is the one rule for whether a
    payment is sent to Stripe; `recordStripePayment` and the receipt both read
    it, so the receipt says "pending" exactly when a record is sent.
  - **`http.ts`, `server.ts`, `index.ts`.** The seller and the rate feed are
    passed to the receipt; the feed starts only when Stripe recording is on.
    The banner names the seller and the rate source.

  Why the perimeter is unaffected:
  - Nothing on the receipt is read by a settlement, refusal or authority
    decision; the blocks and the seller are display and bookkeeping data.
  - The merchant never waits for Stripe or for the rate source: the rate is
    read from a cache, and a hanging Stripe call still returns the receipt
    with the reference pending (test). The order of receipt and recording
    from #4880 is unchanged.
  - The new outbound call is an unauthenticated read of a public price,
    carrying no payment, buyer or merchant data, and nothing reads its answer
    except the receipt text.
  - The SEK amount is labelled indicative and never presented as Stripe's
    figure; with no fresh rate the receipt says so instead of estimating.
  - Haven's accounting keeps reading `saljare.name`, `org_nr` and `moms_nr`;
    a configured seller keeps those keys (test).
  - Wording: `packages/demo-merchant-mcp/README.md` and
    `docs/architecture/04-x402-payment-sequence.md` now say Haven is the
    merchant only of its own demo products and receives payment only for
    them, moving no funds on anyone else's behalf; the joke is verified and
    settled by Coinbase's facilitator (CDP), every other product by the
    merchant's own key (owner decision on #4856, 2026-11-17). The guardrails'
    "Haven acting as merchant of record" line is not edited.

  Tests: `receipt-fixtures.test.ts` (the joke receipt pinned before the
  change; with a Stripe context, with and without a rate, the JSON is that
  receipt plus exactly the two keys and the text is that text with the two
  sections inserted; no block for a payment not settled on chain; the two
  backend fixtures unchanged), `stripe-recording.test.ts` (over HTTP: pending
  reference with receipt number and hash, SEK amount with rate, source and
  time; not available with no rate and with no feed; pending while Stripe
  hangs; no block with Stripe off, for a VPN product, and for a payment to
  the previous deposit address; a configured seller on the receipt),
  `sek-rate.test.ts` (parsing, caching, ageing out, failures keep the last
  rate, `current()` never fetches, the refresh interval) and
  `seller-config.test.ts` (none set, all set, optional bank details, each
  required value missing). Mutation cells, each going red: the settled-on-chain
  guard; the paid-other-address decision; the no-rate branch; the demo IBAN
  leaking into a configured seller; the English render without the sections;
  a rate that never goes stale; the HTTP layer not passing the Stripe context.

  Perimeter unchanged.
