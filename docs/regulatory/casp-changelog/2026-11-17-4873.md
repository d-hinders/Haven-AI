- **#4873** — the demo merchant becomes the first merchant that asks for
  checkout details. One product (`vpn_pro`) advertises the
  `haven-checkout-details` extension in its 402 challenge, asking for a receipt
  email and a billing address, both optional; a paid request may answer with an
  `X-Checkout-Details` header, and the merchant's receipt shows the values in
  full in the buyer block. Every other product's challenge is unchanged, a
  malformed or oversized header is treated as absent, and a paid request that
  arrives without the header is served exactly as today. The merchant still
  sells only its own demo products, and no third-party funds are received or
  moved.

  What changed:
  - **`packages/merchant-payments/src/checkout-details.ts` (new).** The wire
    shape `docs/architecture/13-checkout-details.md` §2 and §3 fixes: the
    extension key and version, the three field names, the address shape, the
    1,536-byte answer budget, the challenge-entry builder, and
    `acceptCheckoutDetails`, which reads the header and never throws. A header
    that is absent, over budget, not base64url(JSON), not an object or not
    version 1 is "no details"; a field without the shape is dropped.
  - **`packages/merchant-payments/src/receipt.ts`.** `buildReceipt` takes an
    optional `checkoutDetails` and adds `receipt_email`, `billing_address` and
    `shipping_address` to the buyer block only when they are present, so a
    receipt without them keeps its exact shape. The Swedish and English renders
    print them under KÖPARE / PAYER.
  - **`packages/demo-merchant-mcp/src/products.ts`.** `vpn_pro` carries the
    request; `checkoutDetailsForProduct` is the one reader, and
    `requiredCheckoutFieldFromEnv` is the dev-only hook that makes one optional
    field required (testnet-only, enforced in code, off by default).
  - **`packages/demo-merchant-mcp/src/x402.ts`.** `buildPaymentRequired` and
    `demoMerchantExtensions` advertise the entry when the product asks for one.
    The echo rule is unchanged: the client echoes the entry verbatim like every
    other extension.
  - **`packages/demo-merchant-mcp/src/http.ts`.** The challenge carries the
    product's request; the paid request's header is read after settlement and
    passed to the receipt; the header is added to the CORS allow-list.
  - **`packages/demo-merchant-mcp/src/server.ts` / `invoice.ts`.** The in-band
    quote advertises the same request the HTTP 402 does, and the receipt
    builder passes the details through.
  - **`packages/demo-merchant-mcp/src/stripe.ts`.** No code change: the record
    sent to Stripe deliberately does not read the buyer block's checkout
    details, and a test pins that.

  Why the perimeter is unaffected:
  - **No settlement behaviour changes.** The header is read AFTER the payment
    has settled, like the tax declaration and the passport check. A malformed,
    oversized or absent header is "no details" and the purchase is served; the
    header never refuses a payment, never changes a price, and never changes
    what is verified or settled.
  - **No new authority, custody or route.** The merchant still verifies and
    settles its own payments with its own key (or through CDP for the joke),
    and the challenge's `accepts` entries are unchanged. The extension is
    advertised on one product and echoed by the client; it carries no payment
    term.
  - **The values are the owner's own data, shared only with the merchant the
    owner's agent is paying.** The merchant does not store them beyond the
    response and does not log them. The paying client reports the merchant's
    receipt back to Haven, so they are stored in `merchant_receipts` and
    attached in the owner's accounting connections — the owner's own
    bookkeeping record (owner decision 2026-11-17, see #4868).
  - **The Stripe record does not carry them.** The PaymentIntent metadata keeps
    the receipt number, the VAT treatment and amount and, from an accepted
    declaration, the buyer's declared VAT number and country. The email and the
    addresses are never read into it.
  - **The paywall proxy's receipts are unchanged.** It calls the same
    `buildReceipt` without checkout details, so its buyer block keeps its exact
    shape; the backend accounting fixtures still reproduce byte for byte.

  Mutation cells, each going red: the extension advertised on every product;

  is absent; the header read before settlement; an oversized header parsed; a

  Perimeter unchanged.
