- **#4882** — One recipient-naming order on every surface: own account,
  contact, Haven catalog merchant, receipt seller name, resource host. The
  surfaces are the dashboard, the transactions list, its search and CSV,
  analytics, and the agent ledger and its CSV. **Display only:** two new
  read-only reverse lookups in `infra/repositories/merchants.ts`, and new
  optional name fields on transaction and ledger rows. No authority, custody,
  route, address handling for payments or money movement changes. The new
  lookups do not share `MERCHANT_FUNDING_AGGREGATES_SQL`, which feeds funding
  derivation.
  - **Catalog step.** A payment is named by a catalog merchant only when
    every live row at that receiving address on that network belongs to one
    merchant, all of them Haven-curated `operator` rows, at least one an
    active, verified x402 row, and the merchant's verified x402 offers there
    all name this one address (the funding derivation's own "verified
    payTo"). Seller-listed `bazaar` rows never name a payment, and an
    ambiguous address names nobody. Owner decision 1 of 2026-11-17 on #4882.
  - **Accepted residual — catalog address spoofing.** `merchant_catalog.pay_to`
    comes from the merchant's own payment challenge. Domain verification
    proves the domain, not control of the address. A curated merchant that
    advertised someone else's address would have that person's payments
    shown under the merchant's name, on screen and in the CSV exports. The
    owner accepted this on 2026-11-17, limited to Haven-curated rows. An
    address-ownership proof would close it, and would be its own slice.
  - **Receipt borrowing.** A receipt seller name whose key (NFKD, case,
    spacing, punctuation and invisible characters folded away) matches any
    catalog merchant's name is used only at an address the catalog records
    for that name: a CURATED row's address when any curated merchant holds
    the name (so a seller-listed copy of a curated name cannot vouch for its
    own address), else the seller-listed rows' own addresses (so an honest
    seller keeps its receipt name on its own payments). If the lookup behind the rule fails, no receipt name is used at
    all (fail closed). **Residual:** the key compares spelling, so look-alike
    letters from another script, and names with no Latin letter or digit,
    are not caught.
  - **Accountant-facing change.** The transactions CSV `counterparty_name`
    and the agent ledger CSV `counterparty_name` now follow this order. The
    address columns are unchanged, so on a funding-leg row of the
    transactions CSV the name is the merchant's while the address stays the
    funding address. Documented in `docs/product/recipient-names.md`.
  - **Mutation-tested:** the order's steps, the catalog uniqueness, operator,
    verified, agreement and chain rules, the borrowing rule (curated-only
    addresses) and its fail-closed read (prove-red cells, all caught).
