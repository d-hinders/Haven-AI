- **#4890 (second PR)** — the demo merchant's Coinbase payment core moves into
  the shared package `@haven_ai/merchant-payments`, which the paywall proxy
  (#4893) will settle through. It adds two time bounds on chain reads and
  otherwise leaves the demo merchant's behaviour unchanged. The first #4890 PR
  (PR #4917, shard `2026-11-17-4890.md`) moved the receipt builder.

  What changed (`packages/merchant-payments/src/`, new unless noted):
  - **`cdp.ts`** (from `packages/demo-merchant-mcp/src/cdp.ts`): the Coinbase
    facilitator client (lazy `@coinbase/x402` + `@x402/core`), the bounded
    facilitator call, the credentials check, the chain reader
    (`authorizationState`, the `AuthorizationUsed` event search, and the check
    that the transaction paid this merchant the price). The chain and the USDC
    address are parameters. `createViemChainReadClient` accepts Base (8453) and
    Base Sepolia (84532) and throws for any other chain; there is no default.
  - **`payment-checks.ts`** (from `x402.ts`): every check the merchant makes
    on its own quote before Coinbase is called (the quoted option, network,
    asset and USDC domain, recipient, amount, resource, extensions echo, the
    EIP-3009 signature and validity window, the searchable-window limit), with
    the chain, network, USDC address and domain as a `PaymentAsset` parameter,
    plus the error types. The demo re-exports the same classes, so there is
    one `PaymentError` identity.
  - **`cdp-settlement.ts`** (from `x402.ts`): settlement through Coinbase with
    the chain as the judge of every failure, and the recovery of an
    authorization already used on-chain. The logic is unchanged.
  - **`settle-once.ts`** (from `x402.ts`): the settle-exactly-once coordinator
    every rail uses. It now records each payment in a consumed-payment store.
  - **`consumed-payment-store.ts`**: the store interface of
    `docs/architecture/12-merchant-kit.md` §6 and an in-memory implementation.
    The demo merchant's processor uses one per process, so a restart forgets
    settled payments, exactly as before.
  - **`log-range.ts`** (moved whole from the demo).
  - The demo keeps self-settlement (`SETTLEMENT_PRIVATE_KEY`), settlement
    readiness, the own-key EIP-3009 path, all of ERC-7710, the QA skip-settle
    hook, the passport and the challenge builder. It passes its chain facts from
    `products.ts`.

  The two behaviour changes, both bounds on how long a request waits:
  - Every chain read the core makes is bounded at 10 s in total: the viem
    transport is built with `retryCount: 0` and a 10 s timeout, and each read is
    also raced against 10 s. Before, viem's default retried a timed-out read
    three times, about 41 s for one hung read.
  - The search for the transaction that used an authorization is bounded at
    30 s in total (`SETTLE_RESOLVE_MS`), and no new log window starts past it.
    Past the bound the recovery answers "outcome unknown": nothing is
    delivered and the buyer is told to retry the same header
    (`facilitator_retryable`), the 503 `settlement_unknown` of the design
    (#4889 §6). It is deliberately NOT served, unlike a search that fails with
    a read error: the buyer chooses `validAfter`, so a payer who cancelled the
    nonce and signed a long window could otherwise be served by a slow search,
    the hole the window limit closed in #4851 (found in review). An honest
    buyer's 300 s quote is searched in one window, far inside the bound; a
    buyer whose money moved and whose search timed out is answered retryable,
    never refused.

  Why the perimeter is unaffected:
  - The merchant receives only its own sales; the new package holds no key,
    and the settlement key (`SETTLEMENT_PRIVATE_KEY`) and the self-settlement
    client stay in the demo merchant. Coinbase's credentials go to the
    facilitator client constructor and nowhere else, as before.
  - No check is removed or reordered: every one of the merchant's own checks
    still runs before Coinbase is called, and the chain still decides every
    settle failure.
  - The two bounds shorten how long a request waits for a chain read. A
    timed-out `authorizationState` read takes the path a failed read always
    took; a timed-out recovery search is answered retryable (above), which
    serves nobody who has not paid.
  - The money-path list already covers the package (`packages/merchant-payments/src/**`,
    added by the first #4890 PR).

  Tests: the demo merchant's suite passes unchanged as the characterization
  (385 tests; the 10 log-range tests moved with the code), including
  `cdp-settlement.test.ts`, `cdp-chain-reader.test.ts`, `x402.test.ts` (the
  re-served payment is the same object; a different product is refused) and
  `erc7710.test.ts`. New in the core: `cdp.test.ts` (a hung transport, each
  read rejecting within the bound, a hung log window, the 30 s resolve bound
  stopping the scan, an unsupported chain refused, the credentials note),
  `consumed-payment-store.test.ts` (key forms, reserve, the token checked by
  hash and never returned, release, the forward cap and takeover, a delivered
  record), and `settle-once.test.ts` (the same object re-served, a different
  product refused while settling and after, a submit failure releasing the
  key, an already-used authorization recorded with and without its hash, a
  reverted transaction clearing the attempt, a transient receipt failure
  keeping the hash, a store whose release throws not hiding the buyer's
  error), and `cdp-settlement.test.ts` (a timed-out search on a used nonce is
  retryable and not served; a read error still serves with no reference; a
  completed search still decides). Mutation cells, each going red: the resolve
  deadline removed from the log read (the scan-stop test); the per-read race
  removed (three hung-read tests); the timeout branch removed from the
  recovery (the not-served test, and the reviewer's probe then serves a
  cancelled nonce); release no longer guarded (the store-throws test).

  Perimeter unchanged.
