- **#4895** — merchant services can be turned on and off, and turning them on
  creates the dedicated account merchant payments are received into. The
  account is an ordinary Haven account with the same signer rules as any other;
  nothing here holds funds, holds keys, or makes a credential sufficient to
  spend.

  What changed (`packages/backend/src/`):
  - **`db/migrations/126_merchant_services.ts` (new).** A per-user setting
    (`merchant_service_settings`: `enabled`, `enabled_at`, `disabled_at`) and a
    per-account marker (`smart_accounts.is_merchant_account`), plus a PARTIAL
    unique index `smart_accounts_one_merchant_per_user` on `(user_id) WHERE
    is_merchant_account`. The index is the invariant: one merchant account per
    user is enforced by the database, not by a route remembering to check.
    `account_entitlements` (032) was the other candidate and is the wrong
    shape — it models paid add-ons granted by hand, keyed `(user_id,
    entitlement)`, with no account dimension.
  - **`modules/accounts/create-additional.ts` (new).** The create-additional
    logic EXTRACTED from `routes/hybrid-accounts.ts`, verbatim and
    behaviour-unchanged, as a function that takes the caller's transaction. The
    extraction is what lets the turn-on route commit the setting, the account
    and the marker together; the #4024 replay/race suites are its
    characterization tests and are unchanged.
  - **`routes/merchant-services.ts` (new).** `POST` turns merchant services on
    in one transaction (setting + account + marker), `DELETE` records the
    setting as off and keeps the account and its history, `GET` returns the
    setting and the merchant account. The request names no account to mark —
    the account is the one the request creates — and the body is closed
    (`additionalProperties: false`), so a body naming one is refused by the
    schema. Every refusal carries a code: the existing
    `SOURCE_ACCOUNT_NOT_FOUND` / `SOURCE_HAS_NO_PASSKEY` / `KEY_NOT_ON_SOURCE` /
    `ACCOUNT_CAP_REACHED`, a new `UNSUPPORTED_NETWORK` (the create-additional
    path answered that case with a sentence and no code), and a new
    `MERCHANT_ACCOUNT_ON_OTHER_NETWORK` for a merchant account that already
    exists on another chain.
  - **`domain/merchant-services.ts` (new).** The refusal codes and the
    `merchant-service:` idempotency-key namespace. `POST /accounts/hybrid` now
    refuses a client-supplied key in that namespace (the spec's `pattern`), so
    a user cannot pre-create an account under the key the turn-on route derives
    and have the merchant marker land on it.
  - **`routes/user-accounts.ts`.** Unlinking the merchant account is refused
    with `MERCHANT_ACCOUNT_UNLINK_REFUSED` (unlinking is a hard DELETE of the
    account row and its indexed payments), and making it the default is refused
    with `MERCHANT_ACCOUNT_DEFAULT_REFUSED`.

  Why the perimeter is unaffected:
  - The merchant account is a normal `smart_accounts` row: one passkey copied
    server-side from a source account the caller already owns, no EOA owner, no
    agents, no budgets, never the default. The server receives no passkey
    assertion — the session is the authentication, and the passkey id is only
    checked for membership on the source account.
  - Nothing moves funds. The route records a pointer (which account merchant
    payments are received into) and a setting; the account it points at is
    governed by the same signer, delegation and budget rules as every other
    account. Haven still holds no key and signs nothing here.
  - The one-account-per-user rule is a database constraint, and the network is
    fixed at first turn-on for the pilot, so the feature cannot be used to
    accumulate receiving accounts or to migrate one between chains.
  - The idempotency namespace closes the only path by which a user could have
    chosen the account the marker lands on.

  Tests: `routes/__tests__/merchant-services.test.ts` (every refusal code, the
  repeat/second-tab answer, the different-network refusal, the closed body, the
  read scoping) and `routes/__tests__/merchant-services.db.test.ts` on the
  real-Postgres harness (the partial unique index refusing a second merchant
  account, setting + account + marker committing together, off/on reusing the
  same account, the reserved idempotency namespace). Mutation cells, each going
  red: dropping the marker from the turn-on transaction; removing the
  existing-merchant-account check; removing the partial unique index; removing
  the `merchant-service:` pattern from the create-additional schema.

  Perimeter widened, not narrowed: `routes/merchant-services.ts`,
  `modules/accounts/create-additional.ts` and `domain/merchant-services.ts`
  join `.github/money-path-globs.json`.
