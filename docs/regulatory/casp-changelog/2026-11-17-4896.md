- **#4896** — the receive-only merchant key. A new credential the merchant's
  server uses to report sales to Haven, created, listed by prefix and revoked by
  the account owner through dashboard routes. It is NOT an agent key: its own
  prefix (`sk_merchant_`), its own table (`merchant_keys`), never stored in
  `agents`, and it authenticates only the merchant routes (sales ingest, #4897).

  What changed (`packages/backend/src/`):
  - **`db/migrations/127_merchant_keys.ts` (new).** `merchant_keys` holds
    `key_hash` (SHA-256 hex, UNIQUE), `key_prefix` (the display prefix), the
    account the key is bound to (`account_id` → `smart_accounts`), and the four
    who/when columns (`created_by`/`created_at`, `revoked_by`/`revoked_at`) plus
    `last_used_at`. A CHECK keeps the revocation pair honest: both set or both
    null. The secret itself is never stored.
  - **`middleware/merchantAuth.ts` (new).** The check beside `agentAuth.ts` and
    `auth.ts`. It accepts only `sk_merchant_` credentials, resolves the account
    from the key row (never from the request), refuses a revoked key, a key
    whose account is no longer a merchant account, and every key of an account
    whose merchant services are off. It writes nothing; the throttled
    `last_used_at` write is an `onResponse` hook that fires only on a 2xx.
  - **`routes/merchant-keys.ts` (new).** `POST` mints a key for the caller's
    merchant account and returns the secret in that one response; `GET` lists
    prefixes only; `DELETE` records who revoked the key and when, idempotently.
    The create body is closed (`additionalProperties: false`), so a body naming
    an account to bind the key to is refused by the schema.
  - **`domain/merchant-keys.ts` (new).** The fixed prefix, the refusal codes and
    the one hashing rule.
  - **`infra/repositories/merchant-keys.ts` (new).** The storage layer; the auth
    lookup scopes the account to the key's own user in the JOIN.
  - **`openapi/spec.ts`, `index.ts`.** The three operations, the module
    registered at `/merchant-keys`, born ENFORCED in the request-validation
    list, and the root-scope last-used hook.
  - **The secret scrubbers.** `modules/feedback/secret-check.ts`,
    `modules/agents/agent-connection-setup.ts`, `packages/cli/src/secret-check.ts`,
    `packages/connect/src/redact.ts` and
    `packages/qa-agent/src/evals/redact-sessions.ts` all recognise
    `sk_merchant_`; the CLI and connector CHANGELOGs carry an entry.

  Why the perimeter is unaffected:
  - The key cannot move funds, sign, change signers, budgets or agents, read
    another account, or read anything about its account except what the merchant
    routes return. It is a bearer credential for the RECEIVE side: it can
    describe payments that already reached its account and cannot create one.
    The on-chain transfer remains the control (#4897 accepts a sale only against
    a transfer Haven read itself).
  - The account is the key's, resolved from the row. There is no request field
    that names an account, so a key cannot act for another account — including
    the same user's other accounts — and the auth JOIN scopes the account to the
    key's own user.
  - The off switch is the owner's: while merchant services are off, every key of
    that account is refused, so turning the feature off does not leave a live
    credential behind.
  - Only a hash and a prefix are stored. The secret is returned by the create
    call and by no later read, and every secret scrubber in the repository
    recognises the prefix, so it cannot reach a log line, a feedback body, a
    connector report or a QA transcript.
  - The key is refused at every agent, payment and dashboard route by
    construction: `agentAuthMiddleware` accepts only `sk_agent_`, and
    `authMiddleware` treats anything else as a session token and fails
    verification. The tests prove this by showing the refusal goes red when the
    same secret is stored in `agents` with the agent prefix.

  Tests: `middleware/merchantAuth.test.ts` (every refusal branch, the
  prefix/table mutation proof, the account binding, the last-used hook),
  `routes/__tests__/merchant-keys.test.ts` (the route contract: secret returned
  once, list prefixes only, revoke idempotent, closed body, no merchant account
  refusal) and `routes/__tests__/merchant-keys.db.test.ts` on the real-Postgres
  harness (the UNIQUE hash, the revocation CHECK, a revoked key refused, the off
  switch refusing every key, the last-used throttle, account scoping, and the
  create/list/revoke cycle). The mutation cells are recorded in the pull
  request.

  Perimeter widened, not narrowed. `middleware/merchantAuth.ts` joins the
  runtime list beside `agentAuth.ts`; `routes/merchant-keys.ts` and
  `domain/merchant-keys.ts` join the control list, because no QA scenario calls
  the dashboard routes yet.
