- **#4903 — every payment into a merchant account is indexed without anyone looking (epic #4885).** The receive index used to be fed only as a side effect of someone loading an account's transaction feed, from the explorers, newest first and capped per read. A merchant account nobody browsed was not indexed, and one that received more payments between reads than the cap lost the older ones. This slice adds a scheduled pass that reads the chain itself, a read of one transaction by hash, and the row identity that lets a transaction's several USDC legs be counted in full.

  What changed (`packages/backend/src/`):
  - **`db/migrations/128_inbound_transfer_identity.ts` (new).** The row identity becomes `(chain_id, LOWER(tx_hash), account_id, log_index)` — a transfer's on-chain identity is its log. `log_index` stays nullable because not every source reports it, so the migration takes the **separate-unique-index-for-the-unknown-case** option: a partial unique index on `(chain_id, LOWER(tx_hash), account_id, log_index) WHERE log_index IS NOT NULL`, and a second partial unique index on `(chain_id, LOWER(tx_hash), account_id, payer_address, amount_raw) WHERE log_index IS NULL`. The old `(chain, hash, account)` index is dropped: it is strictly weaker than the unknown-case index and would refuse a second leg. The migration also adds `sender_is_own_address` (decided at index time) and `inbound_index_cursors` (one cursor per account). **Reconcile rule for rows collapsed before it:** no row is rewritten by the migration; every pre-existing row has `log_index IS NULL` and keeps deduping exactly as before. At ingest time a leg whose log index is known ADOPTS the unknown row written from that same leg (same chain, hash, account, payer and amount) by filling in the index — the adopted row keeps its amount, its match and its `balance_consumed` flag — and every other leg of that transaction is inserted as a new row with `balance_consumed = false`. The receive balance is therefore unchanged for an account whose rows were collapsed, while every leg is indexed. A row no leg matches (one planted through the old caller-supplied route) is never adopted. **The cross-source rule, in both directions:** the two partial indexes are disjoint, so the same leg can arrive from the chain pass (log index known) and the explorer read (Alchemy reports none) in either order, and both orders land ONE row. Explorer first, chain afterwards is the adoption above; chain first, explorer afterwards is a mirror guard in `insertInboundTransfer` that SKIPS an unknown-index leg when a known-index row already exists for the same `(chain, hash, account, payer, amount)` — an explicit `WHERE NOT EXISTS` folded into the insert, because a partial index cannot span both cases. The receive balance is unchanged in both directions. `down()` is deliberately not lossless: it recreates the old index and fails loudly if multi-leg rows exist rather than deleting money-path rows.
  - **`modules/transactions/chain-read.ts` (new).** Two chain reads, both of which ask the chain and never a caller: `readInboundTransfersByTxHash` (the transaction's receipt, its settlement-token `Transfer` logs whose `to` is the account, with their exact log indices) and `readInboundTransfersInBlockRange` (`eth_getLogs` over the account's `to` topic, chunked by the provider's own served span — `effectiveLogBatchBlocks`, #4012). The settlement asset is the registry's USDC by ADDRESS, so a contract that merely names itself USDC is not it. Zero-value transfers are left out. An unreadable chain is `ok: false`, never an empty result: an RPC outage must not become "this transaction did not pay you".
  - **`modules/transactions/merchant-index.ts` (new).** The scheduled pass: every account with `smart_accounts.is_merchant_account` (NOT filtered by `merchant_service_settings.enabled`, so indexing continues while merchant services are off), read from `cursor.last_indexed_block + 1` to `latest`, at most `MAX_BLOCKS_PER_PASS` (10,000) blocks per tick. The first pass seeds the cursor at the block carrying the account's creation time (binary search over block timestamps), so it neither scans from genesis nor misses payments that arrived before the first tick. The cursor moves only after the range was read AND written; a failed read leaves it untouched so the next tick retries. Per-account failures are isolated.
  - **`background-jobs.ts`.** A new row, `merchant inbound index`, every 5 minutes, leader-locked on `LEADER_LOCK_KEYS.merchantInboundIndex` (811013). **Stated figure: a payment into a merchant account is indexed within 5 minutes of the next tick, with no dashboard open.**
  - **`infra/repositories/inbound-transfers.ts`.** The two-identity upsert with the adoption rule above and its mirror guard (an unknown-index leg is skipped when a known-index row for the same leg exists), the already-matched guard in `findUnmatchedByTxHash` (a row whose `(chain, hash, account, payer, amount)` leg is already matched is never matched again, so a replayed receipt drop cannot double-count); `listMerchantAccounts`, `findInboundIndexCursor` / `upsertInboundIndexCursor` (monotonic — `GREATEST`), and `listOwnAccountAddresses` (the set `sender_is_own_address` is decided against; #4897 defines it and may widen it, which is why the flag is recorded per row rather than derived at read time).
  - **`modules/transactions/receive.ts`.** `explorerRowsToLegs` (the explorer read's rows, filtered to inbound settlement-token legs with a non-zero amount, carrying `logIndex` when the provider reports one — Blockscout v2 does), `ingestInboundTransfers` over legs, and `readInboundTransferByTxHash`.
  - **`routes/receive.ts` — the caller-supplied ingest route, decided.** `POST /receive/{accountAddress}/ingest` used to insert an inbound row from values the caller sent, with no chain check; a row planted through it would block the real one and could then be matched as a sale. **Decision: it verifies against the chain.** It takes only `tx_hash`, reads the receipt, and indexes the settlement-token transfers whose `to` is the account. A body naming a payer, amount, token or block time is refused with 400 — by the schema and, when request validation is shadow/off, by the handler. 404 means the chain says the transaction carried no USDC transfer to the account; 503 means the chain could not be read and nothing was written. The ledger read also serves `log_index` and `sender_is_own_address`.
  - **`infra/explorer-api.ts`.** `RawERC20Transfer.logIndex` (optional) and the Blockscout v2 mapper populating it from `log_index`.

  Why the CASP perimeter is unaffected:
  - Nothing here holds a key, signs, moves funds, or settles for anyone. The pass reads the chain and writes the receive index; the by-hash read is read-only; the ingest route writes index rows only. The rows it writes are UNEARNED until matched, exactly like every other inbound row, and nothing is delivered on an unearned row.
  - The chain is the only source of a transfer's facts. The token is the registry's settlement asset by address; the payer, amount, log index and block time come from the log and the block. No route accepts a caller's description of a transfer any more, so from this change on no route can create a row for a hash that did not pay the account. Rows written before it by the old caller-supplied ingest route can still exist, and they carry `log_index NULL` exactly like explorer-derived rows, so a row's presence is not proof the chain carried it: the sales ingest (#4897) stores a sale only from its own by-hash chain read, never from an existing `inbound_transfers` row (recorded on #4897).
  - The pass is idempotent and safe with two replicas: leader-gated, and the writes converge regardless (the row identity dedupes; the cursor only moves forward).
  - Indexing continues while merchant services are off, so a merchant's history stays complete — the account list is the marker, not the setting.

  Perimeter widened, not narrowed. `modules/transactions/chain-read.ts`, `modules/transactions/merchant-index.ts` and `background-jobs.ts` join the CONTROL list in `.github/money-path-globs.json` (and `.github/labeler.yml` and the perimeter doc): no QA scenario drives the scheduled pass or the by-hash read yet — #4897's route does not exist — so a green money-flow run says nothing about them. They move to the runtime list when a QA leg drives the by-hash read. The repository they write and the migration are already on the runtime list through `infra/repositories/**` and `db/migrations/**`.

  Added RPC usage per merchant account per day: the pass runs every 5 minutes (288 ticks/day). Since the review fix below, the cursor stays at the settled block, so a tick reads from the settled block to the head: Base's finalized lag (typically several hundred blocks) or 300 blocks on the depth fallback, plus the ~150 new blocks — so a quiet tick is **one `eth_getBlockNumber`, one `eth_getBlockByNumber('finalized')` and about two `eth_getLogs` calls** at the 500-block default span (more when the provider's learned limit is narrower — #4012); a tick that finds payments adds **one `eth_getBlockByNumber` per distinct block that carried a payment** (cached per chain+block). Re-reading the tail writes nothing new: the row identity dedupes. A backlog is walked at up to 10,000 blocks per tick, so a long outage costs more ticks, not a wider single request.

  Verdict: **Perimeter unchanged.** The slice adds a read-only chain indexer, a read-only by-hash read and a chain-verified ingest route; it holds no key, signs nothing, moves no funds, and grants no authority.
