- **#4932** — A receipt's seller name is merchant-written text, and two kinds
  of it named nobody while still reaching every surface as a "name": an
  address (written in full, or in Haven's own short form `0xA873…DD35`) and
  Haven's own fallback words ("New recipient", "Agent payment", "Deposit" and
  the rest). The display side now refuses both, once, inside each receipt
  candidate of `RECEIPT_MERCHANT_NAMES_SQL` (`infra/repositories/analytics.ts`),
  after the name has been cleaned. A refused name counts as "no usable name",
  exactly like an empty or oversized one: the `DISTINCT ON` falls back to an
  older usable receipt and the flat `merchant_name` fallback still applies.
  The lookup has one caller (`loadRecipientNameIndex`), so one rule covers
  every surface the name reaches — the analytics merchants and agents tables,
  the dashboard's 7-day summary and first-payment card, the transactions and
  agent-ledger wire fields and CSVs, and transactions search (a refused name
  also stops being searchable by that text, which is intended).
  - **The rules.** Address-shaped: the cleaned candidate is refused when it
    matches `^0[xX][0-9a-fA-F]{40}$` (core's `ETH_ADDRESS_RE` plus an
    uppercase `0X`; the SQL pattern is BUILT from the core source, so the two
    cannot drift) or the short form
    `^0[xX][0-9a-fA-F]{2,40}[[:space:]]?(…|\.\.\.)[[:space:]]?[0-9a-fA-F]{2,40}$`.
    Fallback words: an exact match, ASCII case-folded and whitespace-collapsed,
    against `HAVEN_FALLBACK_NAMES` in `@haven_ai/core` (the backend builds its
    SQL from that constant, and the frontend renders the same literals), or a
    name starting with "From " or "Returned from " — the frontend's templated
    fallbacks. The check runs on the CLEANED value, so a zero-width character
    inside an address cannot slip it past.
  - **Scope: display only, receipt names only.** The change is read-only and
    narrows which names are shown. No authority, custody, route, address
    handling for payments or money movement changes; receipt names reach no
    spend picker. Contact and own-account names are the user's own words and
    are never refused. The frontend's `isAddress` guards (#4883) stay: they
    are cheap and cover any non-receipt source.
  - **The accounting underlag is deliberately NOT covered.**
    `sellerFromMerchantReceipt` (`modules/accounting/receipt-underlag.ts`)
    quotes the invoice's seller as written, refusals included, because a
    pinned underlag must re-render byte-identically (#4824). The two sides
    read the same block; only the display side refuses these names.
  - **Accepted residual.** The fallback-word comparison is ASCII case folding,
    so full-width look-alikes ("Ｄｅｐｏｓｉｔ") and trailing punctuation
    ("Deposit.") pass through and still name the seller. The address patterns
    are anchored to the whole name, so an address with a prefix or suffix
    ("Seller 0x…") is not refused either.
  - **Mutation-tested:** removing the address rule turns its test red (the
    address-shaped refusal, the older-receipt fallback and the flat
    `merchant_name` fallback all fail); removing the fallback-word rule turns
    its test red (the same three). The over-match guard — "Deposit Partners
    AB", "0x Labs", "Fromage AB", "Deposits AB", "Returned fromage AB" still
    name the seller — sits beside them, and the SQL full-address pattern is
    pinned to core's `ETH_ADDRESS_RE`.

  Perimeter unchanged.
