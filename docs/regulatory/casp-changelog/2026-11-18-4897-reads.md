- **#4897 — the owner's sales reads and the clear route (epic #4885, PR B of two).** The sales ingest (`2026-11-18-4897.md`) stores a merchant's sale record against a transfer Haven read from the chain. This PR is the owner's side: four owner-session routes that read the sales back and let the owner clear a wrong record. No frontend; the Sales page (#4900) consumes them.

  What changed (`packages/backend/src/`):
  - **`routes/merchant-sales-reads.ts` (new), `modules/transactions/merchant-sales-reads.ts` (new), `infra/repositories/merchant-sales-reads.ts` (new).** `GET /merchant-sales/summary?from&to` (the tiles, `own_moves`, and `by_product`, `by_payer` and `by_day`), `GET /merchant-sales/payments?from&to&cursor&limit` (one row per transaction, newest first, keyset on `(block_time, tx_hash)`, default 50, at most 200), `GET /merchant-sales/payments/:txHash` (the row plus its transfer legs) and `DELETE /merchant-sales/payments/:txHash/record`. All are dashboard-JWT routes, enforced by the request-validation plugin from their first commit. The Sales key is `sk_merchant_...` and the JWT check refuses it (401); a device-login token cannot clear a record (the route is on the census's must-refuse list). Day boundaries are UTC, `from` and `to` inclusive. The reads need merchant services on and the caller's merchant account; off, or no account, they answer the zero state as `routes/merchant-catalogue.ts` does, and the clear answers 409 `MERCHANT_ACCOUNT_REQUIRED`. Every statement is scoped by `user_id` and `account_id`.
  - **One rule for every figure.** The totals, the three breakdowns and the list are cut from one per-transaction relation over the indexed transfers into the account, never from the receive balance or a match kind. Zero-value transfers are not in it; a transfer with `sender_is_own_address` is not revenue. A transaction with a sale row counts once, with the sale's own `amount_raw` (its legs are never added on top); a payment with no sale row counts as revenue without a product, with the sum of its non-own legs; a transaction paid only from the owner's own addresses is an `own_move`: in the list, marked, and in no revenue figure. A sale from several payers, and a payment with no record from several payers, is not attributed in `by_payer` (it is reported as `unattributed`, so the breakdown still adds up to revenue). The breakdowns name the top 100 and fold the rest into `*_other`. `own_moves` counts the transactions that are own moves, so the notice and the list agree.
  - **Payer kinds.** Each payer is a contact (the caller's address book), one of the caller's own addresses (an account, or an agent's delegate address, current or replaced by rotation, revoked agents included: `listOwnAccountAddresses`, with the existing name loaders for accounts and contacts and one new lookup for agent names by delegate address), or a wallet (the address, no name). Only the caller's own accounts, agents and contacts are ever consulted, so another Haven user's agent or account reads as a wallet like any other address, and nothing in a read tells the merchant otherwise.
  - **The label.** `product_label` is the catalogue's name when the product id is known there (`labelSaleProduct`, #4899), else the record's name, else the product id.
  - **Clearing a record.** Deletes the `merchant_sales` row, scoped by account and user; the transfers stay, so the payment remains with no product, and a new record for the transaction is then accepted by `POST /merchant/sales`. The route carries `moneyPathRateLimit` and logs who cleared what. It deletes the merchant's statement and never a transfer.
  - **`db/migrations/132_inbound_transfers_account_time.ts` (new).** An index on `inbound_transfers (account_id, block_time DESC)`: the access path for one account's transfers over a period, which no existing index served. An access path only; no column or constraint changes. 131 is untouched.
  - **`db/migrations/133_inbound_transfers_own_flag_backfill.ts` (new).** A one-time backfill: sets `sender_is_own_address = true` on every existing `inbound_transfers` row whose payer is in the widened own set of the row's own `user_id` (smart accounts, agent delegates, delegates replaced by rotation, in SQL). Rows indexed before migration 128 had the flag defaulted false and rows between 128 and the ingest were stamped against smart accounts only, so an agent delegate's transfer counted as revenue while its payer read `own`. The reads stay index-time (no read-time exclusion). `down()` is a no-op. **Residual:** an ingest whose own-address lookup fails stamps false (`receive.ts`) and nothing repairs that row. Migration 132's index is now built `CONCURRENTLY` (non-transactional).
  - **`openapi/spec.ts`, `openapi/route-modules.generated.ts`, `index.ts`, `modules/transactions/index.ts`.** The four operations and their schemas, the regenerated route-module map and API types, the route registration, and the module's exports.

  Why the CASP perimeter is unaffected:
  - Nothing here holds a key, signs, moves funds or settles for anyone. Three routes read; the fourth deletes a merchant's own statement about a payment, on the owner's decision, and cannot touch the transfer, the receive balance or any match.
  - Every figure is the chain's: the sale's amount, payer, token and time were copied from the chain read at ingest, and a payment with no record is shown from the indexed transfers.
  - A Sales key reaches none of the four routes, and a device-code session cannot clear a record.

  Mutation-tested (each cell reddens the named test, in `merchant-sales-reads.db.test.ts`):
  - Revenue sum keeping the owner's own legs (`merchant-sales-reads.ts` repository) -> "a payment with no record and an own leg beside a customer leg counts only the customer's transfer".
  - A payment with only own legs counted as revenue -> "the totals, the breakdowns and the list agree for the same period" and "a transfer from the owner's own address is in no revenue figure".
  - `amount_raw > 0` loosened to `>= 0` -> "a zero-value transfer is never a sale, a payer or revenue" and the agreement test.
  - A sale's legs added on top of its row -> "a sale is counted once with its own amount".
  - Dropping the several-payers condition from `by_payer` -> "a sale from several payers is not attributed by payer".
  - Preferring the record's name over the catalogue's, or dropping the record's name -> "the product label is the catalogue name, else the record name, else the product id".
  - Treating a delegate address that has an agent name as one of the caller's own, with the agent lookup unscoped by user -> "is a contact, an own address or a wallet, and another Haven user's agent is a wallet".
  - Reads without the account scope -> "reads only the caller's merchant account"; the clear without account and user scope -> "another user cannot clear a record, and the record stands".
  - The clear keeping the record -> "deletes the record, keeps the payment with no product, and accepts a new record afterwards".
  - The owner routes accepting a `sk_merchant_` key -> "a Sales key reaches none of the four routes".

  - A new test seeds a row stamped false whose payer is the owner's agent delegate; after the backfill it is excluded from revenue and its payer is `own` -> removing the user scope, or the agent arm, of the backfill turns it red. Folding at 101 products and payers pins `rn <= 100` / `rn > 100`; the clear route's 429 pins its rate limit; a tampered cursor answers 400.

  Known cost: the list and detail reads re-aggregate the whole period on every page (about 0.85 s for one whole-history page at 130,000 transfers); not optimised here.

  Perimeter widened, not narrowed. `routes/merchant-sales-reads.ts` and `modules/transactions/merchant-sales-reads.ts` join the CONTROL list in `.github/money-path-globs.json` (and `.github/labeler.yml` and the perimeter doc): no QA scenario calls `/merchant-sales` yet. The repository and migration 132 are already on the runtime list through `infra/repositories/**` and `db/migrations/**`.

  Verdict: **Perimeter unchanged.** Read-side routes over the receive index, and the owner deleting a merchant's record; no key, no signing, no funds, no authority.
