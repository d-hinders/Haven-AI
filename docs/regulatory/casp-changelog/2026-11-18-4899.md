- **#4899** — the merchant's catalogue is read from its kit's discovery document
  and kept, so Haven can name a product on a sale and show the owner what the
  account sells. The read only LABELS: it never changes an amount, creates a
  sale, or names a recipient.

  What changed (`packages/backend/src/`):
  - **`db/migrations/130_merchant_catalogue.ts` (new).** Two tables of its own,
    neither of them `merchant_catalog`:
    `merchant_catalogue_sources` (one row per merchant account: the deployment
    address the owner saved, the outcome of the last read, and what the last
    GOOD document said) and `merchant_products` (the list, keyed
    `(merchant_account_id, product_id)`). The separation is the slice's point:
    `merchant_catalog.pay_to` fills the recipient of a merchant-locked budget
    and feeds the public catalogue, and neither may be reachable from
    merchant-supplied data. A product the document no longer lists is marked
    `offered = false` with `removed_at` set and KEPT, so a past sale still names
    it. `price_atomic` is TEXT — the merchant's own atomic amount as a decimal
    string, a label here, never charged. Number 130 because 128 and 129 are
    reserved by in-flight #4903 and #4870; inserted in sorted order in
    `db/migrations/index.ts`.
  - **`infra/http/ssrf-guard.ts`.** A `sameHostOnly` option on the shared guard
    and a `redirect_off_host` refusal. The guard follows up to three redirects
    ACROSS hosts by default, which is right for a probe of a merchant's own
    endpoint and wrong for a document a merchant names as its catalogue: a
    redirect to another host would let the merchant point Haven's read at a
    document it does not serve. With the option set, an off-host hop is refused
    before it is resolved or connected to; a same-host hop is still followed and
    re-validated from scratch. No second fetcher: the catalogue read is
    `safeGetText` with the option, so it keeps the guard's scheme and shape
    rules, its resolution-time address classification, its socket pinning and
    its budgets.
  - **`modules/catalog/merchant-products.ts` (new).** Reads
    `/.well-known/x402` from the saved address — the document URL is built from
    the address's origin, so the read targets `<origin>/.well-known/x402` and
    never the deployment root, which the proxy answers with a 404 — parses the
    kit document
    (`12-merchant-kit.md` §4), and keeps the list. A document whose `pay_to` or
    `network` is not the merchant account's is a MISMATCH: recorded as such, and
    its products are NOT written — a document that is not this account's
    deployment must not label this account's sales. An unreachable, refused or
    malformed document records the outcome and leaves the last good list in
    place. `labelSaleProduct` is the rule #4897's reads use: the catalogue's
    name when the product id is known there (offered or not), otherwise the name
    the sale record carried.
  - **`routes/merchant-catalogue.ts` (new).** `PUT /merchant-catalogue/deployment`
    saves the address and reads it immediately, so the answer to the save is the
    catalogue the document produced; `POST /merchant-catalogue/refresh` reads it
    again on request; `GET /merchant-catalogue` is the owner's read. The address
    is stored as the deployment's ORIGIN — path, query and fragment are dropped
    — so a pasted path cannot become the path Haven reads. The address
    is checked by the guard's own pure policy (`assertSafeUrl`) before it is
    stored, so an address Haven would refuse to read is refused at the field
    with the guard's `reason`. A CHANGED address retires the list the old one
    produced (marked not offered, not deleted). The module is born ENFORCED in
    `index.ts`, and its save body is closed (`additionalProperties: false`).
  - **`background-jobs.ts` + `platform/leader-lock.ts`.** An eleventh row, the
    merchant catalogue refresh, every 15 minutes — the approved mockup's cadence
    for an unreachable kit, and the schedule for a reachable one — under a new
    leader key `merchantCatalogueRefresh` (811013), so two replicas do not read
    the same deployment at once. One source's failure never stops the pass.
  - **`openapi/spec.ts`.** The three paths and the two schemas
    (`MerchantCatalogueState`, `MerchantCatalogueProduct`).

  Why the perimeter is unaffected:
  - The document's `pay_to` is COMPARED against the merchant account's own
    address and stored as a label on the source row. It is never used as a
    payment destination, and nothing in this slice reads it into a budget, a
    delegation or a transfer.
  - The product list is its own table. Nothing here writes `merchant_catalog`,
    so a merchant cannot reach the value that fills a merchant-locked budget's
    recipient or the public catalogue. A test asserts `merchant_catalog` is
    untouched by a read.
  - The read only labels. It changes no amount, creates no sale, signs nothing,
    submits nothing and calls no facilitator. `price_atomic` is stored as text
    and never charged.
  - The fetch is the shared guard, not a second fetcher, and it is stricter than
    the default: same-host redirects only, plus the guard's own refusal of a
    host that resolves into private or local space.
  - Money-path list: `db/migrations/**` already covers the migration;
    `modules/catalog/merchant-products.ts`, `routes/merchant-catalogue.ts` and
    `domain/merchant-catalogue.ts` join the CONTROL list, on the same rule as
    #4895/#4896/#4893 — no QA scenario calls `/merchant-catalogue`, so a green
    money-flow run says nothing about them.

  Pinned by tests: `modules/catalog/__tests__/merchant-products.test.ts` on the
  real-Postgres harness (the list matches the document; a removed product is
  kept, marked not offered and still names a sale; a mismatched `pay_to` or
  `network` writes no products and leaves the last good list; an unreachable,
  malformed or refused read leaves the list and records when it was last read; a
  changed address retires the old list; `merchant_catalog` is untouched; the
  parser refuses a document with no version, no network, no receiving address or
  no products array, skips a product it cannot understand, and reads a higher
  version for the fields it knows), `routes/__tests__/merchant-catalogue.test.ts`
  on the same harness (the address policy refusals with the guard's reason and
  nothing stored, the save reading immediately, a failed read not failing the
  save, the mismatch, the refresh with no address, the closed body, every answer
  against the OpenAPI spec) and three `sameHostOnly` cases in
  `infra/http/__tests__/ssrf-guard.test.ts` (an off-host hop refused without
  being resolved, a same-host hop followed, a chain that leaves and returns
  refused at the first off-host hop).

  Perimeter widened, not narrowed.
