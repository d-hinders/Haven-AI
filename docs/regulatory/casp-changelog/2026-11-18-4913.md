- **#4913**: the merchant kit's receipt, in `@haven_ai/paywall-proxy`
  (`packages/paywall-proxy/src/receipt.ts`, the response path in `handler.ts`,
  the settings in `config.ts`). A paid call through the proxy now returns the
  merchant's own receipt as the `x-receipt-json` response header, built by the
  shared core from #4890 (`buildReceipt`, `receiptNumberForTransaction`,
  `acceptTaxDeclaration`) and following the canonical shape in
  `docs/operations/merchant-receipt-shape.md`. The kit's receipts join the demo
  merchant's as backend accounting fixtures.

  What it does:
  - The receipt carries the seller block from the deployment's configuration
    (`SELLER_NAME`, `SELLER_ADDRESS`, `SELLER_ORG_NR`, `SELLER_VAT_NR`,
    optional `SELLER_IBAN` / `SELLER_BIC`), the buyer block when the request
    carried an `X-Tax-Declaration` that verifies against the payer on this
    chain and is unexpired, the VAT treatment the configured rule gives that
    declaration, one line from the products-file entry, and a receipt number
    derived from the settlement transaction hash. It names no Haven address or
    contact; the support contact is the merchant's.
  - `VAT_RULE` is the merchant's decision. The pilot has one value,
    `SE_25_WITH_EU_REVERSE_CHARGE`: 25% Swedish VAT taken out of the price, and
    reverse charge (VAT 0%, both VAT numbers) for an accepted declaration from
    another EU country. The proxy defines no VAT computation, no
    receipt-number derivation and no declaration verification of its own; it
    calls the shared builder.
  - With no `VAT_RULE` there is no receipt: no header, and no seller detail is
    required. With a rule, the seller's name, organisation number and VAT
    number are required — on Base mainnet the proxy refuses to start without
    them, on a test network it starts with a warning and sends no receipt.
  - The header is sent with the response headers of a delivered call (a 2xx
    passed through, or a 3xx/4xx wrapped into a 200), and the proxy removes
    `x-receipt-json` and `x-receipt-url` from the upstream's response. A
    receipt that cannot be built never fails a settled call: the header is
    left out and the failure is logged. The merchant key and the buyer's
    declaration are never logged.
  - The encoded header is bounded at 64 KiB decoded, the limit at which the
    SDK drops it and the backend refuses it.

  Why the perimeter is unaffected:
  - The receipt is display and bookkeeping data downstream of settlement. No
    settlement, refusal or authority decision reads it, and the change adds no
    key, route, scope or settlement step. The price never changes with the
    treatment: VAT is taken out of the price, never added to it.
  - The declaration check is display only, exactly as in the demo merchant
    (#4855): a missing or refused declaration is treated as absent and never
    gates a purchase.
  - The new settings are identity strings and a tax rule the merchant chooses.
    None is a credential, and none reaches a payment decision: `PAY_TO`,
    `NETWORK` and the products file still decide what is charged and where it
    goes.
  - Money-path list: `packages/paywall-proxy/src/**` stays a control glob, by
    the owner decision on #4893.

  Pinned by tests: `receipt.test.ts` (the shared document from the deployment,
  the product line and the payment; SE_25 and reverse charge; a declaration
  that fails any check treated as absent; the number stable from the hash; the
  64 KiB bound), `receipt-proxy.test.ts` (end to end: the header on a paid
  call, no header without a rule, the upstream's own receipt headers removed,
  reverse charge from a real signed declaration, a malformed declaration
  treated as absent, a receipt that cannot be built leaving the call green and
  logging `receipt_failed`, the number kept across a restart),
  `receipt-fixtures.test.ts` (the two backend fixtures regenerated byte for
  byte with the clock injected), `config.test.ts` (the rule and seller
  requirements, mainnet refusal vs testnet warning), and the backend's
  `kit-receipt-fixtures.test.ts` (Haven's reader accepts each fixture, the
  stated total matches the settled amount, the seller is read correctly).

  Perimeter unchanged.
