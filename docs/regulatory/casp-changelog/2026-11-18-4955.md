- **#4955** — the shared rate-limit bucket is keyed on the identity the route's
  auth verified, never on the raw text of a header. It changes the throttle on
  agent and owner payment routes; it moves no money, signs nothing and changes
  no authority.

  The defect: `rateLimitKeyFor` hashed whatever `Authorization` held, else
  `X-API-Key`. Agent auth accepts `Authorization` only as
  `Bearer sk_agent_…` and otherwise reads `X-API-Key`, so an agent sending
  `Authorization: Bearer junk-<n>` beside its valid key landed in a fresh bucket
  on every request and the 60/min money-path ceiling on `POST /payments`,
  `POST /x402/authorize` and `POST /payments/:id/sign` never bound. On the
  per-IP routes (signup, login, device start and token, ops sign-in, catalog
  submit, the receipt drop) any header at all moved the caller out of the IP
  bucket.

  What changed (`packages/backend/src/`):
  - **`middleware/rate-limit.ts`.** `rateLimitKeyFor` now reads only fields an
    auth hook sets after verifying the caller: `request.merchant.key_id`
    (`merchant_key:`), `request.agent.id` (`agent:`), the operator `opsAuth`
    admitted (`ops:<GitHub id>`), the verified JWT `sub` (`user:`), else
    `ip:<request.ip>`. It reads no header. This works because
    `@fastify/rate-limit` pushes its check onto the end of each route's own
    `onRequest` array, and every rate-limited authenticated route runs its auth
    as an `onRequest` hook, so auth has admitted the caller first; a refused
    credential is answered 401 before the limiter, as before. A route whose
    auth ran later would find no identity and fall back to the IP bucket: a
    collapse, never a bypass.
    - `merchantRateLimitKeyFor` (#4897's per-route generator for
      `POST /merchant/sales`) is removed and the Sales tier uses the shared
      rule, so the rule exists once.
    - The unused `demoRateLimit` is removed with the header line that said the
      demo routes use it.
  - **`middleware/ops-auth.ts`.** `admittedOpsOperator(request)`, a
    non-throwing read of the operator `createOpsAuth` admitted.

  Behaviour changes, stated:
  - An owner is now one bucket across sessions (two tabs share 20/min on the
    company-details writes and 60/min on the money-path owner routes). Before,
    each JWT value was its own bucket. Two owners behind one proxy address
    still never share a bucket.
  - An ops operator is one bucket across sessions on reveal and search.
  - An agent is keyed by its id, so a re-keyed agent keeps its count.
  - The bucket names changed from `cred:<hash>` to the prefixes above, so the
    live counters in `rate_limit_counters` reset once at deploy (each window is
    one minute).

  Docs and comments updated to the new keying: `index.ts` (the plugin
  registration note), `rate-limit.ts` (header, `moneyPathRateLimit`, ops
  reveal and search, `ownerProfileRateLimit`, feedback), the webhook note in
  `routes/accounting-webhooks.ts`, the `ownerProfileRateLimit` 429 and
  description text in `openapi/spec.ts` (and the generated
  `packages/core/src/api-types.ts`), `docs/product/owner-company-details.md`
  and `docs/operations/feedback-channel.md`.

  Tests: `routes/__tests__/rate-limit-identity-keys.test.ts` (new) drives the
  real plugin, the real agent, owner and ops auth hooks and the real payments,
  x402 and hybrid-accounts route modules: a junk Bearer beside a valid
