- **#4959 — the Sales reads take filters, a search and per-payer "last paid" (epic #4885).** The backend half of the Sales page's search and filters (#4960 is the page). Read-only: one new read route, new query parameters and new fields on two reads. Nothing here moves or signs anything.

  What changed (`packages/backend/src/`):
  - **`infra/repositories/merchant-sales-reads.ts`.** The per-transaction relation gains a filtered view, `pay_f`. Every list, count and summary figure reads it, so for one filter set the totals, the breakdowns, `received_in_stripe`, the `total` and the rows agree.
    - The filters are statement parameters, never a cut made after the fetch, so keyset paging stays exact.
    - `kind` matches the existing kinds; `product_id` matches sales only.
    - `payer` matches a payment whose single payer is that address. A payment from several payers matches when any of its legs is from it, read in the same scan of `inbound_transfers` (`BOOL_OR` per transaction).
    - The search arrives resolved to addresses and product ids. Only the receipt number (`ILIKE`, wildcards escaped) and an address prefix are matched in SQL.
    - The scope (`account_id`, `user_id`, chain) is unchanged on every statement.
    - New: `countPayments` (the list's `total`), `readPeriodFacets`, and `listPeriodSaleProducts` (the products that a search term is resolved against, read from `merchant_sales` alone).
    - `by_payer` carries `last_paid_at`. `by_day` splits each day's sales by the products `by_product` names, folds the rest into `other_products_raw`, and adds `without_product_raw`. That split is the scope addition recorded on the issue, which lets #4960 stack the chart by product.
  - **`modules/transactions/merchant-sales-reads.ts`.** `resolveSalesFilters` resolves the search term in JS:
    - against the caller's own contacts, accounts and agents, through the same resolver the reads use to name payers (`buildPayerDirectory`);
    - against the period's product labels (`labelProducts`).

    Another Haven user's account or agent name is in no index this file reads, so it can never match. That wallet is found only by its address. `readSalesFacets` serves `GET /merchant-sales/facets`. `labelProducts` now labels every product of a read with one catalogue query (`labelSaleProducts` in `modules/catalog/merchant-products.ts`, `findCatalogueProductNames` in `infra/repositories/merchant-catalogue.ts`), not one query per product, since the search and the facets label every product of the period. The rule is the same: the catalogue's name, else the record's name, else the id.
  - **`routes/merchant-sales-reads.ts`.** The summary and the list pass the filters through. The new `GET /merchant-sales/facets` sits behind the same owner-session door (`authMiddleware`; a Sales key is refused 401). Repeatable filters are normalized to lists in the handler as well as by the spec, so a handler mounted without the validation plugin cannot bind a bare string to a `text[]`.
  - **`openapi/spec.ts`, `packages/core/src/api-types.ts`, `openapi/route-modules.generated.ts`.** The four parameters (validated: a `kind` enum, a 40-hex `payer`, a bounded `product_id`, and a `q` of 2 to 100 characters with two non-space ones), the facets path and schema, `total`, `last_paid_at` and the day split. Regenerated.

  Why the CASP perimeter is unaffected:
  - Every change narrows or describes the same caller-scoped relation. No statement reads beyond the caller's merchant account, and the new route is a read of that relation.
  - The search widens nothing a read can reach. Its name matching runs only over the caller's own data, the same data the reads already show.
  - No key, no signing, no funds, no authority, no write. The one write in these files (the owner clearing a sale record) is untouched.

  Tests (`routes/__tests__/merchant-sales-reads.db.test.ts`, real Postgres):
  - **Agreement.** The summary agrees with the list for each filter alone, for two combined and for the search. A Stripe-held sale is included, so `received_in_stripe` is checked too.
  - **Several payers.** A payment from several payers is matched by either payer and stays unattributed.
  - **Privacy.** Another user's agent and account both pay the merchant. Neither name matches the search, and each wallet is found by its address.
  - **Validation.** Malformed filters get the plugin's 400 `invalid_request`, and an unknown parameter is ignored.
  - **Search literals.** LIKE wildcards in the term are literal (`__`, `%%` and `r-_` match no receipt). The shortest address prefix is `0x` and four hex digits, and three digits do not count.
  - **Last paid.** `last_paid_at` is the newest revenue payment in the period, and a Stripe-held sale is not in it.
  - **Facets and total.** The facets name every product and payer, uncapped past 100, and `total` counts the filter set across pages.
  - **Day split.** It follows the top 100 and folds the rest.
  - **Sales key.** A Sales key reaches none of the five routes.

  The volume test (`merchant-sales-reads-volume.db.test.ts`, opt-in) gains a filtered summary case and a filtered list case, each with a stated time budget.

  Proved red against `origin/dev`'s sources, with the routes, module, repository and spec swapped in: all 9 new or changed tests fail. Mutation-tested: 21 mutations, each run against the suite, and each reddens a named test. They cover:
  - the summary or `received_in_stripe` reading the unfiltered relation;
  - the payer filter ignoring the legs of a payment from several payers;
  - the product filter matching non-sales;
  - the search skipping product ids, the receipt number, the address prefix, the term itself or case folding;
  - the term's LIKE wildcards left unescaped, or a three-digit prefix accepted as an address;
  - the batched label read skipping products no longer offered (a past sale of a retired product keeps its catalogue name);
  - `last_paid_at` taken as the oldest payment;
  - the facets capped at 100 or missing the legs of payments from several payers;
  - `total` taken as the page length;
  - the day split not capped at the top 100;
  - `q` accepting spaces only;
  - the route dropping the filters.

  One more cell turns the agent names global. On its own it changes no answer, because a name attaches only to the caller's own addresses. Paired with a resolver that names any agent address, it reddens the privacy test and the payer-kind tests.

  Perimeter unchanged. The two Sales read files are already on the CONTROL list in `.github/money-path-globs.json`, and the repository is on the runtime list through `infra/repositories/**`.

  Verdict: **Perimeter unchanged.** Read-only filters and a read route over the caller's own merchant account; no key, no signing, no funds, no authority.
