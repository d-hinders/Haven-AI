- **#4872 (part 2a) — checkout details on the hosted MCP-merchant paths (epic #4868).** The keyless hosted server now answers a merchant's checkout-details request, or refuses, on the MCP-merchant flow. The design is `docs/architecture/13-checkout-details.md`; part 1 (#4979) did the SDK and local paths. The plain-HTTP and state-direct paths follow in part 2b.

  What changed:
  - **`packages/backend/src/modules/x402/merchant-call-context.ts`.** `GET /x402/:id/merchant-call-context` serves `checkout_details_request`: the merchant's request taken verbatim from the challenge already stored at authorize (#1355). Field names and required flags only, merchant content, untrusted. No new storage and no migration; the owner's values are never stored.
  - **`packages/sdk/src/client.ts`, `client-checkout-details.ts`.** `readCheckoutDetails()`, so the keyless hosted server can read the agent's own details (never throws; every failure is a named state). `getX402MerchantCallContext` carries the stored request. `resolveCheckoutDetails` takes the option actually paid, so an erc7710 settlement is sized as erc7710. An honest wording for a settlement that was never sent ("nothing was redeemed").
  - **`packages/mcp-server/src/tools/support/checkout-details.ts` (new).** One module for both halves: the refusal before the intent, and the answer at settle measured on the actual payment header.
  - **`catalog-purchase.ts`.** `haven_pay_mcp_tool` and `haven_prepare_catalog_purchase` refuse a required field the agent cannot share after the quote, cap and scheme and before `prepareX402Erc7710` or `createX402Intent`: no funding intent and no settlement child exist.
  - **`paid-mcp-completion.ts`.** Settle decides before anything is spent: on EIP-3009 before the funding signature is relayed (availability and the real header block on the agent's own header); on erc7710 availability before the settlement child is submitted, and only the block after it — a refusal there sends nothing, so nothing is redeemed (`unsent`). A before-spend refusal stands only while the intent is still `pending_signature`: a repeated settle of a payment that already moved gets the submit's or relay's own answer (the settled replay on erc7710), never "nothing moved", and any delivery then decides as `funded` or `unsent`. On the settle leg the refusal says "Nothing was funded, submitted or sent for this payment", because the intent exists. The complete leg (already funded) decides after the funding wait (`funded`). An explicitly threaded context still reads the stored request, and only the merchant URL the payment was quoted for receives the details (`merchant_mismatch` otherwise). The answer rides only the paid `tools/call`, through the SDK's new `paidRequestHeaders`, never the MCP handshake.
  - **`support/errors.ts`.** The hosted mapper answers `CHECKOUT_DETAILS_UNAVAILABLE` as the local one does, with a `phase` and an omitted reason per stage: only a refusal before payment says to call again; a funded one names `haven_complete_mcp_tool` or verify-then-sweep; an unsent one says to start a new purchase.
  - **Pay tools.** A required request whose challenge is too large to be stored (over 64 KB) is refused at pay time; with an `idempotency_key` the refusal says this call created nothing and points at an earlier payment.

  Why the CASP perimeter is unaffected:
  - **No custody.** The hosted server still holds no key and signs nothing. The answer is unsigned data the owner saved and turned on for this agent.
  - **No widening.** Every change is a refusal before an intent, a refusal before delivery, or one header to the seller. No amount, recipient or authority changes.
  - **Seller only, in memory only.** The values pass through the hosted server's memory to the merchant. They are never stored, logged, returned in a tool result or merged into the echoed `extensions`; a hosted test asserts a known value is absent from the result and from stdout, stderr and the console.

  Tests: `packages/mcp-server/src/tools/checkout-details-hosted.test.ts` — refusal before any intent on both pay tools with no `POST /x402`; the replay wording; the 64 KB refusal; no read when nothing is asked; the answer on settle and complete, only on the paid request; the EIP-3009 settle refusal with NO funding relay; the funded complete refusal and its step; the explicit-context flow answering, and a mismatched URL refusing before funding with no read; erc7710 availability refused with nothing submitted, the same refusal standing while still `pending_signature`, a repeated settle of an already-settled payment with sharing off answering the settled replay, the answer on erc7710, and the unsent refusal after submit; no value in the result or the logs on success and refusal. The SDK's `x402-checkout-details-flow.test.ts` drives the real `completeX402MerchantCall` and shows the answer on `tools/call` only, never on `initialize` or `notifications/initialized`. The backend `x402-delegation.test.ts` pins the request served verbatim and absent when nothing was asked.

  Mutation-tested: 20 mutations, each run against the suites, and each reddens a named test:
  - either pay tool's check removed; a read when nothing was asked; the 64 KB rule dropped; the replay wording dropped;
  - the settle decision moved to delivery (read twice, after the relay); the settle refusal swallowed; the erc7710 block check after submit removed; the status gate removed (a repeated settle refused as "nothing moved"); the settle-leg wording reverted to the pay tools';
  - the explicit context skipping the stored request; a mismatched URL not flagged;
  - the answer on the handshake (hosted and in the SDK's delivery);
  - the funded and unsent steps saying "retry"; the hosted mapping dropped;
  - the SDK dropping the stored request; the backend not serving it;
  - the complete leg deciding before the funding wait.

  Perimeter unchanged. The touched files are already in `casp-risk-guardrails.md`'s scope.

  Verdict: **Perimeter unchanged.** A refusal before an intent or a delivery, and one unsigned header to the seller from the keyless server; no key, no signing, no funds, no authority.
