- **#4872 (part 2b) — checkout details on the hosted plain-HTTP path (epic #4868).** The keyless hosted server now answers a merchant's checkout-details request, or refuses, on the plain-HTTP flow, where the agent sends the paid request itself. The design is `docs/architecture/13-checkout-details.md`; part 1 (#4979) did the SDK and local paths and part 2a (#4992) the hosted MCP-merchant paths. This part completes the issue.

  What changed:
  - **`packages/backend/src/modules/x402/stored-challenge.ts` (new), `routes/x402.ts`.** `GET /x402/:id/payment-required`, read-only and agent-scoped: the merchant's challenge as already stored at authorize (#1355), for any x402 intent of the calling agent. It writes nothing and stores nothing new; the same credential could already read the same challenge through the signer's sign-context. Not found and not yours are one 404; a non-x402 intent is a 409.
  - **`packages/sdk/src/client.ts`.** `getX402StoredPaymentRequired(paymentId)` reads it, normalized by the parser every challenge goes through (`null` when nothing usable was stored).
  - **`packages/mcp-server/src/tools/plain-http-x402.ts`.** `haven_pay_x402_quote` refuses a required field the agent cannot share after the cap and scheme and before `prepareX402Erc7710` or `createX402Intent`, in both its modes: no funding intent and no settlement child exist. The same SDK decision as the MCP-merchant pay tools.
  - **`state-direct-recovery.ts` (`haven_submit` with a `payment_id`).** It reads the stored challenge and decides BEFORE it spends. On EIP-3009 that is before the funding signature is relayed, with availability and the header block estimated from the stored challenge (the agent's payment header never reaches this tool). On erc7710 it is availability before the settlement child is submitted and the real block right after it; a refusal there returns no `payment_header`, so nothing can be redeemed (`unsent`). A before-spend refusal stands only while the intent is still `pending_signature`, as on settle; an unreadable state refuses as `state_unknown`. The answer comes back for the agent's own retry, in `retry_headers` on erc7710 and in `additional_retry_headers` on EIP-3009, and never on the MCP-tool flow, where `haven_complete_mcp_tool` sends it itself. A direct payment has no stored challenge and reads nothing.
  - **`support/checkout-details.ts`.** The pending-signature rule is one helper (`checkoutDetailsWhilePending`) that `haven_settle_mcp_tool` and `haven_submit` both call, unchanged in behaviour for settle.
  - **`support/errors.ts`.** The `unsent` and `state_unknown` next steps name both legs (settle or submit) and `haven_pay_x402_quote`, instead of the MCP-merchant tools only.
  - **Descriptions.** `haven_pay_x402_quote`, `haven_submit` and `haven_resume_x402_payment` gain one sentence each. The hosted resume is not a supported path: its resume state carries no merchant extensions, and its description says a resume sends no answer.

  Why the CASP perimeter is unaffected:
  - **No custody.** The hosted server still holds no key and signs nothing. The answer is unsigned data the owner saved and turned on for this agent.
  - **No widening.** Every change is a read of the agent's own stored challenge, a refusal before an intent, a refusal before a relay or submit, or one header returned for the agent's own request to the seller. No amount, recipient or authority changes.
  - **Seller only, never stored or logged.** On this path the agent sends the paid request, so the hosted server returns the answer in the `haven_submit` result, in the retry headers and nowhere else in it (owner decision 2026-11-17, design §6). It is never stored, logged or merged into the echoed `extensions`; a hosted test asserts a known value, and the encoded header, are absent from stdout, stderr and the console, and from the rest of the result.

  Tests: `packages/mcp-server/src/tools/checkout-details-plain-http.test.ts`, 19 tests through the real handlers and the real keyless client — the pay tool's refusal with no `POST /x402` (sharing off, nothing stored, the `idempotency_key` wording), no read when nothing is asked, an optional field proceeding; on erc7710 the answer in `retry_headers` only, today's headers when nothing is asked, the refusal before submit while pending, the unsent refusal after submit and its step, the settled replay on a repeated submit, `state_unknown`, and a failed challenge read proceeding as today; on EIP-3009 the answer in `additional_retry_headers` only and decided before the relay, the refusal before the relay, the MCP-tool flow returning no answer, a direct payment reading nothing, the relay's 409 on a repeated submit, and the estimated block refusing before the relay. The SDK's `client-x402-stored-payment-required.test.ts` and the backend's real-database `x402-payment-required.test.ts` pin the read.

  Mutation-tested: 20 mutations, each run against its suite, and each reddens a named test:
  - the pay tool's check removed;
  - erc7710: the check before submit removed, the block after submit skipped, the answer left out of `retry_headers`, the value logged;
  - the pending rule removed, an unreadable state skipping the check;
  - EIP-3009: the check before the relay removed, the block estimate removed, the decision moved after the relay, the answer dropped, its reason sentence dropped, the answer returned on the MCP-tool flow;
  - a failed challenge read not tolerated, the details read when nothing was asked;
  - the `unsent` and `state_unknown` steps reverted to the MCP-merchant tools only;
  - the SDK not normalizing the stored blob; the backend serving a non-x402 intent, or not serving the challenge.

  Perimeter unchanged. The touched files are already in `casp-risk-guardrails.md`'s scope (`packages/backend/src/modules/x402/**`, `routes/x402.ts`, the SDK and the hosted server).

  Verdict: **Perimeter unchanged.** A read-only re-serve of the agent's own stored challenge, refusals before an intent or a spend, and one unsigned header returned for the agent's own request to the seller; no key, no signing, no funds, no authority.
