- **#4903 follow-up — the merchant inbound index stops re-reading the same blocks (dev Alchemy incident, 2026-11-20).** From 2026-11-19 the scheduled pass held dev at ~1M Alchemy compute units an hour, 99% `eth_getLogs` on Base Sepolia, and used most of the 30M-unit monthly pool that dev and production share. Three things combined. Alchemy's free plan serves 10 blocks per `eth_getLogs` call, so a range costs one call per 10 blocks. The cursor stopped at `finalized`, which on Base Sepolia lagged the head by 5,445 blocks (~3 hours), so every tick re-read that whole tail. And one failed chunk threw the whole range away: the dev log showed `chain read failed; cursor left unchanged` for blocks 61,244,056–61,253,523, so the next tick asked for all ~9,500 blocks again. The #4903 shard's figure ("about two `eth_getLogs` calls" a quiet tick) assumed a 500-block span and a lag of a few hundred blocks; neither held on dev.

  What changed (`packages/backend/src/`):
  - **`modules/transactions/chain-read.ts`.** `readInboundTransfersInBlockRange` returns `ChainRangeReadResult`. A failure is still `ok: false` and never an empty answer, but it now carries `partial`: every leg in `[fromBlock, readThroughBlock]`, complete for that sub-range, or `null` when no chunk was read. A block time that cannot be read ends the partial result before that block, so nothing is claimed past what was read.
  - **`modules/transactions/merchant-index.ts`.** A read that failed part-way ingests its partial legs and moves the cursor no further than `readThroughBlock`. The cursor ceiling is `max(settled, latest − MAX_UNSETTLED_REREAD_BLOCKS)` (300, the same depth `settledReadBlock` already treats as settled on a chain with no `finalized` tag), so the re-read tail is at most 300 blocks below the head however far `finalized` lags. With no settled block known the cursor still does not move.
  - **`config.ts`, `background-jobs.ts`.** `MERCHANT_INBOUND_INDEX_DISABLED=true` stops the job (unset = running). It is a kill switch for the RPC quota, not a feature flag; indexing resumes from the cursor when it is turned back on.

  Residual, stated: the scheduled pass no longer re-reads a block deeper than 300 below the head (~10 minutes on Base) when `finalized` lags further. A reorg deeper than that would not be re-read by the pass. Such a reorg has not been seen on Base. The sales ingest's own by-hash chain read (#4897) still decides whether a transfer is a sale, so a missed or stale index row cannot make or unmake a sale.

  Added RPC usage, restated per merchant account per tick (every 5 minutes): ~150 new blocks plus at most 300 re-read, so about one `eth_getLogs` call at a 500-block span, and about 45 at Alchemy's 10-block free-plan span. A part-way failure costs only the calls up to it. Batching every merchant account into one `eth_getLogs` per chunk is not done here.

  Why the CASP perimeter is unaffected:
  - Nothing here holds a key, signs, moves funds or grants authority. The pass reads the chain and writes the receive index; rows stay UNEARNED until matched.
  - The chain is still the only source of a transfer's facts, and an unreadable chain is still never "none": a partial result covers only blocks that were read in full.
  - Idempotency and the two-replica guarantee are unchanged: the cursor only moves forward (`GREATEST`) and the row identity dedupes.

  Tested (each cell reddens the named test):
  - Returning `partial: null` on a mid-range failure → `chain-read.test.ts` "keeps the chunks read before a failed chunk".
  - Claiming a block whose time could not be read → "stops the partial result before a block whose time cannot be read".
  - Leaving the cursor unchanged on a partial read → `merchant-index.db.test.ts` "keeps the legs of a read that failed part-way".
  - Dropping the settled ceiling for a partial read → "never moves the cursor past the settled block on a read that failed part-way".
  - Capping the cursor at `settled` alone → "bounds the re-read tail when the finalized block lags far behind the head".

  Verdict: **Perimeter unchanged.** A cost fix to a read-only chain indexer; no key, signature, fund movement or authority is added or changed.
