- **#5008**: the merchant kit gains a pre-flight `check` command
  (`haven-paywall-proxy check`), which tells a developer whether a deployment
  will work before it takes real traffic. It prints one line per check (`ok`,
  `fail`, `skipped` or `not verified`, and a reason in words) and exits non-zero
  when any check fails.

  What changed:
  - **`packages/paywall-proxy/src/check.ts`** (new): the checks, each reusing
    the code that already owns the rule rather than reimplementing it.
    `settings` calls `loadConfig` and prints its `ConfigError.problems` one line
    each; `products` calls `loadProductsFile` and reports
    `ProductsFileError.problems`; `rpc` calls `eth_chainId` and compares it with
    `config.chain.chainId`; `coinbase key` builds the facilitator with
    `createCdpFacilitator` and calls `getSupported()` once, then confirms the
    facilitator lists `exact` on the configured network; `sales key` posts `{}`
    to `{HAVEN_SALES_URL}/merchant/sales` and reads the answer; `store` and
    `outbox` check the directory, and the store's exclusive lock when the file
    exists.
  - **`packages/paywall-proxy/src/index.ts`**: the `check` subcommand, beside
    `report-sale`, and the usage line.
  - **`packages/merchant-payments/src/cdp.ts`**: `CdpFacilitator` gains an
    optional `getSupported()`, and `createCdpFacilitator` takes an optional
    `timeoutMs`. The interface is widened on the runtime perimeter rather than
    cast in `check.ts`, and the timeout is short because `getSupported`'s own
    default is 90 s and it retries a 429 three times.
  - **`packages/backend/src/routes/__tests__/merchant-sales.db.test.ts`**: a
    case pinning the ordering `check` relies on. An invalid key with the body
    `{}` answers `401`, not `400`, and the control (a valid key with the same
    body) answers `400 invalid_request`. Reordering auth after request
    validation turns it red.
  - **Copy**: `packages/paywall-proxy/README.md` (a `check` section, and Step 5
    pointing at it), `docs/architecture/12-merchant-kit.md` §12, and the README
    entry's `last-verified` in `scripts/docs/package-docs.mjs`.

  Why the perimeter is unaffected:
  - **No call can move money or settle.** `check` calls `getSupported` and
    `eth_chainId`, and posts an empty body to the sales route. It never calls
    `verify`, never calls `settle`, and never builds a sale record. The tests
    inject a facilitator whose `verify` and `settle` throw and assert neither is
    reached, and assert the Sales probe's body is exactly `{}`.
  - **The Sales probe writes nothing.** The route's auth runs as an `onRequest`
    hook, before Fastify's schema validation, so an invalid key answers `401`
    and a valid one answers `400` with Haven's `error_code`; the body never
    reaches the ingest, and `last_used_at` is written only when the answer is
    below 400 (`registerMerchantLastUsedHook`). The probe does log one
    `request_validation.refused` line in Haven's logs per run, which the README
    and the design do not hide.
  - **The store is not opened with its opener.** `openSqliteConsumedPaymentStore`
    creates the file and schema and clears reservation hashes, so `check` does
    not use it. It checks the directory, and, when the file exists, takes and
    releases the same `PRAGMA locking_mode=EXCLUSIVE` + `BEGIN EXCLUSIVE` lock
    without writing. A missing file reports `ok (will be created at <path>)`, so
    a mistyped path is visible and no ledger is created there.
  - **No secret is printed.** `check` never prints an error's `message`: viem
    errors embed the URL and x402 errors embed a response excerpt, so every line
    is built from an error's class and a status code. The RPC line names the
    host only, because a provider URL can embed a key. The tests assert that no
    line carries `UPSTREAM_API_KEY`, `CDP_API_KEY_SECRET`,
    `HAVEN_MERCHANT_KEY`, or the configured `RPC_URL` beyond its host.
  - **The Coinbase key check is an authenticated check.** Builder verification
    (#5008): CDP answers a well-formed but wrong key with `401` on
    `GET …/supported`, so a success there is an authenticated success and the
    line may report `ok`. A malformed secret fails locally during JWT signing
    with no network call. When the client cannot exercise the key at all, the
    line reports `not verified` and says why; it never reports `ok` on an
    unauthenticated success.

  Pinned by tests: `check.test.ts` (a complete valid Base Sepolia configuration
  prints one `ok` line per check and exits 0; a malformed products file, an RPC
  on the wrong chain, an unreachable RPC, a malformed Coinbase secret, a
  Coinbase key the facilitator refuses with 401, a facilitator that does not
  list `exact`, a Sales key answered 401, Sales off (403), a 400 without Haven's
  `error_code`, a 404 and an HTML answer, a store held by another process, and a
  missing `PAYMENTS_DB` directory each fail their own line and exit non-zero
  while the other checks still print; a missing setting prints its problem and
  `skipped (settings invalid)` for checks 3–6; a 429 is `not verified (rate
  limited)`; no line carries a secret; no `verify` or `settle` is reached), and
  `merchant-sales.db.test.ts` (the 401-before-400 ordering, with its control).

  No mutation-testing run (prove-red cells) was performed for this slice. The
  tests pin the behaviour directly: each fault is injected on its own and its
  line's status and reason are asserted as literals.

  Perimeter: `packages/paywall-proxy/src/**` is on the control perimeter and
  `packages/merchant-payments/src/**` on the runtime perimeter. The command adds
  no authority, no key handling and no money movement; it reads what the
  deployment already holds and reports it.
