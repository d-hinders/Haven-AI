- **#5012 — the merchant inbound index reads only while its owner views Sales, through the transfer index (epic #4885).** The scheduled pass (#4903) read raw `eth_getLogs` ranges every 5 minutes for every merchant account, on a clock, whether or not anything happened; on a 10-block plan that held dev at ~1M Alchemy compute units an hour (2026-11-20, PR #5004). Sales is demo-only, so the owner chose to read only while someone is looking, through Alchemy's indexed transfers API, and to fetch each payment's log index by transaction hash.

  What changed (`packages/backend/src/`):
  - **`background-jobs.ts`.** The `merchant inbound index` row is removed. `LEADER_LOCK_KEYS.merchantInboundIndex` stays reserved (`platform/leader-lock.ts`) so its number is never reused.
  - **`modules/transactions/merchant-index.ts`.** The per-account body is a function of its own (`indexMerchantAccount`). A new entry point, `refreshMerchantAccountIndex`, refreshes ONE account: it returns at once when `MERCHANT_INBOUND_INDEX_DISABLED` is set, claims the refresh (below), checks the account is a merchant account, and runs the pass. It never throws. The head is pinned once per pass; the read, the settled block and the cursor ceiling refer to that number. The pass reads through the transfer index first, with no block cap, and falls back to the capped `eth_getLogs` range read when the index is not configured. The cursor ceiling (`max(settled, head − 300)`) and the partial-read rule are unchanged.
  - **`modules/transactions/chain-read.ts`.** `readInboundTransfersViaIndex`: the index names the transactions; each is read from the chain by hash with the existing `readInboundTransfersByTxHash`, so the payer, amount, block time and exact log index of every leg come from the receipt. Two byte-identical legs in one transaction stay two rows (owner decision on #5012, option (b)). An idle range is one index call and no receipt. A failed receipt ends the partial result before that transaction's possible block.
  - **`infra/explorer-api.ts`.** `discoverInboundTokenTransferHashes`: `alchemy_getAssetTransfers` for one token into one address, oldest first, inside the range, following `pageKey` to the end (guarded at 100 pages). It returns transaction hashes only. It is a separate read from the activity feed's `fetchAlchemyTransfers`, which is unchanged.
  - **`infra/repositories/inbound-transfers.ts`.** `findMerchantAccountRow`, and `claimInboundIndexRefresh`: ONE conditional `UPDATE inbound_index_cursors SET updated_at = NOW() WHERE … updated_at <= NOW() − interval`, so at most one refresh per account per 30 s across replicas. No migration: `updated_at` exists since migration 128.
  - **`routes/merchant-sales-reads.ts`.** `GET /merchant-sales/summary` and `GET /merchant-sales/payments` fire the refresh for the caller's own Sales account (`resolveSalesScope`), without awaiting it. The answer is unchanged; a transfer the refresh finds shows on the page's next poll. No request or response shape changes.
  - **Frontend.** The Sales overview and the first-run check re-read every 10 s while the tab is visible, silently (`useSalesSummary` / `useSalesPayments` `live`).

  Why the CASP perimeter is unaffected:
  - Nothing here holds a key, signs, moves funds or grants authority. The pass reads and writes the receive index; rows stay UNEARNED until matched.
  - The chain is still the only source of a transfer's facts. The transfer index decides only WHICH transactions are read; a transaction it names is read from the chain by hash, and a transaction that did not pay the account yields no leg. A transfer the index fails to name is not indexed by this pass. The sales ingest's own by-hash read (#4897) still decides every reported sale, and the dashboard feed still writes the transfers it reads.
  - The refresh is scoped to the caller's own merchant account, and idempotent: the row identity dedupes and the cursor only moves forward, so concurrent refreshes converge. The claim limits cost, not correctness.

  Residual, stated: with nobody viewing Sales, an unreported transfer is indexed the next time the owner opens Sales, not within a fixed time (owner decision on #5012: no background reading). A reorg deeper than 300 blocks below the head is still not re-read (unchanged from 2026-11-20).

  Tested (each cell reddens the named test):
  - Treating the index read as capped by `MAX_BLOCKS_PER_PASS` → `merchant-index.db.test.ts` "reads through the transfer index from the cursor to the pinned head in ONE pass".
  - Dropping the `updated_at` condition from the claim → "claims a refresh at most once per interval, across concurrent callers".
  - Removing the kill-switch check from the refresh → "does nothing while MERCHANT_INBOUND_INDEX_DISABLED is set".
  - Reading the index's own transfer values instead of the receipt (no by-hash read) → `chain-read.test.ts` "two byte-identical legs stay two legs".
  - Claiming the failed receipt's block → "stops before the block of a receipt it could not read".
  - Stopping at the feed's page budget → `explorer-alchemy-inbound.test.ts` "follows pageKey past the feed page budget".
  - Removing the refresh call from the summary read → `merchant-sales-reads.db.test.ts` "asks for a refresh of the owner's own account".

  Verdict: **Perimeter unchanged.** A read-only indexer now runs on view instead of on a clock and finds transactions through an index before reading them from the chain; no key, signature, fund movement or authority is added or changed.
