- **#5028 — the Stripe deposit-address registry is gated to testnet Sales
  accounts (epic #4886).** #4952 specified the registry as dev and Stripe
  sandbox only, with a proof of address ownership required before any production
  use, but nothing in the code enforced that scope: the routes were registered
  in every environment and the dashboard rendered the section on every Sales
  account, so the next `dev → main` promotion would have carried the registry to
  production without the proof. This change makes the scope hold in code, per
  Sales account.

  What changed:
  - `modules/transactions/merchant-deposit-addresses.ts` gains
    `depositAddressRegistryOpen(chainId)`, the one predicate both call sites
    ask. It is `!isMainnetChain(chainId)` — the existing fail-closed testnet
    predicate (`modules/catalog/marketplace-scope.ts`), where an unregistered
    chain counts as mainnet. The registry's chain is always the Sales account's
    own, so the gate is a pure function of `scope.chainId`.
  - `routes/merchant-deposit-addresses.ts` answers 403
    `DEPOSIT_ADDRESSES_TESTNET_ONLY` from all three operations (list, register,
    retire) right after `resolveSalesScope` and before any existence check, so
    `DEPOSIT_ADDRESS_ALREADY_REGISTERED` and `DEPOSIT_ADDRESS_NOT_FOUND` are
    never answered on a gated account, and nothing is written.
  - `modules/transactions/merchant-sales.ts` treats the registry as empty on a
    non-testnet Sales account: no address is named to the chain read and no leg
    is attributed to one, so a report for a transfer into a registered address
    is answered exactly as a hash that paid nobody (422
    `no_payment_to_account`). A sale into the Sales account itself is accepted
    as today.
  - The dashboard renders the section only on a testnet Sales account
    (`SalesSetupTab`), and `classifyDepositAddressError` maps the new code to
    its own refusal kind.
  - `openapi/spec.ts` documents the 403 on all three operations and the
    generated `packages/core/src/api-types.ts` follows.

  Why the CASP perimeter is unaffected: the change narrows a money-path
  decision surface rather than widening it. The registry decides which transfers
  are attributed to an account as Stripe-held sales; on a non-testnet account it
  now decides nothing, and the routes refuse before reading or writing. No key
  is held, nothing is signed, no funds move, no balance is touched, and no
  authority is granted. The gate is a chain predicate, not an environment
  predicate: the backend has no production-configuration predicate to use
  (nothing reads `HAVEN_ENV`/`APP_ENV`), and the owner decision of 2026-11-22
  accepted the per-account testnet predicate as the whole gate — production
  Sales accounts on Base Sepolia are not excluded separately, because no Base
  Sepolia relayer is funded on production and a testnet sale has no money value.
  The ownership-proof slice removes the gate.

  Pinned by tests, both sides of each gate:
  - `routes/__tests__/merchant-deposit-addresses.db.test.ts` seeds a Base
    mainnet (8453) Sales account and pins that all three routes answer the one
    403 and write nothing (a directly seeded row stays active, a random id is
    the refusal rather than 404), that the ingest answers a transfer into a
    directly seeded registered address exactly as a hash that paid nobody, that
    the registered address is not named to the chain read, and that a sale into
    the account itself is still accepted. The existing 84532 tests pin the
    allowed side.
  - `SalesSetupTab.test.tsx` pins that the section does not render on an 8453
    account and does not read the route; the existing 84532 test pins that it
    does.
  - `merchant-services.test.ts` pins the new code's mapping.

  Mutation-tested: removing the route gate reddens the refused-side route test;
  removing the ingest gate reddens the ingest test (the chain read returns the
  leg anyway, so only the gate refuses); inverting the predicate reddens the
  allowed-side tests on 84532 and the refused-side tests on 8453.

  Perimeter: no file added or removed. `modules/transactions/merchant-deposit-addresses.ts`
  and `routes/merchant-deposit-addresses.ts` were already `controlGlobs` from
  #4952, and `modules/transactions/merchant-sales.ts` was already one from
  #4897; the `.github/money-path-globs.json` note records the change. Control,
  not runtime, unchanged: no QA scenario drives the registry.

  Perimeter narrowed, not widened.
