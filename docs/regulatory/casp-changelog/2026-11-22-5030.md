- **#5030**: two gaps in the hosted MCP's checkout-details handling (epic
  #4868), both of which could end in a payment that is funded and not
  delivered.

  **Gap 1 — `haven_submit` relayed the funding when the stored-challenge read
  failed.** `haven_submit` decides the merchant's checkout-details request from
  the challenge stored at authorize (`GET /x402/:id/payment-required`). That
  read is rate-limited (`moneyPathRateLimit`), so a 429 is realistic, and any
  failure read as "no request": the submit relayed the funding with no
  `additional_retry_headers` (EIP-3009) or with `retry_headers` lacking
  `X-Checkout-Details` (erc7710). The owner's decision (2026-11-22, option b)
  is that only a payment whose challenge asked for a REQUIRED detail stops on
  a failed read; every other payment proceeds as today, so the 2026-11-16
  decision that ordinary x402 payments are not impacted stands.

  What changed:
  - **`packages/backend/src/modules/x402/checkout-details-required.ts` (new)**
    and **`packages/backend/src/domain/machine-metadata.ts`**: the required
    checkout-details field names a challenge carried are read by the SDK's own
    parser and recorded on the intent at authorize as
    `machine_metadata.checkout_details_required_fields` (field NAMES only —
    the owner's values are not known at authorize and are never stored).
    `checkoutDetailsRequiredFieldsOf` reads them back.
  - **`packages/backend/src/modules/x402/delegation-authorize.ts`**: both
    delegation branches (EIP-3009 and erc7710) write the field.
  - **`packages/backend/src/modules/payments/agent-payment-status.ts`** and
    **`packages/backend/src/openapi/spec.ts`**: the payment status read
    (`GET /machine-payments/:id/status`, not rate-limited) serves the recorded
    names as `checkout_details_required_fields`, present only when the
    challenge asked for at least one. `packages/core/src/api-types.ts` is
    regenerated from the spec.
  - **`packages/sdk/src/types.ts`, `payment-mappers.ts`,
    `client-checkout-details.ts`**: the raw and mapped status types carry the
    field; `challenge_unreadable` joins `CheckoutDetailsRefusalReasonName` and
    `REASON_WORDS`; `checkoutDetailsChallengeUnreadableError` builds the
    refusal with a message that names no field (the read gave none).
  - **`packages/mcp-server/src/tools/support/checkout-details.ts`**:
    `storedChallengeForSubmit` returns the challenge plus the recorded required
    names, reading the payment status when the challenge read fails (a 404 and
    a 409 are answers, not failures, and read nothing);
    `checkoutDetailsBeforeSubmit` refuses as `challenge_unreadable` when the
    read failed and the record names a required detail.
  - **`packages/mcp-server/src/tools/state-direct-recovery.ts`**: the
    stored-challenge read moves INSIDE the `checkoutDetailsWhilePending` guard
    on both schemes, so a failed read is decided under the same
    pending-signature rule as every other before-spend refusal.

  **Gap 2 — the pay tool's 16 KB header-block estimate left out the caller's
  own headers.** `refuseUnshareableCheckoutDetails` called
  `estimatePaidHeaderBlockBytes` without `requestHeaders`, while the SDK counts
  them. A caller `Cookie` of 14.5 KB plus a required `receipt_email` passed the
  hosted check (2,429 bytes) and then answered 431 at the merchant (the SDK's
  estimate for the same request is 16,939 against a 16,384 ceiling).

  What changed:
  - **`packages/mcp-server/src/tools/support/checkout-details.ts`**:
    `refuseUnshareableCheckoutDetails` takes an optional `requestHeaders` and
    passes them to the SDK's estimate.
  - **`packages/mcp-server/src/tools/plain-http-x402.ts`**: `haven_pay_x402_quote`
    passes the caller's `headers` in both its payment_required and request
    modes. The catalog purchase tools have no caller headers and are unchanged.
    The submit's own estimate cannot know the agent's retry headers and stays a
    re-check, as before.

  Why the CASP perimeter is unaffected:
  - **No custody.** The hosted server still holds no key and signs nothing. The
    answer is unsigned data the owner saved and turned on for this agent.
  - **No widening.** The new record is a list of field NAMES derived from the
    merchant's untrusted challenge at authorize; it carries no owner value and
    grants no authority. The new refusal only stops a payment earlier than it
    would otherwise have been relayed; it never moves funds, changes an amount,
    a recipient or a signing step.
  - **Narrower, not wider.** Gap 1 fails closed for exactly the payments the
    owner named (a challenge that asked for a required detail) and leaves every
    other payment on today's path. Gap 2 refuses a payment the merchant would
    have answered 431 to, before any intent exists.
  - **Seller only, never stored or logged.** The owner's values still pass
    through the hosted server only in memory and are never stored, logged or
    merged into the echoed `extensions`.

  Tests:
  - `packages/mcp-server/src/tools/checkout-details-plain-http.test.ts`: on
    both schemes, a 503 and a 429 on the stored-challenge read with a recorded
    required detail refuse as `challenge_unreadable` before the funding relay
    (EIP-3009) and before the settlement child (erc7710), with a message that
    names no field; a failed read with no recorded required detail proceeds; a
    409 (a direct payment) and a 200 with no stored challenge proceed. The
    pre-existing "the stored challenge cannot be read: the submit proceeds as
    today" test is narrowed to the no-required-detail case, not deleted. The
    pay tool refuses `over_budget` before `POST /x402` with a 14.5 KB caller
    `Cookie` and a required `receipt_email`, in payment_required and request
    modes, and the same request without the cookie proceeds; the refusal is
    asserted to match the SDK's own `resolveCheckoutDetails` decision for the
    same request.
  - `packages/backend/src/routes/__tests__/x402-delegation.test.ts`: both
    delegation branches record `checkout_details_required_fields`, and a
    challenge that asks for nothing records an empty list.
  - `packages/backend/src/routes/__tests__/machine-payments.test.ts`: the
    status read serves the recorded names and omits the key when none were
    recorded, matching the OpenAPI spec.

  No mutation-testing run (prove-red cells) was performed for this slice. The
  tests pin the behaviour directly: the refusal is asserted on both schemes for
  both failure statuses, and the pay-tool refusal is asserted against the SDK's
  own decision for the same request.

  Perimeter unchanged.
