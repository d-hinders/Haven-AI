- **#5035**: a delegate sweep whose receipt wait timed out after broadcast was
  booked `failed` with no hash on the row, and could never be replayed.

  What was wrong:
  - The rail waited `provider.waitForTransaction(tx.hash, 1, 90_000)`. ethers
    6.16.0 **rejects** that wait on timeout with a `TIMEOUT` error carrying no
    hash, so the rail's `if (!receipt)` branch ("timeout is NOT failure") never
    ran and `finishRelayerSpend` was skipped — the relayer-spend row kept no
    hash.
  - The rejection reached `submitSweep`, which booked every non-budget error
    `failed` with no `tx_hash` and answered 502. A retry with the same nonce
    answered 409; a landed sweep showed in transaction history as an
    unattributed deposit; the hosted MCP client timed out at the SDK's 30 s
    default before the 90 s wait ended.
  - A lost answer to the broadcast itself (`broadcastSigned` throwing after the
    record was stamped `broadcast` with a hash known before the send) was booked
    the same wrong way.

  What changed:
  - The rail catches the wait's rejection (and a lost broadcast answer) and
    raises `SweepOutcomeUnknownError` carrying the hash. The relayer-spend hash
    is stamped BEFORE the wait, so a rejected wait still leaves it on the row.
  - The synchronous wait is 15 s, inside the SDK transport's 30 s budget, so the
    agent receives the typed answer instead of a client timeout.
  - `submitSweep` books the row under a NEW status, `outcome_unknown`, with the
    hash, and answers a non-2xx typed code (`sweep_outcome_unknown`) carrying
    it. `outcome_unknown` is deliberately not `submitted`: the six queries that
    read `ds.status = 'submitted'` as "landed" do not count it.
  - A new leader-gated confirmer job decides the real outcome from the token's
    `authorizationState(from, nonce)` — independent of which hash mined — marks
    the row `submitted` with the mined hash (following the bump worker's
    `replaced_by` chain, or the `AuthorizationUsed` log) and resolves the
    stranded-funds event; an authorization that expired unused is marked
    `failed`. Re-submitting the same authorization, or calling prepare, answers
    the current state instead of minting a second authorization.
  - The unlink guard (`HAS_OPEN_SWEEPS_FOR_ACCOUNT_SQL`) now treats an
    `outcome_unknown` sweep as open, so an account cannot be unlinked while a
    sweep to it may still land.

  Why the CASP perimeter is unaffected: the sweep still pays the user's own
  Haven account, the EIP-3009 nonce remains single-use on-chain (funds cannot
  move twice), the relayer is still only the gas payer and never a spender, and
  no key, signer, custody or authority surface moves. The change makes the
  booking honest about an outcome the chain had not yet decided, and adds a
  reader that decides it from chain state rather than from a hash. The
  double-spend path is unchanged: a second prepare is refused while one sweep
  is in flight, and a re-submit never broadcasts again.

  Mutation-tested: with the wait's rejection uncaught, the pinned rail test
  fails (the error is not `SweepOutcomeUnknownError` and carries no hash); with
  the pre-wait spend stamp removed, the "stamps the hash BEFORE the wait" test
  fails; with `outcome_unknown` added to the `submitted` readers, the
  transaction-history attribution test fails before the confirmer marks the row.

  Perimeter unchanged.
