- **#5061**: the merchant kit refuses Base mainnet at startup, in
  `@haven_ai/paywall-proxy` (`packages/paywall-proxy/src/config.ts`, the
  `OPEN_NETWORKS` gate and `closedNetworkProblem`; the comment in `chains.ts`;
  the README, `.env.example` and `docs/architecture/12-merchant-kit.md`). Owner
  decision 2026-11-23: the kit refuses Base mainnet in code until the
  regulatory review in #4888 allows it, and the refusal is removed on purpose
  at go-live.

  What it does:
  - `loadConfig` — the one entry point shared by startup (`main.ts`), `check`
    (`check.ts`) and `report-sale` (`report-sale.ts`) — now adds a problem for
    a network the chain table knows but this release is not open on:
    `NETWORK eip155:8453 (Base mainnet) is not open: the merchant kit runs on
    Base Sepolia only until the regulatory review in #4888 allows mainnet`.
    All three commands refuse with the same words, and nothing else needs its
    own gate.
  - The "must be one of" problem now lists only the open networks
    (`eip155:84532`), so it no longer offers `eip155:8453` as valid. For
    `eip155:8453` itself the refusal is emitted alone, not alongside it.
  - The chain facts stay. `eip155:8453` remains in `PROXY_CHAINS`, and
    `chains.test.ts` still pins its chain id and USDC address to core's
    registry. The chain is still resolved for a refused network, so the
    mainnet-only rules (`RPC_URL` required, seller details required with
    `VAT_RULE`) still report alongside the refusal — startup lists every
    problem at once.

  Why the perimeter is unaffected:
  - The change narrows which network the kit can settle on; it adds no route,
    key, scope, custody step or settlement path. A deployment already running
    `NETWORK=eip155:8453` stops starting on its next image pull. That is
    intended: it is the refusal the owner asked for, and it moves no money.
  - `PROXY_CHAINS` is unchanged, so the chain facts core's registry pins are
    unchanged. The gate is a startup refusal in `loadConfig`, not a change to
    what the proxy does once it starts.
  - The refusal names a network and an issue number. It carries no credential,
    no address and no secret, and `ConfigError` still never echoes a secret's
    value.
  - Money-path list: `packages/paywall-proxy/src/**` stays a control glob, by
    the owner decision on #4893.

  Pinned by tests: `config.test.ts` (the refusal word for word, with a name
  that says removing it is a go-live step; the "must be one of" list offering
  only `eip155:84532`; the `RPC_URL` and seller-detail rules asserting the full
  problem list with the refusal included), `check.test.ts` (the `settings` line
  fails with the refusal and checks 3–6 print `skipped (settings invalid)`),
  `report-sale.test.ts` (the command exits 1 with the refusal inside
  `ConfigError`'s "The proxy cannot start:" message), and `chains.test.ts`
  (unchanged: the mainnet chain facts still match core's registry). Prove-red:
  the six new or changed assertions fail against `origin/dev`'s `config.ts`
  and pass with the gate.

  Perimeter unchanged.
