- **#5069**: the demo merchant's HTTP payment gate now resolves a buy-tool call
  to its product through the product registry, and refuses a `tools/call` it
  does not know before the MCP server sees it.

  Before this change, the gate in `extractPaymentToolInfo` was a hand-kept
  switch over four tool names, separate from the tools `server.ts` registers. A
  buy tool registered without a matching branch was not gated: it got no HTTP
  402, and the call went straight to the tool's handler. The reporter's branch
  (`buy_philip`) showed this. Its handler went through `completePurchase`, and
  that function's no-payment branch answered with an in-band `isError`
  "payment required" result. So nothing was delivered unpaid, but the only
  thing stopping it was a convention inside the handler. An agent paying
  through x402 never saw a 402 to pay.

  What changed:
  - **`packages/demo-merchant-mcp/src/products.ts`**:
    - `productToolArgs` is an exhaustive `switch` over the product category. A
      new category is now a compile error, where before it silently resolved to
      `buy_cloud_storage`.
    - `productForToolCall(toolName, args)` finds the product a call selects
      from `PRODUCTS` through `productToolArgs`, the same derivation the tool
      schemas and test helpers use.
    - `paidToolNames()` lists every buy tool name the registry knows.
    - `FREE_TOOL_NAMES` is `{list_products}`.
  - **`packages/demo-merchant-mcp/src/http.ts`**:
    - `extractPaymentToolInfo` takes the product from `productForToolCall`.
      Each 402 `description` suffix comes from a per-category map holding the
      same four strings as before.
    - The new `ungatedToolCall` answers a `tools/call` naming neither a free
      tool nor a registry buy tool. The answer is HTTP 404 with JSON-RPC
      `-32602` "Tool <name> not found", the SDK's own unknown-tool wording,
      before any session or handler runs.

  Why the perimeter is unaffected:
  - **No new authority.** The change adds a refusal and moves the product
    lookup. It grants no new path to settlement. Price, receiving address,
    payment requirements, verification, settlement and the signing key are
    untouched: `handlePaymentGate` receives the same `PaymentToolInfo` for
    every existing product, with the same `productId`, `product` and
    description.
  - **Products the merchant does not offer are unchanged (#4851).** Their
    tools are not registered, and the gate still passes them through, so the
    SDK answers "unknown tool" as before. Arguments that select no product
    (`buy_vpn` with an unknown `plan`) still pass through to the tool's schema,
    which refuses them.
  - **Unknown tool names fail closed.** A tool name the registry does not know
    is now refused by the gate instead of reaching the MCP server. For a name
    no tool registers, the SDK answered "Tool <name> not found" anyway. The
    message is the same; only the HTTP status and the layer that answers
    differ.

  Tests:
  - `payment-gate-registry.test.ts`:
    - A buy tool registered on the server with no product (`buy_unpriced`, the
      #5069 shape) is refused with 404 and `-32602`, and its handler never runs.
      Removing the refusal turns this test red: mutation run on `edfe8bf2e`.
    - Registry buy tools still get a 402, and `list_products` is still served.
    - Every product resolves from its own buy-tool call.
    - A source scan asserts that every `server.tool('<name>'` registration in
      `server.ts`, including the flag-gated ones, is a free tool or a registry
      buy tool.
  - The package's existing 25 test files (492 tests) pass unchanged, including
    the #4850 characterization snapshot of every product's 402 and in-band
    refusal.
