- **#5084** — The hosted MCP purchase refuses a resource-address mismatch
  **before any money moves**, instead of funding a payment that completion then
  refuses. Found by the own-server MCP cold run of 2026-11-25 on Base Sepolia:
  a merchant's challenge named `mcp://tool/haiku` while its tool lived at
  `https://<host>/mcp`. On EIP-3009 Haven stored the challenge's address,
  funded the agent's delegate (0.001 USDC), and only then refused the
  completion for the mismatch; the value sat on the delegate until it was swept
  back.
  - **Pay / prepare** (`haven_pay_mcp_tool`, `haven_prepare_catalog_purchase`,
    EIP-3009 branch): the challenge's `resource.url` is compared with the
    discovered MCP endpoint before the budget pre-check and before any intent.
  - **Settle** (`haven_settle_mcp_tool`, both schemes): an explicit
    `merchant_url` is compared with the payment's stored resource address,
    read from the payment status, before the funding relay or the erc7710
    submit. A failed read refuses with nothing relayed (fail closed).
  - **Refusals only.** The comparison is completion's own (strict string
    equality), so nothing accepted today is refused, and no payment refused
    today is let through. No authority, custody, route, address or amount
    changes; no backend, SDK or migration change.
  - **Residual.** A payment funded through `haven_submit` and then completed
    with a different explicit `merchant_url` still meets the post-funding
    refusal: only an intent created before this change, or by
    `haven_pay_x402_quote` with an MCP challenge. Stated in
    `docs/architecture/04-x402-payment-sequence.md`. #5086 will bind the
    completion to the stored endpoint so an `mcp://tool/<name>` address can be
    paid.

  Perimeter unchanged.
